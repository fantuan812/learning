# 伤害与属性结算可运行证据

> 证据范围：本机可编译运行的 1 个测试 + 基准程序，**15 条断言全部通过**，含 P50/P95/P99 结算耗时；不涉及 UE GAS 运行时、网络与线上环境。按本仓库约定，`evidence/` 属维护基础设施，其 README 的 maturity 字段不参与知识成熟度门禁。

伤害结算是 Gameplay 里"数字最容易对不上"的地方：策划表、客户端表现、服务端结算、战斗日志四方任意一处顺序不同，玩家就会看到"打出的数字和掉的血不一样"。本目录把结算顺序与边界固化成断言，并给出单次结算的真实耗时。

## 问题

1. 属性修正器的求值顺序（Override / Add / Multiply）到底是什么？换插入顺序会不会改变结果？
2. 暴击、增伤、护甲、按类型抗性、受伤加成这五个乘区，谁先谁后？能否叠加成"减伤 100%"？
3. 护盾与血量谁先扣？护盾大于一次伤害时余额怎么算？过量伤害（overkill）要不要单独记？
4. 目标已死亡/免疫时，该次结算是否应当"整段拦截"（不消耗护盾、不改血量）？
5. 单次命中上限（per-hit cap）应该放在减伤之前还是之后？
6. DOT 在多跳与半跳（剩余时长不足一个间隔）时如何取整？
7. 相同随机种子重放，结算结果是否逐次一致（回放与帧同步的前提）？

## 假设

- 结算在服务端单线程内是**确定性**的：同一种子 + 同一输入 → 同一结果。
- 修正器语义：最后一个 Override 覆盖 base，Add 求和，Mul 连乘；三者对插入顺序不敏感（Add/Mul 交换机律）。
- 乘区顺序固定为：`基础 × 攻击属性 → 暴击 → 增伤 → 护甲 → 按类型抗性 → 受伤加成 → 单次上限 → 护盾 → 生命`。
- 护甲减伤采用 `armor / (armor + K)` 曲线，数学上恒小于 1。
- 真实伤害（true damage）跳过护甲，但仍受抗性/受伤加成/上限影响。

## 输入

- 公式断言：固定攻击力、护甲 100/900、抗性 50%、受伤加成 +25%、护盾 30/500、血量 40、上限 150 等构造用例。
- 重放：5 000 次伪随机命中（xorshift64，种子 777），每次命中前重置血量，累加结算哈希。
- 基准：500 轮 × 1 000 次命中 = 500 000 次完整结算（物理/魔法交替，护盾极大以保持每次工作量一致）。

## 结论

1. **乘区顺序必须写死在代码里，而不是靠"谁先调用谁先算"**。A1/A2 证明聚合语义可被精确定义且对插入顺序不敏感；D1–D5 证明五个乘区按固定顺序相乘时结果可被单值断言。
2. **护甲曲线天然免疫"减伤 100%"**：D2 显示即使护甲取到 10⁹，剩余伤害系数仍为正（`residualAtArmor1e9≈1e-7`）。用加法式减伤（`damage × (1 - armor%)`）则会在护甲堆叠后出现 0 伤害，是常见的数值事故来源。
3. **真伤必须显式跳过护甲**（D3），且要明确它是否仍受抗性与上限约束——这两条最容易被含糊处理。
4. **护盾必须先于血量结算，且不得为负**（D6/D7）：护盾大于伤害时余额保留（500 → 420），不会溢出扣血。
5. **过量必须单独记录**（D8）：血量向下取到 0，`overkill` 单独返回。战斗日志与击杀归属（最后一击/过量伤害统计）都依赖这个字段，混进 `toHp` 会让伤害统计虚高。
6. **死亡/免疫应整段拦截**（D9）：返回被拦截且不消耗护盾、不改血量；否则会出现"打尸体掉护盾"的诡异日志。
7. **单次上限放在减伤之后、护盾之前**（D10）。放在减伤之前会让"高减伤 + 低上限"的目标受到超过上限的伤害，放在护盾之后则等于上限失效。
8. **DOT 需要精确取整**（D12）：按 `floor(有效时长 / 间隔)` 计跳，剩余时长不足一跳时不结算但保留余量，避免"最后一跳丢失"或"多打一跳"。
9. **同种子可重放**（D13）：两次相同种子得到同一哈希，换种子则不同，满足回放/帧同步对确定性的基本要求。
10. **单次结算成本极低**：P50 ≈ 14 ns、P99 ≈ 17 ns（约 7.7 × 10⁷ 次/秒）。按 20 Hz Tick 计算，单 Tick 处理 1 万次结算约耗 0.14 ms，**结算本身通常不是性能瓶颈**；真正的开销在属性快照获取、范围查询与网络广播。

## 局限

- **不是 UE GAS**：未使用 `FGameplayEffectSpec`/`AttributeSet`/`GameplayCue`；属性捕获（snapshot）时机、PredictionKey 与网络复制的具体实现不在本证据范围。
- **单线程**：未覆盖并发结算、批量 AOE 的遍历顺序影响、服务端分帧。
- **公式为参考实现**：`armor/(armor+K)` 与乘区顺序是可辩护的工程选择，不代表某个具体项目的策划公式；接入时需按项目数值重新标定。
- **基准是纯逻辑上限**：护盾设为极大以消除分支差异，且完全不涉及内存分配、随机数质量、属性快照与日志；线上数字必然更高。
- **计时方法**：单次结算低于 `steady_clock` 分辨率（约 100 ns），因此采用"分批计时再归一"的方式取每跳成本；结果存在运行间波动，`results/` 保存的是某一次的真实输出。
- 未覆盖：持续伤害的来源归属与叠加策略、伤害反弹、致死护盾、伤害上限与减伤上限的组合、跨服转移中的伤害重放。
