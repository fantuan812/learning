# 工作日志：2026-08-18

## 主题：服务器代码规则 —— 功能正确性优先、扣道具安全与 GDB 断点

### 本次确认的总原则

服务器代码的优先级固定为：

> **功能性正确性 > 可读性 > 速度**

- 先保证业务结果、资源安全和异常边界正确，再考虑代码是否足够清晰，最后才是局部性能优化。
- 不能为了少几次判断、少一次拷贝或追求微小耗时收益，牺牲扣道具、发奖、状态落库等核心逻辑的正确性。
- 性能优化必须建立在可复现的 Profiling / Benchmark 证据上；没有证据时不以“可能更快”为理由复杂化实现。

### 扣道具与发奖的安全口径

对于“消耗道具后发放奖励”的服务器流程，安全目标是**阻止任何可能由异常路径造成的刷道具或重复发奖**。当扣除与发奖之间出现无法确认的中间状态时，宁愿出现“道具已扣除但奖励未发放”，也不能为了补偿方便而留下可被重试利用的刷道具窗口，让风险最终由玩家买单。

#### 推荐处理顺序

1. 先做请求、玩家、配置、道具和目标状态的判空与合法性校验；任何空指针或无效输入都直接返回，不能进入扣除逻辑。
2. 校验玩家拥有的道具数量、活动/任务状态、重复请求标识和奖励配置；校验不通过时不修改资源。
3. 完成扣道具，并确认扣除结果；扣除失败直接返回，不继续发奖。
4. 扣除成功后只允许发放一次奖励；奖励发放失败或结果不确定时，禁止盲目重试、重复扣除或自动回滚出可刷窗口，应记录完整流水并进入可审计的补发/人工核对流程。
5. 对重复请求、超时重试、并发请求和进程重启分别验证幂等性；任何“重试即可多领一次”的路径都视为缺陷。

这条规则不是鼓励忽略玩家权益，而是明确服务器侧的风险边界：**资源扣除可以保守失败，奖励发放绝不能产生可复制的成功结果**。若后续具备经验证的事务、流水或幂等补偿机制，可以在不降低防刷能力的前提下改善“扣除成功但未到账”的体验。

### 代码组织规则：尽量扁平化

- 采用 Guard Clause：先判空、判非法、判状态不满足，立即 `return`；通过所有前置条件后再进入正确逻辑。
- 把异常路径放在前面，把主流程保持在函数末尾，避免多层 `if/else` 嵌套和“正常逻辑被错误分支包住”。
- 判空应覆盖请求对象、玩家对象、背包/道具组件、配置表、奖励配置、目标实体和持久化上下文；判空后不要继续访问其成员。
- 扣道具、发奖、幂等记录和日志应有清晰的阶段边界，变量命名直接表达业务含义，不用隐式副作用串联多个动作。
- 不把关键校验、扣除和发奖压缩成难以断点的长表达式；可读性是发现资源安全问题的前提。
- 速度问题在确认功能正确后再处理，并保留优化前后的测量数据与回归用例。

### GDB 断点调试约定

服务器相关问题优先使用 GDB 断点还原真实控制流，不只依赖日志猜测。调试构建需要保留符号信息，并在不改变业务时序的前提下复现请求。

建议断点位置：

1. 请求入口：确认同一请求是否被调用多次，以及请求参数和玩家身份。
2. 所有判空/非法状态返回前：确认实际命中了哪一个保护分支。
3. 扣道具前后：观察扣除数量、返回值、背包余额和扣除流水是否一致。
4. 发奖前与发奖返回处：确认奖励只进入一次，区分明确失败与未知结果。
5. 幂等键写入、持久化回调和重试入口：验证超时、并发和重启后的控制流。

常用检查动作（按实际函数和变量替换）：

```gdb
break <request_entry>
break <deduct_item>
break <grant_reward>
condition <breakpoint-number> <request-id-condition>
bt
frame <n>
info locals
print <item-count-or-idempotency-key>
next
continue
```

断点验收重点不是“程序走到了发奖函数”，而是确认：输入为空时及时返回、扣除失败不发奖、扣除成功后奖励最多一次、异常重试不会再次消耗或重复发放，以及不确定状态会留下可追踪证据。

### Code Review / 自测清单

| 检查项 | 通过标准 |
| --- | --- |
| 判空与非法输入 | 所有前置对象和配置先校验，失败立即返回 |
| 扣道具前校验 | 数量、资格、状态、重复请求均已确认 |
| 扣除结果 | 明确判断成功/失败，不以调用返回即成功 |
| 发奖次数 | 单请求、重试、并发下均最多一次 |
| 异常状态 | 奖励未知时不盲目重试，保留流水与告警 |
| 代码结构 | 主流程扁平，无不必要的深层嵌套 |
| 性能优化 | 有 Profiling / Benchmark 证据，且不改变正确性 |
| 调试证据 | 使用 GDB 断点核对关键分支和资源变化 |

### 结论

服务器实现先守住功能正确性和资源安全，再追求可读性与速度。涉及扣道具的流程默认采用“防刷优先、失败可审计”的保守策略；代码采用“先判空 return、后处理正确逻辑”的扁平结构；问题定位使用 GDB 在扣除、发奖、幂等和持久化边界设置断点验证。
