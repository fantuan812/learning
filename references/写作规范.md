# 知识库写作与验收规范

> 适用于知识正文、源码分析、案例、实验和维护文档。事实边界来自该文实际核对的来源、版本与环境；不能把另一台机器、一次局部实验或旧教程的结论当作当前全文事实。
> 知识成熟度：L2（写作控制面；规则与现行检查器静态核对，不代表库内正文已完成语义验收）。

## 0. 元数据、身份与可移植链接

新建或修改的非保留名 Markdown 必须含非空 `type` frontmatter；`index.md` / `log.md` 依 [OKF 兼容规范](OKF-兼容规范.md) 的保留名规则处理。2026-08-20 的 390/390 迁移统计是历史快照，当前范围以实际检查输出为准。推荐起点：

```yaml
---
type: Concept
title: "主题"
description: "要解释的问题与适用边界"
tags: []
status: draft
verified: []
maturity: L0
updated: YYYY-MM-DD
sources: []
---
```

- `type` 采用 [OKF profile](../.kb/okf-profile.yaml) 的词汇；未知类型和未知字段应保留，不能为整理而抹除。
- 引用外部事实须有真实来源；L2 及以上注明实际核对的位置、版本或修订日期。`sources` 每项含 `resource`；`resource` 本身表示条目的主要外部资源（适用时）。链接存在不证明内容支持结论。
- `maturity` 表示证据深度；`verified` 是 `{by, at}` 验证事件或其列表，两者不能自动互推。工具或 Agent 的审核不能记成 `human:` 事件；只有可核实的人类审核才能使用对应 actor。没有实际事件就保持 `verified: []`。
- `generated.by` / `generated.at` 只记录真实生成者和时间，不等于复核。`status` / `stale_after` 描述生命周期。
- 稳定身份、当前路径、主责域和关系由 [.kb/knowledge-map.json](../.kb/knowledge-map.json) 维护；可选 `canonical` 必须与它一致。一个概念只有一个 Canonical，导航不复制权威正文；manifest 是机械快照，taxonomy 仅作兼容指针。
- 标准相对 Markdown 链接必须独立可用，wikilink 只能辅助。兼容 Obsidian 不改变来源、身份和验证事件的职责。

## 1. 按读者问题组织教学

长度、标题数、代码行数和固定步骤数都不是质量指标。短文可以完整，长文也可能只堆术语。先明确读者要解释、选择、实现或排查什么，再选择足够的结构；不要求每篇照抄同一套章节。

一篇声称完成的教学正文应让读者能回答：

1. **为什么需要它**：具体问题、目标、前置知识、输入和约束是什么？不用它会在哪里失败？
2. **为什么这样工作**：把关键步骤连成因果链，说明状态、数据或资源如何变化，哪些不变量必须保持，后续结果为何随之发生。术语列表、调用栈和长代码本身不是解释。
3. **怎样复现结论**：给最小正确例及能暴露关键误区的反例，写明输入、操作、预期输出和判定方式；解释差异来自哪个机制。纯概念可用可手算的追踪或推导，代码则区分伪代码、节选与实际运行程序。
4. **何时不成立**：失败路径、边界条件、代价与取舍；哪些前提变化会使结论失效，何时停止重试或换方案。不能把示例常量写成普遍性能预算。
5. **根据什么知道**：原始来源、版本、定位、核对日期，以及观察、推导、假设和未验证项之间的区别。

按内容选择重点：

| 内容 | 必须讲清的核心 | 不应冒充的结论 |
| --- | --- | --- |
| 概念 / 原理 | 定义、机制、可追踪的正确例与反例、成立条件 | 只因解释通顺就宣称实现或性能已验证 |
| 源码分析 | 入口 → 状态/数据改变 → 下游结果；分支、生命周期、线程/网络边界 | 只贴代码、符号或路径就宣称理解完整调用链 |
| 操作 / 案例 | 依赖、可执行步骤、预期结果、失败排查、恢复或停止条件 | 把准备好的命令说成已经执行 |
| 实验 / Benchmark | 假设、实现、输入/负载、正负控制、测量方法、原始结果和可重复命令 | 把模型、计数或合成时延说成端到端实测或生产容量 |
| README / 路线图 | 清楚的职责、导航、依赖顺序与当前状态 | 将目录覆盖率当作内容正确性或完成度 |

流程、状态机或数据流复杂时可用 Mermaid，图下保留文字解释。纵向案例从真实入口追到目标结果，并覆盖相关失败路径；按案例选择必要阶段，不强塞输入、RPC、伤害、回放等无关步骤。阅读入口为[端到端案例路线](../00_Index/学习路线/端到端案例.md)。

## 2. 整篇成熟度与局部证据

`maturity` 和正文顶部的“知识成熟度”应一致，并明确标定范围。等级衡量本文主要承诺获得了多深的证据，不是写作长度或自信程度。

| 等级 | 含义 | 必要证据 |
| --- | --- | --- |
| L0 | 收集或规划 | 主题、来源入口和未完成范围；不冒充成文或已核对 |
| L1 | 能解释概念 | 连贯原理、正确例/反例、适用条件与失败边界 |
| L2 | 已核对原始资料或源码 | 可定位的官方/原始来源，实际核对的版本与范围；静态核对不包含运行结论 |
| L3 | 主要实现已运行 | 最小实现、依赖与命令、实际输入/输出和运行环境；仅提供可运行方案不足以称已运行 |
| L4 | 主要承诺有测试或基准证据 | 真实断言/负向控制或测量方法、原始结果、复现入口与覆盖限制；不要求不相关的 P99 指标 |
| L5 | 真实项目实践与复盘 | 可定位的项目上下文、实际生产证据、失败方案、后果与复盘；不得以本地模拟代替 |

- 全文不能直接取最高子项等级。若只有 Open List 或一个缓存实验获得 L4 证据，而业务链仍是静态分析，全文按主要承诺可支持的等级标定，局部单列“对象、输入、环境、证据、未覆盖项”。
- 若正文真正以该局部问题为完整主题，其全文等级仍可由完整匹配的局部实验支持；不要机械取最小等级，也不要为了绿色检查自动升降等级。
- 修订发现既有误标时，明确记录原标定、证据缺口、调整理由和仍成立的范围。保留原始日志，不倒填不存在的结果。
- 来源覆盖矩阵描述读过/核对过什么；成熟度描述证据深度；`verified` 描述谁在何时做过验证。三者相互独立。

检查器只做最低证据入口 lint：出现 Evidence、P99、测试矩阵或工作日志等词，不证明存在有效实验，更不证明整篇达到 L3/L4/L5。真实覆盖和教学正确性必须逐项独立审查。

## 3. 版本、环境与证据范围

每篇版本敏感的正文写明自己的实际基准。UE 文档从可访问 checkout 的 `Engine/Build/Build.version` 或可核实的官方版本页读取；C++、协议、算法、工具链等使用对应标准、论文或实际工具输出，不套用 UE 模板。

以下是填写合同，尖括号是待替换内容，不是运行事实：

- 版本基准 / 知识基线：`<标准版本、源码revision、依赖版本或原始资料修订>`
- 适用范围：`<问题、输入前提、平台、编辑器/运行时、客户端/服务端或依赖>`
- 来源定位：`<官方链接、论文节号、仓库相对路径和符号>`
- 最后更新：`<实际日期及本次修改范围>`
- 证据范围：`<实际静态核对、实际运行和仅推导的各自范围>`
- 未验证项：`<缺少的环境/依赖/实验；对结论的限制与下一验证入口>`

记录实验时还给出工具版本、构建选项、种子、输入规模/分布、计时口径和原始结果位置。报告失败的命令及退出码，不能删掉失败样本后只报成功；计时必须覆盖所声称的工作，汇总必须能追溯到原始观察。

“未运行 UE / PIE / 弱网 / 压测”是必要边界，不是禁词。未访问源码时如实区分官方文档核对、历史路径引用和待核对项。不得复制固定安装路径、CL、分支或其他机器的环境为本轮观察。

## 4. 源码定位与检查边界

- 在允许访问的实际环境中用 `Test-Path`、`rg --files`、`rg -n` 或等价命令核对文件、符号和版本。不能下载未经授权的私有源码，也不能修改源码树来让引用成立。
- 优先记录 `Engine/Source/...` 等可移植定位；绝对路径只作必要且非私密的环境说明。用行号时同时给路径、revision/版本与定位命令；不能靠行号替代语义解释。
- 节选保留解释所需上下文，标明省略边界，不悄悄改名；伪代码和示意代码不能冒充逐字源码或已编译实现。长代码应拆解说明关键状态变化，避免代码量掩盖推理缺口。
- 未完成项可以明示“待补充”“学习骨架”或“未核对”，但不能同时宣称该范围已完成。路径模板、占位命令和 TODO 不构成证据；“预留”作为 API/协议概念不应被禁词规则误判。
- `check_repo.ps1 -UeInstallRoot <实际checkout根>` 可选执行 `Engine/...` 路径存在性检查。它拒绝越界和重解析点；不提供根时明确报告未运行，显式提供无效根或缺失文件时失败。外部/历史绝对路径不能悄悄重映射成当前机器的已核对来源。
- 路径检查支持行内代码中的定位，以及无空白的裸 `Engine/...` 或原生绝对路径；含空格路径用行内代码包围，其他语法不在提取覆盖范围。零条已检查不代表验证通过。文件存在只证明该位置存在；不证明版本一致、符号存在、代码行为正确或已运行。源码路径检查结果与教学审查、运行验证分别报告。

## 5. 版本差异与废弃 API

以文章真实研究对象为当前基准，不强制统一到某个 UE 版本。旧版本可能正是迁移文章或维护项目的目标，必须写明前后版本、变化点、替代方案和保留场景；不能把跨多个版本的语义当作无条件兼容。

引用废弃 API 时说明其状态、适用范围和有来源支持的迁移方向。官方链接使用现行门禁接受的稳定入口，历史版本事实注明其历史身份并给对应的现行资料；现有领域门禁仍拒绝 `docs.unrealengine.com` 旧域名，本批不豁免该检查。找不到精确页面时标明待核对，不把总页当作具体结论已获支持。

## 6. 编码、链接与导航

- Markdown 使用 UTF-8 无 BOM，无 U+FFFD 替换字符；代码围栏闭合。
- 相对链接使用 `/`，目标在仓库内且真实存在，不通过越界路径或符号链接绕过范围。外部资料使用真实稳定 URL，来源不能只藏在代码块内。
- 每个知识目录有 README；清单和上下级导航与实际文件同步。正文清单使用标准 Markdown 链接，不能仅写反引号文件名。
- 新增、删除、改名后更新相应导航；由单一整合者最后重建 manifest。知识图负责身份与关系，导航和来源不另建 Canonical。
- 书籍、PDF、图片、原始笔记和工作日志保持完整；不能以重写教学正文为由覆盖原始资料或历史运行结果。

## 7. 交付前验收

```powershell
pwsh -NoProfile -File ./scripts/check_repo.ps1 -Root (Get-Location).Path
pwsh -NoProfile -File ./scripts/check_okf.ps1 -Root (Get-Location).Path -Mode Changed
pwsh -NoProfile -File ./scripts/test_quality_evidence.ps1
git diff --check
```

按变更范围继续执行[脚本门禁](../scripts/README.md)和现行 CI 的完整检查；新增回归不能取代既有 Canonical、DS、迁移、编码或路径安全门禁。

独立审稿至少复核：主要问题是否得到因果解释，正反例能否按给定信息复现，失败边界是否真实，来源是否支持具体结论，运行记录是否与输入/环境相符，整篇等级是否偷用了局部证据，以及改动是否保全原文和原始资料。规则文档本身不证明全库已完成这些审查。

受保护来源若存在经明确授权保留的格式欠账，只能按精确路径、整字节指纹、缺陷类型及位置基线逐项报告 `KNOWN_SOURCE_DEFECT`。基线固定在受审控制文件与脚本指纹中，不允许通配、自动刷新或以此豁免其他错误；改字节、新缺陷、孤儿和重复条目均失败。它保留原件并公开欠账，不表示消除了缺陷。

交付报告分别列出机械检查结果、内容审查范围、已运行实验、既有缺陷及未运行项。`WARN` 需要具体原因和影响，不能笼统当作通过；源码核对未运行尤其不能写成“所有证据已验证”。提交和发布遵循 [AGENTS](../AGENTS.md) 及[独立审核门禁](agent协作与发布规则.md)，执行者不自称独立审查者。
