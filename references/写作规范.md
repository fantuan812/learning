# 知识库写作与验收规范

> 适用于当前仓库根 `$RepoRoot` 下的知识正文、分类 README、源码分析与维护文档。规范以本机 UE 5.8 源码和当前官方文档为事实边界，不以记忆或旧教程代替核对。

> 知识成熟度：L2（写作控制面；OKF v0.2 映射具备官方来源与静态检查）。

## 0. OKF 元数据与 Obsidian 兼容

仓库当前 profile 范围已完成 OKF v0.2 迁移（2026-08-20：390/390 受检文档、2 篇操作性排除）。新建或本次修改的非 `index.md` / `log.md` Markdown 必须在首行加入 YAML frontmatter，且至少包含非空 `type`；未来导入 legacy 内容按 hybrid 批次审查后纳入 Strict。推荐模板：

```yaml
---
type: Concept
title: "主题"
description: "一句话说明问题和边界。"
tags: []
status: draft
verified: []
maturity: L0
updated: YYYY-MM-DD
sources: []
---
```

- `type` 使用 [.kb/okf-profile.yaml](../.kb/okf-profile.yaml) 的稳定词汇；未知类型允许保留，但必须在评审中说明。
- `maturity` 仍按 L0~L5 衡量证据深度；`verified` 是一个 `{by, at}` 验证事件或事件列表。消费者按 actor 推导 unverified / machine-confirmed / human-reviewed trust tier，两者不得自动互推。
- `resource` 用于条目所描述的主要外部资源（适用时）；L2 及以上或正文引用外部事实时，在 `sources` 中记录带 `resource` 的来源对象。
- `generated.by` / `generated.at` 只在内容确由工具生成且生成者、时间可核实时填写；它不等于人工复核。`status` / `stale_after` 表达生命周期和复核期限。
- 无法核实来源就保持 `verified: []`，不要填充虚假来源，也不要因存在 `generated` 自动提升成熟度或验证状态。
- `canonical` 是本库唯一权威位置/身份锚点；分类仍由 taxonomy 管理，manifest 仍是当前文件快照，三者不互相替代。
- 关系默认使用标准相对 Markdown 链接。可以额外使用 Obsidian 能力，但 `[[wikilink]]` 不能成为唯一入口。
- 详细规则见 [OKF 兼容规范](OKF-兼容规范.md) 与 [Obsidian 协作指南](Obsidian协作指南.md)。

## 1. 正文结构

正文通常不少于 300 行，推荐保持以下顺序；短文、实验记录、路线图和 README 可按用途豁免，但必须在标题或元数据中说明定位。

1. 概述：问题、适用场景、读者和版本边界。
2. 核心概念：术语中英对照、职责表、输入/输出或生命周期。
3. 原理详解：数据结构、调用链、线程/网络边界和失败路径。
4. 示例：最小可运行 C++、蓝图操作、伪代码或可复现实验；示例须标注“节选”或“示意”。
5. 最佳实践：工程取舍、性能、可维护性、平台/网络限制。
6. FAQ：至少覆盖版本差异、常见误用和排查入口。
7. 关联阅读：使用可验证的相对链接连接同分类或相邻分类。

涉及执行流程、状态机、线程关系、数据流或决策树时，优先使用 Mermaid；图下必须有文字解释，不能让图成为唯一信息来源。

纵向链路文章（`系统实战/`）按 `系统实战/README.md` 的 15 步模板组织：输入 → 预测 → RPC → 服务器校验 → 目标筛选 → 执行 → 冲突 → 伤害 → 同步 → 表现 → 回放 → 异常 → 单测 → 压测 → 性能预算；每步必须给出涉及模块/文件、协议或调用链、边界与失败路径、可验证入口。

## 2. 知识成熟度（L0~L5）

每篇正文顶部元数据标注 `知识成熟度`，区分"看过"与"真正做过"，避免用篇数冒充能力。

| 等级 | 含义 | 证据要求 |
| --- | --- | --- |
| L0 | 收集到主题 | 仅有主题占位或来源收集，尚未成文 |
| L1 | 能解释概念 | 正文完整解释原理、边界与适用场景 |
| L2 | 有源码/官方资料验证 | 带本机源码路径或官方链接，且已实际核对（源码文章须满足第 4 节规则） |
| L3 | 有可运行 Demo | 有可运行的最小实现、实验脚本或项目 Demo，可给出运行方式 |
| L4 | 有 Benchmark / Test | 有测试用例或性能数据（P50/P95/P99、CPU、内存、带宽），数据与复现步骤同文或指向工作日志 |
| L5 | 有真实项目实践与复盘 | 可指向工作日志/线上问题复盘/生产数据，含失败方案与结论 |

标定规则：

- 只能按证据标定，不允许仅凭"理解得差不多"标注 L4/L5；L4/L5 必须可指向证据位置。
- 同一主题不同子项成熟度不同时，取最高证据等级并注明范围，例如 `L3（Open List 部分）/ L2（整体）`。
- 既有文章不强制回填；凡被修订、被纳入系统实战链路的文章，修订时补标。
- 知识成熟度与源码覆盖矩阵（第 7 节）互相独立：矩阵描述"是否读过源码"，成熟度描述"掌握到什么程度"。

## 3. UE5.8 版本元数据

每篇新 UE 文档至少包含以下信息；源码分析和版本敏感的修订文档应完整填写：

```markdown
> 版本基准：UE 5.8.0（本机 `Engine/Build/Build.version`：CL 55116800，分支 `++UE5+Release-5.8`）。
> 源码依据：`C:\Program Files\Epic Games\UE_5.8\Engine\...` 下的实际文件；以本机 5.8 源码为准。
> 适用范围：说明桌面/移动、编辑器/运行时、客户端/服务端或插件依赖。
> 兼容性边界：UE 4.27/早期 UE5 仅作为历史兼容性或迁移说明，不作为当前基准。
> 官方参考：[UE 5.8 官方文档](https://dev.epicgames.com/documentation/en-us/unreal-engine)。
> 最后更新：YYYY-MM-DD（说明本次修改范围）。
> 知识成熟度：L0~L5 之一（规则见第 2 节；例如 L2 表示源码/官方资料已核对，L4 表示有测试或性能数据）。
```

若精确官方页面 slug 不能确认，使用稳定的 UE 5.8 总页、API 模块页或功能总页，并在正文标注“待核对”；禁止保留旧版 `docs.unrealengine.com/<旧版本>` 入口。

## 4. 源码事实规则

- 先用 `Test-Path`、`rg --files`、`rg -n` 或等价命令确认路径、符号和文件名，再写入正文。
- 路径统一以本机 `C:\Program Files\Epic Games\UE_5.8\Engine` 为根；文中可使用 `Engine/Source/...` 的相对展示形式，但必须给出可定位的模块/文件。
- 类名、函数名、宏名、CVar 和模块名必须来自真实源码或官方 UE5.8 API；无法核对的内容写入路线图，不伪造实现细节。
- 代码块标注 `节选`、`示意` 或 `伪代码`。节选不得悄悄改名；示意不得冒充可直接编译代码。
- 行号会随本机构建/分支变化，引用行号时同时给文件路径和验证命令。
- Release Notes 的新特性只在能对应官方页面或本机源码的情况下写成“已覆盖”；否则列为 P1/P2 待补。

## 5. 兼容性与废弃 API

当前基准必须显式写成 UE 5.8。若文章包含 UE 4.27、UE5.0、UE5.3 等版本：

- 用“历史兼容性”“迁移差异”“旧项目注意事项”标题隔离；
- 说明当前 5.8 的替代 API/模块/路径；
- 不把 `UE 4.27 ~ UE 5.x` 作为无条件适用范围；
- 对 `deprecated` 的系统给出迁移目标、保留场景和本机证据。

例如 `MovieSceneCapture` 只能标为兼容/旧管线，UE5.8 的新项目应优先评估 Movie Render Graph（MRG）；未完成源码核对时在 roadmap 标注状态。

## 6. Markdown、链接与编码

- 全部 `.md` 使用 UTF-8 无 BOM；禁止实际出现替换字符（Unicode U+FFFD）。
- 相对链接使用 `/` 分隔，并以真实文件为目标；README 文件清单必须是 `[显示名](相对路径)`。
- 链接到章节锚点时，目标标题应稳定；外链只使用 `https://dev.epicgames.com/documentation/...` 等当前官方入口。
- 代码块必须成对闭合；Mermaid 使用 fenced code block，图中节点文字包含标点时使用引号。
- 不在正文中写入本机私密信息、构建产物或引擎安装目录之外的绝对路径；UE 源码证据可写只读安装根路径。

## 7. README 同步

- 每个知识目录有 README，README 的文件清单与实际文件一一对应。
- 新增/删除/改名正文时，同步更新当前目录 README、上级分类 README（必要时根 README）。
- 清单中的 `README.md` 可以链接自身，但正文文件不能只用反引号展示。
- 覆盖矩阵区分“概念层已有”“源码深度已完成”“简述/待补”“规划”；不能把同名概念文章当作源码分析完成。

## 8. 交付前检查

```powershell
pwsh -NoProfile -File .\scripts\check_repo.ps1 -Root (Get-Location).Path
pwsh -NoProfile -File .\scripts\check_okf.ps1 -Root (Get-Location).Path -Mode Changed
git status --short
git diff --check
```

必须确认：无 BOM、无替换字符、代码围栏闭合、内部 Markdown 文件链接存在、分类 README 齐全、README 文件清单同步。`WARN` 可以保留的情况只能是正文短于 300 行的日志/README/路线图或尚未逐条语义复核的历史内容，并在交付报告中列出。
