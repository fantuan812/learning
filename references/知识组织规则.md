# 知识组织规则

> 当前分类与稳定身份以[知识图](../.kb/knowledge-map.json)为准，[八域知识体系](../知识/README.md)是读者视图。旧目录名只用于历史引用、必要兼容入口与质量规则，不是新内容落点；一个旧分类可对应多个当前职责域，不能整根替换。书籍与工作日志原件保留，来源视图通过链接接入主题。

> 知识成熟度：L2。依据 [AGENTS.md](../AGENTS.md)，在归类、创建主题、去重或结构重构时加载。
> 角色与发布流程见 [Agent 协作与发布规则](agent协作与发布规则.md)。本页只负责知识组织。

# Phase 2 — Semantic Analysis

Semantic analysis can be delegated to `kb_analyzer`.

Determine for each relevant document:

- domain
- subdomain
- topic
- knowledge type
- summary
- key concepts
- project specificity
- related concepts

Knowledge types include:

- Concept
- Principle
- Architecture
- Mechanism
- Implementation
- Tutorial
- Troubleshooting
- BestPractice
- Comparison
- CaseStudy
- Reference
- Research
- Project
- Decision
- Experience
- Interview

Separate:

    Observed Fact
    Inference
    Recommendation

Never present an inference as a fact.

# Phase 3 — Knowledge vs Project Boundary

For documents being analyzed, record the knowledge boundary as one of:

    universal
    project
    mixed
    temporary

Reusable canonical knowledge belongs under `知识/`, in the responsible domain recorded by `.kb/knowledge-map.json`. Read [知识库架构](知识库架构.md) and `.kb/architecture.json` for responsibility boundaries; use graph identities, lexical aliases and decision records when choosing a canonical document.

`universal`, `project`, `mixed` and `temporary` describe scope, not mandatory directory names. Project-specific material stays in its existing authorized source or evidence context unless an explicit structural plan chooses another destination. A reusable case may live in its responsible knowledge domain without losing project constraints. Unclassified material stays in place while a review-queue item records the decision needed; do not recreate retired scaffolds.

Mixed documents may remain intact when project context is needed to explain the concept. Split only when independent reusable content and project constraints justify distinct canonical documents; preserve evidence and links. Source notes and research records may stay under their source/evidence layer but do not become another authoritative copy of an extracted concept.

Use links instead of duplicate copies.

# Phase 4 — Taxonomy

Before creating a new folder or topic, read:

    .kb/knowledge-map.json
    .kb/architecture.json
    .kb/aliases.yaml
    .kb/decisions.md

`.kb/taxonomy.yaml` is a compatibility pointer, not a second domain inventory.

Use kb_architect for significant taxonomy decisions.

Default taxonomy model:

    Domain
      → Subdomain
        → Topic

Prefer 2–4 levels.

Do not create a directory merely because one document exists.

Create a directory when at least one condition holds:

1. There are at least 3 related knowledge units.
2. The topic is expected to grow.
3. The topic represents a clearly independent domain.

Otherwise prefer a Markdown document.

---

# Taxonomy Stability Rule

Do not redesign the taxonomy for small incremental updates.

A taxonomy redesign is justified only when:

- a domain has grown substantially
- many documents cannot be classified cleanly
- duplicated categories have appeared
- the current hierarchy consistently creates ambiguity

Prefer incremental evolution.

---

# Canonical Knowledge Rule

Each knowledge concept has exactly one Canonical Location.

Other locations may contain:

- links
- aliases
- MOC references

Never maintain two authoritative copies of the same knowledge.

---

# Source Is Not Taxonomy

Never use information source as the primary knowledge taxonomy.

Avoid structures such as:

    ChatGPT/
    Claude/
    PDFs/
    Websites/
    2026/
    LearningNotes/

Instead classify by knowledge domain.

Source information belongs in metadata.

---

# Duplicate Handling

Before creating new knowledge:

1. Search existing topics.
2. Search aliases.
3. Search semantically related documents.
4. Decide whether the new information should:

    Extend
    Merge
    Create
    Archive

Duplicate levels:

    exact
    semantic
    overlapping

Exact duplicates:

    DeleteCandidate

Semantic duplicates:

    Merge

Overlapping documents:

    Keep + Refactor
or
    Split + Merge

Never permanently delete automatically. A proposed archival move must appear in the allowlisted structural plan; unresolved candidates remain in place.

An authorized archival operation must name its destination in the structural plan. Unresolved candidates remain at their current paths with a review-queue entry; no fixed archive scaffold is required.

---

# Naming

Prefer concise conceptual names:

    AOI.md
    ECS.md
    Skill-System.md
    Buff-Conflict-Resolution.md
    A-Star.md

Avoid:

    notes1.md
    new-document.md
    today-learning.md
    chatgpt-summary.md

---

# Knowledge Unit Granularity

Avoid giant documents covering unrelated topics.

Also avoid extreme atomic-note fragmentation.

Bad:

    Buff-ID.md
    Buff-Time.md
    Buff-Start.md
    Buff-End.md

Better:

    Buff-System.md
    Buff-Lifecycle.md
    Buff-Stacking-and-Conflict.md

A knowledge unit should be independently understandable and semantically complete.

---

# AI Conversation Processing

Raw AI conversations are not canonical knowledge.

Process:

    Raw Conversation
        ↓
    extract problems
        ↓
    extract conclusions
        ↓
    extract principles
        ↓
    extract trade-offs
        ↓
    extract implementation knowledge
        ↓
    merge into existing knowledge

Keep raw conversations in their existing authorized source context. Any preservation move requires an explicit destination and provenance in the scoped plan; extraction must not replace the original.

Do not build taxonomy around AI provider names.

# Troubleshooting Knowledge

Convert debugging history into reusable engineering knowledge.

Preferred structure:

    # Problem

    ## Symptoms

    ## Environment

    ## Root Cause

    ## Diagnosis

    ## Solution

    ## Why It Works

    ## Prevention

    ## Related Topics

# Research Knowledge

Do not organize research only by PDF files.

Within an existing responsible domain or approved source collection, use topic overviews and links to methods, papers, experiments and ideas as needed. This is a content pattern, not a requirement to create a top-level `Research/` directory.

Important methods from papers should be converted into reusable Method Knowledge where appropriate.

---

# Architecture Decisions

Important engineering decisions should use ADR-style documents:

    # ADR: Decision

    ## Context
    ## Problem
    ## Options
    ## Decision
    ## Reasons
    ## Trade-offs
    ## Consequences
    ## Related Systems

---

# Knowledge Relationships

Graph relationships use the schema supported by `scripts/validate_knowledge.py`:

    prerequisite    prerequisite → dependent knowledge
    implemented_by  primary concept → implementation
    applied_in      primary concept → application case
    verified_by     claim or method → experiment
    related         ordinary association
    reads           reading relationship

Reference existing document IDs. Richer relationships can be explained with ordinary prose and Markdown links; do not silently extend the graph enum or assign a second canonical identity.

Use links instead of content duplication.

---

# MOC

MOC means Map of Content.

Use MOCs for navigation, not large bodies of knowledge.

Possible hierarchy:

    Global MOC
    Domain MOC
    Topic MOC

Do not create an MOC for every document.

---

# Confidence

Use confidence for uncertain classification:

    >= 0.90 strong
    0.75–0.89 likely
    0.50–0.74 needs_review
    < 0.50 uncertain

Any structural action with confidence below 0.75 must enter:

    .kb/review-queue.md

Do not automatically perform it.

---

# Decision Records

Significant structural decisions must be appended to:

    .kb/decisions.md

Each decision should contain:

    Decision ID
    Subject
    Options
    Decision
    Reason
    Confidence
    Affected files

Before revisiting an existing structural decision, check this file.

Do not repeatedly redesign previously settled taxonomy without new evidence.

---

# Operation modes and planning

Ordinary edits stay within their assigned files; do not initiate a taxonomy rebuild for a new document. For supplied raw-material processing: inventory → analyze → search canonical topics → compare overlap → Extend / Merge / Create → link → update graph and navigation where required.

For a significant topic or full architecture rebuild: Inventory → Semantic Analysis → Domain Analysis → Taxonomy Proposal → Duplicate Analysis → Migration Plan → Audit → Execution → Final Audit. Use full rebuild only when requested or clearly justified by structural inconsistency. Do not begin by moving files.

Before structural changes, maintain `.kb/plans/current.md` with goal, scope, current state, findings, proposed taxonomy, exact file allowlist and owners, move mappings, merge/split preservation evidence, review items, risks, audit, progress and final validation. Record each operation as Current → Target, Action, Confidence and Reason. Valid actions include Keep, Move, Rename, Merge, Split, Archive, Create, Extend, CreateMOC, CreateLink and UpdateMetadata. Existing user authorization covers the agreed scope; a plan is not an extra user approval gate.

Final audit checks canonical uniqueness, document boundaries, aliases, taxonomy, links, MOCs, decision records, source/target presence and information preservation. A failed or absent review is not success. See the collaboration policy for execution and publication gates.
