## 概述

NavMesh 解决的是连续空间到多边形图的工程化表达，它不替代动态实体的碰撞约束，也不保证一条多边形通道在任意速度和半径下都安全。
本篇以 Recast/Detour 官方仓库的公开模块边界和源码流程为证据，覆盖烘焙流程、关键参数、多边形邻接、Detour 查询与漏斗、动态 Tile/Obstacle 边界和 Crowd 分层。
本篇只把公开仓库中的模块名、公开源码流程和可观察 API 当作证据，不推断任何未公开引擎的内部实现。

## 一、NavMesh 工程

### 1.1 Recast/Detour 的公开模块边界

Recast 官方仓库把 Recast 定位为 NavMesh 生成模块。

Detour 负责运行时 NavMesh 数据、路径查找和 NavMesh 查询。

DetourTileCache 面向 Tile 缓存、流式和局部动态更新。

DetourCrowd 面向代理移动、碰撞避免和群体模拟。

这个模块划分足以支持工程分层。

它不能证明任意引擎的导航系统内部就是同样的对象、线程或内存布局。

因此本文只把公开仓库中的模块名、公开源码流程和可观察 API 当作证据。

不会把 UE 的私有导航代理、任务调度、网络复制或烘焙管线写成 Recast 官方行为。

### 1.2 烘焙流程

Recast README 描述的公开流程可以抽象为以下阶段。

第一，将输入三角网格栅格化到体素。

第二，过滤代理无法行走的体素。

第三，把可行走体素划分为区域。

第四，将区域重新三角化为 NavMesh 多边形。

工程实现还要固定输入几何的坐标系、单位、法线方向和版本。

烘焙输入必须带源资产哈希。

参数必须带 agent profile 标识。

输出必须带库版本、编译配置和生成时间。

不要只保存一份 navmesh.bin 而不保存生成参数。

缺少参数时，后续无法解释为什么同一地图的多边形数变了。

### 1.3 关键烘焙参数

| 参数 | 作用 | 过小的风险 | 过大的风险 |
| --- | --- | --- | --- |
| cell size | 水平栅格分辨率 | 内存和烘焙时间上升 | 窄通道消失 |
| cell height | 垂直栅格分辨率 | 高度判断不稳定 | 小台阶被吞掉 |
| agent radius | 障碍膨胀与可走边界 | 发生擦碰 | 可行区域过少 |
| agent height | 头部空间过滤 | 矮门误通过 | 可走区域过少 |
| max climb | 可跨越台阶高度 | 角色被切断 | 穿越不该跨的台阶 |
| max slope | 可行走坡度 | 可走坡变少 | 产生滑坡或越界 |
| region min size | 过滤小区域 | 噪声增多 | 小平台消失 |
| region merge size | 合并相邻区域 | 多边形碎片化 | 拓扑细节丢失 |
| max edge length | 多边形边界细分 | 顶点和查询增多 | 曲线边近似粗 |
| max verts per poly | 单多边形顶点上限 | 图规模变大 | 几何近似误差变大 |
| detail sample distance | 细节高度采样 | 路径高度近似粗 | 烘焙成本增加 |
| tile size | 流式与局部重烘焙单位 | Tile 数多、边界多 | 更新范围过大 |

参数不是越精细越好。

先用游戏单位标定最小门宽、最小可站立平台和可跨台阶。

再选择能保留这些特征的 cell size 与 cell height。

最后用固定地图测量烘焙时间、输出大小、查询扩展节点和路径质量。

### 1.4 多边形图与邻接

NavMesh 的节点通常是可行走多边形，而不是原始三角形的每个顶点。

相邻多边形通过公共边、门户或外部连接表达。

多边形图的边代价可以采用门户中心距离、穿越距离或策略加权距离。

如果同一多边形有多个出口，出口位置会影响漏斗路径。

查询时应保存 polyRef 序列和每个 polyRef 对应的 Tile 版本。

不要把多边形索引当作永久 ID。

Tile 重载、NavMesh 重建或对象池复用可能改变引用含义。

polyRef 的位布局和生命周期应以锁定版本源码和 API 为准。

跨 Tile 的邻接必须有测试。

测试应覆盖 Tile 正边界、角点、缺失邻居、异步加载中和旧 Tile 与新 Tile 混合的情况。

### 1.5 Detour 查询与漏斗

Detour 查询可以产生一条多边形走廊。

走廊不是最终的角色轨迹。

漏斗算法把连续门户的左右边界收紧，选择必要的拐点。

它可以减少沿每个多边形中心移动带来的锯齿。

漏斗的输入必须保持门户顺序正确。

门户方向错误会把左边界和右边界交换。

退化门户会导致三点方向判断接近零。

因此漏斗实现要有方向容差和退化回退。

常见回退是保留当前拐点，缩短走廊，或改走门户中心。

不要在漏斗后直接认为路径无碰撞。

仍需对平滑后的线段执行半径膨胀后的可行性检查。

还要考虑角色高度、层级切换、门的方向限制和动态障碍。

### 1.6 NavMesh 烘焙与运行时数据流

~~~mermaid
flowchart TD
    Geometry["源三角网格<br/>资产哈希"] --> Raster["体素栅格化"]
    Raster --> Filter["高度/坡度/半径过滤"]
    Filter --> Region["区域划分与合并"]
    Region --> Poly["多边形生成"]
    Poly --> Tile["Tile 序列化"]
    Tile --> Runtime["Detour 运行时查询"]
    Runtime --> Corridor["多边形走廊"]
    Corridor --> Funnel["漏斗与路径验证"]
    Tile --> Cache["Tile/Obstacle 动态缓存"]
    Cache --> Runtime
~~~

每个产物都应绑定来源版本。

源几何哈希用于发现资产变化。

烘焙参数哈希用于发现 profile 变化。

库版本用于解释第三方实现升级。

Tile 坐标与层级用于查找局部影响范围。

导航数据版本用于服务端和回放之间的兼容检查。

### 1.7 动态 Tile 的边界

动态 Tile 适合把局部地形变化限制在一个可重建区域。

Tile 边界不是无成本的。

一条跨边界的通道可能需要两侧同时更新。

邻接的连接点可能因为局部重烘焙移动。

旧查询拿着旧 polyRef 时，不能继续当作新数据使用。

流式加载期间要区分未加载、加载中、加载完成和加载失败。

把未加载区域当成不可达可能造成暂时绕路。

把未加载区域当成可达可能造成越界或空引用。

服务端应选择一种显式策略并记录。

适合回放的做法是把 Tile 状态事件和完成帧写入输入日志。

### 1.8 动态 Obstacle 的边界

DetourTileCache 可以作为动态障碍和 Tile 缓存的公开代码参考。

它不代表所有项目都必须使用同一更新策略。

动态障碍的轮廓必须先被离散化或体素化。

小障碍可能在 cell size 下消失。

大障碍可能污染整个 Tile。

障碍在 Tile 边界附近时，影响范围要包含安全扩张。

障碍移除时，不能只删除障碍对象而不重新验证受影响多边形。

更新队列需要去重。

同一帧内对同一 Tile 的多次添加、移动和删除应折叠为可重放的最终事件序列。

不要在渲染线程直接修改服务端 NavMesh 数据。

运行时更新应通过版本化命令进入导航线程或固定阶段。

### 1.9 Crowd 与全局路径的边界

Recast 官方仓库把 DetourCrowd 单列为代理移动、碰撞避免和群体模拟模块。

这说明群体移动是运行时层，而不是烘焙阶段的全局路径替代。

工程上可以把每个代理的全局路径点变成偏好速度。

再把邻居和静态边界提供给局部避障。

若局部避障连续无法前进，应触发卡住检测和全局路径修复。

不能只增加避障权重而不改变目标通道。

### 1.10 NavMesh 验证清单

| 检查 | 方法 | 报告字段 |
| --- | --- | --- |
| 输入可复现 | 记录源资产哈希 | geometryHash |
| 参数可复现 | 序列化 profile | agentProfileHash |
| Tile 完整 | 检查坐标、层、大小 | tileCount、missingTiles |
| 邻接完整 | 跨 Tile 双向查询 | brokenLinks |
| 多边形合法 | 面积、法线、顶点数 | degeneratePolys |
| 高度连续 | 走廊采样与台阶检查 | heightDiscontinuities |
| 半径安全 | 线段/胶囊查询 | clearanceFailures |
| 动态更新 | 添加、移动、移除回放 | obstacleUpdateFailures |
| 旧引用安全 | 版本不匹配拒绝访问 | staleRefRejects |

## 术语速查

以下速查表只做术语口径对齐，详细行为边界见上文各小节；表中不给出任何性能数字，性能结论必须以本项目固定场景实测为准。

| 术语 | 含义 | 工程要点 |
| --- | --- | --- |
| Recast | NavMesh 生成模块：栅格化、过滤、区域划分、多边形化 | 生成结果只依赖输入几何与参数，输入带哈希即可复现 |
| Detour | 运行时 NavMesh 数据、路径查找与查询 | 查询结果依赖有效的 polyRef，Tile 重载后引用语义变化 |
| Region | 可行走体素的分区 | region 参数直接影响多边形数量与拓扑 |
| Contour | 区域边界的轮廓数据 | 是生成中间产物，一般不进运行时 |
| PolyMesh | 导航多边形网格 | 多边形顶点数受 max verts per poly 约束 |
| DetailMesh | 多边形表面高度细节网格 | 采样密度影响路径高度近似精度与烘焙成本 |
| Tile | 局部导航数据单元 | 流式加载与局部更新以 Tile 为单位，跨 Tile 邻接要双向校验 |
| Off-Mesh Link | 连接非连续移动的显式链接（跳跃、梯子、滑索等） | 两端必须落在可行走多边形上，方向与代价要验证 |
| Crowd | 代理移动、碰撞避免与群体模拟模块 | 只负责局部运动，全局路径由查询层给出 |
| polyRef | 运行时指向多边形与 Tile 的引用 | 生命周期随 Tile 重载变化，不能当永久 ID 持久化 |
| 体素栅格化 | 把三角网格转换为体素 | cell size 决定分辨率、内存与烘焙时间 |
| 漏斗算法 | 在走廊内收紧门户边界求出拐点 | 门户顺序与退化处理决定结果正确性 |

速查表用于评审与值班对齐口径；数值与性能结论以项目固定场景实测为准。

## 常见反模式

以下反模式按现象、后果与正确做法对照，适合在烘焙流水线评审时逐条核对。

| 反模式 | 现象 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 水密网格失败 | 输入几何有开放边、重叠面或细小裂缝 | 体素化后可行走区域断裂，出现孤立平台或寻路失败 | 烘焙前做闭合性与重叠校验，校验结果进流水线 |
| 参数直接套用示例 | demo 参数不按本项目角色与关卡标定 | 窄门消失、角色擦碰、可行区域过少 | 按最小门宽、台阶与 agent 尺寸标定并序列化 profile |
| 动态障碍误用 | 高频移动实体注册为 Obstacle 或整 Tile 重建 | Tile 反复重建、查询抖动、路径抖动 | 静态障碍进烘焙，高频移动体走 Crowd 局部避障 |
| 单一 Mesh 服务多种尺寸角色 | 不同 agent radius/height 共用同一 NavMesh | 小角色擦碰、大角色穿缝或走不通 | 按 agent profile 分 Mesh 或多层导航 |
| Off-Mesh Link 两端悬空 | 链接端点未落在可行走多边形上 | 跳跃或爬梯后悬空、穿模 | 烘焙后校验端点归属、方向与目标可达性 |
| 开发机与服务器几何漂移 | 本地烘焙产物直接上线，源几何版本不固定 | 运行时路径与烘焙结果不一致，回放对不上 | 几何哈希与参数哈希进产物元数据，统一烘焙或校验 |
| 全局路径每帧重算 | 每帧全量 findPath，不做走廊缓存 | CPU 浪费，路径在轻微扰动下抖动 | 缓存走廊并按失效标记重算，增量搜索参考 `02-动态寻路LPA与DStarLite.md` |

## 典型故障案例

以下两个案例按工程中反复出现的失败形态整理为示意复盘，不代表任何具体项目的事故记录。

### 案例一：寻路失败与绕远

背景：某关卡在两块平台之间配置了 Off-Mesh Link，烘焙输出正常（示意场景）。

经过：
- 上线后部分角色无法到达目标点，日志显示 findPath 返回空或走廊明显绕远。
- 排查发现链接一端没有落在可行走多边形上，端点悬空。
- 另有一处窄门因 cell size 偏大在体素化阶段消失，形成断点。

根因：
- 烘焙校验缺失：没有做网格闭合性检查，也没有校验 Off-Mesh Link 端点归属。
- 参数未按最小门宽标定，窄通道在栅格化阶段就被过滤。

对策：
- 把几何闭合性、链接端点归属与最小门宽采样纳入烘焙校验。
- 对失败场景建立固定地图回归用例，参数变更后自动重放。

### 案例二：动态 Tile 抖动

背景：把大量高频移动实体注册为动态障碍，触发频繁的 Tile 重建（示意形态）。

经过：
- 实体移动时障碍更新频繁，同一 Tile 一帧内多次重建。
- 跨 Tile 通道时而可达时而不可达，路径在帧间抖动。
- 旧查询持有失效 polyRef，出现引用失效与路径抖动的组合现象。

根因：
- 动态与静态边界混淆：高频移动体应走 Crowd 局部避障，而不是更新 Tile。
- 更新没有按频率分层，逐实体触发重建，缺少批次合并。

对策：
- 按静态地形、低频大块变化、高频移动体三层划分更新路径。
- 低频地形变化合并成批次处理，查询侧对失效 polyRef 显式拒绝并降级。
