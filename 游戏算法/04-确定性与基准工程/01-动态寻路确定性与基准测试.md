## 概述

动态寻路的难点不是把 A* 换成一个更响亮的算法名。

难点是地图、单位、障碍、时间步长和服务端预算同时变化时，仍然能回答四个问题。

第一，当前返回的路径是否在本次快照上有效。

第二，局部障碍变化后，是否只重算了受影响的部分。

第三，多个平台回放同一输入时，是否能得到同一决策状态。

第四，当预算不足或几何退化时，系统是否能安全降级并留下证据。

本文将全局路径、局部运动和在线工程分成三层。

全局层负责从起点区域到目标区域的可达性和拓扑方向。

局部层负责短时间窗内的速度选择、邻居避让和转向舒适度。

在线层负责快照版本、确定性、调度、限流、回放、哈希和指标。

这三层可以组合，但不能互相冒充。

D* Lite 或 LPA* 的增量优势来自对已有搜索信息的复用。

它们并不意味着所有动态地图都比一次性 A* 更快。

如果障碍变化接近全图、启发式不一致、图结构频繁重建，增量维护可能反而增加管理成本。

NavMesh 解决的是连续空间到多边形图的工程化表达。

它不替代动态实体的碰撞约束，也不保证一条多边形通道在任意速度和半径下都安全。

RVO/ORCA 解决的是速度空间里的短时碰撞避免。

它需要邻居查询、预测时间窗和相互让行等假设。

它不是全局寻路，也不是死锁的自动证明器。

确定性工程更像一条证据链。

输入快照、随机种子、固定时间步、排序规则和状态哈希共同决定回放能否复现。

单独把随机数换成固定种子，不能消除浮点运算、容器遍历和线程调度造成的差异。

基准工程则把这些边界变成固定场景、固定指标和可审阅报告。

没有固定地图、障碍密度、单位数和目标分布，性能数字无法比较。

没有失败率、尾延迟和回放一致性，平均耗时也无法代表线上风险。

## 核心概念

| 概念 | 英文 | 解决的问题 | 不能承诺的事情 |
| --- | --- | --- | --- |
| A* | A-star | 在静态加权图上按启发式搜索路径 | 不承诺动态障碍下无需重规划 |
| LPA* | Lifelong Planning A* | 复用多次搜索的 g 与 rhs 值 | 不承诺变化越多越快 |
| D* Lite | Dynamic A* Lite | 以反向搜索和 key 调整支持移动起点/边代价变化 | 不承诺全图拓扑改变时仍保持低成本 |
| 一致性 | Consistency | 判断节点当前值是否满足局部 Bellman 条件 | 不等同于浮点平台完全一致 |
| NavMesh | Navigation Mesh | 用可行走多边形表达连续空间 | 不等同于碰撞世界的完整副本 |
| 门 | Portal | 两个相邻多边形之间的公共边或可通行连接 | 不保证全局路径平滑 |
| 漏斗算法 | Funnel / String Pulling | 在多边形通道内收紧左右边界得到拐点 | 不处理通道已因动态障碍失效的情况 |
| Tile | Tiled NavMesh | 将大地图切成可流式和可局部重烘焙的块 | 不保证跨 Tile 更新无缝 |
| 速度障碍 | Velocity Obstacle | 描述给定时间窗内会导致碰撞的相对速度集合 | 不解决长期拥堵和全局绕行 |
| ORCA | Optimal Reciprocal Collision Avoidance | 在局部半平面约束中选择可行速度 | 依赖相互承担避让责任的模型假设 |
| Steering | Steering Behaviors | 把目标、路径和避障转成加速度/速度意图 | 不等同于离散路径规划 |
| 固定点 | Fixed-point | 用整数尺度表达关键状态和比较 | 不能自动消除错误的单位换算 |
| 状态哈希 | State Hash | 检测回放或多端状态分叉 | 哈希一致不等于实现逻辑全部正确 |
| 基准门禁 | Benchmark Gate | 以阈值阻止性能或一致性回归 | 不替代线上真实流量观察 |

## 一、动态寻路

### 1.1 先定义动态变化

“动态地图”不是一个足够精确的输入。

至少要把变化分成边代价变化、边可达性变化、节点属性变化和图结构变化。

边代价变化表示道路还存在，但通行成本、危险度或拥堵权重改变。

边可达性变化表示道路暂时关闭或重新开放。

节点属性变化表示某个格子、三角形或多边形的占用、阵营或权限改变。

图结构变化表示导航数据本身被替换、Tile 被卸载或连通关系被重建。

不同变化对应不同的增量维护成本。

| 变化类型 | 例子 | 可复用的信息 | 典型失效边界 |
| --- | --- | --- | --- |
| 小范围边代价变化 | 某条路临时变危险 | 受影响边附近的 g/rhs | 成本传播跨越大量节点 |
| 小范围封路 | 一扇门关闭 | 受影响局部的前驱/后继 | 关键割边导致整条路径失效 |
| 移动障碍 | 单位占据短时格子 | 仅当障碍映射到稳定图边时 | 障碍连续移动导致每帧图更新 |
| Tile 替换 | 局部地形加载新版本 | 未变化 Tile 的搜索值 | Tile 边界连接或 polyRef 改变 |
| 全图重烘焙 | 地形或代理半径改变 | 通常很少 | 图节点 ID 与邻接整体变化 |
| 目标移动 | 追击目标改变位置 | 反向搜索的局部缓存 | 目标高速跨区域或频繁换层 |

工程上应先为变化分配稳定的 changeId。

changeId 需要能映射到地图版本、Tile、边或多边形。

没有映射关系时，增量算法无法知道应该修复哪些依赖。

### 1.2 LPA* 的核心状态

LPA*（Lifelong Planning A*）把一次搜索过程中每个节点的当前估计 g 与一步前瞻值 rhs 分开保存。

对节点 u，rhs 可以表示为所有前驱 v 的 g(v) 加边代价 c(v,u) 的最小值。

起点的 rhs 通常设为零，其余节点初始为无穷大。

一致节点满足 g(u) 等于 rhs(u)。

过一致节点通常表示 g(u) 大于 rhs(u)，需要向下修复。

欠一致节点通常表示 g(u) 小于 rhs(u)，需要向上撤销或重新传播。

这种分离让旧搜索结果可以在边代价变化后保留下来。

它也带来了维护队列、重复条目和 key 失效等工程成本。

推荐显式保存节点版本或使用可比较的 key。

不要依赖优先队列支持任意删除，除非已经测量过其内存与延迟。

一种稳妥做法是允许重复入队。

弹出时重新计算当前 key。

如果弹出的 key 不是节点当前 key，就丢弃过期条目。

~~~mermaid
stateDiagram-v2
    [*] --> 一致
    一致 --> 过一致: rhs 下降或边变便宜
    一致 --> 欠一致: g 被外部更新或边变昂贵
    过一致 --> 一致: 传播最小 rhs
    欠一致 --> 一致: 重新扫描前驱/后继
    过一致 --> 欠一致: 同一批次多次变化
~~~

### 1.3 D* Lite 的增量前提

D* Lite 通常以目标为根反向维护搜索值，并允许起点移动。

起点移动时，key 中的 km 会累计启发式距离变化。

这样可以复用过去从目标反向建立的搜索信息。

要让复用有意义，至少需要以下前提。

第一，图的节点和边有稳定身份。

第二，变化能够枚举受影响的边或节点。

第三，边代价是可比较的，并且没有因为未记录的外部状态偷偷变化。

第四，启发式满足所选算法需要的条件。

第五，搜索队列和节点值的更新顺序可观察、可测试。

第六，地图快照在一次 ComputeShortestPath 过程中不能被并发修改。

第七，使用的 cost model 与实际验证一致，例如对角线代价不能和几何距离定义冲突。

第八，起点与目标必须能映射到当前图版本中的有效节点。

如果任一前提不成立，应把查询标记为需要全量重建或回退到 A*。

“有动态障碍”本身不是使用 D* Lite 的充分理由。

如果每个单位都把其他单位作为每帧硬障碍写入全局图，变化规模通常与单位数成正比。

更常见的工程分层是静态 NavMesh 加局部避障，少量关键门、桥或地形事件才进入增量全局图。

### 1.4 一致性与开放列表

开放列表不是“看起来最小的候选集合”这么简单。

在增量算法里，它还承载待修复节点的优先级和旧值过滤。

每个队列项至少应能反查节点、key 和生成版本。

比较 key 时要先比较第一关键字，再比较第二关键字，最后比较稳定的节点 ID。

稳定的节点 ID 可以消除相同 key 下的容器顺序差异。

如果 key 是浮点数，不能用原始相等判断“同一个 key”。

更好的做法是 key 中保存定点或量化后的整数成本。

若必须用浮点，比较时要定义绝对容差和相对容差。

容差不应被写成全局神奇常数。

它应与地图单位、最大路径长度和累计操作次数有关。

节点弹出时应执行如下检查。

先取得节点当前 key。

再比较队列项 key 是否落后。

若队列项 key 更旧，重新插入当前 key 后跳过该项。

若节点过一致，执行向下传播。

若节点欠一致，先将 g 置为无穷，再重新评估自身和受影响邻居。

每个批次记录弹出次数、重复条目数和最大队列长度。

这些指标能区分算法退化与单纯地图变大。

### 1.5 D* Lite 伪代码示意

下面的代码是表达状态流的伪代码，不绑定某个库的 API。

~~~text
Initialize():
    for u in graph:
        g[u] = INF
        rhs[u] = INF
    rhs[goal] = 0
    open.push(goal, CalculateKey(goal))

UpdateVertex(u):
    if u != goal:
        rhs[u] = min(g[p] + cost(p, u) for p in predecessors(u))
    open.remove_or_leave_stale(u)
    if g[u] != rhs[u]:
        open.push(u, CalculateKey(u))

ComputeShortestPath():
    while open.top_key() < CalculateKey(start)
          or rhs[start] != g[start]:
        item = open.pop()
        if item.key < CalculateKey(item.node):
            open.push(item.node, CalculateKey(item.node))
            continue
        if g[item.node] > rhs[item.node]:
            g[item.node] = rhs[item.node]
            for s in successors(item.node):
                UpdateVertex(s)
        else:
            g[item.node] = INF
            UpdateVertex(item.node)
            for s in successors(item.node):
                UpdateVertex(s)
~~~

实际实现还需要记录地图版本、变化批次、节点代价版本和预算。

当预算耗尽时，不要返回一个未标记的半条路径。

应返回状态、已扩展节点数、剩余队列规模和可用旧路径。

服务端可以继续沿用上一条仍经验证的路径。

也可以进入停靠、短时直线或安全点策略。

但该策略必须与“全局路径成功”区分。

### 1.6 动态障碍的三种映射

动态障碍可以映射为硬阻塞、软代价或局部邻居。

硬阻塞适用于门、落石、地形断裂等会改变全局可达性的事件。

软代价适用于拥堵、危险区域或策略偏好。

局部邻居适用于其他移动单位、短时相遇和队形避让。

不要把所有移动单位都写进全局图。

否则每个单位移动都会触发边变更、邻居重算和路径缓存失效。

一个实用判定表如下。

| 障碍对象 | 全局图处理 | 局部处理 | 需要回放记录 |
| --- | --- | --- | --- |
| 关闭的门 | 改变门两侧连接或代价 | 近门减速 | 门状态事件与版本 |
| 固定炮塔攻击范围 | 可选软代价层 | 规避即时射线 | 危险场版本 |
| 另一名 NPC | 通常不写入 | 邻居查询和 ORCA | 该帧可见邻居快照或可重建输入 |
| 临时箱子 | 小地图可重算 | 近距离碰撞 | 放置/移除事件 |
| 服务器未确认的客户端障碍 | 不进入权威图 | 客户端表现层预测 | 客户端输入，不作为权威障碍 |

动态障碍半径必须包含代理自身半径和安全缓冲。

如果一个半径为 r 的单位在几何上绕开障碍，配置空间中的障碍边界应扩张近似 r。

NavMesh 烘焙时的 agent radius、运行时的碰撞半径和局部避障半径必须有同一套单位说明。

### 1.7 失效边界与回退

增量重规划可能因为以下原因失效。

地图 Tile 被卸载，导致节点引用失效。

多边形重烘焙后 polyRef 改变，旧路径无法解释。

动态障碍跨越多个 Tile，变化批次扩大到全图。

边代价出现负值或 NaN，破坏最短路假设。

启发式与真实移动代价不再相容。

起点进入未加载区域。

路径缓存的地图版本早于当前权威版本。

开放列表达到内存上限。

重规划预算耗尽且上一条路径已被碰撞验证为失效。

此时要有明确的回退层级。

第一级是复用旧路径中仍通过验证的前缀。

第二级是限定半径或限定节点数的局部 A*。

第三级是当前 Tile 内的直线或局部可见点。

第四级是停靠、安全点或请求异步完整重算。

每次回退都写入 failureReason。

不要把“没有路径”“尚未完成”“预算耗尽”和“数据版本冲突”都编码成同一个空数组。

### 1.8 不要声称所有地图都优于 A*

D* Lite/LPA* 的优势通常出现在多次查询共享图、变化局部、节点身份稳定且前次搜索已充分展开的场景。

一次性查询、图很小、障碍变化很大或启发式很强时，A* 可能更简单也更快。

如果使用二叉堆，静态 A* 的典型搜索成本常写作 O((V+E) log V)，但这不是所有实现的实测延迟。

网格邻接、重复入队、启发式权重和路径平滑会改变常数。

增量算法还要支付保存 g/rhs、变化通知、队列重复项和版本检查的成本。

选型应使用相同地图、相同起终点、相同成本函数和相同停止条件进行对照。

至少比较以下五类场景。

静态单次查询。

静态多次相同起终点查询。

局部门状态变化。

高频移动障碍变化。

整图导航数据替换。

报告中同时给出 A*、LPA*、D* Lite 的扩展节点、墙钟时间和失败率。

### 1.9 动态寻路验收表

| 验收项 | 通过条件 | 失败动作 |
| --- | --- | --- |
| 快照一致 | 一次查询只读一个导航版本 | 记录版本冲突并重试 |
| key 顺序 | 相同输入在所有平台排序一致 | 改用量化 key 和节点 ID |
| 变化映射 | 每个变化可映射到节点/边/Tile | 禁用增量复用 |
| 预算 | 查询有节点数和微秒双预算 | 走回退层级 |
| 路径合法 | 每段通过几何和版本验证 | 截断到最后合法点 |
| 失败可解释 | failureReason 可统计 | 禁止静默返回空路径 |
| 回放可重建 | 只依赖已记录输入 | 扩充输入日志 |
| 全量回退 | 可在版本冲突时重建 | 标记高优先级缺陷 |

## 二、NavMesh 工程

### 2.1 Recast/Detour 的公开模块边界

Recast 官方仓库把 Recast 定位为 NavMesh 生成模块。

Detour 负责运行时 NavMesh 数据、路径查找和 NavMesh 查询。

DetourTileCache 面向 Tile 缓存、流式和局部动态更新。

DetourCrowd 面向代理移动、碰撞避免和群体模拟。

这个模块划分足以支持工程分层。

它不能证明任意引擎的导航系统内部就是同样的对象、线程或内存布局。

因此本文只把公开仓库中的模块名、公开源码流程和可观察 API 当作证据。

不会把 UE 的私有导航代理、任务调度、网络复制或烘焙管线写成 Recast 官方行为。

### 2.2 烘焙流程

Recast README 描述的公开流程可以抽象为以下阶段。

第一，将输入三角网格栅格化到体素。

第二，过滤代理无法行走的体素。

第三，把可行走体素划分为区域。

第四，将区域重新三角化为 NavMesh 多边形。

工程实现还要固定输入几何的坐标系、单位、法线方向和版本。

烘焙输入必须带源资产哈希。

参数必须带 agent profile 标识。

输出必须带库版本、编译配置和生成时间。

不要只保存一份 navmesh.bin 而不保存生成参数。

缺少参数时，后续无法解释为什么同一地图的多边形数变了。

### 2.3 关键烘焙参数

| 参数 | 作用 | 过小的风险 | 过大的风险 |
| --- | --- | --- | --- |
| cell size | 水平栅格分辨率 | 内存和烘焙时间上升 | 窄通道消失 |
| cell height | 垂直栅格分辨率 | 高度判断不稳定 | 小台阶被吞掉 |
| agent radius | 障碍膨胀与可走边界 | 发生擦碰 | 可行区域过少 |
| agent height | 头部空间过滤 | 矮门误通过 | 可走区域过少 |
| max climb | 可跨越台阶高度 | 角色被切断 | 穿越不该跨的台阶 |
| max slope | 可行走坡度 | 可走坡变少 | 产生滑坡或越界 |
| region min size | 过滤小区域 | 噪声增多 | 小平台消失 |
| region merge size | 合并相邻区域 | 多边形碎片化 | 拓扑细节丢失 |
| max edge length | 多边形边界细分 | 顶点和查询增多 | 曲线边近似粗 |
| max verts per poly | 单多边形顶点上限 | 图规模变大 | 几何近似误差变大 |
| detail sample distance | 细节高度采样 | 路径高度近似粗 | 烘焙成本增加 |
| tile size | 流式与局部重烘焙单位 | Tile 数多、边界多 | 更新范围过大 |

参数不是越精细越好。

先用游戏单位标定最小门宽、最小可站立平台和可跨台阶。

再选择能保留这些特征的 cell size 与 cell height。

最后用固定地图测量烘焙时间、输出大小、查询扩展节点和路径质量。

### 2.4 多边形图与邻接

NavMesh 的节点通常是可行走多边形，而不是原始三角形的每个顶点。

相邻多边形通过公共边、门户或外部连接表达。

多边形图的边代价可以采用门户中心距离、穿越距离或策略加权距离。

如果同一多边形有多个出口，出口位置会影响漏斗路径。

查询时应保存 polyRef 序列和每个 polyRef 对应的 Tile 版本。

不要把多边形索引当作永久 ID。

Tile 重载、NavMesh 重建或对象池复用可能改变引用含义。

polyRef 的位布局和生命周期应以锁定版本源码和 API 为准。

跨 Tile 的邻接必须有测试。

测试应覆盖 Tile 正边界、角点、缺失邻居、异步加载中和旧 Tile 与新 Tile 混合的情况。

### 2.5 Detour 查询与漏斗

Detour 查询可以产生一条多边形走廊。

走廊不是最终的角色轨迹。

漏斗算法把连续门户的左右边界收紧，选择必要的拐点。

它可以减少沿每个多边形中心移动带来的锯齿。

漏斗的输入必须保持门户顺序正确。

门户方向错误会把左边界和右边界交换。

退化门户会导致三点方向判断接近零。

因此漏斗实现要有方向容差和退化回退。

常见回退是保留当前拐点，缩短走廊，或改走门户中心。

不要在漏斗后直接认为路径无碰撞。

仍需对平滑后的线段执行半径膨胀后的可行性检查。

还要考虑角色高度、层级切换、门的方向限制和动态障碍。

### 2.6 NavMesh 烘焙与运行时数据流

~~~mermaid
flowchart TD
    Geometry["源三角网格<br/>资产哈希"] --> Raster["体素栅格化"]
    Raster --> Filter["高度/坡度/半径过滤"]
    Filter --> Region["区域划分与合并"]
    Region --> Poly["多边形生成"]
    Poly --> Tile["Tile 序列化"]
    Tile --> Runtime["Detour 运行时查询"]
    Runtime --> Corridor["多边形走廊"]
    Corridor --> Funnel["漏斗与路径验证"]
    Tile --> Cache["Tile/Obstacle 动态缓存"]
    Cache --> Runtime
~~~

每个产物都应绑定来源版本。

源几何哈希用于发现资产变化。

烘焙参数哈希用于发现 profile 变化。

库版本用于解释第三方实现升级。

Tile 坐标与层级用于查找局部影响范围。

导航数据版本用于服务端和回放之间的兼容检查。

### 2.7 动态 Tile 的边界

动态 Tile 适合把局部地形变化限制在一个可重建区域。

Tile 边界不是无成本的。

一条跨边界的通道可能需要两侧同时更新。

邻接的连接点可能因为局部重烘焙移动。

旧查询拿着旧 polyRef 时，不能继续当作新数据使用。

流式加载期间要区分未加载、加载中、加载完成和加载失败。

把未加载区域当成不可达可能造成暂时绕路。

把未加载区域当成可达可能造成越界或空引用。

服务端应选择一种显式策略并记录。

适合回放的做法是把 Tile 状态事件和完成帧写入输入日志。

### 2.8 动态 Obstacle 的边界

DetourTileCache 可以作为动态障碍和 Tile 缓存的公开代码参考。

它不代表所有项目都必须使用同一更新策略。

动态障碍的轮廓必须先被离散化或体素化。

小障碍可能在 cell size 下消失。

大障碍可能污染整个 Tile。

障碍在 Tile 边界附近时，影响范围要包含安全扩张。

障碍移除时，不能只删除障碍对象而不重新验证受影响多边形。

更新队列需要去重。

同一帧内对同一 Tile 的多次添加、移动和删除应折叠为可重放的最终事件序列。

不要在渲染线程直接修改服务端 NavMesh 数据。

运行时更新应通过版本化命令进入导航线程或固定阶段。

### 2.9 Crowd 与全局路径的边界

Recast 官方仓库把 DetourCrowd 单列为代理移动、碰撞避免和群体模拟模块。

这说明群体移动是运行时层，而不是烘焙阶段的全局路径替代。

工程上可以把每个代理的全局路径点变成偏好速度。

再把邻居和静态边界提供给局部避障。

若局部避障连续无法前进，应触发卡住检测和全局路径修复。

不能只增加避障权重而不改变目标通道。

### 2.10 NavMesh 验证清单

| 检查 | 方法 | 报告字段 |
| --- | --- | --- |
| 输入可复现 | 记录源资产哈希 | geometryHash |
| 参数可复现 | 序列化 profile | agentProfileHash |
| Tile 完整 | 检查坐标、层、大小 | tileCount、missingTiles |
| 邻接完整 | 跨 Tile 双向查询 | brokenLinks |
| 多边形合法 | 面积、法线、顶点数 | degeneratePolys |
| 高度连续 | 走廊采样与台阶检查 | heightDiscontinuities |
| 半径安全 | 线段/胶囊查询 | clearanceFailures |
| 动态更新 | 添加、移动、移除回放 | obstacleUpdateFailures |
| 旧引用安全 | 版本不匹配拒绝访问 | staleRefRejects |

## 三、RVO/ORCA 与 Steering

### 3.1 速度障碍假设

速度障碍把两个移动体的相对位置、形状和时间窗转换成速度空间中的碰撞区域。

对一个代理来说，落入该区域的相对速度意味着在预测时间窗内可能发生碰撞。

RVO/ORCA 通过让相互作用的代理分担调整责任，构造局部可行速度约束。

RVO2 官方页面描述了每个代理独立感知环境并计算无碰撞运动。

该模型假设输入的邻居、半径、速度和障碍在计算期间有一致快照。

它通常关注短时局部运动，不负责跨地图的拓扑绕行。

如果目标被墙挡住，ORCA 可能找到一个合法但无法到达目标的速度。

全局路径和局部速度必须分开监控。

### 3.2 邻居查询

邻居查询是局部避障的主要成本入口之一。

朴素方式对 N 个代理做 O(N²) 两两检查。

网格、动态树、KD 树或空间哈希可以把候选查询限制在半径范围。

数据结构选择取决于移动频率、分布、半径和平台。

AOI 分区可以提供粗粒度候选，但不应直接当作精确碰撞邻居。

先按 AOI 或空间分区筛选。

再按距离平方、碰撞层、时间窗和实体状态过滤。

最后按稳定的 entityId 排序并截断到 maxNeighbors。

截断必须确定性。

不能依赖哈希表遍历顺序。

不能按指针地址排序。

如果邻居数量被截断，报告每帧的候选数和截断数。

### 3.3 RVO/ORCA 与 Steering 分层

Steering 通常把路径方向、目标方向、队形、速度限制和避障意图混合成一个期望速度或加速度。

ORCA 则把局部碰撞约束转换为可行速度区域。

推荐的输入顺序如下。

先从全局走廊得到下一个路径目标。

再根据角色状态计算 preferredVelocity。

再用静态碰撞边界和邻居约束裁剪速度。

最后应用加速度、转向速率和动画表现限制。

不要让动画根骨骼直接改变服务端权威位置。

不要让局部避障直接修改全局 NavMesh。

### 3.4 优先级和礼让规则

优先级需要是约束的一部分，而不是仅用于日志。

可以用优先级决定责任比例、最大让行时间、可占用通道或是否允许局部停止。

高优先级不应意味着永远穿过其他单位。

低优先级也不应被无限期推离目标。

一个可落地的约束集合包括以下字段。

agentId。

priorityClass。

teamMask。

collisionLayer。

preferredSpeed。

maxAcceleration。

maxNeighbors。

timeHorizon。

yieldDeadline。

这些字段必须进入回放输入或能由输入重建。

### 3.5 振荡

振荡通常表现为两个代理在左右方向之间来回切换。

原因可能是相同优先级下的对称决策、邻居排序不稳定或预测窗口太短。

还可能是位置积分和速度求解使用了不同的时间步。

常见抑制手段如下。

用稳定 entityId 打破同速同距的平局。

对上一帧速度方向加入小的滞回项。

为目标侧绕行方向生成短时锁定。

限制单帧转向角和加速度。

检测连续方向翻转次数。

在超阈值后采用一条确定性侧向偏移。

所有抑制项都应记录版本和参数。

不要用随机左右选择来“看起来更自然”，除非随机流也被严格记录。

### 3.6 死锁

死锁表现为速度合法但长时间位移接近零。

典型场景包括窄门双向对冲、圆环队列、三个代理互相让行和优先级环。

卡住检测至少要看位移、目标距离进展、速度和碰撞约束数量。

如果只看速度，原地旋转可能被误认为进展。

如果只看位置，低速爬坡可能被误判。

一个检测窗口可以按固定帧数表达。

在窗口内累计目标距离下降量小于 epsilonProgress。

同时累计实际位移小于 epsilonDisplacement。

并且局部约束活跃数超过阈值。

触发后按等级恢复。

先降低非关键邻居的让行优先级。

再短暂提高等待代理的侧向偏移。

再请求局部绕行点或重新查询全局路径。

最后才进入停靠或由服务端裁决的脱困动作。

### 3.7 服务端预算

局部避障预算应按帧、分区和实体类别分配。

关键战斗单位可以有更高的邻居数和更短的更新周期。

远离玩家的 NPC 可以使用较低频率或群体代理。

预算不足时要优先保证权威安全性。

可以减少邻居上限。

可以延长非关键单位的更新周期。

可以复用上一帧可行速度。

不能在没有验证的情况下直接穿过静态障碍。

每帧记录 localAvoidanceBudgetUs、agentsProcessed、neighborTruncated 和 fallbackCount。

### 3.8 局部避障示意代码

~~~cpp
struct AgentSnapshot
{
    uint64_t id;
    Vec2 position;
    Vec2 velocity;
    Vec2 preferredVelocity;
    float radius;
    uint16_t priority;
};

struct AvoidanceResult
{
    Vec2 velocity;
    bool feasible;
    uint32_t activeConstraints;
};

AvoidanceResult SolveAvoidance(
    const AgentSnapshot& self,
    Span<const AgentSnapshot> neighbors,
    float dt)
{
    ConstraintSet constraints;
    for (const AgentSnapshot& other : neighbors)
    {
        if (!CollidesByLayer(self, other))
            continue;
        constraints.AddReciprocalHalfPlane(
            BuildOrcaConstraint(self, other, dt));
    }

    Vec2 candidate = ProjectToFeasibleVelocity(
        self.preferredVelocity,
        constraints,
        self.id);

    candidate = ClampAcceleration(
        self.velocity,
        candidate,
        MaxAcceleration(self),
        dt);

    return {
        candidate,
        constraints.Contains(candidate),
        constraints.Size()
    };
}
~~~

这里的 ProjectToFeasibleVelocity 只是接口边界。

具体 ORCA 求解器的几何细节必须和所选实现版本对照。

重要的是快照、排序、时间步、失败状态和结果哈希都被外层控制。

## 四、数值鲁棒性

### 4.1 浮点误差的来源

浮点误差来自表示、运算顺序、编译器优化、指令集和数据结构遍历。

两台机器使用同一份十进制输入，不代表中间加法顺序相同。

同一平台启用不同的 FMA、快速数学或 SIMD，也可能改变最后几位。

路径排序中的最后几位差异可能放大为不同的开放列表顺序。

局部避障中接近切线的半平面判断也可能因此翻转。

所以确定性不是把所有数都声明为 float32。

要定义哪些量必须完全一致，哪些量只需要在容差内一致。

### 4.2 容差模型

建议把容差分为绝对长度、相对长度、面积、时间和速度五类。

绝对长度适合接近原点的小几何。

相对长度适合坐标范围跨越多个数量级的比较。

面积容差用于方向和退化三角形判断。

时间容差用于固定步积分的累计误差监控。

速度容差用于判断是否卡住或是否接近零速。

容差定义必须带单位。

不要把 1e-5 直接复制到所有函数。

应根据 worldUnitPerMeter、角色半径、最小通道宽和最大地图跨度标定。

### 4.3 退化几何

退化几何包括零长度边、重复点、共线三点、零面积三角形和重合圆。

多边形裁剪前要去重和去掉接近共线的顶点。

方向函数的结果接近零时要进入明确的共线分支。

线段投影的分母接近零时，应该返回端点或指定的最近点。

门户左右边界重合时，漏斗应使用门户中心或直接判定通道不可用。

不要让 NaN 通过比较器进入 priority_queue。

收到 NaN 或无穷时，立即记录输入对象、函数阶段和地图版本。

### 4.4 GJK/EPA/CCD 的工程边界

GJK（Gilbert-Johnson-Keerthi）常用于凸体相交或距离判断。

EPA（Expanding Polytope Algorithm）可以在相交后估计穿透深度和方向。

CCD（Continuous Collision Detection）用于避免离散步长造成的穿透或隧穿。

这三个缩写不能被当成一个“精确碰撞开关”。

GJK 的支持点函数必须对坐标系、半径和边界定义一致。

EPA 对退化单纯形、接近共面和最大迭代次数敏感。

CCD 需要明确扫掠形状、时间区间和接触响应。

Box2D 官方文档说明离散时间步可能出现 tunneling，并提供 TOI 与 speculative collision 等机制。

Bullet 官方仓库可作为另一套实时碰撞实现的源码参考。

在导航验证中，通常不必用完整物理求解器替代所有路径检查。

可以先用包围盒、胶囊或圆的粗查询。

再对候选路径段做精确的 swept test。

超时或退化时宁可判定为需重规划，也不要默认为安全。

### 4.5 坐标尺度

坐标尺度会同时影响网格 cell、代理半径、容差、哈希和日志可读性。

Box2D 官方文档以 MKS 为示例，并警告过大的世界会损失精度。

这不是所有引擎的通用硬阈值。

它可以作为单位设计和尺度测试的提醒。

项目应该记录一个明确的单位契约。

例如 1 world unit 是否等于 1 米。

角色半径、最大速度、最大加速度和地图跨度分别是多少。

导航体素、碰撞体和渲染坐标是否共享原点。

跨区地图是否采用局部原点重定位。

如果使用分区局部坐标，哈希必须包含分区坐标和重定位版本。

### 4.6 稳定比较器

所有路径和邻居相关容器都要显式定义比较器。

比较器应优先比较量化后的主成本。

再比较量化后的次成本。

最后比较稳定的节点或实体 ID。

不要让比较器对 NaN 返回不满足严格弱序。

不要把浮点误差用随机扰动解决。

不要让内存地址参与排序。

不要在同一逻辑层混用本地时间和模拟时间。

### 4.7 数值测试矩阵

| 测试 | 输入 | 期望 |
| --- | --- | --- |
| 原点测试 | 坐标接近零 | 结果合法 |
| 大坐标测试 | 远离原点的同一几何 | 在规定容差内等价 |
| 缩放测试 | 全场景乘 0.1、1、10 | 明确记录允许差异 |
| 共线测试 | 三点完全共线 | 不崩溃，有定义分支 |
| 重合测试 | 两体中心相同 | 有限结果或安全失败 |
| 极薄通道 | 宽度接近直径 | 不穿透 |
| 极长路径 | 节点数很大 | 不溢出，尾延迟可报告 |
| 负/NaN 输入 | 代价或坐标非法 | 拒绝并记录 |

## 五、联机与回放确定性

### 5.1 权威边界

服务端权威移动应负责最终位置、速度、路径版本、碰撞结果和事件顺序。

客户端可以预测输入、插值表现和动画。

客户端不应凭本地 NavMesh 结果直接修改服务端权威状态。

服务端可以接受客户端的目标、移动输入或能力请求。

服务端应重新验证导航版本、权限、速度上限和碰撞结果。

回放记录的是足以重建权威状态的输入和外部事件。

不一定要记录每一帧完整状态。

但在调试模式可以定期记录状态快照和哈希，便于定位第一处分叉。

### 5.2 固定时间步

用模拟 tick 号而不是墙钟时间驱动权威移动。

固定 dt 可以减少不同帧率导致的积分差异。

输入应绑定到 tick。

迟到输入应按照协议进入指定的未来 tick 或被拒绝。

不要在寻路算法里读取 DateTime.Now、线程睡眠时间或渲染帧时间。

服务端调度延迟可以影响处理时间，但不能改变模拟时间。

### 5.3 随机种子派生

随机种子不能只写一个全局 seed。

应该由 matchSeed、场景版本、tick、实体 ID、系统名和流版本派生子流。

派生顺序要固定。

不同子系统不能共享同一个可变随机游标。

否则一个路径查询多消耗一次随机数，就会改变掉落、AI 或其他系统的后续结果。

PCG 官方资料可以作为随机数生成器设计和流隔离的参考。

伪代码如下。

~~~cpp
uint64_t DeriveSeed(
    uint64_t matchSeed,
    uint32_t mapVersion,
    uint64_t tick,
    uint64_t entityId,
    uint32_t streamId)
{
    uint64_t x = matchSeed;
    x = Mix64(x ^ uint64_t(mapVersion));
    x = Mix64(x ^ tick);
    x = Mix64(x ^ entityId);
    x = Mix64(x ^ uint64_t(streamId));
    return x;
}
~~~

Mix64 只是占位的确定性混合函数。

实际使用时要固定实现、端序和测试向量。

不要把语言标准库默认随机引擎的序列当作跨语言协议。

### 5.4 固定点和混合精度

若必须跨 CPU、编译器和语言严格复现，关键决策量可以使用固定点。

位置、速度、代价和时间需要先定义缩放因子。

例如位置可以用毫米整数，时间可以用 tick 整数，路径成本可以用固定的千分之一单位。

固定点会带来量化误差和溢出风险。

必须为加法、乘法、平方距离和累计路径长度设计宽度。

可以使用 int64 或更宽的中间类型。

不要在固定点系统里偷偷转换为 float 再比较。

混合策略通常更现实。

用固定点决定排序、门状态、碰撞命中和路径选择。

用浮点做客户端表现、曲线插值或非权威动画。

若服务端使用浮点，要至少保证比较器、积分顺序和状态哈希序列化规则稳定。

### 5.5 状态哈希

状态哈希应覆盖能够影响后续决策的状态。

典型字段包括 tick、地图版本、导航版本、实体 ID、量化位置、量化速度、路径游标、目标 ID、随机流计数和状态标志。

字段顺序必须固定。

容器遍历顺序必须固定。

字符串应统一编码或转换成稳定 ID。

浮点应先按规定量化或序列化位模式。

哈希算法应固定版本。

哈希只作为分叉检测，不是加密认证。

线上日志至少保存 hashVersion、stateHash 和触发快照的 tick。

### 5.6 输入回放

回放输入应分成三类。

第一类是玩家和脚本的逻辑输入。

第二类是地图、门、障碍、技能和服务端事件。

第三类是环境快照，例如导航版本、实体生成、随机种子和配置版本。

每一类都要有序列号。

事件相同 tick 时按类型优先级和 eventId 排序。

回放加载时先校验地图资产和配置哈希。

如果不匹配，报告不可比较，而不是静默继续。

### 5.7 客户端表现与服务端权威

客户端可以使用更平滑的 Steering。

客户端可以使用不同的帧率和插值。

客户端可以在服务端确认前显示预测路径。

但服务端返回的路径版本和位置修正必须有明确时间戳。

客户端回滚后要重新应用同一批输入。

服务端不要接受客户端提交的最终位置作为路径证据。

### 5.8 确定性顺序图

~~~mermaid
flowchart TD
    Seed["matchSeed + 版本"] --> Streams["派生独立随机流"]
    Input["tick 输入事件"] --> Sort["按类型/序列排序"]
    Snapshot["导航/实体快照"] --> Sort
    Sort --> Search["全局搜索与重规划"]
    Search --> Avoid["邻居排序与局部避障"]
    Avoid --> Integrate["固定 dt 积分"]
    Streams --> Search
    Streams --> Avoid
    Integrate --> Hash["量化字段状态哈希"]
    Hash --> Replay["回放校验与分叉定位"]
~~~

## 六、基准工程

### 6.1 基准的最小固定条件

一个可比较的寻路基准至少固定以下输入。

地图文件或生成器版本。

地图坐标系和单位。

导航 profile 与 Tile 大小。

障碍数量、半径、移动轨迹和更新时间。

单位数量、类别、半径、速度和目标数量。

起点分布、目标分布和随机种子。

查询批次顺序。

编译器、优化级别、CPU 核数和线程数。

预热轮数、采样轮数和内存测量方式。

如果任一条件变化，报告必须标记为新基线。

### 6.2 场景矩阵

| 场景 ID | 地图 | 障碍密度 | 单位数 | 动态障碍 | 目标分布 | 用途 |
| --- | --- | --- | --- | --- | --- | --- |
| S0 | 小型室内 | 低 | 32 | 0 | 均匀 | 算法正确性 |
| S1 | 小型室内 | 中 | 128 | 8 | 门附近 | 局部重规划 |
| S2 | 城市街区 | 中 | 512 | 32 | 分区均匀 | 常态服务端 |
| S3 | 城市街区 | 高 | 2048 | 128 | 热点区域 | 邻居与尾延迟 |
| S4 | 开放世界 Tile | 低 | 512 | 64 | 跨 Tile | 流式边界 |
| S5 | 窄门对冲 | 中 | 64 | 2 | 两侧对向 | 死锁与振荡 |
| S6 | 全图事件 | 高 | 1024 | 1024 | 随机 | 增量失效边界 |
| S7 | 回放长跑 | 固定 | 固定 | 固定 | 固定 | 确定性回归 |

障碍密度要定义分母。

可以使用障碍覆盖面积除以可行走面积。

也可以使用占用栅格比例。

不能只写低、中、高而没有数值。

目标分布至少要区分均匀、热点、跨区和同点汇聚。

### 6.3 指标

必须报告扩展节点数。

扩展节点数比单纯的函数调用次数更能反映搜索工作量。

必须报告路径长度。

路径长度应说明是多边形走廊长度、漏斗折线长度还是实际积分轨迹长度。

必须报告重规划耗时。

重规划耗时包括队列维护还是只包括 ComputeShortestPath，需要在报告中注明。

必须报告 P50、P95 和 P99。

平均数可以辅助定位，但不能替代尾延迟。

必须报告内存。

至少区分导航数据、搜索节点、开放列表、邻居缓存、回放和临时分配。

必须报告失败率。

失败率要分解为无路、预算耗尽、版本冲突、几何验证失败、数据缺失和超时。

建议再报告以下指标。

重复队列条目数。

最大开放列表长度。

邻居候选数和截断数。

局部约束数。

卡住事件数。

回退层级分布。

状态哈希分叉 tick。

### 6.4 百分位计算

先固定样本集合和预热规则。

不要在不同批次混用冷启动与热缓存。

对每个查询记录独立样本。

按耗时升序排序。

P50、P95、P99 的索引规则要固定。

当样本数很小，报告样本数并避免过度解读百分位。

可以使用线性插值，但所有报告必须采用同一算法。

### 6.6 Python 3.12 汇总示意

~~~python
from dataclasses import dataclass
from statistics import median

@dataclass(frozen=True)
class Sample:
    micros: int
    expanded: int
    path_mm: int
    memory_bytes: int
    failure: str

def percentile(values: list[int], q: float) -> float:
    ordered = sorted(values)
    if not ordered:
        return float("nan")
    position = (len(ordered) - 1) * q
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    weight = position - lower
    return ordered[lower] * (1 - weight) + ordered[upper] * weight

def summarize(samples: list[Sample]) -> dict:
    times = [s.micros for s in samples]
    return {
        "count": len(samples),
        "p50_us": percentile(times, 0.50),
        "p95_us": percentile(times, 0.95),
        "p99_us": percentile(times, 0.99),
        "median_expanded": median(s.expanded for s in samples),
        "max_memory_bytes": max(s.memory_bytes for s in samples),
        "failure_rate": sum(s.failure != "none" for s in samples) / len(samples),
    }
~~~

真实工具还应处理空样本、异常进程退出和 schema 版本。

### 6.7 Property test

属性测试不是只随机生成起点和终点。

应随机生成可解释的地图、障碍变更和查询序列。

第一条属性是路径上的每一段都通过可行性判定。

第二条属性是没有障碍变化时，增量算法与基准 A* 的路径成本在允许 tie-break 差异内一致。

第三条属性是同一输入序列重复运行时，状态哈希序列一致。

第四条属性是障碍添加后，旧路径若穿过受影响区域必须被拒绝或重规划。

第五条属性是障碍移除后，不应产生比基准可行路径更差的不可达判定，除非版本状态未完成。

第六条属性是邻居集合排序只依赖输入字段，不依赖插入顺序。

第七条属性是任何非法浮点输入都不会导致 NaN 扩散到状态哈希。

~~~python
def prop_replay_is_stable(case):
    first = run_simulation(case, seed=case.seed)
    second = run_simulation(case, seed=case.seed)
    assert first.state_hashes == second.state_hashes

def prop_path_is_clear(case):
    result = run_planner(case)
    if result.success:
        assert all(segment_is_clear(segment, case.obstacles)
                   for segment in result.path_segments)

def prop_neighbor_order_is_input_based(case):
    a = sorted_neighbors(case.agents)
    b = sorted_neighbors(list(reversed(case.agents)))
    assert [x.id for x in a] == [x.id for x in b]
~~~

属性失败时保存最小化输入。

最小化输入需要保留地图版本、随机种子、变化序列和失败 tick。

不要只保存随机种子而丢失生成器版本。

### 6.8 回归阈值

阈值应按基线值和绝对上限双重定义。

例如 P95 不得超过基线的 1.15 倍，且不得超过 2 毫秒。

相对阈值能识别小场景回归。

绝对阈值能保护线上预算。

失败率通常使用绝对百分点差，而不是相对倍数。

状态哈希分叉应是零，除非测试明确标记为允许差异。

路径长度回归应区分算法 tie-break 和真正的可行性失败。

阈值文件需要版本控制。

## 七、跨系统联动

### 7.1 与 AOI 联动

AOI 负责确定实体应该看到哪些对象。

局部避障负责从候选对象中挑选实际邻居。

二者不能共用一个没有语义的“附近列表”。

AOI 事件可以触发邻居缓存失效。

导航系统应使用服务端权威实体快照，而不是客户端可见列表。

跨 AOI 边界时，实体可能在同一 tick 既离开一个分区又进入另一个分区。

事件排序必须稳定。

回放需要记录分区版本或能从权威实体位置重建。

相关空间索引和视野边界可参阅 [AOI 与视野计算](../03-工程与实用技巧/03-AOI与视野计算.md)。

### 7.2 与服务端 AI 联动

服务端 AI 应把目标选择、路径请求、局部避障和动画表现意图分开。

行为树或 StateTree 可以请求“去某区域”。

寻路系统返回路径状态和失败原因。

移动系统输出可行速度。

战斗系统决定是否允许停下、绕行或继续受击。

不要让行为树每帧无条件重发同一寻路请求。

使用目标版本、路径版本和请求去重键。

当目标未变且障碍版本未影响通道时复用旧查询。

### 7.3 与限流、幂等和可靠性联动

路径请求是服务器资源，不是无限廉价的纯函数。

请求应带 requesterId、requestId、priority、deadline、mapVersion 和目标版本。

相同幂等键的重复请求返回相同的已确认结果或处理中状态。

超出预算时按优先级退化。

可以延迟低优先级请求。

可以合并同一实体的旧目标请求。

不能把高频重规划放进无界队列。

重启或迁移时，路径缓存必须携带版本。

相关的鉴权、限流、幂等、灾备和可观测性可参阅 [服务端可靠性专题](../../游戏服务端/04-平台与可靠性/01-鉴权限流幂等灾备与可观测性.md)。

### 7.4 与回放和评测联动

AI 评测应该把路径质量、卡住率、回放一致性和资源预算一起评估。

只看“是否到达目标”会漏掉严重的尾延迟和作弊边界问题。

回放失败时，应定位第一处分叉而不是只报最终位置不同。

关联的评测、回放和安全约束可参阅 [AI 评测回放与 LLM 安全](../../游戏AI/03-评测与安全/01-AI评测回放与LLM安全.md)。

## 八、失败路径与运行手册

### 8.1 失败路径表

| 失败路径 | 触发信号 | 保守处理 | 后续动作 |
| --- | --- | --- | --- |
| 起点不在 NavMesh | 定位失败 | 投影到最近合法点或停靠 | 记录投影距离 |
| 目标不在 NavMesh | 目标定位失败 | 选择最近可达点 | 返回目标修正原因 |
| 地图版本过期 | snapshotVersion 不同 | 拒绝旧查询结果 | 重新提交当前版本 |
| 动态门关闭 | 路径穿过受影响边 | 截断并重规划 | 写入 doorChangeId |
| Tile 未加载 | polyRef 无效 | 停在边界安全点 | 等待或走回退路径 |
| 增量预算耗尽 | pop 或微秒超限 | 复用合法前缀 | 异步继续或降级 |
| 邻居过多 | maxNeighbors 截断 | 按稳定排序裁剪 | 记录截断率 |
| ORCA 无可行速度 | 约束交集为空 | 使用安全停靠速度 | 触发死锁计时 |
| 几何退化 | 面积/方向接近零 | 采用安全分支 | 采集最小输入 |
| 回放分叉 | hash 不同 | 停止比较后续帧 | 导出第一处分叉快照 |
| 服务端超载 | 队列或预算超限 | 按优先级降级 | 触发限流指标 |

### 8.2 线上排障顺序

先确认地图、NavMesh 和配置哈希。

再确认请求实体的输入 tick 和目标版本。

再确认导航快照是否在查询期间稳定。

再看全局搜索扩展节点和队列重复项。

再看路径几何验证和动态障碍版本。

再看邻居候选、局部约束和卡住检测。

最后比对状态哈希和随机流计数。

不要先从“调大避障半径”开始。

很多所谓避障问题其实是导航版本、邻居排序或坐标尺度问题。

### 8.3 指标告警

P99 重规划耗时连续超过阈值时，告警而不是只看平均数。

失败率上升但扩展节点不变时，优先检查版本冲突和数据缺失。

扩展节点上升且重复队列条目上升时，检查变化批次和 key 失效。

邻居截断上升时，检查 AOI 热点和空间索引退化。

卡住率上升但 ORCA 求解耗时不变时，检查优先级、窄门和全局路径。

回放分叉只在某平台出现时，检查浮点、FMA、编译选项和容器排序。

## 九、复杂度与选型对比

| 方案 | 主要成本 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| A* | 单次搜索与开放列表 | 静态或低频查询 | 反复变化会重复工作 |
| LPA* | g/rhs 与变化传播 | 多次同图查询 | 更新依赖管理复杂 |
| D* Lite | 反向增量搜索与移动起点 | 局部变化、长路径复用 | 变化过大时接近全量修复 |
| NavMesh + 漏斗 | 烘焙、查询、几何收紧 | 连续可行走空间 | 烘焙参数和动态边界敏感 |
| 网格流场 | 共享目标的批量传播 | 大量单位同目标 | 多目标和动态成本维护复杂 |
| RVO/ORCA | 邻居查询与速度约束 | 短时群体避让 | 死锁、抖动和非全局最优 |
| Steering | 每单位规则与积分 | 表现和低成本移动 | 不能替代全局可达性 |
| 固定点 | 整数算术与量化 | 权威回放、跨平台 | 溢出和量化误差 |
| 浮点 + 容差 | 开发效率和几何表达 | 单平台或非权威表现 | 跨平台分叉 |

复杂度只能作为工作量趋势。

不能用某个论文或库 README 的复杂度直接替代项目实测。

## 十、最佳实践

1. 先建立静态 A* 基线，再以相同输入比较增量算法。
2. 把地图、障碍、目标和配置都版本化，并在路径结果中回传版本。
3. 只把会改变全局可达性的动态对象纳入全局图。
4. 把移动单位留给局部邻居查询和速度层，除非业务明确需要硬占位。
5. 开放列表使用稳定 key、稳定节点 ID 和过期条目检查。
6. 所有预算耗尽都返回可区分的状态，不伪装成无路。
7. NavMesh 烘焙参数、源资产哈希和库版本一起存档。
8. 漏斗之后再做半径和动态障碍验证，不把多边形走廊当作安全轨迹。
9. 邻居查询先空间过滤，再按 entityId 做稳定排序和截断。
10. 用固定 tick、独立随机流和量化状态哈希做回放门禁。
11. 把 P50、P95、P99、内存和失败率写入同一份报告。
12. 用 property test 覆盖退化几何、版本冲突和输入顺序变化。
13. 线上按单位类别、分区和请求优先级分配预算。
14. 卡住检测要结合进展、位移、速度和约束，不只看一个阈值。
15. 每次降级都写 failureReason、fallbackLevel 和相关版本。

## 十一、常见问题 FAQ

### Q1：D* Lite 是否一定比 A* 快？

不是。

它在多次搜索共享图、变化局部且旧搜索信息可复用时更有机会降低重复工作。

一次性查询、整图变化或图很小时，A* 可能更简单、更快、更容易验证。

必须用同一场景矩阵测量。

### Q2：移动单位应该全部加入 NavMesh 动态障碍吗？

通常不应该。

移动单位每帧变化会把全局图更新变成高频事件。

更常见的分层是静态或低频动态 NavMesh 加局部邻居避让。

只有会改变战略可达性的单位或门控事件才适合进入全局层。

### Q3：NavMesh 烘焙成功是否代表角色一定不会穿墙？

不代表。

烘焙参数表达的是某个代理 profile 下的可行区域。

运行时还会有速度、半径、动态障碍、几何误差和碰撞步长。

必须在漏斗路径后做运行时验证。

### Q4：ORCA 能否解决两个单位卡在窄门的问题？

不能保证。

ORCA 的局部速度约束可能让双方都找到短时合法速度，但没有战略上的先后顺序。

需要优先级、礼让期限、卡住检测和全局绕行策略。

### Q5：固定随机种子后，回放为什么仍会分叉？

因为分叉还可能来自浮点运算顺序、容器遍历、线程调度、版本差异和隐式随机流。

应记录独立随机流、固定排序、状态哈希和第一处分叉快照。

### Q6：为什么要同时报告 P50、P95 和 P99？

P50 代表常态，P95 代表较常见的尾部，P99 用来发现热点、全图变化和分配抖动。

只看平均值会掩盖服务端在拥堵或批量重规划时的预算超限。

### Q7：状态哈希应该包含完整路径吗？

如果路径游标、路径版本或下一段方向会影响后续决策，就应包含它们或包含能重建它们的输入。

完整路径可能增加日志成本。

可以使用路径摘要、版本和游标，并在分叉时导出完整快照。

### Q8：浮点系统是否必须全部改成固定点？

不必一刀切。

权威路径选择、排序、命中和回放关键状态可以使用固定点或严格量化。

表现层和非权威动画可以继续使用浮点。

关键是边界清楚、容差有单位、回放有测试。

### Q9：动态 Tile 边界最容易出什么问题？

最常见的是旧 polyRef 与新 Tile 混用、跨边界邻接未同步、加载中的区域被错误当作可达以及更新范围没有包含安全扩张。

用 Tile 版本和跨边界测试覆盖这些情况。

### Q10：基准测试能否直接作为线上容量承诺？

不能。

基准可以提供固定输入下的回归证据和容量趋势。

线上还受脚本、网络、实体分布、GC、线程争用和故障重试影响。

应把基准门禁与线上指标、压测和回放样本结合。
