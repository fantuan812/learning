## 概述

动态寻路的难点不是把 A* 换成一个更响亮的算法名。

难点是地图、单位、障碍、时间步长和服务端预算同时变化时，仍然能回答四个问题。

第一，当前返回的路径是否在本次快照上有效。

第二，局部障碍变化后，是否只重算了受影响的部分。

第三，多个平台回放同一输入时，是否能得到同一决策状态。

第四，当预算不足或几何退化时，系统是否能安全降级并留下证据。

本文将全局路径、局部运动和在线工程分成三层。

全局层负责从起点区域到目标区域的可达性和拓扑方向。

局部层负责短时间窗内的速度选择、邻居避让和转向舒适度。

在线层负责快照版本、确定性、调度、限流、回放、哈希和指标。

这三层可以组合，但不能互相冒充。

D* Lite 或 LPA* 的增量优势来自对已有搜索信息的复用。

它们并不意味着所有动态地图都比一次性 A* 更快。

如果障碍变化接近全图、启发式不一致、图结构频繁重建，增量维护可能反而增加管理成本。

NavMesh 解决的是连续空间到多边形图的工程化表达。

它不替代动态实体的碰撞约束，也不保证一条多边形通道在任意速度和半径下都安全。

RVO/ORCA 解决的是速度空间里的短时碰撞避免。

它需要邻居查询、预测时间窗和相互让行等假设。

它不是全局寻路，也不是死锁的自动证明器。

确定性工程更像一条证据链。

输入快照、随机种子、固定时间步、排序规则和状态哈希共同决定回放能否复现。

单独把随机数换成固定种子，不能消除浮点运算、容器遍历和线程调度造成的差异。

基准工程则把这些边界变成固定场景、固定指标和可审阅报告。

没有固定地图、障碍密度、单位数和目标分布，性能数字无法比较。

没有失败率、尾延迟和回放一致性，平均耗时也无法代表线上风险。

## 核心概念

| 概念 | 英文 | 解决的问题 | 不能承诺的事情 |
| --- | --- | --- | --- |
| A* | A-star | 在静态加权图上按启发式搜索路径 | 不承诺动态障碍下无需重规划 |
| LPA* | Lifelong Planning A* | 复用多次搜索的 g 与 rhs 值 | 不承诺变化越多越快 |
| D* Lite | Dynamic A* Lite | 以反向搜索和 key 调整支持移动起点/边代价变化 | 不承诺全图拓扑改变时仍保持低成本 |
| 一致性 | Consistency | 判断节点当前值是否满足局部 Bellman 条件 | 不等同于浮点平台完全一致 |
| NavMesh | Navigation Mesh | 用可行走多边形表达连续空间 | 不等同于碰撞世界的完整副本 |
| 门 | Portal | 两个相邻多边形之间的公共边或可通行连接 | 不保证全局路径平滑 |
| 漏斗算法 | Funnel / String Pulling | 在多边形通道内收紧左右边界得到拐点 | 不处理通道已因动态障碍失效的情况 |
| Tile | Tiled NavMesh | 将大地图切成可流式和可局部重烘焙的块 | 不保证跨 Tile 更新无缝 |
| 速度障碍 | Velocity Obstacle | 描述给定时间窗内会导致碰撞的相对速度集合 | 不解决长期拥堵和全局绕行 |
| ORCA | Optimal Reciprocal Collision Avoidance | 在局部半平面约束中选择可行速度 | 依赖相互承担避让责任的模型假设 |
| Steering | Steering Behaviors | 把目标、路径和避障转成加速度/速度意图 | 不等同于离散路径规划 |
| 固定点 | Fixed-point | 用整数尺度表达关键状态和比较 | 不能自动消除错误的单位换算 |
| 状态哈希 | State Hash | 检测回放或多端状态分叉 | 哈希一致不等于实现逻辑全部正确 |
| 基准门禁 | Benchmark Gate | 以阈值阻止性能或一致性回归 | 不替代线上真实流量观察 |

建议把一帧内的顺序固定为以下阶段。

先读取并冻结本帧输入快照。

再应用已确认的地图和动态障碍版本。

然后执行全局路径查询或增量重规划。

接着在通道上做漏斗收紧和路径有效性检查。

再查询邻居并执行局部速度选择。

最后以固定步长积分，更新状态哈希和指标。

## 一、失败路径与运行手册

### 1.1 失败路径表

| 失败路径 | 触发信号 | 保守处理 | 后续动作 |
| --- | --- | --- | --- |
| 起点不在 NavMesh | 定位失败 | 投影到最近合法点或停靠 | 记录投影距离 |
| 目标不在 NavMesh | 目标定位失败 | 选择最近可达点 | 返回目标修正原因 |
| 地图版本过期 | snapshotVersion 不同 | 拒绝旧查询结果 | 重新提交当前版本 |
| 动态门关闭 | 路径穿过受影响边 | 截断并重规划 | 写入 doorChangeId |
| Tile 未加载 | polyRef 无效 | 停在边界安全点 | 等待或走回退路径 |
| 增量预算耗尽 | pop 或微秒超限 | 复用合法前缀 | 异步继续或降级 |
| 邻居过多 | maxNeighbors 截断 | 按稳定排序裁剪 | 记录截断率 |
| ORCA 无可行速度 | 约束交集为空 | 使用安全停靠速度 | 触发死锁计时 |
| 几何退化 | 面积/方向接近零 | 采用安全分支 | 采集最小输入 |
| 回放分叉 | hash 不同 | 停止比较后续帧 | 导出第一处分叉快照 |
| 服务端超载 | 队列或预算超限 | 按优先级降级 | 触发限流指标 |

### 1.2 线上排障顺序

先确认地图、NavMesh 和配置哈希。

再确认请求实体的输入 tick 和目标版本。

再确认导航快照是否在查询期间稳定。

再看全局搜索扩展节点和队列重复项。

再看路径几何验证和动态障碍版本。

再看邻居候选、局部约束和卡住检测。

最后比对状态哈希和随机流计数。

不要先从“调大避障半径”开始。

很多所谓避障问题其实是导航版本、邻居排序或坐标尺度问题。

### 1.3 指标告警

P99 重规划耗时连续超过阈值时，告警而不是只看平均数。

失败率上升但扩展节点不变时，优先检查版本冲突和数据缺失。

扩展节点上升且重复队列条目上升时，检查变化批次和 key 失效。

邻居截断上升时，检查 AOI 热点和空间索引退化。

卡住率上升但 ORCA 求解耗时不变时，检查优先级、窄门和全局路径。

回放分叉只在某平台出现时，检查浮点、FMA、编译选项和容器排序。

## 二、复杂度与选型对比

| 方案 | 主要成本 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| A* | 单次搜索与开放列表 | 静态或低频查询 | 反复变化会重复工作 |
| LPA* | g/rhs 与变化传播 | 多次同图查询 | 更新依赖管理复杂 |
| D* Lite | 反向增量搜索与移动起点 | 局部变化、长路径复用 | 变化过大时接近全量修复 |
| NavMesh + 漏斗 | 烘焙、查询、几何收紧 | 连续可行走空间 | 烘焙参数和动态边界敏感 |
| 网格流场 | 共享目标的批量传播 | 大量单位同目标 | 多目标和动态成本维护复杂 |
| RVO/ORCA | 邻居查询与速度约束 | 短时群体避让 | 死锁、抖动和非全局最优 |
| Steering | 每单位规则与积分 | 表现和低成本移动 | 不能替代全局可达性 |
| 固定点 | 整数算术与量化 | 权威回放、跨平台 | 溢出和量化误差 |
| 浮点 + 容差 | 开发效率和几何表达 | 单平台或非权威表现 | 跨平台分叉 |

## 三、最佳实践

1. 先建立静态 A* 基线，再以相同输入比较增量算法。
2. 把地图、障碍、目标和配置都版本化，并在路径结果中回传版本。
3. 只把会改变全局可达性的动态对象纳入全局图。
4. 把移动单位留给局部邻居查询和速度层，除非业务明确需要硬占位。
5. 开放列表使用稳定 key、稳定节点 ID 和过期条目检查。
6. 所有预算耗尽都返回可区分的状态，不伪装成无路。
7. NavMesh 烘焙参数、源资产哈希和库版本一起存档。
8. 漏斗之后再做半径和动态障碍验证，不把多边形走廊当作安全轨迹。
9. 邻居查询先空间过滤，再按 entityId 做稳定排序和截断。
10. 用固定 tick、独立随机流和量化状态哈希做回放门禁。
11. 把 P50、P95、P99、内存和失败率写入同一份报告。
12. 用 property test 覆盖退化几何、版本冲突和输入顺序变化。
13. 线上按单位类别、分区和请求优先级分配预算。
14. 卡住检测要结合进展、位移、速度和约束，不只看一个阈值。
15. 每次降级都写 failureReason、fallbackLevel 和相关版本。

## 四、常见问题 FAQ

### Q1：D* Lite 是否一定比 A* 快？

不是。

它在多次搜索共享图、变化局部且旧搜索信息可复用时更有机会降低重复工作。

一次性查询、整图变化或图很小时，A* 可能更简单、更快、更容易验证。

必须用同一场景矩阵测量。

### Q2：移动单位应该全部加入 NavMesh 动态障碍吗？

通常不应该。

移动单位每帧变化会把全局图更新变成高频事件。

更常见的分层是静态或低频动态 NavMesh 加局部邻居避让。

只有会改变战略可达性的单位或门控事件才适合进入全局层。

### Q3：NavMesh 烘焙成功是否代表角色一定不会穿墙？

不代表。

烘焙参数表达的是某个代理 profile 下的可行区域。

运行时还会有速度、半径、动态障碍、几何误差和碰撞步长。

必须在漏斗路径后做运行时验证。

### Q4：ORCA 能否解决两个单位卡在窄门的问题？

不能保证。

ORCA 的局部速度约束可能让双方都找到短时合法速度，但没有战略上的先后顺序。

需要优先级、礼让期限、卡住检测和全局绕行策略。

### Q5：固定随机种子后，回放为什么仍会分叉？

因为分叉还可能来自浮点运算顺序、容器遍历、线程调度、版本差异和隐式随机流。

应记录独立随机流、固定排序、状态哈希和第一处分叉快照。

### Q6：为什么要同时报告 P50、P95 和 P99？

P50 代表常态，P95 代表较常见的尾部，P99 用来发现热点、全图变化和分配抖动。

只看平均值会掩盖服务端在拥堵或批量重规划时的预算超限。

### Q7：状态哈希应该包含完整路径吗？

如果路径游标、路径版本或下一段方向会影响后续决策，就应包含它们或包含能重建它们的输入。

完整路径可能增加日志成本。

可以使用路径摘要、版本和游标，并在分叉时导出完整快照。

### Q8：浮点系统是否必须全部改成固定点？

不必一刀切。

权威路径选择、排序、命中和回放关键状态可以使用固定点或严格量化。

表现层和非权威动画可以继续使用浮点。

关键是边界清楚、容差有单位、回放有测试。

### Q9：动态 Tile 边界最容易出什么问题？

最常见的是旧 polyRef 与新 Tile 混用、跨边界邻接未同步、加载中的区域被错误当作可达以及更新范围没有包含安全扩张。

用 Tile 版本和跨边界测试覆盖这些情况。

### Q10：基准测试能否直接作为线上容量承诺？

不能。

基准可以提供固定输入下的回归证据和容量趋势。

线上还受脚本、网络、实体分布、GC、线程争用和故障重试影响。

应把基准门禁与线上指标、压测和回放样本结合。
