# 游戏算法 · 寻路与图论（Pathfinding & Graph Theory）

> 本目录是《游戏算法》知识库的第一部分：**寻路与图论**。从图论基础出发，依次覆盖 BFS/DFS/Dijkstra 等经典搜索、游戏寻路的事实标准 A* 及其工业级优化（二叉堆、跳点搜索 JPS、分层寻路 HPA*），再到支撑 RTS 千人同屏的流场（Flow Field）群体寻路，最后补上让这一切跑得动的高性能空间分区与索引结构（均匀网格、四叉树/八叉树、BVH、KD 树、空间哈希）。

## 2. 分类简介

### 2.1 这一分类解决什么问题

游戏世界本质上是**离散化之后才能被算法处理**的：无论是 RTS 里上千个单位的集体行军，还是 MMO 里几十万玩家相互感知的 AOI 管理，抑或是 FPS 里敌人的导航与射击线检测，背后都是同一套数学工具——**图（Graph）** 与**空间数据结构**。

本分类的 4 篇正文构成一条完整的技术主线：

1. **先有图**：把游戏地图抽象成顶点与边（01 篇）；
2. **再在图上有目的地搜索**：从无启发式的 BFS/Dijkstra 到带启发式的 A*（01、02 篇）；
3. **再考虑规模**：当单位数量从 1 变成 1000，从"每单位搜一次"变成"全场算一次"的流场方案（03 篇）；
4. **最后考虑性能底座**：任何搜索与查询都要回答"邻居是谁、附近有什么"，空间分区与索引（04 篇）让这些查询从 O(n) 降到 O(log n) 甚至 O(1)。

### 2.2 阅读对象

- 游戏客户端/服务端程序员，尤其是从事 **AI、战斗、玩法系统** 的开发者；
- 想系统化补齐"寻路算法"知识树、准备技术面试的从业者；
- 独立游戏开发者，需要为自己的项目选择合适寻路方案；
- 引擎/工具链开发者，需要实现或维护 NavMesh、AOI、剔除系统。

### 2.3 与相邻分类的关系

- 本分类是 **行为决策（行为树/状态机）** 的下游：AI 决定"做什么"，寻路决定"怎么走过去"；
- 与 **物理与碰撞** 分类共享空间分区技术（04 篇的 BVH、网格同样服务于碰撞检测）；
- 与 **网络与同步** 分类共享 AOI 概念（04 篇的均匀网格是 MMO AOI 的标准实现）；
- 与 **渲染与优化** 分类共享四叉树/八叉树、视锥剔除等结构。

## 4. 学习顺序建议

### 4.1 路线一：按部就班（推荐，约 3~5 天）

这是本分类的标准阅读顺序，后一篇默认使用前一篇的概念：

1. **先读 `01-图论基础与搜索算法.md`**：掌握图的存储与三种基础搜索（BFS/DFS/Dijkstra）。它们是所有后续内容的词汇表；
2. **再读 `02-A星算法与优化.md`**：A* 就是"Dijkstra + 启发函数"，01 篇的优先队列实现直接复用；
3. **然后读 `03-流场与群体寻路.md`**：流场的距离场就是"从目标出发跑一次 Dijkstra"，需要 01 篇做底子；
4. **穿插读 `04-空间分区与索引.md`**：空间分区与搜索算法相对独立，可以在任何时间读；放在最后是为了强调"性能底座"的位置。

> 建议：每读完一篇，把文中的伪代码用手写一遍（不复制），再实现一个最小可运行版本（例如在 50×50 的二维数组地图上跑通 A*），再进入下一篇。

### 4.2 路线二：快速上手"给单位找路"（约 1~2 天）

只想尽快做出一个能用的寻路系统：

1. `01-图论基础与搜索算法.md` 的「3. 图的存储」「4. BFS」「7. Dijkstra」三节；
2. `02-A星算法与优化.md` 全文（重点：第 3 节 A* 原理、第 4 节启发函数、第 9 节拐点平滑）；
3. 有空再回补 `03` 与 `04`。

### 4.3 路线三：RTS / 千人同屏向

目标是即时战略、大规模战争、塔防类项目：

1. 必读 `01`（Dijkstra 部分）与 `02`（A* 部分）；
2. 精读 `03-流场与群体寻路.md`：流场正是为"单位多、目标少"的 RTS 场景而生；
3. 精读 `04-空间分区与索引.md` 的均匀网格与空间哈希：RTS 的索敌、攻击判定都依赖它们；
4. 可再了解 D* Lite（动态障碍重规划）与寻路请求合并（Path Request Batching）作为延伸。

### 4.4 路线四：引擎 / 工具链开发向

目标是实现 NavMesh 烘焙、编辑器工具或引擎底层模块：

1. `01` 全篇（图的存储是烘焙工具的数据基础）；
2. `02` 的「8. 网格 vs NavMesh」「9. 路径优化」两节；
3. `04` 全篇：四叉树/八叉树/BVH 是烘焙、剔除、查询工具的核心结构。

## 6. 配套练习建议

### 练习 1：网格地图寻路（对应 01、02 篇）

用任意语言生成一张 64×64 的随机障碍地图（约 30% 障碍），实现：

- 邻接表（隐式图：邻居由坐标计算）上的 BFS；
- Dijkstra（带地形代价：平原 1、沼泽 3、坡地 2）；
- A*（曼哈顿启发 + 二叉堆）；
- 对比三者找出的路径长度与耗时，画出折线图。

### 练习 2：拐点平滑（对应 02 篇）

在练习 1 的 A* 路径上实现漏斗（Funnel）算法，把"折线路径"变成"贴墙走的最短可视路径"，观察路径缩短比例。

### 练习 3：流场（对应 03 篇）

在同一张地图上从目标点反向跑一次 Dijkstra 得到距离场，再为每个格子生成梯度方向；用 200 个随机起点同时走向目标，观察拥塞与绕行效果；再把"已走过格子的代价 +1"模拟流量代价，观察路径是否分散。

### 练习 4：AOI（对应 04 篇）

模拟 10000 个随机移动的对象，比较"全量 O(n²) 两两检测"与"均匀网格九宫格查询"的每帧开销；再尝试四叉树版本，记录三者数据。

## 10. 常见问题 FAQ（关于本分类）

**Q1：我只做 2D 游戏，需要学 NavMesh 吗？**
2D 游戏通常用网格（Tilemap）寻路即可，A* + JPS 足够；但如果你的 2D 地图是任意多边形障碍（而非格子），把地图烘焙成 2D NavMesh 再用 A* 也是常见做法。

**Q2：A* 已经很快了，为什么还要学流场？**
单位数量是关键变量：A* 的耗时随单位数量线性增长（每个单位搜一次），而流场一次计算可服务任意数量单位。1000 个单位同时寻路时，流场优势是数量级的。

**Q3：这些算法在生产环境还常用吗？**
常用。A* 仍是绝大多数游戏寻路的核心（Unity、Unreal 的 NavMesh 寻路内部即 A* 变体）；流场被 Supreme Commander 2、Planetary Annihilation 等 RTS 用于大规模单位移动；四叉树/八叉树/BVH 是引擎渲染与物理模块的标准结构。

**Q4：是否需要先学完本分类才能读其他分类？**
不需要。本分类内部按顺序读即可；与行为树、物理、网络等分类的交叉点已在各篇「关联阅读」中标注。
