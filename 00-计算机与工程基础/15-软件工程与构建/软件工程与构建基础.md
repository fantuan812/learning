# 软件工程与构建基础
> 验证与基准：按文中命令执行最小实验，记录结果与边界。

> 知识成熟度：L2（流程与工具可执行；命令与实验计划已给出但尚未形成运行证据，组织级指标需持续采集）。
> 知识基线：CMake/Build.cs、依赖管理、架构治理、测试金字塔、CI/CD 与发布。
> 最后更新：2026-08-20。
> 官方参考：[CMake documentation](https://cmake.org/cmake/help/latest/)、[Google Testing Blog](https://testing.googleblog.com/)。
> 验证入口：执行构建、单元测试、静态分析和 CI 门禁。
> 证据状态：尚未保存完整构建日志、测试报告、静态分析结果或 CI 运行记录。

## 1. 工程目标

软件工程的交付物不仅是可运行程序，还包括源代码、配置、依赖、测试、文档、制品和运行证据。

质量可从正确性、可靠性、性能、安全性、可维护性和可部署性六个维度观察。

需求应写成可验证的行为，避免只描述实现偏好。

用风险优先级安排工作：影响面乘发生概率，再减去可探测性带来的缓解。

小步提交使回滚、评审和二分定位更便宜。

## 2. 版本控制

提交应表达单一意图，标题说明动词、范围和结果。

不要提交生成目录、凭据、个人 IDE 配置和机器相关路径。

分支保护要求评审、自动测试和线性历史时，应在服务器端强制。

合并冲突先理解两边语义，再解决文本冲突。

重写公共历史前必须确认没有消费者依赖旧哈希。

标签用于发布版本，发布说明记录不兼容变更和迁移步骤。

## 3. 构建模型

构建图是目标、源文件、生成文件和工具链之间的有向无环图。

增量构建只重建受变更影响的节点；隐式依赖会破坏正确性。

声明依赖关系比手写编译顺序更可靠。

编译、链接、打包和部署应区分为可缓存的阶段。

Debug、Release、Sanitizer 和交叉编译属于不同配置，不要混用产物。

工具链文件应明确编译器、系统根、目标架构和链接器。

## 4. CMake 要点

使用 target-oriented API：`add_library`、`add_executable` 和 `target_link_libraries`。

通过 `PRIVATE`、`PUBLIC`、`INTERFACE` 表达包含目录、宏和链接传播。

将源文件列入目标，避免全局 `include_directories` 和 `add_definitions`。

用 option 控制可选特性，但默认配置必须可构建、可测试。

导出 package config，使下游通过 `find_package` 使用目标。

为第三方依赖记录版本、补丁和许可证，避免隐式系统库漂移。

生成器表达构建系统，`cmake --build` 隔离底层工具差异。

安装规则应包含运行库、头文件、配置文件和调试符号策略。

## 5. 依赖管理

依赖分为编译期、链接期、运行期和测试期，生命周期不同。

锁文件保证解析结果稳定，升级应一次只改变有限集合。

二进制缓存要校验编译器、标准库、架构和编译选项。

供应链检查包括来源、哈希、签名、许可证和已知漏洞。

不要把网络下载放进不可审计的构建脚本。

依赖失败应有离线缓存和清晰错误信息。

## 6. 模块与架构

模块边界依据变化原因、所有权和数据不变量，而非目录大小。

依赖方向应从稳定抽象指向实现细节，避免环依赖。

接口要小而明确，错误模型和线程安全契约属于接口的一部分。

跨模块传递所有权时，明确生命周期、分配器和 ABI。

架构决策记录（ADR）至少包含上下文、决策、后果和替代方案。

技术债要有偿还触发条件，而不是只写“以后优化”。

## 7. 测试层次

单元测试验证纯函数、边界和错误路径，反馈最快。

组件测试验证模块与真实依赖的协议，不应全靠 mock。

集成测试验证数据库、网络、文件系统等组合行为。

端到端测试验证关键用户路径，数量应少而稳定。

契约测试让服务提供者和消费者独立演进。

回归测试来自真实缺陷，测试名应描述可观察行为。

属性测试检查不变量，随机种子必须可复现。

模糊测试关注解析器、序列化和状态机的异常输入。

## 8. 测试设计

边界值包括零、空、最大值、溢出、重复和乱序。

时间相关代码使用可注入时钟，避免依赖墙上时间。

并发测试需要控制调度、超时和资源清理。

测试失败输出输入、环境、版本、随机种子和最小堆栈。

禁止通过无限重试掩盖非确定性；应统计并修复 flaky 原因。

测试数据要隔离租户、凭据和个人信息。

## 9. 静态质量

格式化是机械规则，代码评审关注语义和设计。

编译警告在 CI 中按等级处理，关键告警不得降级。

静态分析配置应版本化，并保留误报抑制理由。

覆盖率用于发现未执行区域，不等于正确性。

变异测试可检验断言是否真正敏感。

Sanitizer 用于越界、未定义行为、泄漏和数据竞争发现。

## 10. CI/CD

CI 步骤应分为校验、编译、测试、打包、扫描和发布。

并行化独立任务，缓存按锁文件和工具链哈希失效。

构建环境固定时区、语言、随机种子和依赖源。

制品不可变，发布引用制品哈希而不是“latest”。

渐进发布包括灰度、指标观察、暂停和自动回滚。

数据库迁移采用向前兼容的扩展、迁移、收缩阶段。

## 11. 可复现与调试

记录命令行、环境变量、编译器版本和源码提交。

二进制应能关联符号、构建 ID 和源代码版本。

问题报告包含现象、预期、复现步骤、日志和影响范围。

先用最小样例确认编译器、库或业务逻辑边界。

性能回归使用固定工作负载、预热、重复次数和置信区间。

## 12. 工程清单

- [ ] 干净机器可配置并构建
- [ ] 依赖版本、哈希和许可证已记录
- [ ] 单元和集成测试覆盖关键不变量
- [ ] CI 失败能定位到具体阶段
- [ ] 制品可追溯且可回滚
- [ ] 架构决策和迁移步骤已记录
- [ ] 监控、告警和运行手册已准备

## 13. 常见反模式

只在本机成功、构建脚本偷偷联网、全局编译宏、复制粘贴配置、无限重试、忽略警告、用覆盖率数字替代测试设计、把 mock 当成集成测试、发布不可追溯制品，都会增加长期成本。

修复反模式的第一步是增加可观测证据，再进行最小变更。

## 14. API 与兼容性

语义化版本只在兼容性承诺真实存在时使用。

公共头文件变更可能影响编译、链接和运行时行为。

删除字段前先停止写入，再兼容读取，最后清理。

协议演进优先采用向后兼容的新增字段。

错误码和日志字段保持稳定，便于自动化处理。

## 15. 发布治理

发布候选制品在隔离环境做冒烟测试。

变更窗口应避开高峰和不可逆迁移。

回滚方案必须在发布前验证，而不是出故障才编写。

发布审批依据风险证据，不依赖个人记忆。

## 16. 依赖升级

升级前记录当前版本、漏洞状态和行为基线。

先升级补丁版本，再处理跨主版本破坏性变化。

锁文件冲突要重新解析并审查完整差异。

删除未使用依赖可降低构建时间和攻击面。

## 17. 并行构建

编译任务应声明精确输入，避免共享临时文件。

并行链接可能受内存峰值约束，需要资源上限。

远程缓存必须校验编译器和源码哈希。

缓存命中率应作为构建效率指标。

## 18. 文档与知识

README 说明入口和最小成功路径。

设计文档记录不变量、边界和失败模式。

操作手册提供可复制命令和预期输出。

示例代码应定期在 CI 中编译。

## 19. 代码评审

评审先看行为、数据流和错误处理，再看格式。

大型变更拆成可独立验证的提交。

评审意见区分阻塞项、建议项和问题澄清。

作者回应每条意见并更新测试证据。

## 20. 交付指标

Lead time、部署频率、变更失败率和恢复时间反映交付系统。

指标不用于惩罚团队，否则会诱导隐藏失败。

构建队列时间过长时优先分析瓶颈节点。

测试失败率按类型统计，避免把 flaky 与真实缺陷混合。

## 21. 最终检查

- [ ] 变更有唯一需求或缺陷编号
- [ ] 构建、测试、扫描和制品证据可追溯
- [ ] 兼容性、迁移和回滚影响已评估
- [ ] 运行手册、告警和负责人已更新
- [ ] 失败路径和资源清理经过验证

## 22. 小结

构建系统描述输入、工具和输出。

依赖管理控制变化和供应链风险。

测试体系提供不同速度与置信度的反馈。

CI 将规则自动化并保存证据。

发布系统保证制品可追溯、可观测、可回滚。

架构记录帮助团队在时间中保持一致。

工程质量来自持续反馈，而非一次性检查。

遇到不确定性时，先增加实验和测量。

每项自动化都应有失败提示和人工接管路径。

团队应定期删除无效规则、过期依赖和无人维护脚本。

构建和测试结果应可被机器解析。

失败产物保留足够时间供调查。

变更风险随影响范围和不可逆程度上升。

自动化优先覆盖高频、易错、可验证流程。

手工步骤必须有负责人和操作记录。

这套方法适用于库、服务、工具和游戏客户端。

完成定义应同时包含代码、测试、文档和运行准备。

质量门禁服务于反馈，不应成为形式审批。

指标变化需要结合上下文和用户影响解释。

最终目标是让可靠交付成为默认路径。

持续改进从可重复的证据开始。

责任边界应在工具和文档中体现。
