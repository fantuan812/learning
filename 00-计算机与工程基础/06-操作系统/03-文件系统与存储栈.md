## 可运行实验

### 环境

- Linux 6.1+，ext4/XFS 文件系统。
- 工具：`fio`、`iostat`、`blktrace`、`strace`。
- 使用独立测试目录，禁止在生产盘执行破坏性命令。

```bash
mkdir -p /tmp/fs-lab && mountpoint /tmp
df -T /tmp
fio --version
```

预期输出包含文件系统类型和 fio 版本；缺少工具时记录安装来源，不直接修改系统镜像。

### 顺序与随机写入

```bash
fio --name=seq --directory=/tmp/fs-lab --rw=write --bs=1M --size=1G \
  --iodepth=32 --direct=1 --runtime=30 --time_based --group_reporting
fio --name=rand --directory=/tmp/fs-lab --rw=randwrite --bs=4k --size=1G \
  --iodepth=32 --direct=1 --runtime=30 --time_based --group_reporting
```

记录 bandwidth、IOPS、clat p50/p95/p99、CPU 使用率和队列深度。重复三次，报告中位数与离散度。

### 页缓存与 fsync

```bash
strace -f -e trace=openat,write,fdatasync,fsync \
  dd if=/dev/zero of=/tmp/fs-lab/a bs=4k count=1024 conv=fsync
sync
iostat -xz 1 5
```

`conv=fsync` 应在结束前出现同步调用；若只观察到 write，检查 dd 实现与跟踪过滤器。

### 崩溃一致性模型

测试程序按“写临时文件—fsync 文件—rename—fsync 目录”顺序更新清单。每轮在 rename 前后终止进程，重启后校验清单只包含旧版本或完整新版本，不接受半行数据。

```text
打开 tmp(O_CREAT|O_EXCL)
写入并 fsync(tmp)
rename(tmp, live)
打开父目录并 fsync(dir)
```

失败信号：出现空文件、截断 JSON、目录项丢失。回滚：删除实验目录并恢复备份快照，不对根文件系统运行 fsck。

### Benchmark 矩阵

|变量|水平|
|---|---|
|文件系统|ext4、XFS|
|块大小|4K、64K、1M|
|访问模式|顺序、随机|
|同步策略|buffered、direct、fsync|
|队列深度|1、8、32|
|介质|NVMe、SATA（若可用）|

验收阈值：同一配置三次运行的 p99 差异小于 20%；超过则增加预热轮次并报告后台回收、温控和 dirty pages。

## 故障排查

1. 吞吐低：检查 `iostat -xz` 的 await、util、队列深度。
2. p99 抖动：检查 GC、温度、内核回写和 SSD 磨损。
3. fsync 慢：确认设备缓存策略与挂载选项，区分 fsync 与 fdatasync。
4. 空间异常：检查稀疏文件、预留块、inode 使用率。
5. 目录遍历慢：用 `perf record -g` 区分 dentry miss 与磁盘延迟。

## 目标
理解路径到介质的完整数据路径，并能解释一致性、崩溃恢复与尾延迟。

## 分层
1. 应用通过 `open/read/write/fsync` 表达意图。
2. VFS 统一 inode、dentry、file 与 mount。
3. 文件系统实现 ext4、XFS、Btrfs 的目录、分配与日志。
4. 页缓存合并小写入，回写线程受 dirty ratio 控制。
5. 块层负责 bio、I/O scheduler、队列深度与合并。
6. 驱动把请求转换为 NVMe/SATA 命令。
7. SSD FTL 完成映射、磨损均衡、垃圾回收。

## 核心对象
- inode 保存类型、权限、大小、时间和块映射。
- dentry 缓存名称到 inode 的解析结果。
- superblock 描述文件系统参数与特性。
- journal 记录元数据事务，保证崩溃后可重放。
- extent 以连续区间描述文件块，降低元数据开销。

## 一致性语义
- `write` 通常只修改页缓存，不代表持久化。
- `fsync(fd)` 推进数据及必要元数据到稳定介质。
- `fdatasync` 尽量省略与数据无关的元数据。
- `rename` 在同一文件系统内具有原子名字切换语义。
- 临时文件写完后 `fsync`，再 rename，最后 fsync 目录。
- 数据库 WAL 与文件系统日志是两层协议，不能混为一谈。

## 崩溃恢复
1. 写入意图进入 journal 或 copy-on-write 树。
2. 提交记录带校验和与序列号。
3. 掉电后扫描未完成事务。
4. 重放已提交记录，撤销未提交记录。
5. 文件系统恢复成功不等于应用数据完整，应用仍需 WAL/校验。

## 性能模型
- 机械盘瓶颈是 seek 与 rotational latency。
- SSD 瓶颈包括并行队列、写放大、GC 和热节流。
- 随机 IOPS 受请求大小、队列深度、同步点影响。
- 吞吐提升可能牺牲尾延迟；必须观察 p95/p99。
- 页缓存命中隐藏介质延迟，冷缓存 benchmark 才能暴露真实成本。

## 诊断清单
- `stat` 检查 inode、链接数和时间。
- `df` 看容量，`df -i` 看 inode 耗尽。
- `du` 与 `lsof +L1` 定位删除但仍占用空间的文件。
- `iostat -xz` 观察 await、util、队列。
- `vmstat` 观察回写、swap 与 runnable。
- `blktrace`/eBPF 关联应用请求与块设备完成。

## 工程实践
- 日志采用追加写、分段滚动和校验和。
- 关键配置使用原子替换，避免半写文件。
- 大文件顺序读使用 `posix_fadvise` 提示模式。
- 临时缓存明确淘汰策略，避免页缓存与应用缓存双重占用。
- 备份验证必须做恢复演练，而非只检查备份成功日志。

## 实验
- 比较 buffered I/O、`O_DIRECT`、mmap 的延迟分布。
- 注入断电/kill -9，验证 rename+fsync 流程。
- 调整 dirty_background_ratio，观察回写抖动。
- 逐步增加 NVMe queue depth，绘制吞吐与 p99 曲线。
- 通过 fio 对比 4K 随机与 1M 顺序负载。

## 易错点
- `close` 不保证数据已落盘。
- mmap 修改页也需要 msync/fsync 组合与明确语义。
- 磁盘满、inode 满、quota 满是三种不同故障。
- RAID 提升可用性不等于提供应用级一致性。
- SSD 的“已完成”仍可能停留在设备易失缓存，需正确 flush。

## 实验与 Benchmark

### 系统调用与页缓存

目标是拆分用户态、VFS、文件系统、块层和设备延迟。准备 1 GiB 文件，使用 4 KiB、64 KiB、1 MiB 缓冲区各复制五次，并分别测试冷缓存和热缓存。

```bash
strace -tt -e trace=openat,read,write,fsync ./file_copy a.bin b.bin
perf stat -e cycles,instructions,cache-misses,major-faults,minor-faults ./file_copy a.bin b.bin
```

记录吞吐、系统调用次数、CPU 周期/字节和 p95。冷缓存通常受设备与队列影响，热缓存通常受 memcpy、分支和调用开销影响。`fsync` 会把设备持久化延迟暴露出来。

### 持久化与崩溃一致性

程序先写临时文件、`fdatasync`、`rename`，最后对目录 `fsync`。在每个步骤之间发送 `SIGKILL`，重启后校验目标内容是否为旧版本或新版本。

```c
write(fd, data, len); fdatasync(fd); close(fd);
rename(".tmp", "target");
int d=open(".",O_DIRECTORY|O_RDONLY); fsync(d); close(d);
```

比较 ext4 `data=ordered/writeback` 与 XFS。原子 rename 只保证命名空间切换，不保证数据已经穿透设备易失缓存。

### fio 工作负载矩阵

```bash
fio --name=seq --filename=test.dat --rw=read --bs=1M --size=4G --iodepth=32 --direct=1 --runtime=60 --time_based
fio --name=rand --filename=test.dat --rw=randread --bs=4k --size=4G --iodepth=32 --direct=1 --runtime=60 --time_based
```

矩阵维度包括顺序/随机、读写比例、块大小 4K/64K/1M、iodepth 1/16/64、buffered/direct。报告 IOPS、MB/s、p50/p95/p99、await、队列长度和设备 util。

### 排障清单

1. 确认是否 buffered/direct I/O。
2. 查看 `vmstat` dirty、pgscan、swap。
3. 查看 `iostat -x` await、队列与利用率。
4. 用 blktrace/bpftrace 检查请求合并与重试。
5. 区分文件系统锁、块设备、网络存储 RTT。
6. 检查 inode、quota、稀疏文件和 mount 选项。
7. 记录内核、文件系统、设备固件和 CPU 频率。

### Benchmark 模板

| 类别 | 必填内容 |
|---|---|
| 环境 | 内核、文件系统、挂载参数、设备型号 |
| 负载 | 总大小、块大小、随机性、并发度 |
| 方法 | 预热、冷缓存、样本数、统计方式 |
| 指标 | 吞吐、IOPS、p50/p95/p99、错误率 |
| 结论 | 瓶颈证据、置信区间、适用边界 |

### 常见误区

- 把 `du` 与 `ls -l` 差异误判为数据丢失，实际可能是稀疏文件。
- 只看平均延迟，忽略刷盘和 GC 造成的长尾。
- 在容器内测试却忽略宿主机 cgroup I/O 限额。
- 用单线程小文件结果推导数据库或对象存储性能。
- 把 RAID 可用性误认为应用级一致性。
- 认为写系统调用返回即代表掉电安全。

## 可复现故障注入与恢复验收

以下步骤只在专用 loop 镜像或临时目录执行。先建立可回滚的镜像，记录哈希，禁止把设备名替换成生产盘。

```bash
truncate -s 2G /tmp/fs-lab.img
mkfs.ext4 -F /tmp/fs-lab.img
mkdir -p /tmp/fs-mnt
sudo mount -o loop /tmp/fs-lab.img /tmp/fs-mnt
sha256sum /tmp/fs-lab.img > /tmp/fs-lab.before.sha256
```

### 写入中断矩阵

测试程序每 100 ms 原子替换一个带序列号的文件，并在以下阶段注入 `SIGKILL`：写入、文件 fsync、rename、目录 fsync。重启挂载后执行校验脚本，要求文件内容只能是完整的 `generation=N` 或 `generation=N-1`。

|阶段|预期状态|观测命令|失败判定|
|---|---|---|---|
|write 未完成|旧文件|`cat live`|出现半行或非法校验和|
|file fsync 后|临时文件完整|`stat .tmp`|临时文件损坏|
|rename 后|新旧名字二选一|`ls -li`|目录项指向不存在 inode|
|dir fsync 后|新名字持久|重新挂载后 `cat live`|出现空文件|

恢复验收包括：`e2fsck -fn` 无未预期错误、镜像 SHA-256 变化可解释、应用校验和通过、挂载参数未被修改。任何 `fsck` 修复操作都必须复制镜像后再做。

### 页缓存回写实验

```bash
sysctl vm.dirty_background_bytes vm.dirty_bytes
dd if=/dev/zero of=/tmp/fs-lab/cache.bin bs=1M count=512 status=progress
grep -E 'Dirty|Writeback' /proc/meminfo
vmstat 1 10
```

记录 Dirty/Writeback 峰值、写入耗时和回写期间的 p99。将 `vm.dirty_bytes` 调低后重复，预期前台写入更早受到节流；恢复原值并确认 `/proc/meminfo` 的 Writeback 回到基线。

### 故障矩阵与处置

|症状|优先证据|可能原因|恢复动作|
|---|---|---|---|
|ENOSPC|`df -h`,`df -i`|容量或 inode 耗尽|清理临时文件，扩容前保留快照|
|写入卡顿|`iostat -xz`,`vmstat`|脏页回写或设备 GC|降低并发，等待回写，检查温度|
|删除后空间未释放|`lsof +L1`|进程仍持有 fd|滚动重启持有者，确认空间回收|
|挂载只读|`dmesg`,`findmnt`|I/O 错误或错误计数|停止写入，复制镜像后离线检查|
|fsync 延迟尖峰|`perf`,`blktrace`|设备 flush、队列拥塞|分离同步批次，保留 p99 证据|
|恢复后缺少新文件|应用 WAL/校验和|目录未 fsync 或设备缓存|重放 WAL，修订持久化协议|

### Benchmark 结果记录

每个工作负载至少保存 fio JSON、`iostat` 原始日志和环境快照：

```bash
fio --output-format=json --output=/tmp/fs-lab/fio.json \
  --name=rand4k --filename=/tmp/fs-mnt/data --rw=randrw \
  --rwmixread=70 --bs=4k --size=512M --iodepth=16 \
  --direct=1 --runtime=60 --time_based --group_reporting
uname -a > /tmp/fs-lab/uname.txt
findmnt -T /tmp/fs-mnt > /tmp/fs-lab/mount.txt
```

验收阈值：三次中位数相对偏差小于 10%，p99 退化超过 20% 必须标记为回归；不同设备不得直接比较绝对值，只比较同机相对变化。报告中同时给出失败请求数、超时数和温度。

### 回滚与清理验收

```bash
sync
sudo umount /tmp/fs-mnt
sha256sum -c /tmp/fs-lab.before.sha256 || true
rm -f /tmp/fs-lab.img
rm -rf /tmp/fs-mnt /tmp/fs-lab
```

清理后确认 `mountpoint /tmp/fs-mnt` 返回非挂载状态，`lsof +D /tmp/fs-mnt` 无残留进程，生产 `df -h` 与实验前一致。若镜像检查失败，保留镜像和日志，不继续删除。
