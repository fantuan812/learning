# 容器云与可观测性基础

> 知识成熟度：L2（Linux 机制与观测闭环已有实验计划但尚未形成运行证据；云平台行为需目标环境验证）。
> 知识基线：Namespace/cgroups、容器运行时、Metrics/Logs/Traces、SLO 与容量模型。
> 最后更新：2026-08-20。
> 官方参考：[OpenTelemetry](https://opentelemetry.io/docs/)、[Linux cgroups](https://docs.kernel.org/admin-guide/cgroup-v2.html)。
> 验证入口：用容器限制、故障注入和观测查询验证资源与告警。
> 验证与基准：记录 CPU/内存限制、采集延迟、错误率和容量 P95/P99。
> 证据状态：当前未保存容器编排文件、故障注入脚本、指标查询结果或容量测试原始数据。

## 1. Linux 隔离

Namespace 隔离进程、挂载、网络、用户、IPC、UTS 和 cgroup 视图。

PID namespace 让容器拥有独立进程树，但宿主仍可观察和管理它。

Mount namespace 配合只读根文件系统、bind mount 和 tmpfs 组织文件视图。

Network namespace 提供独立接口、路由表、iptables 和端口空间。

User namespace 将容器 root 映射为宿主非特权用户。

Cgroup 控制 CPU、内存、IO、进程数和设备访问。

资源限制触发 OOM、节流或回收时必须有指标和告警。

## 2. 容器镜像

镜像由内容寻址层和配置清单组成，层可复用但不可变。

Dockerfile 应使用固定基础镜像、少量层和非 root 用户。

多阶段构建把编译工具与运行时分开，减少攻击面。

镜像标签可变，生产部署应固定 digest。

SBOM 列出组件和版本，扫描结果要区分可达性与实际风险。

签名和验证建立制品来源信任，但不能替代运行时权限控制。

## 3. 运行时

OCI image、runtime 和 distribution 规范定义了互操作边界。

容器启动过程包括拉取、解包、创建 namespace、配置 cgroup 和执行入口。

优雅停止先发送 TERM，再经过宽限期发送 KILL。

探针分为启动、存活和就绪，失败含义不同。

就绪失败应摘除流量，存活失败才考虑重启。

进程应把日志写到标准输出，由平台统一收集。

## 4. 网络

容器网络常见模型有 bridge、host、overlay 和 CNI 插件。

Service 把稳定虚拟地址映射到短生命周期实例。

DNS 服务发现要考虑缓存、TTL、负载和故障传播。

入口层负责 TLS、路由、限流和连接超时。

网络策略按最小连通性放行，而不是默认全网互通。

连接池、重试和超时必须共同设计，避免重试风暴。

## 5. 存储

容器文件系统通常是临时层，重启后不保证数据存在。

Volume 生命周期独立于容器，适合持久数据。

Stateful 工作负载需要稳定身份、顺序启动和备份恢复。

存储类描述性能、可用区、加密和回收策略。

备份必须定期演练恢复，并测量 RPO 与 RTO。

## 6. 调度

请求值参与放置，限制值定义运行上限；二者都应基于实测。

节点亲和、反亲和和拓扑分布影响高可用与成本。

污点和容忍度隔离 GPU、专用网络或维护节点。

抢占、驱逐和滚动更新要有业务感知的优雅终止。

水平扩缩容依赖稳定指标，避免只按 CPU 推断用户负载。

## 7. 安全

容器安全包括镜像、运行时、网络、身份和供应链。

禁止特权容器、host PID、host network 和不必要设备映射。

使用 seccomp、Capabilities、AppArmor 或 SELinux 收窄系统调用。

密钥通过专用 Secret 管理，避免写入镜像和日志。

服务账号只授予所需 API 权限，定期审计绑定关系。

## 8. 指标

Counter 只增不减，Gauge 表示瞬时值，Histogram 描述分布。

指标名称、单位和标签要稳定，避免高基数用户 ID 标签。

延迟应使用分位数和桶，平均值不能代表尾延迟。

RED 关注请求率、错误率和耗时；USE 关注利用率、饱和度和错误。

采集端要设置超时、重试和丢弃策略，避免监控系统反过来拖垮服务。

## 9. 日志

结构化日志包含时间、级别、消息、请求 ID、服务和版本。

错误日志应包含上下文和动作建议，不记录凭据和隐私。

采样、聚合和保留策略需按故障调查需求制定。

日志时间统一 UTC，并同步时钟以便跨主机排序。

## 10. 追踪

Trace 由 Span 组成，传播上下文贯穿网关、服务和数据库。

Span 名称应稳定，属性控制在低基数且不含敏感数据。

尾采样可以保留错误和高延迟请求，但需要采集链路支持。

关联 trace ID、日志和指标能缩短定位路径。

异步消息要显式传递上下文，并记录生产与消费时间。

## 11. OpenTelemetry

统一 API 与 SDK，导出器把数据发送到 Collector 或后端。

Collector 可做批处理、采样、脱敏和路由，减轻应用耦合。

资源属性记录服务名、版本、环境和实例。

仪表化应优先覆盖关键用户路径和边界调用。

升级 SDK 要验证采样、批量和内存开销。

## 12. SLI 与 SLO

SLI 是用户可感知的成功比例、延迟或新鲜度测量。

SLO 指定目标窗口，例如滚动 30 天的可用性。

错误预算是允许失败的余量，用于平衡速度与稳定性。

告警应针对预算消耗速度，而非每个瞬时抖动。

SLO 例外、维护窗口和多区域聚合必须明确。

## 13. 容量与成本

容量模型把请求率、并发、资源消耗和尾延迟联系起来。

压测使用接近生产的数据分布，并覆盖冷启动和故障场景。

预留容量应满足故障转移、升级和突发峰值。

成本按服务、团队和环境分摊，避免只看集群总账单。

空闲资源、过度请求和无效日志是常见浪费来源。

## 14. 故障处理

Runbook 写明症状、检查命令、回滚步骤和升级联系人。

故障优先保护用户数据和可用性，再追求根因完整性。

熔断、限流、舱壁和降级应有明确恢复条件。

演练验证备份、区域故障、证书过期和依赖不可用。

事后复盘聚焦系统改进，不把责任归因于个人疏忽。

## 15. 反模式

只监控 CPU、无限重试、日志无结构、探针检查错误依赖、容器使用 root、镜像用 latest、把所有标签设成用户 ID、没有预算驱动告警，都会制造不可控风险。

## 16. 检查清单

- [ ] 镜像固定 digest 并有 SBOM
- [ ] 容器非 root、最小 capability、只读根文件系统
- [ ] 请求、限制、探针和优雅停止已设置
- [ ] 网络策略和 Secret 权限经过审计
- [ ] 指标、日志、追踪可按版本和请求关联
- [ ] 关键路径有 SLI、SLO 和错误预算
- [ ] 有容量模型、成本归属和恢复演练

## 17. 集群控制面

控制面保存期望状态，节点代理负责收敛实际状态。

声明式配置应幂等，重复应用不会产生额外副作用。

控制器处理事件和队列，必须具备退避与去重。

资源版本冲突需要乐观并发控制和重试。

控制面不可用时，已运行工作负载应保持数据面服务。

## 18. 发布策略

滚动更新限制同时不可用实例数量。

蓝绿发布保留旧环境，切换快但成本更高。

金丝雀发布按流量或租户逐步扩大范围。

回滚要同时处理配置、数据库和缓存兼容性。

## 19. 可靠性模式

超时是资源保护边界，不是越长越安全。

重试只针对幂等、瞬态错误，并使用指数退避和抖动。

熔断器在连续失败后快速失败，恢复时半开探测。

舱壁隔离线程、连接和队列，避免单依赖耗尽全局资源。

降级返回可接受的旧数据或有限功能。

## 20. 数据与隐私

遥测数据应分类，明确个人信息、业务机密和公开字段。

采集前做脱敏、哈希或采样，删除不必要字段。

访问日志和追踪后端启用最小权限与审计。

保留期限与法规、调查需求和成本共同决定。

跨区域传输要评估数据驻留和加密要求。

## 21. 多租户

租户隔离可在命名空间、网络、身份和数据层组合实现。

配额防止单租户消耗共享资源。

公平调度需要按租户统计请求率、延迟和错误。

噪声邻居问题通过限流、舱壁和独立节点缓解。

## 22. 成本工程

资源标签必须覆盖团队、服务、环境和版本。

按 CPU、内存、存储、出口流量和遥测量分摊成本。

右尺寸化基于峰值、分位数和故障余量。

自动关停临时环境，避免忘记释放。

成本告警与容量告警分离，便于定位动作。

## 23. 调试路径

先确认影响范围、时间线和版本，再进入单实例。

用指标定位异常窗口，用追踪定位依赖，用日志确认原因。

检查调度事件、资源压力、网络策略和证书状态。

收集诊断信息时避免执行破坏性命令。

临时修复要记录过期时间和后续永久方案。

## 24. 学习与演练

定期演练节点丢失、区域故障、镜像仓库不可用。

演练结果形成可执行改进项和负责人。

新成员通过最小服务部署和故障注入熟悉平台。

保留真实事故的匿名样例用于回归测试。

## 25. 平台检查

- [ ] 控制面和数据面职责清晰
- [ ] 发布、回滚和迁移有自动化路径
- [ ] 超时、重试、熔断和限流参数有依据
- [ ] 遥测脱敏、保留和访问策略已定义
- [ ] 多租户配额和成本归属可查询
- [ ] 故障演练覆盖关键依赖和恢复目标

## 26. 小结

容器把进程和资源边界显式化。

云平台负责调度、发现、发布和修复。

可观测性把运行状态转换为可查询证据。

SLO 把技术信号连接到用户结果。

容量、成本和安全必须与可靠性一起设计。

平台规则应尽量自动化，并保留清晰的逃生通道。
