# 安全与密码基础总览
> 验证与基准：按文中命令执行最小实验，记录结果与边界。

> 知识成熟度：L2（威胁模型与标准资料核对；具体系统需安全评审）。
> 知识基线：机密性、完整性、可用性、密码学、认证授权、内存安全与 SDL。
> 最后更新：2026-08-20。
> 官方参考：[OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)、[NIST CSF](https://www.nist.gov/cyberframework)。
> 验证入口：使用威胁建模、静态分析、依赖扫描和安全测试复核。

## 1. 安全目标与威胁模型

### 1.1 CIA 与扩展目标

- 机密性：未授权主体不能读取数据。
- 完整性：数据和状态不能被未授权篡改。
- 可用性：合法用户在目标时间内得到服务。
- 真实性：能够确认消息或主体来源。
- 可审计性：关键行为可追溯且日志不可抵赖。
- 隐私性：减少不必要收集，控制关联与推断风险。

### 1.2 资产、主体与边界

- 资产包括账号、密钥、源码、玩家财产、服务容量和声誉。
- 主体包括用户、客户端、服务端、管理员、第三方和自动化作业。
- 信任边界是权限或验证规则发生变化的位置。
- 数据流图应标注入口、出口、存储、处理器和跨边界传输。

### 1.3 攻击者与风险

- 匿名远程攻击者、被盗账号、恶意客户端和内部人员能力不同。
- 风险可粗略表示为影响乘以发生可能性；不要用单一分数掩盖假设。
- 关注攻击路径、前置条件、检测能力和恢复成本。
- 安全控制应与威胁优先级匹配，避免高成本低收益的形式主义。

### 1.4 常见模型

- STRIDE：欺骗、篡改、抵赖、信息泄露、拒绝服务、权限提升。
- Attack tree 从攻击目标向前展开必要条件或替代路径。
- Abuse case 描述“攻击者如何滥用正常功能”。
- 数据分级决定加密、保留、脱敏与访问审计要求。

## 2. 密码学基本概念

### 2.1 密钥与随机数

- 密钥必须来自密码学安全随机源，不能使用时间、进程号或 `rand()`。
- 密钥、口令、令牌、盐和 nonce 是不同概念，生命周期也不同。
- 密钥应有生成、分发、使用、轮换、吊销、备份和销毁策略。
- nonce 通常不要求保密，但在同一密钥下必须满足算法规定的唯一性。

### 2.2 哈希与消息认证

- 哈希提供固定长度摘要，要求抗原像、抗第二原像和抗碰撞。
- SHA-2/SHA-3 用于摘要；不要把快速哈希用于口令存储。
- MAC 需要共享密钥，HMAC 是常见构造。
- 比较 MAC 时使用常数时间比较，避免时序泄漏。

### 2.3 对称加密

- AEAD 同时提供机密性和完整性，优先使用 AES-GCM 或 ChaCha20-Poly1305 等成熟方案。
- ECB 会泄露块模式，禁止用于一般数据。
- CBC 若使用不当会遭遇填充预言机；应使用经过认证的构造。
- AAD 可认证但不加密元数据，如版本号、租户号和路由信息。
- 密文、nonce、tag 和算法版本应按协议明确编码。

### 2.4 非对称密码

- 公钥加密解决密钥分发，数字签名解决身份认证和完整性。
- RSA、椭圆曲线等参数必须采用标准推荐尺寸和实现。
- 签名验证前先明确编码、上下文和算法标识，防止混淆攻击。
- 私钥存储应使用受保护密钥库或硬件模块，避免进入日志和崩溃转储。

### 2.5 密钥派生与口令

- KDF 用于从主密钥或口令派生用途隔离的子密钥。
- 口令存储使用 Argon2id、scrypt 或 bcrypt 等带成本参数的方案。
- 每个口令使用独立随机盐；盐不需要保密，但必须持久化。
- 口令策略应结合速率限制、多因素认证和泄露检测，而不是只要求复杂度。

### 2.6 随机数与重放

- challenge、session nonce 和令牌标识要有足够熵并避免重复。
- 防重放可使用 nonce 缓存、单调计数器、时间窗和服务器端状态。
- 分布式生成 ID 时要评估碰撞、排序泄露和跨区域时钟问题。

## 3. 安全协议与传输

### 3.1 TLS 与证书

- TLS 提供传输机密性、完整性和服务器身份认证。
- 客户端必须验证证书链、域名、有效期和吊销策略。
- 禁止关闭证书校验来“解决开发环境问题”；应使用受信任测试 CA。
- 版本、密码套件和曲线使用平台默认安全配置并持续更新。

### 3.2 会话与令牌

- 会话令牌应不可预测、短生命周期、可撤销并绑定必要上下文。
- Cookie 设置 `Secure`、`HttpOnly`、合适的 `SameSite` 属性。
- JWT 的签名算法、受众、签发者和过期时间必须显式校验。
- 不把敏感信息放入可被客户端读取或长期缓存的令牌载荷。

### 3.3 安全消息协议

- 每条消息应包含版本、类型、长度、序列号和认证范围。
- 解析器先做长度和资源限制，再执行昂贵的解码。
- 失败响应不要泄露密钥、内部路径或详细验证分支。
- 协议变更采用版本协商和向后兼容测试，避免降级攻击。

## 4. 身份认证与授权

### 4.1 身份生命周期

- 注册、验证、恢复、冻结、注销和删除必须有一致状态机。
- 高风险操作应重新认证或要求多因素确认。
- 账号恢复是高价值攻击面，不能只依赖可猜测个人信息。

### 4.2 多因素认证

- 知识因子：口令或 PIN；持有因子：硬件密钥或设备；生物因子：指纹等。
- 优先使用抗钓鱼的 WebAuthn/FIDO2；短信验证码不是强认证。
- 备份码要一次性、可撤销并安全展示。

### 4.3 授权模型

- 最小权限：主体只获得完成任务所需权限。
- RBAC 按角色授权；ABAC 按主体、资源、动作和环境属性判定。
- ACL 适合资源级控制；能力令牌把权限封装到不可伪造的引用中。
- 默认拒绝，显式允许；权限检查应集中并可审计。

### 4.4 服务间身份

- 服务账号分离，禁止共享管理员凭据。
- mTLS、短期 token 和工作负载身份优于静态密钥。
- 权限应区分读、写、管理和破坏性操作。
- 轮换期间支持双密钥窗口，完成后撤销旧密钥。

## 5. 输入、输出与应用安全

### 5.1 输入验证

- 语法验证、语义验证和业务不变量分层执行。
- 使用允许列表和结构化解析，避免黑名单遗漏。
- 限制长度、深度、数量、时间和内存，防止资源耗尽。
- 将外部输入视为不可信，即使来自“内部”服务。

### 5.2 注入与编码

- SQL 使用参数化查询；Shell 使用参数数组而非拼接命令。
- HTML 输出按上下文编码，模板默认转义。
- 路径拼接要阻止 `..`、绝对路径、符号链接和编码绕过。
- JSON、URL、日志和数据库各有不同编码规则，不能混用转义函数。

### 5.3 CSRF、XSS 与 SSRF

- CSRF 保护使用 SameSite、不可猜 token 和来源校验组合。
- XSS 防御依赖上下文输出编码、CSP 和安全模板。
- SSRF 需要限制协议、解析结果、重定向、内网地址和 DNS 重新绑定。
- 管理接口与元数据服务应有独立网络策略和身份验证。

## 6. 内存安全

### 6.1 常见漏洞

- 越界读写、Use-after-free、Double free、整数溢出和格式化字符串。
- 未初始化内存可能泄露密钥或改变控制流。
- 竞态条件会把本来安全的检查与使用拆开。
- 反序列化对象若缺乏边界检查会形成远程代码执行入口。

### 6.2 C/C++ 防护

- 优先 RAII、智能指针、`std::span`、边界感知容器和明确所有权。
- 避免裸 owning pointer；接口文档写清借用、转移和线程安全。
- 有符号/无符号转换、乘法溢出和长度截断要显式检查。
- 使用 ASan、UBSan、TSan、静态分析和模糊测试。
- 编译启用栈保护、PIE、RELRO、CFI 等平台支持的缓解措施。

### 6.3 生命周期与并发

- 引用计数不能自动解决循环引用和并发竞态。
- 原子操作要匹配内存序，发布对象前保证初始化完成。
- 资源释放路径包括异常、取消、超时和部分初始化。
- 采用单一所有者、不可变数据或消息传递降低共享状态风险。

### 6.4 安全语言与边界

- Rust 等内存安全语言减少一类漏洞，但仍需验证逻辑、权限和不安全块。
- FFI 边界进行长度、编码、所有权和异常转换检查。
- 第三方库版本、构建产物和供应链来源必须可追踪。

## 7. 日志、检测与响应

- 日志记录主体、动作、资源、结果、时间、关联 ID 和来源。
- 禁止记录口令、完整 token、私钥和未经脱敏的个人数据。
- 日志写入通道应防篡改、限速并与业务故障隔离。
- 告警按严重度、置信度和处置时限分级，避免告警疲劳。
- 事件响应流程包括确认、遏制、根除、恢复和复盘。
- 保留取证所需证据链，同时遵守数据最小化与保留期限。

## 8. 安全开发生命周期

- 需求阶段建立资产清单、滥用案例和安全验收标准。
- 设计阶段进行威胁建模、密钥方案评审和信任边界审查。
- 编码阶段启用 lint、SAST、依赖扫描和秘密扫描。
- 测试阶段加入 DAST、模糊测试、权限矩阵和故障注入。
- 发布阶段签名制品、生成 SBOM、执行灰度和回滚演练。
- 运行阶段监控漏洞、密钥轮换、补丁时限和异常行为。

## 9. 游戏与服务端场景

- 客户端永远不是真实裁判；关键状态由服务端验证和重放保护。
- 货币、道具、匹配和排行榜更新必须幂等且可审计。
- 反作弊是风险控制系统，不应依赖单一客户端检测。
- GM/运营工具实施分权、审批、双人复核和高质量审计。
- 回放与遥测数据脱敏，避免泄露玩家隐私和内部协议。

## 10. 最低实践清单

- 能画出一个服务的数据流和信任边界。
- 能解释 AEAD、KDF、盐、nonce、MAC、签名的用途差异。
- 能设计登录、会话、授权和密钥轮换状态机。
- 能识别注入、越界、UAF、重放和权限提升路径。
- 能在 CI 中运行静态分析、依赖扫描、秘密扫描和模糊测试。
- 能制定事件响应、证据保留和漏洞修复 SLA。

## 11. 常见错误清单

- 自己设计加密算法或修改标准算法常量。
- 把 Base64、异或或编码误认为加密。
- 使用可预测 UUID、时间戳或递增 ID 作为安全 token。
- 在日志、URL、分析事件中泄露访问令牌。
- 只验证 JWT 签名，不验证 `iss`、`aud`、过期和算法。
- 只在网关授权，内部服务缺少对象级权限检查。
- 用客户端传来的价格、伤害、库存作为最终事实。
- 把管理员调试接口留在生产网络中。
- 用黑名单过滤危险字符串，忽略解析上下文。
- 关闭 TLS 校验、CORS 或 CSRF 保护来绕过测试问题。
- 忽略 DNS、重定向和 IPv6 导致的 SSRF 绕过。
- 仅依靠单元测试而没有模糊测试和边界测试。
- 认为内存安全语言自动解决认证和业务逻辑漏洞。
- 把依赖扫描报告全部标为误报而不记录理由。
- 不验证构建制品来源、签名和可复现性。
- 发生事件后只打补丁，不修复检测和恢复流程。
- 没有密钥轮换演练，导致泄露后无法快速止血。
- 让所有服务共用一个数据库超级用户。
- 把安全告警直接发送给无权限的公共频道。
- 以“内部网络可信”为由跳过身份和加密。
- 依赖人工记忆权限，未建立可审计的矩阵。
- 以高复杂度口令规则替代多因素认证和速率限制。
- 不区分认证失败、授权失败和资源不存在的处理策略。
- 对错误响应返回堆栈、SQL、路径和密钥元数据。
- 未设置请求体、递归深度、解压倍率和并发上限。

## 12. 复核问题

- 谁能读取、修改、删除和导出这项资产？
- 这个结论依赖哪个身份、租户和时间上下文？
- 重放同一请求会发生什么？请求是否幂等？
- 密钥泄露后能否撤销、轮换并定位影响范围？
- 服务降级时安全默认值是什么？
- 失败是否泄露了“账号存在”“权限存在”等侧信道？
- 哪些日志能证明一次关键操作由谁完成？
- 第三方依赖和构建工具是否有可验证来源？
- 是否有自动化测试证明越权路径被拒绝？
- 这项控制的监控指标、告警阈值和负责人是谁？

## 13. 安全验证练习

- 为登录接口画 STRIDE 数据流图。
- 设计一次 token 重放测试并验证服务端拒绝。
- 检查 Cookie、CORS、CSRF 和 CSP 配置。
- 用参数化查询替换一处字符串拼接 SQL。
- 为文件上传加入类型、大小、路径和内容验证。
- 用 ASan 复现并修复一次越界写。
- 用 TSan 定位共享计数器竞态。
- 为服务账号建立只读、写入和管理权限矩阵。
- 设计密钥轮换的双版本兼容窗口。
- 检查崩溃转储和日志是否含秘密。
- 为反序列化入口加入深度和资源上限。
- 编写一个最小模糊测试器并保存崩溃样本。
- 生成 SBOM 并验证关键依赖签名。
- 演练撤销泄露 token、隔离主机和恢复服务。
- 复盘告警到处置的时间线和证据完整性。

## 14. 记忆卡片

- 安全先定义资产和边界。
- 机密性不等于完整性。
- 哈希不提供保密性。
- MAC 需要共享密钥。
- 签名提供来源和完整性。
- AEAD 同时认证密文。
- nonce 唯一性极其重要。
- 盐可公开但必须随机。
- KDF 用于用途隔离。
- TLS 必须验证证书。
- 令牌应短期、可撤销。
- 授权默认拒绝。
- 最小权限减少爆炸半径。
- 输入验证要限制资源。
- 参数化查询防注入。
- 客户端输入永远不可信。
- ASan 发现越界和 UAF。
- TSan 发现数据竞态。
- 日志不能记录秘密。
- 密钥必须可轮换。
- 依赖必须可追踪。
- 事件响应需要演练。
