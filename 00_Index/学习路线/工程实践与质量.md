# 工程实践与质量：学习路线

本页提供前置知识、阅读选择、练习与验收建议，知识成熟度：L0；主题细节由链接主文负责。练习均待执行，本文不提供新的 UE、运行时、生产或基准验证，也不表示所有正文事实已经全面核实。

## 调试与性能基础：保留现场再验证假设

先从 [调试与性能分析方法论](../../知识/08-工程实践与质量/调试与性能分析/01-调试与性能分析方法论.md)建立复现 → 保全现场 → 提出假设 → 缩小范围 → 修复 → 回归的循环，再读 [性能工具：插桩与 perf 采样](../../知识/08-工程实践与质量/调试与性能分析/03-性能工具：插桩与perf采样.md)。前置是[编程与计算机基础路线](编程与计算机基础.md)中的所有权、线程、ABI 与存储模型；否则调用栈和计数器只是现象。

内存破坏先用 ASan 检查适用的越界和释放后访问，未定义行为用 UBSan，并发数据竞争用 TSan；各工具支持平台、可组合性、覆盖范围与开销须按实际构建核对。它们不能证明没有所有死锁或逻辑竞态，旧导航的固定倍数开销只作为测量问题。线上崩溃用 GDB／LLDB／WinDbg、Core Dump／Minidump 和匹配的符号／二进制恢复现场，记录构建身份、输入和全线程栈；Core 生成策略和转储权限须纳入实际部署要求。

性能分析先用 RAII 计时或追踪分出 Tick、AOI、AI、网络与存盘阶段，再以 perf／Tracy／VTune／Unreal Insights 定位热点、等待、缓存缺失和调用路径。采样火焰图横向宽度表示该采样模型下的权重，不能当作完整时间轴；用时间线核对并发和尖峰，用系统指标核对 I/O 或 CPU 饱和。对死锁检查线程等待图，对高 CPU 检查自旋、循环和有效工作，不凭单张热点图决定修复。

练习交付一个带符号的最小崩溃包和一个尾延迟问题：保留修复前后的相同输入、命令、环境、断言与剖析材料。性能优化只在正确性不退化的条件下比较 P50／P95／P99 与资源代价；UE CrashReportClient／Symbol Server、Insights 和服务端自动转储属于后续实际环境接入，不由配置文件存在宣布可用。

工作快记保留为个人速查入口：[插桩测试速查](../../知识/08-工程实践与质量/调试与性能分析/插桩测试.md)用于定位指定阶段/耗时点，[perf 采样分析速查](../../知识/08-工程实践与质量/调试与性能分析/perf性能分析.md)用于寻找热点与调用路径，两者沿上面的性能工具主文对照使用。短笔记不替代主题主文、完整实验或原始工作记录；复用命令或结论时先补齐构建、平台、输入、采样/插桩开销和原始输出，未复测的历史观察不能成为当前性能验证。

## 工程与构建基础：依赖、反馈与交付

按 [软件工程与构建基础](../../知识/08-工程实践与质量/工程设计与协作/软件工程与构建基础.md) → [版本控制、依赖与构建工程](../../知识/08-工程实践与质量/工程设计与协作/版本控制依赖与构建工程.md) → [测试、静态分析、Fuzz 与持续交付](../../知识/08-工程实践与质量/测试策略与自动化/测试静态分析Fuzz与持续交付.md)推进。先把模块职责、单向依赖和技术债写成能验证的边界与 ADR，再选择分支／主干策略、Git LFS 和资源管理方式，最后把质量反馈放入构建与交付流程。

构建练习从 CMake／UBT 依赖图和头文件包含开始：比较完整构建、单个头文件变化、源文件变化以及缓存冷／热情况下的时长。IWYU、PCH、Unity Build、ccache／FASTBuild 或分布式编译都要记录失效范围、缓存命中和诊断影响，不继承“90 分钟降到 15 分钟”的未经本项目测量数字；大文件与美术资产是否拆仓，也要由协作、检出和版本一致性需求决定。

测试按风险配置单元、集成和系统反馈；使用 Clang-Tidy、Sanitizers 与 libFuzzer 检查外部协议解析。Fuzz 产物应包括语料、覆盖、可重现崩溃和资源限制，随机运行次数不是“彻底排除漏洞”的证明。CI Gate 要明确哪些检查必须通过、失败怎样回退；制品身份、完整性、灰度范围与发布回滚单独验收。最终交付一份可复现构建说明、一条最小持续集成链和一次失败回退记录。

## 安全基础：威胁、认证与权威判定

先读 [安全与密码基础总览](../../知识/08-工程实践与质量/安全与防护/安全与密码基础总览.md)，区分机密性、完整性、可用性、加密、散列、MAC 与签名，再读 [TLS、认证授权与反作弊](../../知识/08-工程实践与质量/安全与防护/02-TLS认证授权与反作弊.md)。用威胁模型识别资产、信任边界、攻击面与恢复路径；采用经过审查的协议／库，不能自行拼接密码方案。

TLS／mTLS、证书链验证、OAuth2／JWT 和令牌生命周期要分别解释“对端是谁”“能做什么”“何时失效”。防重放考虑序列号、时间窗、会话代次和重试语义；HMAC／AEAD 的使用依赖密钥管理及协议条件。证书固定需要轮换与恢复计划，不能表述为保证无法抓包；客户端 XOR 混淆、代码哈希、IAT／EAT／虚表检查和资产加密只能提高某类攻击成本，不能取代服务端对移动、伤害、购买等操作的权威校验。

练习产物是一个登录／会话／业务请求的信任边界图，列出过期令牌、重复请求、篡改字段、权限越界与客户端离线修改的期望结果；验收服务端拒绝非法状态转换，并说明监测、撤销和恢复。这里只形成防护学习与测试要求，不把客户端反调试或加密功能的存在作为系统安全证明。

## 容器与可观测性基础：对局生命周期与故障证据

前置读 [权限、安全与隔离](../../知识/01-编程与计算机基础/操作系统与系统I-O/04-权限安全与隔离.md)、[虚拟化与硬件辅助隔离](../../知识/01-编程与计算机基础/硬件体系结构与性能/05-虚拟化与硬件辅助隔离.md)，再按 [容器云与可观测性基础](../../知识/08-工程实践与质量/部署运维与可观测性/容器云与可观测性基础.md) → [可观测性、SLO 与故障演练](../../知识/08-工程实践与质量/部署运维与可观测性/02-可观测性SLO与故障演练.md)推进。先理解 OCI 镜像分层／OverlayFS、Namespaces、cgroups v2、容器网络和 Kubernetes 声明式状态，再将 Ready／Allocated／Shutdown 等游戏服生命周期放入调度模型。

DS 不能照搬无状态 Web 服务的随意重启思路；Agones 等编排需要核对分配、健康检查、保护、驱逐和节点故障的具体行为，不能声称处于对局状态就“绝不自动驱逐”或不会被 OOM 终止。内存／CPU 配额和预留量应来自峰值、throttling、对局密度和故障测试，固定预留 20%～30% 只能是候选起点，不能视为容量保证。产物是从等待分配到结束对局的状态图，明确停止接入、排空、存盘和退出顺序。

可观测性练习把 CCU、Tick P95／P99、RTT、丢包、GC 暂停、存盘队列和资源峰值连接到用户可感知的成功率／延迟 SLI，再定义 SLO、错误预算和告警动作。Prometheus／Grafana、OpenTelemetry 与 TraceID 用于串联指标、日志与追踪；采样率、时钟、基数和缺失数据影响诊断，不能保证所有节点都有微秒级准确延迟。

故障演练限定在可控环境，覆盖断网、单点失效、慢存储、配额不足和对局中退出；事先写预期影响、停止条件与恢复目标。验收告警能触发、对局与玩家数据按约定处理、恢复时间与数据损失有记录。只完成部署或采集配置不代表 SLO 已达成，生产结果须由真实运行证据支持。

## 测试手段与练习产物

客户端比较 Simple/Complex Automation、Latent Command 异步等待、Functional Test 关卡/蓝图断言和截图基线；截图需区分平台、渲染波动、分辨率与容差。说明测试模块/Build.cs 和无人值守 CI 命令怎样对应环境；与 Unity EditMode/PlayMode 比较仅用于选择测试层次，API 细节回各自主文。

服务端在传输、编解码、业务、数据和安全边界放断言，使用依赖注入与属性测试检查契约。普通无状态请求压测与有会话/移动/战斗状态的机器人不同：先定目标和基线，再阶梯加压找拐点，做长稳/尖峰，最后出报告。比较 wrk、ghz、k6、Locust 或自研客户端时先看协议和状态模型；故障注入限定范围与回收办法。

非功能练习固定 GameThread/RenderThread/GPU、设备档次、内存与功耗口径，执行基线→回归→定位→再采集。网络覆盖延迟、丢包、抖动、带宽、断网与切网；热更同时检查增量补丁、强更、回滚、协议与存档新旧并存。DS 报告区分舒适容量与极限容量，并交代机器人行为、单实例与区域假设。

专项自测还要回答：迁移输入/输出/回滚与责任如何追溯；安全如何分阻断/观察/豁免并脱敏留证；本地化与无障碍如何覆盖语言、输入、感知与核心恢复流程。测试环境区分本地、CI、测试服、灰度与压测，保存版本、配置和数据工厂输入。

## 把阈值写成可复核的项目约定

每条门禁需声明输入、环境、指标定义/分母、阈值、证据、负责人、例外审批与复审/到期日；提交、合入、版本、发布分别设门槛。记录 QPS、错误率、P50/P95/P99、资源水位与性能拐点；逃逸率、重开率、MTTD/MTTR 和崩溃率必须有一致统计窗口。修复应有能复现原缺陷的回归证据，流水线耗时超预算则重划测试层次。

原入口中的核心覆盖率80%/70%、外围40%、15分钟合入门禁、10分钟冒烟、500ms接口P99、30FPS低端基线、0.5%崩溃率以及P0<2h/P1<24h是示例起点，需按风险和项目阶段校准；测试通过率要求也只对选定测试集有效。灰度1%→10%→50%→100%同样是示例，每阶段需明确定义停止、回滚和证据检查。

## 按角色与问题选择

客户端开发：策略→客户端自动化→非功能；服务端开发：策略→服务端测试→CI；QA：策略→客户端→非功能→CI；策划：黑盒/边界值→蓝图测试；性能/兼容：非功能→策略→服务端压测；技术负责人：策略→CI/度量。

新系统先做策略与发布门禁；卡顿/闪退先固定性能与兼容基线；弱网交易/战斗同时查网络故障、超时与幂等；上线事故以缺陷闭环反馈ROI。DS上线走联机E2E与实例平台，容量问题再接机器人负载和运行参数。每条路径最终必须能解释“输入是什么、证据是什么、失败由谁处理”。

## 角色 E：先启动模块，再 UBT 与 UAT

必须先读 [引擎启动流程与模块架构](../../%E7%9F%A5%E8%AF%86/03-%E5%BC%95%E6%93%8E%E6%9E%B6%E6%9E%84%E4%B8%8E%E8%B5%84%E6%BA%90%E7%B3%BB%E7%BB%9F/%E8%BF%90%E8%A1%8C%E6%9E%B6%E6%9E%84%E4%B8%8E%E4%BB%BB%E5%8A%A1%E8%B0%83%E5%BA%A6/04-%E5%BC%95%E6%93%8E%E5%90%AF%E5%8A%A8%E6%B5%81%E7%A8%8B%E4%B8%8E%E6%A8%A1%E5%9D%97%E6%9E%B6%E6%9E%84.md)，明确启动时序、Runtime/Editor 模块边界、LoadingPhase 与依赖就绪条件，再进入 [UBT 构建系统与编译配置](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E6%9E%84%E5%BB%BA%E7%BC%96%E8%AF%91%E4%B8%8E%E5%88%B6%E5%93%81/01-UBT%E6%9E%84%E5%BB%BA%E7%B3%BB%E7%BB%9F%E4%B8%8E%E7%BC%96%E8%AF%91%E9%85%8D%E7%BD%AE.md) → [UAT 与自动化打包](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E6%9E%84%E5%BB%BA%E7%BC%96%E8%AF%91%E4%B8%8E%E5%88%B6%E5%93%81/02-UAT%E4%B8%8E%E8%87%AA%E5%8A%A8%E5%8C%96%E6%89%93%E5%8C%85.md)。编译时依赖图、运行时模块加载与资源就绪是不同问题，不能因 Build.cs 成功就认定启动阶段正确。

共同前置是 [编译链接与 ABI](../../%E7%9F%A5%E8%AF%86/01-%E7%BC%96%E7%A8%8B%E4%B8%8E%E8%AE%A1%E7%AE%97%E6%9C%BA%E5%9F%BA%E7%A1%80/%E7%BC%96%E8%AF%91%E9%93%BE%E6%8E%A5%E4%B8%8EABI/01-%E7%BC%96%E8%AF%91%E9%93%BE%E6%8E%A5%E4%B8%8EABI%E5%85%A8%E6%B5%81%E7%A8%8B.md)、[版本控制、依赖与构建](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E5%B7%A5%E7%A8%8B%E8%AE%BE%E8%AE%A1%E4%B8%8E%E5%8D%8F%E4%BD%9C/%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6%E4%BE%9D%E8%B5%96%E4%B8%8E%E6%9E%84%E5%BB%BA%E5%B7%A5%E7%A8%8B.md)；部署分支再补容器与可观测性。阅读时逐项区分 Target/Module、构建配置、编译、Cook、Stage、Package、Archive 的输入与产物，不以一次 BuildCookRun 命令替代阶段定位。

练习给一个含 Runtime/Editor 模块的小插件画两张图：编译依赖图与启动加载图；说明各符号导出、资源使用和子系统访问何时合法。验收要求定位“编译通过但运行阶段未就绪”这类问题的检查点，再能按阶段解释一次打包失败的日志与缺失产物。本次不执行插件、构建或发布操作。

练习选一条实际可解释的资产规则，准备合规与不合规样本，列出导入、验证、报告与阻断阶段；自动化批处理先在副本验证输入输出与幂等性。验收应能够定位具体资产和规则，重复执行不重复破坏内容，失败有可恢复产物。命名、纹理或碰撞规则必须来自项目需求，不能把示例规则当成所有项目统一标准。

## Shader、资源交付与发布门禁

练习对客户端与服务器依赖做一份项目级保留清单，裁剪前后检查启动、加入、碰撞、导航与技能结果，同时记录包体、常驻/峰值内存与 Tick 成本。验收关心功能等价及成本变化，不沿用镜像或内存固定阈值，也不能因为无画面就直接删除全部动画或其他可能参与服务器玩法的数据。

## 性能诊断与 UI 的跨域边界

从 [Profiling](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E8%B0%83%E8%AF%95%E4%B8%8E%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/03-%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90%E5%B7%A5%E5%85%B7%E4%B8%8EProfiling.md) 建立症状、捕获、定位、假设、改动与复测的顺序，再进 [渲染/加载性能](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E8%B0%83%E8%AF%95%E4%B8%8E%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/04-%E6%B8%B2%E6%9F%93%E4%B8%8E%E5%8A%A0%E8%BD%BD%E6%80%A7%E8%83%BD%E4%BC%98%E5%8C%96.md) 和 [GameplayDebugger](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E8%B0%83%E8%AF%95%E4%B8%8E%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/05-GameplayDebugger%E4%B8%8E%E8%BF%90%E8%A1%8C%E6%97%B6%E8%B0%83%E8%AF%95.md)。结合 [Trace 源码](../../%E7%9F%A5%E8%AF%86/08-%E5%B7%A5%E7%A8%8B%E5%AE%9E%E8%B7%B5%E4%B8%8E%E8%B4%A8%E9%87%8F/%E8%B0%83%E8%AF%95%E4%B8%8E%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/28-UnrealInsights%E4%B8%8ETrace%E6%BA%90%E7%A0%81.md) 理解采集和解释成本。UI 数据/焦点的责任在 Gameplay，工程路线负责量测它带来的布局、绘制、输入延迟与资源开销。

练习复现一次菜单打开或列表滚动卡顿，在固定输入下比较事件通知、控件复用或缓存策略，记录 CPU/GPU/内存及行为回归。验收能将热点关联具体状态变化，证明改动没有丢失刷新或焦点，并保留原始 Trace；只有确实运行的数据才写结论。源码阅读、独立工具实验、实际 UE 场景与生产发布门禁各有证据范围，不能互相替代。
