## 1. 概述

AI 是服务器 CPU 的隐形大头：成百上千个 Bot/NPC 每 Tick 都要决策、寻路、移动。不做预算管理时，AI 消耗会随实体数线性增长，**在玩家人数峰值与开服活动时吃掉整个 Tick 预算**。时间预算的本质是：

```text
固定预算 + 优先级 + 分帧/降级 = 可预测的 AI 开销（P99 可控）
```

本文回答：

1. AI 开销为什么必须分层预算（决策/移动/寻路）？
2. 寻路怎么做"可中断 + 时间片"（预算内搜不完怎么办）？
3. Staggered Update 与优先级怎么分配？
4. 过载时降级阶梯怎么设计？
5. 本机实验能证明什么（A* P99 与 Tick 过载）？

## 2. 核心概念

| 术语 | 中文 | 一句话定义 |
| --- | --- | --- |
| AI budget | AI 预算 | 每 Tick 分配给 AI 系统的 CPU 时间上限 |
| Decision rate | 决策频率 | 选目标/切状态的频率（常低于 Tick 频率） |
| Staggered update | 分帧更新 | 实体分批决策/移动，摊薄到多 Tick |
| Path query budget | 寻路预算 | 每次寻路允许消耗的时间片 |
| Interruptible search | 可中断搜索 | A* 支持"搜一半暂停，下 Tick 续搜" |
| Priority scheduling | 优先级调度 | 玩家附近/战斗中的实体先获得预算 |
| Degradation ladder | 降级阶梯 | 超预算时按影响从低到高逐级降级 |
| Cache + fallback | 缓存与回退 | 路径缓存命中省搜索；失败/超时回退直线或旧路径 |
| Search suspension | 搜索挂起 | A* 预算用尽时保存状态，下 Tick 续搜 |
| Priority bucket | 优先级分桶 | 按距离/重要性分档排序，避免热路径全排序 |

## 3. 原理详解

### 3.1 三层频率与三层预算

```text
决策层（5~10Hz）：选目标、切状态 —— 每 Tick 只处理 1/4~1/2 的实体（分帧）
移动层（20Hz）：沿路径推进 —— 轻量，只读路径
寻路层（按需）：目标变化才搜 —— 单次查询是重头，必须时间片化
```

每层独立预算片，超时各自降级：

| 层 | 预算占比（示意） | 超时降级 |
| --- | ---: | --- |
| 决策 | 40% | 决策频率减半（5Hz→2.5Hz） |
| 移动 | 20% | 暂停非战斗移动（原地等待） |
| 寻路 | 40% | 预算收缩、缓存优先、失败冷却 |

### 3.2 可中断寻路与时间片

A* 的展开循环天然可中断：**每展开 N 个节点检查一次时间片，超时即暂停**，保存 open/closed 状态到下一 Tick 续搜（或直接返回部分路径）。

```cpp
// 示意：时间片式 A* 展开
while (!open.empty()) {
    if (++expanded % kCheckEvery == 0 && elapsed() > budgetUs) {
        return SearchStatus::Suspended;   // 下 Tick 续搜（保存状态）或降级
    }
    Node cur = pop();
    // ... 展开邻居
}
```

工程选择：

- **小地图/短路径**：预算内一次搜完，无需续搜（本机实验 100×100 单查询 P99 < 0.2ms）；
- **大地图/长路径**：续搜（保存状态）或"部分路径 + 下 Tick 重规划"——部分路径对移动系统更友好；
- **必须保底**：预算内没结果 → 直线/旧路径降级 + 冷却重试，绝不阻塞 Tick。

### 3.3 Staggered Update 与优先级

```text
每 Tick 只更新 1/K 的实体（K=决策周期/Tick 周期）
顺序：玩家附近 → 战斗中 → 视野内 → 远距/非关键
```

优先级排序的代价必须可控：用"分桶 + 近似排序"（如按距离分档），不要在热路径做全量排序（O(n log n) 每 Tick 不可接受）。

### 3.4 缓存与失败冷却

- **路径缓存**（LRU，(起点,终点)）：假人群体共享路径命中率高（本机实验命中 33 倍提速）；
- **失败冷却**：不可达目标指数退避重试，避免每 Tick 空转；
- **缓存失效**：地图版本变化整体失效（见 [07-假人AI完整链路](../../系统实战/07-假人AI完整链路.md) 的验证矩阵）。

缓存实现注意：缓存键包含"起点格子 + 终点格子 + 地图版本"，起点按格子而非精确坐标（否则几乎永不命中）；LRU 容量按内存预算设定（128~1024 条）。

### 3.5 降级阶梯（过载时）

```text
第 1 级：AI 决策降频（5Hz→2.5Hz）            —— 影响小，恢复快
第 2 级：寻路预算收缩 + 缓存优先             —— 路径质量略降
第 3 级：非玩家实体 Update 降频（AOI 联动）   —— 视觉表现降级
第 4 级：暂停非关键 Bot（战斗外 NPC 挂起）    —— 保玩家体验
```

每级降级都有恢复条件（**滞回**：如 P99 连续 30s 低于预算 70% 才升回上一级），防止抖动。

### 3.6 与 Tick 预算表的联动

AI/寻路预算写进 [01-ServerMainLoop与TickScheduler](01-ServerMainLoop与TickScheduler.md) 的预算表（按 P99 签）：示例 20Hz 下 AI 总预算 5ms（决策 2ms、移动 1ms、寻路 2ms），寻路单查询 P99 0.2ms → 每 Tick 最多 10 个完整查询，超出走分帧/续搜。

### 3.7 与假人 AI 链路的衔接

预算机制与 [系统实战/07-假人AI完整链路](../../系统实战/07-假人AI完整链路.md) 的对应关系：

| 链路环节 | 预算机制 | 对应章节 |
| --- | --- | --- |
| 决策（5~10Hz） | 分帧更新 + 优先级分桶 | 本文 3.3 |
| A* 请求 | 可中断寻路 + 时间片 | 本文 3.2 |
| 路径缓存 | LRU + 地图版本失效 | 本文 3.4 |
| 移动执行 | 轻量只读路径，不占寻路预算 | 本文 3.1 |
| 过载降级 | 四级阶梯（决策降频→寻路收缩→Update 降频→暂停非关键） | 本文 3.5 |

## 4. 示例：预算监控与降级状态机

```cpp
struct AiBudget {
    double decideUs, moveUs, pathUs;   // 各层本 Tick 已用
    int    decideRateHz = 5;           // 当前决策频率（可降级）
    bool   pathCacheOnly = false;      // 第 2 级：只用缓存路径
    bool   suspendNonCritical = false; // 第 4 级
};

// 每 Tick 结束：更新预算统计并判定降级/恢复（示意）
void UpdateBudgetState(AiBudget& b, double tickP99Us, double budgetUs) {
    if (tickP99Us > budgetUs * 0.9) {
        b.decideRateHz = std::max(1, b.decideRateHz / 2);   // 第 1 级
        if (b.decideRateHz <= 2) b.pathCacheOnly = true;    // 第 2 级
    } else if (tickP99Us < budgetUs * 0.7 && steady30s) {
        // 恢复（滞回）：逐级回升
    }
}
```

### 4.1 预算监控字段

```text
ai_budget_decision_p99_us     # 决策层 P99
ai_budget_move_p99_us         # 移动层 P99
ai_budget_path_p99_us         # 寻路层 P99
path_query_count              # 每 Tick 查询数
path_timeout_count            # 超时（未搜完）次数
path_cache_hit_rate           # 缓存命中率
ai_degrade_level              # 当前降级等级（0~4）
```

告警：`path_timeout_count` 连续上升 = 预算不足；`path_cache_hit_rate` 骤降 = 缓存失效/负载模式变化；`ai_degrade_level ≥ 2` 持续 = 需要扩容或调参。

### 4.2 决策分帧示例

```cpp
// 每 Tick 只决策 1/K 的实体（K = 决策周期）
const int kDecideEveryTick = 4;   // 20Hz Tick 下 5Hz 决策
for (size_t i = tickIndex % kDecideEveryTick; i < bots.size(); i += kDecideEveryTick) {
    Decide(bots[i], tickIndex);   // 决策只改目标点/行为，不占寻路预算
}
```

分帧 + 优先级分桶的组合：先按距离分桶（近/中/远），每 Tick 从高到低消耗预算片；预算耗尽即停，下 Tick 继续。

## 5. 实验结果与结论（复用本机证据）

### 5.1 A* 基准（evidence/algorithms/astar）

环境：Windows x64 / MSVC 2022 `/O2`，100×100 网格，1000 次查询，2026-08-12。原始输出 `results/astar_benchmark_win_x64_msvc.txt`：

| 指标 | 二叉堆 | 线性扫描 | 对预算的意义 |
| --- | ---: | ---: | ---: |
| P50 | 0.027ms | 0.060ms | 平均查询成本低，预算充裕 |
| **P99** | **0.117ms** | **0.630ms** | 长尾决定预算：堆实现 20Hz 下每 Tick 可容纳 ~85 次查询 |
| 扩展节点 | 257 | 258 | 与 Open List 实现无关（启发决定） |
| 缓存命中 | 0.001ms | 未命中 0.033ms | 命中 ≈ 33 倍省，缓存是预算杠杆 |

结论：**预算按 P99 签**——线性实现 P99 0.63ms 意味着 20Hz 预算 2ms 下每 Tick 只能 3 次查询；堆实现可 17 次。这就是"结构优化直接转化为容量"的量化证据。

### 5.2 Tick 过载模拟（evidence/server/tick-scheduler）

| 场景 | ticks | drops | catch | 意义 |
| --- | ---: | ---: | ---: | ---: |
| 10000 实体，负载 1.3，catch-up | 7800 | 0 | 1800 | 预算内靠补帧自愈 |
| 10000 实体，负载 1.3，drop | 6000 | 1500 | 0 | 世界减速，需降级干预 |

结论：AI 超预算的后果不是"AI 慢一点"而是**整个世界时间漂移（drop）或单帧突发（catch-up）**——预算管理是"保护世界时间"的手段。

对预算设计的量化含义（以 20Hz、AI 预算 5ms 为例）：

```text
决策层：2ms ÷ 0.05ms/次 = 40 次决策/Tick → 分帧后支持 2000 个实体 5Hz 决策
寻路层：2ms ÷ 0.12ms(P99) = 16 次完整查询/Tick；超出的请求排队/分帧
移动层：1ms 覆盖全部实体（读路径，成本极低）
```

这些数字让"预算表"变成可计算的容量模型，而不是拍脑袋。

注意：模型数字会随地图规模与启发质量变化（100×100 是小型地图；500×500 的 P99 会显著上升），上线前用目标地图重跑基准。

## 6. 最佳实践

1. **三层独立预算**：决策/移动/寻路各占时间片，超时各自降级，互不阻塞。
2. **寻路可中断 + 保底**：预算片展开、超时续搜/部分路径；绝不阻塞 Tick。
3. **分帧更新**：决策 5~10Hz + 分桶优先级，热路径不做全量排序。
4. **缓存优先**：LRU 路径缓存 + 地图版本失效；命中率进监控。
5. **失败冷却**：不可达指数退避，防空转。
6. **降级阶梯 + 滞回恢复**：四级降级明确触发/恢复条件，防抖动。
7. **预算按 P99 签**：用本机基准（5.1）换算每 Tick 查询容量，写进预算表。
8. **监控三件套**：各层预算占用 P99、寻路超时/失败计数、缓存命中率。
9. **确定性**：决策/寻路用 Tick 种子随机，回放可复现（关联 [07-假人AI完整链路](../../系统实战/07-假人AI完整链路.md)）。
10. **预算参数配置化**：决策频率/预算片/降级阈值进配置表，压测扫参后定稿，不写死。
11. **降级可观测**：每次降级/恢复记录时间、等级、触发指标（P99/lag），复盘时能还原因果。
12. **先保玩家再保 AI**：预算分配玩家相关 AI 优先；纯装饰 NPC 是最先降级对象。
13. **分帧 + 分桶组合**：决策按 Tick 取模分帧，优先级按距离分桶，预算片从高到低消费。
14. **参数与代码分离**：决策频率/预算/阈值全进配置，压测扫参定稿。

## 7. FAQ

**Q1：预算片内 A* 没搜完，返回部分路径安全吗？**
安全但要用对：部分路径 + "到点重规划"语义（移动系统到达部分路径终点时重新请求）；不要假装它是完整路径。

**Q2：分帧更新会让人看到"AI 卡顿"吗？**
决策频率 5Hz 对人类感知足够；移动层仍然每 Tick 执行（读路径推进），视觉上连续。真正卡顿来自"决策与移动同时被跳过"。

**Q3：缓存命中率多少算健康？**
假人群体 50%+；玩家路径低（目标多变）。命中率低时检查缓存键设计（是否包含起点精度/地图版本）。

**Q4：多线程寻路能替代预算吗？**
不能替代，只能扩大容量：预算解决"单 Tick 时间确定性"，多线程解决"总吞吐"；两者结合（预算内提交、线程池执行、Tick 边界合并结果）。

**Q5：降级阶梯会不会影响玩法公平？**
降级只影响非关键/远距实体（第 3、4 级），玩家附近与战斗中实体保持最高优先级——公平性由优先级保证，降级不触碰关键路径。

**Q6：预算监控的粒度多大合适？**
按层聚合（决策/移动/寻路）到 P99 即可；逐实体监控成本太高。异常定位靠"分层 P99 + 超时计数"下钻。

**Q7：本机基准能直接用于容量规划吗？**
能给出换算框架（P99 × 查询数/秒 = 预算占用），真实容量用机器人压测校准（关联 [游戏测试与质量](../../游戏测试与质量/README.md) 07）。

**Q8：预算内"每 Tick 最多 10 次查询"，但请求有 50 个怎么办？**
队列化：本 Tick 处理最高优先级 10 个，其余下 Tick；配合分帧（50 个请求按优先级分布在 5 个 Tick 内）。请求积压长度本身是监控项。

**Q9：续搜（Suspended）状态存哪里？**
存在寻路请求对象里（open/closed 快照），随实体生命周期管理（Despawn 时释放）；续搜也要吃预算片，防止"续搜永不完"。

**Q10：降级后玩家体验真的无感吗？**
第 1、2 级（决策降频、寻路收缩）对玩家基本无感；第 3 级（远处 NPC 更新降频）在视觉上可察觉；第 4 级（暂停非关键 NPC）明显但保住了玩家战斗。设计目标：日常峰值只到第 1~2 级。

**Q11：预算表和实际 CPU 时间对不上怎么办？**
预算表是"目标分配"，实际消耗按层 P99 度量；偏差 >20% 说明某个系统超支（分配/GC/锁），先定位再调参——不要直接放宽预算掩盖问题。

**Q12：寻路查询的排队会影响玩家体验吗？**
玩家相关寻路请求永远最高优先级（先进先做）；排队只影响非关键 Bot。队列长度是监控项，超过阈值即触发降级（AI 降频），而不是让玩家等。

**Q13：决策分帧的取模起点会带来"同帧决策聚集"吗？**
不会：`tickIndex % K` 让实体均匀分布在 K 个 Tick 上；但要注意 Spawn 密集的实体可能同帧创建（SpawnBatch 按 ID 取模分配决策槽，见 03-Entity 篇）。

## 8. 验证与基准

- 复用实验：`evidence/algorithms/astar/scripts/build_run.ps1` 与 `evidence/server/tick-scheduler/scripts/build_run.ps1`（原始结果见各自 results/）；
- 预算验收：100/1000/10000 Bot 场景下各层预算 P99 占用 ≤ 预算表，且无连续 drop；
- 降级验收：过载注入（实体数翻倍）后 30s 内降级生效、P99 回落、恢复无抖动；
- 确定性验收：同种子两次压测结果一致（扩展节点/路径/事件）；
- 队列验收：请求积压按优先级正确排序、无饥饿（低优先级不永久等待）；
- 降级恢复验收：过载注入后等级上升、恢复后逐级回落（滞回参数验证）；
- 容量模型验收：预算表的"次数上限"与实际压测查询数吻合（±20%）；
- 缓存键验收：LRU 命中率稳定、地图版本切换后 0 命中（正确失效）；
- 升级 L5：真实项目 AI 预算数据（分层 P99、超时计数、降级事件）回填工作日志。

### 8.1 预算健康度速查

```text
寻路 P99 > 预算 × 0.9？→ 查询数超容量：分帧/队列/缓存优先
决策 P99 超预算？   → 分帧比例不足：K 调大（5Hz→2.5Hz）
缓存命中率 < 30%？  → 键设计/负载模式问题，先查缓存键
timeout_count 上升？→ 地图太大或障碍过密：续搜/部分路径
降级频繁抖动？      → 滞回参数过窄：加宽阈值与持续时长
```
