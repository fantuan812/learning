# 05-AOI与InterestManagement

> 知识基线：AOI（Area of Interest）与 Interest Management 的运行时语义（Enter/Leave/Update、限流、批量）；算法层数据结构见 [游戏算法/01-寻路与图论](../../游戏算法/01-寻路与图论/README.md)（九宫格/十字链表/Quadtree）；UE 对照为 ReplicationGraph（interest management 的 UE 实现）。
> 版本基准：UE5.8（ReplicationGraph 为本机源码可核对）；本层不绑定具体引擎，讲真实服务器 Tick/Scene/send 流程中的 AOI。
> 适用范围：MMO/实时服务器的大规模场景同步；与 [01-ServerMainLoop与TickScheduler](01-ServerMainLoop与TickScheduler.md) 的 Tick 预算配合。
> 官方参考：[UE5.8 ReplicationGraph 文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)、[UE5.8 官方文档](https://dev.epicgames.com/documentation/en-us/unreal-engine)。
> 最后更新：2026-08-12（首版，含本机模拟器）。
> 知识成熟度：L4（模拟器 + 原始结果，见 [evidence/algorithms/aoi](../../evidence/algorithms/aoi/README.md)）。

## 1. 概述

算法层告诉你"AOI 有九宫格、十字链表、四叉树"；运行时层回答：**AOI 在真实服务器里从"实体移动"到"客户端收到数据"到底怎么跑**。本文串起完整链路：

```text
Move → Cell Change → Interest Diff → Enter/Leave → Update Set → Priority → Rate Limit → Network Batch → 客户端 Replication
```

并回答四个问题：

1. 每 Tick 网格 AOI 的实际比较次数与耗时随实体规模怎么变？
2. Enter/Leave 事件怎么保证正确（相对 ground truth）？
3. 兴趣集结果怎么变成"可发送"的网络包（限流/批量/优先级）？
4. 实现质量对性能的影响有多大（哈希容器 vs 扁平数组）？

目标读者：需要实现或维护大规模场景同步的服务器工程师；前置：网格/空间索引概念（[游戏算法](../../游戏算法/README.md)）、Tick 调度（[01](01-ServerMainLoop与TickScheduler.md)）。

## 2. 核心概念

| 术语 | 中文 | 一句话定义 |
| --- | --- | --- |
| AOI | 兴趣区域 | 实体只关心视野范围内的其他实体 |
| Interest Set | 兴趣集 | 某实体当前"应该知道"的实体集合 |
| Enter/Leave/Update | 进出/更新 | 兴趣集的三种变化事件（同步消息的来源） |
| Cell / Grid | 网格 | 空间分桶，AOI 的最简数据结构 |
| Interest Diff | 兴趣差 | 新旧兴趣集对比，算出 Enter/Leave |
| Priority | 优先级 | 消息重要度（玩家 > 战斗 > 远距 AI） |
| Rate Limit | 限流 | 每连接每秒最大消息数/带宽 |
| Network Batch | 网络批量 | 多个实体的更新合并为一个包 |
| ReplicationGraph | UE 同步图 | UE 的 interest management 实现（网格分桶 + 条件过滤） |
| Cell Change | 跨格 | 实体所在网格变化（Enter/Leave diff 的触发器） |
| Update Set | 更新集 | 仍在视野内但位置变化的实体集合 |
| Ground truth | 基准真值 | 两两关系暴力计算的"正确兴趣集"（测试用） |

## 3. 原理详解

### 3.1 完整运行时链路

```mermaid
flowchart TD
    A[实体 Move] --> B[Cell Change?]
    B -- 是 --> C[更新网格：移出旧格/加入新格]
    C --> D[扫描 (2R+1)^2 邻域格]
    B -- 否 --> D
    D --> E[候选兴趣集]
    E --> F[与新旧集合对比 → Interest Diff]
    F --> G[Enter / Leave / Update 事件]
    G --> H[按优先级排序]
    H --> I[限流：超阈值降频/丢弃低优先级]
    I --> J[Network Batch 打包]
    J --> K[客户端 Replication]
```

每 Tick 的关键动作：

1. **移动收集**：实体每 Tick 上报位置（或 Tick 内自己移动）；
2. **网格维护**：跨格才更新（`Cell Change` 是 diff 的触发器）；
3. **兴趣计算**：扫描邻域格收集候选，与上一 Tick 的兴趣集做 diff；
4. **事件产出**：Enter（新进视野）/ Leave（离开视野）/ Update（仍在视野内移动）；
5. **发送决策**：优先级 + 限流 + 批量——不是每个事件都立即发。

### 3.2 正确性：什么是"对的"兴趣集

本层把正确性定义为：**网格 AOI 的 Enter/Leave 事件与 ground truth（两两关系）一致**。实验里 ground truth 用切比雪夫格距（与网格同口径）时一致率 100%；若用欧氏圆口径，角落格存在固有差异（圆方差异），属于可接受的近似。

工程含义：

- 兴趣集必须**确定且可复现**（同输入同结果），否则回放与压测失真；
- 正确性测试要有 ground truth 对照（随机场景 + 两两暴力），而不是只看"有没有报错"。

可断言的正确性清单（进 CI）：

```text
断言 1：网格 Enter/Leave 事件 == 暴力 Enter/Leave 事件（口径一致时差为 0）
断言 2：兴趣集对称差 == 0（逐实体对比）
断言 3：跨格计数 == 网格维护次数（内部一致性）
断言 4：同种子两次运行结果一致（确定性）
```

### 3.3 从兴趣集到网络包：限流与批量

兴趣集是"该知道什么"，网络包是"实际发什么"——中间隔了三层：

1. **优先级**：玩家自身 > 战斗/交互对象 > 视野内 AI > 远距实体；同 Tick 超预算时按优先级裁剪；
2. **限流**：每连接每秒消息数/带宽上限；超限时降频（Update 合并、Leave 延迟）；
3. **批量**：同一 Tick 的多个实体的 Update 合并成一个包（减少包头与系统调用）；
4. **降级**：过载时缩小视野半径、降低非玩家实体更新频率（与 [01-ServerMainLoop与TickScheduler](01-ServerMainLoop与TickScheduler.md) 的降级联动）。

### 3.4 UE 对照：ReplicationGraph

UE 的 interest management 实现是 ReplicationGraph（`Engine\Source\Runtime\Engine\Private\ReplicationGraph.cpp`，源码专题见 [12-引擎源码分析](../../游戏知识/12-引擎源码分析/README.md)）：

- 按网格（`SpatializationGrid`）分桶实体，Actor 移动后更新网格归属；
- 连接按网格收集候选 + 条件（`FActorRepListType`）过滤 → 决定每个连接"该同步哪些 Actor"；
- 支持 `AlwaysRelevant`/`NotRelevant`/距离条件等自定义策略；
- 与自研网格 AOI 的差异：UE 是"以连接为中心"的过滤，自研服务器常见"以实体为中心"的兴趣集——两种视角可互相映射。

### 3.5 网格实现的工程细节

1. **cell 大小**：视野半径 R 与 cell 大小的关系决定扫描格数。cell = 视野半径（如 R=3 格）时扫描 49 格；cell 更小（细分）扫描更多格但候选更少；cell 更大候选更粗。经验：cell 边长 ≈ 平均视野半径，扫描 5×5~9×9 格。
2. **边界处理**：地图边缘的实体扫描格越界要跳过（实验对 200×200 地图显式处理），否则读越界。
3. **跨格判断**：实体位置变化后 `floor(pos)` 变化才更新网格——未跨格只更新位置，不触发网格维护（diff 的触发器）。
4. **大实体/多格实体**：体积超过一格的对象需要占多格或按中心格 + 半径修正；战斗 Boss、载具尤其要注意。
5. **动态半径**：不同实体类型可不同视野半径（玩家 10 格、NPC 5 格）——半径按实体类型存，扫描格数按其半径计算。
6. **兴趣集表示**：有序向量（排序 + 双指针 diff）比 `unordered_set` 快一个量级（见 5.1 实现质量对比）；修改频率低时用"脏标记 + 延迟重算"。

### 3.6 与 Tick 预算表的联动

AOI 的 CPU 与带宽消耗都要进 [01-ServerMainLoop与TickScheduler](01-ServerMainLoop与TickScheduler.md) 的预算表：

| 预算项 | 估算公式 | 10000 实体示例（实验参数） |
| --- | --- | --- |
| 兴趣计算 CPU | 实体数 × 扫描格数 × 平均格内实体 | 7.3ms/帧（实验实测） |
| Enter/Leave 事件 | 每帧跨格率 × 兴趣集大小 | 669424 事件/帧（两口径一致） |
| Update 发送量 | 兴趣集平均大小 × 实体数 | 120226 条/帧（实验估算） |
| 带宽 | 发送量 × 单条消息字节数 | 按协议计算，超限即降级 |

降级顺序（预算 P99 超限时）：AOI 半径收缩 → 非玩家实体 Update 降频 → Leave 延迟 → 战斗/交互相关实体豁免。

### 3.7 事件可靠性分级与协议设计

AOI 产出的三类事件在协议里可靠性不同：

| 事件 | 语义 | 可靠性 | 协议处理 |
| --- | --- | --- | --- |
| Enter | 对象进入视野 | 必须可靠 | 显式消息 + 全量实体信息；丢失则客户端永远看不到对象 |
| Leave | 对象离开视野 | 尽力 | 显式消息；丢失只是幽灵残留，可被后续 Update 修正 |
| Update | 视野内位置/状态变化 | 尽力 + 可合并 | 批量包、按频率限流、最后状态优先（不需要逐帧全量） |

协议设计的两个常见错误：

1. **把 Update 当可靠消息**：逐帧全量可靠同步 → 带宽爆炸、重传风暴；Update 应走"最后状态优先"的不可靠通道；
2. **Enter 不带全量信息**：客户端只收到"有对象"却要再请求详情 → 额外往返；Enter 应携带实体初始状态。

## 4. 示例：本机模拟器

`evidence/algorithms/aoi/src/aoi_simulator.cpp`：200×200 格地图、实体随机游走、视野半径 3 格，100/1000/10000 实体；网格 AOI（扁平 cell 数组 + 有序向量兴趣集）对比暴力两两；每帧校验 Enter/Leave 正确率、比较次数、发送估算、分段耗时。

### 4.1 模拟器实现要点（可复现性）

- **ground truth 口径**：切比雪夫格距 ≤ R（与网格 AOI 同口径），保证正确率可断言；欧氏圆差异单独统计为"圆方差异对"；
- **分段计时**：网格路径（移动+兴趣+事件 diff）与暴力路径（两两距离）分开计时，避免把 ground truth 成本算进被测实现（初版把暴力算进网格耗时导致 153ms 假象）；
- **校验和防消除**：暴力循环累加校验和并输出，防止编译器把无副作用循环优化掉（初版暴力耗时 0.000ms 的教训）；
- **固定种子**：三档规模各用固定种子，结果可复现、可 diff。

### 4.2 实现演进：为什么初版比暴力还慢

初版用 `unordered_map<int, vector<int>>` 存网格 + `unordered_set` 存兴趣集，10000 实体时每帧 153ms（比暴力 39ms 还慢）。原因：每实体每帧 49 次哈希查找（49 万次）+ 130 万次 unordered_set 插入/遍历。改为扁平 `vector<vector<int>>` + 有序向量后降到 7.3ms。**这是"数据结构选型决定 AOI 生死"的现场证据**。

## 5. 实验结果与结论

环境：Windows x64，MSVC 14.44.35207，`/O2 /std:c++17`，2026-08-12。完整输出见 [evidence/algorithms/aoi/README.md](../../evidence/algorithms/aoi/README.md)。

| 实体数 | 网格比较/帧 | 暴力比较/帧 | 网格 ms/帧 | 暴力 ms/帧 | 正确率 | 发送估算/帧 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 111 | 4950 | 0.009 | 0.010 | 100% | 11 |
| 1000 | 2178 | 499500 | 0.165 | 0.966 | 100% | 1178 |
| 10000 | 130226 | 49995000 | 7.299 | 96.003 | 100% | 120226 |

结论：

1. **正确率 100%**：网格 AOI 与切比雪夫 ground truth 的 Enter/Leave 完全一致（0 不一致）。
2. **比较次数**：10000 实体时网格每帧 13 万次 vs 暴力 5000 万次；耗时 7.3ms vs 96ms（**约 13 倍**），规模越大差距越大（100 时相当，1000 时 5.9 倍）。
3. **发送量是主要预算项**：10000 实体每帧约 12 万次兴趣更新——必须限流/批量/优先级裁剪，否则网络先于 CPU 崩溃。
4. **圆方差异**：每帧 2/249/25386 对（10000 时约 0.05%），方形视野的固有近似；需要严格圆视野时在候选集上做距离过滤。
5. **实现质量教训**：哈希容器版（unordered_set/map）在 10000 实体时 153ms 反而慢于暴力 39ms；扁平数组 + 有序向量版 7.3ms——**AOI 热路径禁用哈希容器**。

### 5.1 与初版实现的质量对比

| 实现 | 1000 实体 | 10000 实体 | 说明 |
| --- | ---: | ---: | --- |
| 哈希容器版（unordered_map + unordered_set） | ~11ms | ~153ms | 每实体 49 次哈希查找 + 哈希集合操作 |
| 扁平数组版（vector 网格 + 有序向量） | 0.165ms | 7.3ms | 直接索引 + 双指针 diff |
| 暴力两两（ground truth） | 0.97ms | 96ms | 仅作对照，生产不可用 |

结论：同一算法（网格 AOI），实现质量带来 **20 倍**差距（10000 实体时 7.3ms vs 153ms）；性能结论必须绑定实现形态，否则会误判算法本身。

### 5.2 参数敏感性（可自行复测）

- **视野半径 R 从 3 增到 5**：扫描格数 49→121（2.5 倍），兴趣集与发送量近似按 (5/3)²≈2.8 倍放大——半径是发送预算的第一杠杆；
- **实体密度翻倍**（同地图 20000 实体）：格内实体数翻倍，比较次数与发送量近似线性放大；
- **静止比例 50%**：跨格率减半，Enter/Leave 事件大幅下降，但 Update 仍在——压测场景必须混合静止/移动（见 FAQ Q7）；
- **cell 大小减半**（R=6 格、cell 3 单位）：扫描格数变多但候选更少，总比较次数通常下降；最优值随密度分布变化，用模拟器扫参。

这些敏感性都可以用 `aoi_simulator` 改参数直接复测（源码内常量 + 固定种子），是"可复现实验优于口头结论"的示范。

复测操作：修改 `kViewRadius`/地图尺寸/实体数后重跑 `build_run.ps1`，对比正确率与耗时变化；建议把扫参结果（参数 × 指标）追加到实验 README 的 results 区，形成参数敏感性档案。

### 5.3 复杂度视角

网格 AOI 的每帧成本 = O(实体数 × 扫描格数 × 平均格内实体数)，与暴力 O(N²) 的关键区别是**与 N 解耦的部分只来自局部密度**：均匀分布下平均格内实体数 ≈ N/格总数，因此网格法近似 O(N)；聚集场景（密度不均）下格内实体数上升，网格优势缩小——这正是四叉树等自适应结构的动机，也解释了"压测场景必须覆盖聚集分布"。

## 6. 最佳实践

1. **数据结构用扁平数组**：cell 用 `vector<vector<int>>` 直接索引，兴趣集用有序向量 + 双指针 diff；禁止每 Tick 建 `unordered_set`。
2. **跨格才更新**：Cell Change 是 diff 触发器，未跨格只更新位置不重建兴趣集。
3. **Enter/Leave 与 Update 分流**：Enter 必须可靠送达（否则看不到对象），Update 可合并/降频，Leave 可延迟。
4. **限流与优先级写进发送层**：兴趣集是"逻辑集合"，发送层按带宽预算裁剪——两者解耦，便于过载降级。
5. **正确性测试带 ground truth**：随机场景 + 暴力对照 + Enter/Leave 一致率断言，进 CI。
6. **规模规划**：按"兴趣集平均大小 × 实体数"估算每帧发送量，超过带宽预算即触发 AOI 半径收缩/AI 降频（与 W2-01 预算表联动）。
7. **UE 侧**：服务端自研 AOI 时参考 ReplicationGraph 的网格 + 条件过滤结构；客户端表现层用插值消费，不直接依赖 AOI 节奏。
8. **半径/格大小做成配置**：上线后按真实分布调参（密度、聚集度），不要写死。
9. **事件分级**：Enter 可靠、Leave 尽力、Update 合并——同步协议按可靠性分级设计（见 FAQ Q3）。
10. **过载联动**：AOI 半径收缩、非玩家更新降频、Leave 延迟三条降级路径写进调度器（与 W2-01 降级预案一致）。
11. **静态对象不进 AOI 网格**：建筑、装饰物用独立可见性表，避免污染动态网格（兴趣集只含动态实体）。
12. **上线前用模拟器扫参**：半径/cell/密度三参数在模拟器里扫一遍再进压测，省真实环境迭代成本。
13. **多线程分片**：AOI 按 Zone/线程分片时，跨片边界实体需要"共享兴趣集"或双写（成本可控），避免全局锁（关联 04-并发篇的缓存行竞争）。

## 7. FAQ

**Q1：九宫格、十字链表、四叉树怎么选？**
九宫格（网格）实现简单、局部性好，适合均匀分布；十字链表适合实体极少移动的静态场景；四叉树适合密度不均（城市/野外分界）。本层建议网格起步，热点再换。

**Q2：AOI 半径怎么定？**
由玩法可见距离决定（渲染距离、交互距离、战斗距离取 max）；过大会放大发送量（平方级），过小导致"看到敌人消失"——上线前用压测标定。

**Q3：Enter/Leave 事件丢了会怎样？**
Enter 丢 → 客户端永远看不到对象（最严重）；Leave 丢 → 幽灵对象残留；所以 Enter 可靠、Leave 尽力、Update 随意——可靠性分级是同步协议设计的核心。

**Q4：模拟器的"正确率 100%"说明网格 AOI 无错吗？**
只说明与切比雪夫口径的 ground truth 一致；真实项目若用欧氏距离判定可见性，角落格存在圆方差异（本实验 10000 实体约 2.5 万对/帧），需按玩法接受或加距离过滤。

**Q5：UE ReplicationGraph 和自研 AOI 能混用吗？**
DS 场景直接用 ReplicationGraph（引擎内置）；自研服务器（非 UE 逻辑服）用自研 AOI，两者是同一问题的两种实现，可互相参考策略（AlwaysRelevant、距离条件、网格分桶）。

**Q6：为什么发送估算和比较次数差这么多？**
比较次数是"扫描成本"（CPU），发送估算是"兴趣集大小"（带宽）——CPU 与带宽是独立的预算维度，都要进预算表。

**Q7：实体静止时 AOI 还有成本吗？**
静止实体不跨格、兴趣集不变 → 每帧只更新位置（Update），无 Enter/Leave；成本从"兴趣计算"降为"发送 Update"，这是聚集场景的主要节省点——所以压测场景要混合静止/移动比例。

**Q8：兴趣集 diff 每帧都做吗？**
可以按帧做（实验口径），也可以按"跨格才 diff"（静止省成本）；工程上常用"跨格触发 diff + 定期全量校准"，防止漏事件。

**Q9：AOI 结果怎么进网络包？**
Enter/Leave 是可靠的显式消息（带实体完整信息）；Update 是批量位置/状态包（合并多实体）；优先级与限流在发送层执行（见 3.3），AOI 层只产出"逻辑事件"。

**Q10：模拟器能直接用于容量规划吗？**
能给出结构结论（比较次数、发送量随规模的变化率），不能直接给带宽绝对值——带宽 = 发送量 × 真实消息大小 × 频率，需要协议与压测校准；两者结合才是容量结论。

**Q11：AOI 与寻路的空间索引能共用吗？**
可以部分共用（同一网格/四叉树），但访问模式不同：AOI 是"邻域聚合 + 每帧 diff"，寻路是"单点查询 + 高频局部更新"；共用时注意锁与缓存行竞争（见 04-并发篇）。

**Q12：为什么断言"正确率 100%"仍要保留暴力对照？**
暴力对照是"唯一能证明正确"的手段（ground truth）；实现重构（换数据结构、改半径逻辑）后对照能在 CI 里立刻暴露回归，成本是测试环境的 O(N²) 上限——只在测试规模（如 2000 实体）跑，不跑生产规模。

**Q13：Enter 全量信息会不会太大？**
Enter 携带"实体 ID + 初始位置 + 类型 + 关键状态"的压缩摘要；全量属性通过后续 Update 补齐。体积换取的是"客户端立即可见"，比二次请求的往返更划算。

**Q14：AOI 半径与渲染距离必须一致吗？**
不必。AOI 是"逻辑可见"，渲染距离是"表现可见"；AOI 半径通常略大于渲染距离（预留移动缓冲），两者分离后各自可调（AOI 影响带宽，渲染影响 GPU）。

**Q15：Enter 可靠、Update 尽力，断线重连怎么办？**
重连客户端应收到"全量快照"（当前兴趣集 + 位置），而不是依赖断线期间的事件流——这是重连协议与 AOI 的接口（关联 DS 会话重连专题），事件流只服务在线期间的增量。

**Q16：AOI 网格与场景加载（Zone streaming）怎么配合？**
实体只进入已加载的 Zone；AOI 网格按 Zone 划分，跨 Zone 边界实体走"迁移"而非普通跨格（见 `04-Scene-Map-Zone与实例管理` 规划）——AOI 数据结构要支持 Zone 维度的独立网格与迁移钩子。
