# UE Dedicated Server 机器人压测与容量评估

> 用真实 UE 协议的机器人负载驱动 Dedicated Server，从单实例容量、阶梯加压、资源拐点到区域容量规划的完整评估方法。

## 元数据

- 版本基线：UE5.8.0 / CL55116800 / ++UE5+Release-5.8
- 适用范围：Dedicated Server 的机器人压测场景设计、无头机器人实现方案、阶梯加压、容量拐点、资源监控与容量评估报告。
- 事实边界：UE/Gauntlet 能力以 Epic 5.8 官方文档与既有联机验收专题为边界；机器人实现、场景脚本、压测编排与容量数字均为项目方案。
- 事实边界：本文不把未核对的 UE 内置压测 API 或第三方工具写成既有事实；所有 `<...>` 名称、数值和路径都是占位符。
- 官方参考：https://dev.epicgames.com/documentation/en-us/unreal-engine
- 最后更新：2026-08-07

## 概述

机器人压测（Bot Load Testing）回答三个问题：
这台 DS 单实例能承载多少玩家？拐点在哪里？区域需要多少实例？

与通用服务端压测（HTTP 接口/QPS）不同，UE DS 压测必须驱动真实游戏协议：
连接、登录、复制、RPC、移动、战斗、结算都是状态耦合的路径，只打网络层端口测不出容量。
机器人需要像真实客户端一样走完"连接 → 登录 → 进入地图 → 行为循环 → 结算/退出"，
同时服务端记录 Tick、带宽、内存、连接与复制指标。

压测结果要能回答容量问题，而不是只输出"没崩"：
容量结论 = 场景定义 + 硬件基线 + 拐点证据 + 余量策略。

## 2. 核心概念表

| 概念 | 英文 | 作用 | 常见误区 |
| --- | --- | --- | --- |
| 机器人 | Bot | 模拟真实玩家行为的无头客户端/协议代理 | 只做登录挂机，测不出真实容量 |
| 行为脚本 | Behavior Script | 定义机器人的行为比例与序列 | 所有机器人行为相同 |
| 阶梯加压 | Ramp-up | 逐步增加负载找拐点 | 一次打满，看不出拐点 |
| 容量拐点 | Capacity Inflection | 延迟/资源开始恶化的负载点 | 把"不崩"当拐点 |
| 单实例容量 | Per-Instance Capacity | 一台 DS 可承载的玩家/连接数 | 只看 CCU，忽略连接与端口 |
| 复制负载 | Replication Load | 复制对象、频率与带宽成本 | 忽略复制只测网络层 |
| 场景混合 | Behavior Mix | 接近真实玩家的行为分布 | 压测场景与线上脱节 |

## 3. 机器人形态

### 3.1 三种形态对比

| 形态 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 无头 UE 客户端 | 用客户端 Target 无头运行机器人（`-nullrhi`/`-unattended` 等参数） | 协议、复制、预测完全真实 | 资源占用高、编排复杂 |
| 外部协议机器人 | 复用协议编解码栈的非 UE 进程 | 密度高、部署灵活 | 协议漂移风险、复制行为不完整 |
| 录制回放 | 抓取真实对局回放驱动 | 行为真实 | 覆盖场景有限 |

UE 无头客户端是否支持、支持哪些参数，以目标构建与官方文档核对为准。
大规模压测通常组合使用：协议机器人在接入层施压，无头 UE 客户端在少数节点验证端到端路径。

### 3.2 机器人必须走真实路径

```text
机器人路径 = 连接 + 登录 + 进入地图 + 行为循环 + 结算/退出

行为循环 = 移动 + 交互/技能 + 聊天/事件 + 观察
```

只测"连接后挂机"会严重低估复制、移动与战斗负载。
压测场景必须包含线上真实行为比例（场景混合）。

## 4. 场景与负载模型

### 4.1 场景定义

| 场景 | 行为构成（示意） | 目标 |
| --- | --- | --- |
| 登录风暴 | 大量并发登录/退出 | 登录路径容量与拒绝策略 |
| 常规对局 | 移动 + 技能 + 事件 | 单实例真实容量 |
| 高密度战斗 | 高频技能、命中、结算 | 复制与 Tick 压力 |
| 满员长稳 | 满容量 + 长时间运行 | 泄漏与漂移 |
| 尖峰加入 | 突发大量 JIP | 快照与带宽冲击 |
| 弱网混合 | 部分机器人带延迟/丢包 | 弱网容量衰减 |

### 4.2 负载模型

```mermaid
flowchart LR
    A[基线小负载] --> B[阶梯加压]
    B --> C[拐点识别]
    C --> D[拐点上下确认]
    D --> E[满员长稳]
    E --> F[尖峰与恢复]
    F --> G[容量结论]
```

阶梯加压建议步长小、每级停留足够时间（让指标稳定）：

```text
0 -> 4 -> 8 -> 16 -> 24 -> 32 -> 40 -> 48 -> 56 -> 64
每级停留 <n> 分钟，采集 P50/P95/P99 与资源曲线
```

## 5. 指标与监控

### 5.1 服务端指标

| 指标 | 口径 | 拐点信号 |
| --- | --- | --- |
| Tick 时间 | mean/P95/P99 | P95 持续上升且不回落 |
| 连接数 | 活跃连接/CCU | 连接成本非线性增长 |
| 收发包 | 每连接每秒 | 队列积压 |
| 复制字节 | 每连接每秒 | 带宽预算打满 |
| 内存 | 峰值/增长斜率 | 单调增长（泄漏） |
| CPU | 单线程/多核分解 | 单核打满 |
| 长帧 | P99/最长帧 | 复制或 GC 尖峰 |

### 5.2 客户端视角指标

机器人同时上报客户端视角指标：连接耗时、登录耗时、状态同步延迟、行为执行成功率。
服务端指标正常但客户端体验变差，说明存在"服务端吞吐高、体验差"的隐性拐点。

### 5.3 指标关联

所有指标带 `buildId`、`map`、`population`、`hardware` 与网络条件标签。
长帧要关联连接数、收发包与复制字节，才能解释"偶发卡顿"。

## 6. 压测环境

### 6.1 环境要求

| 要求 | 理由 |
| --- | --- |
| 与生产同构 | CPU 架构、内存、网络拓扑一致，容量结论才可信 |
| 压测端独立部署 | 压测程序不与被测服务器抢资源 |
| 端口池 | 多实例/多测试原子分配端口 |
| 数据隔离 | 机器人账号独立分区，不污染正式数据 |
| 版本锁定 | 服务端、客户端、机器人协议同一 BuildId |

### 6.2 编排

压测编排器负责：

1. 启动被测 DS 实例（干净 Stage/Archive）。
2. 按阶梯模型调度机器人进场/离场。
3. 采集服务端与机器人指标。
4. 触发拐点后自动停止并保存证据包。
5. 输出容量报告。

```text
编排输出：
  - 每级负载的指标快照
  - 拐点判定（规则或人工）
  - 容量结论与建议
  - 证据包（日志、Trace、报告 JSON）
```

## 7. 容量评估模型

### 7.1 单实例容量

单实例容量 = f(玩法场景, 硬件, 带宽, Tick 预算, 内存, 连接上限)

```text
容量结论模板：
  场景：<mode/map>
  硬件：<cpu/mem/network>
  舒适容量：<n> 玩家（P95 Tick < 阈值，无丢更新）
  极限容量：<m> 玩家（拒绝增长或体验不可接受）
  主要瓶颈：<Tick/带宽/内存/连接>
```

### 7.2 区域容量

```text
区域实例数 = ceil(区域峰值 CCU / 单实例舒适容量) * 冗余系数

冗余系数 = 1 / (1 - 故障余量 - 波动余量)
```

区域容量还要考虑：匹配等待、尖峰（开服/活动）、Draining 期间的不可分配比例、
发布灰度期间新旧版本并存的双倍容量需求。

### 7.3 容量报告

报告必须包含：

1. 目标与场景定义。
2. 环境与版本（硬件、BuildId、地图、参数）。
3. 指标曲线与拐点证据。
4. 瓶颈定位与建议。
5. 舒适容量/极限容量结论。
6. 复测计划与回归门禁。

## 8. 门禁与回归

### 8.1 容量门禁

| 门禁 | 通过标准（示意） |
| --- | --- |
| 舒适容量 P95 Tick | `< 阈值 ms` |
| 舒适容量丢更新 | `= 0` |
| 内存增长 | `Soak 内无单调增长` |
| 拐点后恢复 | `降载后指标回落` |
| 登录成功率 | `>= 阈值` |

### 8.2 回归

每次大版本（复制、AI、战斗、地图）后重跑核心场景。
容量退化是渐进问题，回归压测要保留基线对比。

## 10. 失败路径

| 症状 | 优先检查 | 处置方向 |
| --- | --- | --- |
| 压测端先崩 | 压测机资源、连接数上限 | 独立压测端与扩容 |
| 机器人不真实 | 行为混合、协议栈 | 复用真实协议与行为数据 |
| 拐点不明显 | 步长过大、停留过短 | 细化阶梯与稳定时间 |
| 指标漂移 | 环境不同构 | 锁版本与环境 |
| 长稳泄漏 | 内存斜率、连接积累 | 定位泄漏并复测 |
| 结论不可复现 | 证据不完整 | 固定 BuildId 与报告模板 |

## 11. 最佳实践

### 实践 1：场景混合接近线上

用线上行为数据校准机器人比例，压测才逼近真实负载。

### 实践 2：阶梯找拐点

小步长、每级稳定后采数，找到"指标开始恶化"的拐点而不是"没崩"。

### 实践 3：服务端与客户端指标双看

服务端吞吐正常不代表体验正常，机器人客户端视角是隐性拐点的探测器。

### 实践 4：环境与生产同构

CPU 架构、内存、网络拓扑不一致时，容量结论不可信。

### 实践 5：容量结论带证据

舒适容量、极限容量、瓶颈与建议都附指标曲线与证据包。

### 实践 6：容量回归常态化

大版本后重跑核心场景，容量退化要能被门禁拦截。

### 实践 7：不把"不崩"当容量

容量拐点由延迟、丢更新、Tick 与资源恶化定义，不是进程存活。

## 12. 常见问题 FAQ

### Q1：机器人数 = 玩家数吗？

不等于。机器人行为与真实玩家有差异，需要场景校准；
容量结论应表达为"该场景下可承载的玩家数"。

### Q2：一定要用无头 UE 客户端吗？

不一定。协议机器人密度高，无头 UE 客户端端到端更真实，通常组合使用。
选择取决于测什么：接入容量还是完整玩法路径。

### Q3：拐点怎么定义？

建议规则：P95 Tick 连续上升超过阈值、丢更新出现、登录失败率上升或内存单调增长。
拐点定义写入压测配置，避免人工拍脑袋。

### Q4：压测能替代 Soak 吗？

不能。压测找容量，Soak 找泄漏与漂移，二者都要。

### Q5：弱网下容量会变吗？

会。延迟、丢包会增加重传与队列压力，容量模型要包含弱网衰减因子。

### Q6：容量报告多久更新一次？

大版本与关键系统变更后必须更新；日常按版本节奏回归。
