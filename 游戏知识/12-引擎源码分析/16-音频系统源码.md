## 一、概述（对应知识点）

知识库《10-音频系统/01-音频基础与播放》从"资产怎么选、PlaySound 怎么打、音量怎么控"讲清了音频的**使用层**。本篇源码分析回答的是同一批问题的**实现层**：

1. **一个 WAV 资产（USoundWave）从磁盘到声卡**，中间经过哪些对象、哪些线程、哪些缓冲；
2. **PlaySound2D / UAudioComponent::Play 按下的一瞬间**，引擎在游戏线程做了什么、又往音频线程投递了什么；
3. **混音管线**：FMixerSource、FMixerSourceManager、FMixerSubmix 三者如何分工，Submix 效果器挂在哪个环节；
4. **5.8 的音频关键类**：以实际源码为准，理清 FAudioDevice / FMixerDevice / FSoundSource / FMixerSource 的继承与组合关系。

阅读前建议先通读对应知识点文档，把"声音类、播放方式、Sound Class、Submix"这些概念名词带上，再对照本文件中的真实代码。**全文代码节选均由脚本按行区间从 5.8.2 checkout 机械抽取**：每块前一行是「摘自 `<仓库相对路径>`（第 N 行起）」，块内第一个非节选标记行逐字等于该文件第 N 行，节选处标注省略的真实行区间与行数。

> ⚠️ 版本差异提示：5.8 源码中 **FAudioDevice 上已经没有名为 `PlaySound` 的成员函数**（任务描述中的"PlaySound"在 5.8 对应 `UGameplayStatics::PlaySound2D/PlaySoundAtLocation` 与 `UAudioComponent::Play` 等高层入口，最终统一收敛到 `FAudioDevice::AddNewActiveSound`）。这一点在 3.4 节有完整证据链，请不要按旧版本文档的记忆去查找 `FAudioDevice::PlaySound`。

## 三、关键类/函数剖析
### 3.1 音频架构总览：三个线程 + 一个回调

UE 5.8 的音频运行时由四个执行上下文组成（这是理解所有代码的前提）：

| 执行上下文 | 线程 | 主要职责 | 关键入口 |
| --- | --- | --- | --- |
| 游戏线程 | Game Thread | 资产访问、`UAudioComponent::Play`、`PlaySound2D`、参数下发 | `UGameplayStatics`、`UAudioComponent` |
| 音频线程 | Audio Thread（`FAudioThread`） | 声音请求入队、ActiveSound 更新、SoundClass 音量、WaveInstance 生成 | `FAudioDevice::Update` |
| 音频渲染线程 | Audio Render Thread（平台回调） | 解码、DSP、混音、输出 | `FMixerDevice::OnProcessAudioStream` |
| 渲染工作线程（5.8 新增） | UE Tasks Worker | 并行渲染各 Source 的渲染步骤 | `FAudioRenderScheduler::RenderBlock` |

5.8 源码中的第一个关键证据是游戏线程→音频线程的**唯一投递口** `FAudioThread::RunCommandOnAudioThread`（无返回值、无队列参数，真正的命令体由传入的 `TUniqueFunction` 承载；未启用线程化音频时由同文件的 `GetCommandWrapper` 直接原地执行）：
`FMixerDevice::OnProcessAudioStream` 是音频渲染线程回调，声明见 `Engine/Source/Runtime/AudioMixer/Public/AudioMixerDevice.h` 第 223 行。其实现开头就有这样一段注释，证明 5.8 中渲染回调可能跑在任务管理器的工作线程上：

摘自 `Engine/Source/Runtime/Engine/Public/AudioThread.h`（第 50 行起）

```cpp
public:
	/** Starts the audio thread. */
	static ENGINE_API void StartAudioThread();

	/** Stops the audio thread. */
	static ENGINE_API void StopAudioThread();

	/** Execute a command on the audio thread. If it's safe the command will execute immediately. */
	static ENGINE_API void RunCommandOnAudioThread(TUniqueFunction<void()> InFunction, const TStatId InStatId = TStatId());

	/** Processes all enqueued audio thread commands. */
	static ENGINE_API void ProcessAllCommands();
```
它紧接的调用顺序就是「一个渲染块」的骨架：`NotifyAudioDevicePreRender` → `PumpCommandQueue` → Quartz 时钟 `QuantizedEventClockManager.Update` → `SourceManager->ComputeNextBlockOfSamples()`；随后（`AudioMixerDevice.cpp` 第 1704~1708 行）取主 Submix 并调用 `MainSubmixPtr->ProcessAudio(Output)`，最后（第 1721 行）`SourceManager->UpdateSourceState()`。注意这里同时印证了上表两条：渲染回调入口是 `OnProcessAudioStream`，而真正的 Source 渲染调度在 `FMixerSourceManager`（3.6 节）。

### 3.2 FAudioDevice / FMixerDevice —— 音频设备入口

#### 3.2.1 继承关系（真实声明）

`FAudioDevice` 是引擎侧音频设备的抽象基类，声明见 `Engine/Source/Runtime/Engine/Public/AudioDevice.h` 第 416 行；`FMixerDevice` 是 AudioMixer 模块对它的实现，同时实现 `IAudioMixer`（渲染回调接口）与 `FGCObject`（UObject 引用追踪）：

摘自 `Engine/Source/Runtime/AudioMixer/Private/AudioMixerDevice.cpp`（第 1666 行起）

```cpp
	bool FMixerDevice::OnProcessAudioStream(FAlignedFloatBuffer& Output)
	{
		LLM_SCOPE(ELLMTag::AudioMixer);

		// This function could be called in a task manager, which means the thread ID may change between calls.
		ResetAudioRenderingThreadId();

		// Cache the audio platform thread id for debugging purposes. This is
		// an attempt to narrow down the causes of UE-209237. The theory is
		// that the there are multiple threads attempting to run audio rendering
		// commands. To catch the issue we attempt to cache the thread id before
		// running audio rendering commands. We then check that the thread id
		// has not changed for the duration that render thread commands have
		// run.
		std::atomic<int32> CurrentAudioPlatformThreadId = AudioPlatformThreadId.load();

		// Update the audio render thread time at the head of the render
		AudioThreadTimingData.AudioRenderThreadTime = FPlatformTime::Seconds() - AudioThreadTimingData.StartTime;

		// notify interested parties
		FAudioDeviceRenderInfo RenderInfo;
		RenderInfo.NumFrames = SourceManager->GetNumOutputFrames();
		NotifyAudioDevicePreRender(RenderInfo);

		// Pump the command queue to the audio render thread
		PumpCommandQueue();

		// update the clock manager
		QuantizedEventClockManager.Update(SourceManager->GetNumOutputFrames());

		// Compute the next block of audio in the source manager
		SourceManager->ComputeNextBlockOfSamples();
```

把 3.4.3 / 3.4.4 的源码顺序合起来看，一次"点播放"到"出声"的实际顺序是：

1. 游戏线程：`FActiveSound` 组装 → `AddNewActiveSound` → `Sound->InitResources()`；
2. 投递：不在音频线程时 `FAudioThread::RunCommandOnAudioThread(lambda)`（`AudioDevice.cpp` 第 5300~5303 行）；
3. 音频线程：`AddNewActiveSoundInternal` 入列 → 每帧 `FAudioDevice::Update` → 求值出 `FWaveInstance` → `StartSources`；
4. `StartSources` 内：`FreeSources.Pop()`（第 4582 行）→ `PrepareForInitialization`（第 4589 行）→ `IsPreparedToInit`（第 4595 行）→ `Init`（第 4598 行）→ `Update`（第 4607 行）→ `Play`（第 4612 行）；
5. `FMixerSource::Init` 内：`MixerDevice->GetMixerSourceVoice()`（`AudioMixerSource.cpp` 第 344 行）→ `MixerSourceVoice->Init(InitParams)`（第 658 行）→ `SourceManager->InitSource(SourceId, InitParams)`（`AudioMixerSourceVoice.cpp` 第 88 行）；
6. 渲染线程：`PumpCommandQueue` 执行 `InitSource` → 进入 `FSourceInfo` 槽位 → 下一渲染块开始真正解码输出。

**这条顺序解释了 3.4.4 里"先 Update 后 Play"为什么不是笔误**：`Update()` 会把音量/音高/Submix 发送等参数写入 SourceManager 的命令队列，`Play()` 只是把 `SourceInfo.bIsPlaying` 置真；如果先 Play 后 Update，第一块音频就会用上一次的参数（或默认值）渲染。

```cpp
	{
```

```cpp
		CSV_SCOPED_TIMING_STAT(Audio, SourceManagerUpdate);
```
