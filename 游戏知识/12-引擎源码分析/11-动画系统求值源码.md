## 三、关键类/函数剖析

### 3.1 AnimInstance 与 Proxy 的分离设计

#### 3.1.1 为什么要有 Proxy

`UAnimInstance` 是 UObject，受 GC 管理、只能在游戏线程安全访问；而动画图（AnimGraph）的求值在 UE 4.14+ 之后可以放到工作线程（TaskGraph）并行执行。直接把"节点树运行时状态"放在 UObject 里会导致工作线程读写 GC 对象。因此引擎把**可并行求值的运行时状态**全部搬进 `FAnimInstanceProxy`（一个普通 C++ 对象），UAnimInstance 只保留游戏线程数据与薄薄的转发层。

#### 3.1.2 Proxy 的创建与获取（AnimInstance.h 节选）

（2026-09-15：原示意块已替换为 5.8 源码逐字版）

Proxy 的**创建点**是虚函数 `UAnimInstance::CreateAnimInstanceProxy()`，**获取点**是一对模板函数 `GetProxyOnGameThread<T>()` / `GetProxyOnAnyThread<T>()`（二者都是 `protected`，所以业务代码里通常通过 C++ 子类或公开转发接口取用）。5.8 的真实实现如下。

摘自 `Engine/Source/Runtime/Engine/Classes/Animation/AnimInstance.h`（第 1715 行起）

```cpp

	ENGINE_API virtual FAnimInstanceProxy* CreateAnimInstanceProxy();

	/** Override point for derived classes to destroy their own proxy objects (allows custom allocation) */
	ENGINE_API virtual void DestroyAnimInstanceProxy(FAnimInstanceProxy* InProxy);

	/** Access the proxy but block if a task is currently in progress as it wouldn't be safe to access it
	 *	This is protected static member for allowing derived to access
	 */
	template <typename T /*= FAnimInstanceProxy*/>	// @TODO: Cant default parameters to this function on Xbox One until we move off the VS2012 compiler

	{

```

工作线程侧的取用接口是另一个模板，它只在“当前就在游戏线程”时才去等并行任务：

摘自 `Engine/Source/Runtime/Engine/Classes/Animation/AnimInstance.h`（第 1767 行起）

```cpp
	/** Access the proxy but block if a task is currently in progress (and we are on the game thread) as it wouldn't be safe to access it */
	template <typename T/* = FAnimInstanceProxy*/>	// @TODO: Cant default parameters to this function on Xbox One until we move off the VS2012 compiler
	inline T& GetProxyOnAnyThread()
	{
		if(IsSkeletalMeshComponent(GetOuter()))
		{
			if(IsInGameThread())
			{
				HandleExistingParallelEvaluationTask(GetSkelMeshComponent());
			}
		}
		if(AnimInstanceProxy == nullptr)
		{
			AnimInstanceProxy = CreateAnimInstanceProxy();
		}
		return *static_cast<T*>(AnimInstanceProxy);
	}
```

逐行解构：

- `CreateAnimInstanceProxy()` 是虚函数，默认返回 `new FAnimInstanceProxy(this)`；C++ 子类可以重写它返回自己的 Proxy 子类（例如带骨骼缓存的自定义 Proxy），蓝图生成的类（`UAnimBlueprintGeneratedClass` 派生的 AnimInstance 子类）也会重写它以附带编译期生成的节点实例数据。
- **`GetProxyOnGameThread` 不是“纯懒创建”**：它先 `check(IsInGameThread())`，再看 AnimInstance 的 Outer 是不是 `USkeletalMeshComponent`；若是，就先调用 `HandleExistingParallelEvaluationTask(...)`——**如果此刻有一个并行求值任务正在跑，游戏线程会在这里等它跑完**，然后才允许访问 Proxy。这是“游戏线程读姿势不会读到半成品”的保护，也是函数上方注释 "block if a task is currently in progress as it wouldn't be safe to access it" 的字面含义（原文把它写成“拿不到就创建”的纯懒创建，漏掉了这道同步门）。
- `GetProxyOnAnyThread<T>()` 在工作线程上不会等待（`IsInGameThread()` 为假时跳过 `HandleExistingParallelEvaluationTask`），这正是它敢被 `ParallelEvaluateAnimation` 这类工作线程函数调用的原因；代价是**工作线程绝不能写 UAnimInstance 的可变数据**。
- `DestroyAnimInstanceProxy(FAnimInstanceProxy* InProxy)` 与创建配对，同样只能在游戏线程调用（AnimInstance 卸载/重建路径）。
- `HandleExistingParallelEvaluationTask` 是 `UAnimInstance` 的静态成员，声明在该头文件第 1813 行；它内部对 `ParallelAnimationEvaluationTask` 做 `WaitUntilTaskCompletes`（`SkeletalMeshComponent.cpp` 第 5025 行），因此这里的“等”是有真实任务句柄支撑的，不是空注释。

#### 3.1.3 Proxy 的并行求值入口（AnimInstanceProxy.cpp 节选）

（2026-09-15：原示意块已替换为 5.8 源码逐字版）

`FAnimInstanceProxy::UpdateAnimation()` 是“更新整棵动画图”的唯一入口——它在游戏线程（`NeedsImmediateUpdate` 为真时，经 `UAnimInstance::ParallelUpdateAnimation()` 转进来）或工作线程（并行求值任务）上都会执行，因此函数体内不允许访问任何 UObject 的可变数据。

摘自 `Engine/Source/Runtime/Engine/Private/Animation/AnimInstanceProxy.cpp`（第 1231 行起）

```cpp
void FAnimInstanceProxy::UpdateAnimation()
{
	LLM_SCOPE(ELLMTag::Animation);
	DECLARE_SCOPE_HIERARCHICAL_COUNTER_FUNC()

	FMemMark Mark(FMemStack::Get());
	FAnimationUpdateSharedContext SharedContext;
	FAnimationUpdateContext Context(this, CurrentDeltaSeconds, &SharedContext);
	UE_LOG_CONTEXT("AnimBlueprint", FTopLevelAssetPath(GetAnimInstanceObject() ? GetAnimInstanceObject()->GetClass() : nullptr));

	if(AnimClassInterface && AnimClassInterface->GetAnimBlueprintFunctions().Num() > 0)
	{
		Context.SetNodeId(AnimClassInterface->GetAnimBlueprintFunctions()[0].OutputPoseNodeIndex);
	}

	UpdateAnimation_WithRoot(Context, RootNode, NAME_AnimGraph);

	// Tick syncing
	Sync.TickAssetPlayerInstances(*this, CurrentDeltaSeconds);

	// Now that we have updated our asset players we record their tick records from read buffer (meaning they have up-to-date info).
#if ANIM_TRACE_ENABLED
	{
		for (const TTuple<FName, FAnimGroupInstance>& TickRecordGroup : Sync.GetSyncGroupMapRead())
		{
			for (const FAnimTickRecord& TickRecord : TickRecordGroup.Value.ActivePlayers)
			{
				TRACE_ANIM_TICK_RECORD(Context, TickRecord)
			}
		}

		for (const FAnimTickRecord& TickRecord : Sync.GetUngroupedActivePlayersRead())
		{
			TRACE_ANIM_TICK_RECORD(Context, TickRecord)
		}
	}
#endif
}
```

要点：

- 函数体只有四步：建共享上下文与更新上下文（`FAnimationUpdateSharedContext` + `FAnimationUpdateContext(this, CurrentDeltaSeconds, &SharedContext)`）→ 给上下文设 NodeId（供 Tracing/调试用）→ 下推 `UpdateAnimation_WithRoot(Context, RootNode, NAME_AnimGraph)` → `Sync.TickAssetPlayerInstances(*this, CurrentDeltaSeconds)` 推进同步组。**Native/蓝图侧的更新调用不在这里，而在 `UpdateAnimation_WithRoot` 内部**（见 3.2.3 的第二块）。

#### 3.2.1 调用者：SkeletalMeshComponent

- **`bNeedsValidRootMotion && RootMotionMode == RootMotionFromEverything`**：要从动画里取 Root Motion 驱动移动，必须先算完姿势。这也是 `EUpdateAnimationFlag::ForceParallelUpdate` 存在的理由（CharacterMovement 提前消费 Root Motion 时会改传这个 flag）。
- **`!CanRunParallelWork()`**：实例级“不能跑并行”的判定（例如工作线程不可用、实例被标记为不可并行）。
- **`GIntraFrameDebuggingGameThread`**：蓝图断点/逐步调试期间强制回游戏线程，保证有稳定的调试栈。
- **`WITH_EDITOR` 下的两个条件**：该 AnimBP 正被“作为调试对象”打开（`Blueprint->GetObjectBeingDebugged() == this`），或该蓝图设了断点（`FKismetDebugUtilities::BlueprintHasBreakpoints`）——**只有编辑器构建才有这两个条件**，Shipping/Test 下不存在。
- **CVar 三兄弟**（真实名字与默认值见 `SkeletalMeshComponent.cpp` 第 76~78 行）：`a.ParallelAnimUpdate`（`CVarUseParallelAnimUpdate`，默认 1，管“更新”）、`a.ParallelAnimEvaluation`（`CVarUseParallelAnimationEvaluation`，默认 1，管“求值”）、`a.ForceParallelAnimUpdate`（`CVarForceUseParallelAnimUpdate`，默认 0）。原文只提了前两个；**第三个是“无视项目/实例开关、强制走工作线程更新”的调试开关**，且它是 `bUseParallelUpdateAnimation` 表达式里的“或”项——置 1 时连项目设置都会失效。
- **`!bUseParallelUpdateAnimation`**：即 `(GetDefault<UEngine>()->bAllowMultiThreadedAnimationUpdate && bUseMultiThreadedAnimationUpdate) == false`。注意两个成员名**都真实存在**：项目级是 `UEngine::bAllowMultiThreadedAnimationUpdate`（`Engine.h` 第 1659 行），实例级是 `UAnimInstance::bUseMultiThreadedAnimationUpdate`（`AnimInstance.h` 第 382 行，位域 `uint8 ... : 1`）——不是 `bAllowMultiThreadedAnimationUpdate` 的实例版。
- **`DeltaSeconds == 0.0f`**：暂停帧（`TickAnimation(0.f, false)` 的强制刷新路径）直接同步算完。

- **求值任务 `FParallelAnimationEvaluationTask`**：`GetDesiredThread()` 返回 `CPrio_ParallelAnimationEvaluationTask.Get()`；该优先级对象由 `FAutoConsoleTaskPriority` 声明在同文件第 138~144 行，CVar 名为 `TaskGraph.TaskPriorities.ParallelAnimationEvaluationTask`，取值组合是“高优先级线程 + 普通任务优先级，否则普通线程 + 高任务优先级”。工作线程上的 `DoTask` 做三件事——打 UObject 计时作用域（`FScopeCycleCounterUObject`）、在非 Shipping 构建里读 `CVarStallParallelAnimation` 人为制造延迟（用于复现并行时序 bug）、`GInitRunaway()` 检查平台线程是否跑飞，最后调用 `Comp->ParallelAnimationEvaluation()`。非 Shipping 构建还会把耗时喂给 `FParallelAnimationEvaluationStats`。
- **完成任务 `FParallelAnimationCompletionTask`**：`GetDesiredThread()` 返回**游戏线程**（若 CVar `GParallelAnimCompletionTaskHighPriority` 为真则加 `HighTaskPriority`），`DoTask` 里先校验 `Comp->ParallelAnimationEvaluationTask` 仍是有效 GraphEvent，再调 `Comp->CompleteParallelAnimationEvaluation(true)`——**收尾（姿势写回、通知分发、PostAnimEvaluation）永远在游戏线程**。
- 两个任务都只用 `TWeakObjectPtr<USkeletalMeshComponent>` 持有组件：组件可能在任务排队期间被销毁，弱指针让任务能安全地“什么都不做”。
- 两者都返回 `ESubsequentsMode::TrackSubsequents`，因此完成任务可以挂在前置任务之后（见 3.3.5 的 `Prerequistes`）。
- 结构上还有一个细节：完成任务的 `DoTask` 开头就是 `SCOPE_CYCLE_COUNTER(STAT_AnimGameThreadTime)` 与 `CSV_SCOPED_TIMING_STAT_EXCLUSIVE(Animation)`，说明**这段游戏线程耗时会被算进 Anim 的游戏线程预算**，`stat Anim` 里能看到。

#### 3.3.4 更新阶段向节点的传递（AnimInstanceProxy.cpp 节选）

更新阶段“下推到节点”发生在 `FAnimInstanceProxy::UpdateAnimationNode_WithRoot`：它先递增根节点的 `UpdateCounter`，再用 `UE::Anim::FNodeFunctionCaller` 依次派发节点上挂的蓝图函数，最后才调 `Update_AnyThread`。

摘自 `Engine/Source/Runtime/Engine/Private/Animation/AnimInstanceProxy.cpp`（第 127 行起）

```cpp
void FAnimInstanceProxy::UpdateAnimationNode_WithRoot(const FAnimationUpdateContext& InContext, FAnimNode_Base* InRootNode, FName InLayerName)
{
	LLM_SCOPE_BYNAME(TEXT("Animation/Graph"));

	TRACE_SCOPED_ANIM_GRAPH(InContext)
	TRACE_SCOPED_ANIM_NODE(InContext)

	if(InRootNode != nullptr)
	{
		if (InRootNode == RootNode)
		{
			UpdateCounter.Increment();
		}

		UE::Anim::FNodeFunctionCaller::InitialUpdate(InContext, *InRootNode);
		UE::Anim::FNodeFunctionCaller::BecomeRelevant(InContext, *InRootNode);
		UE::Anim::FNodeFunctionCaller::Update(InContext, *InRootNode);
		InRootNode->Update_AnyThread(InContext);

		// We've updated the graph, now update the fractured saved pose sections
		// Note SavedPoseQueueMap can be empty if we have no cached poses in use
		if(TArray<FAnimNode_SaveCachedPose*>* SavedPoseQueue = SavedPoseQueueMap.Find(InLayerName))
		{
			for(FAnimNode_SaveCachedPose* PoseNode : *SavedPoseQueue)
			{
				PoseNode->PostGraphUpdate();
			}
		}
	}
}
```

可以看到：

- 更新是**从根节点开始深度优先递归**的（`Update_AnyThread` 内部继续调子节点的 `Update_AnyThread`），每个节点拿到同一个 `FAnimationUpdateContext`（携带 DeltaSeconds、最终混合权重 `GetFinalBlendWeight()` 等）。
- **蓝图节点函数的三个派发点**：`FNodeFunctionCaller::InitialUpdate` / `BecomeRelevant` / `Update` 依次在 `Update_AnyThread` 之前执行——这三者对应 AnimGraph 节点详情面板上的同名事件，是“节点自己的蓝图逻辑”与“节点 C++ 更新”的执行次序依据。
- `UpdateCounter.Increment()` 只对根节点做（`InRootNode == RootNode` 分支），所以 Proxy 级别的 `UpdateCounter` 表达的是“本帧动画图是否被更新过”。
- 函数末尾处理 `SavedPoseQueueMap`：缓存姿势节点（`FAnimNode_SaveCachedPose`）在整图更新完后才 `PostGraphUpdate()`——**缓存姿势必须在所有引用它的节点更新之后落盘**，这就是它被单独排队的原因。
- 该函数是 `virtual`（`AnimInstanceProxy.h` 第 624 行），Proxy 子类可以整体替换更新逻辑；`UpdateAnimationNode(InContext)`（第 127 行）只是以 `RootNode + NAME_AnimGraph` 转发进来。

```cpp
void USkeletalMeshComponent::DispatchParallelEvaluationTasks(FActorComponentTickFunction* TickFunction)
{
	// If we try and start parallel evaluation in a transaction, just run it immediately instead as it
	// is unsafe to have a transactional thread interacting with anything async.
	if (AutoRTFM::IsTransactional())
	{
		ensureMsgf(false, TEXT("Should not be calling `DispatchParallelEvaluationTasks` from within a transaction!"));
		check(!IsValidRef(ParallelAnimationEvaluationTask));
		DoParallelEvaluationTasks_OnGameThread();
		return;
	}

	LLM_SCOPE(ELLMTag::SkeletalMesh);
	SwapEvaluationContextBuffers();

#if WITH_EDITOR
	// We can only finish compilation on the game-thread, so wait here before spawning eval tasks.
	if (GetSkeletalMeshAsset() && GetSkeletalMeshAsset()->IsCompiling())
	{
		FSkinnedAssetCompilingManager::Get().FinishCompilation({ GetSkeletalMeshAsset() });
	}
#endif

	// start parallel work
	check(!IsValidRef(ParallelAnimationEvaluationTask));
	ParallelAnimationEvaluationTask = TGraphTask<FParallelAnimationEvaluationTask>::CreateTask().ConstructAndDispatchWhenReady(this);

	// set up a task to run on the game thread to accept the results
	FGraphEventArray Prerequistes;
	Prerequistes.Add(ParallelAnimationEvaluationTask);
	FGraphEventRef TickCompletionEvent = TGraphTask<FParallelAnimationCompletionTask>::CreateTask(&Prerequistes).ConstructAndDispatchWhenReady(this);

	if ( TickFunction )
	{
		TickFunction->GetCompletionHandle()->DontCompleteUntil(TickCompletionEvent);
	}
}
```

要点：

- `SwapEvaluationContextBuffers()` 在投递前先交换双缓冲，保证工作线程读到的是上一帧稳定数据、写的是本帧缓冲。
- `TGraphTask<FParallelAnimationEvaluationTask>::CreateTask().ConstructAndDispatchWhenReady(this)` 是 TaskGraph 的标准投递写法；完成任务的 `CreateTask(&Prerequistes)` 把求值任务作为前置依赖——**TaskGraph 自动保证“算完才收”。**
- `TickFunction->GetCompletionHandle()->DontCompleteUntil(TickCompletionEvent)` 让本组件的 Tick 在“收尾任务完成”之前不算结束。这就是“动画姿势在本帧后续逻辑（如骨骼变换消费）里一定可用”的调度保证。
- 事务（`AutoRTFM::IsTransactional()`）下不允许投异步任务，会直接 `DoParallelEvaluationTasks_OnGameThread()` 同步跑完，并 `ensureMsgf` 报警。

- 需要“游戏线程预处理”的节点可以重写 `HasPreUpdate()` / `PreUpdate(const UAnimInstance* InAnimInstance)`（5.8 真实签名见 3.4.1），它在游戏线程、节点更新之前被调用（典型例子：`FAnimNode_ModifyBone` —— 5.8 位于 AnimGraphRuntime 模块，`Engine/Source/Runtime/AnimGraphRuntime/Public/BoneControllers/AnimNode_ModifyBone.h`）。
- 求值侧有两条对称入口：`Evaluate_AnyThread(FPoseContext&)`（局部空间）与 `EvaluateComponentSpace_AnyThread(FComponentSpacePoseContext&)`（组件空间），头文件注释明确要求“实现其中之一，不要两个都实现”（第 750、758 行原文 "You should implement either Evaluate or EvaluateComponentSpace, but not both of these."）。

```cpp
bool FAnimNode_StateMachine::FindValidTransition(const FAnimationUpdateContext& Context, const FBakedAnimationState& StateInfo, /*out*/ FAnimationPotentialTransition& OutPotentialTransition, /*out*/ TArray<int32, TInlineAllocator<4>>& OutVisitedStateIndices)
{
	// There is a possibility we'll revisit states connected through conduits,
	// so we can avoid doing unnecessary work (and infinite loops) by caching off states we have already checked
	const int32 CheckingStateIndex = GetStateIndex(StateInfo);
	if (OutVisitedStateIndices.Contains(CheckingStateIndex))
	{
		return false;
	}
	OutVisitedStateIndices.Add(CheckingStateIndex);

	const IAnimClassInterface* AnimBlueprintClass = Context.GetAnimClass();

	// Conduit 'states' have an additional entry rule which must be true to consider taking any transitions via the conduit
	//@TODO: It would add flexibility to be able to define this on normal state nodes as well, assuming the dual-graph editing is sorted out
	if (FAnimNode_TransitionResult* StateEntryRuleNode = GetNodeFromPropertyIndex<FAnimNode_TransitionResult>(Context.AnimInstanceProxy->GetAnimInstanceObject(), AnimBlueprintClass, StateInfo.EntryRuleNodeIndex))
	{
		if (StateEntryRuleNode->NativeTransitionDelegate.IsBound())
		{
			// attempt to evaluate native rule
			StateEntryRuleNode->bCanEnterTransition = StateEntryRuleNode->NativeTransitionDelegate.Execute();
		}
		else
		{
			// Execute it and see if we can take this rule
			StateEntryRuleNode->GetEvaluateGraphExposedInputs().Execute(Context);
		}

		// not ok, back out
		if (!StateEntryRuleNode->bCanEnterTransition)
		{
			return false;
		}
	}

	const double WorldTime = Context.AnimInstanceProxy->GetAnimInstanceObject()->GetWorld()->GetTimeSeconds();

	const int32 NumTransitions = StateInfo.Transitions.Num();
	for (int32 TransitionIndex = 0; TransitionIndex < NumTransitions; ++TransitionIndex)
	{
		const FBakedStateExitTransition& TransitionRule = StateInfo.Transitions[TransitionIndex];
		if (TransitionRule.CanTakeDelegateIndex == INDEX_NONE)
		{
			continue;
		}

		// Per-transition opt-in: skip rule evaluation entirely when the state machine's update context is inactive.
		if (TransitionRule.bOnlyEvaluateWhenActive && !Context.IsActive())
		{
			continue;
		}

		const FAnimationTransitionBetweenStates& TransitionInfo = GetTransitionInfo(TransitionRule.TransitionIndex);
		const int32 NextState = TransitionInfo.NextState;
		const FBakedAnimationState& NextStateInfo = GetStateInfo(NextState);

		// Check transition de-bounce time
		if (TransitionInfo.MinTimeBeforeReentry >= 0.0f && (WorldTime - LastStateEntryTime[NextState]) < TransitionInfo.MinTimeBeforeReentry)
		{
			continue;
		}

		FAnimNode_TransitionResult* ResultNode = GetNodeFromPropertyIndex<FAnimNode_TransitionResult>(Context.AnimInstanceProxy->GetAnimInstanceObject(), AnimBlueprintClass, TransitionRule.CanTakeDelegateIndex);
		float CrossfadeTimeAdjustment = 0.f;

		// If we require a valid sync group, check that first.
		if ((TransitionRule.SyncGroupNameToRequireValidMarkersRule != NAME_None)
			&& !Context.AnimInstanceProxy->IsSyncGroupValid(TransitionRule.SyncGroupNameToRequireValidMarkersRule))
		{
			ResultNode->bCanEnterTransition = false;
		}
		else if (ResultNode->NativeTransitionDelegate.IsBound())
		{
			// attempt to evaluate native rule
			ResultNode->bCanEnterTransition = ResultNode->NativeTransitionDelegate.Execute();
		}
		else if (TransitionRule.bAutomaticRemainingTimeRule)
		{
			bool bCanEnterTransition = false;
			if (const FAnimNode_AssetPlayerRelevancyBase* RelevantPlayer = GetRelevantAssetPlayerInterfaceFromState(Context, StateInfo))
			{
				if (const UAnimationAsset* AnimAsset = RelevantPlayer->GetAnimAsset())
				{
					float AnimTimeRemaining = AnimAsset->GetPlayLength() - RelevantPlayer->GetAccumulatedTime();

					// Check whether the player looped last frame
					if (RelevantPlayer->IsLooping() && AnimTimeRemaining > 0.f)
					{
						if (const FDeltaTimeRecord* DeltaTimeRecord = RelevantPlayer->GetDeltaTimeRecord())
						{
							if (DeltaTimeRecord->IsPreviousValid())
							{
								const float DeltaTimeFromPlayer = RelevantPlayer->GetAccumulatedTime() - DeltaTimeRecord->GetPrevious();
								const float DeltaTimeFromRecord = DeltaTimeRecord->Delta;

								// deal with negative play rates
								if (DeltaTimeFromPlayer * DeltaTimeFromRecord < 0.f)
								{
									AnimTimeRemaining = 0.f;
								}
							}
						}
					}

					// For transitions that go to a conduit the user is not able to edit the transition's cross fade duration,
					// therefore we force the cross fade duration to zero to ensure the transition is always triggerred upon reaching the end of the animation.
					const float CrossfadeDuration = GetStateInfo(TransitionInfo.NextState).bIsAConduit ? 0.0f : TransitionInfo.CrossfadeDuration;

					// Allow for used to determine the automatic transition trigger time or fallback to using cross fade duration.
					const float TransitionTriggerTime = (TransitionRule.AutomaticRuleTriggerTime >= 0.0f) ? TransitionRule.AutomaticRuleTriggerTime : CrossfadeDuration;
					CrossfadeTimeAdjustment = TransitionTriggerTime - AnimTimeRemaining;

					// Trigger transition only if we have "CrossfadeTimeAdjustment" seconds left before reaching animation end boundary.
					bCanEnterTransition = (CrossfadeTimeAdjustment >= 0.f);
				}
			}

			ResultNode->bCanEnterTransition = bCanEnterTransition;
		}
		else
		{
			// Execute it and see if we can take this rule
			ResultNode->GetEvaluateGraphExposedInputs().Execute(Context);
		}

		if (ResultNode->bCanEnterTransition == TransitionRule.bDesiredTransitionReturnValue)
		{
			// if next state is a conduit we want to check for transitions using that state as the root
			if (NextStateInfo.bIsAConduit)
			{
				if (FindValidTransition(Context, NextStateInfo, /*out*/ OutPotentialTransition, /*out*/ OutVisitedStateIndices))
				{
					OutPotentialTransition.SourceTransitionIndices.Add(TransitionRule.TransitionIndex);

					return true;
				}
			}
			// otherwise we have found a content state, so we can record our potential transition
			else
			{
				// clear out any potential transition we already have
				OutPotentialTransition.Clear();

				// fill out the potential transition information
				OutPotentialTransition.TransitionRule = &TransitionRule;
				OutPotentialTransition.TargetState = NextState;
				OutPotentialTransition.CrossfadeTimeAdjustment = CrossfadeTimeAdjustment;
				OutPotentialTransition.SourceTransitionIndices.Add(TransitionRule.TransitionIndex);

				return true;
			}
		}
	}

	return false;
}
```

解构：

- **conduit 防环**：`OutVisitedStateIndices` 是外部传入的“已访问状态”集合（调用方在 3.5.2 的循环里每次新建，见第 468 行），conduit 回环时直接返回 false。
- **conduit 的 Entry Rule 先行**（第 756~774 行）：conduit 状态有额外的进入条件；原生规则（`NativeTransitionDelegate.IsBound()`）直接 `Execute()` 拿布尔值，否则执行规则图。
- **去抖动与惰性求值**：`MinTimeBeforeReentry`（第 798 行）让“刚进入过的目标状态”在冷却期内不可再进；`bOnlyEvaluateWhenActive`（第 788 行）在状态机正在 blended out（`Context.IsActive()` 为假）时**整条规则跳过求值**——这两点在原文里都没有。
- **SyncGroup 前置校验**（第 807~811 行）：要求“同步组标记有效”的转换，若同步组无效则直接把结果节点布尔值置 false，连规则图都不跑。
- **自动剩余时间规则**（第 817~859 行）：`bAutomaticRemainingTimeRule` 为真时不用蓝图规则，而是按“目标资产剩余时间”触发，`CrossfadeTimeAdjustment = TransitionTriggerTime - AnimTimeRemaining`；若是走向 conduit，则强制把 crossfade 时长当 0，保证动画播完立刻转换。
- **真正的规则求值**（第 860~864 行）：`ResultNode->GetEvaluateGraphExposedInputs().Execute(Context)` —— 这就是“转换规则里调函数/读变量”的落点；结果写回 `bCanEnterTransition`，再与 `TransitionRule.bDesiredTransitionReturnValue` 比较（第 866 行，支持“取反”的转换）。
- **conduit 递归**（第 869~877 行）：目标状态是 conduit 时递归调用自己，把沿途的 `TransitionIndex` 收集进 `OutPotentialTransition.SourceTransitionIndices`；只有落到“内容状态”才填 `TransitionRule` / `TargetState` / `CrossfadeTimeAdjustment` 并返回 true。
- `GetEvaluateGraphExposedInputs()` 本身是 `FORCENOINLINE const FExposedValueHandler& FAnimNode_Base::GetEvaluateGraphExposedInputs() const`（`AnimNodeBase.cpp` 第 262 行）——它刻意不内联，因为这是每个节点更新路径上的固定开销点。

```cpp
{
	check(StateCachedPoses.Num() == StatePoseLinks.Num());

	FPoseContext* CachePosePtr = StateCachedPoses[StateIndex];
	if (CachePosePtr == nullptr)
	{
		CachePosePtr = new FPoseContext(Context);
		check(CachePosePtr);
		StateCachedPoses[StateIndex] = CachePosePtr;

		if (!IsAConduitState(StateIndex))
		{
			// Make sure CacheBones has been called before evaluating.
			ConditionallyCacheBonesForState(StateIndex, Context);

			StatePoseLinks[StateIndex].Evaluate(*CachePosePtr);
		}
	}

	return *CachePosePtr;
}
```

要点：

- `UpdateState` 有三重门禁：`StateIndex != INDEX_NONE`、`!StatesUpdated.Contains(StateIndex)`（**同一状态每帧只更新一次**，即使它同时出现在多条活动转换里）、`!IsAConduitState(...)`（conduit 不更新节点树）。
- `StatesUpdated.Add(StateIndex)` 就是上面那道去重的载体；`UE::Anim::FActiveStateMachineScope` 消息用于给通知打上“当前状态机/状态”元数据（`bCreateNotifyMetaData` 控制，见 3.5.1）。
- `EvaluateState` 用 `StateCachedPoses[StateIndex]` 做**每状态一份的姿势缓存**：同一状态在一帧内被多条转换求值时只算一次，正是 3.5.4 里 `EvaluateTransitionStandardBlend` 能安全复用 `PreviousStateResult` 的前提。

```cpp
			return;
		}
	}

		return;
	}

	ANIM_MT_SCOPE_CYCLE_COUNTER(EvaluateAnimStateMachine, !IsInGameThread());

	if (ActiveTransitionArray.Num() > 0)
	{
		check(Output.AnimInstanceProxy->GetSkeleton());

		check(StateCachedPoses.Num() == 0);
		StateCachedPoses.AddZeroed(StatePoseLinks.Num());

		//each transition stomps over the last because they will already include the output from the transition before it
		for (int32 Index = 0; Index < ActiveTransitionArray.Num(); ++Index)
		{
			// if there is any source pose, blend it here
			FAnimationActiveTransitionEntry& ActiveTransition = ActiveTransitionArray[Index];

			// when evaluating multiple transitions we need to store the pose from previous results
			// so we can feed the next transitions
			const bool bIntermediatePoseIsValid = Index > 0;

			if (ActiveTransition.bActive)
			{
				switch (ActiveTransition.LogicType)
				{
				case ETransitionLogicType::TLT_StandardBlend:

					break;
				case ETransitionLogicType::TLT_Inertialization:
					EvaluateState(ActiveTransition.NextState, Output);
					break;
				case ETransitionLogicType::TLT_Custom:
					EvaluateTransitionCustomBlend(Output, ActiveTransition, bIntermediatePoseIsValid);
					break;

					break;
```

- **前置防御**（第 956~983 行）：机器描述为空、状态数组为空、`CurrentState` 非法、或当前状态是 conduit 时，**输出复位为参考姿势**并返回；conduit 作为当前状态在编辑器下会直接报 `EMessageSeverity::Error`（"Current state is a conduit and will reset to ref pose."），非编辑器构建走 `ensureMsgf`。这是“状态机停在 conduit 上会看到 T-Pose”的源码依据。

- **无活动转换时**（第 1033~1040 行）：先 `ConditionallyCacheBonesForState(CurrentState, Output)`（按状态粒度检查骨骼缓存，LOD 切换相关），再 `StatePoseLinks[CurrentState].Evaluate(Output)` —— 状态内部的节点树由此进入求值。

要点：

- **`CrossfadeDuration` 的公式**（第 70 行）：`(LogicType == TLT_Inertialization) ? 0.0f : FMath::Max(ReferenceTransitionInfo.CrossfadeDuration - CrossfadeTimeAdjustment, 0.f) * CalculateInverseAlpha(BlendOption, Scaler)`。原文 FAQ Q5 只写了 `FMath::Max(...)`，漏了两件事：① 惯性化转换的时长恒为 0（它不用 crossfade，改由惯性化请求驱动）；② 还要乘一个“反解 alpha”的缩放 `CalculateInverseAlpha`（HermiteCubic 用三次多项式反解，其余用 `FMath::Clamp`，见第 78~96 行）；③ `Scaler = 1.0f - ExistingWeightOfNextState`，即目标状态已有权重时混合会缩短（注释原文 "may be shorter than the nominal duration specified by the state machine if the target state had non-zero weight at the start"）。

```cpp
struct FGraphTraversalCounter
{
private:
	// Number of the last external frame where we updated the counter (total global frame count)
	uint64 LastSyncronizedFrame;

	// Number of counter increments since last reset
	int16 Counter;

	// Number of external frames that URO is currently scheduled to skip
	int16 SkipFrames;

public:

	FGraphTraversalCounter()
		: LastSyncronizedFrame(INDEX_NONE)
		, Counter(INDEX_NONE)
		, SkipFrames(0)

	{}

	int16 Get() const
	{
		return Counter;
	}

	bool HasEverBeenUpdated() const
	{
		return (Counter != INDEX_NONE) && (LastSyncronizedFrame != INDEX_NONE);
	}

	/** Increases the internal counter, and refreshes the current global frame counter */
	void Increment()
	{
		Counter++;
		LastSyncronizedFrame = GFrameCounter;

		// Avoid wrapping over back to INDEX_NONE, as this means 'never been traversed'
		if (Counter == INDEX_NONE)
		{
			Counter++;
		}
	}

	/** Sets the number of expected frames to be skipped by URO */
	void SetMaxSkippedFrames(int16 InMaxSkippedFrames)
	{
		SkipFrames = InMaxSkippedFrames;
	}

	/** Gets the number of expected frames to be skipped by URO */
	int16 GetMaxSkippedFrames() const
	{
		return SkipFrames;
	}

	/** Clear the internal counters and frame skip */
	void Reset()
	{
		Counter = INDEX_NONE;
		LastSyncronizedFrame = INDEX_NONE;
		SkipFrames = 0;
	}
```

要点：

- 它不是一个简单的 `int`：除了 `Counter`，还带 `LastSyncronizedFrame`（最后一次递增时的 `GFrameCounter`）与 `SkipFrames`（URO 计划跳过的帧数）。
- **`Increment()` 会同步 `GFrameCounter`**（第 175~185 行），并特意避免把 `Counter` 回绕到 `INDEX_NONE`——因为 `INDEX_NONE` 的语义是“从未遍历过”（`HasEverBeenUpdated()` 第 169~172 行就是这么判的）。这与 3.2.4 里 `Proxy.ResetUpdateCounter()` 的分支相呼应。

```cpp
	{
		/**
			If we're set to OnlyTickMontagesWhenNotRendered and we haven't been recently rendered,
			then only update montages and skip everything else.
		*/

		{
			/**
				Clear NotifyQueue prior to ticking montages.
				This is typically done in 'PreUpdate', but we're skipping this here since we're not updating the graph.

			*/
```

## 六、常见问题 FAQ

### Q1：`NativeUpdateAnimation` 和 `BlueprintUpdateAnimation` 都写了，会执行两次吗？

会，而且这是**设计行为**。`UpdateAnimation` 里两个调用是并列的（`AnimInstance.cpp` 第 789~798 行，先 Native 后 Blueprint，各自带独立的 `SCOPE_CYCLE_COUNTER`）。C++ 侧重写在 `NativeUpdateAnimation`，蓝图侧重写在 `BlueprintUpdateAnimation`，互不覆盖。若只想跑一边，就在另一边留空（不要互相调用，避免重复计算）。

### Q2：为什么调试动画蓝图时角色动画会明显变慢/掉帧？

因为 `GIntraFrameDebuggingGameThread` 为真、或该 AnimBP 正被作为调试对象/设有断点时，`NeedsImmediateUpdate` 返回 true（`AnimInstance.cpp` 第 1028~1039 行），整个动画系统退回游戏线程同步求值，且 `FParallelAnimationEvaluationTask` 不再被投递（`RefreshBoneTransforms` 走 `DoParallelEvaluationTasks_OnGameThread()` 分支，第 2986~2993 行）。这是功能限制，不是性能回退 bug。

### Q3：工作线程上崩溃（崩溃栈里是 `ParallelEvaluateAnimation` / `Update_AnyThread`），最常见原因是什么？

自定义动画节点在工作线程访问了非线程安全数据：`GetWorld()`、修改 UPROPERTY、调用蓝图函数、读写全局状态。按 3.4 节协议处理：状态放节点结构体自身，游戏线程数据通过 `PreUpdate` 提前搬运（3.4.1），需要只读查询时用 Proxy 的 AnyThread 接口——例如 `FAnimInstanceProxy::GetInstanceAssetPlayers(const FName& GraphName) const`（`AnimInstanceProxy.h` 第 542 行，`UAnimInstance::GetInstanceAssetPlayers` 在 `AnimInstance.cpp` 第 4910~4912 行转发到 `GetProxyOnAnyThread<FAnimInstanceProxy>()`，是原文提到的 `GetInstanceAssetPlayers` 的真实落点）。

### Q4：`UpdateCounter` / `WasSynchronizedCounter` 是干什么的？

`FGraphTraversalCounter`（`AnimTypes.h` 第 143 行起，逐字块见 3.8）不是普通计数器，它带三个字段：`Counter`（本轮遍历计数）、`LastSyncronizedFrame`（最后一次递增时的 `GFrameCounter`）、`SkipFrames`（URO 计划跳过的帧数）。`HasEverBeenUpdated()` 用“两个字段都不是 `INDEX_NONE`”来判断“从未遍历过”。`WasSynchronizedCounter(other)`（第 234~247 行）比“相等”宽松：**它允许自己比主计数器落后一帧**（把自身递增一次再比较），因此 URO 跳帧后仍然算“同步过”而不触发重置。状态机用它实现 `bReinitializeOnBecomingRelevant`（3.5.2 的逐字块第 385 行），缓存姿势节点用它决定缓存是否有效。

### Q5：状态机里"瞬移式切换"（没有过渡混合）怎么做？

把转换的混合时长设为 0 即可。机制不是“跳过 `SetStateInternal`”：`TransitionToState` 末尾一定会 `SetState(Context, NextState, ...)`（`AnimNode_StateMachine.cpp` 第 1411 行），而混合时长在 `FAnimationActiveTransitionEntry` 的构造函数里算成 `FMath::Max(CrossfadeDuration - CrossfadeTimeAdjustment, 0.f) * CalculateInverseAlpha(BlendOption, Scaler)`（第 70 行，逐字块见 3.5.5）——`FMath::Max` 保证非负，0 时长意味着 `FAlphaBlend` 当帧即完成，`ActiveTransitionArray` 随即被清空（第 604~612 行）。注意**惯性化（`TLT_Inertialization`）的 crossfade 时长恒为 0**，那一条不是“瞬切”，而是由惯性化请求接管过渡。

### Q6：UE4 的 `FAnimNode_StateMachine::Update/Evaluate` 与 UE5 的 `Update_AnyThread/Evaluate_AnyThread` 有什么区别？

在 5.8 里 `FAnimNode_StateMachine` **只声明并实现了 `Initialize_AnyThread` / `CacheBones_AnyThread` / `Update_AnyThread` / `Evaluate_AnyThread`** 四个接口（`AnimNode_StateMachine.h` 第 245~248 行，无 `Update`/`Evaluate` 覆写）；基类 `FAnimNode_Base::Update_AnyThread` 的默认实现是**空函数**（`AnimNodeBase.cpp` 第 136~138 行，逐字块见 3.4），不再转发到 UE4 的 `Update`。所以自定义节点请直接重写 `*_AnyThread`。状态机相对 UE4 的运行时增强包括：`MaxTransitionsPerFrame`（默认 3）、`bSkipFirstUpdateTransition`、`QueuedTransitionEvents`（转换事件队列，3.5.1）、`bReinitializeOnBecomingRelevant`、`bAllowConduitEntryStates`。

### Q7：为什么 `BlueprintThreadSafeUpdateAnimation` 里不能访问我蓝图里的普通变量？

该事件对应 `NativeThreadSafeUpdateAnimation`，调用点在 **Proxy 的更新路径**里（`AnimInstanceProxy.cpp` 第 1349~1355 行，逐字块见 3.2.3），也就是并行求值任务的工作线程上。那里只能安全访问标记为“线程安全”的数据（Proxy 的读写缓冲、AnyThread 只读接口、节点自身状态）；普通蓝图变量属于 `UAnimInstance` 实例数据，工作线程读写会和游戏线程造成数据竞争——这正是 AnimInstance/Proxy 分离要解决的问题（3.1）。
