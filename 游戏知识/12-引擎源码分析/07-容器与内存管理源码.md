## 三、TArray：连续内存的动态数组

### 3.1 内存模型：FScriptArray

`TArray<ElementType>` 的无类型镜像**没有** `Data` 成员：元素指针由分配器实例（`FHeapAllocator::ForAnyElementType`）持有，`TScriptArray` 自身只用两个 `int32` 记录逻辑大小与容量，并通过 `protected` 继承分配器基类拿到分配指针。这一点直接决定了 `TArray` 对象本身的大小与 `TArray` 之间的移动语义（移动一个 `TArray` 就是移动分配器状态 + 两个整数）。

摘自 `Engine/Source/Runtime/Core/Public/Containers/ScriptArray.h`（第 19 行起；节选，省略第 22~227 行，共 206 行）：

```cpp
class TScriptArray
	: protected AllocatorType::ForAnyElementType
{
// …（节选：省略第 22~227 行，共 206 行）
protected:

	[[nodiscard]] TScriptArray( int32 InNum, int32 NumBytesPerElement, uint32 AlignmentOfElement )
		: ArrayNum( 0 )
		, ArrayMax( InNum )
	{
		if (ArrayMax)
		{
			ResizeInit(NumBytesPerElement, AlignmentOfElement);
		}
		ArrayNum = InNum;

		SlackTrackerNumChanged();
	}
	int32 ArrayNum;
	int32 ArrayMax;

	FORCENOINLINE void ResizeInit(int32 NumBytesPerElement, uint32 AlignmentOfElement)
	{
		ArrayMax = this->CalculateSlackReserve(ArrayMax, NumBytesPerElement, AlignmentOfElement);
		this->ResizeAllocation(ArrayNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
	}
	FORCENOINLINE void ResizeGrow(int32 OldNum, int32 NumBytesPerElement, uint32 AlignmentOfElement)
	{
		ArrayMax = this->CalculateSlackGrow(ArrayNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
		this->ResizeAllocation(OldNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
	}
	FORCENOINLINE void ResizeShrink(int32 NumBytesPerElement, uint32 AlignmentOfElement)
	{
		const int32 NewArrayMax = this->CalculateSlackShrink(ArrayNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
		if (NewArrayMax != ArrayMax)
		{
			ArrayMax = NewArrayMax;
			this->ResizeAllocation(ArrayNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
		}
	}
	FORCENOINLINE void ResizeTo(int32 NewMax, int32 NumBytesPerElement, uint32 AlignmentOfElement)
	{
		if (NewMax)
		{
			NewMax = this->CalculateSlackReserve(NewMax, NumBytesPerElement);
		}
		if (NewMax != ArrayMax)
		{
			ArrayMax = NewMax;
			this->ResizeAllocation(ArrayNum, ArrayMax, NumBytesPerElement, AlignmentOfElement);
		}
	}

```

```cpp
	friend class TIndirectArray;

	ElementAllocatorType AllocatorInstance;
	SizeType             ArrayNum;
	SizeType             ArrayMax;
```

三个字段是理解 TArray 一切行为的钥匙：

| 字段 | 含义 | 举例（TArray<float>，每元素 4 字节） |
| --- | --- | --- |
| 元素指针 | 由 `AllocatorInstance` 持有的堆内存基址（脚本镜像里是 `GetData()` 的返回值） | `0x000001F8A000` |
| `ArrayNum` | 有效元素数 | 5（逻辑上有 5 个 float） |
| `ArrayMax` | 容量 | 8（内存里能装 8 个，多出的 3 个是"余量"） |

`ArrayMax > ArrayNum` 的余量就是**扩容余量**：`Add` 元素时只要 `ArrayNum < ArrayMax`，直接写入内存 + `ArrayNum++`，**零分配**。只有 `ArrayNum == ArrayMax` 时才触发扩容（见 3.2）。`AddUninitialized()` 的注释把这个判断写成了"single cmp"，并把整个热路径用 `// Begin sensitive code!` 圈起来，摘自 `Engine/Source/Runtime/Core/Public/Containers/Array.h`（第 1903 行起；节选，省略第 1944~1945 行，共 2 行）：

### 3.2 扩容策略：CalculateSlackGrow 与 ReallocGrow（5.8）

容量耗尽时，`TArray` 先向分配器实例要新容量，再让分配器重新分配并搬移旧元素。单元素 `Add` 走 `ReallocGrow1_DoAlloc_Impl`（模板只按分配器实例实例化，不为每个元素类型复制一份代码）：

摘自 `Engine/Source/Runtime/Core/Public/Containers/Array.h`（第 504 行起）：

```cpp
	// Called only when we KNOW we are going to do a realloc increasing by 1.
	// In this case, we know that max == num and can simplify things in a very
	// hot location in the code.
	// This returns the old ArrayMax in order to save a register clobber/reload.
	template <uint32 Flags, typename AllocatorInstanceType>
	UE_FORCEINLINE_HINT TAllocatorSizeType_T<AllocatorInstanceType> ReallocGrow1_DoAlloc_Impl(
		uint32                                       ElementSize,
		uint32                                       ElementAlignment,
		AllocatorInstanceType&                       AllocatorInstance,
		TAllocatorSizeType_T<AllocatorInstanceType>& ArrayMax
	)
	{
		using SizeType  = TAllocatorSizeType_T<AllocatorInstanceType>;
		using USizeType = std::make_unsigned_t<SizeType>;

		const USizeType UOldMax = (USizeType)ArrayMax;
		const USizeType UNewNum = UOldMax + 1U;
		const SizeType  OldMax  = (SizeType)UOldMax;
		const SizeType  NewNum  = (SizeType)UNewNum;

		// This should only happen when we've underflowed or overflowed SizeType
		if (NewNum < OldMax)
		{
			OnInvalidArrayNum((unsigned long long)UNewNum);
		}

		SizeType NewMax;
		if constexpr (!!(Flags & 1)) // TAllocatorTraits<AllocatorType>::SupportsElementAlignment
		{
			NewMax = AllocatorInstance.CalculateSlackGrow(NewNum, OldMax, ElementSize, ElementAlignment);
			AllocatorInstance.ResizeAllocation(UOldMax, NewMax, ElementSize, ElementAlignment);
		}
		else
		{
			NewMax = AllocatorInstance.CalculateSlackGrow(NewNum, OldMax, ElementSize);
			AllocatorInstance.ResizeAllocation(UOldMax, NewMax, ElementSize);
		}
		ArrayMax = NewMax;
		#if UE_ENABLE_ARRAY_SLACK_TRACKING
		if constexpr (!!(Flags & 2)) // TAllocatorTraits<AllocatorType>::SupportsSlackTracking
		{
			AllocatorInstance.SlackTrackerLogNum(NewNum);
		}
		#endif

		return OldMax;
	}
```

增长公式的**真实数值**在分配器侧，与流传很广的"约 1.5 倍"不符：

摘自 `Engine/Source/Runtime/Core/Public/Containers/ContainerAllocationPolicies.h`（第 121 行起）：

```cpp
#ifndef UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR
	#if AGGRESSIVE_MEMORY_SAVING
		#define UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR 1
	#else
		#define UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR 3
	#endif
#endif

#ifndef UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR
	#if AGGRESSIVE_MEMORY_SAVING
		#define UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR 4
	#else
		#define UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR 8
	#endif
#endif
static_assert(UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR > 0, "UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR must be greater than 0");
static_assert(UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR > UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR, "UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR must be greater than UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR");
```

摘自 `Engine/Source/Runtime/Core/Public/Containers/ContainerAllocationPolicies.h`（第 169 行起）：

```cpp
template <typename SizeType>
UE_FORCEINLINE_HINT SizeType DefaultCalculateSlackGrow(SizeType NewMax, SizeType CurrentMax, SIZE_T BytesPerElement, bool bAllowQuantize, uint32 Alignment = DEFAULT_ALIGNMENT)
{
#if !defined(AGGRESSIVE_MEMORY_SAVING)
	#error "AGGRESSIVE_MEMORY_SAVING must be defined"
#endif
#if AGGRESSIVE_MEMORY_SAVING
	const SIZE_T FirstGrow = 1;
	const SIZE_T ConstantGrow = 0;
#else
	const SIZE_T FirstGrow = 4;
	const SIZE_T ConstantGrow = 16;
#endif

	SizeType Retval;
	checkSlow(NewMax > CurrentMax && NewMax > 0);

	SIZE_T Grow = FirstGrow; // this is the amount for the first alloc

#if CONTAINER_INITIAL_ALLOC_ZERO_SLACK
	if (CurrentMax)
	{
		// Allocate slack for the array proportional to its size.
		Grow = SIZE_T(NewMax) + UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR * SIZE_T(NewMax) / UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR + ConstantGrow;
	}
	else if (SIZE_T(NewMax) > Grow)
	{
		Grow = SIZE_T(NewMax);
	}
#else
	if (CurrentMax || SIZE_T(NewMax) > Grow)
	{
		// Allocate slack for the array proportional to its size.
		Grow = SIZE_T(NewMax) + UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR * SIZE_T(NewMax) / UE_CONTAINER_SLACK_GROWTH_FACTOR_DENOMINATOR + ConstantGrow;
	}
#endif

	if (bAllowQuantize)
	{
		Retval = (SizeType)(FMemory::QuantizeSize(Grow * BytesPerElement, Alignment) / BytesPerElement);
	}
	else
	{
		Retval = (SizeType)Grow;
	}
	// NumElements and MaxElements are stored in 32 bit signed integers so we must be careful not to overflow here.
	if (NewMax > Retval)
	{
		Retval = TNumericLimits<SizeType>::Max();
	}

	return Retval;
}
```

要点（数值均以上面两段为准）：

1. **增长比例是 3/8，不是 1/2**：默认 `UE_CONTAINER_SLACK_GROWTH_FACTOR_NUMERATOR/DENOMINATOR = 3/8`，公式为 `Grow = NewMax + 3*NewMax/8 + 16`，即约 **1.375 倍**（不是 1.5 倍）；`AGGRESSIVE_MEMORY_SAVING` 打开时变成 `1/4` 比例且 `ConstantGrow = 0`。**本文订正**：原文"约 1.5 倍增长"应改为"约 1.375 倍"。
2. **首次分配固定 4 个元素，不是 8 个**：`FirstGrow = 4`；再叠加默认开启的 `CONTAINER_INITIAL_ALLOC_ZERO_SLACK = 1`（第 109~111 行），`CurrentMax == 0` 时不按比例给 slack，`NewMax <= 4` 时容量就是 4。**本文订正**：原文"首次至少 8 个元素"应改为"首次固定 4 个元素"。
3. `bAllowQuantize` 为真时用 `FMemory::QuantizeSize(Grow * BytesPerElement, Alignment) / BytesPerElement` 把字节数对齐到分配器实际 bin 粒度再折回元素数——这才是"按分配器粒度取整"的真实位置，而不是在 `TArray` 里。
4. 溢出保护：若 `NewMax > Retval`，直接取 `TNumericLimits<SizeType>::Max()` 而不是环绕。
5. 显式 `Reserve(int32 Number)` 走 `CalculateSlackReserve`（即 `DefaultCalculateSlackReserve`），不套用 3/8 增长；见 3.7。
6. `Empty`/`Shrink` 才真正归还内存；`Reset` 只把 `ArrayNum` 归零、保留容量（`ArrayMax` 不变），用于复用内存。

### 3.3 元素构造/析构/移动

`RelocateConstructItems` **不在** `Array.h` 里，而在 `Templates/MemoryOps.h`。5.8 用 C++20 `requires` 约束把它拆成两个重载，判据是 `TCanBitwiseRelocate_V`（不是 `if constexpr`，也不是 `TIsTriviallyRelocatable`），非平凡分支是 `while` 循环 + 显式析构调用：

摘自 `Engine/Source/Runtime/Core/Public/Templates/MemoryOps.h`（第 191 行起）：

```cpp
/**
 * Relocates a range of items to a new memory location as a new type. This is a so-called 'destructive move' for which
 * there is no single operation in C++ but which can be implemented very efficiently in general.
 *
 * @param	Dest		The memory location to relocate to.
 * @param	Source		A pointer to the first item to relocate.
 * @param	Count		The number of elements to relocate.
 */
template <typename DestinationElementType, typename SourceElementType, typename SizeType>
	requires (sizeof(DestinationElementType) > 0 && sizeof(SourceElementType) > 0 && UE::Core::Private::MemoryOps::TCanBitwiseRelocate_V<DestinationElementType, SourceElementType>) // the sizeof here should improve the error messages we get when we try to call this function with incomplete types
FORCEINLINE void RelocateConstructItems(void* Dest, SourceElementType* Source, SizeType Count)
{
	static_assert(!std::is_const_v<SourceElementType>, "RelocateConstructItems: Source cannot be const");

	/* All existing UE containers seem to assume trivial relocatability (i.e. memcpy'able) of their members,
	 * so we're going to assume that this is safe here.  However, it's not generally possible to assume this
	 * in general as objects which contain pointers/references to themselves are not safe to be trivially
	 * relocated.
	 *
	 * However, it is not yet possible to automatically infer this at compile time, so we can't enable
	 * different (i.e. safer) implementations anyway. */

	FMemory::Memmove(Dest, Source, sizeof(SourceElementType) * Count);
}
template <typename DestinationElementType, typename SourceElementType, typename SizeType>
	requires (sizeof(DestinationElementType) > 0 && sizeof(SourceElementType) > 0 && !UE::Core::Private::MemoryOps::TCanBitwiseRelocate_V<DestinationElementType, SourceElementType>) // the sizeof here should improve the error messages we get when we try to call this function with incomplete types
FORCENOINLINE void RelocateConstructItems(void* Dest, SourceElementType* Source, SizeType Count)
{
	static_assert(!std::is_const_v<SourceElementType>, "RelocateConstructItems: Source cannot be const");

	while (Count)
	{
		// We need a typedef here because VC won't compile the destructor call below if SourceElementType itself has a member called SourceElementType
		typedef SourceElementType RelocateConstructItemsElementTypeTypedef;

		::new ((void*)Dest) DestinationElementType((SourceElementType&&)*Source);
		++(DestinationElementType*&)Dest;
		(Source++)->RelocateConstructItemsElementTypeTypedef::~RelocateConstructItemsElementTypeTypedef();
		--Count;
	}
}
```

约束分支让 **POD/可平凡重定位类型（int、float、FVector）的搬移退化为一次 `FMemory::Memmove`**，而带自管理内存的类型（TArray、FString）走 `::new (Dest) T((T&&)*Source)` + 显式析构。这就是为什么自定义结构体里放 `TArray`/`TSharedPtr` 可以安全放进 `TArray`——但前提是这些类型**可平凡重定位**：`TCompactSet` 的析构里就有一条 `UE_STATIC_ASSERT_WARN(TIsTriviallyRelocatable_V<InElementType>, "TMapBase can only be used with trivially relocatable types")`（`CompactSet.h.inl` 第 383 行，注意这句提示文案仍写着旧名 `TMapBase`）。含自引用指针/引用成员的类型不满足该前提，放进容器会静默出错，而不是编译报错。


### 3.4 迭代器失效规则

| 操作 | 迭代器/索引是否失效 | 原因 |
| --- | --- | --- |
| 遍历中只读 | 安全 | 无内存变动 |
| `Add`（未触发扩容） | 不失效 | 内存地址不变 |
| `Add`（触发扩容） | **全部失效** | `Data` 被 realloc，地址变了 |
| `RemoveAt` / `RemoveAtSwap` | 被删位置之后失效 | 元素搬移（RemoveAtSwap 只失效最后一个） |
| `Empty` / `Reset` | 全部失效 | 释放或逻辑清空 |
| `Shrink` | 全部失效 | 可能 realloc |

核心规则一句话：**任何可能导致 `Data` 重新分配或元素搬移的操作都会使既有指针/迭代器失效**。`RemoveAtSwap` 用"尾元素填坑"换取 O(1)，代价是**顺序不稳定**（UI 列表按索引取数据时慎用）。

### 3.7 Reserve 与收缩：ReallocTo、DefaultCalculateSlackReserve 与 DefaultCalculateSlackShrink

`Reserve(n)` 不走 3/8 增长，而是直接向分配器要"刚好 n 个元素并量化后的容量"：`ReallocTo` 先调 `CalculateSlackReserve`，若新容量与旧容量不同才 `ResizeAllocation`。

摘自 `Engine/Source/Runtime/Core/Public/Containers/Array.h`（第 671 行起）：

```cpp
	// This should be used for setting an allocation to a specific size.
	// Precondition: NewMax >= ArrayNum.
	template <uint32 Flags, typename AllocatorInstanceType>
	FORCENOINLINE void ReallocTo(
		uint32                                       ElementSize,
		uint32                                       ElementAlignment,
		TAllocatorSizeType_T<AllocatorInstanceType>  NewMax,
		AllocatorInstanceType&                       AllocatorInstance,
		TAllocatorSizeType_T<AllocatorInstanceType>  ArrayNum,
		TAllocatorSizeType_T<AllocatorInstanceType>& ArrayMax
	)
	{
		if constexpr (!!(Flags & 1)) // TAllocatorTraits<AllocatorType>::SupportsElementAlignment
		{
			if (NewMax)
			{
				NewMax = AllocatorInstance.CalculateSlackReserve(NewMax, ElementSize, ElementAlignment);
			}
			if (NewMax != ArrayMax)
			{
				ArrayMax = NewMax;
				AllocatorInstance.ResizeAllocation(ArrayNum, NewMax, ElementSize, ElementAlignment);
			}
		}
		else
		{
			if (NewMax)
			{
				NewMax = AllocatorInstance.CalculateSlackReserve(NewMax, ElementSize);
			}
			if (NewMax != ArrayMax)
			{
				ArrayMax = NewMax;
				AllocatorInstance.ResizeAllocation(ArrayNum, NewMax, ElementSize);
			}
		}
	}
```

被调用的 `CalculateSlackReserve` 本体（只做量化与溢出保护），摘自 `Engine/Source/Runtime/Core/Public/Containers/ContainerAllocationPolicies.h`（第 223 行起）：

```cpp
template <typename SizeType>
UE_FORCEINLINE_HINT SizeType DefaultCalculateSlackReserve(SizeType NewMax, SIZE_T BytesPerElement, bool bAllowQuantize, uint32 Alignment = DEFAULT_ALIGNMENT)
{
	SizeType Retval = NewMax;
	checkSlow(NewMax > 0);
	if (bAllowQuantize)
	{
		Retval = (SizeType)(FMemory::QuantizeSize(SIZE_T(Retval) * SIZE_T(BytesPerElement), Alignment) / BytesPerElement);
		// NumElements and MaxElements are stored in 32 bit signed integers so we must be careful not to overflow here.
		if (NewMax > Retval)
		{
			Retval = TNumericLimits<SizeType>::Max();
		}
	}

	return Retval;
}
```

收缩的门槛比直觉严格得多——只有"多余字节 ≥ 16384"或"3*NewMax < 2*CurrentMax"**并且**剩余空槽 > 64（或 NewMax 为 0）时才真收缩，否则容量原地不动。这正是"删了很多元素但内存没降"的源码级原因，摘自 `Engine/Source/Runtime/Core/Public/Containers/ContainerAllocationPolicies.h`（第 139 行起）：

```cpp
template <typename SizeType>
UE_FORCEINLINE_HINT SizeType DefaultCalculateSlackShrink(SizeType NewMax, SizeType CurrentMax, SIZE_T BytesPerElement, bool bAllowQuantize, uint32 Alignment = DEFAULT_ALIGNMENT)
{
	SizeType Retval;
	checkSlow(NewMax < CurrentMax);

	// If the container has too much slack, shrink it to exactly fit the number of elements.
	const SizeType CurrentSlackElements = CurrentMax - NewMax;
	const SIZE_T CurrentSlackBytes = (CurrentMax - NewMax)*BytesPerElement;
	const bool bTooManySlackBytes = CurrentSlackBytes >= 16384;
	const bool bTooManySlackElements = 3 * NewMax < 2 * CurrentMax;
	if ((bTooManySlackBytes || bTooManySlackElements) && (CurrentSlackElements > 64 || !NewMax)) //  hard coded 64 :-(
	{
		Retval = NewMax;
		if (Retval > 0)
		{
			if (bAllowQuantize)
			{
				Retval = (SizeType)(FMemory::QuantizeSize(Retval * BytesPerElement, Alignment) / BytesPerElement);
			}
		}
	}
	else
	{
		Retval = CurrentMax;
	}

	return Retval;
}
```

因此工程上的三条结论：① 循环 `Add` 前先 `Reserve`，此时的余量是"量化的精确值"，没有 3/8 的额外浪费；② 想真正还内存给分配器必须 `Empty()` 或 `Shrink()`，只 `Reset()` 只会让 `ArrayMax` 保持在扩容后的高位；③ 大数组缩容后如果没到上面两条阈值，`Shrink()` 也是空操作，这是设计如此而非 bug。

布局示意（以默认紧凑集为例，**作者示例（非引擎源码）**，依据上面两段源码的字段关系绘制）：

```text
Elements（一块连续分配，ElementAllocatorType）
+---------------------------+---------------------------+
| 元素 0 | 元素 1 | ... | 元素 N-1 |  HashCount  | 桶/NextIndices 区 |
+---------------------------+---------------------------+

                                      Elements.GetAllocation() + GetElementsSizeInBytes(MaxElements, Layout)
```

```text

+------+------+------+------+------+
|  0   |  1   |  2   |  3   | ...  |   每个桶存"元素在稀疏数组中的索引 + 1"
+------+------+------+------+------+

TSparseArray（元素区，连续但可能有空洞）
+-------+-------+-------+-------+
| elem3 | FREE  | elem1 | elem2 |    FREE 槽通过空闲链表复用
+-------+-------+-------+-------+
```

哈希冲突用**链式**解决：同桶元素通过"索引 + 1"串成链表，查找时沿链比对 `KeyFuncs::Matches`。`UE_ENABLE_COMPACTHASHTABLE_KEYSTORAGE` 打开时，紧凑集还会把 `GetHashKey(Item) % (HashSize - 1)` 一并存下来，从而在删除单个元素时**免去整表重哈希**（`CompactSet.h.inl` 第 65 行注释）。

真正的"算哈希 → 定位桶 → 沿冲突链比对"在 `TCompactSet::FindIndexByHash` 里，并且为了性能把整个循环展开成了按索引宽度分派的宏，摘自 `Engine/Source/Runtime/Core/Public/Containers/CompactSet.h.inl`（第 1535 行起）：

```cpp
	template<typename ComparableKey>
	[[nodiscard]] SizeType FindIndexByHash(uint32 KeyHash, const ComparableKey& Key) const
	{
		if (this->NumElements == 0)
		{
			return INDEX_NONE;
		}

		const ElementType* ElementData = GetData();
		const HashCountType* HashTable = this->GetHashTableMemory(GetSetLayout());
		const uint8* NextIndicesData = (const uint8*)(HashTable + 1);
		const uint32 HashCount = *HashTable;

		// Inlining this can save up to 40% perf compared to GetHashTableView().Find()
		#define UE_COMPACTHASHTABLE_EXECUTEBYTYPE(Type) \
				const Type* NextIndices = (const Type *)NextIndicesData; \
				const Type* HashIndices = NextIndices + this->MaxElements * this->KeyStorageMultiplier; \
				for (Type Index = HashIndices[KeyHash & (HashCount-1)]; Index != (Type)INDEX_NONE; Index = NextIndices[Index]) \
				{ \
					checkSlow((SizeType)Index < this->NumElements); \
						if (KeyFuncs::Matches(KeyFuncs::GetSetKey(ElementData[Index]), Key)) \
						{ \
							return Index; \
						} \
				}

		UE_COMPACTHASHTABLE_CALLBYTYPE(this->MaxElements)
		#undef UE_COMPACTHASHTABLE_EXECUTEBYTYPE

		return INDEX_NONE;
```

读懂这段要看三点：① 桶下标是 `KeyHash & (HashCount-1)`，即**桶数是 2 的幂**，用位与代替取模；② `HashIndices` 与 `NextIndices` 都从同一个 `NextIndicesData` 出发，前者整体偏移 `MaxElements * KeyStorageMultiplier`——这就是"哈希表尾随元素区"的具体地址算法；③ 相等判定是 `KeyFuncs::Matches(KeyFuncs::GetSetKey(ElementData[Index]), Key)`，对 `TMap` 就是 `TDefaultMapKeyFuncs::Matches`（只比 Key，不比 Value）。整体成本：哈希计算 O(1) + 链长（负载因子低时≈1）。

### 4.3 Emplace 流程

`TMap::Emplace` 在 5.8 里同样是薄封装——它把参数打成 `TPairInitializer` 交给 `Pairs.Emplace`，返回值按 `FSetElementId` 取回 `Value`：

摘自 `Engine/Source/Runtime/Core/Public/Containers/Map.h.inl`（第 356 行起）：

```cpp

	 * Sets the value associated with a key.
	 *
	 * @param InKey The key to associate the value with.
	 * @param InValue The value to associate with the key.
	 * @return A reference to the value as stored in the map. The reference is only valid until the next change to any key in the map.
	 */
	template <typename InitKeyType = KeyType, typename InitValueType = ValueType>
	ValueType& Emplace(InitKeyType&& InKey, InitValueType&& InValue)
	{
		const FSetElementId PairId = Pairs.Emplace(TPairInitializer<InitKeyType&&, InitValueType&&>(Forward<InitKeyType>(InKey), Forward<InitValueType>(InValue)));

		return Pairs[PairId].Value;
	}

	ValueType& EmplaceByHash(uint32 KeyHash, InitKeyType&& InKey, InitValueType&& InValue)
	{
		const FSetElementId PairId = Pairs.EmplaceByHash(KeyHash, TPairInitializer<InitKeyType&&, InitValueType&&>(Forward<InitKeyType>(InKey), Forward<InitValueType>(InValue)));

		return Pairs[PairId].Value;
	}
```

真正的四阶段（构造临时元素 → 算哈希 → 查重 → 落位或覆盖）在 `TCompactSet::Emplace(EInPlace, ...)` 里。注意它对"已存在"的处理**不是**原地更新值，而是把新元素 move-relocate 到已有元素上：

摘自 `Engine/Source/Runtime/Core/Public/Containers/CompactSet.h.inl`（第 746 行起）：

```cpp
    /**
     * Adds an element to the set by constructing the ElementType in-place with multiple args.
     *
     * @param   EInPlace   Tag to disambiguate in-place construction.
     * @param   InArgs     Arguments forwarded to ElementType's constructor.
     * @return  Pair of (element id, whether an equivalent element already existed).
     */
    template <typename... ArgTypes>
    TPair<FSetElementId, bool> Emplace(EInPlace, ArgTypes&&... InArgs)
    {
		alignas(alignof(ElementType))char StackElement[sizeof(ElementType)];
		ElementType& TempElement = *new (StackElement) ElementType(Forward<ArgTypes>(InArgs)...);
		SizeType ExistingIndex(INDEX_NONE);

		const KeyInitType Key = KeyFuncs::GetSetKey(TempElement);
		const uint32 KeyHash = KeyFuncs::GetKeyHash(Key);

		if constexpr (!KeyFuncs::bAllowDuplicateKeys)
		{
			ExistingIndex = FindIndexByHash(KeyHash, Key);
		}

		const bool bAlreadyInSet = ExistingIndex != INDEX_NONE;

		if (!bAlreadyInSet)
		{
			ExistingIndex = this->NumElements;
			ElementType& NewElement = AddUninitialized(KeyHash);
			RelocateConstructItem<ElementType, ElementType, SizeType>(&NewElement, &TempElement);
		}
		else
		{
			ElementType& ExistingElement = GetData()[ExistingIndex];
			MoveByRelocate(ExistingElement, TempElement);
		}

		return { FSetElementId::FromInteger(ExistingIndex), bAlreadyInSet };
	}
```

槽位分配与挂链合并成了一个函数：`AddUninitialized(KeyHash)` 先按需 `Reserve`，再把 `(NumElements, KeyHash)` 直接插进哈希视图，最后返回**未初始化**的槽位引用，由调用方 placement-new：

摘自 `Engine/Source/Runtime/Core/Public/Containers/CompactSet.h.inl`（第 1519 行起）：

```cpp
	[[nodiscard]] ElementType& AddUninitialized(uint32 KeyHash)
	{
		checkSlow(this->MaxElements >= 0);
		if (this->NumElements == this->MaxElements)
		{
			Reserve(this->AllocatorCalculateSlackGrow(this->NumElements + 1, GetSetLayout()));
		}
		GetHashTableView().Add(this->NumElements, KeyHash);
		return GetData()[this->NumElements++];
	}
```

四个阶段对应四类开销：构造临时元素（在**栈上**构造，见 `alignas(alignof(ElementType)) char StackElement[sizeof(ElementType)]`）→ 哈希（O(1)）→ 查找（O(链长)）→ 扩容（`AllocatorCalculateSlackGrow` + 重新分配 + 重哈希，偶发 O(n)）。所以 TMap 的 Emplace 最坏情况不是 O(1)；高频插入时**先 `Reserve` 预估容量**能显著减少重分配与重哈希。另外提醒一点 5.8 特有的行为：`Emplace` 里即便元素已存在，也先在栈上构造了一个 `TempElement`（`MoveByRelocate` 之后随即析构），所以"重复 Emplace 同一 Key"并非零代价。

### 4.4 GetTypeHash 与 KeyFuncs

`Emplace`/`Find` 全链路上没有任何"比较 Value"的动作，键的相等与哈希完全由 `KeyFuncs` 决定。默认键函数分两层：`TDefaultMapKeyFuncs` 提供 `GetSetKey`/`Matches`/`GetKeyHash`，`TDefaultMapHashableKeyFuncs` 只加一条编译期可用性检查（键类型必须有 `GetTypeHash` 重载）。

摘自 `Engine/Source/Runtime/Core/Public/Containers/Map.h`（第 76 行起）：

```cpp
/** Defines how the map's pairs are hashed. */
template<typename KeyType, typename ValueType, bool bInAllowDuplicateKeys>
struct TDefaultMapKeyFuncs : BaseKeyFuncs<TPair<KeyType, ValueType>, KeyType, bInAllowDuplicateKeys>
{
	typedef typename TTypeTraits<KeyType>::ConstPointerType KeyInitType;
	typedef const TPairInitializer<typename TTypeTraits<KeyType>::ConstInitType, typename TTypeTraits<ValueType>::ConstInitType>& ElementInitType;

	[[nodiscard]] static UE_FORCEINLINE_HINT KeyInitType GetSetKey(ElementInitType Element)
	{
		return Element.Key;
	}

	[[nodiscard]] static UE_FORCEINLINE_HINT bool Matches(KeyInitType A, KeyInitType B)
	{
		return A == B;
	}

	template<typename ComparableKey>
	[[nodiscard]] static UE_FORCEINLINE_HINT bool Matches(KeyInitType A, ComparableKey B)
	{
		return A == B;
	}

	[[nodiscard]] static UE_FORCEINLINE_HINT uint32 GetKeyHash(KeyInitType Key)
	{
		return GetTypeHash(Key);
	}

	template<typename ComparableKey>
	[[nodiscard]] static UE_FORCEINLINE_HINT uint32 GetKeyHash(ComparableKey Key)
	{
		return GetTypeHash(Key);
	}
};

template<typename KeyType, typename ValueType, bool bInAllowDuplicateKeys>
struct TDefaultMapHashableKeyFuncs : TDefaultMapKeyFuncs<KeyType, ValueType, bInAllowDuplicateKeys>
{
	// Check that the key type is actually hashable
	//
	// If this line fails to compile then your key doesn't have
	// a GetTypeHash() overload.
	using HashabilityCheck = decltype(GetTypeHash(DeclVal<const KeyType>()));
};
```

注意 `Matches` 有**两个**重载：一个比 `KeyInitType`，一个模板化的 `ComparableKey`——后者是 ByHash 系列 API（如 `FindByHash(KeyHash, FName)` 用 `FString` 查 `FName` 键）能工作的原因。作者自写的哈希特化示例（**作者示例（非引擎源码）**）：

```cpp
// 自定义类型的哈希函数：特化全局 GetTypeHash 即可被 TMap/TSet 使用
uint32 GetTypeHash(const FMyId& Id)
{
	return HashCombine(GetTypeHash(Id.Primary), GetTypeHash(Id.Secondary));
}
```

注意事项：① `GetTypeHash` 必须与 `==` 一致（相等对象哈希必同）；② **可变键陷阱**——已插入 TMap 的键若被修改到哈希变化，将永远找不到（`Find` 按新哈希定位不到旧链），引擎的 `FGameplayTag`/`FName` 等键类型都是不可变的，自定义可变结构体做键时要特别小心；③ 桶数是 2 的幂，用 `KeyHash & (HashCount-1)` 定位；④ `GetKeyHash` 只是转发到 `GetTypeHash`，所以 `TMap`/`TSet` 的"哈希质量"完全等于你为键类型写的那个函数的质量。

### 4.5 ByHash 系列：把哈希算一次用两次

`TMap` 为每个操作都提供了 `ByHash` 变体（`FindByHash`/`EmplaceByHash`/`AddByHash`/`FindOrAddByHash`/`RemoveByHash` 等），语义是"哈希已经由调用方算好，引擎不再重复调用 `GetTypeHash`"。这在两个场景下是实打实的优化：

1. `Find` 后紧接 `Emplace`：同一 Key 会算两次哈希。改成先 `KeyHash = GetTypeHash(Key)`，再 `FindByHash` / `EmplaceByHash`。
2. `GetTypeHash` 本身昂贵（如自定义结构体里 `HashCombine` 了多个 `FString`）：调用方可以自己缓存哈希。

绑定实现上，`FindByHash` 只是把哈希透传给 `Pairs.FindByHash`，摘自 `Engine/Source/Runtime/Core/Public/Containers/Map.h.inl`（第 503 行起）：

```cpp

		}
```

`FindOrAddImpl` 是 `FindByHash` 的复用者，它的两条分支正好对应 4.3 的"查重 + 落位"，摘自 `Engine/Source/Runtime/Core/Public/Containers/Map.h.inl`（第 565 行起）：

```cpp
	[[nodiscard]] ValueType& FindOrAddImpl(uint32 KeyHash, InitKeyType&& Key)
	{
		if (auto* Pair = Pairs.FindByHash(KeyHash, Key))
		{
			return Pair->Value;
		}

		return AddByHash(KeyHash, Forward<InitKeyType>(Key));
	}
```

**常见误解**：`FindOrAdd(Key)` 不是"先 Find 再 Add 的语法糖"——它**总会**执行一次哈希 + 一次查找（`FindOrAddImpl` 第一行就是 `FindByHash`），命中时只省下一次元素构造。所以把 `FindOrAdd` 用在高频热路径上，并不会比显式 `Find` + 条件 `Add` 便宜。

### 5.2 TSparseArray：空洞与空闲链表

稀疏数组的关键设计是"**元素与空闲链表节点共用同一块内存**"：`TSparseArrayElementOrFreeListLink` 是一个 `union`，元素活着时是元素本身，死了就变成前后空闲索引。这既是它省内存的原因，也是它**不能放非平凡类型**的根本约束。

摘自 `Engine/Source/Runtime/Core/Public/Containers/SparseArray.h`（第 44 行起）：

```cpp

		/** If the element isn't allocated, this is a link to the next element in the array's free list. */
		int32 NextFreeIndex;
	};
};
```

`AddUninitialized()` 的真实实现是"有空闲槽就复用链表头，否则追加"，并对 `FirstFreeIndex` 做双向前后维护，摘自 `Engine/Source/Runtime/Core/Public/Containers/SparseArray.h`（第 113 行起）：

```cpp
	/**
	 * Allocates space for an element in the array.  The element is not initialized, and you must use the corresponding placement new operator
	 * to construct the element in the allocated memory.
	 */
	FSparseArrayAllocationInfo AddUninitialized()
	{
		int32 Index;
		if(NumFreeIndices)
		{
			FElementOrFreeListLink* DataPtr = (FElementOrFreeListLink*)Data.GetData();

			// Remove and use the first index from the list of free elements.
			Index = FirstFreeIndex;
			FirstFreeIndex = DataPtr[FirstFreeIndex].NextFreeIndex;
			--NumFreeIndices;
			if(NumFreeIndices)
			{
				DataPtr[FirstFreeIndex].PrevFreeIndex = -1;
			}
		}
		else
		{
			// Add a new element.
			Index = Data.AddUninitialized(1);
			AllocationFlags.Add(false);
		}

		return AllocateIndex(Index);
	}
```

与笔记里常见的"`FreeList` 单链表头"模型不同，5.8 的实际结构是**双向空闲链表**：`FirstFreeIndex` 指向链表头，每个空闲槽里存 `PrevFreeIndex`/`NextFreeIndex`，并额外维护 `NumFreeIndices` 计数（通用版 `TSparseArrayBase` 见 `Public/Containers/SparseArray.h` 第 499~510 行，脚本镜像版 `TScriptSparseArray` 见第 1631~1632 行）。这就解释了为什么 `AddUninitialized()` 在复用分支里要写 `DataPtr[FirstFreeIndex].PrevFreeIndex = -1;`——头节点没有前驱。

稀疏数组的精髓：**删除 O(1) 且不搬移其他元素**（只把槽挂回空闲链表），代价是遍历要跳过空洞、内存可能有碎片。这正是多播委托（见《06-委托与事件系统源码》）和 `TSparseSet`/`TSparseMap` 选择它的原因——**索引/句柄稳定性优先**。但要记住：5.8 的默认 `TSet`/`TMap` 已经是紧凑集，**不再有这个空闲链表**，删除单个元素改成"尾元素填坑 + 重哈希"，见 5.3。

### 5.3 紧凑集的删除：尾元素填坑而非空闲链表

默认 `TSet`/`TMap` 的 `Remove` 不维护空闲链表。`TScriptCompactSet::RemoveAt` 的做法是：把最后一个元素 `memmove` 到被删位置，从哈希视图里摘掉两条索引链，再让 `NumElements` 减一。这就是"紧凑"的含义——元素区永远没有空洞。

摘自 `Engine/Source/Runtime/Core/Public/Containers/ScriptCompactSet.h`（第 82 行起）：

```cpp
	void RemoveAt(int32 Index, const FScriptCompactSetLayout& Layout, TFunctionRef<uint32 (const void*)> GetKeyHash, TFunctionRef<void (void*)> DestructItem)
	{
		check(IsValidIndex(Index));

		FCompactHashTableView HashTable = this->GetHashTableView(Layout);

		void* Dst = GetData(Index, Layout);
#if UE_ENABLE_COMPACTHASHTABLE_KEYSTORAGE
		const uint32 DstKeyHash = HashTable.GetStoredKey(Index, this->NumElements);
#else
		const uint32 DstKeyHash = GetKeyHash(Dst);
#endif

		const int32 LastElementIndex = this->NumElements - 1;
		if (Index == LastElementIndex)
		{
			HashTable.Remove(Index, DstKeyHash, Index, 0);
			DestructItem(Dst);
		}
		else
		{
			void* Src = GetData(LastElementIndex, Layout);
#if UE_ENABLE_COMPACTHASHTABLE_KEYSTORAGE
			const uint32 SrcKeyHash = HashTable.GetStoredKey(LastElementIndex, this->NumElements);
#else
			const uint32 SrcKeyHash = GetKeyHash(Src);
#endif
			HashTable.Remove(Index, DstKeyHash, LastElementIndex, SrcKeyHash);
			DestructItem(Dst);

			// Memmove is fine here as our containers already only work if data is trivially relocatable
			FMemory::Memmove(Dst, Src, Layout.Size);
		}

		--this->NumElements;
	}
```

与 `TSparseArray` 对照，两者满足完全不同的需求（**作者示例（非引擎源码）**结论归纳，依据为上面两段源码）：

| 维度 | 稀疏集 `TSparseSet` / `TSparseArray` | 紧凑集 `TSet`（5.8 默认）/ `TMap` |
| --- | --- | --- |
| 元素区空洞 | 有（空闲链表复用） | 无（尾元素填坑） |
| 单元素删除 | O(1)，**不搬移任何其他元素** | O(1)，搬移 1 个元素（`FMemory::Memmove` 一次） |
| 元素索引稳定性 | 稳定（`FSetElementId` 长期有效） | **不稳定**（删除会改变最后一个元素的索引） |
| 迭代顺序 | 稀疏数组物理顺序（插入序，删除后不保证） | 紧凑顺序（删除后最后一个元素会"跳位"） |
| 哈希表位置 | 独立的一块 `Hash` 分配 | 与元素区**同一块分配**（见 4.1） |

因此工程上有一条容易踩的坑：**不要把 5.8 默认 `TSet`/`TMap` 的 `FSetElementId` 当长期句柄用**——只要中间发生过 `Remove`，之前拿到的 Id 就可能指向别的元素。需要"索引稳定"的语义，请显式改用 `TSparseSet`/`TSparseMap`，或干脆用 `TMap<Key, Value>` 按 Key 索引。


## 六、TSharedPtr：引用计数智能指针

### 6.1 FSharedReferencer 与共享状态

`TSharedPtr<ObjectType, ESPMode>` 的核心是"引用计数块 + 两个引用者"。5.8 里**没有** `FSharedPtrState`：状态块的基类就是 `TReferenceControllerBase<Mode>`，两个计数以花括号直接初始化，`Mode` 决定计数类型是 `std::atomic<int32>` 还是普通 `int32`。

摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointerInternals.h`（第 46 行起）：

```cpp
	template <ESPMode Mode>
	class TReferenceControllerBase
	{
		using RefCountType = std::conditional_t<Mode == ESPMode::ThreadSafe, std::atomic<int32>, int32>;

	public:
		UE_FORCEINLINE_HINT explicit TReferenceControllerBase() = default;

		// Number of shared references to this object.  When this count reaches zero, the associated object
		// will be destroyed (even if there are still weak references!), but not the reference controller.
		//
		// This starts at 1 because we create reference controllers via the construction of a TSharedPtr,
		// and that is the first reference.  There is no point in starting at 0 and then incrementing it.
		RefCountType SharedReferenceCount{1};

		// Number of weak references to this object.  If there are any shared references, that counts as one
		// weak reference too.  When this count reaches zero, the reference controller will be deleted.
		//
		// This starts at 1 because it represents the shared reference that we are also initializing
		// SharedReferenceCount with.
		RefCountType WeakReferenceCount{1};

		/** Destroys the object associated with this reference counter.  */
		virtual void DestroyObject() = 0;

		virtual ~TReferenceControllerBase() = default;
```

"强引用归零销毁对象、弱引用归零销毁控制块"这条链路的真实代码（ThreadSafe 分支用 `fetch_sub(1, std::memory_order_acq_rel)`，非 ThreadSafe 分支就是 `--`）：

摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointerInternals.h`（第 213 行起）：

```cpp
		inline void ReleaseSharedReference()
		{
			if constexpr (Mode == ESPMode::ThreadSafe)
			{
				UE_AUTORTFM_ONCOMMIT(this)
				{
					// std::memory_order_acq_rel is used here so that, if we do end up executing the destructor, it's not possible
					// for side effects from executing the destructor end up being visible before we've determined that the shared
					// reference count is actually zero.

					int32 OldSharedCount = SharedReferenceCount.fetch_sub(1, std::memory_order_acq_rel);
					checkSlow(OldSharedCount > 0);
					if (OldSharedCount == 1)
					{
						// Last shared reference was released!  Destroy the referenced object.
						DestroyObject();

						// No more shared referencers, so decrement the weak reference count by one.  When the weak
						// reference count reaches zero, this object will be deleted.
						ReleaseWeakReference();
					}
				};
			}
			else
			{
				checkSlow( SharedReferenceCount > 0 );

				if( --SharedReferenceCount == 0 )
				{
					// Last shared reference was released!  Destroy the referenced object.
					DestroyObject();

					// No more shared referencers, so decrement the weak reference count by one.  When the weak
					// reference count reaches zero, this object will be deleted.
					ReleaseWeakReference();
				}
			}
		}
```

`FSharedReferencer` 本身只是控制块指针的 RAII 外壳：拷贝构造加一次引用，移动构造**不动计数只是搬指针**，析构统一走 `ReleaseSharedReferenceNoInline`（函数体只有一句 null 检查 + `ReleaseSharedReference()`，为了代码体积刻意不内联）：

摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointerInternals.h`（第 534 行起；节选，省略第 560~610 行，共 51 行）：

```cpp
	template< ESPMode Mode >
	class FSharedReferencer
	{
	public:

		/** Constructor for an empty shared referencer object */
		UE_FORCEINLINE_HINT FSharedReferencer()
			: ReferenceController( nullptr )
		{ }

		/** Constructor that references the specified controller, without incrementing the shared count */
		inline explicit FSharedReferencer( TReferenceControllerBase<Mode>* InReferenceController )
			: ReferenceController( InReferenceController )
		{ }

		/** Copy constructor creates a new reference to the existing object */
		inline FSharedReferencer( FSharedReferencer const& InSharedReference )
			: ReferenceController( InSharedReference.ReferenceController )
		{
			// If the incoming reference had an object associated with it, then go ahead and increment the
			// shared reference count

			{
				ReferenceController->AddSharedReference();
			}
		}
// …（节选：省略第 560~610 行，共 51 行）
```

引用计数模型：

```text
                    TReferenceControllerBase（堆上共享块）
   TSharedPtr A  ──►  ┌────────────────────────┐
   TSharedPtr B  ──►  │ SharedReferenceCount = 2 │
   TWeakPtr   C  ──►  │ WeakReferenceCount   = 3 │
                       │ DestroyObject()（虚函数）│──► 真实对象
                       └────────────────────────┘
```

注意上图里 `WeakReferenceCount` 不是 1：源码注释写明"如果有任何强引用，它也算作一个弱引用"，且计数**从 1 开始**（第 61~66 行）。所以有 2 个 `TSharedPtr` + 1 个 `TWeakPtr` 时是 `Shared=2, Weak=3`；强引用全部释放后 `Weak` 落到 2，`TWeakPtr` 再释放才落到 1，控制块本身在**最后一次 `ReleaseWeakReference`** 时析构。关键语义：**SharedReferenceCount 归零 → `DestroyObject()` 销毁真实对象；WeakReferenceCount 归零 → 共享状态块本身析构**。所以 `TWeakPtr` 能检测对象是否存活，但不阻止对象销毁。

### 6.2 线程安全：ESPMode

`ESPMode` 定义在 `SharedPointerFwd.h`（不是 `SharedPointer.h`），且**默认值是 `ThreadSafe`**——这跟 `std::shared_ptr` 的直觉一致，但跟"UE 默认追求性能所以默认非线程安全"的常见印象相反。

摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointerFwd.h`（第 11 行起）：

```cpp
enum class ESPMode : uint8
{
	/** Forced to be not thread-safe. */
	NotThreadSafe = 0,

	/** Thread-safe, never spin locks, but slower */
	ThreadSafe = 1
};

// IWYU pragma: begin_exports

// Forward declarations.  By default, thread safety features are turned on. (Mode = ESPMode::ThreadSafe).
// If you are more concerned with performance of ref-counting, you should use ESPMode::NotThreadSafe.
template< class ObjectType, ESPMode Mode = ESPMode::ThreadSafe > class TSharedRef;
template< class ObjectType, ESPMode Mode = ESPMode::ThreadSafe > class TSharedPtr;
template< class ObjectType, ESPMode Mode = ESPMode::ThreadSafe > class TWeakPtr;
template< class ObjectType, ESPMode Mode = ESPMode::ThreadSafe > class TSharedFromThis;
```

注意两点：① `ESPMode::ThreadSafe` 只保证**引用计数本身**的原子性，**不保证对象成员访问的线程安全**；② `TSharedRef`（强引用、非空承诺）与 `TSharedPtr` 共享同一计数，`TSharedRef` 可安全转换为 `TSharedPtr`，反之必须显式 `ToSharedRef()`。要拿性能就显式写 `TSharedPtr<T, ESPMode::NotThreadSafe>`。

### 6.3 TWeakPtr 与 TWeakObjectPtr

`TWeakPtr::Pin()` 在 5.8 里**不是** `if (IsValid()) return TSharedPtr(...) else nullptr`——它就直接构造一个 `TSharedPtr`，把"对象是否还活着"这件事完全交给 `TReferenceControllerBase::ConditionallyAddSharedReference()`（第 145 行起）内部的 CAS 循环来判断。两个重载分别对应 `const&`（拷贝一个弱引用）与 `&&`（移动弱引用）。

摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointer.h`（第 1565 行起）：

```cpp
	[[nodiscard]] UE_REWRITE TSharedPtr< ObjectType, Mode > Pin() const&
	{
		return TSharedPtr< ObjectType, Mode >( *this );
	}

	/**
	 * Converts this weak pointer to a shared pointer that you can use to access the object (if it
	 * hasn't expired yet.)  Remember, if there are no more shared references to the object, the
	 * returned shared pointer will not be valid.  You should always check to make sure the returned
	 * pointer is valid before trying to dereference the shared pointer!
	 *
	 * @return  Shared pointer for this object (will only be valid if still referenced!)
	 */
	[[nodiscard]] UE_REWRITE TSharedPtr< ObjectType, Mode > Pin() &&
	{
		return TSharedPtr< ObjectType, Mode >( MoveTemp( *this ) );
	}

	/**
	 * Checks to see if this weak pointer actually has a valid reference to an object
	 *
	 * @return  True if the weak pointer is valid and a pin operator would have succeeded
	 */
	[[nodiscard]] UE_NODEBUG inline bool IsValid() const
	{
		return Object != nullptr && WeakReferenceCount.IsValid();
	}
```

成员是"弱引用者 + 裸对象指针"两个字段，`IsValid()` 的判据是 `Object != nullptr && WeakReferenceCount.IsValid()`——**先看裸指针，再看控制块**。这意味着 `TWeakPtr` 的 `IsValid()` 本身不保证线程安全地"锁定"对象，真正安全的使用方式是 `Pin()` 拿到强引用后再用：

```cpp
// 作者示例（非引擎源码）
if (TSharedPtr<FMyNode> Pinned = WeakNode.Pin())   // 从这一刻起对象保证不被销毁
{
    Pinned->DoWork();
}
```

| 智能指针 | 引用性质 | 典型用途 |
| --- | --- | --- |
| `TSharedPtr` / `TSharedRef` | 强引用（计数持有） | 管理器、资源句柄、非 UObject 系统对象 |
| `TWeakPtr` | 弱引用（不阻止销毁） | 缓存、观察者，防止环引用 |
| `TWeakObjectPtr` | UObject 弱引用（GC 感知） | 引用 UObject 但不阻止 GC |

`TWeakObjectPtr` 与 `TWeakPtr` 是**两套机制**：前者走 UObject 的 GC 跟踪（对象由 GC 决定生死，没有引用计数），后者走引用计数。选错会导致"对象永远不释放"（TSharedPtr 环）或"对象被 GC 后崩溃"（裸 UObject* 存成员）。

### 6.4 TSharedRef 与 MakeShared：控制块与对象同块分配

`MakeShared<T>(Args...)` 与 `MakeShareable(new T(...))` 的差别不只是写法：前者走 `TIntrusiveReferenceController`，它把对象**直接构造在控制块内部**的 `TTypeCompatibleBytes<ObjectType> ObjectStorage` 里，因此只有**一次**分配；后者需要 `new T` 一次、控制块再一次。

控制块的构造工厂（对象与引用计数同块，`new` 只发生一次），摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointerInternals.h`（第 473 行起）：

`MakeShared` 的返回类型是 `TSharedRef` 而不是 `TSharedPtr`，摘自 `Engine/Source/Runtime/Core/Public/Templates/SharedPointer.h`（第 2110 行起）：

```cpp
{
	SharedPointerInternals::TIntrusiveReferenceController<InObjectType, InMode>* Controller = SharedPointerInternals::NewIntrusiveReferenceController<InMode, InObjectType>(Forward<InArgTypes>(Args)...);
```

三点工程含义：① `MakeShared` 要求目标类型的构造函数对 `TIntrusiveReferenceController` 可达（构造函数至少不能是 `private` 且未授权），源码注释给出的正解是"公开一个 `FPrivateToken` 结构体做参数"（第 409~424 行）；② `MakeShared` 不能配合自定义 deleter，需要自定义 deleter 只能用 `MakeShareable`/`TSharedPtr<T>(new T, Deleter)`；③ 因为对象在控制块里，`TSharedPtr::Get()` 返回的指针指向控制块内部，`MakeShared` 出来的对象**不能**再交给 `delete`，也不能 `MakeShareable` 同一地址两次。

```cpp
FORCEINLINE void* FMemory_MallocInline(SIZE_T Count, uint32 Alignment)
{
	// AutoRTFM: For non-transactional code, all of these calls optimize away and the
	// behavior is the same as it always has been.
	// For transactional code, we call the allocator in the 'open' as an optimization, so that
	// we don't end up keeping track of the writes to the allocator's internal data structures.
	// This is because allocators are already transactional - malloc can be rolled back by
	// calling free.
	void* Ptr = nullptr;

	UE_AUTORTFM_OPEN_NO_VALIDATION
	{
		if (UNLIKELY(!FMEMORY_INLINE_GMalloc))
		{
			Ptr = FMemory::MallocExternal(Count, Alignment);
		}
		else
		{
			DoGamethreadHook(0);
			FScopedMallocTimer Timer(0);
			Ptr = FMEMORY_INLINE_GMalloc->Malloc(Count, Alignment);
		}
		// optional tracking of every allocation
		LLM_IF_ENABLED(FLowLevelMemTracker::Get().OnLowLevelAlloc(ELLMTracker::Default, Ptr, Count, ELLMTag::Untagged, ELLMAllocType::FMalloc));
	};

	// AutoRTFM: This is a no-op for non-transactional code.
	// For transactional code, this defers a call to Free if the transaction aborts,
	// so that rolling back this allocation will end up freeing the memory.
	UE_AUTORTFM_ONABORT(Ptr)
	{
		// Disable the code analysis warning that complains that Free is being passed
		// a pointer that may be null. Free explicitly handles this case already.
		FMemory::Free(Ptr); //-V575
```

### 7.2 FMallocBinned 家族：分桶分配器

分桶的核心思想：**把不同大小范围的请求分到固定大小的桶，桶内用空闲链表复用，减少系统调用与碎片**。5.8 的常量全部改成 `UE_MB2_*` / `UE_MB3_*` / `UE_MBC_*` 前缀，`BINNED2_MINIMUM_ALIGNMENT` 已不存在。

摘自 `Engine/Source/Runtime/Core/Public/HAL/MallocBinned2.h`（第 21 行起）：

摘自 `Engine/Source/Runtime/Core/Public/HAL/MallocBinned3.h`（第 40 行起；节选，省略第 41~42 行，共 2 行）：

`UE_MB2_LARGE_ALLOC = 65536` 的注释写的是"OS 分配指针的对齐"——它不是"大于 64KB 就走大块路径"的阈值（那个阈值是 `UE_MB2_MAX_SMALL_POOL_SIZE`，非节省内存配置下为 `32768-16`），而是一个**对齐量**。这是最容易误读的一个常量。

Binned2 的真实分配入口，三条路径全部可见：小请求 → `MallocExternalSmall`；对齐过大但可提升到更大桶 → 仍走小池；否则 → `MallocExternalLarge`。

摘自 `Engine/Source/Runtime/Core/Private/HAL/MallocBinned2.cpp`（第 565 行起）：

```cpp
FORCEINLINE static bool UseSmallAlloc(SIZE_T Size, uint32 Alignment)
{
	return ((Size <= UE_MB2_MAX_SMALL_POOL_SIZE) & (Alignment <= UE_MBC_STANDARD_ALIGNMENT)); // one branch, not two
}

void* FMallocBinned2::Malloc(SIZE_T Size, uint32 Alignment)
{
	// Only allocate from the small pools if the size is small enough and the alignment isn't crazy large.
	// With large alignments, we'll waste a lot of memory allocating an entire page, but such alignments are highly unlikely in practice.
	bool bUseSmallPool = UseSmallAlloc(Size, Alignment);
	if (!bUseSmallPool)
	{
		bUseSmallPool = PromoteToLargerBin(Size, Alignment, *this);
	}

	if (bUseSmallPool)
	{
		return MallocExternalSmall(Size, Alignment);
	}
	return MallocExternalLarge(Size, Alignment);
}
```

小池路径的线程本地缓存（`GMallocBinnedPerThreadCaches`）是"无锁快路径"的所在地：先 `ObtainRecycledPartial` 取下全局回收队列的部分空桶，再 `Lists->Malloc(PoolIndex)` 从线程本地空闲链表摘块；只有都失败才落到 `FPoolTable& Table = SmallPoolTables[PoolIndex]` 加锁分配。

Binned3 的入口结构相同，但小池上限与对齐策略不同（`UE_MB3_MAX_SMALL_POOL_SIZE`；默认 128KB，节省内存配置下取 `UE_MBC_MAX_LISTED_SMALL_POOL_SIZE`），且对大对齐多了一步 `PromoteToLargerBin` 的注释说明——把"16 字节请求 + 128 字节对齐"提升到 128 字节桶，避免直接落到至少 4KB 的 OS 分配：

摘自 `Engine/Source/Runtime/Core/Private/HAL/MallocBinned3.cpp`（第 597 行起）：

```cpp
void* FMallocBinned3::Malloc(SIZE_T Size, uint32 Alignment)
{
	// Fast path: Allocate from the small pools if the size is small enough and the alignment <= binned3 min alignment.
	//            Larger alignments can waste a lot of memory allocating an entire page, so some smaller alignments are
	//			  handled in the fallback path if less than a predefined max small pool alignment.

	bool UsePools = (Size <= UE_MB3_MAX_SMALL_POOL_SIZE);

	check(FMath::IsPowerOfTwo(Alignment));

	if (UNLIKELY(UsePools && (Alignment > UE_MBC_STANDARD_ALIGNMENT)))
	{
		// check if allocations that require alignment larger than UE_MBC_STANDARD_ALIGNMENT can be promoted to a bin with a natural alignment that matches
		// i.e. 16 bytes allocation with 128 bytes alignment can be promoted to 128 bytes bin
		// this will save us a lot of memory as otherwise allocations will be promoted to OS allocs that are at least 4 KB large, depending on a platform
		UsePools = PromoteToLargerBin(Size, Alignment, *this);
	}
```

| 分配器 | 版本 | 核心机制 | 特点 |
| --- | --- | --- | --- |
| `FMallocBinned` | UE4 早期 | 固定大小桶 + 池 | 简单，桶多，内部碎片一般；5.8 里仍存在（`MallocBinned.cpp`），Windows 上作为 `EMemoryAllocatorToUse::Binned` 的默认分支 |
| `FMallocBinned2` | UE4 中期 | 小池 + 线程本地缓存 + 缓存行对齐 | `UE_MB2_SMALL_POOL_COUNT` 为 48（省内存）或 51（默认） |
| `FMallocBinned3` | UE5 | 小池 + `PromoteToLargerBin` + 更小页粒度（`UE_MB3_BASE_PAGE_SIZE = 4096`） | macOS/Unix/Android 上作为 64 位默认；Windows 上由 `EMemoryAllocatorToUse::Binned3` 选择 |

（`FMallocBinned`/`FMallocBinned2`/`FMallocBinned3` 均无"UE5 中 64 位平台默认 = Binned3"这一全局结论：选择发生在 `FWindowsPlatformMemory::BaseAllocator()` 的 `switch (EMemoryAllocatorToUse)` 与 `FUnixPlatformMemory`/`FMacPlatformMemory`/`FAndroidPlatformMemory` 各自的 `BaseAllocator()` 里，见 7.1 引用的 `WindowsPlatformMemory.cpp` 第 256~265 行。**本文订正**：原文表格里"FMallocBinned3｜UE5（5.8 中 64 位平台默认）"过于绝对。）

### 7.3 对齐与缓存行

`DEFAULT_ALIGNMENT = 0` 不是"不对齐"，而是"交给分配器按引擎规则决定"；`MIN_ALIGNMENT = 8` 是分配器能力的下界。源码注释把规则写得很直白：**≥16 字节的块按 16 字节对齐，<16 字节的块按 8 字节对齐**；分配器不支持对齐时该参数被忽略。

摘自 `Engine/Source/Runtime/Core/Public/HAL/MemoryBase.h`（第 19 行起）：

```cpp
enum
{
	// Default allocator alignment. If the default is specified, the allocator applies to engine rules.
	// Blocks >= 16 bytes will be 16-byte-aligned, Blocks < 16 will be 8-byte aligned. If the allocator does
	// not support allocation alignment, the alignment will be ignored.
	DEFAULT_ALIGNMENT = 0,

	// Minimum allocator alignment
	MIN_ALIGNMENT = 8,
};
```

要点：

- `FMemory::Malloc(Size, 0)` 与 `FMemory::Malloc(Size, alignof(T))` 在 `T` 是 `float`/`int32` 时是同一件事；只有在 `alignof(T) > 16`（如 `alignas(64)` 的缓存行结构、`alignas(32)` 的 AVX 类型）时才必须显式传对齐。
- 分配器侧的对齐门槛是 `UE_MBC_STANDARD_ALIGNMENT = 16`（`Public/HAL/MallocBinnedCommon.h` 第 37 行，注释为"除 8 字节块按 8 字节对齐外，所有分配的标准对齐"）。超过它就进入 `PromoteToLargerBin` / OS 分配分支。
- 缓存行（通常 64 字节）：Binned 系列把"同一缓存行的内存尽量分给同一线程"的思路体现在**每线程独立的小池空闲链表**上——线程 A 和线程 B 各自从不同 Pool 的本地链表摘块，天然减少伪共享（False Sharing）。这是"线程本地缓存"除了省锁之外的第二个收益。
- `FMemory::QuantizeSize(Size, Alignment)` 返回分配器实际会占用的字节数（≥ Size），容器用它把 `ArrayMax` 对齐到真实 bin 粒度——这也是 `stat memory` 里"容器容量 × 元素大小"与实际占用不等的原因。

### 7.5 TArray 与分配器的边界：哪些数字是"上层"的，哪些是"下层"的

把 3.2 / 7.2 / 7.3 串起来看，一次 `TArray::Add` 触发扩容时经过的数值变换是（**作者示例（非引擎源码）**归纳，每一步的依据见括号内行号）：

| 步骤 | 数值来源 | 依据 |
| --- | --- | --- |
| ① 触发条件 | `ArrayNum == ArrayMax` | `Array.h` 第 1923 行 |
| ② 目标元素数 | `NewNum = ArrayMax + 1` | `Array.h` 第 520 行 |
| ③ 上层增长 | `Grow = NewNum + 3*NewNum/8 + 16` | `ContainerAllocationPolicies.h` 第 192 / 202 行 |
| ④ 量化到 bin | `Retval = QuantizeSize(Grow * BytesPerElement, Alignment) / BytesPerElement` | `ContainerAllocationPolicies.h` 第 208 行 |
| ⑤ 实际分配 | `FMemory::Malloc(NewMax * ElementSize, Alignment)` → `FMEMORY_INLINE_GMalloc->Malloc` | `FMemory.inl` 第 36 行 |
| ⑥ 分桶 | `BoundSizeToPoolIndex(Size, MemSizeToPoolIndex)` 或 `MallocExternalLarge` | `MallocBinned2.cpp` 第 589 / 584 行 |

结论：**"TArray 从 1.375 倍增长"只是第 ③ 步**。到了第 ④ 步，元素数会被向上取整到分配器 bin 边界，"实际占了多少字节"只有第 ⑥ 步的分桶表才知道。所以用"元素数 × sizeof(T)"估算内存峰值会系统性偏低，正确做法是用 `FMemory::QuantizeSize` 或在 Development 配置直接看 `stat memory` / LLM 标签。

## 九、与业务关联

1. **高频 Update 里的容器纪律**：每帧调用的 Tick 中禁止 `TArray`/`TMap` 反复 `Add` 触发扩容——先 `Reserve`；遍历中需要删除用"收集 Id 后统一 Remove"或 `RemoveAtSwap`；这直接决定移动端发热与掉帧。
2. **UI 列表与容器**：UMG 列表数据源用 `TArray` + 索引访问（缓存友好）；需要"按键查数据"（背包按物品 ID 查）用 `TMap<FGameplayTag/FName, T>`；`TMap` 的键优先用 `FName`（内部已哈希）而非 `FString`（每次 `GetTypeHash` 都要遍历字符）。
3. **GC 压力**：UObject 的创建/销毁有 GC 开销；高频临时数据（子弹、飘字）优先用对象池 + 结构体容器（`TArray<FProjectileData>` 值语义），而不是 new UObject。
4. **智能指针选型**：非 UObject 系统对象用 `TSharedPtr`；**跨系统观察引用用 `TWeakPtr`**（避免环）；引用 UObject 一律 `TWeakObjectPtr`/`UPROPERTY` 而非裸指针；把 `TSharedPtr` 存进 UObject 成员时用 `UPROPERTY()` 反射支持的类型包装。
5. **内存分析**：`stat memory`/`memreport` 看总览，Unreal Insights 的 Memory 面板定位具体分配点；发现"某系统内存只涨不降"优先查 `TArray` 是否只 `Reset` 不 `Empty`、`TMap` 是否不断插入新键、`TSharedPtr` 是否有环。
6. **数据包/存档**：网络同步与存档序列化遍历容器时，注意迭代器失效规则——序列化循环内不要增删容器（`TArray::Add` 扩容会让正在遍历的 `Index` 越界风险）。

## 十、常见问题 FAQ

**Q1：TArray 的 RemoveAt 和 RemoveAtSwap 怎么选？**
需要保持元素顺序（UI 列表、按索引映射的数组）用 `RemoveAt`（O(n)）；只做集合用途、顺序无所谓（对象池、临时收集器）用 `RemoveAtSwap`（O(1)），注意它会改变最后一个元素的位置。

**Q2：遍历 TMap 时删除元素崩溃怎么办？**
不要在 `for (auto& KV : Map)` 里直接 `Remove`。方案：① 记录要删的 Key 到临时 `TArray`，遍历完再删；② 用 `TMap` 的 `RemoveAndCopyValue` 取出后延迟处理；③ UE 的 `TMap` 迭代器没有 erase 接口，这是与 `std::map` 的明显差异。

**Q3：TMap 查找比预期慢？**
① 键类型哈希太贵（`FString` 键换成 `FName`）；② 负载因子过高频繁重哈希（`Reserve` 预分配）；③ 冲突严重（自定义 `GetTypeHash` 质量差——用 `HashCombine` 混合多个字段）；④ 误用 `FindOrAdd`（它总会执行一次查找+可能的构造）。

**Q4：TSharedPtr 造成的内存泄漏？**
典型是**环引用**：A 持有 B 的 `TSharedPtr`，B 持有 A 的 `TSharedPtr`，双方计数永不归零。解法：环中至少一侧改用 `TWeakPtr`；或设计明确的所有权层级（父持有子强引用，子持有父弱引用）。

**Q5：为什么自定义结构体放进 TArray 会编译报错？**
需要满足容器对元素的要求：可拷贝/可移动构造、可析构；含 `TUniquePtr` 等不可拷贝成员时，要么删除拷贝语义（`TArray` 需 `MoveTemp` 使用），要么改用 `TArray<TSharedPtr<T>>` 或 `TObjectPtr`。`USTRUCT` 加 `GENERATED_BODY()` 并保证 UPROPERTY 字段可复制通常即可。

**Q6：binned 分配器的内存为什么比预期大？**
① 每个分配有头部元数据（桶索引、大小）；② 桶粒度导致内部碎片（申请 17B 实际占 32B 桶）；③ 池预分配（大块 Pool 按页切分，整页预取）；④ 对齐 padding。`stat memory` 里的 "OS Alloc" 与 "Pool" 差值反映池容量与实际使用量的差异。小对象合并（如 `TArray` 存值而非指针）是减少这类开销的直接手段。

**Q7：Shipping 与 Development 内存行为不同？**
分配器**不是**由 Development/Shipping 直接决定的，而是由平台 `BaseAllocator()` 里的 `EMemoryAllocatorToUse` 决定（Windows 见 `Private/Windows/WindowsPlatformMemory.cpp` 第 256~265 行：`Binned2`/`Binned3`/`Binned` 三分支；generic 平台兜底 `new FMallocAnsi()`，`Private/GenericPlatform/GenericPlatformMemory.cpp` 第 307~318 行）。真正随配置变化的是**外层代理**：`FMemory_GCreateMalloc_ThreadUnsafe` 会按编译开关把 `GMalloc` 依次包上 `FMallocPurgatoryProxy`、`FMallocTraceProxy`（`MemoryTrace_Create`）、`FMallocStomp2`、`FMallocThreadSafeProxy`（仅当分配器自身非线程安全）、`FMallocVerifyProxy`、`FMallocLeakDetectionProxy`、`FMallocPoisonProxy`、`FMallocDoubleFreeFinder`、`FMallocFrameProfiler`（`Private/HAL/UnrealMemory.cpp` 第 347~415 行）。用 `FMallocBinned2::MallocExternalSmall` 里的 `#if UE_MB2_ALLOCATOR_STATS` 这类开关对比时，请以 Shipping（或等价 `-stat` 配置）为准；Development 的代理链与检查会显著改变每笔分配的耗时与额外内存。
