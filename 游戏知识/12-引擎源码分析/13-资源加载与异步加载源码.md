流程要点（每条都能回到上面两个函数的真实行）：

1. **先解析名字再查找**：`StaticLoadObjectInternal` 一进来就调 `ResolveName2(InOuter, StrName, true, true, ResolveFlags, InstancingContext)`（`:1427`）——第三个参数 `true` 表示"允许创建/加载包"，第四个 `true` 表示"失败即报错"。`ResolveFlags` 由 `LoadFlags &= LOAD_EditorOnly | LOAD_NoVerify | LOAD_DeferDependencyLoads` 再 `|= LOAD_Quiet | LOAD_NoWarn` 拼出（`:1423-1425`）；
2. **内存优先**：只有名字里含 `.`（`bContainsObjectName`，`:1421`）且 `bAllowObjectReconciliation` 为真时才走 `StaticFindObjectFast`（`:1438`）；命中但带 `RF_NeedLoad | RF_NeedPostLoad | RF_NeedPostLoadSubobjects | RF_WillBeLoaded` 任一标志时**故意把结果置空**（`:1439-1443`）——这就是"能查到但还没加载完，必须继续往下走"的实现；
3. **整包加载**：包不是 `PKG_CompiledIn` 时调 `LoadPackage(NULL, *InOuter->GetOutermost()->GetName(), LoadFlags & ~LOAD_Verify, nullptr, InstancingContext)`（`:1451`）——源码注释写得很直白："now that we have one asset per package, we load the entire package whenever a single object is requested"；
4. **重定向与"主资产"补全**：找不到时先试 `UObjectRedirector`（`:1458-1470`，`LOAD_NoRedirects` 时跳过）；名字不带对象名时把 `Name.Name` 再递归一次（`:1474-1482`），假定"包名 = 主资产名"；
5. `StaticLoadObject` 自身只是 `StaticLoadObjectInternal(... LoadFlags | LOAD_NoWarn ...)`（`:1493`）再加一段 `bWarnIfMissing` 日志（`:1500-1509`）。

> 关于 `ResolveName`：5.8 里真正干活的是 `ResolveName2(UObject*& InPackage, FStringBuilderBase& InOutName, bool Create, bool Throw, uint32 LoadFlags = LOAD_None, const FLinkerInstancingContext* InstancingContext = nullptr)`（`UObjectGlobals.cpp:1219`，`UObjectGlobals.h:312` 是 `FString&` 版声明），`ResolveName`（`:1323`）只是把 `FString` 包成 `FStringBuilderBase` 再转调 `ResolveName2`。路径解析内部已迁移到 `FPackagePath` / `FTopLevelAssetPath` 体系（见 3.2）。

关键判断为什么这样写：

- `ThreadContext.SyncLoadUsingAsyncLoaderCount++/--`（`:1738`、`:1766`）把"当前线程正在用异步加载器做同步加载"这一事实公开出去，加载线程/GC 据此调整行为；配对的 `--` 在 `FlushAsyncLoading` 之后，保证等待期间计数有效；
- `FCoreDelegates::OnSyncLoadPackage.Broadcast`（`:1735`）上方注释说明了它**只在游戏线程且非加载线程**广播——因为该委托不是线程安全的；这也是"抓同步加载卡顿"的挂点；
- 返回值分两条路：`InOuter` 非空时直接返回 `InOuter`（`:1768-1771`）；否则 `FindObjectFast<UPackage>(nullptr, PackageName)`（`:1773`），失败再按 `FCoreRedirects::GetRedirectedName(ECoreRedirectFlags::Type_Package, ...)` 查一次重定向后的包名（`:1776-1782`）——**这就是"资源改名/移动后仍能加载"的包级兜底**；
- 空路径（`:1714`）与 `PackageName.IsNone()`（`:1724`）在真正发请求前就返回 `nullptr`，避免把坏路径塞进加载队列。

与相邻阶段衔接：`LoadPackage(UPackage*, const TCHAR*, ...)`（`:1787`）负责短包名/文件名到 `FPackagePath` 的规范化后转调本函数；`LoadPackage(UPackage*, const FPackagePath&, ...)`（`:1851`）直接转调（`:1873`）。下游就是 3.6 / 3.8 的异步加载线程。

这是 UE 5.x 最重要的架构事实：**同步加载在引擎内部被实现为"异步请求 + 针对该 RequestID 的 FlushAsyncLoading"**。`LoadPackage(UPackage* InOuter, const TCHAR* InLongPackageNameOrFilename, uint32 LoadFlags, ...)`（以及 5.8 的 `LoadPackage(UPackage* InOuter, const FPackagePath& InPackagePath, ...)` 重载）只是 `LoadPackageInternal` 的一层壳（负责把字符串/路径转成 `FPackagePath`）。

对业务的启示：

- `LoadObject` / `LoadPackage` 造成的卡顿，本质上就是"异步加载线程把整张依赖图跑完"的时间——优化方向不是"换一个更快的同步 API"，而是**把同样的请求改成真正的异步**（`LoadPackageAsync` / `FStreamableManager`）；
- `FCoreDelegates::OnSyncLoadPackage` 是"谁在同步加载"的全局广播（`:1733-1736`），用 Unreal Insights 或挂这个委托即可抓出所有卡顿点；
- `SyncLoadUsingAsyncLoaderCount` 是线程上下文计数器（`:1738` / `:1766`）：加载线程/GC 检测到"游戏线程在同步加载"时会调整行为（例如暂停增量 GC 的某些阶段）。

> 补充可核实点：`LoadPackageAsync` 的四个重载声明在 `UObjectGlobals.h:837`（`FLoadPackageAsyncOptionalParams` 版）、`:854`、`:877`、`:887`；`EAsyncLoadingResult` 枚举在 `:711-728`。发起请求的那一个（`LoadPackageInternal:1759`）用的是 `:837` 的重载。

`PostLoad` 的执行时机与顺序：

1. 全部导出反序列化完成后，进入 PostLoad 阶段（异步系统里是 `FAsyncPackage2::ConditionalBeginPostLoad`，见 3.6 节）；
2. 引擎按"**依赖优先**"的顺序对带 `RF_NeedPostLoad` 的对象调用 `ConditionalPostLoad()`（内部：清标志 → 调 `PostLoad()` → 处理子对象 `PostLoadSubobjects`）；
3. 对象 `PostLoad` 里访问的**所有引用对象**此时必然已经"可安全访问"（要么已 PostLoad，要么引擎保证其 Preload 完成）——这就是为什么 `PostLoad` 里可以放心地初始化缓存、解析软引用；
4. 一轮 PostLoad 后仍带 `RF_NeedPostLoad` 的对象（如循环引用）会进入**第二轮**，直到全部收敛。

> 自定义 `PostLoad` 的黄金规则：不要在里面 `LoadObject`（会打乱依赖顺序、可能死锁），需要外部数据请用软引用 + 延迟加载，或确保在 Preload 阶段已就绪。

bool FAsyncPackage2::PreloadLinkerLoadExports(FAsyncLoadingThreadState2& ThreadState)
{
	// Serialize exports
	UE::TUniqueLock LinkerLock(LinkerLoadState->Linker->Mutex);

	const int32 ExportCount = LinkerLoadState->Linker->ExportMap.Num();

		if (ExportObject.Object != LinkerExport.Object)

这四段在做什么／关键判断为什么这样写：

- `StartLoading` 一进来就把状态置为 `EAsyncPackageLoadingState2::WaitingForIo`（`:7574`），紧接着 `CallProgressCallbacks()`——源码注释（`:7576-7577`）说明**必须在置状态之后调用**，否则进度回调读到的是旧状态、等于没派发；
- 若 `LinkerLoadState.IsSet()`（即 Linker 已提前建好），`StartLoading` 不读 chunk，而是直接 `ReleaseBarrier(&ThreadState)` 放行 `Package_ProcessSummary` 节点（`:7584-7588`）——这就是"事件图"的第一手证据：推进靠**放行屏障**，不是靠循环轮询；
- 真正发 IO 的是 `IoBatch.ReadWithCallback(ChunkId, ReadOptions, Desc.Priority, [this](TIoStatusOr<FIoBuffer> Result){...})`（`:7631-7655`），chunk id 由 `CreateIoChunkId(Desc.PackageIdToLoad.Value(), ChunkIndex, EIoChunkType::ExportBundleData)` 构造（`:7630`，`ChunkIndex` 在非编辑器下恒为 0，`:7626-7629`）；回调里 `GetPackageNode(EEventLoadNode2::Package_ProcessSummary).ReleaseBarrier(nullptr)`（`:7650`）把节点放行，`PendingIoRequestsCounter` 归零时 `AltZenaphore.NotifyOne()`（`:7651-7654`）唤醒加载线程——**IO 完成 → 屏障放行 → 事件队列被唤醒**，这条链是 EDL2 的核心；
- `PreloadLinkerLoadExports` 全程持 `UE::TUniqueLock LinkerLock(LinkerLoadState->Linker->Mutex)`（`:7903`，与 3.3.3 节 `Preload` 内的 `UE::TUniqueLock UniqueLock(Mutex)` 是同一把锁）；每轮 `ThreadState.MarkAsActive()`（`:7909`）后自增 `SerializeExportIndex`；`IsTimeLimitExceeded(TEXT("SerializeLinkerLoadExports"))` 为真时 **`return false` 让出线程**（`:7934-7937`）——返回值就是"还没做完"，由事件图下次再来，不是异常；
- `LinkerExport.Object` 为空时**直接跳过**（`:7915`），与 3.3.2 节的 `CreateExportAndPreload` 不同：这里不创建对象，只对已存在且带 `RF_NeedLoad` 的对象补 `Preload`，所以本函数是"序列化"阶段而非"创建"阶段；
- `ConditionalBeginPostLoad` 的第一行 `check(AsyncPackageLoadingState == EAsyncPackageLoadingState2::ExportsDone)`（`:6047`）是**状态机不变式**：PostLoad 只能在 `ExportsDone` 之后进入；随后 `AsyncPackageLoadingState = PostLoad`（`:6048`）→ `ConditionalReleasePartialRequests` → `ConditionalBeginPostLoadPhase`。`ConditionalReleasePartialRequests` 的作用见 3.9。
- **易误解点**：`PreloadLinkerLoadExports` 的返回值是 `bool`，`false` 表示"时间片用完，下次继续"，**不是失败**；真正的失败走 `LoadStatus = EAsyncLoadingResult::FailedLinker`（例如 `ProcessLinkerLoadPackageSummary` 里 `:7725`）。

线程模型要点：

- **不是"加载线程池"**：5.8 只有一个异步加载线程类 `FAsyncLoadingThread2`（`AsyncLoading2.cpp:4730`，`class FAsyncLoadingThread2 final`），它既是线程体（`Run`）也是加载器（`IAsyncPackageLoader`）实现。单个包的 `FAsyncPackage2` 是同一线程上的状态机实例，"并行度"来自 IoStore 的异步 IO 与事件图，不是来自多个反序列化线程。每个包的状态机由 `EAsyncPackageLoadingState2`（`:3408-3431`，共 21 个值：`NewPackage / WaitingForIo / ProcessPackageSummary / ProcessDependencies / WaitingForDependencies / DependenciesReady / CreateExports / WaitingForImportDependencies / ResolveImports / PreloadExports / WaitingForExternalReads / ExportsDone / PostLoad / DeferredPostLoad / DeferredPostLoadDone / Finalize / PostLoadInstances / CreateClusters / Complete / DeferredClearImportedPackages / DeferredDelete`）驱动；枚举值是 `WaitingForIo`（小写 o），不存在 `LinkerCreated` 值（原文这点是对的）；
- **依赖图**：`ImportPackagesRecursive`（`:7443`）递归登记所有 Import 包；某包的节点在"所有依赖包到达指定状态"前不释放（`WaitForAllDependenciesToReachState`，`:10176`），从机制上保证"父包反序列化时，它引用的对象一定已就绪"；
- **PostLoad 分层**：`ConditionalBeginPostLoad` 之后是 `ConditionalBeginDeferredPostLoad`（`:6053`），且**后者的第一件事是 `MoveConstructedObjectsToPhase2()`**（`:6059`），源码注释（`:6057-6058`）写明目的是"让 PostLoad 里的 `StaticFind` 能看到已就绪的对象"；
- **完成回调**：`ConditionalFinishLoading`（`:10215`）里 `WaitForAllDependenciesToReachState(..., EAsyncPackageLoadingState2::DeferredPostLoadDone, ...)` 通过后把包推进到 `Finalize` 并加入 `LoadedPackagesToProcess`（`:10222-10223`），再由游戏线程派发 `FLoadPackageAsyncDelegate`；
- **时间片**：`ThreadState.IsTimeLimitExceeded(...)`（如 `:7934`）让长任务分段让出，避免单个大包独占加载线程。注意这只在 `bAsyncLoadingThreadEnabled` 时有意义，见 3.8.2。

> 版本注（已按 5.8.2 复核）：UE 4.27 ~ 5.0 的旧系统是 `FAsyncPackage`（AsyncLoading.cpp），包内为显式状态机，由 `FAsyncPackage::Tick` 推进 `SetupDependencies → CreateLinker → LoadAllObjects → PostLoadObjects → CompletionCallback`。**5.8.2 中 `Engine/Source/Runtime/CoreUObject/Private/Serialization/AsyncLoading.cpp` 只剩 1253 行，全部内容围绕 `FAsyncArchive`（文件拷贝/预取缓存）与 `STAT_FAsyncPackage_*` 等统计声明（如 `:78` 的 `DECLARE_CYCLE_STAT(TEXT("Tick AsyncPackage"), STAT_FAsyncPackage_Tick, STATGROUP_AsyncLoad)`），既不定义 `FAsyncPackage` 也不定义 `FAsyncLoadingThread`**——详见 3.8.1 的逐条检索证据。看到网上老文章讲 `FAsyncPackage::Tick` 时，注意那对应 5.0 及更早版本。

- `FAsyncPackage2` 内部持有 `FEventLoadNode2` 节点（类声明在 `:3477`），节点集合由 `CreatePackageNodes(const FAsyncLoadEventSpec* EventSpecs)`（`:12140`）按 `EventSpecs` 表创建；节点之间靠 `AddBarrier` / `ReleaseBarrier` 计数（`StartLoading` 里 `GetPackageNode(EEventLoadNode2::Package_ProcessSummary).AddBarrier()` 在 `:7597`、`ReleaseBarrier` 在 `:7586` / `:7612` / `:7650`）；

- `EEventLoadNodeExecutionResult`（`Event_PostLoad` / `Event_DeferredPostLoad` / `Event_ExportsDone` 等的返回类型，如 `:10233`、`:10369`、`:9938`）表示"本轮执行结果"，让事件队列知道是继续、让出还是完成；
- **易误解点**：`check(LinkerResult != FLinkerLoad::LINKER_TimedOut); // TODO: Add support for timeouts here`（`ProcessLinkerLoadPackageSummary`，`:7722`）——Summary 解析阶段**不支持时间片**，源码里留了 TODO。所以"大包 Summary 一大就必然吃满一次 tick"是这个阶段的已知限制；

## 六、常见问题 FAQ

### Q1：`LoadObject` 返回了对象，但对象的子资源（材质/网格）还没就绪？

不可能——同步加载保证整张依赖图（ImportMap 递归）加载完成才返回。若"拿到对象但表现不对"，通常是对象 `PostLoad` 里解析的**软引用**没加载（软引用不随包加载），需要显式 `TryLoad` / `RequestAsyncLoad`。

### Q2：异步加载回调里 `GetLoadedAsset()` 返回 null？

先查 `EAsyncLoadingResult`（`UObjectGlobals.h:711-728`）：`Failed / FailedMissing / FailedLinker / FailedNotInstalled / Canceled` 都会触发回调但结果为空（只有 `Succeeded` 才是成功）。另外回调委托若绑定的是 `FStreamableDelegate`（无参版，`StreamableManager.h:38`），请从**句柄**取资产（`FStreamableDelegateWithHandle` 版本，`:39`，把句柄传进回调）。路径错误、资源被移动（重定向未生效）是两大常见原因。

> 顺带纠正一个常见误用：**5.8 没有 `FStreamableHandle::IsComplete()`**。要判断状态请用 `HasLoadCompleted()` / `IsLoadingInProgress()` / `IsActive()` / `IsStalled()`（`StreamableManager.h:203 / 215 / 221 / 227`）。

### Q3：为什么"异步加载中"调用 `FlushAsyncLoading()` 还是会卡？

因为 `FlushAsyncLoading` 的语义就是"**等到全部完成**"：它把异步请求的等待期压缩到当前帧。正确姿势是不要 Flush，用完成回调驱动后续逻辑；确需等待特定资源时用 `ProcessAsyncLoadingUntilComplete(谓词)` 缩小等待范围。

### Q4：`RequestAsyncLoad` 同一个资源调用两次，会加载两次吗？

不会（但条件需按 5.8 源码确认）：`FStreamableHandle::CreateCombinedHandle`（`StreamableManager.cpp:1446`）与 `UpdateCombinedHandle`（`:1238`）确实存在合并机制，`HandleDebugName_CombinedHandle` 的字面值是 `"CreateCombinedHandle"`（`:125`）。不过"同路径重复请求**必然**合并"这一强断言本轮未逐行核实其全部条件——**请查阅源文件 `Engine/Source/Runtime/Engine/Private/StreamableManager.cpp` 第 1446 行起与第 1238 行起**。（原文提到的 `StreamInternal` 符号本轮未在 5.8.2 的 `StreamableManager.cpp` 中核实到，请以 `CreateCombinedHandle` 为准。）

### Q5：打包后 `LoadObject` 找不到 `/Game/...` 路径的资源？

打包后资源进入 Pak / IoStore 容器，路径本身不变；找不到通常是：(1) 资源被裁剪（未被打包——检查 Asset Manager 主资源表 / 引用链）；(2) 路径大小写或重定向问题（用 `FSoftObjectPath` 存引用可自动跟随重定向）；(3) 平台差异（如 Android 的 `--sandbox` 挂载）。

### Q6：`PostLoad` 里能 `LoadObject` 吗？

技术上能，但强烈不建议：PostLoad 阶段处于"依赖优先"的全局排序中，插入同步加载会破坏顺序、可能触发死锁（A 的 PostLoad 等 B，B 的 PostLoad 等 A）。需要外部数据时用软引用 + 延迟加载，或把逻辑推迟到 `BeginPlay` / 首次使用时。

### Q7：UE4.27 项目里的 `FAsyncPackage` 与 UE5.8 的 `FAsyncPackage2` 对业务有影响吗？

没有直接 API 影响：`LoadPackageAsync` / `FStreamableManager` 接口跨版本稳定，变化在引擎内部实现（EDL2 事件驱动）。只有深度定制加载流程（如自研流送系统直接操作包状态）的代码需要迁移。
