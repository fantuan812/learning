## 三、关键类/函数剖析

### 3.1 启动链路：RunBehaviorTree → StartTree

#### 3.1.1 AIController 入口（AIController.cpp 节选）

摘自 `Engine/Source/Runtime/AIModule/Private/AIController.cpp`（第 1001 行起）

```cpp
bool AAIController::RunBehaviorTree(UBehaviorTree* BTAsset)
{
	// @todo: find BrainComponent and see if it's BehaviorTreeComponent
	// Also check if BTAsset requires BlackBoardComponent, and if so
	// check if BB type is accepted by BTAsset.
	// Spawn BehaviorTreeComponent if none present.
	// Spawn BlackBoardComponent if none present, but fail if one is present but is not of compatible class
	if (BTAsset == NULL)
	{
		UE_VLOG(this, LogBehaviorTree, Warning, TEXT("RunBehaviorTree: Unable to run NULL behavior tree"));
		return false;
	}

	bool bSuccess = true;

	// see if need a blackboard component at all
	UBlackboardComponent* BlackboardComp = Blackboard;
	if (BTAsset->BlackboardAsset && (Blackboard == nullptr || Blackboard->IsCompatibleWith(BTAsset->BlackboardAsset) == false))
	{
		bSuccess = UseBlackboard(BTAsset->BlackboardAsset, BlackboardComp);
	}

	if (bSuccess)
	{
		UBehaviorTreeComponent* BTComp = Cast<UBehaviorTreeComponent>(BrainComponent);
		if (BTComp == NULL)
		{
			UE_VLOG(this, LogBehaviorTree, Log, TEXT("RunBehaviorTree: spawning BehaviorTreeComponent.."));

			BTComp = NewObject<UBehaviorTreeComponent>(this);
			BTComp->RegisterComponent();
			REDIRECT_OBJECT_TO_VLOG(BTComp, this);
		}

		// make sure BrainComponent points at the newly created BT component
		BrainComponent = BTComp;

		check(BTComp != NULL);
		BTComp->StartTree(*BTAsset, EBTExecutionMode::Looped);
	}

	return bSuccess;
}
```

这段在做什么：`AAIController::RunBehaviorTree` 是"资产 → 运行实例"的唯一官方入口，它不碰任何行为树运行时数据结构，只做两件事——**准备黑板组件**、**准备/复用 `UBehaviorTreeComponent` 并转交 `StartTree`**。

关键判断为什么这样写：

1. `BTAsset == NULL` 的检查排在最前，并且**不先检查黑板**——因为空资产连 `BlackboardAsset` 都无法读取；此时只写一条 `UE_VLOG` 警告并返回 false，不抛异常、不改组件状态。
2. 黑板只在"资产确实要黑板 **且** 现有黑板不兼容"时才重建：`BTAsset->BlackboardAsset && (Blackboard == nullptr || Blackboard->IsCompatibleWith(BTAsset->BlackboardAsset) == false)`。这里的 `IsCompatibleWith` 会沿 `UBlackboardData::Parent` 链比较（见 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BlackboardComponent.cpp` 第 506 行起），所以**派生黑板资产可以复用同一个组件**。
3. `UseBlackboard(...)` 是"输出参数"风格：`BlackboardComp` 先被初始化为当前的 `Blackboard`，函数内部按需创建并回写；返回值 `bSuccess` 才决定是否继续。
4. 组件复用优先于新建：`Cast<UBehaviorTreeComponent>(BrainComponent)` 成功就直接复用（一个 Controller 上不会出现两个 BT 组件），失败才 `NewObject` + `RegisterComponent`，然后**无条件把 `BrainComponent` 指过去**。
5. 最后 `StartTree(*BTAsset, EBTExecutionMode::Looped)` 是**引用传参**（`UBehaviorTree&`），本函数不持有该资产的运行状态。

与相邻阶段衔接：本函数只把请求交给 `UBehaviorTreeComponent::StartTree`（3.1.2），真正建实例发生在 `ProcessPendingInitialize`（3.1.3）。

易误解点：

- 返回值 `bSuccess` 是"黑板是否就绪"的结果，**不是**"树是否跑起来"的结果；`StartTree` 的失败（如同一棵树已运行）不会反映在这里。
- `BrainComponent` 是 `TObjectPtr<UBrainComponent>`（`Engine/Source/Runtime/AIModule/Classes/AIController.h` 第 140 行），`Blackboard` 是另一个独立成员（第 148 行）——"黑板组件"与"脑组件"是并列挂载的，不是父子关系。
- 文章正文中出现的函数名必须写全限定名 `AAIController::RunBehaviorTree`：`AIController` 只是头文件名，5.8 里没有叫 `AIController` 的类。

要点：

- `UBehaviorTreeComponent` 继承自 `UBrainComponent`（`UActorComponent` 子类），是**运行时引擎**；`UBehaviorTree` 资产本身只是一棵"节点模板树"（`RootNode` 等），不保存运行状态。（2026-09-15 补：`UBehaviorTree::RootNode` 的真实声明在 `Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BehaviorTree.h` 第 21 行 `TObjectPtr<UBTCompositeNode> RootNode;`，`BlackboardAsset` 在同文件第 42 行。）
- `UseBlackboard(BTAsset->BlackboardAsset, BlackboardComp)`：黑板组件与行为树共用同一份 `UBlackboardData` 资产，后续所有节点通过"键名 → KeyID"访问同一块内存。
- 注意 `BTAsset->BlackboardAsset` 是 `UBlackboardData*` 类型（UE 5.1 起 `UBlackboard` 更名为 `UBlackboardData`；4.x 中叫 `UBlackboard`）。

#### 3.1.2 StartTree（BehaviorTreeComponent.cpp 节选，UE 5.8）

摘自 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeComponent.cpp`（第 240 行起）

```cpp
void UBehaviorTreeComponent::StartTree(UBehaviorTree& Asset, EBTExecutionMode::Type ExecuteMode /*= EBTExecutionMode::Looped*/)
{
	// clear instance stack, start should always run new tree from root
	UBehaviorTree* CurrentRoot = GetRootTree();

	if (CurrentRoot == &Asset && TreeHasBeenStarted())
	{
		UE_VLOG(GetOwner(), LogBehaviorTree, Log, TEXT("Skipping behavior start request - it's already running"));
		return;
	}
	else if (CurrentRoot)
	{
		UE_VLOG(GetOwner(), LogBehaviorTree, Log, TEXT("Abandoning behavior %s to start new one (%s)"),
			*GetNameSafe(CurrentRoot), *Asset.GetName());
	}

	StopTree(EBTStopMode::Safe);

	TreeStartInfo.Asset = &Asset;
	TreeStartInfo.ExecuteMode = ExecuteMode;
	TreeStartInfo.bPendingInitialize = true;

	ProcessPendingInitialize();
}
```

这段在做什么：`StartTree` 只做"登记 + 转交"——把启动意图写进 `TreeStartInfo`，再调 `ProcessPendingInitialize` 尝试落地。

关键判断为什么这样写：

- `CurrentRoot == &Asset && TreeHasBeenStarted()` 是**同一棵树的防重入**：注意判定用的是 `GetRootTree()`（栈底实例的资产）而不是 `GetCurrentTree()`，所以"父树里嵌了同一棵树"这种自嵌套会被识别为"已经在跑"。
- `CurrentRoot` 非空但不是同一棵树时，只写一条 VLOG 说明"正在放弃旧树"，**不在这里做任何拆除**——拆除交给下一行的 `StopTree(EBTStopMode::Safe)`。
- `TreeStartInfo.bPendingInitialize = true` 是关键：如果此刻还有任务处于"延迟中止"（`bWaitingForLatentAborts`），`StopTree(Safe)` 与 `ProcessPendingInitialize` 都会提前返回，启动请求就**留在 `TreeStartInfo` 里等**，由 `OnTaskFinished` 末尾的 `TreeStartInfo.HasPendingInitialize()` 分支补跑（见 3.4.2）。
- `EBTStopMode::Safe` vs `Forced`：Safe 会先让正在跑的任务走 `AbortTask` 流程（可延迟），Forced 直接丢弃。`StartTree` 选 Safe，是为了让"切树"时正在移动/攻击的任务有机会清理自己。

与相邻阶段衔接：`TreeStartInfo` 是 `FBTTreeStartInfo`（`Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BehaviorTreeComponent.h` 第 70 行起），三个字段 `Asset / ExecuteMode / bPendingInitialize` 正好就是本次调用的全部输入。

易误解点：`StopTree` 内部还有"分支动作挂起"（`SuspendedBranchActions`）机制——若当前正处于某次搜索/中止的临界区，`StopTree` 不会立刻执行，而是把请求压进 `PendingBranchActionRequests` 排队（见 3.6.2 的 `RequestBranchDeactivation` 同款写法）。

版本注：`ExecuteTree(UBehaviorTree& InAsset, UBTNode* InRootOverride)` 并非 UE 官方 API（5.8 的 AIModule 源码中不存在该方法，部分旧教程的误称）；行为树启动入口自 UE4 起始终是 `StartTree(UBehaviorTree& Asset, EBTExecutionMode::Type ExecuteMode)`。`EBTExecutionMode` 只有 `SingleRun` 与 `Looped` 两值（`BehaviorTreeTypes.h`）：

摘自 `Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BehaviorTreeTypes.h`（第 99 行起）

```cpp

		SingleRun,
```

#### 3.1.3 ProcessPendingInitialize：真正建实例（节选）

摘自 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeComponent.cpp`（第 265 行起）

```cpp
void UBehaviorTreeComponent::ProcessPendingInitialize()
{
	if ((SuspendedBranchActions & EBTBranchAction::ProcessPendingInitialize) != EBTBranchAction::None)
	{
		UE_VLOG(GetOwner(), LogBehaviorTree, Verbose, TEXT("ProcessPendingInitialize(%s) queued up"), *GetNameSafe(TreeStartInfo.Asset));
		PendingBranchActionRequests.Emplace(nullptr, EBTBranchAction::ProcessPendingInitialize);
		return;
	}

	StopTree(EBTStopMode::Safe);
	if (bWaitingForLatentAborts)
	{
		return;
	}

	// finish cleanup
	RemoveAllInstances();

	bLoopExecution = (TreeStartInfo.ExecuteMode == EBTExecutionMode::Looped);
	bIsRunning = true;

#if USE_BEHAVIORTREE_DEBUGGER
	DebuggerSteps.Reset();
#endif

	UBehaviorTreeManager* BTManager = UBehaviorTreeManager::GetCurrent(GetWorld());
	if (BTManager)
	{
		BTManager->AddActiveComponent(*this);
	}

	// push new instance
	const bool bPushed = PushInstance(*TreeStartInfo.Asset);
	TreeStartInfo.bPendingInitialize = false;
}
```

这段在做什么：这是"树真正开始运行"的时刻——清空旧状态、设置运行标志、向 `UBehaviorTreeManager` 注册、压入第一个实例。

关键判断为什么这样写：

- 第一道判断 `(SuspendedBranchActions & EBTBranchAction::ProcessPendingInitialize) != None` 是**拓扑变更的互斥保护**：初始化会改 `InstanceStack`，若此刻树正在被遍历（改栈会破坏遍历），就只能排队。`EBTBranchAction` 是一个 `uint16` 位掩码枚举（`BehaviorTreeComponent.h` 第 81 行起），`ProcessPendingInitialize = 0x200` 属于 `Changing_Topology_Actions` 组。
- 第二道判断是"本次调用属于首次启动还是重入"：`TreeStartInfo.bPendingInitialize` 在函数末尾才被清掉，因此**在被 `OnTaskFinished` 重入调用时**它仍为 true。
- `if (bWaitingForLatentAborts) return;` 后面的注释是源码原文（"// finish cleanup"）：中止没结束前不拆实例，等 `TrackPendingLatentAborts` 收尾后由 tick 再驱动。
- `bLoopExecution` 与 `bIsRunning` 分开存：前者决定"树跑空后是否重跑根节点"（见 3.4.2 的 `OnTreeFinished`），后者决定"组件是否允许被 tick"。
- `UBehaviorTreeManager::GetCurrent(GetWorld())` 允许返回 null（世界已销毁），所以有 `if (BTManager)` 保护；`AddActiveComponent` 只用于全局统计与调试器枚举。
- `const bool bPushed = PushInstance(...)` 的返回值**在本函数里没有被检查**——这是刻意的：成功与失败都会清 `bPendingInitialize`，失败时后续 tick 会因 `InstanceStack.Num() == 0` 自然空转。`bPushed` 在 5.8 中确实是未使用变量。

与相邻阶段衔接：本函数结束即进入 `PushInstance`（3.1.4），实例压栈后才会有第一次搜索。

`PushInstance` 内部会：为整棵树按 `UBTNode::GetInstanceMemorySize()` 分配一块 `FBehaviorTreeInstance::InstanceMemory`（TArray<uint8>），对每个节点调用 `InitializeNode(...)` 填好父子/执行索引/内存偏移，然后请求一次"从根开始的搜索执行"。

摘自 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeComponent.cpp`（第 2707 行起）

```cpp
bool UBehaviorTreeComponent::PushInstance(UBehaviorTree& TreeAsset)
{
	// check if blackboard class match
	if (TreeAsset.BlackboardAsset && BlackboardComp && !BlackboardComp->IsCompatibleWith(TreeAsset.BlackboardAsset))
	{
		UE_VLOG(GetOwner(), LogBehaviorTree, Warning, TEXT("Failed to execute tree %s: blackboard %s is not compatibile with current: %s!"),
			*TreeAsset.GetName(), *GetNameSafe(TreeAsset.BlackboardAsset), *GetNameSafe(BlackboardComp->GetBlackboardAsset()));

		return false;
	}

	UBehaviorTreeManager* BTManager = UBehaviorTreeManager::GetCurrent(GetWorld());
	if (BTManager == NULL)
	{
		UE_VLOG(GetOwner(), LogBehaviorTree, Warning, TEXT("Failed to execute tree %s: behavior tree manager not found!"), *TreeAsset.GetName());
		return false;
	}

	// check if parent node allows it
	const UBTNode* ActiveNode = GetActiveNode();
	const UBTCompositeNode* ActiveParent = ActiveNode ? ActiveNode->GetParentNode() : NULL;
	if (ActiveParent)
	{
		uint8* ParentMemory = GetNodeMemory((UBTNode*)ActiveParent, InstanceStack.Num() - 1);
		int32 ChildIdx = ActiveNode ? ActiveParent->GetChildIndex(*ActiveNode) : INDEX_NONE;

		const bool bIsAllowed = ActiveParent->CanPushSubtree(*this, ParentMemory, ChildIdx);
		if (!bIsAllowed)
		{
			UE_VLOG(GetOwner(), LogBehaviorTree, Warning, TEXT("Failed to execute tree %s: parent of active node does not allow it! (%s)"),
				*TreeAsset.GetName(), *UBehaviorTreeTypes::DescribeNodeHelper(ActiveParent));
			return false;
		}
	}

	UBTCompositeNode* RootNode = NULL;
	uint16 InstanceMemorySize = 0;

	const bool bLoaded = BTManager->LoadTree(TreeAsset, RootNode, InstanceMemorySize);
	if (bLoaded)
	{
		FBehaviorTreeInstance& NewInstance = InstanceStack.AddDefaulted_GetRef();
		NewInstance.InstanceIdIndex = UpdateInstanceId(&TreeAsset, ActiveNode, InstanceStack.Num() - 1);
		NewInstance.RootNode = RootNode;
		NewInstance.ActiveNode = NULL;
		NewInstance.ActiveNodeType = EBTActiveNode::Composite;

		// initialize memory and node instances
		FBehaviorTreeInstanceId& InstanceInfo = KnownInstances[NewInstance.InstanceIdIndex];
		int32 NodeInstanceIndex = InstanceInfo.FirstNodeInstance;
		const bool bFirstTime = (InstanceInfo.InstanceMemory.Num() != InstanceMemorySize);
		if (bFirstTime)
		{
			InstanceInfo.InstanceMemory.AddZeroed(InstanceMemorySize);
			InstanceInfo.RootNode = RootNode;
		}

		NewInstance.SetInstanceMemory(InstanceInfo.InstanceMemory);
		NewInstance.Initialize(*this, *RootNode, NodeInstanceIndex, bFirstTime ? EBTMemoryInit::Initialize : EBTMemoryInit::RestoreSubtree);


		const int32 InstanceIndex = InstanceStack.Num() - 1;
		ActiveInstanceIdx = IntCastChecked<uint16>(InstanceIndex);

		// start root level services now (they won't be removed on looping tree anyway)
		for (int32 ServiceIndex = 0; ServiceIndex < RootNode->Services.Num(); ServiceIndex++)
		{
			UBTService* ServiceNode = RootNode->Services[ServiceIndex];
			uint8* NodeMemory = (uint8*)ServiceNode->GetNodeMemory<uint8>(InstanceStack[ActiveInstanceIdx]);

			// send initial on search start events in case someone is using them for init logic
			ServiceNode->NotifyParentActivation(SearchData);

			InstanceStack[ActiveInstanceIdx].AddToActiveAuxNodes(*this,ServiceNode);
			ServiceNode->WrappedOnBecomeRelevant(*this, NodeMemory);
		}

		FBehaviorTreeDelegates::OnTreeStarted.Broadcast(*this, TreeAsset);

		if ((SuspendedBranchActions & EBTBranchAction::SubTreeEvaluate) != EBTBranchAction::None)
		{
			UE_VLOG(GetOwner(), LogBehaviorTree, Verbose, TEXT("Evaluate sub tree(%s) root(%s) queued up"), *TreeAsset.GetName(), *UBehaviorTreeTypes::DescribeNodeHelper(RootNode));
			PendingBranchActionRequests.Emplace(RootNode, EBTBranchAction::SubTreeEvaluate);
			return true;
		}

		// start new task
		RequestExecution(RootNode, ActiveInstanceIdx, RootNode, 0, EBTNodeResult::InProgress);
		return true;
	}

	return false;
}
```

上面是 `PushInstance` 的完整实现（43 行函数体，未裁剪）。它回答了"实例化一个子树到底要准备哪些东西"这个问题，共三层：

**第一层：三次前置校验（任一失败直接 return false，不产生副作用）**

| 校验 | 条件 | 失败后果 |
| --- | --- | --- |
| 黑板兼容 | `TreeAsset.BlackboardAsset && BlackboardComp && !BlackboardComp->IsCompatibleWith(...)` | 子树用的黑板与父树不兼容，拒绝压栈 |
| 管理器存在 | `UBehaviorTreeManager::GetCurrent(GetWorld()) == NULL` | 无法 `LoadTree`，拒绝压栈 |
| 父节点许可 | `ActiveParent->CanPushSubtree(*this, ParentMemory, ChildIdx)` | 例如 `UBTTask_RunBehaviorDynamic` 未配置、或 SimpleParallel 不允许再挂子树 |

**第二层：内存与实例的两套数据**

- `BTManager->LoadTree(TreeAsset, RootNode, InstanceMemorySize)` 返回**模板根节点**与**整棵树的内存总大小**（模板是共享的，`MemorySize` 由节点 `GetInstanceMemorySize()` 之和编译期算好）。
- `InstanceStack.AddDefaulted_GetRef()` 拿到栈上的运行实例 `FBehaviorTreeInstance`，并用 `UpdateInstanceId` 算出/复用它的 `KnownInstances` 下标。
- `const bool bFirstTime = (InstanceInfo.InstanceMemory.Num() != InstanceMemorySize)` 是**首次进入 vs 重入**的分水岭：首次要 `AddZeroed` 并保存 `RootNode`；重入则直接复用 `InstanceInfo.InstanceMemory`（这就是"存盘 / 读档"式子树记忆，对应 3.3.1 表格里的 `EBTMemoryInit::RestoreSubtree`）。
- `NewInstance.SetInstanceMemory(...)` 让运行实例与持久副本共享同一块字节；随后 `NewInstance.Initialize(*this, *RootNode, NodeInstanceIndex, bFirstTime ? Initialize : RestoreSubtree)` 递归初始化整棵子树的节点内存，`NodeInstanceIndex` 是引用参数，为 `bCreateNodeInstance` 的节点在 `NodeInstances` 数组里分配槽位。

**第三层：根级服务与首次搜索**

- 循环 `RootNode->Services`：先 `NotifyParentActivation(SearchData)`（服务可以借机做 `OnSearchStart` / 立即补一次 tick，见 3.7），再 `AddToActiveAuxNodes` + `WrappedOnBecomeRelevant`。**根级服务在压栈时就激活**，因为它们在整棵树存活期间都不该被移除。（2026-09-15 补：`NotifyParentActivation` 的声明在 `Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BTService.h` 第 40 行，实现见 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BTService.cpp` 第 34~66 行，§3.7 已逐字引用。）
- `FBehaviorTreeDelegates::OnTreeStarted.Broadcast(*this, TreeAsset)` 是**唯一对外的"树已启动"通知**（声明见 `Engine/Source/Runtime/AIModule/Public/BehaviorTreeDelegates.h` 第 15 行 `DECLARE_MULTICAST_DELEGATE_TwoParams(FOnTreeStarted, …)` 与第 21 行的静态成员 `OnTreeStarted`；广播点就是本块第 326 行），编辑器调试器就是靠它挂载；运行时代码不应依赖它做游戏逻辑。
- 函数末尾 `RequestExecution(RootNode, ActiveInstanceIdx, RootNode, 0, EBTNodeResult::InProgress)`：以 `InProgress` 而非 `Succeeded` 启动，是因为 `InProgress` 不会被 `RequestExecution` 当成"切换优先级"（`Aborted` 有特殊含义，见 3.4.2 的 `OnTreeFinished` 注释）。

易误解点：`PushInstance` 只压栈、不执行任务；真正的第一次 `ExecuteTask` 发生在下一次 `TickComponent → ProcessExecutionRequest → ProcessPendingExecution`。

#### 3.3.2 执行期回调（UE 4.x 与 5.x 的差异）

```cpp
void UBehaviorTreeComponent::OnTaskFinished(const UBTTaskNode* TaskNode, EBTNodeResult::Type TaskResult)
{
	if (TaskNode == NULL || InstanceStack.Num() == 0 || !IsValidChecked(this))
	{
		return;
	}

	UE_VLOG(GetOwner(), LogBehaviorTree, Log, TEXT("Task %s finished: %s"),
		*UBehaviorTreeTypes::DescribeNodeHelper(TaskNode), *UBehaviorTreeTypes::DescribeNodeResult(TaskResult));

	// notify parent node
	UBTCompositeNode* ParentNode = TaskNode->GetParentNode();
	const int32 TaskInstanceIdx = FindInstanceContainingNode(TaskNode);
	if (!InstanceStack.IsValidIndex(TaskInstanceIdx))
	{
		return;
	}

	uint8* ParentMemory = ParentNode->GetNodeMemory<uint8>(InstanceStack[TaskInstanceIdx]);

	ParentNode->ConditionalNotifyChildExecution(*this, ParentMemory, *TaskNode, TaskResult);

	if (TaskResult != EBTNodeResult::InProgress)
	{
		StoreDebuggerSearchStep(TaskNode, IntCastChecked<uint16>(TaskInstanceIdx), TaskResult);

		// cleanup task observers
		UnregisterMessageObserversFrom(TaskNode);

		// notify task about it
		uint8* TaskMemory = TaskNode->GetNodeMemory<uint8>(InstanceStack[TaskInstanceIdx]);
		TaskNode->WrappedOnTaskFinished(*this, TaskMemory, TaskResult);

		// update execution when active task is finished
		if (InstanceStack.IsValidIndex(ActiveInstanceIdx) && InstanceStack[ActiveInstanceIdx].ActiveNode == TaskNode)
		{
			FBehaviorTreeInstance& ActiveInstance = InstanceStack[ActiveInstanceIdx];
			const bool bWasAborting = (ActiveInstance.ActiveNodeType == EBTActiveNode::AbortingTask);
			ActiveInstance.ActiveNodeType = EBTActiveNode::InactiveTask;

			// request execution from parent
			if (!bWasAborting)
			{
				RequestExecution(TaskResult);
			}
			// schedule an update to process a pending execution when task is done aborting
			else if (PendingExecution.IsSet())
			{
				ScheduleExecutionUpdate();
			}
		}
		else if (TaskResult == EBTNodeResult::Aborted && InstanceStack.IsValidIndex(TaskInstanceIdx) && InstanceStack[TaskInstanceIdx].ActiveNode == TaskNode)
		{
			// active instance may be already changed when getting back from AbortCurrentTask
			// (e.g. new task is higher on stack)

			InstanceStack[TaskInstanceIdx].ActiveNodeType = EBTActiveNode::InactiveTask;
		}
	}

	TrackNewLatentAborts();

	if (TreeStartInfo.HasPendingInitialize())
	{
		ProcessPendingInitialize();
	}
}
```

上面是 `OnTaskFinished` 的完整实现（67 行，未裁剪）——它把文章原先"内部会填充 ExecutionRequest / 调用 SearchAndUpdate 等，节选略"的空白补全为可核对的控制流。要点：

1. **入口守卫**：`TaskNode == NULL || InstanceStack.Num() == 0 || !IsValidChecked(this)` 三者任一成立就返回。第三项是 GC 期间的危险期保护。
2. **通知父复合节点**：`ParentNode->ConditionalNotifyChildExecution(...)`——这是"任务结束后父节点有权改写结果"的唯一机会（例如 `UBTComposite_SimpleParallel` 需要吞掉主任务的结束、`UBTDecorator_ForceSuccess` 需要把 Failed 改写成 Succeeded）。注意 `TaskResult` 是**引用传参**，可被就地修改。
3. **`InProgress` 直接跳过后续**：`if (TaskResult != EBTNodeResult::InProgress)` 之外的代码（注销消息观察者、`WrappedOnTaskFinished`、请求新执行）都不会跑。这就是"多帧任务只 tick 不搜索"的实现方式——`InProgress` 的任务每帧只走 `WrappedTickTask`。
4. **注销消息观察者早于通知任务**（第 544 行在 548 行之前）：先 `UnregisterMessageObserversFrom(TaskNode)` 防止任务在 `OnTaskFinished` 回调里又收到旧消息。
5. **两条分支的关键区别**：若结束的就是当前活动实例的活动节点，则把 `ActiveNodeType` 置为 `InactiveTask`；**若它此前处于 `AbortingTask`（`bWasAborting`），就不再发起新搜索，而是 `ScheduleExecutionUpdate()`**（等中止流程自己收尾）——否则会从中止途中重新发起搜索，导致状态撕裂。
6. **`else if (TaskResult == EBTNodeResult::Aborted && ...)` 那段注释解释了它存在的原因**：从 `AbortCurrentTask` 返回时活动实例可能已经变了（新任务压在更高层），此时只需把**原实例**标记为 `InactiveTask` 即可，不能去改当前活动实例。
7. **函数尾部两件事**：`TrackNewLatentAborts()`（登记新出现的延迟中止）与 `if (TreeStartInfo.HasPendingInitialize()) ProcessPendingInitialize();`——这正是 3.1.2 里"启动请求被挂起"的回收点。

易误解点：任务结果**不直接返回给父节点对象**，而是通过 `RequestExecution(TaskResult)`（第 560 行）把结果写进 `ExecutionRequest`，真正的分支选择发生在此后某次 `TickComponent` 的 `ProcessExecutionRequest`（见 3.6.2）。

任务结果不直接"返回"给父节点对象——它写入 `FBTNodeExecutionInfo`（见 3.5.2），由下一次搜索（`ProcessPendingExecution`）统一处理。

#### 3.5.3 选择子节点的真实逻辑（BTCompositeNode.cpp 节选）

摘自 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BTCompositeNode.cpp`（第 35 行起）

```cpp
int32 UBTCompositeNode::FindChildToExecute(FBehaviorTreeSearchData& SearchData, EBTNodeResult::Type& LastResult) const
{
	FBTCompositeMemory* NodeMemory = GetNodeMemory<FBTCompositeMemory>(SearchData);
	int32 RetIdx = BTSpecialChild::ReturnToParent;

	if (Children.Num())
	{
		int32 ChildIdx = GetNextChild(SearchData, NodeMemory->CurrentChild, LastResult);
		while (Children.IsValidIndex(ChildIdx) && !SearchData.bPostponeSearch)
		{
			// check decorators
			if (DoDecoratorsAllowExecution(SearchData.OwnerComp, SearchData.OwnerComp.ActiveInstanceIdx, ChildIdx))
			{
				OnChildActivation(SearchData, ChildIdx);
				RetIdx = ChildIdx;
				break;
			}
			else
			{
				LastResult = EBTNodeResult::Failed;

				const bool bCanNotify = !bUseDecoratorsFailedActivationCheck || CanNotifyDecoratorsOnFailedActivation(SearchData, ChildIdx, LastResult);
				if (bCanNotify)
				{
					NotifyDecoratorsOnFailedActivation(SearchData, ChildIdx, LastResult);
				}
			}

			ChildIdx = GetNextChild(SearchData, ChildIdx, LastResult);
		}
	}

	return RetIdx;
}
```

上面是 `UBTCompositeNode::FindChildToExecute` 的**完整实现**（34 行，未裁剪）。它推翻了"基类只做默认实现、具体策略全在子类"的简化说法，实际结构是：

（作者绘制：以下为本篇作者整理的调用层级示意，非引擎源码。）
```text
FindChildToExecute（基类，本块）
  ├── GetNextChild(SearchData, CurrentChild, LastResult)   ← 决定"下一个候选是谁"
  │     └── GetNextChildHandler(...)                       ← 子类唯一需要重写的部分
  ├── DoDecoratorsAllowExecution(...)                      ← 装饰器是否放行
  ├── OnChildActivation(...)                               ← 放行则激活该子节点
  └── NotifyDecoratorsOnFailedActivation(...)               ← 不放行则通知"激活失败"
  ```

关键判断为什么这样写：

- **`while` 循环同时受 `SearchData.bPostponeSearch` 约束**：若某次装饰器求值期间外部要求"推迟本次搜索"，循环立刻退出并返回 `BTSpecialChild::ReturnToParent`，而不是继续试探下一个兄弟节点。
- **`CurrentChild` 来自节点内存**（`GetNodeMemory<FBTCompositeMemory>(SearchData)`，`FBTCompositeMemory` 定义在 `BTCompositeNode.h` 第 15 行起，两个 `int8`：`CurrentChild` 与 `OverrideChild`）：这就是"共享模板 + 每实例状态"的最小示例——同一个 Selector 模板给 100 个 AI 用，各自记住"上次试到第几个子节点"。
- **装饰器不通过时把 `LastResult` 改成 `Failed`**（第 54 行）：这是 Sequence 语义的关键——被装饰器挡住的分支对父复合节点而言等于"这个分支失败了"，于是 Sequence 会继续试下一个，Selector 则会返回失败。
- **两条通知路径成对出现**：放行走 `OnChildActivation`；不放行走 `CanNotifyDecoratorsOnFailedActivation` + `NotifyDecoratorsOnFailedActivation`，让装饰器有机会知道"我被求值了但没通过"（用于调试器高亮与自定义反馈）。
- 返回值 `BTSpecialChild::ReturnToParent`（`-2`，定义在 `BehaviorTreeTypes.h` 第 77 行）表示"这个复合节点没有可执行的子节点，把结果交回父节点"。

与相邻阶段衔接：`FindChildToExecute` 返回子节点下标后，由**搜索循环**（`UBehaviorTreeComponent::ProcessExecutionRequest`，见 3.6.2）继续下钻到该子节点，而不是在本函数里递归。

```cpp
bool UBTCompositeNode::DoDecoratorsAllowExecution(UBehaviorTreeComponent& OwnerComp, const int32 InstanceIdx, const int32 ChildIdx) const
{
	ensure(Children.IsValidIndex(ChildIdx));
	if (Children.IsValidIndex(ChildIdx) == false)
	{
		UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Error, TEXT("%s: DoDecoratorsAllowExecution called with ChildIdx = %d which is not a valid child index")
			, *UBehaviorTreeTypes::DescribeNodeHelper(this), ChildIdx);
		return false;
	}

	const FBTCompositeChild& ChildInfo = Children[ChildIdx];
	bool bResult = true;

	if (ChildInfo.Decorators.Num() == 0)
	{
		return bResult;
	}

	FBehaviorTreeInstance& MyInstance = OwnerComp.InstanceStack[InstanceIdx];

	const uint16 InstanceIdxUint16 = IntCastChecked<uint16>(InstanceIdx);

	if (ChildInfo.DecoratorOps.Num() == 0)
	{
		// simple check: all decorators must agree
		for (int32 DecoratorIndex = 0; DecoratorIndex < ChildInfo.Decorators.Num(); DecoratorIndex++)
		{
			const UBTDecorator* TestDecorator = ChildInfo.Decorators[DecoratorIndex];
			const bool bIsAllowed = TestDecorator ? TestDecorator->WrappedCanExecute(OwnerComp, TestDecorator->GetNodeMemory<uint8>(MyInstance)) : false;
			OwnerComp.StoreDebuggerSearchStep(TestDecorator, InstanceIdxUint16, bIsAllowed);

			const UBTNode* ChildNode = GetChildNode(ChildIdx);

			if (!bIsAllowed)
			{
				UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("Child[%d] \"%s\" execution forbidden by %s"),
					ChildIdx, *UBehaviorTreeTypes::DescribeNodeHelper(ChildNode), *UBehaviorTreeTypes::DescribeNodeHelper(TestDecorator));

				bResult = false;
				break;
			}
			else
			{
				UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("Child[%d] \"%s\" execution allowed by %s"),
					ChildIdx, *UBehaviorTreeTypes::DescribeNodeHelper(ChildNode), *UBehaviorTreeTypes::DescribeNodeHelper(TestDecorator));
			}
		}
	}
	else
	{
		// advanced check: follow decorator logic operations (composite decorator on child link)
		UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("Child[%d] execution test with logic operations"), ChildIdx);

		TArray<FOperationStackInfo> OperationStack;
		FString Indent;

		// debugger data collection:
		// - get index of each decorator from main AND test, they will match graph nodes
		// - if first operator is not AND it means, that there's only single composite decorator on line
		// - while updating top level stack, grab index of first failed node

		int32 NodeDecoratorIdx = INDEX_NONE;
		int32 FailedDecoratorIdx = INDEX_NONE;
		bool bShouldStoreNodeIndex = true;

		for (int32 OperationIndex = 0; OperationIndex < ChildInfo.DecoratorOps.Num(); OperationIndex++)
		{
			const FBTDecoratorLogic& DecoratorOp = ChildInfo.DecoratorOps[OperationIndex];
			if (IsLogicOp(DecoratorOp))
			{
				OperationStack.Add(FOperationStackInfo(DecoratorOp));
				Indent += TEXT("  ");
				UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("%spushed %s:%d"), *Indent,
					*DescribeLogicOp(DecoratorOp.Operation), DecoratorOp.Number);
			}
			else if (DecoratorOp.Operation == EBTDecoratorLogic::Test)
			{
				const bool bHasOverride = OperationStack.Num() ? OperationStack.Last().bHasForcedResult : false;
				const bool bCurrentOverride = OperationStack.Num() ? OperationStack.Last().bForcedResult : false;

				// debugger: store first decorator of graph node
				if (bShouldStoreNodeIndex)
				{
					bShouldStoreNodeIndex = false;
					NodeDecoratorIdx = DecoratorOp.Number;
				}

				UBTDecorator* TestDecorator = ChildInfo.Decorators[DecoratorOp.Number];
				const bool bIsAllowed = bHasOverride ? bCurrentOverride : TestDecorator->WrappedCanExecute(OwnerComp, TestDecorator->GetNodeMemory<uint8>(MyInstance));
				UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("%s%s %s: %s"), *Indent,
					bHasOverride ? TEXT("skipping") : TEXT("testing"),
					*UBehaviorTreeTypes::DescribeNodeHelper(TestDecorator),
					bIsAllowed ? TEXT("allowed") : TEXT("forbidden"));

				bResult = UpdateOperationStack(OwnerComp, Indent, OperationStack, bIsAllowed, FailedDecoratorIdx, NodeDecoratorIdx, bShouldStoreNodeIndex);
				if (OperationStack.Num() == 0)
				{
					UE_VLOG(OwnerComp.GetOwner(), LogBehaviorTree, Verbose, TEXT("finished execution test: %s"),
						bResult ? TEXT("allowed") : TEXT("forbidden"));

					OwnerComp.StoreDebuggerSearchStep(ChildInfo.Decorators[FMath::Max(0, FailedDecoratorIdx)], InstanceIdxUint16, bResult);
					break;
				}
			}
		}
	}

	return bResult;
}
```

这段在做什么：`DoDecoratorsAllowExecution` 是"这个子分支能不能进"的唯一判定函数，它有两种走法：

| 走法 | 触发条件 | 语义 |
| --- | --- | --- |
| 简单检查（第 454~479 行） | `ChildInfo.DecoratorOps.Num() == 0` | 所有装饰器**逐一求值，全部为真才放行**（隐式 AND） |
| 高级检查（第 480~537 行） | `DecoratorOps.Num() != 0` | 按逆波兰序列求值，支持 AND / OR / NOT 任意组合 |

高级检查的求值器由一个显式操作数栈 `TArray<FOperationStackInfo> OperationStack` 驱动，规则是：

- 遇到 `And/Or/Not`（`IsLogicOp` 为真）→ 入栈，`NumLeft = DecoratorOp.Number`（该运算符还等着收几个操作数）。
- 遇到 `Test` → 取出 `ChildInfo.Decorators[DecoratorOp.Number]` 求值，把结果喂给栈顶运算符。
- **短路优化写在 `UpdateOperationStack` 里**：`And` 第一次收到 false、`Or` 第一次收到 true 时，把 `bHasForcedResult/bForcedResult` 记下来；此后同层再来的 `Test` **不再调用 `WrappedCanExecute`**（第 520 行 `bHasOverride ? bCurrentOverride : TestDecorator->WrappedCanExecute(...)`），直接复用已知结果——这就是"AND 短路 / OR 短路"实现，按 3.6 节优化装饰器数量时要注意它只作用于同一运算符层内。
- `Not` 就地取反（第 397 行）。
- 栈顶 `NumLeft` 归零 → 弹栈并把结果回填给下一层（第 426 行的**递归调用**），直到栈空，得到最终 `bResult`。

易误解点：

- `bResult` 的初值是 `true`（第 443 行），但**只有 `Decorators.Num() == 0` 时才可能"提前为真"**；有装饰器时最终值一定由 `UpdateOperationStack` 覆盖。
- 调试信息（`FailedDecoratorIdx` / `NodeDecoratorIdx` / `bShouldStoreNodeIndex`）混在同一个循环里，是**为 `StoreDebuggerSearchStep` 服务的**；它们不影响判定结果，只在 `ENABLE_VISUAL_LOG` 下可见失败装饰器。
- 第 460 行与第 520 行都调用 `TestDecorator->GetNodeMemory<uint8>(MyInstance)`：装饰器求值读的是**本实例**的内存，不是模板对象状态。

`DecoratorOps` 里的运算符取值（`Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BTCompositeNode.h`，第 31 行起，本块紧随其后的是完整枚举与 `FBTDecoratorLogic` 结构体）：

上面把 `OnChildActivation` / `OnChildDeactivation` / `OnNodeActivation` / `OnNodeDeactivation` 四个函数的实现**一次性完整给出**（原文只给了四条声明）。请特别注意第 113~114 行的源码注释——它直接纠正了一个常见误解：

> **`OnChildActivation` 不会激活任务的服务。** 源码原文：`// don't activate task services here, it's applied BEFORE aborting (e.g. abort lower pri decorator)` / `// use UBehaviorTreeComponent::ExecuteTask instead`。

因此装饰器 / 服务的启停必须按三个不同入口分别理解：

| 辅助节点位置 | 谁把它加入活动列表 | 时机 |
| --- | --- | --- |
| **复合节点自己的 `Services`** | `UBTCompositeNode::OnNodeActivation` 里 `SearchData.AddUniqueUpdate(..., EBTNodeUpdateMode::Add)` | 执行流进入该复合节点时 |
| **挂在子链接上的 `Decorators`** | `UBTCompositeNode::OnChildActivation` → `NotifyDecoratorsOnActivation` | 该子节点被选中时 |
| **任务节点自己的 `Services`** | `UBehaviorTreeComponent::ExecuteTask` 里 `ActiveInstance.AddToActiveAuxNodes(*this, ServiceNode)` | 任务真正开始执行前（`Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeComponent.cpp`：`ExecuteTask` 定义自第 2456 行起，`AddToActiveAuxNodes` 调用在第 2473 行） |

关键判断为什么这样写：

- **`OnChildActivation` 里"先通知装饰器、后改 `NodeMemory->CurrentChild`"**（第 105~106 行注释原文：`// pass to decorators before changing current child in node memory / so they can access previously executed one if needed`）——装饰器在 `OnBecomeRelevant` 里可能想读"上一个跑过的子节点"，所以更新必须放在通知之后。
- **`OnChildActivation` 不把辅助节点直接塞进 `ActiveAuxNodes`，而是写进 `SearchData.PendingUpdates`**（`AddUniqueUpdate`）。原因写在 `FBehaviorTreeSearchData` 的定义注释里（`BehaviorTreeTypes.h` 第 538~539 行）：`// requested updates of additional nodes (preconditions, services, parallels) / buffered during search to prevent instant add & remove pairs`——**缓冲是为了消掉"刚加又删"的抖动**：一次搜索可能要连续下钻多层，某层加的服务可能马上被下一层拆掉，缓冲后由 `ApplyAllSearchUpdates` 统一结算（`FBehaviorTreeSearchData::AddUniqueUpdate` 的实现见 `Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeTypes.cpp` 第 476 行起，`AssignSearchId` 在同文件第 520 行起）。
- **`OnChildDeactivation` 处理服务、`OnNodeDeactivation` 处理自己的服务**：前者只看"被失活的这个子节点是不是任务"（是任务就 Remove 它的 Services），后者把本复合节点的所有 Services Remove——两处都用 `EBTNodeUpdateMode::Remove`，与激活路径成对。
- **`OnNodeActivation` 的第一行是 `OnNodeRestart(SearchData)`**：每次进入复合节点都先做一次"重启"通知（`OnNodeRestart` 在 `BTCompositeNode.cpp` 第 220 行起，默认实现调 `NotifyNodeRestart`），保证 `bUseNodeActivationNotify` 之外的重启逻辑也能跑。
- **`OnNodeActivation` 里 `Services[i]->NotifyParentActivation(SearchData)` 紧跟在 Add 之后**：服务注册完立刻获得一次"搜索开始"回调，这样"依赖 EQS / 感知结果的装饰器"在被求值前，其同级服务已经刷新过数据。这解释了 3.7 节 `bCallTickOnSearchStart` 为何存在。

易误解点：本块第 126~129 行是 `OnChildDeactivation(const UBTNode&)` 到 `OnChildDeactivation(int32)` 的转发函数（`OnChildDeactivation(SearchData, GetChildIndex(SearchData, ChildNode), NodeResult, bRequestedFromValidInstance);`），原文写「省略第 126~129 行，共 4 行」，但核实后该 4 行**逐字包含在块内**（2026-09-15 更正，假标记已删除）——转发本身只做 `GetChildIndex` 换名。

`OnChildActivation` 是**装饰器/服务启停的总开关**：子分支被选中时，它把该子节点的 Decorators 与 Services 注册为"活动辅助节点"（加入 `FBehaviorTreeInstance::ActiveAuxNodes`），并调用其 `OnBecomeRelevant`；`OnChildDeactivation` 时反向调用 `OnCeaseRelevant` 并注销。这就是"装饰器只在所属分支活动期间生效"的机制来源。

**这解释了为什么"黑板值变化 → 装饰器中止"不会递归爆栈**：搜索过程中拓扑变更被挂起、请求排队，等搜索收尾后统一重放。

流程拆解（对照知识库文章的 Self / Descend / Siblings 中止概念）：

1. **条件翻转的检测**：装饰器通过黑板观察者（见 3.8 节）在"它所观察的黑板键"变化时被唤醒；也可以在 Service 的 `TickNode` 里主动调 `ConditionalFlowAbort`；
2. **Self 中止**（中止自己分支）：`RequestBranchDeactivation(*this)` → 组件沿 `ActiveNodeStack` 找到该装饰器所在分支，对正在运行的任务调用 `WrappedAbortTask`（任务可能返回 `InProgress`，此时进入"延迟中止"等待 `FinishLatentAbort`），分支拆除后重新评估父复合节点；
3. **LowerPriority 中止**（中止低优先级兄弟分支）：搜索从"该装饰器所属复合节点的子节点"开始，把**执行索引大于当前分支**的所有活动任务/子树中止掉，然后重跑父复合节点的 `FindChildToExecute`——被中止的兄弟分支就此让位；
4. **重评估入口**：中止完成后组件发起一次新的受限搜索（`RequestExecution` 系接口），从根重新向下找"现在该跑谁"。`FBehaviorTreeSearchData` 里累积的 `PendingUpdates`（`FBehaviorTreeSearchUpdate`：Add/Remove 辅助节点）由 `ApplySearchUpdates` 统一应用，保证中途增删装饰器/服务不会破坏遍历。

上面是 `ConditionalFlowAbort` 的**完整实现**（33 行）：它只做"翻牌"，不做任何搜索。三处细节值得注意：

- **`FlowAbortMode == None` 直接 return**：这一条就是 FAQ Q3 的第一问的源码依据——装饰器配成 "Nothing" 时，即使手工调 `ConditionalFlowAbort` 也什么都不会发生。
- **`FindInstanceContainingNode(GetParentNode())` 而不是 `...(&RequestedBy)`**：找的是**父复合节点**所在的实例下标。装饰器本身不是实例栈上的节点，它挂在子链接上。
- **`bAlwaysRequestWhenPassing` 的语义**：`RequestMode == EBTDecoratorAbortRequest::ConditionPassing` 表示"条件为真时也要请求一次执行"（用于 `LowerPriority` 装饰器需要主动抢占的场景）；条件为假时无论 RequestMode 如何都走 `RequestBranchDeactivation`。

`EvaluateBranch` 决定"中止范围"的核心映射（`Engine/Source/Runtime/AIModule/Private/BehaviorTree/BehaviorTreeComponent.cpp` 第 922 行起，注释为源码原文）：

- `LowerPriority` → 结果用 `EBTNodeResult::Aborted`，`RequestExecution` 从装饰器父节点出发**向下尝试进入该分支**；

```cpp
				ensureMsgf(!SearchData.DeactivatedBranchStart.IsSet(), TEXT("There should not have more than one deactivated branch. (Previous start:%s, New start:%s"), *SearchData.DeactivatedBranchStart.Describe(), *NewDeactivatedBranchStart.Describe());

				ensureMsgf(!SearchData.DeactivatedBranchEnd.IsSet(), TEXT("There should not have more than one deactivated branch. (Previous end:%s, New end:%s"), *SearchData.DeactivatedBranchEnd.Describe(), *NewDeactivatedBranchEnd.Describe());
				SearchData.DeactivatedBranchEnd = NewDeactivatedBranchEnd;
			}
		}

		FBehaviorTreeInstance& ActiveInstance = InstanceStack[ActiveInstanceIdx];
		const UBTCompositeNode* TestNode = ExecutionRequest.ExecuteNode;
		SearchData.AssignSearchId();
		SearchData.bPostponeSearch = false;
		SearchData.bSearchInProgress = true;

		// activate root node if needed (can't be handled by parent composite...)
		if (ActiveInstance.ActiveNode == NULL)
		{
			ActiveInstance.ActiveNode = InstanceStack[ActiveInstanceIdx].RootNode;
			ActiveInstance.RootNode->OnNodeActivation(SearchData);
			BT_SEARCHLOG(SearchData, Verbose, TEXT("Activated root node: %s"), *UBehaviorTreeTypes::DescribeNodeHelper(ActiveInstance.RootNode));
		}

		// additional operations for restarting:
		if (!ExecutionRequest.bTryNextChild)
		{
			// mark all decorators less important than current search start node for removal
			const FBTNodeIndex DeactivateIdx(ExecutionRequest.SearchStart.InstanceIndex, ExecutionRequest.SearchStart.ExecutionIndex - 1);
			UnregisterAuxNodesUpTo(ExecutionRequest.SearchStart.ExecutionIndex ? DeactivateIdx : ExecutionRequest.SearchStart);

			// reactivate top search node, so it could use search range correctly
			BT_SEARCHLOG(SearchData, Verbose, TEXT("Reactivate node: %s [restart]"), *UBehaviorTreeTypes::DescribeNodeHelper(TestNode));
			ExecutionRequest.ExecuteNode->OnNodeRestart(SearchData);

			SearchData.SearchStart = ExecutionRequest.SearchStart;
			SearchData.SearchEnd = ExecutionRequest.SearchEnd;

			BT_SEARCHLOG(SearchData, Verbose, TEXT("Clamping search range: %s .. %s"),
				*SearchData.SearchStart.Describe(), *SearchData.SearchEnd.Describe());
		}
		else
		{
			// mark all decorators less important than current search start node for removal
			// (keep aux nodes for requesting node since it is higher priority)
			if (ExecutionRequest.ContinueWithResult == EBTNodeResult::Failed)
			{
				BT_SEARCHLOG(SearchData, Verbose, TEXT("Unregistering aux nodes up to %s"), *ExecutionRequest.SearchStart.Describe());
				UnregisterAuxNodesUpTo(ExecutionRequest.SearchStart);
			}
```

关键结论：**"Descend（向下中止子树）"在源码里对应 `RequestBranchDeactivation` 后对活动任务栈的 `WrappedAbortTask` 调用链；"Siblings（中止兄弟）"对应 `EvaluateBranch` 重跑 `FindChildToExecute`**。

这段在做什么：`ProcessExecutionRequest` 是"受限搜索"的唯一执行体，读 `ExecutionRequest`（`FBTNodeExecutionInfo`，见 3.5.2）作为输入，产出 `ActiveInstance.ActiveNode`（新活动任务）或让树跑空。它的流水线是固定的五步：

1. **四道守卫**（第 1956~1986 行）：组件未注册 / 活动实例下标无效 → 返回；`bIsPaused` → 返回（暂停时**丢弃**本次请求，不排队）；`bWaitingForLatentAborts` → 返回（等中止）；`PendingExecution.IsSet()` → 直接转 `ProcessPendingExecution()`；`ExecutionRequest.ExecuteNode == nullptr` → 返回。
2. **记录回滚点**（第 1989~1994 行）：把当前 `ActiveInstanceIdx` 与被停用分支范围存进 `SearchData.Rollback*` 字段，并设置 `SearchData.SearchRootNode`。**这就是"搜索失败可以整体回滚"的支点**（回滚执行体是 `RollbackSearchChanges`，第 2281 行起）。
3. **备份当前实例内存**（第 2010 行 `CopyInstanceMemoryToPersistent()`）：把运行实例内存拷进 `FBehaviorTreeInstanceId::InstanceMemory`（见 3.2 节的双内存表），搜索若回滚就靠它还原。**这一步在任何搜索前都会执行，是行为树每帧的固定开销之一。**
4. **`DeactivateUpTo` + 停用分支范围计算**（第 2013~2040 行）：若当前活动节点不是本次要执行的节点，就沿栈向下拆到 `ExecutionRequest.ExecuteNode`。返回的 `LastDeactivatedChildIndex` 被换算成 `DeactivatedBranchStart/End` 这对 `FBTNodeIndex`（第 2032~2033 行用 `GetChildExecutionIndex(..., EBTChildIndex::FirstNode)` 取分支首节点），后续用来**过滤掉被拆分支在遍历途中发出的新执行请求**（`SearchData.bFilterOutRequestFromDeactivatedBranch`）。这三处 `ensureMsgf` 明确约束"一次搜索最多只能有一个被停用分支"。
5. **设置搜索状态并驱动搜索**（第 2042~2068 行）：`SearchData.AssignSearchId()`（唯一搜索号，用于调试器串联）、`bPostponeSearch = false`、**`bSearchInProgress = true`**（这就是线索表里那个 `bSearchInProgress` 的真实归属：`FBehaviorTreeSearchData` 成员，`BehaviorTreeTypes.h` 第 579 行，不是 `UBehaviorTreeComponent` 的成员）；活动节点为空时先把 `ActiveInstance.ActiveNode` 设为 `RootNode` 并 `OnNodeActivation`（注释原文：`// activate root node if needed (can't be handled by parent composite...)`，因为根节点没有父复合节点替它做激活）。

**`bTryNextChild` 决定搜索方向**，这是理解"任务结束"与"装饰器重启"两条路径差别的关键：

| `ExecutionRequest.bTryNextChild` | 场景 | 搜索范围 | 辅助节点处理 |
| --- | --- | --- | --- |
| 真（默认，任务正常结束） | 父节点选下一个子节点 | `SearchStart` 之后 | 仅在 `ContinueWithResult == Failed` 时 `UnregisterAuxNodesUpTo(SearchStart)`（保留请求方自己，因为它优先级更高） |
| 假（`bIsRestart`，装饰器触发） | 重新评估一个分支 | 严格限制在 `ExecutionRequest.SearchStart..SearchEnd`（第 2067~2068 行） | 先 `UnregisterAuxNodesUpTo(SearchStart - 1)` 把"比搜索起点更不重要"的辅助节点全部标记移除，再 `ExecuteNode->OnNodeRestart(SearchData)` 让复合节点可以重置自己的 `CurrentChild` |

易误解点：**搜索不是从根开始的**。`SearchData.SearchStart/SearchEnd` 把它限制在 `ExecutionRequest.ExecuteNode` 之下的一段（`EBTFNodeIndexRange`），`UBTCompositeNode::GetMatchingChildIndex`（`BTCompositeNode.cpp` 第 542 行起）负责把"搜索起点"换算成"该走哪个子节点"。源码里的 VLOG 也直接叫它 `Clamping search range`（第 2070 行）。本文 3.5.3 的流程图里"从根重新向下找"是不准确的表述：**重评的入口是装饰器父节点，不是根。**

服务与任务 Tick 的区别：

- 任务 `TickTask` 只在自己是 `ActiveNode` 时被 tick（帧级）；服务 `TickNode` 按 `Interval +/- RandomDeviation` 的**周期**触发，且服务在分支活动期间一直有效；
- `WrappedTickNode` 内部先检查「距上次 Tick 是否已过 Interval」，未到期直接返回 false，从而支持「比帧率更低频」的服务；
- `bCallTickOnSearchStart`：每次搜索命中该分支时立即补一次 Tick（常用于"进分支先刷新一次目标位置"）；
- `NotifyParentActivation` / `OnSearchStart`：搜索命中该分支时由组件调用，真实实现见下块（`Engine/Source/Runtime/AIModule/Private/BehaviorTree/BTService.cpp` 第 34~66 行）——`bNotifyOnSearch` 为真才调 `OnSearchStart`，`bCallTickOnSearchStart` 为真才额外补一次 `TickNode`，`bRestartTimerOnEachActivation` 为真则重新计时；

```cpp
		auto KeyID = BlackboardKey.GetSelectedKeyID();
		BlackboardComp->RegisterObserver(KeyID, this, FOnBlackboardChangeNotification::CreateUObject(this, &UBTDecorator_BlackboardBase::OnBlackboardKeyValueChange));
	}
}

void UBTDecorator_BlackboardBase::OnCeaseRelevant(UBehaviorTreeComponent& OwnerComp, uint8* NodeMemory)
{
	UBlackboardComponent* BlackboardComp = OwnerComp.GetBlackboardComponent();
	if (BlackboardComp)
	{
		BlackboardComp->UnregisterObserversFrom(this);
	}
}

EBlackboardNotificationResult UBTDecorator_BlackboardBase::OnBlackboardKeyValueChange(const UBlackboardComponent& Blackboard, FBlackboard::FKey ChangedKeyID)
{
	UBehaviorTreeComponent* BehaviorComp = (UBehaviorTreeComponent*)Blackboard.GetBrainComponent();
	if (BehaviorComp == nullptr)
	{
		return EBlackboardNotificationResult::RemoveObserver;
	}

	if (BlackboardKey.GetSelectedKeyID() == ChangedKeyID)
	{
		BehaviorComp->RequestExecution(this);
	}
	return EBlackboardNotificationResult::ContinueObserving;
}
```

## 六、常见问题 FAQ

### Q1：`ExecuteTask` 返回 `InProgress` 后没调用 `FinishLatentTask`，会怎样？

任务永远占着 `FBehaviorTreeInstance::ActiveNode`，树被"卡死"：后续搜索无法切换到其他分支（`GetActiveNode` 始终指向它），中止也会一直等 `FinishLatentAbort`。调试时用 Behavior Tree Debugger 看"当前活动节点"即可定位。

### Q2：装饰器"中止自己分支"（Self）和"中止低优先级"（LowerPriority）有什么区别？

Self 中止的是装饰器**所在分支**（包括它自己挂载的节点树）；LowerPriority 中止的是父复合节点中**执行顺序在其后**的兄弟分支。对应源码 `RequestBranchDeactivation`（拆自己分支）与 `EvaluateBranch` 重跑 `FindChildToExecute`（让位给更高优先级分支）。

### Q3：为什么装饰器条件变了，任务却没有被中止？

查三件事：(1) `FlowAbortMode` 是否设置（`None` 只做执行条件、不中止）；(2) 装饰器是否**选了有效的黑板键**且键名正确——**5.8 没有 `bUseBlackboardKey` 成员**（`Engine/Source` 全树 `rg -n 'bUseBlackboardKey'` **0 命中**）；真实载体是装饰器上的 `BlackboardKey`，类型 `FBlackboardKeySelector`（`Engine/Source/Runtime/AIModule/Classes/BehaviorTree/BehaviorTreeTypes.h` 第 623 行），键名字段 `SelectedKeyName`（第 637 行），运行时由 `GetSelectedKeyID()`（第 661 行）解析；观察者只对已注册的键生效；(3) 键类型是否与写入类型一致（类型不符时 `SetValue` 直接失败）。

### Q4：蓝图自定义节点报"Access None"或内存错乱，最常见原因？

在 `bCreateNodeInstance = false`（默认模板共享）的节点里把运行状态写进了节点 UPROPERTY。正确做法：重写 `GetInstanceMemorySize()`，用 `GetNodeMemory<FMyMemory>()` 保存状态，并遵守"回调函数视为 const"的约定（BTTaskNode.h 注释明确写了这一点）。

### Q5：Service 的 Interval 设 0.5，为什么有时候"不按 0.5 秒"触发？

两个原因：(1) `RandomDeviation` 会给 Interval 加随机抖动（用于错开多个 AI 的 Tick 峰）；(2) 服务只在所属分支活动期间计数，且搜索命中时 `bCallTickOnSearchStart` 会额外补一次。（2026-09-15 补源码依据：下一次 tick 时间由 `UBTService::ScheduleNextTick` 用 `FMath::FRandRange(FMath::Max(0.0f, Interval - RandomDeviation), (Interval + RandomDeviation))` 抽出——`Engine/Source/Runtime/AIModule/Private/BehaviorTree/BTService.cpp` 第 105~107 行；默认值 `Interval = 0.5f`、`RandomDeviation = 0.1f` 来自构造函数，同文件第 20~21 行。）

### Q6：UE4 项目的 `SetNextBranch` 在 UE5 里怎么找不到了？

UE 5.0 重构了执行引擎：`SetNextBranch` 被 `FBTNodeExecutionInfo` + `FBehaviorTreeSearchData` 搜索模型取代（见 3.5.2）。行为语义不变：任务结束 → 父复合节点选下一个子节点。业务侧自定义节点无需改动，只有深度定制引擎的代码需要迁移。

### Q7：`StartTree` 与网上资料常说的 `ExecuteTree` 是什么关系？

`ExecuteTree(UBehaviorTree& InAsset, UBTNode* InRootOverride)` 不是 UE 官方 API：5.8 的 AIModule 源码中不存在该方法，自 UE4 起行为树启动入口一直是 `StartTree(UBehaviorTree& Asset, EBTExecutionMode::Type ExecuteMode)`（5.8 中重启用 `RestartTree(EBTRestartMode RestartMode = EBTRestartMode::ForceReevaluateRootNode)`）。看到旧教程写 `ExecuteTree` 时，直接按 `StartTree` 理解即可。
