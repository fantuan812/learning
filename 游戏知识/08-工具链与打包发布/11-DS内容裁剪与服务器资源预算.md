# DS 内容裁剪与服务器资源预算

> 以本机 UE5.8 编译方向与 Cook 语义为边界，说明 Dedicated Server 如何裁剪渲染/音频内容、控制加载集合与内存预算。

## 元数据

- 版本基线：UE5.8.0 / CL55116800 / ++UE5+Release-5.8
- 适用范围：Dedicated Server 的 Cook 内容策略、服务器加载集合、无渲染/无音频运行、World Partition/Level Streaming 服务器行为与内存预算。
- 事实边界：编译定义与 Cook 语义以本机 UE5.8 源码和既有构建专题为证据；平台数据、质量等级、资产标记与加载策略均为项目方案。
- 事实边界：本文不声称项目存在某个资产标记、平台扩展或加载脚本；所有 `<...>` 名称与路径都是占位符。
- 官方参考：https://dev.epicgames.com/documentation/en-us/unreal-engine
- 最后更新：2026-08-07

## 概述

Dedicated Server 不需要渲染、不需要音频、不需要客户端 UI，但它仍然需要玩法逻辑、
物理、AI、寻路、动画骨架（供逻辑判断）与游戏状态相关的资产。
内容裁剪（Content Trimming）的目标是：服务器只加载"玩法所需"的资源，
避免把客户端资源、材质、贴图、VFX 与音频一起加载，从而降低内存、磁盘与启动成本。

裁剪有三个层次：
编译层（`UE_SERVER`/`USE_NULL_RHI` 等定义决定代码形态）、
Cook 层（服务器 Cook 产物只包含所需资源）、
运行层（加载策略、World Partition/流送行为、平台数据选择）。

裁剪不是"能省就省"，而是"以玩法闭环为准"：
任何裁剪都必须经过功能验收，防止"服务器不加载某资产导致玩法缺失"。

## 3. 编译层：服务器代码形态

### 3.1 已核对定义

既有构建专题已核对：

- `TargetType.Server` 是 Cooked monolithic server 目标语义。
- Server 分支写入 `UE_SERVER=1` 与 `USE_NULL_RHI=1`。
- `WITH_SERVER_CODE`/`WITH_CLIENT_CODE` 由 `bWithServerCode`/`bWithClientCode` 决定。
- Game/Client/Server 默认 `bBuildRequiresCookedData` 为真。

这些定义决定"服务器二进制里编译了什么"，不决定"运行时加载什么"。
代码层用 `UE_SERVER` 等宏隔离客户端专属逻辑，资源层用 Cook 与加载策略控制内容。

### 3.2 代码裁剪的边界

```cpp
// 方案示意：用服务器编译定义隔离客户端专属逻辑。
#if UE_SERVER
    // 服务器侧逻辑：权威校验、AI、结算
#else
    // 客户端侧逻辑：输入、渲染反馈、UI
#endif
```

不要把业务逻辑整个包在 `UE_SERVER` 里，只隔离真正平台专属的路径。
玩法规则必须服务器可执行，裁剪的是表现与交互层。

## 4. Cook 层：服务器内容集合

### 4.1 服务器 Cook 的目标

服务器 Cook 产物应满足：启动、地图加载、AI/物理/逻辑依赖、登录与最小玩法闭环。
不需要：材质贴图（非逻辑）、VFX 特效、音频资产、客户端 UI 资源。

```text
服务器需要（示意）：
  - 玩法蓝图/数据资产（规则、配置、掉落、任务）
  - 物理资产（碰撞、物理材质）
  - AI 资产（行为树、黑板、NavMesh 数据）
  - 动画骨架/姿态（逻辑判断需要时）
  - 地图与关卡数据

服务器通常不需要（示意）：
  - 贴图与材质（渲染相关）
  - 音频文件与衰减配置
  - VFX/Niagara 特效资产
  - 客户端 UI 资源
```

具体需要与否以玩法实现为准：如果玩法用动画通知做判定，动画资产就是服务器依赖。

### 4.2 Cook 验证

服务器 Cook 的验收不能只看构建成功：

1. Stage 产物自洽，启动无缺失资产错误。
2. 目标地图与依赖全部进入 Cook。
3. 服务器能完成登录冒烟与最小玩法闭环。
4. 缺失资产有明确日志与失败分类。

```powershell
# 方案示意：验证 Stage 关键产物。
Test-Path -LiteralPath '<StageDir>\<ProjectServer>Server' -ErrorAction SilentlyContinue
Get-ChildItem -LiteralPath '<StageDir>' -Recurse -File | Select-Object FullName, Length
```

## 5. 运行层：加载策略与内存

### 5.1 服务器内存构成

```text
服务器内存 = 引擎与模块 + 地图数据 + 玩法对象 + AI/物理数据 + 连接与复制 + 缓存与日志
```

内存预算要按构成拆分监控，而不是只看总内存：

| 构成 | 常见增长源 | 监控方式 |
| --- | --- | --- |
| 玩法对象 | 实体数、组件、状态 | 对象计数 |
| AI/物理 | 行为树实例、物理体 | 场景统计 |
| 连接与复制 | 连接数、复制对象 | 连接计数、复制统计 |
| 缓存 | 资源缓存、日志缓冲 | 缓存命中与上限 |
| 日志 | 滚动日志、Trace | 日志大小与保留 |

### 5.2 加载策略

服务器加载策略包括：

1. 启动加载最小集合（玩法必需）。
2. 地图加载按 World Partition/流送规则。
3. 按需加载业务资产（任务、活动、模式）。
4. 上限与释放策略（缓存、日志、Trace）。

```text
加载分级示意（项目方案）：
  P0 启动必需：引擎、玩法框架、核心数据
  P1 地图依赖：当前地图与逻辑资产
  P2 按需加载：活动、模式、扩展内容
  P3 不加载：渲染、音频、UI、VFX（除非逻辑依赖）
```

## 6. World Partition 与流送

World Partition 与 Level Streaming 在服务器上的行为可能与客户端不同：
服务器不需要渲染流送，但需要玩法相关的分区加载与卸载。

服务器流送关注：

- 玩家所在分区与邻近分区的逻辑实体是否加载。
- 卸载分区时玩法状态（任务、事件）是否保留或迁移。
- 流送风暴对 Tick 与内存的冲击。

```text
服务器流送验收示意：
  - 玩家跨分区时逻辑实体正确加载/卸载
  - 分区卸载不丢失任务与事件状态
  - 流送峰值在 Tick 与内存预算内
```

具体配置以项目地图与玩法为准，本文只给验收维度。

## 7. 平台数据与质量等级

平台数据（Platform Data）与质量等级是内容变体机制，不是服务器裁剪的专用开关。
服务器可以使用平台标记选择"服务器变体"资产，但：

1. 平台标记的选择逻辑必须经过验证，不能依赖"默认就是对的"。
2. 质量等级用于渲染降级，服务器大多不适用，但逻辑资产变体要明确。
3. 变体选择错误会造成服务器与客户端使用不同数据，玩法不一致。

```text
变体验证示意：
  - 服务器与客户端使用同一规则数据的同一版本
  - 平台变体差异有清单与验收
  - 新增变体必须覆盖服务器路径测试
```

## 8. 裁剪与玩法一致性的风险

| 风险 | 示例 | 控制 |
| --- | --- | --- |
| 逻辑依赖被裁 | 动画通知驱动判定，动画被裁 | 依赖清单与启动验收 |
| 数据版本不一致 | 服务器/客户端不同平台变体 | 变体清单与一致性测试 |
| 流送状态丢失 | 分区卸载丢任务 | 状态保留设计 |
| 内存预算失控 | 缓存无上限 | 缓存上限与监控 |
| 裁剪后不可复现 | 缺失资产日志不足 | 结构化缺失日志 |

### 8.1 裁剪变更流程

内容裁剪不是一次性动作，每次裁剪变更都应走固定流程：

1. 列出拟裁剪资产与理由（哪类、为什么、玩法是否依赖）。
2. 用依赖扫描与启动日志确认隐式依赖。
3. 在测试环境完成服务器启动冒烟与最小玩法闭环。
4. 跑双客户端联机 E2E 与容量基线对比。
5. 记录裁剪前后内存、启动耗时与缺失资产数量。
6. 变更进入构建记录与发布门禁，可回滚。

裁剪记录示例：

```text
裁剪变更记录：
  buildId: <build-id>
  removed: <asset-category / count>
  rationale: <玩法不依赖 / 渲染专属>
  verified: <启动冒烟 / E2E / 容量基线>
  memoryBefore -> After: <mb> -> <mb>
```

## 9. 验证与门禁

### 9.1 服务器内容验收清单

- [ ] 服务器启动无缺失资产错误。
- [ ] 目标地图与玩法依赖全部加载。
- [ ] 登录冒烟与最小玩法闭环通过。
- [ ] AI/物理/结算等权威路径使用服务器数据。
- [ ] 渲染/音频/UI 资产未进入服务器加载集合。
- [ ] 内存构成有基线、有监控、有上限。
- [ ] 流送与分区行为在预算内。
- [ ] 裁剪变更经过完整联机验收。

### 9.2 回归

内容裁剪的回归与联机验收绑定：
每次裁剪变更后，重跑启动冒烟、双客户端 E2E 与容量基线。

## 10. 失败路径

| 症状 | 优先检查 | 处置方向 |
| --- | --- | --- |
| 启动缺失资产 | Cook 集合与隐式依赖 | 补依赖并重 Cook |
| 玩法判定缺失 | 逻辑依赖被裁 | 恢复依赖并加清单 |
| 内存超预算 | 加载集合与缓存 | 裁剪与上限 |
| 流送丢状态 | 分区卸载逻辑 | 状态保留设计 |
| 数据不一致 | 平台变体 | 统一版本与清单 |

## 11. 最佳实践

### 实践 1：以玩法闭环为准

裁剪标准是"玩法闭环所需"，不是"能省就省"。

### 实践 2：三层分离

编译层管代码形态，Cook 层管内容集合，运行层管加载与内存，三层分别验证。

### 实践 3：依赖清单化

服务器依赖资产有清单，新增玩法依赖时同步更新清单与验收。

### 实践 4：内存按构成监控

总内存之外，对象数、连接、缓存与日志分别监控。

### 实践 5：裁剪与验收绑定

每次裁剪变更都过启动冒烟、联机 E2E 与容量基线。

### 实践 6：渲染/音频资产默认不进服务器

除非玩法逻辑依赖，否则渲染、音频、UI、VFX 不进服务器加载集合。

## 12. 常见问题 FAQ

### Q1：服务器完全不加载贴图材质吗？

默认方向是服务器不加载渲染资产，但如果玩法逻辑引用了它们（如数据驱动配置），
依赖仍会进入加载集合。以实际依赖为准。

### Q2：`USE_NULL_RHI` 是不是就是"没有 GPU"？

它是服务器不初始化渲染设备的编译方向之一，不代表所有资源加载都被跳过。

### Q3：质量等级能用于服务器裁剪吗？

质量等级是渲染降级机制，服务器裁剪应使用明确的平台标记与加载策略，并做一致性验证。

### Q4：World Partition 在服务器上怎么加载？

服务器按玩法需要加载分区，行为与客户端可能不同，要单独验收逻辑实体与状态保留。

### Q5：怎么发现隐式依赖？

通过启动日志、缺失资产报告与加载追踪定位，依赖清单持续维护。

### Q6：裁剪后客户端与服务器数据不一致怎么办？

统一数据版本与平台变体清单，服务器路径纳入一致性测试。
