# 06 · UI 状态与可观测性闭环

> 版本基准：UE 5.8.0（本机 Engine/Build/Build.version：CL 55116800，分支 ++UE5+Release-5.8）。
> 基线摘要：UE5.8.0 / CL55116800 / ++UE5+Release-5.8。
> 源码依据：本机只读 UE 5.8 源码，重点核对 CommonUI、ModelViewViewModel、Enhanced Input、TraceLog、TraceServices 与 TraceInsights。
> 适用范围：桌面、主机、移动客户端的运行时 UI；适用于单人和多人客户端的本地玩家界面，覆盖编辑器开发、Development/测试包和受控 Shipping 采集。
> 兼容性边界：UE 4.27 与 UE 5.0–5.7 只作为迁移背景；CommonUI 激活树、UMG MVVM 绑定执行、Enhanced Input 资源和 Trace 事件以 UE 5.8 为当前基准，UMG Viewmodel 的 Beta/插件边界必须由项目实际启用状态确认。
> 官方参考：[UE 5.8 官方文档](https://dev.epicgames.com/documentation/en-us/unreal-engine)。
> 最后更新：2026-08-06（新增 CommonUI、UMG MVVM、Enhanced Input 与 Unreal Insights/Trace 的状态、输入、数据和验收闭环）。

## 1. 概述

UI 卡顿、按键穿透、手柄焦点丢失、界面显示旧数据，通常不是某一个 Widget 的孤立缺陷。

它们往往来自四条没有对齐的生命周期。

第一条是页面激活生命周期：页面何时进入激活栈，何时成为 Active Leaf，何时退出。

第二条是输入生命周期：哪个 LocalPlayer 接收输入，哪个 Action Domain 先匹配，哪个 Mapping Context 当前有效。

第三条是数据生命周期：ViewModel 何时创建、绑定、刷新、失效和销毁。

第四条是证据生命周期：事件何时产生，Trace 如何采集，Insights 会话如何分析，以及结论如何进入自动化验收。

本专题把这四条线收敛为一个可执行闭环。

闭环的最小目标不是“界面能显示”。

闭环的目标是：一次用户意图能够被正确的本地玩家接收，被当前激活页面消费，驱动可验证的 ViewModel 变更，在预算内完成渲染，并留下可以在 Unreal Insights 中重建的证据。

### 1.1 读者与场景

本文面向负责 UI 框架、CommonUI 页面、UMG MVVM、输入整合、性能治理和客户端测试的开发者。

典型场景包括大厅页面、背包、商城、任务面板、设置页、确认弹窗、断线重连提示和多人分屏 UI。

如果只需要学习 UMG 控件树，请先阅读本分类的 UMG 基础文档。

如果只需要学习属性绑定或 ViewModel 建立，请先阅读本分类的 MVVM 文档。

如果问题是整帧卡顿或 GPU 开销，应把本专题与 Profiling 和渲染加载专题一起使用。

### 1.2 本文的验收定义

一个 UI 状态闭环至少要能回答以下问题。

| 问题 | 必须能定位的证据 |
| --- | --- |
| 页面是否真的激活 | PageId、ActivationSerial、ActiveRoot、ActiveLeaf |
| 输入由谁消费 | LocalPlayerIndex、PlatformUserId、InputDevice、ActionId、RouteResult |
| 焦点是否稳定 | FocusedWidgetId、DesiredFocusId、FocusRestored |
| 数据是否新鲜 | ViewModelId、DataRevision、RequestId、AppliedRevision |
| 是否发生竞争 | SourceRevision、Generation、DiscardReason、Thread |
| 是否超预算 | OpenDurationMs、BindingCostUs、FocusCostUs、SlateCostUs |
| Trace 是否可分析 | TraceChannel、SessionId、ScenarioId、事件时间窗 |
| Shipping 是否合规 | BuildConfiguration、CaptureEnabled、SensitiveFieldPolicy |

### 1.3 先确定问题属于哪一层

“按钮没有反应”不等于“按钮事件没有绑定”。

“界面显示旧数据”不等于“网络数据没有到达”。

“打开页面卡顿”不等于“UMG 本身很慢”。

排查时先把故障归类到状态、输入、数据、线程或观测层，再看对应证据。

| 现象 | 第一检查点 | 第二检查点 |
| --- | --- | --- |
| 页面可见但不响应 | CommonUI 激活状态 | Action Domain 与焦点 |
| 手柄按键落到玩法层 | Router 的 RouteResult | Mapping Context 优先级 |
| 弹窗关闭后焦点漂移 | Desired Focus | Focus Restoration Target |
| 文本偶尔回退 | DataRevision | 异步结果的 Generation |
| 首次打开尖峰 | 激活耗时事件 | 资源加载和绑定执行 |
| Insights 没有事件 | Trace Channel | Shipping 编译门控 |
| 多人分屏互相抢输入 | LocalPlayer 归属 | Platform User 映射 |
| 自动化偶发失败 | ScenarioId 与时间窗 | 是否等待状态稳定 |

## 2. 总体闭环模型

### 2.1 四条生命周期线

页面状态不是 Visibility 的别名。

输入状态不是 Enhanced Input 映射的别名。

数据状态也不是某个 UObject 当前字段值的别名。

每条线都应该有明确的开始、进行中、成功、失败、取消和清理。

| 线 | 开始 | 进行中 | 成功 | 失败/取消 | 清理 |
| --- | --- | --- | --- | --- | --- |
| 页面 | 请求 Push | Activating | Active | Rejected/Failed | Deactivating/Removed |
| 输入 | 添加 Context | Router 查找 | Consumed | Unhandled/Blocked | 移除 Context |
| 数据 | 创建 Request | Loading/Binding | Applied | Stale/Error | 解绑 delegate |
| 观测 | Start Trace | Emit/Scope | Session Ready | Dropped/Unavailable | Stop/Flush |

### 2.2 Mermaid：从意图到证据

~~~mermaid
flowchart LR
    A["用户意图"] --> B["LocalPlayer 输入入口"]
    B --> C{"CommonUI Active Root/Leaf"}
    C -->|拒绝或未激活| X["失败事件与回退"]
    C -->|动作匹配| D["Action Domain 与 Binding"]
    D --> E["Enhanced Input Context"]
    E --> F["页面命令"]
    F --> G["ViewModel 写入"]
    G --> H["FieldNotify / Binding"]
    H --> I["UMG/Slate 更新"]
    I --> J["性能 Scope 与状态事件"]
    J --> K["Trace 缓冲"]
    K --> L[".utrace / Insights Session"]
    L --> M["Timing、事件、验收结论"]
    X --> M
~~~

图中的箭头代表责任边界，不代表所有调用都同步完成。

异步加载或网络返回可以在 G 之前停留较长时间，但结果必须携带可比较的版本信息。

Trace 是证据层，不应反过来改变页面状态。

### 2.3 闭环的最小合同

每个可观测页面都定义一个 Page Contract。

Contract 至少包含稳定的 PageId、输入策略、ViewModel 来源、预算、失败策略和观测字段。

PageId 不应直接使用临时 Widget 指针地址。

输入策略要声明是否阻断玩法层、是否需要手柄焦点、是否需要鼠标捕获。

ViewModel 来源要声明是页面私有、LocalPlayer 共享还是跨页面只读。

失败策略要说明展示错误、保留旧数据、重试、返回上一级还是安全关闭。

预算要拆成首次打开、重复打开、交互帧和持续刷新四类。

观测字段要避免玩家隐私、聊天正文、账号令牌和完整业务 payload。

## 3. 核心概念

### 3.1 术语表

| 中文 | 英文 | 责任 | 不负责什么 |
| --- | --- | --- | --- |
| 激活栈 | Activation Stack | 管理页面的进入、退出和当前叶节点 | 不负责网络同步 |
| 激活树 | Activatable Tree | 让页面层级参与 CommonUI 路由 | 不等同于 Slate Widget Path |
| 输入路由器 | Action Router | 按 LocalPlayer 分发 UI 输入 | 不替代 Enhanced Input 资源 |
| 输入域 | Action Domain | 限制动作查找范围 | 不决定所有鼠标命中 |
| 焦点恢复 | Focus Restoration | 页面切换后恢复可交互控件 | 不保证目标永远存在 |
| 本地玩家 | LocalPlayer | 隔离用户、输入、焦点和子系统 | 不代表服务器玩家状态 |
| 映射上下文 | Mapping Context | 定义 InputAction 到按键的映射 | 不决定 UI 是否消费 |
| ViewModel | ViewModel | 暴露 UI 可读写的字段和命令 | 不应直接持有 Widget 树 |
| 字段通知 | FieldNotify | 精确通知绑定字段发生改变 | 不自动解决线程安全 |
| 绑定执行 | Binding Execution | 把源字段写入目标属性 | 不保证数据来源永远有效 |
| 数据代数 | Data Revision | 判断结果新旧 | 不替代服务器权威校验 |
| 生成号 | Generation | 使旧异步任务结果失效 | 不会自动取消后台任务 |
| 事件 | Trace Event | 提供可过滤的离散状态证据 | 不代替日志全文 |
| Timing Scope | Timing Scope | 提供连续耗时和嵌套关系 | 不说明业务语义的全部细节 |
| 分析会话 | Analysis Session | 读取并组织 Trace Provider | 不修改原始 Trace |
| 性能预算 | Performance Budget | 把耗时转为可验收阈值 | 不保证所有平台相同 |

### 3.2 状态集合

建议为页面定义有限状态机，而不是在多个 Bool 之间推断状态。

~~~text
Closed
  -> Requested
  -> Loading
  -> Activating
  -> Active
  -> Deactivating
  -> Closed

Loading -> Error
Error -> RetryPending
RetryPending -> Loading
Requested -> Cancelled
Activating -> Failed
Active -> Suspended
Suspended -> Active
~~~

上面的状态是产品语义状态，不要求一一映射到 UUserWidget 的全部生命周期回调。

特别要区分 Constructed、Activated 和 Visible。

一个 Widget 可以已经 Constructed 但尚未 Activated。

一个页面也可能保持 Visible，却已经 Suspended，不应再消费页面动作。

### 3.3 状态转移不变量

状态转移需要可以写成断言。

任何从 Closed 直接写入 Active 的路径都必须说明跳过了哪些加载和激活步骤。

同一个 RequestId 只能产生一次最终 Applied 或一次最终 Discarded。

Deactivate 之后不得出现新的页面动作消费。

旧 Generation 的数据不得覆盖新 Generation。

LocalPlayer A 产生的焦点和映射不得写入 LocalPlayer B。

Trace 事件里的 PageId 必须能在测试结果中还原到一个页面合同。

### 3.4 Mermaid：状态机

~~~mermaid
stateDiagram-v2
    [*] --> Closed
    Closed --> Requested: RequestOpen
    Requested --> Loading: AssetReady=false
    Requested --> Activating: AssetReady=true
    Loading --> Activating: LoadSuccess
    Loading --> Error: LoadFailed
    Error --> Loading: Retry
    Requested --> Cancelled: UserCancel
    Activating --> Active: ActivateSuccess
    Activating --> Failed: ActivateFailed
    Active --> Suspended: PushModal
    Suspended --> Active: ModalClosed
    Active --> Deactivating: RequestClose
    Suspended --> Deactivating: ParentClose
    Deactivating --> Closed: CleanupDone
    Failed --> Closed: RollbackDone
    Cancelled --> Closed: CancelCleanup
~~~

每条转移都应产生一个状态事件。

状态事件不需要记录完整对象内容，但需要记录 FromState、ToState、Reason 和序列号。

## 4. CommonUI：激活栈、输入路由与焦点

### 4.1 责任分层

CommonUI 建立在 UMG/Slate 之上，解决的是跨设备页面激活、输入消费和焦点协作。

UCommonActivatableWidget 是页面级激活语义的主要入口。

UCommonUIActionRouterBase 是 LocalPlayer 级别的输入路由器。

CommonActivatableWidgetContainer 相关容器承担页面堆栈、切换或队列的组织。

Slate Widget Path 负责视觉焦点和导航路径。

FActivatableTreeNode 语义树负责 CommonUI 的激活和输入范围。

这两棵树有关联，但不能互相替代。

只调用 SetVisibility 不会自动注册激活节点、刷新 InputConfig、建立焦点恢复目标或清除页面映射。

### 4.2 激活栈的进入合同

Push 页面前，调用方必须确定页面所属 LocalPlayer。

如果页面需要异步资源，先进入 Loading 并产生 RequestId。

资源就绪后再创建或取得页面实例，避免半初始化页面进入 Active Root。

调用 ActivateWidget 后，等待激活回调或项目的状态通知确认。

激活成功后再添加页面专属 Enhanced Input Mapping Context。

确认 Desired Focus 目标已构建，再请求焦点刷新。

最终状态设为 Active，并发出 PageActivated 事件。

激活失败必须回滚已添加的 Context、delegate 和临时引用。

### 4.3 停用合同

Close 页面时先阻止新的页面命令。

进入 Deactivating 后停止接受重复的 Open、Back 和 Submit。

调用 DeactivateWidget，等待页面停用回调。

移除页面专属 Mapping Context，保证隐藏页面不再响应。

清理焦点恢复目标，避免指向已销毁 Widget。

解除 ViewModel、网络请求和异步任务的回调归属。

发出 PageDeactivated 事件后，才允许回到 Closed。

### 4.4 输入路由顺序

一个实用的路由顺序如下。

第一步，平台输入进入 Slate/CommonInput 的输入前置处理。

第二步，按 PlatformUser 或设备归属找到目标 LocalPlayer。

第三步，UCommonUIActionRouterBase 读取当前 Active Root 和 Active Leaf。

第四步，按 Action Domain、Binding Priority 和页面输入配置筛选候选动作。

第五步，匹配 UI Action Binding 或页面命令。

第六步，记录 RouteResult，并决定是否继续给玩法层。

第七步，若 UI 未消费且策略允许，才让普通玩法输入继续。

PageId、LocalPlayerIndex 和 RouteResult 必须在同一个事件上下文中关联。

### 4.5 输入结果分类

项目应把引擎的输入结果映射为稳定的诊断枚举。

| 结果 | 说明 | 典型处理 |
| --- | --- | --- |
| Consumed | 页面动作已处理 | 不继续给玩法层 |
| HandledNoCommand | UI 层识别到输入但没有业务命令 | 记录绑定缺失 |
| Unhandled | 当前 UI 没有消费 | 按 InputConfig 决定是否放行 |
| BlockedByModal | 模态页面阻断了父页面 | 检查 Active Leaf |
| NoLocalPlayer | 设备无法归属本地玩家 | 记录设备和用户映射 |
| NoFocus | 需要焦点但没有有效目标 | 触发焦点恢复或失败 |
| StalePage | 路由命中旧页面 | 丢弃并记录序列号 |

不要用一个 bool 表达所有未响应原因。

### 4.6 焦点是独立状态

焦点目标应是页面合同的一部分。

Desired Focus 可以是默认按钮、列表第一项、上一次合法选中项或恢复策略计算出的控件。

目标必须在当前 Widget Tree 中、可见、可聚焦且没有被禁用。

页面重建、列表刷新、分辨率切换和 Modal 关闭后，旧 Slate Widget Path 可能失效。

此时先验证目标，再请求焦点刷新，不要强行向旧路径发送输入。

焦点恢复成功时记录 DesiredFocusId、ActualFocusId 和 FocusRestored。

焦点恢复失败时记录 FocusFailureReason，例如 Missing、NotFocusable、Hidden 或 TreeRebuilt。

### 4.7 LocalPlayer 边界

CommonUIActionRouterBase 继承 LocalPlayerSubsystem，路由状态按 LocalPlayer 隔离。

EnhancedInputLocalPlayerSubsystem 也属于 LocalPlayer 级别。

同一个进程的两个分屏玩家不应共享激活根、输入映射、焦点目标或页面 ViewModel。

PlatformUserId、ControllerId、LocalPlayerIndex 和 DeviceId 可能不是同一个标识。

项目应在登录、手柄热插拔和分屏创建时建立显式映射。

页面创建函数不得隐式调用 GetFirstLocalPlayer。

如果只能从 Widget 取得 OwningLocalPlayer，应在没有拥有者时走失败路径，而不是使用全局单例。

### 4.8 CommonUI 与 Enhanced Input 的边界

Enhanced Input 定义 InputAction、InputMappingContext、Triggers、Modifiers 和优先级。

CommonUI 定义页面激活、路由、Action Domain、焦点和 UI 消费边界。

二者组合时，页面 Context 负责声明动作到按键的映射。

Router 负责决定当前页面是否有资格消费该动作。

InputConfig 负责 UI/游戏输入模式、鼠标捕获等策略。

Action Domain 负责限定动作搜索范围。

不要把“Context 已添加”误判为“UI 一定会收到动作”。

不要把“焦点在按钮上”误判为“Action Binding 一定存在”。

### 4.9 映射上下文的对称性

每一次页面专属 AddMappingContext 都应能定位到对应的 RemoveMappingContext。

用页面激活序列或 ContextLeaseId 记录配对关系。

重复激活同一页面时，要明确采用引用计数、幂等添加还是拒绝重复激活。

页面关闭失败时也要执行 RemoveMappingContext。

World 切换、LocalPlayer 重置和登录退出时应有兜底清理。

Enhanced Input 的 TrackingMode 产生未移除上下文警告时，应把它当作生命周期缺陷处理。

### 4.10 输入与数据的交叉竞争

按下确认键后，页面可能发起网络请求并进入 Confirming。

在响应回来前，用户又按下 Back 或切换到另一个页面。

如果命令只按 Widget 指针回调，旧响应可能重新打开已关闭页面。

命令必须携带 PageActivationSerial、RequestId 和 ViewModelGeneration。

回调到达时先检查页面仍为 Active 或允许接收结果，再决定是否应用。

拒绝旧结果也必须留事件，便于区分“请求失败”和“结果被正确丢弃”。

## 5. UMG MVVM：ViewModel、绑定与生命周期

### 5.1 View 与 ViewModel 的职责

View 负责布局、动画、可视性和焦点目标。

ViewModel 负责 UI 可读字段、可写字段和面向 UI 的命令。

Model 或业务服务负责权威数据、规则、网络请求和持久化。

ViewModel 可以转换 Model 数据为展示字段，但不应直接修改 Widget 子控件。

View 不应通过 Tick 主动轮询所有业务状态。

业务层也不应保存强引用 Widget 并在任意线程直接调用 UMG。

### 5.2 UE 5.8 MVVM 运行时边界

本机 UE 5.8 的 ModelViewViewModel 插件包含 Runtime、Blueprint、Editor 和 Debugger 相关模块。

UMVVMView 是附着在 UUserWidget 上的运行时扩展。

UMVVMViewClass 保存生成的 sources、bindings、conditions 和 events 描述。

UMVVMViewModelBase 提供 ViewModel 常用基类能力，并与 FieldNotify 通知协作。

MVVMView::ConstructView、InitializeBindings 和 SetViewModel 是需要重点理解的运行时入口。

绑定编译器把字段路径、方向和转换函数编译到绑定库。

Binding 执行模式可能是 Immediate、Delayed 或 Tick；项目应按实际配置确认，不要只按名称推断。

5.8 的插件和 Beta 边界意味着生成类布局、Private 实现和弃用兼容类型不能当作跨版本 ABI。

### 5.3 FieldNotify 的正确写入方式

只修改 C++ 成员变量不一定会触发 UI 刷新。

ViewModel setter 应在值真正变化时更新并广播字段通知。

现有 UE 5.8 源码和项目约定常使用 UE_MVVM_SET_PROPERTY_VALUE 等宏封装比较与通知。

宏和头文件版本应以项目当前 Build.cs 与本机插件头文件为准。

如果使用手写广播，要确认通知字段 ID 与绑定字段路径一致。

数组、结构体和可变集合需要定义整体通知还是增量通知。

通知不应包含完整列表 payload；UI 只需要知道哪个字段或哪个索引发生了变化。

### 5.4 绑定方向

OneWay 是 Model/ViewModel 到 View 的常见展示绑定。

TwoWay 适合设置项、输入框和可编辑表单，但必须防止回写触发无限循环。

Event Binding 适合把 View 的用户动作转成 ViewModel 命令。

转换函数应是纯的、快速的、无网络副作用的。

一个复杂转换函数若需要访问 World、Asset 或网络服务，应改成 ViewModel 预计算字段。

### 5.5 ViewModel 生命周期状态

ViewModel 需要自己的生命周期标记，不能只依赖 UObject 是否被 GC。

建议使用 Detached、Attached、Bound、Suspended、Invalid 五个语义状态。

Widget Construct 时取得或创建 ViewModel。

View Construct 后设置 source 并建立绑定。

页面 Activated 后允许命令执行。

页面 Suspended 时可以保持只读刷新，但应暂停高频交互或昂贵转换。

页面 Deactivate 时先禁止命令，再解除绑定和外部 delegate。

Widget Rebuild 时不要重复叠加 FieldNotify delegate。

### 5.6 绑定与页面激活的组合

CommonActivatableWidget 负责“现在谁能响应输入”。

UMVVMView 负责“现在显示哪些数据”。

一个页面可以保持 ViewModel 存活而暂时不处于 Active。

但页面不 Active 时，Command 入口必须被拒绝或转发到明确的父页面。

页面从 Suspended 回到 Active 时，应检查数据 Revision 是否仍是最新。

如果 ViewModel 被共享，页面必须只绑定自己允许读取的字段。

共享 ViewModel 的失败不能让一个玩家的页面影响另一个玩家。

### 5.7 列表刷新策略

列表刷新分为全量替换、增量更新和可视项更新。

全量替换简单但可能导致大量 Widget 重建和焦点丢失。

增量更新需要稳定 ItemId、ItemRevision 和删除语义。

可视项更新只更新当前可见条目，适合大型列表和移动端。

更新列表前保存 FocusedItemId，而不是保存子控件指针。

更新完成后用 ItemId 找回当前有效控件，再请求焦点恢复。

列表项 ViewModel 销毁时必须解除条目级绑定。

### 5.8 绑定成本的来源

绑定成本不只包括 setter 本身。

它还包括 FieldNotify 广播、字段路径遍历、转换函数、Widget 属性写入和 Slate invalidation。

Tick binding 还会产生每帧检查成本，即使数据没有变化。

Delayed binding 可能把多个变化合并，但会增加 UI 可见延迟。

Immediate binding 适合小字段和强一致的交互反馈。

项目应依据场景测量，而不是把某一种执行模式作为全局规则。

## 6. 线程、LocalPlayer 与数据竞争

### 6.1 线程边界表

| 线程/执行域 | 可以做 | 不可以做 | 交接方式 |
| --- | --- | --- | --- |
| Game Thread | UWidget、UMVVMView、LocalPlayerSubsystem、输入和焦点 | 阻塞等待网络/磁盘 | 事件或异步任务 |
| Worker/Task | 解析不可变数据、计算排序、构建快照 | 直接改 UObject/UMG/Slate | AsyncTask 回 Game Thread |
| Render Thread | 渲染命令和资源同步 | 修改 ViewModel 或路由器 | 引擎渲染接口 |
| RHI Thread | RHI 工作 | 读取未同步业务对象 | RHI/Render fence |
| Trace 写入路径 | 写入允许的 Trace 事件字段 | 依赖 UObject 生命周期回调 | 只传值类型/稳定字符串 |
| Insights 分析进程 | 读取 Session/Provider | 回写游戏状态 | 文件或报告产物 |

UMG、Slate、CommonUI 和大多数 UObject 状态修改必须回到 Game Thread。

TraceLog 的线程本地缓冲不等于业务对象可以跨线程访问。

即便 Trace 事件能从 Worker 线程发出，也只能写入已经复制到安全值对象中的字段。

### 6.2 不可变快照

网络线程或 Worker 线程先构造不可变的 FInventorySnapshot。

快照携带 AccountScope、LocalPlayerIndex、RequestId、SourceRevision 和 Generation。

回到 Game Thread 后，再比较目标 ViewModel 当前 Generation。

版本不匹配时丢弃快照，并记录 DiscardReason=StaleGeneration。

不要在 Worker 线程保存裸 UUserWidget 指针以便稍后回调。

可以保存弱引用或逻辑 ID，但最终使用前仍要在 Game Thread 验证。

### 6.3 生成号与请求号

RequestId 区分并行请求。

Generation 区分同一个页面实例经历过几轮打开/关闭。

DataRevision 区分业务数据的新旧。

三者不要用一个整数混合表达。

页面关闭后递增 Generation，使迟到结果自然失效。

请求重试时生成新的 RequestId，但可以保留同一个 UserIntentId。

业务服务返回 SourceRevision 时，ViewModel 只接受不早于当前 AppliedRevision 的结果。

### 6.4 数据竞争的常见形式

竞争一：旧网络响应覆盖新响应。

竞争二：用户改设置后，本地保存回调把旧值写回。

竞争三：列表排序完成后，页面已经换到另一个筛选条件。

竞争四：Widget 重建后，旧 delegate 再次执行。

竞争五：页面 A 和页面 B 共享 ViewModel，却用不同的展示过滤器覆盖字段。

竞争六：分屏玩家 A 的输入事件被错误映射到玩家 B。

每种竞争都要有可检测的 Token 或 Scope。

### 6.5 Mermaid：异步结果回主线程

~~~mermaid
sequenceDiagram
    participant Input as Game Thread 输入
    participant Page as CommonUI 页面
    participant VM as ViewModel
    participant Task as Worker/网络任务
    participant Trace as Trace
    Input->>Page: Submit(UserIntentId)
    Page->>VM: Generation +1，进入 Loading
    Page->>Task: Request(RequestId, Generation)
    Task-->>Trace: RequestStarted
    Task-->>Page: Immutable Snapshot
    Page->>Page: 回 Game Thread
    alt Generation 和 Revision 仍有效
        Page->>VM: ApplySnapshot
        VM-->>Trace: DataApplied
        VM-->>Page: FieldNotify
    else 结果已过期
        Page-->>Trace: DataDiscarded
    end
~~~

跨线程交接的核心不是“加一把锁就结束”。

核心是只在正确线程修改 UI，并用版本判断让迟到结果可解释地失败。

### 6.6 锁与队列的取舍

不要用一把跨所有 UI 对象的全局锁保护 Game Thread。

锁会把 UI 交互等待和后台计算耦合，可能把短尖峰变成长尾卡顿。

优先使用不可变快照、单写者模型和 Game Thread 消息队列。

如果确实需要共享缓存，锁只保护纯数据结构，不能在持锁期间调用 UMG、Slate 或网络接口。

把锁等待时间单独埋入 Timing Scope，避免把竞争误判为绑定耗时。

## 7. 可观测性设计

### 7.1 事件、Timing 和日志的分工

事件适合离散状态变化和可过滤字段。

Timing Scope 适合连续耗时、嵌套关系和线程视图。

日志适合人类诊断、错误堆栈和少量上下文。

计数器适合累计次数、丢弃数、重试数和队列长度。

不要用一条长日志代替所有类型的证据。

### 7.2 事件分类

| 事件 | 产生时机 | 关键字段 |
| --- | --- | --- |
| PageRequested | 请求打开页面 | PageId、UserIntentId、LocalPlayerIndex |
| PageStateChanged | 任意状态转移 | From、To、Reason、ActivationSerial |
| PageActivated | 激活完成 | ActiveRoot、ActiveLeaf、DesiredFocusId |
| PageDeactivated | 停用完成 | CloseReason、CleanupMask |
| InputRouted | 输入完成路由 | ActionId、InputDevice、RouteResult |
| FocusChanged | 焦点变化 | OldId、NewId、Restored、FailureReason |
| ViewModelAttached | source 建立 | ViewModelId、ContextName、Generation |
| BindingExecuted | 绑定执行 | BindingId、Mode、Changed、CostUs |
| DataRequested | 请求开始 | RequestId、SourceRevision、Generation |
| DataApplied | 快照应用 | RequestId、AppliedRevision、ItemCount |
| DataDiscarded | 结果被丢弃 | RequestId、DiscardReason、Generation |
| UIError | 失败路径 | ErrorCode、Recoverable、Fallback |
| BudgetExceeded | 超预算 | BudgetName、Observed、Threshold |
| TraceSession | 采集状态 | Channel、CaptureEnabled、FileId |

### 7.3 字段命名规则

字段名采用稳定英文 PascalCase，含义写入事件字典。

枚举字段优先用有限值，不把任意字符串作为筛选键。

PageId、ActionId、BindingId 和 ScenarioId 要求可跨会话比较。

对象名如会变化，使用逻辑 ID 而不是内存地址。

时间统一记录为微秒或毫秒，并在字段名中明确单位。

Revision、Generation、Serial 使用无符号整数并在文档中说明递增点。

失败原因采用有限枚举，附加诊断文字可以放日志。

### 7.4 推荐的通用字段

| 字段 | 类型建议 | 用途 |
| --- | --- | --- |
| ScenarioId | uint32/稳定字符串 | 关联自动化场景 |
| UserIntentId | uint64 | 关联一次用户意图 |
| RequestId | uint64 | 关联异步请求 |
| PageId | 名称/字典 ID | 识别页面 |
| PageState | 枚举 | 识别状态 |
| ActivationSerial | uint32 | 区分页面重复打开 |
| LocalPlayerIndex | int32 | 区分本地玩家 |
| PlatformUserId | uint64/脱敏 ID | 关联设备用户 |
| InputDevice | 枚举 | 键鼠/手柄/触控 |
| ActionId | 字典 ID | 识别动作 |
| RouteResult | 枚举 | 识别消费边界 |
| FocusedWidgetId | 字典 ID | 识别焦点 |
| ViewModelId | 字典 ID | 识别数据源 |
| BindingId | 字典 ID | 识别绑定 |
| SourceRevision | uint64 | 识别数据来源版本 |
| AppliedRevision | uint64 | 识别已显示版本 |
| Generation | uint32 | 识别页面实例代数 |
| Thread | 枚举/线程 ID | 识别执行线程 |
| DurationUs | uint64 | 识别耗时 |
| DiscardReason | 枚举 | 识别丢弃原因 |
| BuildConfiguration | 枚举 | 区分 Development/Shipping |
| CaptureEnabled | bool | 识别采集是否启用 |

### 7.5 隐私与可回溯性

Trace 字段不要写聊天正文、完整账号、访问令牌、支付信息或未脱敏设备标识。

业务对象名可能包含玩家自定义文本，也应使用字典 ID 或哈希后的稳定标签。

ScenarioId 和 PageId 要能回到代码、测试或产品用例。

UserIntentId 只用于一次运行上下文，不应当被当作跨用户身份。

原始 .utrace 文件要按项目访问控制保存。

对外提供性能报告时优先提供聚合数据和裁剪后的会话。

### 7.6 自定义 Trace 事件的边界

UE 5.8 的 Trace 事件 schema 由 Trace/Trace.h 中的宏描述。

事件定义和事件实例字段必须保持类型与名称一致。

事件发出前确认目标 Trace Channel 已启用。

高频字段要控制长度，避免每次事件拷贝大字符串或完整容器。

事件写入只记录证据，不在写入点执行聚合、排序或 UI 逻辑。

一次页面打开可用 PageStateChanged 加若干 Timing Scope 表达，不需要每帧发送完整页面快照。

### 7.7 Timing Scope 设计

页面打开至少拆成 Resolve、Load、Construct、Activate、Bind、Focus 和 FirstPaint。

数据刷新至少拆成 Decode、Validate、Apply、Notify 和 SlateUpdate。

输入处理至少拆成 Receive、Route、Command 和 SideEffect。

Scope 名称应包含系统和动作，例如 UI.Inventory.Open.Activate。

不要在 Scope 名称中拼接玩家名、物品名或任意长字符串。

Scope 的条件采集要与项目的 Trace Channel 开关一致。

### 7.8 采集到分析的证据链

第一层是运行时产生的事件和 Scope。

第二层是 TraceLog 缓冲和传输。

第三层是 .utrace 文件或实时会话。

第四层是 TraceServices 创建的 Analysis Session 和 Provider。

第五层是 TraceInsights Timing View、事件视图和导出结果。

任何一层缺失，都必须在报告中写明，而不是直接说“Insights 没数据”。

## 8. 性能预算

### 8.1 预算不是拍脑袋的单点数值

预算应绑定目标平台、分辨率、输入设备和页面规模。

桌面高端机、主机、低端移动机不应共用一个无条件阈值。

建议先从基线会话取得 P50、P95、P99，再设置告警阈值。

首开尖峰和稳定交互帧要分开统计。

预算超标时先定位贡献者，再决定减功能、延迟加载、虚拟化或改变绑定模式。

### 8.2 建议的初始预算表

以下是工程启动时的经验基线，不是 UE 的硬性保证。

| 指标 | 桌面/主机 P95 | 中低端移动 P95 | 备注 |
| --- | ---: | ---: | --- |
| 页面首开总耗时 | 100 ms | 180 ms | 不含不可避免的首次登录网络等待 |
| 激活栈更新 | 1.0 ms | 2.0 ms | 不含资源加载 |
| 输入路由单次 | 0.10 ms | 0.25 ms | 不在高频 Tick 中重建动作域 |
| 焦点恢复 | 0.50 ms | 1.00 ms | 列表规模需单独标注 |
| 单次绑定批次 | 0.50 ms | 1.00 ms | 以字段变更批次计 |
| 交互帧 UI CPU | 2.0 ms | 4.0 ms | 目标帧率决定最终预算 |
| 持续刷新批次 | 0.25 ms | 0.50 ms | 不含网络解码 |
| UI 事件额外开销 | 0.10 ms | 0.20 ms | 只记录必要事件 |
| 首次可交互时间 | 150 ms | 250 ms | 页面可响应而非仅可见 |

移动端 Trace 采集开销可能明显改变基线。

采集与非采集都要运行同一场景，并记录 CaptureEnabled。

### 8.3 页面预算拆分

一个页面的首开预算可按以下公式分解。

~~~text
OpenTotal
  = Resolve
  + AsyncLoadWait
  + Construct
  + Activate
  + BindingInitialize
  + FocusRestore
  + FirstPaint
~~~

如果 OpenTotal 超标但各部分相加不完整，说明还有等待、锁竞争或线程切换未埋点。

绑定预算不要只看平均值。

列表页面应同时记录 VisibleItemCount、TotalItemCount 和 ChangedFieldCount。

### 8.4 预算告警

测试环境可以在 PageStateChanged 到 Active 时计算 OpenDurationMs。

如果超过阈值，发出 BudgetExceeded，并保留同一个 ScenarioId。

预算告警不应直接让 Shipping 玩家退出页面。

开发和 CI 可以把 P95 超标视为失败。

生产采集可以只采样告警页面，减少数据量。

### 8.5 长尾排查

P50 正常、P99 异常时，优先检查资源加载、GC、同步磁盘、锁等待和网络重试。

如果所有设备都在同一个 Binding Scope 超时，检查 ViewModel 转换和列表批量通知。

如果只有手柄场景超时，检查焦点导航搜索和列表重建。

如果只有首开超时，检查硬引用、Asset Load 和生成 Widget 数量。

如果录制时才超时，分离 Trace 写入、文件传输和分析成本。

### 9.2 ViewModel setter 示意

> 以下为示意 C++；UE 5.8 的 FieldNotify 与 MVVM 宏应以 ModelViewViewModel 插件头文件和项目启用配置为准。

~~~cpp
UCLASS()
class UInventoryViewModel : public UMVVMViewModelBase
{
    GENERATED_BODY()

public:
    UPROPERTY(BlueprintReadWrite, FieldNotify)
    int32 Gold = 0;

    UFUNCTION(BlueprintCallable)
    void SetGold(int32 NewGold)
    {
        if (Gold == NewGold)
        {
            return;
        }

        UE_MVVM_SET_PROPERTY_VALUE(Gold, NewGold);
    }

    UPROPERTY(BlueprintReadOnly, FieldNotify)
    int32 AppliedRevision = 0;
};
~~~

setter 的重要点是比较、更新、通知三件事具有一致顺序。

如果业务层需要保留旧值，也在 ViewModel 外部保存，不让 UI 绑定函数承担历史记录。

### 9.3 LocalPlayer 取得输入子系统

> 以下为示意 C++，展示 LocalPlayer 边界与映射上下文配对。

~~~cpp
void UInventoryPage::AddPageInput()
{
    ULocalPlayer* LP = GetOwningLocalPlayer();
    if (!IsValid(LP) || !PageInputContext)
    {
        EmitInputFailure(TEXT("NoLocalPlayerOrContext"));
        return;
    }

    UEnhancedInputLocalPlayerSubsystem* Subsystem =
        LP->GetSubsystem<UEnhancedInputLocalPlayerSubsystem>();
    if (!Subsystem)
    {
        EmitInputFailure(TEXT("NoEnhancedInputSubsystem"));
        return;
    }

    Subsystem->AddMappingContext(PageInputContext, PageInputPriority);
    bPageContextAdded = true;
}

void UInventoryPage::RemovePageInput()
{
    ULocalPlayer* LP = GetOwningLocalPlayer();
    UEnhancedInputLocalPlayerSubsystem* Subsystem =
        LP ? LP->GetSubsystem<UEnhancedInputLocalPlayerSubsystem>() : nullptr;
    if (Subsystem && PageInputContext && bPageContextAdded)
    {
        Subsystem->RemoveMappingContext(PageInputContext);
    }

    bPageContextAdded = false;
}
~~~

在真实项目中还要保存 ContextLeaseId 或激活序列，避免重复激活导致错误移除。

### 9.4 CommonUI 页面伪代码

~~~text
RequestOpen(PageId, LocalPlayer, UserIntentId):
    assert(GameThread)
    token = NewToken(PageId, LocalPlayer)
    Emit(PageRequested, token)
    State = Requested

    if not ResolveAssets(token):
        State = Loading
        StartAsyncLoad(token)
        return

    Activate(token)

Activate(token):
    if token.Generation != CurrentGeneration:
        Emit(PageStateChanged, Failed, "StaleToken")
        return
    State = Activating
    Scope(UI.Page.Activate)
    ActivateWidget()
    if not IsActivated():
        Rollback("ActivateRejected")
        return
    AddPageInput()
    if not HasValidDesiredFocus():
        Rollback("NoDesiredFocus")
        return
    RequestRefreshFocus()
    State = Active
    Emit(PageActivated, token)
~~~

### 9.5 异步结果应用伪代码

~~~text
OnSnapshotArrived(Snapshot):
    ScheduleOnGameThread:
        if not IsPageAlive():
            Emit(DataDiscarded, "PageGone")
            return
        if Snapshot.Generation != Page.Generation:
            Emit(DataDiscarded, "StaleGeneration")
            return
        if Snapshot.SourceRevision < ViewModel.AppliedRevision:
            Emit(DataDiscarded, "OlderRevision")
            return
        Scope(UI.ViewModel.Apply)
        ViewModel.ApplySnapshot(Snapshot)
        Emit(DataApplied, Snapshot.RequestId, Snapshot.SourceRevision)
~~~

这里的 ScheduleOnGameThread 是伪代码，项目可以用 AsyncTask、TaskGraph 或自己的消息队列实现。

### 9.6 Trace CPU Scope 示意

    << LocalPlayerIndex(LocalPlayerIndex)
    << Reason(static_cast<uint8>(Reason));
~~~

示意代码没有包含所有注册、模块依赖和采集开关。

不要把 UE_TRACE_EVENT_FIELD 的 schema 定义和普通 UE_LOG 格式字符串混写。

### 9.9 采集与分析命令示意

> 命令是项目实验流程示意，具体参数要按目标平台和项目启用的 Trace Channel 调整。

~~~text

~~~

本地分析先按 ScenarioId 找事件，再按 PageId 过滤 Timing。

如果事件有但 Timing 为空，检查 Scope 的采集条件、时间窗口和线程轨道。

## 10. 自动化验收

### 10.1 验收分层

单元测试验证状态机、版本比较和清理配对。

功能自动化验证页面激活、输入消费、焦点和数据展示。

性能自动化验证 P95/P99、长尾和预算告警。

设备自动化验证键鼠、手柄、触控和多 LocalPlayer。

Trace 回归验证事件字段、通道、会话可打开和分析结果可定位。

Shipping 验证采集门控、隐私字段和无 Trace 时的功能回退。

### 10.2 测试场景矩阵

| 场景 | 输入 | 数据 | 预期状态 | 必须断言 |
| --- | --- | --- | --- | --- |
| 首次打开 | 键鼠 | 立即数据 | Active | Focus、Binding、预算 |
| 手柄打开 | 手柄 | 立即数据 | Active | Action Consumed |
| 手柄弹窗 | 手柄 | 延迟数据 | Suspended/Active | 父页面不吃动作 |
| 网络超时 | 任意 | Error | Error | 可重试且不悬挂 |
| 旧响应 | 任意 | Stale | Active | DataDiscarded |

| 列表重建 | 导航 | 增量数据 | Active | 焦点按 ItemId 恢复 |
| 分屏 | 两个手柄 | 独立数据 | Active | 不串 LocalPlayer |
| 触控 | 触控 | 立即数据 | Active | 命中测试有效 |
| Trace 关闭 | 任意 | 任意 | 正常 | 功能不依赖 Trace |

### 10.3 状态机单元测试

测试每个合法转移至少一次。

测试 Closed 不能消费页面动作。

测试 Deactivating 拒绝重复关闭和提交。

测试旧 Generation 结果一定被丢弃。

测试 SourceRevision 小于 AppliedRevision 时不回退。

测试激活失败会移除已添加的 Mapping Context。

测试焦点目标缺失会进入 Failed 或 Error，而不是 Active。

测试重复 Add/Remove Context 后最终计数为零。

### 10.4 输入自动化

输入测试必须经过实际输入路由层。

不要只在测试中直接调用 ViewModel 命令。

至少覆盖 UI Accept、UI Back、导航方向、鼠标点击和触控命中。

断言 RouteResult、ActiveLeaf、ActionId 和 GameplayFallbackCount。

模态弹窗测试必须确认背景页不会收到同一个动作。

手柄测试必须确认焦点目标在列表重建后仍是合法项。

分屏测试必须给每个设备明确 PlatformUserId。

### 10.5 MVVM 自动化

创建 ViewModel 后验证默认字段和 View Context。

修改字段一次，验证 FieldNotify 次数为一。

写入同值，验证不产生无意义刷新。

销毁 Widget 后触发字段通知，验证没有访问已销毁 View 的回调。

重复 Construct/Rebuild，验证绑定数量不增长。

Delayed 模式下验证通知最终合并且不丢最后值。

Tick 模式下验证无变化帧不会重复执行昂贵转换。

### 10.6 Trace 自动化

自动化场景开始时分配 ScenarioId。

所有 PageStateChanged 和 DataApplied 事件必须带 ScenarioId。

场景结束时检查是否存在未闭合页面、未清理 Context 或未完成 Request。

检查 Trace 文件可以被 Unreal Insights 打开。

检查 Timing Scope 名称满足命名规则。

检查敏感字段为空、脱敏或不在 schema 中。

检查采集关闭时页面功能仍然通过。

### 10.7 性能门禁

先运行预热流程，单独统计冷启动和稳态。

每个平台至少采集三次，报告 P50、P95 和最大值。

页面首开用 OpenDurationMs，不把网络等待和 UI 处理混为一个指标。

交互帧使用 UI CPU、Slate、Binding 和 Focus Scope 汇总。

超过预算时输出 PageId、ScenarioId、Observed、Threshold 和设备档位。

CI 失败信息要能直接链接到会话文件或导出的聚合表。

## 11. Shipping 采集边界

### 11.1 配置分层

Development 可以启用较完整的 UI 事件、CPU Scope、书签和诊断日志。

测试包可以按白名单开启项目 UI Channel，并控制采集时长。

Shipping 默认只保留产品允许的最小采集能力。

Shipping 不应依赖 Unreal Insights 进程存在才能正确显示界面。

Trace 不可用、Channel 关闭或文件不可写时，页面功能必须走无观测回退。

### 11.2 编译和运行门控

把高成本的调试字段和测试断言用编译宏或项目配置门控。

不要把仅 Editor 模块的代码链接进 Runtime 或 Shipping。

CommonUIEditor、ModelViewViewModelEditor 和 TraceInsights 工具模块的边界要在 Build.cs 与打包产物中分别确认。

Runtime 可以提供轻量的事件生产，但分析工具和编辑器 UI 不应进入客户端包。

Shipping 采集开关要有服务器策略、项目配置和命令行策略的明确优先级。

### 11.3 采样策略

普通玩家默认关闭高频 BindingExecuted 事件。

页面首开异常可以采样 PageStateChanged 和 BudgetExceeded。

内部测试账号可以按 ScenarioId 开启更细的 Trace。

高频输入只记录动作、结果和时间，不记录每个底层鼠标移动。

移动端优先短时本地文件或受控 TraceHost，避免长时间网络传输。

### 11.4 数据安全清单

不采集明文账号标识。

不采集访问令牌和支付字段。

不采集聊天正文和用户自定义文本。

不把完整路径、机器用户名和本地文件名作为事件字段。

对设备、用户和会话标识做稳定但不可逆的脱敏。

限制 .utrace 的保存时长和访问角色。

发布前抽样打开会话，确认字段内容与隐私策略一致。

### 11.5 无观测回退

EmitEvent 应是 BestEffort，不应在事件失败时改变页面状态。

Trace Channel 未启用时，性能 Scope 可以为空操作。

事件字典缺失时使用稳定的数值 ID 或最小名称。

本地磁盘不可写时，不要阻塞 UI 等待重试。

自动化测试可以把 CaptureEnabled=false 作为独立场景跑一次。

## 12. 失败路径与排查矩阵

### 12.1 页面与输入失败

| 失败 | 根因候选 | 证据 | 修复方向 |
| --- | --- | --- | --- |
| 可见但不激活 | 只改 Visibility | PageStateChanged 缺失 | 统一 ActivateWidget |
| 输入穿透 | Leaf 或 InputConfig 错误 | RouteResult=Unhandled | 调整激活栈和阻断策略 |
| Back 无效 | Binding/ActionDomain 缺失 | ActionId 不存在 | 检查 Back Action |
| 焦点为空 | Desired Focus 无效 | FocusFailureReason | 延迟到树构建后刷新 |
| 隐藏页仍响应 | Context 未移除 | PageContextCount | 对称清理 |
| 分屏串输入 | LocalPlayer 映射错误 | PlatformUserId 不一致 | 建立显式设备映射 |

### 12.2 数据与绑定失败

| 失败 | 根因候选 | 证据 | 修复方向 |
| --- | --- | --- | --- |
| UI 不刷新 | 没有 FieldNotify | BindingExecuted 缺失 | 修正 setter 和通知 |
| UI 回退旧值 | 旧响应覆盖 | DataDiscarded 缺失 | 增加 Revision 比较 |
| 重建后重复刷新 | delegate 重复注册 | BindingCount 增长 | 绑定与解绑配对 |
| 列表焦点丢失 | 全量重建无 ItemId | FocusedItemId 缺失 | 使用逻辑 ItemId |
| Tick 开销高 | 每帧绑定/转换 | Binding Mode=Tick | 改通知或批处理 |
| ViewModel 泄漏 | 外部 delegate 持有 | ViewModelAttached 无对应 Detach | 统一生命周期所有权 |

### 12.3 Trace 与分析失败

| 失败 | 根因候选 | 证据 | 修复方向 |
| --- | --- | --- | --- |
| 完全无事件 | Channel 未开 | TraceSession | 重启采集并确认参数 |
| 有事件无 Timing | Scope 未启用 | Timing 轨道空 | 开启 CPU channel |
| 文件打不开 | 文件截断/占用 | 文件大小和结束事件 | 本地完整 Stop/Flush |
| 分析很慢 | 文件过大/轨道过多 | Session 分析耗时 | 缩短窗口并裁剪通道 |
| 字段无法筛选 | 类型或字典不稳定 | Event schema | 固定字段和 ID |
| Shipping 无采集 | 编译门控预期 | BuildConfiguration | 走受控白名单策略 |

### 12.4 排查顺序

先确认 ScenarioId 和 PageId。

再确认 PageStateChanged 是否完整闭合。

然后确认 LocalPlayer、ActionId 和 RouteResult。

接着确认 ViewModelAttached、DataApplied 或 DataDiscarded。

再看 UI Page Scope 的耗时分解。

最后才调整 TimingView 筛选、Provider 或展示设置。

如果上游事件缺失，不要先修改 Insights 视图。

## 13. 最佳实践清单

### 13.1 架构

页面状态使用有限状态机。

页面身份使用 PageId 加 ActivationSerial。

异步结果使用 RequestId、Generation 和 Revision。

输入、数据和观测都显式带 LocalPlayer 边界。

CommonUI 管激活、路由和焦点，MVVM 管数据绑定，业务服务管权威数据。

### 13.2 输入

页面激活和 Mapping Context 添加保持有序。

页面停用和 Mapping Context 移除保持对称。

模态页面明确阻断父页面的规则。

焦点目标使用逻辑 ID 或稳定策略恢复。

键鼠、手柄和触控分别验收。

### 13.3 MVVM

setter 只在值变化时通知。

转换函数保持纯和短。

列表优先增量或虚拟化。

ViewModel 所有权清晰，绑定句柄可清理。

不要在 ViewModel 中持有 Widget 树强引用。

### 13.4 性能

首开、稳态、重建和失败重试分别设预算。

同时记录 P50、P95 和 P99。

Trace 采集和非采集都测。

高频事件采用采样或计数器。

预算告警包含场景、页面、设备和配置。

### 13.5 可观测性

状态转移、输入结果、数据应用和丢弃都产生有限事件。

Timing Scope 表达耗时，事件表达语义。

字段命名稳定，避免任意字符串。

失败路径与成功路径同等重要。

原始 Trace 与聚合报告分级保存。

- [ ] ViewModel 绑定可重复建立和清理。
- [ ] 异步结果带 RequestId、Generation、Revision。
- [ ] Worker 线程不直接访问 UMG/Slate/UObject。
- [ ] 有键鼠、手柄、触控验收。
- [ ] 有多 LocalPlayer 验收。
- [ ] 有旧结果丢弃验收。
- [ ] 有 UI CPU 与首次打开预算。

## 14. 常见问题 FAQ

### Q1：CommonUI 页面可见，为什么输入仍然到了玩法层？

可见只说明 Slate/UMG 可能绘制了控件，不说明页面已经成为 Active Leaf。

检查 PageState、ActiveRoot、ActiveLeaf、InputConfig、ActionDomain 和 RouteResult。

如果只设置 Visibility，改为走 ActivateWidget/DeactivateWidget 的页面合同。

### Q2：Enhanced Input 已经 AddMappingContext，为什么按钮动作没有触发？

Mapping Context 只定义动作映射，不保证 CommonUI 当前页面有权消费。

继续检查 InputAction 是否绑定、Action Domain 是否覆盖、LocalPlayer 是否正确以及焦点是否满足页面策略。

### Q3：弹窗有焦点，背景页面为什么还能响应？

焦点路径与 CommonUI 激活语义树不是同一棵树。

检查弹窗是否真正进入 Active Leaf，是否配置了阻断父域的 InputConfig，以及背景 Context 是否仍然有效。

### Q4：页面关闭后，迟到网络响应又把它打开了，怎么处理？

关闭页面时递增 Generation，并在回调回到 Game Thread 后比较 Generation。

旧结果只发 DataDiscarded，不得调用页面命令或重新激活。

### Q5：MVVM 绑定后数据变化但界面不刷新，先查什么？

先确认 setter 是否触发 FieldNotify，再确认 ViewModel 是否设置到正确的 View Context。

然后检查绑定方向、字段路径、执行模式和 Widget 是否已经 Rebuild。

不要先在 Widget Tick 中强制刷新掩盖通知缺失。

### Q6：为什么同值写入也会造成 UI 卡顿？

如果 setter 没有比较就广播，FieldNotify、转换、Slate invalidation 都可能重复执行。

让 setter 只在值发生变化时通知，并对列表定义增量更新策略。

### Q7：ViewModel 应该放在 GameInstance 还是 Widget？

取决于数据的所有权。

页面私有展示状态可以跟随 Widget 或页面控制器。

LocalPlayer 范围的用户设置和输入相关状态应放在 LocalPlayer 语义范围。

跨页面共享数据应由明确的 LocalPlayer 服务或业务模型拥有，再由各页面绑定只读字段。

### Q8：Worker 线程可以直接发 FieldNotify 吗？

不应直接这么做。

先把数据做成不可变快照，在 Game Thread 验证 Generation 和 Revision，再修改 ViewModel 并通知。

Trace 事件可以记录 Worker 侧结果，但不能因此绕过 UObject 线程边界。

### Q9：Immediate、Delayed 和 Tick binding 如何选？

立即反馈、小字段和低频交互可考虑 Immediate。

需要合并多次变更的批次可考虑 Delayed。

Tick 只在确有周期性来源且测量证明合理时使用。

最终选择要用 BindingExecuted、Changed 和 CostUs 数据验证。

### Q10：Insights 中事件有了，但看不到页面打开耗时，为什么？

事件描述离散状态，不能自动形成完整持续区间。

为 Resolve、Load、Activate、Bind、Focus 和 FirstPaint 添加 CPU Timing Scope，并确认 CPU Trace Channel 已启用。

### Q11：Trace 采集后页面更卡，测试结果还可信吗？

采集会带来事件构造、缓冲、传输和文件开销。

同时执行 CaptureEnabled=true/false 的同一场景，分别报告两组数据。

使用短时、精简通道和采样，关键结论用多次运行交叉验证。

### Q12：Shipping 是否应该一直打开 Trace？

通常不应默认打开完整采集。

应使用受控白名单、最小字段、采样和时长限制，并确保隐私字段不进入 schema。

功能必须在没有 Trace 时仍然正确。

### Q13：分屏玩家的 UI 偶尔串输入，为什么只在主机出现？

主机常同时存在多个 LocalPlayer，PlatformUserId、ControllerId 和 LocalPlayerIndex 的映射更容易暴露错误。

检查页面 OwningLocalPlayer、CommonUI Router、Enhanced Input Subsystem 和设备映射是否全部使用同一归属。

### Q14：列表刷新后焦点跳到第一项，是不是 Slate 的 bug？

多数情况下是列表全量重建后旧 Widget Path 失效，而项目没有保存稳定 ItemId。

刷新前保存 ItemId，刷新后查找当前有效条目，再请求焦点恢复，并记录恢复失败原因。

### Q15：自动化里直接调用 OnClicked 可以吗？

它只能验证 View 层命令，不足以验证输入路由、焦点、LocalPlayer 和 Mapping Context。

至少增加一条经过实际输入注入与 CommonUI 路由的设备级场景。

### Q16：为什么没有完整业务数据，仍然需要 DataDiscarded 事件？

丢弃事件说明系统正确拒绝了旧结果、错误玩家或已关闭页面。

没有它，分析者容易把“无变化”误判为“网络失败”或“绑定失效”。
