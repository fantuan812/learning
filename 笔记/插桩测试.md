# 插桩测试（Instrumentation）—— 耗时点测试方法一

## 1. 是什么
- 在代码中插入计时/统计代码，直接测量指定代码段的耗时。
- 属于"侵入式"测量：需要改代码（或由编译器自动插入），有固定测量开销。

## 2. 适用场景
- 已经大概知道热点在哪（如 A* 的某几个阶段），需要精确数值。
- 需要按 Tick / 按调用统计累计、平均、最大耗时，以及调用次数。
- 需要逻辑层数据：分支命中、失败率、队列长度等。

## 3. 常用实现方式
### 3.1 手动打点
```cpp
auto t0 = steady_clock::now();
// 被测代码段
auto t1 = steady_clock::now();
acc += duration_cast<microseconds>(t1 - t0);
```
- 时钟选择：C++ 用 `steady_clock`（单调时钟，避免系统时间跳变）；Windows 用 `QueryPerformanceCounter`；x86 可用 `rdtsc`（注意乱序执行，需配合 cpuid/lfence 或使用 `rdtscp`）。
- 统计维度：调用次数、累计耗时、平均、最大、耗时占比。

### 3.2 RAII / 宏封装
- 进入作用域时构造计时器，退出时自动累加（RAII），避免漏写结束点；可用宏开关（如 `#ifdef PROFILE`）控制编译，线上版本直接关闭。

### 3.3 编译器自动插桩
- GCC/Clang：`-finstrument-functions`，在每个函数进出调用 `__cyg_profile_func_enter/exit` 回调；适合全量分析，但开销大、函数粒度粗。
- `-pg`（gprof）：编译期插桩 + 运行时统计，适合小规模单进程程序。
- 动态插桩（如 Intel Pin / DynamoRIO / 商业 APM）：无需改源码，运行时注入，但部署复杂。

### 3.4 轻量设计要点
- 用线程局部存储（thread_local）累加，避免加锁竞争。
- 热路径上只做累加，周期性（每秒）输出一次汇总，避免日志 I/O 干扰测量。
- 环形缓冲区记录耗时分布，供离线分析（分位数、长尾）。

## 4. 服务器场景的统计模式
- 按 Tick 统计：每 Tick 内 A* 总耗时、超过预算的 Tick 次数（即卡顿点）。
- 分层统计：整体寻路 → Open List 操作 → 邻居扩展 → 路径重建，各阶段占比相加约 100%，一眼看出大头。
- 对比实验：同一压测场景，优化前后各跑相同时间，比较累计耗时与最大值。

## 5. 优点
- 精确：测的就是目标代码段，无采样误差。
- 能拿到逻辑层信息：调用次数、失败率、分支情况。
- 能测量极短代码段（微秒级）。

## 6. 缺点
- 侵入性：要改代码，可能影响编译器优化/内联，测量值含少量打点开销。
- 覆盖不全：没插桩的代码测不到，可能漏掉真正的热点。
- 生产环境维护成本：需要开关机制与定期清理。

## 7. 与采样分析（perf）配合使用
- 插桩：圈定"逻辑上"最耗时的代码段，给出精确数值。
- perf：无侵入验证，并发现插桩没覆盖的底层问题（内存分配、缓存缺失、锁竞争、系统调用）。
- 推荐流程：**插桩粗定位 → perf 细验证/查漏 → 优化 → 再对比**（详见 `perf性能分析.md`）。
