# Learning 仓库知识体系完善执行方案

> 仓库：`fantuan812/learning`
> 基线日期：2026-08-20（保留 2026-08-12 原始路线图，按当前仓库状态增量校正）。
> 方案目标：把当前“高覆盖文档知识库”升级为“知识树 + 技能树 + 项目树 + Evidence + OKF 互操作层”的工程能力库。
> 执行原则：先补结构性短板，再做纵向闭环；先提高成熟度，再增加篇数；所有 L3/L4/L5 必须能指向可验证证据。

---

## 0. 方案摘要

当前仓库的知识分类已经基本完整：计算机基础、UE 客户端、游戏服务端、游戏算法、游戏 AI、测试质量，以及系统实战都已经有明确位置；UE 源码、Dedicated Server、AI、测试体系的横向覆盖尤其充分。

下一阶段不应继续以“新增多少篇 Markdown”为核心目标。2026-08-20 复核后的真实基线是：计算机与工程基础已有 40 篇正文；Runtime 已落地 11/14；系统实战已落地假人 AI 与技能/Buff 两类链路，DS 上线链仍待建；成熟度阶段 B 门禁已经启用。当前集中解决四个问题：

1. 基础层广度已形成，但 L3/L4 可运行 Evidence 覆盖仍需提升。
2. Runtime 仍缺 SpatialQuery、动态分线与大规模战斗的工程证据。
3. 系统实战仍缺 Dedicated Server 上线闭环与更多真实复盘。
4. 文档已有成熟度、taxonomy、manifest 与 MOC，但缺少可被 Obsidian/Agent/其他工具共同消费的标准元数据、来源、验证状态和时效边界。

### 0.1 OKF + Obsidian 兼容层（2026-08-20）

采用 GoogleCloudPlatform/knowledge-catalog 发布的 Open Knowledge Format（OKF）v0.2 hybrid 模式，不创建以 Google 或 Obsidian 命名的知识分类，也不批量改写 386 篇 legacy Markdown：

- 仓库根 `index.md` 是 OKF/Obsidian 入口；`README.md` 继续服务 GitHub，`00_Index/MOC.md` 继续服务主题导航。
- 新建或本次修改的非保留 Markdown 必须有 YAML frontmatter 和非空 `type`；`index.md` / `log.md` 是保留名。
- `maturity` 衡量 L0~L5 证据深度；`verified` 保存 `{by, at}` 验证事件，信任层级由 actor 推导，两者正交。
- `sources`、`updated`、`stale_after` 补充来源与时效；canonical、taxonomy、manifest 的现有职责保持不变。
- Obsidian 直接打开仓库根，通过 Properties、Backlinks、Graph、Templates 与 `00_Index/Knowledge.base` 消费同一批 Markdown；Git 与 Obsidian Sync 不同时写同一文件。
- legacy 文档按“触碰即迁移”逐批补齐；全量 Strict 迁移必须单独审计与批准。

因此执行顺序固定为：

```text
OKF/Obsidian 互操作收口
  ↓
治理收口
  ↓
00 基础层落地
  ↓
Runtime 落地
  ↓
Evidence 基础设施
  ↓
三条高优先级系统实战
  ↓
已有重点文章升 L3/L4/L5
  ↓
大型项目级架构（Lyra）
  ↓
P2 横向补充
```

# 1. 最终目标架构

最终仓库逻辑上形成四层，而不是只有知识文章：

```text
                     Learning
                        │
        ┌───────────────┼────────────────┐
        │               │                │
      知识树           技能树           项目树
        │               │                │
基础 / UE / Server   L0 ~ L5        系统实战链路
Algorithm / AI / QA     │                │
        │               └──────┬─────────┘
        │                      │
        └────────────────── Evidence
                               │
                  Demo / Test / Benchmark
                  Replay / Raw Data / Log
                  WorkLog / Postmortem
```

最终不再用“有一篇文章”判断掌握度，而使用：

```text
主题 → 原理 → 来源验证 → Demo → Test → Benchmark → 项目复盘
 L1      L2        L3      L4        L5
```

# 2. 全局 Definition of Done

所有后续建设统一采用以下完成定义。

## 2.1 文档 DoD

一篇正式知识正文至少满足：

- 问题与适用范围明确。
- 有知识/版本基线。
- 有失败路径与边界条件。
- 有真实来源；版本敏感内容必须使用当前来源。
- 示例明确标记“可运行 / 节选 / 示意 / 伪代码”。
- 有验证入口。
- 有关联阅读。
- 有 `知识成熟度` 字段。

## 2.2 L3 DoD

L3 必须同时满足：

- 有可运行 Demo 或实验。
- 有运行命令。
- 有预期输出或断言。
- 文档能链接到对应 Evidence。

不能仅凭一段代码块标 L3。

## 2.3 L4 DoD

L4 必须同时满足：

- 满足 L3。
- 有自动测试或 Benchmark。
- 保存原始结果，而非只写总结。
- 至少记录测试环境和核心指标。
- 性能主题优先记录 P50/P95/P99、CPU、内存、吞吐、带宽中的适用项。

## 2.4 L5 DoD

L5 必须同时满足：

- 满足 L4 或有等价的真实生产证据。
- 能指向真实项目/工作日志/问题复盘。
- 记录“假设 → 实验 → 数据 → 结论 → 失败方案 → 最终方案”。
- 无法公开公司源码时必须提供脱敏证据或可复现实验替代。

## W0-03 将知识成熟度纳入门禁

### 修改

扩展 `scripts/check_repo.ps1`。

新增字段检测：

```text
知识成熟度：L0|L1|L2|L3|L4|L5
```

新增 Evidence 规则：

| 等级 | 自动检查要求 |
| --- | --- |
| L0 | 允许规划文件；正式正文不建议长期停留 |
| L1 | 必须有知识基线、最后更新、验证入口 |
| L2 | 必须存在外部来源或源码证据 |
| L3 | 必须存在 `Evidence`/`Demo` 入口 |
| L4 | 必须存在 Test/Benchmark 入口 |
| L5 | 必须存在工作日志/复盘/生产证据入口 |

新增错误示例：

```text
FAIL: 标注 L4 但缺少 Benchmark/Test 证据
FAIL: 标注 L5 但缺少工作日志/项目复盘证据
WARN: 正文缺少知识成熟度
```

### 迁移策略

不要一次强制所有 216 篇正文变为 FAIL。

采用两阶段：

**阶段 A**

- 既有正文缺成熟度：WARN。
- 新增或本次修改正文缺成熟度：FAIL。

**阶段 B**

- 核心知识域完成回填后，再把所有正文缺成熟度升级为 FAIL。

### 验收

人为把一篇 L2 文档改成 L4 且不提供 Benchmark，脚本必须失败。

## W0-06 建立 OKF 与 Obsidian 互操作门禁

### 执行

1. 以 `.kb/okf-profile.yaml` 固化 OKF v0.2 hybrid profile。
2. 新增根 `index.md` / `log.md`，与 GitHub README、Global MOC、维护经验日志明确分工。
3. 新建/修改 Markdown 通过 `scripts/check_okf.ps1 -Mode Changed`；`Audit` 只报告 legacy 欠账，`Strict` 是本库非排除文档的迁移门禁，不冒充通用 YAML/OKF parser。
4. 用 `references/templates/OKF-知识条目.md` 创建新条目；默认 `status: draft / verified: [] / maturity: L0`，不得自动提升。
5. 用 `00_Index/Knowledge.base` 浏览已迁移 Properties；不覆盖任务前 `.obsidian`，只忽略 workspace 本机状态。

### 验收

- Changed 模式对缺 `type` 的新建/修改文档返回 FAIL。
- Audit 模式准确给出 Conformant / Legacy / Excluded，不把 hybrid 误报为 Strict。
- Windows PowerShell 5.1 与 `pwsh` 均可执行门禁。
- Obsidian 能打开 Base、插入模板、使用反向链接；标准 Markdown 链接在非 Obsidian 消费者中仍可用。
- `.obsidian/app.json`、`appearance.json`、`core-plugins.json` 与任务前哈希一致；忽略并保留可能由 Obsidian 外部更新的 workspace 本机状态。

# 20. 完成后的仓库应具备什么能力

完成 P0/P1 后，仓库应能够回答四类问题。

## 20.1 “为什么”

例如：

- 为什么 false sharing 会让多线程变慢？
- 为什么 allocator 会影响服务器？
- 为什么 acquire/release 足以实现某些同步？
- 为什么 page fault 会造成卡顿？

由 `00-计算机与工程基础` 回答。

## 20.2 “系统怎么跑”

例如：

- 一次服务器 Tick 怎么调度？
- AOI 如何从移动一路变成网络 send？
- AI/寻路超预算怎么办？
- 服务器崩溃后世界状态怎么恢复？

由 Runtime 回答。

## 20.3 “一个功能怎么端到端完成”

例如：

- 技能从输入到 Buff/网络/测试怎么走？
- Bot 从决策到寻路、移动、AOI、性能怎么走？
- DS 从 Build 到 Ready、玩家登录、崩溃、容量怎么走？

由系统实战回答。

## 20.4 “你怎么证明它是对的”

由 Evidence + 测试库回答：

```text
Source
Demo
Test
Benchmark
Replay
WorkLog
Postmortem
```

最终仓库的核心价值不再是“有 200+ 篇知识文档”，而是：

> 对关键游戏工程问题，能够从计算机底层原理一路解释到引擎/服务端实现，再给出可运行实验、测试、性能数据和真实项目复盘。

这就是后续所有建设工作的最终验收标准。
