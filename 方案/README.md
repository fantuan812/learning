## 使用方式

1. 先看主方案中的 P0/P1/P2 优先级，不按文章数量平均扩张。
2. 每次只推进一个 Workstream 或一个可验收任务包，完成后回填状态矩阵。
3. 新增正文仍遵循 `references/写作规范.md`；L3/L4/L5 必须有真实 Evidence。
4. 新增目录或正文时同步对应 README、`references/仓库结构.md` 与根 `README.md`。
5. 每次交付前运行 `scripts/check_repo.ps1`，并把新增的成熟度、Evidence 与计划状态纳入门禁。

## 维护原则

- “规划”不等于“完成”；只有正文、代码、测试或数据落地后才更新状态。
- 不以 Markdown 数量作为核心 KPI，优先提升 L2/L3/L4/L5 的比例。
- 对已有高覆盖领域（UE 功能、测试理论、AI 理论）实行横向扩张冻结，优先补基础层、Runtime、系统实战与 Evidence。
- 真实工作无法公开源码时，允许使用脱敏 Demo、伪数据、Benchmark 脚本、流程证据和复盘结论替代公司代码。
