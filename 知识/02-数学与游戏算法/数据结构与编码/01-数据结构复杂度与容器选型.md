# 数据结构、复杂度与工程容器选型

> 知识基线：ISO C++20 语义以公开工作草案 N4861、固定提交 `6aea7f6be0895b9dd361c6562bdee2f3809e4fa0` 的相关条款解释；草案不是正式 ISO 出版物。通用算法另注明计算模型，不把标准容器的合同外推给所有同名数据结构。
> 知识成熟度：L2。主要承诺是已核对的容器合同、可手算的复杂度推导和工程取舍；没有本篇 C++ 编译、benchmark、性能采样或 UE 运行证据。
> 最后更新：2026-10-09，修订复杂度量词、操作后的句柄效力、游戏索引设计和测量口径，保留原有结构覆盖、检查清单及实践方向。
> 验证与基准：第 12 节给出纸面正反例和待执行测量合同。旧文“已有可执行命令”的说法不成立：可访问的本篇 current/legacy 历史未包含基准源码、实际输入输出或原始计时，不能补造结果。
> 适用范围：C++20 客户端批处理、工具和实时服务器的数据组织决策；UE 只列迁移检查项，不认证某个引擎版本、源码布局、GC 路径或性能。

## 1. 先把需求写成操作，而不是先选容器

假设一个游戏系统既要每 Tick 遍历活跃实体，又要按 ID 找对象，还会批量销毁实体。把全部对象放进哈希表，确实给了一个按键入口，却未回答遍历局部性、销毁期间句柄、确定性顺序和扩容时机。反过来，只用紧凑数组也未解决稳定 ID 到当前位置的映射。选型的对象往往是“主存储 + 索引 + 生命周期协议”，不是一个容器名。

先记录 n 的常见值、峰值和增长方式，键/值大小，按序/随机/按键/按优先级/邻域访问比例，命中与未命中比例，尾插/中插/删除/整批重建分布，以及哪些引用要跨哪些修改存活。还要记录重复键、稳定顺序、跨帧借用、线程归属、内存上限与实际帧或 Tick 预算。没有这些输入，“vector 比 list 快”或“哈希 O(1) 最好”都不是完整决策。

本文负责数据结构不变量、复杂度、完整操作成本和游戏工作负载选型。[STL 容器与 Allocator](../../01-编程与计算机基础/C++语言与对象模型/02-STL容器与Allocator.md) 负责完整的 allocator、异常和句柄矩阵；[Copy-Move 与值语义](../../01-编程与计算机基础/C++语言与对象模型/02-Copy-Move与值语义.md) 负责对象复制/移动能力。那两篇各有自己的版本及局部实验，不能借它们的退出码替本篇声称运行过。

## 2. 四种复杂度口径，以及它们没有回答什么

本文用 n 表示元素数，V/E 表示图顶点/边数，L 表示键长度，q 表示操作序列长度，k 表示返回结果数。空间区分输入、额外索引、工作内存和递归栈。比较、哈希、元素复制/移动若非恒定成本，应另用 `Ccmp(L)`、`Chash(L)`、`Cmove(T)` 计入。

| 口径 | 问的是什么 | 使用前提与边界 |
| --- | --- | --- |
| 最坏复杂度 | 固定规模下所有合法输入中，计数最多有多少 | 是指定计算模型的上界，不是纳秒、P99 或硬实时上界 |
| 平均复杂度 | 对声明的输入分布取平均 | 必须说明哪些键/查询/更新随机，不能拿一个测量均值代替证明 |
| 期望复杂度 | 对明确的随机变量取数学期望 | 例如固定输入、对随机选择的哈希函数取期望；它不等同每次调用都有保证 |
| 均摊复杂度 | 任意合法长序列的总成本，分摊到各次操作 | 不需要输入随机；某次调用仍可能很贵 |

O 是渐进上界，不自动表示紧界，更不包含确定常数。O(1) 只说计数不随所选规模增长；一次分配、锁竞争、缺页或系统调用的时长仍会变化。N4861 `[container.requirements.general]` 的容器复杂度按所含对象操作计数，`vector<vector<int>>` 复制的外层线性不能掩盖内层总元素复制量；`[structure.specifications]` 还说明标准库复杂度要求是上界。[容器计数合同](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L38-L54)、[库规范上界](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/lib-intro.tex#L680-L705)

### 2.1 能手算的证明与反例

- 两个独立的 n 次循环嵌套访问 n² 对；若 `i=1..n，j=i..n`，次数为 n(n+1)/2，仍是 Θ(n²)。循环边界不同就重新求和，不能见两个 for 就判平方。
- 每步把正整数候选范围减半，到 1 为止需要 Θ(log n) 步，取整只改常数；若每步同时线性搬移剩余元素，就还要计算搬移成本。
- 递推 `T(n)=aT(n/b)+f(n)` 只是一种分治模型，必须给出子问题数、规模、合并工作和边界，不能把任意递归硬套主定理。尾递归消除不由 C++20 普遍保证，空间要计实际调用栈。
- 假想动态数组从容量 1 开始、满时翻倍。追加 8 个常数大小元素，新元素写入 8 次，旧元素迁移 1+2+4=7 次；总计 15 次。第 9 次追加单独需迁移 8 项并写 1 项，成本是 9，而不是 1。任意 q 次追加的旧元素迁移形成几何级数，总计 O(q)，故均摊 O(1)。这是翻倍模型的推导，不是某个 STL 容量曲线的实测。
- 若每次只能多出一个槽位，旧元素累计迁移 0+1+…+(q−1)=Θ(q²)。反复调用 `reserve(size()+1)` 可能破坏原增长安排；标准不要求 reserve 必须恰好分配所请求容量，也不规定统一 1.5 倍或 2 倍增长因子。

## 3. 连续、节点与队列：移动什么，定位花多少

### 3.1 数组和动态数组

固定数组提供常数下标定位，但容量固定，没有通用的“尾插扩容”。普通 `vector<T>`（排除 `vector<bool>`）元素连续，尾插均摊常数；一次重分配线性。无重分配中插要移动后缀，擦除后也要把后缀向前补齐。中间删除成本不能直接推广给 `pop_back`，后者只处理末尾。

`reserve(N)` 不创建 N 个元素、不改变 size；合法下标仍是 `[0,size())`。成功预留后，在 size 不超过 capacity 的插入中不会重分配，但新元素和它的成员仍可能分配或抛异常。`resize` 改变元素数；缩小时结束尾部元素寿命，增长按具体重载构造元素。增长时旧值究竟复制还是移动，由类型能力、allocator 和该操作的异常保证共同约束，不以“有 move”或“有 noexcept”一句概括。[N4861 vector 概览及容量](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L5543-L5568)、[reserve](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L5808-L5864)

连续布局为顺序扫描提供相邻地址，常有利于预取；它不是“任何访问模式下最佳”。AoS 适合一次取同一实体的多个字段，SoA 将同一字段集中以适应批量更新；热冷拆分可减少无关字节，但新增数组、索引同步和对象语义成本也必须计入。随机取指针所指对象时，连续的只是指针数组，不是对象载荷。

### 3.2 单链表、双链表与 free list

双链表保存前后链接，支持双向遍历；在已有合法节点 iterator 时，可用常数次链接修改插入或删除单节点。若先按 ID、索引或值查找位置，仍可能先走 O(n)。单链表删除普通节点需要其前驱：`forward_list::erase_after` 以已知前驱为合同；只拿到待删节点指针，不能普遍 O(1) 删除并保持对象身份。

节点还承担指针、对齐、分配器元数据和回收成本。离散节点可能使预取难以跟上，但池分配与访问顺序会改变局部性，因此不把每次访问必定 cache miss 写成规律。侵入式链表把链接嵌进业务对象，省掉某些独立包装节点，却要求对象在仍挂链时地址和寿命满足结构不变量；对象搬迁或销毁前必须处理其全部挂链关系。哨兵统一空链/首尾边界，不能代替这些责任。

free list 复用槽位可减少向后端申请存储，仍要明确活对象销毁、槽位再构造和外部句柄撤销。实时路径应安排容量和耗尽策略，不能从“池内取槽 O(1)”推出不会缺页、不会争用或可无限增长。

### 3.3 栈、队列、deque 和固定环形缓冲

栈是后进先出，适合 DFS、撤销历史；队列是先进先出，适合请求处理。抽象接口本身没有统一实现成本：vector-backed 栈的 push 均摊 O(1)、扩容时 O(n)，不能一概写栈 push 最坏 O(1)。标准 `stack/queue` 的操作转交底层容器，默认底层为 deque。deque 随机访问是常数，但不保证全部元素连续；两端单元素插入按元素操作计数为常数，仍可能申请内部存储。

固定环形队列用读位置 r、写位置 w 和 count 区分空/满。容量 C=4，依次入队 A/B/C/D 后满；再入队 E 必须按合同拒绝或另走明确的丢弃策略。出队 A 后再入队 E，队列逻辑顺序为 B/C/D/E，尽管物理数组可能是 E/B/C/D。仅见 r==w 无法分清空和满，需 count、额外标志或预留一个空槽。

`(index+1)&(C−1)` 只在 C 是非零的 2 的幂、索引算术合法时才等价相应取模。它不消除越界、满队列或并发问题。SPSC/MPSC/MPMC、内存可见性和回收协议分别设计；无锁不等于无等待，也不自动排除 ABA。阻塞队列还需关闭、唤醒、超时和积压上限，不能只列容器插入复杂度。

## 4. 哈希：平均快的前提与碰撞反例

哈希先计算 key 的散列，再定位桶或探测位置，最后用相等谓词确认。装载因子 λ=n/B 是平均每桶元素数，不是最大桶长或尾延迟指标。若键很长，计算散列及比较可能扫描 L 个字符；此时按 n 平均 O(1) 的查找仍有 `Chash(L)` 等工作。

拉链表的常见模型在均匀散列前提下，查找期望 O(1+λ)；开放寻址还依赖探测规则、装载率、墓碑数量和输入分布。线性探测连续却易聚集；二次探测减少主聚集，但探测覆盖还取决于容量和步进参数。删除开放寻址槽不能随意设空：必须保留墓碑或正确后移修复探测链。标准 `unordered_*` 不能直接等同某个开放寻址实现。

**纸面碰撞反例**：教学哈希 `h(k)=k mod 4`、键 `{0,4,8,12}` 全进同桶。在线性桶链中查找不存在的 16，需要比较这四个键；扩大为 n 个 4 的倍数就能触及 n 项。把桶数写大不证明真实 Hash 对新桶映射仍会分散；要看完整映射和键分布。常量 Hash 对任何桶数都碰撞，仍可满足“等价键同哈希”的正确性要求，但性能很差。

N4861 `[unord.req]` 对 find 给出平均常数、最坏线性；rehash 与 reserve 则是平均线性、最坏平方，不能统一写“哈希操作 O(1)”或“rehash 最坏 O(n)”。`reserve(N)` 的参数是目标元素数，相当于按当前最大装载因子请求 `rehash(ceil(N/max_load_factor()))`；rehash 参数是桶数下界。设置合适因子后预留，再记录实际 bucket_count/load_factor，不把请求数字当精确桶数或内存字节预算。[无序容器合同与预留](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L2183-L2260)、[rehash/reserve 复杂度](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L2955-L2969)

Hash/Pred 要一致且在键留在表内时稳定：Pred 等价的键必须哈希相同，反向不成立。忽略大小写相等配合区分大小写的 Hash 就可能违约。浮点键不是语言禁用项，但业务需处理量化规则、±0、NaN 和相等语义；朴素“距离小于 ε”可能不具传递性，不能作为任意无序容器的等价关系。最好先把业务身份规范化成明确整数/字符串 ID，而不是拿连续坐标的近似相等代替身份。

随机化适当的哈希族可在明确威胁模型下减轻某些对抗碰撞，标准不承诺 `std::hash` 自带抗 DoS、秘密种子或最坏常数上界。攻击者输入还应有长度/数量上限、资源预算和退化处置；不能只加一个公开 seed 就宣称安全。并发访问另由线程归属、外部锁、分片或专用并发结构协调，rehash 不是可与任意无锁读并行的普通更新。

## 5. 有序结构、树和堆分别保留什么信息

排序数组把排序关系编码在元素顺序中。随机访问范围上的二分可用 O(log n) 次比较/位置跳转查找，插删却可能移动 O(n) 元素。`std::lower_bound` 最低要求是相对该查询谓词已分区；全局排序是常用的充分条件。对 list 等非随机访问 iterator，它仍可用对数次比较，却要线性步进。若已有 `map`，用其成员 lower_bound 才能利用树结构，而不是对 iterator 调用通用算法。[N4861 二分查找](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/algorithms.tex#L6568-L6630)

普通二叉搜索树的查找随高度 h 变化；按 1、2、3、4 顺序插入而不平衡可得到链，h=n。AVL 和红黑树以不同约束与旋转维持对数高度；“红黑树更新常数总比 AVL 低”没有跨实现保证。`std::map/set` 保证比较器次序和指定对数操作，不规定必须采用红黑树。Compare 应形成稳定的严格弱序；两个方向都不小于的键按该关系等价，不一定等于 `operator==`。B 树用较大节点组织多个键，适合按页/块访问；页尺寸、扇出、写放大及内存实现仍按具体系统分析。

二叉堆只保证父子之间的优先级关系，不提供全局排序遍历。访问非空堆顶 O(1)；删除堆顶并恢复堆 O(log n)。`pop_heap` 把旧堆顶放到区间末尾并恢复其余部分的堆性质，不改变容器 size，还需 pop_back 才删除元素。自底向上建堆为 O(n)：高度越大的节点越少，总工作可按 `n·Σ(h/2^h)` 界定。逐次插入 n 项则通常按 O(n log n) 总上界分析。

标准 `priority_queue::push` 是底层 push_back 加 push_heap；默认 vector 在某次扩容时还会线性搬迁，所以不能拿 heap 调整的对数比较次数冒充完整 push 的单次最坏成本。top 返回根引用，pop 不返回旧值；空队列先检查。[N4861 堆算法](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/algorithms.tex#L7731-L7915)、[priority_queue 操作组合](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L10244-L10305)

需要改优先级时有两条常见路线：维护“业务 ID→堆位置”并在每次交换后修复映射，或推入带版本的新条目、出队时跳过旧版本。标准 priority_queue 没有任意节点 decrease-key 接口。不能保存裸数组位置后改变优先级而不修堆，也不能让比较器读取会变化的外部优先级而期待旧堆自动恢复。惰性删除减少即刻定位维护，但堆大小按实际条目 H 计，陈旧条目占内存且会在以后消费预算。A* 的正确性和重开策略见[专篇](../路径搜索与导航/02-A星算法与优化.md)，本篇只负责这组存储与更新代价。

## 6. 图与并查集：把表示成本计进算法

| 表示/算法 | 在这里采用的前提与成本 | 容易漏掉的部分 |
| --- | --- | --- |
| 邻接矩阵 | O(V²) 空间，编号有效时查某条边 O(1) | 枚举一个顶点的邻居可能扫描 V 项 |
| 邻接表 | O(V+E) 空间，遍历全部邻接项 O(V+E) | 查特定边一般 O(deg(v))；加入排序/哈希索引另计 |
| CSR 连续邻接存储 | offsets 与边数组便于静态稀疏图批量遍历 | 任意增删边可能触发搬移或重建，不能只看读路径 |
| BFS / DFS | 邻接表、每顶点标记一次、每邻接项处理常数次时 O(V+E) | 顶点标记、队列/栈、递归深度；矩阵版通常 O(V²) |
| Dijkstra | 有限非负权、正确松弛；二叉堆与邻接表常见界 O((V+E)log V) | 重复条目的实现另以实际堆条目数计；负边破坏该贪心前提 |
| Bellman-Ford | 标准多轮松弛最坏 O(VE)，可处理负边并检测相关负环 | 可达负环会使某些最短距离不存在，不能只说“支持负边” |
| 拓扑排序 | 有向无环图才存在完整拓扑序，邻接表实现 O(V+E) | 若未处理全部顶点应报告环，不返回假装完整的顺序 |

BFS 的线性界来自每个顶点入队至多一次、每个邻接项检查至多一次；若到出队才标记而让同一顶点反复入队，或每次查询邻居都全表扫描，就需要重新计数。DFS 同样依赖访问标记，递归版最深可能达到 V 层。

图输入必须固定顶点编号范围、边方向、重复边策略、权重类型和溢出处理。V/E 是不同量，不能前面用 m 表边数、后面又让 m 表操作数而不重新定义。

并查集用 parent 森林代表分组：find 沿父链找根，union 先找两根、若不同再链接。按大小合并让小树挂到大树；按秩合并维护秩上界，两者都是控制深度的策略。路径压缩把一次 find 经过的节点指向根，降低以后的访问工作，当前 find 仍要先走完原路径。

**手算例**：初始 `{0},{1},{2},{3}`；合并 0/1、2/3 后，再把两组相连。若同大小时让第二根挂到第一根，可得到 `parent=[0,0,0,2]`。find(3) 走 `3→2→0` 后改成 `parent[3]=0`；下一次走 `3→0`。代表元由合并策略决定，不是固定业务 leader ID。删除一条关系后能否分裂成两组，普通并查集并不支持，需重建或使用适合的动态连通结构。

带路径压缩和按秩合并，包含 n 次 make-set 的 q 次操作可用 O(q·α(n)) 序列上界；α 是反 Ackermann 函数，增长极慢，但并非真正的常数，也不是单次操作最坏 O(1)。本次核对 [MIT 2012 Lecture 16 §16.2.3 / Theorem 16.2](https://ocw.mit.edu/courses/6-046j-design-and-analysis-of-algorithms-spring-2012/b1e5ac3c8f7d60db9b8d5b66c40bc55e_MIT6_046JS12_Notes.pdf#page=112) 的按秩结论，以及 [Tarjan 1974 报告](https://www2.eecs.berkeley.edu/Pubs/TechRpts/1974/Archive/ERL-m-434.pdf#page=12) 的按大小合并/压缩模型与式 (20)。这是指定序列模型的上界，未声称本篇重新证明全文或运行实现。

## 7. 字符串与空间索引：结构查询还要算输出

trie 沿键的符号序列走，每步子节点定位若是常数，查询为 O(L)；若孩子存在有序表或线性表中，还需把每步查询成本相乘/相加。压缩 trie 合并单分支路径，省节点但要比较边上的多符号片段。Unicode 的字节、代码单元、码点和用户可见字符不是同一长度，L 必须固定计量单位。

`std::string` 连续保存字符，短串 SSO 是可采用的实现策略，阈值和具体分配次数不是本文的标准承诺。`string_view` 不拥有字符；所有者销毁、重分配或更改键内容，可能分别破坏地址寿命或哈希/排序不变量。把临时拼接结果的 view 放进长期索引不是“零复制优化”。[N4861 string 与 string_view](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/strings.tex#L735-L760)、[string_view 定义](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/strings.tex#L3928-L3947)

网格用量化坐标定位格，四叉树用递归分区适应密度变化，空间哈希让稀疏格不必全部物化。没有一种结构普遍“邻域 O(1)”：设访问 c 个格/节点，检查 t 个候选，返回 k 项，总成本至少含定位、扫描候选和输出 k 项；若全部实体挤在一个格里，t 可达 n。移动实体还要维护旧格删除、新格插入与可见集差分，树的分裂/合并或重建也消耗预算。

格尺寸与查询半径、密度分布和更新速度一起选择。负坐标量化通常需要数学 floor，简单截断会把 -0.2 与 +0.2 错误映射到同侧；边界、超大坐标和键打包溢出要另测。本篇不认证 AOI 专篇中的旧毫秒数或某款引擎实现，工程链路可接着阅读 [AOI 与 Interest Management](../../07-网络与游戏服务端/状态复制与兴趣管理/05-AOI与InterestManagement.md)。

## 8. 句柄稳定、位置稳定与业务身份是三个问题

数组下标说明当前位置，iterator 说明容器遍历位置，指针/引用关联对象，业务 ID 或带代数的 handle 说明要找哪个实体。一个地址仍可读，不证明原实体还在该地址；某个 iterator 仍有效，也不证明它原来对应的值没被排序或赋值改变。

下表仅用于本篇选型决策，描述成功操作、合法前置条件，vector 排除 bool 特化。详细异常、swap、node handle 和 allocator 传播规则见 STL 专篇。

| 操作 | 原有元素 iterator | 原有元素引用/指针 | 旧 end 与身份注意事项 |
| --- | --- | --- | --- |
| vector 成功重分配 | 全失效 | 全失效 | 旧 end 也失效 |
| vector 容量内尾插 | 保留旧元素 iterator | 保留旧元素引用/指针 | 旧 end 失效 |
| vector 无重分配中插 / 非空 erase | 插入/擦除点及以后失效 | 不继续按旧位置关联使用点及以后句柄 | 后缀下标对应的实体可能改变，旧 end 失效 |
| deque 两端插入单元素 | 全失效 | 既有元素保留 | 旧 end 失效，不概括为“两端操作稳定” |
| deque 中间插入 | 全失效 | 全失效 | 旧 end 不再使用 |
| deque 擦除 | 擦最后元素：仅被擦元素 iterator 失效；只擦首部且不含尾：同样；中间擦除：全失效 | 对应被擦对象或全部元素失效 | 擦尾或中间使旧 end 失效；只擦首部且不含尾时保留 |
| list / map 插入、擦别的节点 | 未被擦元素保留 | 未被擦元素保留 | 删除原对象仍会结束其寿命 |
| unordered rehash | 失效 | 现存元素保留 | 旧 end 不继续使用；遍历顺序不保证 |
| unordered 插入 | 若 `(N+s) <= z·B` 则不使 iterator 失效，否则不能依赖保留 | 现存元素保留 | N 为原元素数，s 为实际新增数，z/B 为当前最大装载因子/原桶数 |
| unordered erase | 仅被擦元素失效 | 仅被擦元素失效 | 不能把被删元素的地址继续当身份 |

这些区别来自 [vector.modifiers](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L5984-L6078)、[deque.modifiers](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L3918-L4008) 和 [unord.req](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L3007-L3038)。读取或比较失效 iterator 不能作为试验判断；应按合同停用并重新获取，或使用 erase 等操作返回的合法位置。

**地址与身份反例**：整数数组 `[A,B,C,D]` 用“末项覆盖待删位置，再 pop_back”删除 B 后成为 `[A,D,C]`。这不是 vector::erase 的保序语义；位置 1 现在是 D，D 的反向索引必须从 3 改为 1。即使某个地址没变，持有“下标 1 就是 B”的调用者已经错了。`sort` 也可在不重分配的情况下改变位置上承载的值，所以不把 iterator 未失效解释为业务身份稳定。

稳定 handle 可表示为 `(slot,generation)`：解析时检查 slot 范围、占用标志和 generation 相等，再读 slot→dense 索引。删除 B 时撤销其占用并改变 generation；复用同一 slot 的新对象即使 dense 位置相同，也不能被 B 的旧 handle 访问。generation 计数会溢出，需足够宽度和明确的回绕/停止复用规则；它也不替代跨线程同步、对象所有权或悬空裸指针回收。handle 稳定的含义是能验证身份，不是保证对象永不被删除。

## 9. 把选择放回游戏热点

### 9.1 活跃实体：密集遍历与 ID 查询同时存在

若每 Tick 主要更新所有活跃实体，可把紧凑数组作为候选，再用 ID→slot 和 slot→dense 映射完成查询。删除采用保序 erase、swap-pop 或墓碑，由稳定顺序和引用需求决定。swap-pop 的主数组操作可以常数次完成，前提是移动/赋值成本、映射更新与删除策略已满足；额外 ID 哈希定位仍是平均/最坏不同的工作。

一次销毁必须使“主数组、反向映射、slot 占用/代数、待处理事件”一致。中途抛出或异步读发生时若只更新了一半，容器本身合法仍可能返回错误实体；工程上可限制该段操作不抛、预留必要容量、统一在受控阶段提交修改，或设计可恢复事务。这里是设计方案，未提供已测的 ECS 或服务器实现。

保留客户端 AoS/SoA 对照：如果只更新位置/速度，可比较拆字段数组；如果每次要调用多态行为、读大量冷状态，布局和间接访问收益要重新衡量。跨线程优先明确单写者或消息传递，发布不可变快照时还需安排旧快照的读者结束点和回收成本。

### 9.2 定时器与任务：低频更新还是频繁改期

每次取最早任务可用最小堆；取消/改期少时，可把 `(deadline, sequence, id, version)` 作为不可变条目，出队核对 version。频繁改期使旧条目积累时，索引堆或可管理句柄的结构可能更合适。一次 Tick 处理 k 个到期任务至少要做 k 次业务工作，不能因读 top O(1) 就称调度 O(1)。同 deadline 用明确 sequence 打破平局，序号溢出策略和确定性要求另列。

### 9.3 小集合、配置表与排序批次

少量技能标签/背包槽的连续线性扫描可作为候选，不预设“小于某 n 一定胜过哈希”。测量要同时改变键长度、命中位置、未命中比例和读写次数。读多写少的配置可使用排序数组，批量更新后重建；若要求稳定节点、在线中插或有序范围查询，树结构的维护代价可能值得承担。

批量键先排序再归并时，已经排序的两组大小 n/q 可在线性 O(n+q) 内归并；未排序时还要加排序、去重和恢复原请求顺序的成本。C++20 `std::sort` 对 n 项给出 O(n log n) 比较上界，键比较自身的成本另计；不能把所有排序算法都概括成同一个界。快照交换让读者看到完整版本，但旧/新副本并存增加峰值内存，回收不能由“指针已切换”推定完成。

### 9.4 空间邻域与高密度突发

AOI/近邻查询不只选 cell 内用 vector 还是链表，还要确定移动率、每格密度、每次查询访问范围和最终输出大小。vector 格在密度低、批量扫描多时可列候选；稳定挂链需求可能让侵入节点有价值，但销毁、跨格迁移和对象搬迁必须保持链接与索引一致。热点格拥挤时应测候选数、出入格成本和总 Tick 工作，不能从均匀分布下平均快推出高密度稳定。

## 10. 内存、局部性与实际预算

估算先列组成项，再测量：

| 候选 | 需要列入的内存项 | 峰值与观察边界 |
| --- | --- | --- |
| vector | 容量 C×sizeof(T)、容器状态、元素间接拥有的载荷 | 重分配时可能新旧缓冲并存；容量不是 size |
| 节点链/树 | 值、链接/平衡信息、对齐填充、分配元数据 | 对象池保留和碎片；不能只算 sizeof(value) |
| 哈希 | 桶、节点或槽、控制字节、负载率余量、键和值 | rehash 暂存与旧桶；具体布局由实现决定 |
| ID/handle 方案 | 主数组、正反索引、generation/占用位、待回收对象 | 索引数多会增加写放大及峰值 |
| 不可变快照 | 当前/待发布/尚有读者的旧版本 | 读者滞留时不能只按双份预算 |

CPU 缓存行大小、TLB、预取和分支预测由硬件决定；64 字节是常见取值而非 C++ 标准要求。结构体填充和对齐取决于类型/ABI；给对象过度对齐也可能增大工作集。紧凑索引可能降低带宽需求，却要付边界检查、解码或额外映射成本。

减少指针追踪、随机访问或间接调用是待测假设。批处理可能摊薄调用与检查，但优化器可能已消除部分工作，不能直接计算固定收益。若计划把“比较次数×每次常数”换成帧预算，必须先说明那个常数在目标平台如何测得，且覆盖缓存、分配、锁、I/O 和回收范围；O(log n) 只能约束算法工作，不保证操作系统调度下的最大完成时间。更完整的硬件观察方法见[处理器存储层次与性能工程](../../01-编程与计算机基础/硬件体系结构与性能/01-处理器存储层次与性能工程.md)。

## 11. C++20 与 UE 的边界

本篇具体标准合同只来自 N4861；不把相邻 C++23 STL 专篇的 `flat_map` 当作 C++20 标准容器。C++20 下“排序 vector”是可以讨论的表示方案，第三方 flat 容器则另核接口、失效和许可。

UE `TArray/TMap` 是工程候选名，不能因为分别像 vector/哈希表，就移植标准库的增长因子、句柄失效、异常安全或 allocator 行为。选定实际引擎版本后，应核对相应接口、元素 relocation 能力、Num/容量、移除是否保序和遍历顺序；本次未读取 UE checkout 或运行 Unreal Insights。UE 对象引用还需符合所用版本的 GC 可见性与所有权约定。普通指针容器不自动拥有/保活被指对象，标准智能指针也不能替代 Unreal 的对象管理合同。

跨容器/跨线程持有对象前，先画清所有者、最后访问者和销毁时机。要声明“帧内零分配”，必须覆盖主容器、元素成员、索引、日志/事件与后端资源，而不是仅见一次 reserve。资源和异常的详细处理继续由 STL/RAII 专篇负责，本篇不复制那组 allocator 实验。

每个候选必须实现相同业务语义和输出，明确计时边界，预先保存数据而非在计时区内临时随机生成。下面是设计输入，不是已运行数据：

| 内存 | 请求层分配次数/字节、峰值活分配、容器容量/桶数、RSS 的采样定义 | 不把资源接口次数当系统 malloc，不把累计字节当峰值 |

例如只比较精确查找，可先建同一组唯一键和值，保存相同查询顺序，输出每次“是否命中及值”或其可核对摘要；排序数组先完成排序，哈希先完成建表，再分别报告建表成本和只读查询成本。比较混合负载则把维护排序/映射/再哈希也计入。两种口径可同时给，但不能让一个方案只测查询、另一个含构建。

已知失败/成功的少量确定查询先核对正确性，计时结果继续消费为可观察输出，防止编译器删掉工作。校验和只是防删与初筛，可能碰撞，不替代完整正确性对照；不要把 console 输出放进单次查询计时内。预热必须记录次数与状态，冷启动实验另建初态，不能将已预热数据叫“冷缓存”。

### 12.3 输出、统计与停机条件

保存每轮原始样本、实际操作数、结果核对、完整命令、退出码和异常，记录构建/测量/回收时间。失败样本和中途终止保留，不删掉最慢结果后只报最佳轮。计时器单次读取的开销和精度应评估，短操作可批次计时。

- 吞吐是所声明计时区间内完成的业务操作数除以时长；明确多线程、失败/重试和未命中是否计数
- 批次 `elapsed/operations` 是每操作平均成本；对这些批均值取 P99 仍是“批均值 P99”，不是单操作 P99
- 若需要单操作尾延迟，需对应原始时间戳/测量方式并说明采样扰动；服务端请求延迟还要包含其声称范围内的排队，不能只测出队后的容器调用
- 说明分位数算法，例如对 s 个已排序样本采用 nearest-rank `ceil(p·s)`，并记录 s、重复轮次与离散程度；小样本的 P99 接近最大样本，并不等于可靠极端尾部估计
- P50/P95/P99、最大观察值、均值和吞吐各自回答不同问题；最大观察值不是最坏上界，不直接平均各线程/各轮的分位数来冒充总体分位数
- 性能采样可用目标平台适用的 perf、VTune、ETW 或 Unreal Insights；硬件事件是否可用、采样范围和归因另报告，不假设所有工具都直接提供同口径 cache miss

任何结果不一致、意外异常、样本不足、计时范围错误、热状态混杂或仪器误差主导，都应停下修正实验合同，不宣布性能胜出。每帧/Tick 门槛来自项目需求，不能从示例规模发明“通用 P99 预算”。差异小于不确定性时保留多个候选；微基准胜出后，仍需在真实业务回放和集成路径检验总耗时、峰值、回收与尾部。

## 13. 速查、FAQ 与评审模板

### 13.1 复杂度速查表

以下按常数大小键/值和相应结构不变量计操作次数；字符串、回调、分配/同步和结果输出另计。平均、均摊和最坏不能互相删除限定词。

| 结构/操作 | 计数级别 | 前提或例外 |
| --- | --- | --- |
| 数组、vector、deque 下标定位 | O(1) | 合法下标；deque 不保证连续 |
| vector 单元素尾插 | 均摊 O(1)，某次最坏 O(n) | 扩容与元素代价；固定数组没有同一扩容合同 |
| vector 中间单插/保序擦除 | 最坏 O(n) | 具体与后缀长度有关；尾删 O(1) |
| 链表按索引/值找位置 | 最坏 O(n) | 额外索引可换取维护成本 |
| 双链表已知合法位置单插/单删 | O(1) 次节点/元素操作 | 单链表删除需已知前驱；不含定位成本 |
| vector-backed 栈 push / pop | 均摊 O(1) / O(1) | push 的某次扩容 O(n) |
| deque 两端单插/单删 | O(1) 次元素操作 | 不保证无分配或固定耗时 |
| 固定容量环形队列单入/单出 | O(1) | 有效空满检查、固定元素操作成本、未计阻塞/同步 |
| unordered find | 平均 O(1)，最坏 O(n) | Hash/Pred 正确；输入分布/键成本影响实际耗时 |
| unordered rehash / reserve | 平均 O(n)，最坏 O(n²) | 参数分别为桶数/元素数，不等于查找成本 |
| 平衡树查找/普通单插 | O(log n) | 比较器合同；不包含所有特殊 hint/erase 重载 |
| 二叉堆访问根 / 删除根并修堆 | O(1) / O(log n) | 非空；底层操作与值成本另计 |
| 二叉堆插入后的修堆 | O(log n) | 底层 vector 扩容可使完整单次 push 达 O(n) |
| 自底向上建堆 | O(n) | 随机访问范围；不是 n 次独立插入 |
| 邻接表 BFS / DFS | O(V+E) | 一次标记和有界边处理，另计输出与栈空间 |
| 并查集 find/union | 序列均摊 O(α(n)) | 路径压缩+按秩/大小合并；不能写单次最坏 O(1) |
| 排序数组二分 / 单插 | O(log n) / O(n) | 同一比较语义，前者计随机访问范围 |
| trie 查询 | O(L) | 每符号子节点定位 O(1)，L 的编码单位固定 |
| 空间索引邻域查询 | 依访问桶/节点、候选 t、输出 k 而定 | 热点退化和更新成本单列 |

### 13.2 常见问题

**为什么 O(1) 哈希不一定比线性扫描快？** 哈希键处理、桶定位和间接访问有常数成本；小工作集可能很快扫描完。实际交叉点依输入与平台，不能用固定 n 保证。

**list 插入常数，所以更新多就用 list？** 先确认位置如何得到；线性定位、节点分配和读路径可能占主导。若需要保留稳定节点，这是语义约束，再找满足约束的实现。

**reserve 后引用就永久稳定吗？** 它只约束相应容量内插入不重分配。erase、中插、后续更大 reserve、容器销毁或业务排序，仍分别影响句柄或身份。

**哈希降低装载率就能保证 P99 吗？** 不能。坏散列、键成本、rehash、分配器和排队都有影响，P99 需要明确负载与实际样本。

**vector 存对象指针能否同时拿到连续性与稳定身份？** 连续的是指针槽；所指对象的地址/寿命由另一层所有者决定，间接访问与管理成本仍存在。销毁对象后指针容器不会自动清掉所有观察者。

**无锁队列能直接替换普通队列吗？** 先核生产者/消费者数量、顺序、满队列与回收语义，以及进度保证；同步正确性并不由容器平均复杂度推出。

**理论复杂度和基准曲线不同就是证明错了吗？** 先检查规模参数、工作单位、输入分布和计时范围。渐进界不描述小规模常数，也不能替正确性证明。
