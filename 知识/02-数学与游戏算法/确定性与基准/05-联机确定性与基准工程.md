## 1. 同一录像为什么仍可能走出两条路

假设两次运行读取同一张地图、同一批移动请求，也使用同一个seed，最后角色位置却不同。问题可能发生在寻路之前：同Tick两条事件的顺序变了；也可能发生在寻路之后：先完成的worker先改变了世界，后完成的worker看见另一份邻居状态。最后再把位置取整算hash，并不能把这两次执行变回相同。

我们需要分别回答三个问题：状态变化是否符合规则；声明的两次执行是否得到相同状态；完成这些工作用了多少资源。一个有缺陷的模拟可以每次都得到相同错误结果，一个正确实现也可能慢得不能上线。因此正确性、确定性和性能是三种判据，需要分别保留证据。

### 1.1 先把“相同”写成可以检验的承诺

本文把 `S_t` 定义为第t步已经完整提交后的权威状态，`I_t` 是从 `S_(t-1)` 推进到 `S_t` 的有序输入。固定版本R下：

```text
S_t = F_R(S_(t-1), I_t, h, 已接纳外部结果_t)
B_t = Encode_schema(S_t)
H_t = Hash_algorithm(B_t)
```

R包含会改变转移的代码、规则、资产及数值约定；随机状态若参与转移就是S的一部分。若F对所声明的输入域是单值的，两次初态、每步输入和F都相同，按步归纳才得到相同S。hash在这条因果链的末端，用于观察结果；它不会约束F怎样运行。

“同机同二进制重复”“不同线程数重复”“跨CPU/操作系统/编译器重复”是不同承诺。声明应列出实际支持的环境矩阵和比较口径。逐位一致比较规范状态字节；容差比较则必须说明具体字段、单位、阈值和允许后果，不能仍称逐位一致。客户端画面插值相近，也不是权威状态一致的证据。

Fiedler的lockstep文章强调相同初态、输入和步长，并将其ODE例的同机同构建结果与跨平台区分；这些限定适用于阅读它的实验，不能把文章里的演示当本项目运行结果。[一手来源](https://gafferongames.com/post/deterministic_lockstep/)

| 承诺的一部分 | 必须固定或记录的内容 | 不足以替代它的条件 |
| --- | --- | --- |
| 初态与版本 | 可恢复的完整状态、地图/导航/规则版本和所需资源 | 同地图文件名、同seed |
| 输入归属 | 已接受的Tick、唯一事件身份、同Tick全序、缺失/迟到政策 | 收到同一集合、按网络到达顺序处理 |
| 调度可见行为 | 读哪份稳定状态、任务合并与归约顺序、预算造成的决定 | 有锁、无数据竞争、线程数相同 |
| 数值 | 类型/宽度、单位、运算顺序、舍入/溢出、允许的浮点环境 | 固定dt、只把最终位置转整数 |
| 随机 | 引擎和映射版本、完整状态/缓存、逻辑流与消费轨迹 | 初始化seed相同 |
| 比较 | 同一提交切点、字段集合、顺序/编码/schema和hash版本 | 只比较终点、哈希函数相同 |

### 1.2 从接纳输入到提交状态的正常路径

1. **建立可比较基线。** 核对版本和初态；必要地图或规则不匹配就返回 `INCOMPARABLE`，不静默换成当前资产。基线对应真实一致切点，不能逐个读取活实体后贴上最后一个Tick号。
2. **形成I_t。** 权威侧验证目标、权限、导航版本、速度/碰撞约束；给已接受输入确定Tick和顺序。迟到输入可以拒绝、安排未来Tick，或进入项目既定回滚协议，政策和实际决定必须可重放。lockstep缺输入等待，不能当作所有服务器统一的迟到政策。
3. **只读上一份已确认状态进行计算。** 全局搜索、重规划、邻居查询和避障使用声明的版本与排序。并行任务的结果先归入稳定逻辑身份，再按规则合并；不得让完成先后隐式成为玩法顺序。
4. **按固定h推进并提交。** 只有实际完成的步才能成为S_t。调度器计划跑三步却只完成一步，不能记录三步成功。暂停、倍率和失败后的时间责任继续遵循GameClock。
5. **从这个切点编码并比较。** 保留当步输入、完整可诊断状态或恢复到该处的材料，计算B_t/H_t。分叉时定位首个不同的提交点，再查看字段及其生产过程。

这条路径是本文的集成设计推导。外部数据库回复、墙钟截止、异步寻路结果若影响权威决定，要变成已接纳输入并保存足够结果，或证明可以由受控状态唯一重建；回放时重新请求一次外部系统，不是重用原输入。网络复制录像和持久恢复日志各有职责，不能只因叫“Replay”就混用。

## 2. 两个实体、三个Tick：先把正常运行算清楚

### 2.1 题设和输入

这是一个刻意很小的一维整数移动模型，不含寻路、碰撞、随机、并行或网络。协议D1固定 `map=1、rules=1、h=1 tick`，位置单位为格，速度单位为格/tick；两个实体的永久ID为10和20，本例不复用ID。初态S0为 `10:(x=0,v=2)`、`20:(x=10,v=-1)`。

每步先按seq升序应用该Tick的速度事件，再对两个实体各执行一次 `x := x+v`。SET把v设为参数，ADD把参数加到v。本例输入已接纳，seq唯一；未知操作、身份或版本不属于成功域，真实入口必须在模拟前拒绝。不是任意Python对象的解析器。

| Tick | seq | 事件 |
| --- | --- | --- |
| 1 | 1 | SET(10,3) |
| 1 | 2 | ADD(10,-1) |
| 2 | 3 | SET(20,0) |
| 3 | 4 | ADD(10,1) |

### 2.2 状态怎样得到，比较什么

| 提交点 | 先应用事件后的速度 | 积分后10的(x,v) | 积分后20的(x,v) | 相同输入的第二次运行 |
| --- | --- | --- | --- | --- |
| S1 | 10先3再2；20仍-1 | (2,2) | (9,-1) | 完整状态相同 |
| S2 | 10仍2；20变0 | (4,2) | (9,0) | 完整状态相同 |
| S3 | 10变3；20仍0 | (7,3) | (9,0) | 完整状态相同 |

例如S2不只是 `x10=4`：下一步还需要v10=2；如果只保存位置，无法由它唯一推进。两实体在本例互不相互作用，所以积分循环顺序不影响数值，但序列化必须仍按ID排序，否则创建字典的顺序不同就会产生不同字节。这分别演示了“计算顺序是否有影响”和“输出顺序必须明确”。

D1的字节格式为两个ASCII字节 `D1`、一个无符号8位Tick，再按ID10、20各写 `ID:uint8、x:int16、v:int16`。多字节整数用大端；固定两个实体，无填充，共13字节。x/v按带符号16位字段表示，本例所有中间值也远在范围内；不能据此省略真实定点实现的溢出检查。D1本身绑定上面的固定规则，扩展地图、字段或步长就要更新协议，不能继续复用D1解释不同语义。

| 提交点 | B_t的完整十六进制，PAPER_EXPECTED | 校验结果 |
| --- | --- | --- |
| S1 | `4431010a00020002140009ffff` | 两次B1相同，所以SHA-256(B1)相同 |
| S2 | `4431020a000400021400090000` | 两次B2相同，所以SHA-256(B2)相同 |
| S3 | `4431030a000700031400090000` | 两次B3相同，所以SHA-256(B3)相同 |

表中没有填写臆造的摘要值。精确字节首先是可手工检查的预期，§3的一次局部运行又与这些字节逐字吻合；SHA-256用于展示实际系统常用的固定长度比较入口。Python的`struct`显式`>`采用大端、标准大小和无对齐填充；省略前缀默认native不能当跨平台协议。[struct文档](https://docs.python.org/3.12/library/struct.html)

### 2.3 一个反例：相同事件集合不等于相同输入序列

只把Tick1事件反过来：v10从2先ADD(-1)得到1，再SET(3)得到3。因此S1成为 `10:(3,3)、20:(9,-1)`，B1为 `4431010a00030003140009ffff`。第一处分叉就是Tick1，后续10的位置依次为6、10，而正确路线为4、7。

这个反例没有换seed、地图或Tick长度。它说明需要保存有序I_t，而且最终位置差不能直接归罪于浮点。调查应从S0、Tick1两条事件及速度更新开始，不必先分析Tick3的所有代码。

## 3. 一个完整而有限的教学入口

下面是Python 3.12标准库完整程序，本轮已用Python 3.12.14按第7节获批合同执行一次，实际记录见本节末尾。可整段保存为独立脚本；本次冻结文件名为 `determinism_demo.NOT_RUN.py`，名称沿用准备阶段，实际运行状态以本次记录为准。它只处理代码内写死的2实体、3Tick和4事件，执行3条轨迹共9步、18次位置更新；无输入文件、随机调用、线程、网络、计时或依赖安装。反序运行是故意注入的错误实现，不是允许的另一种规则。

```python
from hashlib import sha256
from struct import pack

# 已接纳的固定输入：(tick, seq, entity_id, operation, value)
EVENTS = (
    (1, 1, 10, "set", 3),
    (1, 2, 10, "add", -1),
    (2, 3, 20, "set", 0),
    (3, 4, 10, "add", 1),
)
EXPECTED = (
    bytes.fromhex("4431010a00020002140009ffff"),
    bytes.fromhex("4431020a000400021400090000"),
    bytes.fromhex("4431030a000700031400090000"),
)

def replay(reverse_storage=False, wrong_event_order=False):
    initial = ((10, 0, 2), (20, 10, -1))
    if reverse_storage:
        initial = tuple(reversed(initial))
    state = {entity_id: [x, v] for entity_id, x, v in initial}
    trace = []
    for tick in (1, 2, 3):
        events = sorted((e for e in EVENTS if e[0] == tick),
                        key=lambda e: e[1])
        if wrong_event_order and tick == 1:
            events.reverse()  # 仅作负向控制
        for _, _, entity_id, operation, value in events:
            if operation == "set":
                state[entity_id][1] = value
            elif operation == "add":
                state[entity_id][1] += value
            else:
                raise ValueError("unknown operation")
        for entity_id in sorted(state):
            state[entity_id][0] += state[entity_id][1]
        raw = b"D1" + pack(">B", tick)
        for entity_id in sorted(state):
            x, v = state[entity_id]
            raw += pack(">Bhh", entity_id, x, v)
        trace.append((raw, sha256(raw).digest()))
    return tuple(trace)

def first_byte_mismatch(a, b):
    if len(a) != len(b):
        raise ValueError("incomplete trace")
    for tick, (left, right) in enumerate(zip(a, b), start=1):
        if left[0] != right[0]:
            return tick
    return None

if __name__ == "__main__":
    first = replay()
    second = replay(reverse_storage=True)
    broken = replay(wrong_event_order=True)
    # 正确性预期独立写成固定字节，不只让同一实现互相比较。
    if tuple(row[0] for row in first) != EXPECTED:
        raise AssertionError("state trace differs from the paper oracle")
    if first != second:
        raise AssertionError("storage order changed canonical state/hash")
    if first_byte_mismatch(first, broken) != 1:
        raise AssertionError("negative control was not detected at tick 1")
    for tick, (raw, _) in enumerate(first, start=1):
        print(f"tick={tick} bytes={raw.hex()}")
    print("same_state_and_hash=True")
    print("first_byte_mismatch=1")
```

以下五行最初是PAPER_EXPECTED；本次唯一目标进程的完整stdout与其逐字相同，包括末行LF，共167字节。程序用显式异常而非会被`-O`移除的`assert`表达判据，未吞掉编码或摘要库异常。

```text
tick=1 bytes=4431010a00020002140009ffff
tick=2 bytes=4431020a000400021400090000
tick=3 bytes=4431030a000700031400090000
same_state_and_hash=True
first_byte_mismatch=1
```

这个入口同时检查人工状态预期、创建顺序变化后的规范编码，以及反序错误的首个字节分叉；不能据一次通过宣称寻路、RNG、并发或跨平台引擎确定。`hashlib.sha256`接收字节并生成摘要的接口由[Python文档](https://docs.python.org/3.12/library/hashlib.html)支持，D1格式和状态转移则是本文自己定义的教学协议。

## 4. 从小模型扩展到实际回放，哪些条件不能丢

### 4.1 固定时间步和执行顺序

固定h让每步执行相同的积分时间，渲染帧率可以不同；它不固定输入顺序，也不让不足预算的工作自动完成。用墙钟测调度和耗时是正常的，问题是把不可复现的观测直接放进玩法转移。Fiedler说明固定步与显示可以解耦，也讨论追赶过多导致过载；具体暂停、调速、已接纳时间和已提交Tick采用[GameClock GC2–GC5](../../07-网络与游戏服务端/运行调度与过载保护/12-世界时间确定性与GameClock.md)的合同。[固定步原文](https://gafferongames.com/post/fix_your_timestep/)

寻路尤其要区分两种预算：固定扩展最多2000个节点，在图、队列tie-break和计数定义都固定时，可以是确定的逻辑限制；“运行300微秒就停止”可能在两台机器停在不同节点。若后者改变权威结果，就要把实际结果、接纳/拒绝决定、所属Tick及顺序作为可重放输入保存；或采用结果与接纳顺序都能由受控状态唯一决定的逻辑预算。只固定提交边界并不够：两机都在Tick10提交，快机接纳新路径而慢机沿用旧路径，仍会分叉；按截止或完成先后选择结果时，仍需记录上述决定。2000和300仅为解释两种单位，均不是生产建议，也没有对应实测。

同理，并行任务各读S_(t-1)，把结果按实体ID/请求ID合并，可以避免“先完成者先影响后者”的一类差异，但仍要控制共享随机消费和浮点归约。给全局数组写入加mutex只防止同时写坏，抢锁先后仍可改变数组顺序。Box2D作者的2024案例专门区分算法、多线程和跨平台确定性，并给出按稳定身份组合工作结果的实现思路；它不证明本项目已采用同样设计。[Box2D原文](https://box2d.org/posts/2024/08/determinism/)

需要一个完整tie-break：例如A*键为 `(f,h,nodeStableID)`，邻居键为 `(distanceKey,entityStableID)`。它必须符合所用容器的比较器要求；近似相等关系未必传递，不能把随意epsilon比较塞进排序。ID复用时须带代次或等价身份，不用指针地址作持久顺序。候选集本身也应由同一权威快照产生，最后排序不能补回漏掉的邻居。

### 4.2 浮点和定点是不同数值合同

相同类型名与相同源码不足以指定完整浮点计算。以binary32、逐操作舍入到最近值且中点取偶为题设，`(16777216+1)-16777216`先把中间值舍回16777216，结果为0；`16777216+(1-16777216)`的结果为1。这个纸例说明改变结合顺序即可改变结果，不是本轮编译器实验。

因此跨平台浮点承诺需要明确目标架构、编译器与优化、计算精度、运算/归约顺序、舍入、非正规数处理、数学库及特殊值政策。LLVM 18.1.8分别定义`reassoc`、`contract`、`afn`以及NaN/Inf/有符号零相关标志；`fast`集合允许的变化不能被“数值上差不多”消掉。控制这些选项是约束条件，还需实际平台矩阵验证；没有一个选项独自提供游戏全局确定性。[固定版本LLVM文档](https://releases.llvm.org/18.1.8/docs/LangRef.html#fast-math-flags)

定点把关键量表示为有尺度的整数，例如毫米、格或成本千分位，能使协议更明确，但需要规定乘除中间宽度、舍入/负数除法、最大范围、溢出拒绝或其他指定政策。`int64`不是无限范围。平方距离可能先溢出，不能等转换浮点后再“修正”。也不能在决定碰撞或路径分支时偷偷转float而仍声称全程整数。

可以用整数/定点决定权威路径、门和命中，用浮点做客户端动画与插值；这是适用时的工程选择，不是所有游戏必须使用定点。Box2D的具体浮点实现与支持环境也说明“使用浮点必然不能跨平台”过强。NaN/Inf应在定义的入口/运算边界拒绝或作明确处理；若按位哈希浮点，还要决定负零和NaN的表示语义，不能一边规范化丢差异，一边允许那些差异影响后续F。

### 4.3 随机流：固定seed之后还需要什么

将随机流绑定稳定的逻辑对象，如match、系统、实体/代次或事件，避免绑定worker号和完成先后。两种常见选择是持久子流及其完整状态，或按事件身份与draw索引求值的固定算法。前者记录状态与调用轨迹；后者固定编码、算法版本、索引和碰撞/重复身份政策。不是每次调用都用同一个seed重新初始化，也不是无条件要求把当前Tick放入每种seed公式。

纸面例：共享流的下一批原始值为 `[5,8,2]`，AI先取5，掉落取8；若AI新增一次消费，掉落就改取2。初始seed没有改变。拆成AI和掉落两条逻辑流可隔离这种消费耦合，但仍需各流自身版本、状态、整数映射和失败消费一致；隔离消费并不自动证明统计独立或密码安全。

PCG minimal C文档区分初始化状态与stream选择，支持显式保存/使用独立生成器对象；它的API示例不是任意语言的通用序列协议。[PCG作者文档](https://www.pcg-random.org/using-pcg-c-basic.html)。引擎、distribution缓存、拒绝映射及失败消费的准确合同见[随机数与洗牌 §4](../随机采样与程序化生成/01-随机数与洗牌算法.md)。原文`Mix64`仅为占位思路，保存在修订前版本中；它没有给出可据以跨语言重放的实际派生实现。

### 4.4 状态hash的三种盲区

**第一，遗漏未来状态。** 两个实体当前位置同为0，但速度分别为1和2，位置hash可以相同，下一Tick已不同。真实寻路系统还可能需要路径游标、目标/导航版本、搜索中的队列或能唯一重建它的材料、随机状态、待处理输入和决定。并非所有缓存都必须原样序列化：能证明不影响F且可从规范状态重建的缓存可以省略；缓存淘汰或命中会影响预算/结果时就要重新判断。

**第二，比较前丢失差异。** 将1.04与1.03按同一规则量化到0.1得到1.0，摘要相同；若原浮点仍参与后续 `x>1.035`，两边决策已经不同。只有权威状态本身就是该量化整数，或已经证明该等价类对所有后续转移封闭，才能把这种比较称为对应范围的精确状态比较。否则只能说量化字段暂时相同。

**第三，把摘要相同当证明。** 有限摘要可能碰撞，错误字段集合也可能让不同真实状态产生相同B。摘要相同提供的是所选检查下未检测到差异；摘要不同说明输入字节不同，不直接告诉你哪个业务字段错。无密钥hash也不能认证来源或写权。对小例直接比较B，对大状态在首个摘要差处展开规范字段/子系统摘要及对应输入，保留可复核证据。

计算hash前要固定字段顺序、实体顺序、整数端序/宽度、字符串编码、集合长度、空值与schema。不能hash包含padding、指针或未初始化内容的原生对象内存。一次字段集合的一致切点问题归[世界Snapshot §2.2](../../07-网络与游戏服务端/世界权威与故障恢复/13-世界Snapshot与故障恢复.md)；每个字段各自atomic或者checksum正确，都不能证明它们来自同一时刻。恢复已决定结果事件与重新模拟原始输入，也是该篇明确区分的两条路线。

### 4.5 怎样定位第一处分叉

先核比较对象的版本与轨迹是否完整。环境本来不在承诺矩阵、资产不匹配或日志缺段，应报不可比较/不完整，不把它归为零分叉。然后从初态起按提交点比较B或H；发现不同，保留之前最近可用完整快照、当步输入顺序、相关逻辑流状态、导航/实体版本以及字段差异。

只存每100Tick的hash时，第100Tick不同只能把问题界定在一个区间，需从可信快照重放并逐步比较才能细化。最终状态重新相同也不能排除中途已经分叉；没有额外单调性证明，不用“最终hash相同”跳过整段，更不能对普通状态hash盲目二分假定差异一旦出现就永不消失。失败输入应最小化，但保留使问题成立的版本、顺序、失败消费和首分叉Tick。

## 5. 寻路基准：相同工作，再比较代价

### 5.1 明确基准单位和可比性

一条回放轨迹通常比较“相同初态与有序输入下的状态序列”；一个性能样本可以是一次寻路计算，也可以是请求入队到返回的端到端延迟。后两者计时范围不同。若声称服务端容量，排队、调度、并发竞争、网络和失败都不能由一个函数耗时推出来。

可比较报告至少固定或明确标注变化的维度：地图内容或生成器版本/seed、坐标系和单位、导航profile与Tile、障碍形状/密度/轨迹/更新频率、实体数量/半径/速度、起终点分布、查询批次顺序、实现提交与构建产物、编译器/优化/目标架构、CPU/OS/线程数、预热及采样规则、计时/内存口径。比较新旧实现时有意改变的实现版本是实验因素，其他无关条件应受控；平台或负载变化就另分组，不能硬并成同一基线。

原C++ `RunCase`展示的计时只包住`Replan`，不含其外部准备与入队等待；`BytesInUse`也不能凭名字代表全进程峰值。原`Budget{2000,300}`没有字段定义，不应猜它已实现节点/微秒的双重约束。这些节选仍按历史设计材料解释。真实runner应按既定样本数完成、逐条保存结果与退出/超时，不反复重跑直到凑出“足够成功”。

| S0 | 小型室内 | 低 | 32 | 0 | 均匀 | 路径可行性及成本oracle |

### 5.3 指标从问题推导，失败单独保留

| 指标 | 明确测量对象 | 常见误读 |
| --- | --- | --- |
| 扩展节点、重复条目、最大Open List | 哪个循环算一次扩展；累计或每查询 | 函数调用数当实际工作量 |
| 路径成本/长度 | 图成本、多边形走廊、漏斗折线或积分轨迹；单位 | 同成本要求同一节点序列 |
| 重规划耗时 | 包含更新、队列维护还是只含求解；是否含等待 | 函数快等于端到端快 |
| P50/P95/P99 | 样本集合、数量、预热、分位算法及单位 | 少数样本的P99当稳定线上尾部 |
| 内存 | 导航数据、搜索节点、邻居/路径缓存、回放、临时分配；存量或峰值 | 自定义分配计数当RSS峰值 |
| 失败与未完成 | 无路、预算耗尽、版本冲突、几何校验失败、数据缺失、超时/进程异常各自计数 | 删除失败样本后仍称总失败率 |
| 回放分叉 | 完整且可比较的轨迹数、首处分叉Tick及字段 | 缺日志也算零分叉 |
| 群体行为 | 邻居候选/截断、约束数、卡住事件和回退层级 | 只看最终到达忽略抖动或退化 |

无路可能是场景的正确结果；只有在存在可行路的oracle下误报无路，才是相应正确性错误。预算耗尽属于政策终态，也不能和算法证明不可达混淆。耗时报告可以分别展示所有已观测终态的响应延迟和成功查询耗时，必须标明分母；超时只能提供观测至截止的时间，不能装成底层实际完成耗时。保留已开始但未完成的尝试，解释进程失败造成的样本缺口。

Python `perf_counter_ns`适合读取短时性能计数的整数纳秒差，包含等待/睡眠经过的时间；它不是CPU执行时间，返回单位也不证明实际分辨率达到1ns。只能在其适用时钟域取差。CPU时间与端到端时间分别选择明确指标。[Python time](https://docs.python.org/3.12/library/time.html)

### 5.4 手算百分位，避免输出一个含糊的P99

保留原文线性插值口径：对n个升序样本，位置为 `(n-1)q`，取相邻值线性插值。人工样本 `[10,20,30,40,100]` 微秒，n=5：P50=30，P95的位置3.8，结果88；P99的位置3.96，结果97.6。它们是**PAPER_EXPECTED的汇总算术**，不是本文测量过五次查询，也不能代表一个服务的尾延迟。

选择另一种合法分位定义可能得到不同数字，所以基线与候选必须沿用同一算法。空样本不应由`NaN`掩盖成有效报告：返回 `NO_SAMPLES`/不完整及原因，不判pass。原Python示意对空集合的median/max/division未完整处理，属于修订前版本的示意代码；它不作为当前完整runner。冷启动和热缓存分组，固定预热排除范围，保留各批次与失败记录。

### 5.5 正确性/确定性门禁先于性能门禁

寻路正例可在同一静态图和同一代价模型上，以已知最优算法作oracle，核路径每段可行且成本相同；成立前提包括图、代价、搜索终止和精度/容差，不能只把另一个实现叫“A*”就当真值。相同最优成本可能有多条路径，tie-break影响路径身份，不应当作允许更差成本的借口。

继续保留原有属性测试意图：障碍新增使穿越区域的旧路径失效或触发重规划；障碍移除且版本已完成时不要误判不可达；邻居顺序只依赖固定输入键；非法浮点不扩散；同一完整输入下逐Tick状态符合承诺。需要能触发错误的负向控制，例如本篇Tick1反序、漏掉速度字段、故意不规范实体输出顺序。固定输入重复两次只检一种关系，不能替代独立规则预期或路径可行性检查。

再按场景比较性能阈值。例如原文“P95≤基线×1.15且≤2ms”只是阈值设计例：若基线1ms、候选1.2ms，绝对值虽低于2ms，相对门仍失败；这些数值需项目预算支持，本文没有测得它们。失败率常以绝对百分点差解释，路径质量、失败率和完整回放各有自己的门，不能靠更快掩盖错误。

判定建议至少区分 `PASS / REGRESSION / INCOMPARABLE / INCOMPLETE`。版本或测量方法改变而不满足比较合同，用INCOMPARABLE；漏样本/进程失败用INCOMPLETE；已运行的明确阈值失败用REGRESSION。不能把“未运行”默认当通过，更新golden hash前须解释规则变化并评估正确性，不为了让CI变绿盲目覆盖。

### 5.6 报告必须能回到原样本

报告从运行身份连接到输入清单、实现/构建、环境、逐样本原始输出和失败，再给汇总/门禁结果。schema要带版本，时间与内存带单位，原始样本要能识别caseId和试次；结果摘要不是原始观测的替代品。

原文YAML中的 `local-commit`、`recorded-by-runner`、`...`和P99=700us等数值位于“报告格式”示例，仍按修订前版本中的示例解释，不把它转换成本轮测量或直接否认其他历史实验。库内确有[A*历史结果](../../../evidence/algorithms/astar/results/astar_benchmark_win_x64_msvc.txt)及[runner入口](../../../evidence/algorithms/astar/scripts/run_benchmark.py)，用于追溯它们自己的局部工作负载；本轮只定位/读取已有文本，没有重跑，也没有从它们推导本篇跨平台或在线容量结论。原结果中的异常比值不在本次改写范围，不据其异常删掉整份资料或编造修正值。

| 预算与可靠性 | 请求含requesterId/requestId、优先级、期限、地图和目标版本；容量不足按规则拒绝/延后 | 合并可替代旧目标、限制队列；相同身份异参要冲突，不能借幂等返回错目标结果 |
| 重启、迁移与持久回放 | 携有效版本与完整恢复材料，明确原输入重演还是已决定结果恢复 | 路径缓存命中和内存hash不是耐久、幂等或写权证明 |
| AI评测 | 同时看路径质量、卡住、回放分叉和资源；保存第一处分叉所需材料 | 只看是否到达漏掉尾延迟、退化和权威违规 |

本篇不为这些系统增加一个通用异步/恢复框架。所需导航、AOI、时间权威和恢复能力分别链接到原责任文档；本文只说明它们交给回放/基准的数据为何必须完整且可解释。
