# 13 本地化发布工作流：身份、翻译制品与运行时可用性

> 版本基准：UE 5.6 官方固定版本页中本轮实际选读的章节；HTTP 200 空壳的 FText::FromStringTable 独立 API 页未作为签名证据，本轮未核读引擎源码。
> 最后更新：2026-10-10
> 知识成熟度：L2。主要承诺是本地化发布机制与失败边界的静态教学；2026-10-10 选读 Epic **UE 5.6** 官方版本页，页面标题与版本参数一致。本文没有运行 UE、Gather、翻译导入、Compile、Cook、Stage、打包或目标设备测试；示例与案例均为 `PAPER_EXPECTED`，运行结果均为 `NOT_RUN`，不构成可用实现或发布通过证据。
>
> 历史初稿标注 UE 5.8.0 / CL 55116800 与“本机逐项核对”。本轮未访问该引擎 checkout，也未重证这些历史记录；不把它们沿用为本轮事实。本文改以实际读取的 5.6 资料为边界，迁往项目的具体引擎版本仍须重核配置、工具与资源行为。版本页是文档定位，不是不可变源码 commit。

## 1. 本篇负责什么：同一条文案如何完整到达玩家

一条按钮文本在开发机上显示法语，不等于发行包已支持法语。可能只有编辑器加载了译文，也可能项目刚导入了新的 PO，而发行包仍带旧 LocRes。发布要连续证明：文本身份没有错配；当前源文对应的译文已审校；编译资源来自该次输入；所需数据确实进入目标包；运行时加载了该目标、语言及依赖；最终显示与交互可用。

读者是客户端、本地化负责人、构建与 QA。输入包括固定项目版本、文本与资产、目标文化、Target 配置、翻译交付版本及发布平台；输出是可追溯的本地化制品和验收记录。没有明确目标文化、内容快照或负责人时，先补合同，不能用“翻译率 100%”替代发布决定。

本篇保持原有的 Gather → 翻译 → 导入 → 发布主责，补齐中间独立的 Compile、Cook、Stage 与加载证据。FText 与字符串表只解释会影响此链的边界，内存实现读[文本类型底层](../../03-引擎架构与资源系统/对象模型与生命周期/10-FName与FString底层.md)；通用构建参数读[UAT 与自动化打包](../构建编译与制品/02-UAT与自动化打包.md)；体验矩阵读[本地化、无障碍与多端验收](../../05-Gameplay与交互系统/界面设置与无障碍/10-本地化无障碍与多端体验验收.md)。这些是职责导航，邻篇存在不等于它们所有历史结论都已复核。

### 1.1 先拆开几个容易混淆的对象

| 对象 | 它回答的问题 | 不能由它单独证明什么 |
| --- | --- | --- |
| Localization Target | 哪些来源组成一个翻译与加载单元，原生文化是什么 | 不是 UBT 构建 Target；创建成功不保证运行时加载 |
| 文本 identity | 同一 namespace/key 指哪条可本地化文本 | 不是显示字符串，也不是 FName 内部索引 |
| Source String | 译文针对哪一版源文，是否已过时 | 相同 key 不证明旧译文仍适合新语义 |
| Language / Locale | 选哪套翻译 / 用哪套数字日期格式 | 设置成功不证明对应资源已进包 |
| Asset group culture | 某组资产独立使用什么文化，例如语音 | 不自动替换已经加载的资产实例 |
| `.manifest` / `.archive` / `.po` | 收集清单 / 按文化的译文数据 / 交换格式 | 都不是“将 PO 放进包就能运行” |
| `.locres` / `.locmeta` | 编译的译文资源 / Target 元数据 | 文件存在不证明版本、Stage 或加载策略正确 |

此处 `.manifest` 是 UE 本地化产物，与知识库自己的机械文件清单无关。概念和制品分工依据[Overview 的 Localization Targets / Localization Pipeline](https://dev.epicgames.com/documentation/en-us/unreal-engine/localization-overview-for-unreal-engine?application_version=5.6)。

## 2. 发布输入先定身份，再处理显示文本

### 2.1 FName、FString 与 FText 不能互相替代责任

- `FName` 服务于名字和标识的查找、比较；不承载翻译关系。其名称比较有大小写不敏感语义，不用它的进程内索引充当跨版本文案 ID。把它 `FromName` 转为 FText，也不会凭空产生本地化条目。
- `FString` 服务于可操作的字符串，例如文件路径或外部 API 数据；它没有 FText 的本地化历史。适合做边界上的字符串处理，不能作为保存翻译身份的方法。
- `FText` 是面向用户的文本载体，支持本地化、格式化和文化相关生成；**不是所有 FText 都有 namespace/key，也不是所有 FText 都可被 Gather**。空文本、文化不变文本、数字生成文本、字符串表引用与本地化 literal 的来历不同。

`FText::ToString()` 得到当下显示字符串，会丢掉本地化历史；再 `FromString()` 不会自动恢复原 identity。5.6 文档还明确区分 Editor 与非 Editor：`FromString` 在非 Editor 构建等同非本地化文本；Editor 中未标记 culture-invariant，保存到资产 FText 属性后可能变成可本地化文本。因此“Editor 里能翻译”不能证明运行时从字符串构造的文案也能翻译。依据 [FText Conversion](https://dev.epicgames.com/documentation/en-us/unreal-engine/ftext-in-unreal-engine?application_version=5.6) 与 [FName Conversions](https://dev.epicgames.com/documentation/en-us/unreal-engine/fname-in-unreal-engine?application_version=5.6)。

工程规则：需要翻译的固定 UI 语句保留 FText 来历直到显示；外部玩家名等按产品语义作为文化不变参数，既不送去翻译，也不拿它作格式模板。业务 ID 与显示名分开保存；不能用翻译后的“开始”反推业务动作。需要序列化文本身份时核对专门的文本序列化/编组机制，不把 ToString/FromString 当无损序列化协议。

### 2.2 namespace/key、源文本、译文分别变化

对于本地化 literal，namespace 与 key 组成 identity，Source String 提供翻译源文及过时检查依据。可见文字相同，不代表语义相同：菜单的 “Open” 与状态的 “Open” 可能需要不同词形，应有独立上下文/身份；反之，同一含义的统一术语可用字符串表共享。

| 改动 | 要追踪的影响 | 发布前动作 |
| --- | --- | --- |
| key 不变，源文从 “Delete” 改为 “Delete permanently” | 旧译文可能遗漏重要含义 | 重 Gather、审查 stale、重新翻译/批准、Compile，再确认包内版本 |
| 源文相同但 namespace/key 改名 | 新旧身份是否映射；旧引用与翻译资产可能断开 | 给出显式迁移方案和差异记录，不假设工具自动保留所有译文 |
| 两个来源同 identity 却有不同源文 | 同一个键承担互相矛盾的语义 | 修复身份冲突，禁止用最后写入覆盖掩盖问题 |
| 同一字符串表条目被复用到不同语境 | 译者只能给同一个身份一个语义 | 拆开确实不同的含义，附使用位置和完整句子 |
| 只修改译文、不改源文 | identity 仍相同，但运行资源已过期 | 导入后 Compile；Stage 的摘要必须对应新产物 |

稳定 key 的价值是减少无意义的身份抖动，**不豁免源文改动后的审校**。5.6 Overview 说明外语以原生文化文本作为翻译源，原生文本变化会使外语译文 stale；编译步骤有允许 stale 的选项。本文的发布建议是：关键操作默认不接受未经审查的 stale；如产品接受例外，记录具体条目、理由、期限和批准者，而不是悄悄放宽整个 Target。

`LOCTEXT` / `NSLOCTEXT` 声明可本地化 literal；`INVTEXT` / `AsCultureInvariant` 则是刻意不参与翻译的文本。不能把 INVTEXT 列进可翻译声明名单。依据 [Text Literals 与 culture-invariant 说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/text-localization-in-unreal-engine?application_version=5.6)。

## 3. 完整句子、参数类型与文化切换是一份合同

先让译者能改变语序，再让引擎按目标语言处理复数等规则。不要先把一句话拆成数个独立译文片段，再按英语语序拼回去；片段各自正确，整句仍可能错误。命名参数让用途清楚，但名称稳定不是自动校验器：项目须另外验证源/译模板的参数集合、类型、修饰符和代表输入。

下面是自拟 C++ **机制示意**，`PAPER_EXPECTED / NOT_RUN`。只展示文本构造，未包含项目头文件、模块依赖、UI 生命周期、Gather 设置或资产配置，未编译，不是可直接运行的工程：

```cpp
#define LOCTEXT_NAMESPACE "InventoryUI"

// Count 是数值参数；PlayerName 是外部昵称，不能作为模板执行。
FFormatNamedArguments Args;
Args.Add(TEXT("Count"), ItemCount);
Args.Add(TEXT("Player"), FText::AsCultureInvariant(PlayerName));
const FText Pattern = LOCTEXT(
    "PlayerItemCount",
    "{Player} has {Count} {Count}|plural(one=item,other=items).");
const FText Label = FText::Format(Pattern, Args);

#undef LOCTEXT_NAMESPACE
```

在英语源文、昵称 Ada、整数 1/2 的假设下，纸面预期分别为 “Ada has 1 item.” 与 “Ada has 2 items.”。翻译者可以将 `{Player}`、`{Count}` 重排，并为目标文化提供适当词形；不要把英语 `Count == 1` 分支硬编码成所有语言的规则。数值先转成“2”这样的 FText 再作为复数判定参数，会丢掉本例需要的数值类型合同，应保留数值实参。

5.6 的 plural/ordinal 按文化的 CLDR 规则选择 `zero/one/two/few/many/other` 等类别；类别不等于数字字面值，例如不能把 `zero` 解释为所有语言都自动在 0 时命中。项目应为实际支持的文化与参数范围挑样例，包含 0、1、2、其他整数，允许小数时再加小数边界。`gender` 接收 `ETextGender`，分支顺序为 masculine、feminine、可选 neuter；这是一种语法参数，不是要求推断或收集玩家性别。物品名的语法性别也不保证从任意词条自动推导，优先写可完整翻译的句子。依据 [Text Formatting / Argument Modifiers](https://dev.epicgames.com/documentation/en-us/unreal-engine/text-localization-in-unreal-engine?application_version=5.6)。

数值、百分比、日期时间应保留数值或时间语义，再用文化相关生成方法。货币必须明确币种和金额单位；地区格式不替你决定汇率或价格。日期必须明确输入是否 UTC 以及目标时区，不能把已经转换过的本地时间又当 UTC 转一次。此处给出的是输入合同，不提供未验证的货币单位代码或时区封装。

### 3.1 改 Language 不等于改 Locale，也不等于重载语音

[Managing the Active Culture](https://dev.epicgames.com/documentation/en-us/unreal-engine/managing-the-active-culture-at-runtime?application_version=5.6) 将三者分开：Language 决定翻译资源，Locale 决定数字/日期等格式，Asset group culture 可让语音与 UI 分离。`SetCurrentCulture` 作用于整体；想保留“法语界面、日语语音”等选择时，应使用符合产品语义的分开设置并回读，不以一个笼统 Culture 字段覆盖所有偏好。

文本历史支持文化变化后的重建；这不意味着应用层提前缓存的 FString、截屏纹理、排序结果或任何自制 UI 缓存也自动更新。发布验收至少记录：切换前后请求值、实际 Language/Locale/语音组值、同一个已显示控件的更新、重开页面的结果及重启后的持久化结果。若产品只承诺重启后生效，就在用户流程与测试中一致执行，不能宣传即时切换。

文化回退也不是任意字符串前缀裁剪：实际支持文化、映射、限制、ICU 数据与已加载资源共同决定选择。对 `zh-Hans` / `zh-Hant` 等脚本分支应按目标市场明确提供与验证；缺少目标语言时“能显示源文”只是一种降级，不表示该语言已验收通过。只更改 Locale 的测试应保持语言合同不变，只更改 Language 的测试应检查格式是否按产品策略变化。

## 4. 字符串表是共享来源，还需要加载、持有与进包证据

[5.6 String Tables](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-string-tables-for-text-in-unreal-engine?application_version=5.6) 支持 C++ 定义、CSV 与 String Table 资产；条目通过表 ID 和 key 引用。表中的源文仍走本地化管线，不是把每种语言直接塞进任意 CSV 列就完成翻译。CSV 的基本列为 Key、SourceString，额外列可作元数据；它与翻译用 PO、对话用 Dialogue CSV 是三种不同合同。

| 来源形态 | 发布需要确认 | 常见假阳性 |
| --- | --- | --- |
| C++ 注册的表 | 注册时机早于使用；退出/模块卸载后不再使用失效来源；收集覆盖对应定义 | 调试路径先注册了，冷启动另一入口却先取文本 |
| `LOCTABLE_FROMFILE_X` 读取 CSV | 正确相对根、编码/转义、实际 CSV 在 Stage 产物中；所有目标平台可读 | Editor 文件监视自动重导入有效，误以为发行包也自动发现更新 |
| String Table 资产 | 资产进入 Cook/Stage，路径/重定向有效，运行加载完成且生命周期覆盖使用期 | 表只在编辑器中被手动打开，测试时碰巧已加载 |

官方明确：CSV 字符串表**不会自动 Stage**，文件监视重导入也只适用于 Editor 构建。运行时读 CSV 与把 CSV 导入成资产是不同部署方式；前者需要项目配置非资产目录的打包，后者验证实际资产依赖，不应把同一个源 CSV 一律额外发到用户设备。

### 4.1 “找到了引用”与“资源可用”分开验证

[String Table Loading Policy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/EStringTableLoadingPolicy?application_version=5.6) 的区别是：

- `Find` 只查找，不尝试加载。
- `FindOrLoad` 可以尝试加载，但查到的表不保证已经完整加载。
- `FindOrFullyLoad` 会尝试获得完整加载状态，可能阻塞；只在确认可安全阻塞的位置谨慎使用，不能放进任意 Tick/UI 绘制来掩盖加载顺序错误。

[FStringTableRegistry](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/FStringTableRegistry?application_version=5.6) 的内部查表入口明确可能在找不到条目时返回占位 FText；所以“返回了一个 FText 值”不是成功判据。表不存在与 key 不存在要分别报错，不能把占位文字当业务译文。

发布合同应另有明确的资源 owner：由谁加载/注册、什么时候算 ready、在控件或会话使用期间由谁保持有效引用、何时允许卸载/注销、失败时展示什么。保留 FText 历史与资产持有是两个不同问题；本轮未读项目 UObject/GC 实现，不声称任意 FText 引用总能或总不能保活 UStringTable。要获得该项目结论，需在实际加载方案中记录 owner、完成回调、GC/卸载压力下的结果，再验收。

本篇建议冷启动直接打开依赖该表的最早页面，并覆盖关页重开、地图切换或模块卸载、文化切换后的重复访问。查表前临时打开所有资产会污染测试条件。重命名表/键时，5.6 支持表或键重定向与资产 Redirector；迁移仍须核对历史引用、打包后重定向和删除旧条目的时机，不能仅凭 Editor 中不报错就删掉旧入口。

## 5. Gather 的范围、缓存与 Target 加载策略

Localization Dashboard 围绕 Target 管理收集来源和文化。5.6 文档建议一般项目从 Game Target 开始；拆插件/DLC Target 应有独立内容、加载/分发边界或交付责任，不因文案多就机械拆分。新 Target 的 loading policy 必须适合运行场景，通常是 Game；**收集配置存在不等于运行时会加载该 Target**。依据 [Localization Tools](https://dev.epicgames.com/documentation/en-us/unreal-engine/localization-tools-in-unreal-engine?application_version=5.6)。

正式收集前固定一份输入记录：

| 输入项 | 最小记录 | 目的 |
| --- | --- | --- |
| 项目版本与引擎 | commit、引擎版本/构建标识、构建配置 | 使后续文本与制品可以追到同一输入 |
| Target | 名称、原生文化、目标文化、loading policy | 防止 Editor-only 目标被当发行目标 |
| Gather 范围 | 源码/资产 include、exclude、插件与依赖、实际生成的配置 | 解释漏收、重复收集及来源归属 |
| 语义数据 | namespace/key/source、使用位置、译者注释 | 让翻译与冲突处理能定位到源 |
| 缓存与报告 | 资产保存状态、cache 检查策略、Gather 日志及差异 | 避免把旧缓存误当当前资产文本 |

Gather 只覆盖配置纳入且被收集器识别的来源，不是扫描项目运行时出现过的每个字符串。`LOCTEXT` 等需要按工具支持的形式使用；把任意运行时数据包装成 FText 不会自动被离线收集。资产侧还有可收集性检查；文化不变、空/纯空白文本及字符串表引用本身不通过相同的资产文本收集条件。表引用不会重复成为一份源文，但**表的定义/来源仍要进入相应收集范围**。

[Pipeline Optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/pipeline-optimization-for-localization-in-unreal-engine?application_version=5.6) 说明部分资产利用保存时生成的 gather cache，含字节码的资产可能仍需加载。`ReportStaleGatherCache` 是报告入口；`FixStaleGatherCache` / `FixMissingGatherCache` 会尝试重存资产，属于写入操作。先固定内容版本、保存报告并评估影响，再按项目授权修复，不把它们当无副作用的验收开关。这里不运行这些流程，也不提供脱离项目的“一键修复”脚本。

用 Dashboard 生成的 commandlet 配置作为自动化输入，记录它的版本和实参。Dashboard 配置与 commandlet 配置布局不同，不能把某个 UI 设置文件直接当等价命令行配置。本文不复用旧稿那些只凭文件名推断出的 5.8 命令let行为，也不声称某个旧导入/导出命令不存在。

## 6. 翻译交换、Import 与 Compile 各自交付什么

### 6.1 按同一内容快照迭代，保留“过时”状态

1. 固定项目及 Target 输入，Gather 得到该次收集清单；检查新增、删除、冲突和异常减少，不能只看命令退出码。
2. 导出对应文化的 PO，与上下文、术语表、截图/使用位置及输入版本一起交译者；记录该交付面向哪份源文。
3. 返回后核对 Target、文化、格式模式与基线；不要把来自另一分支或旧源文的文件直接当当前译文。先对照变化，再 Import。
4. Import 更新译文数据后，审查未翻译、Needs Review 与 Completed；这些状态描述文本数据与源文的关系，Completed 仍不等于语境质量、字体或打包通过。
5. 按当前翻译数据执行独立的 **Compile**，保留日志与 `.locres` / `.locmeta` 摘要；确认产物来自本轮输入，而非目录中遗留的旧文件。
6. 再进入 Cook/Stage/Package 与目标运行验收；任何上游输入变化都重建受影响产物，不能沿用下游旧通过记录。

这是本文建议的追溯流程，具体按钮和自动化参数以目标版本生成配置为准。5.6 [Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/localization-overview-for-unreal-engine?application_version=5.6) 区分 Manifest（收集时重生成）、Archive（按文化管理译文，收集/导入会清理旧来源）、PO（交换）、LocRes/LocMeta（编译后供运行时并 Stage）。它们的生命周期不同，不能手改 Manifest 后期望下次 Gather 保留，更不能把翻译导入成功当作运行资源已更新。

### 6.2 PO 的 identity 编码不能用一行示例冒充通用协议

默认 PO 导出的 collapse 模式会改变 context：按“文本 identity + source”折叠与按“namespace + source”折叠，不是同一种 identity 粒度；另有针对翻译服务的替代导出格式。5.6 Overview 还指出其中一种替代格式缺少译文当时对应的源文，无法用同样方式检测 PO 导入的 stale。

因此不要把 `Namespace|Key`、`Namespace.Key` 或另一手写分隔方式规定为所有 UE PO 的 `msgctxt`。本篇不提供可导入 PO 样板；实际样例应从目标配置真实导出，再固定 header、collapse/export 模式和工具版本。翻译方可以改允许的译文及注释，不能擅改参数名、identity、转义或把格式修饰符当普通标点。

审校应包含一条有命名参数的完整句子、一条复数句和项目确实使用的复杂语法案例；先验证格式能解析且参数合同相符，再由目标语言审校者判断语义与语气。引擎的导入按钮存在，不证明项目已经实现了“所有占位符错漏都会使构建失败”的校验。

### 6.3 制品应能独立追溯，也能成组回滚

建议记录 `ContentRevision + TargetConfigRevision + SourceSnapshot + TranslationRevision + Culture + CompileToolVersion + ArtifactDigest`。字段是项目的发布契约示意，不是 UE 自带 manifest 格式；摘要证明文件身份，不证明翻译正确。归档源文与导出输入可解释译文为什么被接受；归档编译制品能检查 Stage 是否混入旧资源。

若发现错译，仅重发 PO 不会让已经安装的游戏自动更新。回滚时明确回退的代码/资产、LocRes/LocMeta、字体和语音依赖是否兼容；不把互不对应的 key/source 与旧译文强行组合。实际补丁安装、资源挂载、校验与回滚执行读[资源管理与热更新](04-资源管理与热更新.md)，本篇只定义它需要消费的本地化版本关系。

## 7. Compile、Cook、Stage、Package 是不同关口

[Packaging Your Project](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project?application_version=5.6) 将 Build、Cook、Stage、Package 分开。Cook 把资产变为目标平台可用形式；Stage 汇集该发布所需文件；Package 形成可分发制品。**本地化 Compile 不应改名为 Cook**，不能期待通用打包自动补做一次遗漏的译文编译。项目可以显式编排这些步骤，但须有日志证明它实际做了。

发布验证至少分四组：

| 关口 | 要核对的对象 | 失败如何处理 |
| --- | --- | --- |
| 翻译编译 | 当前 Target/文化的 LocRes、LocMeta、输入版本与 stale 策略 | 产物过旧或来源不明时重建；不以文件存在判通过 |
| 本地化与国际化数据 | Localizations to Package、Internationalization Support（ICU 数据） | 选中的文化与 ICU 支持须匹配；不是“有 locres 就足够” |
| 内容与依赖 | 字符串表、非资产 CSV、字体、L10N 资产/音频、具体 chunk/可用时间 | 检查实际输出清单；首屏需要的资源不得依赖尚未安装包 |
| 目标运行加载 | Target loading policy、实际文化、资源加载与 UI 生命周期 | 冷启动/重启等实测区分未加载、缺文化、缺表、缺字或旧缓存 |

[Overview 的 Packaging Localization Data](https://dev.epicgames.com/documentation/en-us/unreal-engine/localization-overview-for-unreal-engine?application_version=5.6) 明确要求同时检查 `Localizations to Package` 与 `Internationalization Support`。原生文化、fallback 数据及目标元数据也必须按项目方案验证。发布不只带 LocRes：还涉及 LocMeta、ICU 和所需内容；工作用 PO/Archive 不应被当作普通运行时自动翻译来源，是否另作诊断归档需由项目目的决定。

Chunk/DLC/补丁是交付策略，不是翻译可用性的自动保证。新增语言至少需要：受支持的文化选择、完整资源与依赖、目标平台打包与安装路径、运行时发现/加载方式、已有用户的更新行为和回滚方案。把一份新 LocRes 放到服务器不证明客户端会下载、挂载或刷新，不能承诺“后补语言走一次热更就必然生效”。

本篇不展开 UAT 通用构建拓扑、签名、平台 SDK 或部署凭证；这些由[构建主篇](../构建编译与制品/02-UAT与自动化打包.md)负责。5.6 Localization Tools 对 UAT `Localize` 的特定 Editor 构建前提有说明，不能把那份示例推广为任意主机/版本可用的流水线。本轮没有运行 UAT。

## 8. 资产、对白与字体的交付支线

### 8.1 文本已切换，已加载资产仍可能是旧文化

[Asset Localization](https://dev.epicgames.com/documentation/en-us/unreal-engine/asset-localization-in-unreal-engine?application_version=5.6) 的例子把 `/Game/UI/Panel` 的法语变体放在 `/Game/L10N/fr/UI/Panel` 对应位置。替换的是资产，不是把所有业务对象和蓝图状态重新运行一遍；5.6 文档还限制含字节码资产的本地化替换。不要据此承诺任意 Blueprint 类能作为文化资产被替换。

关键边界是**运行时切文化不会自动热重载本地化资产**。若产品未实现安全卸载/重载流程，重启后加载是需要明确验证的路径；Editor 支持热重载不代表发行包有同样行为。语音组与文本分离时也一样：UI 显示法语不能证明日语 SoundWave 已装载，回读文化设置不能替代试听或资源身份检查。

### 8.2 Dialogue Wave 携带上下文，不是自动对齐录音的工具

Dialogue Wave 可描述 spoken text、可选字幕覆盖、说话者与听者上下文，并为相应组合关联 SoundWave；它不是完整会话系统。不同语言可能需要不同录音组合，不能假设一条英语录音等于所有语言的一条录音。

官方支线是：收集对白 → 导出每文化 Dialogue CSV → 按其 `AudioFileName` 录制并存放到文化目录 → 导入对白资源；录音时如修订台词，要回填对应文本，保持字幕与录音同版。原生台词变化可能使翻译与录音都需重做，排期按这个依赖关系推进。

旧稿把 `InternationalizationConditioningCommandlet` 解释为“裁剪/重采样以匹配文本时长”，本轮读取的官方资料不支持该断言，故不提供这个修复配方。音画/字幕不一致时，应分别查台词版本、音频映射、实际播放资源、时序和字幕切分；不能凭命令let名字推导自动修正能力。

### 8.3 字体与布局不能靠固定膨胀百分比验收

5.6 Asset Localization 给出 Composite Font 与按文化替换字体两条路；项目有动态文化切换或不受限玩家输入时，优先研究覆盖多文化字符的复合字体方案。字体进入包、字符覆盖、塑形、双向文本、组合字符与 fallback 都需要实际输出验证。正确译文但缺字方框，仍是发布缺陷。

原稿“德语/俄语比英语长 20–40%”不作为通用预算。按钮短词、整句、字号和译法不同，扩展比例会变化；用项目最长关键译文、伪本地化和缩放矩阵测量。先给布局换行/扩展与可访问字号留空间，再验证，不能只把字体缩小到不可读。字体授权、平台分发约束与目标市场要求由实际项目确认，本文不作法律结论。细项验收交给[体验验收篇](../../05-Gameplay与交互系统/界面设置与无障碍/10-本地化无障碍与多端体验验收.md)。

## 9. 一个可追踪的发布例与有限反例

以下所有案例都是自拟纸面合同：状态统一为 **`PAPER_EXPECTED`，实际执行 `NOT_RUN`**。没有 UE 项目、真实译文交付或目标构建，表内“预期”不是观察结果。工程团队实施时须补实际输入摘要、环境、日志/截图与通过判据，不能把此表复制成测试报告。

### 9.1 正例：物品计数文本从源文到法语包

假设游戏使用 Game Target，原生文化 en，目标文化 fr，表中/源码中的物品计数句 identity 已固定；本例整数范围为 0–2，玩家名为文化不变参数。输入快照 A 收集含 `{Player}` 与数值 `{Count}` 的模板，导出当前 PO；译者在同一参数合同下提供法语整句并审校；Import 后 Compile 产出版本 R1 的 LocRes/LocMeta。

包装选择 fr 和所需国际化数据，包含对应字体、字符串表来源与首屏依赖；Stage 输出清单中记录 R1 摘要。实际程序冷启动请求 fr，确认 Game Target 已加载，打开控件分别显示 0/1/2 语义正确的法语文本，外部玩家名不被翻译。重开页面及重启后仍符合产品保存策略，才能给该构建该文化通过。各阶段若只留下一个“成功”日志而没有输入/产物关联，这条证据链仍不完整。

### 9.2 正反输入、预期与下一验证入口

| ID | 有限输入与操作 | 纸面预期 / 禁止判定 | 真实验证入口（本轮均 NOT_RUN） |
| --- | --- | --- | --- |
| L01 | 同 identity，源文 A 改 B；保留按 A 翻译的 PO | 必须暴露源文变化并按 stale 策略处理；key 稳定不等于译文获准 | 固定两次 Gather/Import/Compile 输入及报告，核对目标屏幕 |
| L02 | 把按钮 literal 改为 INVTEXT | 不能期望常规翻译资源让它换语言；显示源文不能算目标语言通过 | 检查 Gather 差异、FText 来历与切换前后输出 |
| L03 | 英语模板、整数 1/2；再对实际支持的另一文化审校 | 1/2 的英语结果见 §3；别的文化不沿用英语 if 分支 | 真实 Format 输出、类型、源/译模板及语言审校记录 |
| L04 | 译文把 `{Count}` 写成 `{Amount}`，或把数值实参变成显示文本 | 应被项目的参数合同检查/用例发现；不宣称引擎必然使构建失败 | 格式解析、参数集合/类型检查，记录实际错误或输出 |
| L05 | 语言从 en→fr，Locale 保持原设置；自制缓存为 FString | 应按分开设置合同更新；旧字符串缓存需失效/重建，不推定自动变更 | 已开控件、重开页面、数值格式和实际文化回读 |
| L06 | 冷启动时只有 `Find`，表未加载；或表有而 key 缺失 | 两类原因分开；非空 FText/占位值不证明成功 | 表/条目存在性、加载完成、错误路径、资源 owner 记录 |
| L07 | Editor 从磁盘读 CSV，但 Stage 未包含它 | 不得凭 Editor 成功判发行可用 | 包内非资产文件清单与无开发目录依赖的冷启动 |
| L08 | 新 PO 导入成功，未 Compile；或 Compile 完却 Stage 旧 LocRes | 发布链断在不同关口；都不能宣布新翻译上线 | 输入版本→编译摘要→包内摘要→实际加载逐级对照 |
| L09 | fr LocRes 已在包内，Target loading policy 不适合游戏 | 文件存在不证明运行时已加载；先核 Target 再怪翻译 | 打包后 Target/文化加载记录和指定句输出 |
| L10 | 新文化已翻译，但未选入 Localizations to Package 或 ICU 不匹配 | 标记该文化不可验收；配置成功不等于完整资源支持 | 实际 Stage 清单、文化支持范围与目标启动 |
| L11 | 音频已按 en 加载，UI 切 fr；另设音频组为 ja | 不承诺资产自动变更；按产品重启/重载合同验证 | 记录实际音频资源身份、试听、字幕及重启后结果 |
| L12 | 源文/译文正确，但长文本、组合字符或 CJK 缺字 | 文本链通过不能替代呈现质量 | 目标字体、分辨率/缩放、完整流程截图及人工体验 |

这些案例只覆盖所列输入，不能推出所有文化、复数类别、设备、网络下载、GC 生命周期或资产类型都通过。特别是字符串表加载/持有、语言包安装与回滚、真实录音时序属于项目运行验证，不能由静态阅读补足。

## 10. 排障按第一处失去合同的位置推进

| 现象 | 先看什么 | 避免的无效修复 |
| --- | --- | --- |
| 完全没译文 | FText 来历、可收集性、Gather 范围及 identity | 反复运行 Compile，却没有任何已收集条目 |
| 仍是旧译文 | 源文版本、Import 输出、Compile/Stage 摘要、实际加载来源 | 只编辑 PO 或把 stale 全局放行 |
| Editor 正确、发行包错误 | Target loading、文化/ICU、CSV/表/字体/资产进包 | 反复在编辑器手动打开资产使测试偶然成功 |
| 个别句子出错 | context、参数、词形、复用语境与字符处理 | 为所有语言手写英语语序拼接 |
| 切换后部分内容不变 | Language/Locale/语音组、自制缓存与已加载资产 | 假设 SetCurrentCulture 会重建任意 UI 和 UObject |
| 文本存在但不可读 | 实际字体、塑形、字符覆盖与布局 | 用“翻译率 100%”关闭缺字/截断缺陷 |

停止条件是定位到缺失证据或被破坏的不变量后，修复该层并重验依赖链；不是不断重试最后一个步骤直到偶然看到译文。发布放行应明确“哪一构建、哪些文化、哪些平台、哪些用户路径、什么降级及例外”，将结论交给[质量门禁与灰度回滚](08-全栈质量门禁与灰度回滚.md)消费。

## 11. 来源、历史与未验证边界

本轮官方资料实际选读范围：Overview 的 Target/产物/PO/Packaging；Text Localization 的 literal、历史、格式修饰符与文本生成；FText/FName 的转换边界；String Tables 的 CSV/引用/重定向；LoadingPolicy/Registry 的加载和缺失条目行为；Tools 的 Dashboard/状态/自动化前提；Pipeline Optimization 的缓存与重存副作用；Culture 的独立设置、回退与预览；Asset Localization 的资产切换、字体和对白；Packaging 的 Build/Cook/Stage/Package 职责。

核读 `FText::FromStringTable` 的单独 API 路由时，HTTP 200 返回的页面缺少标题与正文，因此未把它作为已核实 API 签名。引用方式依据已成功取得的 String Tables 正文；加载政策依据单独的 5.6 枚举与 Registry 页。本轮没有下载、执行或核对 UE 私有源码，不声称这些网页逐行证明项目的线程、GC 或内存实现。

PIE/UMG 本地化预览尤其不能替代发行包：5.6 Culture 页面说明它们主要加载预览本地化数据，并不完整改变 Language/Locale；更接近运行时的 standalone 仍不代替实际目标包的内容完整性。旧稿直接启动后退出的 `-culture=xx` 示意没有形成可观测断言，本轮不把它保留为“本地化已验证”的命令。伪本地化要有真正执行的环境、观察路径与失败证据才产生验收价值。
