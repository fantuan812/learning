# TLS、认证授权与反作弊
> 知识成熟度：L2

> 知识基线：以当前标准、协议或 Linux/工具链版本为准，平台差异需实测。
> 最后更新：2026-08-20。
> 官方参考：https://en.cppreference.com/、https://man7.org/。

## TLS 基础
- TLS 提供机密性、完整性和端点认证。
- 握手协商版本、密码套件、随机数和密钥交换参数。
- ECDHE 提供前向保密；证书用于绑定公钥与身份。
- 证书链由根 CA、签发 CA 和叶证书组成。
- 主机名校验、有效期校验和撤销策略不可省略。
- 会话恢复降低握手成本，但要控制票据寿命。
- ALPN 协商 HTTP/2、HTTP/3 等应用协议。
- 禁用过时协议、弱套件和明文回退。

## 身份认证
- 认证回答“你是谁”，授权回答“你能做什么”。
- 密码应使用 Argon2id、scrypt 或 bcrypt 加盐哈希。
- MFA 将知识、持有、生物特征组合降低单点风险。
- OAuth 适合委托访问；OIDC 在其上提供身份层。
- Access token 短时有效，Refresh token 需轮换和撤销。
- 服务间认证可用 mTLS 或签名令牌。
- 密钥放入 KMS/密钥库，不写入仓库和日志。

## 授权设计
- 默认拒绝，按最小权限授予。
- RBAC 按角色管理；ABAC 根据主体、资源、环境属性决策。
- 多租户必须校验 tenant_id，不能只依赖前端参数。
- 资源级授权要在服务端每个入口执行。
- 审计日志记录主体、动作、资源、结果和追踪 ID。

## 威胁建模
- 列资产、入口、信任边界、滥用场景和控制措施。
- STRIDE 用于发现欺骗、篡改、抵赖、信息泄露、拒绝服务、提权。
- 对外接口需要限流、重放保护、输入校验和超时。
- 供应链锁定版本并校验来源和 SBOM。

## 游戏反作弊
- 客户端是不可信环境，关键判定必须服务端重算。
- 服务器验证速度、射线、冷却、资源和时间单调性。
- 遥测应采集最少必要数据并保护隐私。
- 检测系统输出风险分，不直接依据单一特征封禁。
- 回放和证据链支持申诉复核。
- 反调试、完整性校验只能提高成本，不能替代权威服务器。

## 演练
1. 使用代理替换证书验证，确认客户端拒绝。
2. 重放过期令牌，验证 nonce 和时间窗。
3. 修改客户端速度包，验证服务端限幅和告警。
# 案例：登录与会话
客户端通过 TLS 1.3 建立连接，服务端校验证书链、SNI 和 ALPN。
登录接口使用短时 access token 与可撤销 refresh token。
密码只保存 Argon2id 哈希，禁止日志记录明文凭据。
权限检查采用主体、资源、动作三元组，并在服务端执行。
高风险操作要求二次认证和幂等请求号。
密钥轮换保留旧密钥验证窗口，避免全量会话同时失效。

## 实验：TLS 配置
使用 openssl s_server 与 s_client 建立本地 TLS 1.3 连接。
分别开启和禁用 session resumption，测量握手耗时。
切换 RSA、ECDSA 证书，记录握手 CPU 与证书大小。
验证过期证书、错误主机名和未知 CA 必须失败。
抓取握手元数据但不得保存会话密钥和用户数据。
使用 `h2load` 测量 HTTP/2 在 1、10、100 并发下的 p95。

## 案例：反作弊遥测
客户端上报输入时间戳、帧号和签名摘要，服务端只信任可验证字段。
检测速度、加速度、操作间隔的异常分布，采用分数而非单阈值封禁。
模型特征做版本化，保留人工复核和申诉路径。
重放攻击由 nonce、时间窗和服务端序列号阻断。
敏感检测逻辑放在服务端，客户端仅提供不可伪造的证明材料。

## Benchmark
测量 TLS 握手 QPS、连接复用率、加解密吞吐和 p99。
对比无 TLS、TLS 1.2、TLS 1.3 和 mTLS。
固定消息大小 128 B、4 KiB、64 KiB，分别报告 CPU 百分比。
认证授权基准覆盖缓存命中、缓存失效和策略复杂度 1、10、100 条。
反作弊规则引擎记录每请求特征提取耗时与误报率。

## 安全验收
禁用弱密码套件、过时协议和匿名密码组。
所有授权失败返回一致错误，避免泄露资源存在性。
密钥和 token 不出现在 URL、日志、崩溃转储中。
依赖库定期扫描 CVE，补丁在预发布环境回归。
每季度演练证书吊销、密钥泄露和账号接管响应。

## RFC 与规范基线
TLS 1.3 以 RFC 8446 为准；HTTP/2、HTTP/3 参考 RFC 9113、RFC 9114，QUIC 参考 RFC 9000/9001。
OAuth 2.0 参考 RFC 6749，OIDC 参考 OpenID Connect Core；访问控制检查 OWASP ASVS 与 Top 10。

## 可运行 TLS 与 mTLS 实验
生成本地证书：`openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 1 -subj /CN=localhost`。
服务端：`openssl s_server -accept 8443 -cert cert.pem -key key.pem -www -tls1_3`；客户端使用 `openssl s_client -connect localhost:8443 -tls1_3 -CAfile cert.pem -servername localhost`。
预期 Verify return code 为 0；移除 CA、错误 SNI、过期证书分别验证失败。创建测试 CA 和客户端证书后启用 `-Verify 1 -CAfile ca.pem` 验证 mTLS，无客户端证书应拒绝。

## OAuth/OIDC 与反作弊实验
授权码 + PKCE 流程验证 state、nonce、issuer、audience、过期时间和 redirect_uri 白名单；禁止 token 出现在 URL 或日志。
客户端只提交输入、时间戳和会话证明，判定在服务端完成；重放旧签名包应被 nonce、时间窗和单调序列拒绝。
篡改速度、角度、射击间隔，记录命中原因；用真实高水平玩家样本测量误报率并支持人工复核。

## 失败排查与证据
证书失败检查系统时间、SAN、信任链、SNI 和中间证书顺序；握手超时抓取 ClientHello/ServerHello 检查 MTU 与丢包。
mTLS 拒绝检查 EKU、签发 CA、有效期和验证深度；OAuth 劫持检查 state、PKCE、SameSite Cookie。
误封升高时分离检测分数与处置阈值，回放标注样本并校准模型；性能回退检查链长度、硬件加速和会话票据。
保存证书生成命令（不保存私钥）、握手摘要、工具版本、原始 CSV、攻击前提、响应时间及误报漏报。

## TLS 1.3 握手逐步核对
TLS 1.3 的 ClientHello 携带 supported_versions、key_share、signature_algorithms、server_name 和 ALPN。服务端选择版本与组后返回 ServerHello；从此之后的握手消息都由握手密钥保护。EncryptedExtensions 确认 ALPN，Certificate、CertificateVerify 和 Finished 分别提供身份链、私钥持有证明和握手完整性。客户端必须验证 transcript hash，而不是只检查证书主题名。

排障时记录：协商版本、密码套件、椭圆曲线、ALPN、是否恢复会话、证书链长度、OCSP stapling 状态。不要记录 ClientKeyExchange、应用数据或会话票据原文。TLS 1.3 不再支持静态 RSA 密钥交换；证书签名算法和密钥交换组要分别配置。

### 证书生命周期
开发环境使用短期测试 CA，生产环境由 ACME、企业 CA 或云 KMS 自动签发。叶证书建议 30 至 90 天，轮换必须提前覆盖 DNS、负载均衡和服务实例的缓存窗口。部署时同时保留旧证书一段时间，确认连接排空后再撤销旧证书。

证书验收清单：SAN 覆盖所有访问名；KeyUsage 包含 digitalSignature；服务端 EKU 为 serverAuth，客户端证书 EKU 为 clientAuth；中间证书顺序正确；私钥权限为服务用户可读；密钥不进入镜像层和日志。吊销策略要明确 CRL、OCSP 或短证书三选一的可用性与失败行为。

## 可复现的 mTLS 实验
先创建 CA，再创建服务端和客户端 CSR。示例命令如下（仅用于临时实验目录）：

```bash
openssl genrsa -out ca.key 2048
openssl req -x509 -new -nodes -key ca.key -sha256 -days 7 -out ca.crt -subj "/CN=lab-ca"
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=localhost"
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 7 -out server.crt
openssl req -newkey rsa:2048 -nodes -keyout client.key -out client.csr -subj "/CN=lab-client"
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 7 -out client.crt
```

服务端使用 `openssl s_server -accept 8443 -cert server.crt -key server.key -CAfile ca.crt -Verify 1 -www`；客户端使用 `openssl s_client -connect localhost:8443 -cert client.crt -key client.key -CAfile ca.crt -servername localhost`。无客户端证书时，预期握手失败；使用其他 CA 签发的证书时，预期 verify error。记录命令、OpenSSL 版本和 `-state -tlsextdebug` 摘要。

## OAuth 2.0、OIDC 与 PKCE
浏览器应用使用 Authorization Code + PKCE。客户端先生成高熵 code_verifier，发送其 S256 challenge；回调时服务端校验 state、code_verifier、redirect_uri、issuer、audience、nonce 和授权码一次性使用。Access token 只放内存或受保护的后端会话，Refresh token 轮换并绑定客户端；禁止把 token 放在 URL、Referer、日志或分析事件中。

OIDC 的 ID Token 只用于证明登录上下文，不应直接当作 API access token。验证签名算法白名单、JWKS issuer、exp、iat、nonce、sub 和 aud。缓存 JWKS 时设置过期时间并处理密钥轮换；收到未知 kid 时限速刷新，防止远程触发大量回源。

Cookie 会话设置 Secure、HttpOnly、SameSite=Lax/Strict，并使用 CSRF token 保护状态改变请求。登出应撤销 refresh token、删除服务端会话并使旧 session version 失效。高风险动作要求重新认证或 WebAuthn，且带幂等键与审计记录。

### OAuth 实验验收
构造四组请求：正确 state/PKCE、错误 state、重复授权码、错误 redirect_uri。预期只有第一组成功。将 access token 过期时间设为 60 秒，验证过期返回 401 且不泄露 token 内容；轮换 refresh token 后重放旧 token，预期触发撤销链并记录安全事件。

## 会话安全与重放防护
每个会话拥有随机 session_id、版本号和最近序列号。敏感请求包含 nonce、issued_at、expires_at、request_hash 和签名；服务器检查时间窗、单调序列、用户/设备绑定及 nonce 去重表。分布式部署时 nonce 表需使用带 TTL 的强一致存储，或按用户分片并保证单写者。

重放实验：保存一份合法请求，在 30 秒内重复发送、修改 payload、跨账号发送和延迟到窗口外发送。预期分别得到 duplicate、bad signature、binding failure、expired 四类可观测错误；对外响应保持统一，详细原因只写入受保护审计日志。

限流采用主体、IP、设备、接口和全局多维度桶。登录失败使用指数退避；验证码和密码重置接口设置更严格额度。限流器本身应防止时钟回拨，使用单调时钟计算窗口，并在 Redis/网关故障时选择 fail-closed 或受限 fail-open 的明确策略。

## 反作弊威胁模型
资产包括比赛结果、虚拟物品、账号信誉、隐私遥测和服务容量。攻击者可能控制客户端进程、注入 DLL、修改内存、伪造输入、重放网络包、操纵时钟或合谋刷号。信任边界位于客户端与服务端之间；客户端报告只能作为证据，不能成为最终事实。

服务端权威校验应覆盖移动速度、加速度、碰撞、弹药、冷却、视线、命中时间和资源转移。每个规则保存版本、输入字段、阈值、样本量和误报率。规则结果进入风险分层：观察、增加采样、限制匹配、人工复核、暂时隔离，避免单一信号自动永久封禁。

遥测遵循数据最小化：只收集检测所需字段，使用伪名化账号 ID，设置保留期限和访问审计。证据包包含事件时间线、服务器重算结果、规则版本、签名摘要和关联 trace_id；原始隐私数据分开加密存储。

### 反作弊基准
准备正常玩家、高手、网络抖动、脚本注入模拟和重放攻击五类数据集。按玩家划分训练与测试，避免同一玩家泄漏到两侧。报告 precision、recall、FPR、FNR、检测延迟和每千请求 CPU。阈值调整必须同时给出封禁量变化、申诉通过率和业务损失估计。

## 密钥、令牌与供应链
密钥按用途分层：根密钥只在 KMS，签名密钥可由 HSM 代理，短期服务密钥由工作负载身份获取。轮换采用双读单写，旧密钥保留验证窗口；发现泄露时先阻断签发、吊销或缩短 TTL，再通知受影响主体。

依赖锁定版本和哈希，构建生成 SBOM，CI 中执行漏洞扫描、许可证检查和恶意包检测。供应链事件演练应验证从发现、隔离、回滚到密钥轮换的时间，并保存每一步的负责人和证据。

## 性能 Benchmark 方法
固定 CPU 型号、内核、OpenSSL、编译器、证书链、消息大小和并发；预热 30 秒后采样至少 5 分钟，报告 p50/p95/p99、错误率、CPU、RSS、握手 QPS 和连接复用率。每个场景运行至少 5 次，给出均值、标准差和置信区间。

场景 A 对比 TLS 1.2、TLS 1.3、mTLS 新连接握手；场景 B 对比 keep-alive、HTTP/2 多路复用和 HTTP/3；场景 C 测量 128 B、4 KiB、64 KiB 载荷的吞吐与尾延迟；场景 D 测量 JWT 本地校验、JWKS 缓存命中、远端 introspection；场景 E 测量规则 1、10、100 条时的每请求开销。

预期输出至少包含 CSV 原始数据、工具命令、环境摘要、火焰图或 perf stat、异常样本和结论。不能用单次最好成绩作为验收；回归阈值应以基线 p99 增幅（例如不超过 10%）和错误率上限共同定义。

## 故障排查矩阵
证书校验失败：检查系统时间、SAN、SNI、信任根、中间证书顺序、EKU 和验证深度。协议版本失败：检查双方 supported_versions、密码套件、曲线和 ALPN。握手慢：区分 DNS、TCP、证书链、CPU、OCSP 和丢包，分别采集时间戳。

OAuth 回调失败：检查 state/nonce、PKCE、issuer、redirect_uri 和 cookie SameSite。间歇性 401：检查时钟偏差、JWKS 轮换、缓存过期和 token audience。mTLS 只在部分实例失败：比较实例证书、CA bundle、权限、容器时间和负载均衡透传配置。

反作弊误报：按规则版本和玩家分层，回放原始事件，比较服务端重算与客户端报告。性能退化：检查证书链长度、硬件加速、会话恢复率、日志采样和规则特征数量。所有排查结果关联 incident_id、trace_id、工具版本和时间窗口。

## 安全验收门槛
发布前必须通过：TLS 1.2/1.3 仅允许批准套件；错误主机名、过期证书、未知 CA、缺失 mTLS 客户端证书均失败；OAuth 错误 state、重放授权码、错误 redirect_uri 均失败；token 不出现在日志和 URL；限流、nonce 去重和审计可观测；反作弊规则具备回放、申诉和回滚路径。

验收记录应包含测试环境、版本、命令、原始输出、失败样本、风险接受人和修复截止日期。没有可复现证据的结论只能标为 L2 设计，不得标成已验证的 L3。

## 密码学选择与实现边界
应用通常不应自行实现 AES、ChaCha20、HKDF、Ed25519 或签名验证，而应调用经过审计的 TLS、libsodium 或平台密码库。随机数必须来自操作系统 CSPRNG；不得使用时间、进程号或 `rand()` 生成 nonce、密码或密钥。比较 MAC、token 摘要和 session ID 时使用常数时间比较，避免长度和早停泄漏。

密码哈希参数需用目标硬件校准。Argon2id 记录版本、内存、迭代和并行度；升级参数时保留旧参数验证窗口，登录成功后重新哈希。密码重置 token 应是单次、短时、不可预测值，数据库只保存其哈希，消费后立即失效。

加密数据必须同时保存算法标识、版本、key_id、nonce 和认证标签。解密失败统一返回错误，不区分 padding、标签还是格式，详细原因进入受控指标。禁止把密钥和明文同时写入 crash dump；进程退出时尽力清零短期密钥缓冲区。

## HTTP 安全边界
反向代理终止 TLS 时，代理到应用的链路仍应使用 mTLS 或受限网络。应用只信任经过认证的 `X-Forwarded-*`，不能直接接受客户端伪造的 scheme、host 和 client IP。HSTS、Content-Security-Policy、X-Content-Type-Options 和 Referrer-Policy 按域名分阶段启用。

上传接口限制大小、类型、解压比和处理时间；先保存到隔离目录再扫描，避免路径穿越和多态文件。JSON 解析限制深度、字段数和数字范围。错误页面不返回栈、SQL、证书路径或内部主机名。

## 身份与授权案例：多租户物品交易
请求携带主体 token、tenant_id、item_id 和操作。服务端先验证 token issuer/aud/exp，再从数据库读取 item 所属租户和状态，最后执行“主体是否拥有该资源、是否具备交易权限、是否满足风控策略”三项检查。客户端传入 tenant_id 只作为查询提示，不作为授权依据。

交易写入使用幂等键和数据库唯一约束；重复请求返回第一次结果，跨租户 item_id 返回同一类 404，避免枚举资源。审计事件包含 actor、tenant、resource、policy_version、decision、request_id 和时间戳。人工撤销后立即增加 session version，使旧 token 在下一次请求被拒绝。

## 网络攻击演练
在隔离环境执行证书替换、降级到 TLS 1.2、ALPN 错配、重放请求、窃取 refresh token、伪造 X-Forwarded-For、超大 header 和慢速上传。每项演练预先定义攻击前提、允许范围、停止条件和回滚方式。

证据采集顺序：客户端命令与时间、代理访问日志、服务端结构化日志、指标、trace、抓包元数据。抓包只保留五元组、握手摘要和包长，不保存生产应用数据。演练结束删除临时证书、token、pcap 和测试账号。

## TLS 连接池与部署实践
连接池按上游身份、SNI、ALPN 和证书策略隔离，禁止把一个租户的客户端证书复用于另一个租户。设置最大连接年龄和空闲时间，证书轮换时主动排空旧连接。HTTP/2 要限制并发 stream、header table 和单连接请求数，防止单连接资源占满。

服务启动时预加载信任根并验证证书；热更新采用新旧配置原子切换，失败时保留旧配置。部署探针应分别测试 TCP、TLS、HTTP 健康和业务授权，不能用“端口可连”代替端到端健康。

## 观测字段与告警
TLS 指标包括 handshake_total、handshake_failure_total（按安全的错误类别聚合）、session_resumption_ratio、certificate_expiry_seconds 和 active_connections。认证指标包括 login_failure、token_refresh、jwks_fetch、policy_denied 和 replay_detected。反作弊指标包括 score_distribution、review_queue_age、false_positive_sample 和 rule_latency。

告警阈值以基线和变化率组合：证书剩余时间小于 14 天、握手失败率超过基线三倍、JWKS 回源错误持续五分钟、重放事件突增或规则 p99 超过预算。告警内容不得带 token、密码、完整证书私钥或可逆个人数据。

## 变更评审模板
每次安全变更填写：威胁模型变化、影响的信任边界、协议/套件、密钥与证书生命周期、回滚版本、兼容客户端、性能预算、隐私影响、监控指标和演练日期。涉及认证或授权的变更必须由服务负责人和安全负责人双人审批。

灰度发布先对内部账号和低风险租户启用，比较成功率、p99、拒绝率、申诉率和异常流量。出现回归时只回滚策略版本或路由，不删除审计证据。灰度结束后更新运行手册、威胁模型和应急联系人。

## 最小实验报告格式
实验名称：TLS/mTLS/OAuth/反作弊之一。
环境：操作系统、内核、CPU、容器镜像、OpenSSL、客户端和服务端版本。
前提：网络拓扑、证书来源、测试账号、数据规模和攻击者能力。
步骤：完整命令、配置摘要、开始结束时间和清理命令。
原始结果：CSV、日志摘要、指标截图或哈希，确保可追溯。
结论：成功条件、失败条件、误报漏报、性能变化和风险接受。
后续：修复负责人、截止日期、回归测试和证据存放位置。

## 常见错误示例
把 TLS 加密误当作授权：加密只保护传输，服务端仍需验证主体和资源权限。
把 JWT 签名有效误当作用户仍在线：撤销、session version 和设备状态仍需查询。
把 mTLS 证书存在误当作终端可信：证书只证明密钥持有和签发关系，设备完整性需额外证明。
把客户端反作弊模块报告误当作事实：客户端可被修改，关键状态必须由服务端重算。
把 p99 下降误当作安全改进：必须同时检查失败率、重试放大、审计完整性和误封变化。

## 复盘问题清单
事件是否涉及密钥、token、证书、个人数据或比赛结果？
攻击者从哪个入口越过了哪条信任边界？
哪个控制措施本应阻断但未生效，监控何时发现？
是否能用保存的证据重放请求并复现判定？
修复是否改变协议兼容、延迟、成本或误报？
哪些规则、密钥、依赖和运行手册需要同步更新？

## 版本兼容与迁移
协议升级先建立兼容矩阵：客户端版本、服务端版本、TLS 版本、ALPN、证书算法和系统时间。新旧客户端并行期间，服务端拒绝未知扩展时应返回可诊断但不泄露内部信息的错误。移除旧协议前，统计真实协商比例并通知仍在使用的主体。

迁移 access token 时同时接受旧 issuer 和新 issuer 的短窗口，签发只使用新 issuer；窗口结束后撤销旧密钥并检查拒绝率。迁移密码哈希时采用登录触发重哈希，不批量读取明文密码。迁移 mTLS CA 时先信任双 CA，再切换签发，最后删除旧 CA。

## 资源耗尽防护
TLS 握手、证书链解析、JWT 解码、正则规则和回放去重都可能消耗 CPU 或内存。为每个阶段设置超时、最大长度、最大深度和并发上限；拒绝前记录聚合计数，不记录攻击载荷。连接级限额与主体级限额同时生效，避免攻击者通过大量匿名主体绕过单一桶。

压力实验逐步增加并发，观察排队延迟、线程数、GC、RSS、文件描述符和错误率。注入半开连接、慢客户端、超长证书链、超大 JWT 和高频 nonce，确认系统按预算降级，而不是连锁重试。

## 数据保留与隐私
证据和审计按用途分级：安全事件原始证据短期加密保存，聚合指标可长期保留，个人标识使用哈希或令牌化。访问原始证据需要审批并留下审计；导出和申诉流程应能证明数据未被篡改。

反作弊模型训练数据标注规则、采集时间、来源和删除期限。测试账号与真实账号隔离，生产数据脱敏后才能进入实验环境。隐私删除请求不得破坏不可否认的安全审计，可将主体字段替换为不可逆占位符。

## 发布检查签字项
- [ ] TLS 版本、套件、ALPN 与兼容矩阵已评审。
- [ ] 服务端和客户端证书的 SAN、EKU、链、轮换和撤销已演练。
- [ ] OAuth/OIDC 的 state、nonce、PKCE、issuer、audience、cookie 和 token 生命周期已测试。
- [ ] nonce、序列号、幂等键、限流和时钟偏差有明确边界。
- [ ] 关键游戏状态由服务端重算，规则版本可回放、灰度和回滚。
- [ ] Benchmark 有基线、重复运行、原始数据和性能预算。
- [ ] 日志、trace、指标和证据不包含秘密及不必要个人数据。
- [ ] 依赖、SBOM、漏洞扫描和密钥泄露响应已完成。

只有所有签字项和失败演练证据齐全，安全基线才可从设计级 L2 提升为验证级 L3。

## 应急响应最小流程
发现疑似密钥或 token 泄露时，先确认范围与时间窗口，冻结高风险操作并保留审计。随后停止旧密钥签发、轮换验证密钥、撤销 refresh token、缩短会话 TTL，并通过受控渠道通知受影响主体。完成修复后用原始请求和回放数据验证旧凭据确实失效。

若证书即将过期，优先切换备用证书并验证所有实例；不要直接删除旧信任根。若反作弊误封激增，暂停自动永久处置，保留观察和人工复核，同时锁定规则版本与样本。事件结束必须输出时间线、影响量、根因、检测缺口、修复项和回归证据。

应急演练每半年至少一次，覆盖证书、KMS、OAuth、数据库和反作弊规则五类对象。演练负责人记录发现时间、遏制时间、恢复时间与证据完整率，并将结果转换为下一季度的修复任务。任何无法回放的安全判定都必须降低处置强度，直到证据链补齐。

## 参考实现边界
示例命令只在隔离目录运行，生产私钥由 KMS 或 HSM 生成。
生产配置禁止 `-nodes`，禁止调试服务器暴露公网。
测试 CA、账号、token、pcap 和日志在实验结束时全部销毁。
每次实验保存工具版本与配置哈希，确保结果可重复。
性能结论必须注明硬件、并发、载荷、采样窗口和误差。
安全结论必须注明攻击者能力、信任边界和剩余风险。
这份文档描述控制目标，不替代具体产品的安全评审。
所有阈值都应通过压测和攻击演练校准。
所有例外都应有期限、负责人和回滚方案。
