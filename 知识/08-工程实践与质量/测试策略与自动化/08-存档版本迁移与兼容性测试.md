# 08 · 存档版本迁移与兼容性测试
> 知识成熟度：L2。主要结论为原始资料静态核阅；下述纯数据例已完成正常与唯一语义负控各一次有限运行，不代表 UE 存档、实际持久化或产品发布验证。

## 文档定位

- 定位：游戏测试与质量库的存档数据可靠性专题。
- 目标：验证本地 SaveGame 与服务端持久化在版本演进、失败恢复和跨版本运行时仍可预测。
- 适用对象：客户端、服务端、数据平台、QA、发布工程和客服恢复团队。
- 最后更新：2026-10-10（补齐纯数据迁移正例、独立期望值与发布判据，并记录两次有限运行；初稿标记日期为 2026-08-07）。
- 稳定结论：存档格式是长期接口，不能把一次性反序列化脚本当作迁移方案。
- 事实边界：本文不规定具体引擎、数据库、云厂商或序列化库。
- 事实边界：平台云存档的容量、冲突和保留期限必须以目标平台当前文档为准。
- 事实边界：涉及玩家申诉的数据恢复必须遵守产品隐私政策和当地法规。
- 核心取舍：宁可拒绝不安全的旧数据，也不应静默覆盖玩家进度。
- 核心取舍：迁移应可观测、可重放、可回滚，不能只在发布日人工盯日志。
- 核心取舍：小而明确的 schema 变化优于一次跨多个大版本的隐式重写。

## 阅读和使用方式

- 先看“事实边界”，再根据产品架构选择本地、云端或混合矩阵。
- 先建立版本目录，再编写迁移测试；不要从异常样本反推唯一版本。
- 将每个测试用例绑定输入快照、迁移脚本版本、输出快照和校验结果。
- 将门禁结果接入发布流水线，禁止只在测试人员电脑上运行。
- 将玩家可见提示与内部诊断码分离，避免在界面暴露内部路径或凭据。
- 若产品没有服务端存档，仍应执行本地损坏、备份和跨客户端测试。
- 若产品只有服务端存档，仍应执行离线、断网和旧客户端读取测试。

## 先走通一次：v1 旧档如何变成可发布的 v3

### 先确定什么不能变

玩家 Lin 的旧档里有 Sword×2。v2 把 `oldPlayerName` 改名为 `playerName` 并新增难度，v3 为每种物品补耐久百分比。迁移后名字仍是 Lin、Sword 仍是 2 个；Normal 和 100 是这两个版本明确选择的兼容默认值。若只检查“JSON 能打开、版本等于 3”，把数量误写成 3 的错误仍可能通过，所以测试还需要独立写出的期望值。

步骤应是**验证源版本 → 在独立候选上逐级转换 → 验证当前版本及语义 → 条件满足才发布**。源验证回答“这份 v1 是否完整”，不能先拿 v3 的必填字段拒绝合法 v1；每步输出验证能定位是哪一步破坏了合同。失败只丢弃候选，输入快照和当前选定副本都保留。这个例子沿用 [SaveGame 主文的迁移案例](../../05-Gameplay与交互系统/背包装备与存档/12-SaveGame存档系统与序列化.md#p11-迁移与字段缺失)的名字、物品与默认值，专门把测试判据和结果展开；UE 反射、旧属性加载与真实槽位实现仍由主文负责。

| 阶段 | 输入及变换 | 应得到的结果 |
| --- | --- | --- |
| 源 v1 | Lin；Sword×2；不含难度、耐久 | 按 v1 规则验证通过 |
| v1→v2 | 改名；显式设 difficulty=Normal | 名字和数量不变，schemaVersion=2 |
| v2→v3 | 每项显式设 conditionPercent=100 | 名字和数量不变，schemaVersion=3 |
| 当前验证 | 与独立写出的 v3 期望对象比较 | 不只验证版本号，还验证字段值和数量 |
| 发布 | 原始 generation=7，当前副本仍与读入快照一致 | 内存选定副本成为 generation=8/v3，原始字符串仍在 |

这里有两个不同的“重复”。迁移函数 M 接受 v1/v2/v3，并让已经到达 v3 的有效数据保持不变，所以 `M(M(x))=M(x)`；某个只接受 v1 的单步转换本身不需要再次接受 v2。发布则负责并发修订号：不能每次计算候选都给 generation 加一，也不能拿旧 generation 覆盖新数据。示例让当前 v3 重试得到 NoChange、旧 generation 重放得到 Conflict，这不等同于网络协议中的结果重放或 exactly-once。

### 完整最小程序：只操作合成数据与一个内存槽

依赖为 Python 3.12 标准库，无第三方包。将下面完整代码保存为 `save_migration_demo.py`，运行 `python3 save_migration_demo.py`（Windows 可用 `py -3.12 save_migration_demo.py`）。**后面的五行输出在执行前已固定为 PAPER_EXPECTED；本次实际运行记录另列在本节末尾。代码开头的 NOT_RUN 注释保留其准备阶段原貌，实际状态以运行记录为准，勿将其推广为其他测试矩阵已执行。**

有限合同：一个已选定的合成 profile、单线程、最多 4 KiB JSON 文本、2 种物品，每种定义只出现一次；只识别 Sword/Potion，数量 1–999，名称最多 64 个 UTF-8 字节，空名称合法，耐久 0–100。额外字段被明确拒绝，不静默删除。`generation` 放在内存槽的外层，schemaVersion 放在载荷内；未实现账号鉴权、通用 envelope、校验签名、真实文件写入或生产发布流程。

Python 默认 JSON 解码会接受重复键并保留后值，也接受 NaN/Infinity；这里用 `object_pairs_hook` 和 `parse_constant` 明确拒绝。`type(value) is int` 避免把 Python 的布尔值当作数量。排序输出只是本程序有限数据的稳定编码，不能据此声称实现了跨语言规范化 JSON；文本长度上限也不是完整的深度、CPU 或内存安全证明。[CPython 3.12.0 固定文档源码](https://github.com/python/cpython/blob/0fb18b02c8ad56299d6a2910be0bab8ad601ef24/Doc/library/json.rst#L618-L666)、[RFC 8259 §4、§6](https://www.rfc-editor.org/rfc/rfc8259)

```python
"""Original finite teaching model. NOT_RUN during preparation.

Python 3.12 standard library; one in-memory slot, no file or network I/O.
This is not Unreal SaveGame encoding, durable storage, or concurrent CAS.
"""
import json


class SaveError(ValueError):
    pass


def require(ok, code):
    if not ok:
        raise SaveError(code)


def unique_object(pairs):
    result = {}
    for key, value in pairs:
        require(key not in result, "DuplicateKey")
        result[key] = value
    return result


def reject_constant(_):
    raise SaveError("NonFiniteNumber")


def decode(text):
    require(type(text) is str and len(text.encode("utf-8")) <= 4096,
            "InputSize")
    return json.loads(text, object_pairs_hook=unique_object,
                      parse_constant=reject_constant)


def encode(data):
    return json.dumps(data, ensure_ascii=False, sort_keys=True,
                      separators=(",", ":"), allow_nan=False)


def validate(data):
    require(type(data) is dict, "RootType")
    version = data.get("schemaVersion")
    require(type(version) is int and version in (1, 2, 3), "UnsupportedSchema")
    name_key = "oldPlayerName" if version == 1 else "playerName"
    keys = {"schemaVersion", name_key, "inventory"}
    if version >= 2:
        keys.add("difficulty")
    require(set(data) == keys, "Fields")
    name = data[name_key]
    require(type(name) is str and len(name.encode("utf-8")) <= 64, "Name")
    if version >= 2:
        require(data["difficulty"] in ("Normal", "Hard"), "Difficulty")
    items = data["inventory"]
    require(type(items) is list and len(items) <= 2, "Inventory")
    seen = set()
    for item in items:
        fields = {"definitionId", "count"}
        if version == 3:
            fields.add("conditionPercent")
        require(type(item) is dict and set(item) == fields, "ItemFields")
        key, count = item["definitionId"], item["count"]
        require(type(key) is str and key in ("Sword", "Potion") and
                key not in seen, "DefinitionId")
        seen.add(key)
        require(type(count) is int and 1 <= count <= 999, "Count")
        if version == 3:
            value = item["conditionPercent"]
            require(type(value) is int and 0 <= value <= 100, "Condition")


def migrate(text):
    candidate = decode(text)  # Fresh object; the input string stays unchanged.
    validate(candidate)       # Validate the actual source schema first.
    while candidate["schemaVersion"] < 3:
        if candidate["schemaVersion"] == 1:
            candidate["playerName"] = candidate.pop("oldPlayerName")
            candidate["difficulty"] = "Normal"  # Explicit v1 -> v2 rule.
            candidate["schemaVersion"] = 2
        else:  # Only validated v2 can reach this branch.
            for item in candidate["inventory"]:
                item["conditionPercent"] = 100  # Explicit v2 -> v3 rule.
            candidate["schemaVersion"] = 3
        validate(candidate)  # Every intermediate output obeys its own schema.
    return encode(candidate)


def publish(current, expected, candidate_text):
    # Tuples are (generation, JSON string). This function is single-threaded.
    if current != expected:
        return "Conflict", current
    candidate = decode(candidate_text)
    validate(candidate)
    require(candidate["schemaVersion"] == 3, "NotCurrent")
    # Tiny model: recompute to bind the candidate to this exact source snapshot.
    require(candidate_text == migrate(expected[1]), "CandidateMismatch")
    if candidate_text == encode(decode(expected[1])):
        return "NoChange", current
    return "PublishedInMemory", (current[0] + 1, candidate_text)


def must_reject(text, code):
    try:
        migrate(text)
    except SaveError as error:
        require(str(error) == code, "WrongError")
    else:
        raise SaveError("ExpectedRejection")


def main():
    v1 = ('{"schemaVersion":1,"oldPlayerName":"Lin",'
          '"inventory":[{"definitionId":"Sword","count":2}]}')
    v2 = ('{"schemaVersion":2,"playerName":"Lin","difficulty":"Normal",'
          '"inventory":[{"definitionId":"Sword","count":2}]}')
    # Independent expected value: do not generate this with migrate().
    expected_v3 = {
        "schemaVersion": 3, "playerName": "Lin", "difficulty": "Normal",
        "inventory": [{"definitionId": "Sword", "count": 2,
                       "conditionPercent": 100}],
    }
    slot = (7, v1)
    original = slot
    candidate = migrate(v1)
    require(decode(candidate) == expected_v3, "WrongMigration")
    require(migrate(v2) == candidate, "BrokenChain")
    require(migrate(candidate) == candidate, "NotIdempotent")
    require(slot == original, "ChangedBeforePublish")
    print("candidate:", candidate)

    result, slot = publish(slot, original, candidate)
    require(result == "PublishedInMemory" and slot == (8, candidate), "Publish")
    print("publish:", result, "generation:", slot[0])
    replay, unchanged = publish(slot, slot, migrate(slot[1]))
    require(replay == "NoChange" and unchanged == slot, "Replay")
    print("replay:", replay, "generation:", unchanged[0])
    stale, unchanged = publish(slot, original, candidate)
    require(stale == "Conflict" and unchanged == slot, "StaleOverwrite")
    print("stale:", stale, "generation:", unchanged[0])

    must_reject(v1.replace('"schemaVersion":1', '"schemaVersion":4'),
                "UnsupportedSchema")
    must_reject(v1.replace('"schemaVersion":1,', ''), "UnsupportedSchema")
    must_reject(v1.replace('"count":2', '"count":true'), "Count")
    must_reject(v1.replace('"count":2', '"count":0'), "Count")
    must_reject(v1.replace('"schemaVersion":1',
                           '"schemaVersion":1,"schemaVersion":1'), "DuplicateKey")
    try:
        publish(original, original, candidate.replace('"count":2', '"count":3'))
    except SaveError as error:
        require(str(error) == "CandidateMismatch", "WrongCandidateError")
    else:
        raise SaveError("AcceptedChangedAssets")
    require(original == (7, v1), "LostOriginal")
    print("finite checks: OK; original generation: 7; Sword count: 2")


if __name__ == "__main__":
    main()
```

预期标准输出如下，退出码应为 0；这段文字不是实际运行日志：

```text
candidate: {"difficulty":"Normal","inventory":[{"conditionPercent":100,"count":2,"definitionId":"Sword"}],"playerName":"Lin","schemaVersion":3}
publish: PublishedInMemory generation: 8
replay: NoChange generation: 8
stale: Conflict generation: 8
finite checks: OK; original generation: 7; Sword count: 2
```

先单独看正常路径：`migrate(v1)` 创建并转换新对象，`slot` 仍为原 v1；与手写 `expected_v3` 对比之后，`publish` 才选择新副本。这个有限程序为绑定源与候选，发布前重新计算并核对候选；实际系统可采用受控迁移工件、源摘要与候选摘要绑定，但不能仅用“候选验证通过”证明它来自这份输入。程序没有奖励回调、时钟、随机数或网络查询，因而示例转换不会从这些入口增加资产或引入非确定输入。

### 只在正常路径之后加入必要反例

| 程序中的输入或操作 | 预期结果 | 为什么有这个测试 |
| --- | --- | --- |
| 正常 v2 直接迁到 v3 | 与 v1 经两步迁移的输出相同 | 检查迁移链的中间入口 |
| 当前有效 v3 再次迁移 | 候选文本不变；发布 NoChange，generation 不增长 | 区分纯转换幂等与提交次数 |
| schemaVersion 缺失或为 4 | UnsupportedSchema | 缺版本、未来版本不能冒充最新版本或空新档 |
| count 为 true 或 0 | Count | 编码能解析不等于数量合法 |
| 重复 schemaVersion 键 | DuplicateKey | 不让解析器后值覆盖掩盖歧义 |
| 将合法 v3 候选中的 Sword×2 改成 Sword×3 | CandidateMismatch | 当前 schema 验证合法，仍不符合这份源档的迁移结果 |
| 仍拿 generation=7 发布，当前已是 8 | Conflict，当前副本不变 | 成功转换不能授权覆盖后来的写入 |

`expected_v3` 是独立写出的值；若把 v2→v3 的 100 故意改成 0，结构校验依然合法，但正常样例应在 WrongMigration 处失败。本次已对这个唯一变体执行一次，实际结果见下；没有增加其他故障或任意输入实验。主程序只覆盖表中有限样例，不把未列出的畸形 JSON、Unicode、递归深度或任意输入都归入同一诊断码。

PublishedInMemory 只表示这个单线程程序返回并选择了新 tuple。比较 generation 与赋值不构成多线程/多进程原子 CAS；数据库或对象存储要使用真实事务/条件写并核结果。原始 tuple 仍可读也不等于有断电后可用的备份，更不代表 UE 旧二进制能加载、云端同步完成或游戏版本可以发布。真实项目仍须完成下文适用的跨版本、存储故障与发布门禁；此例的通过不能代替它们。

## 术语与数据对象

- SaveGame：玩家可恢复的游戏状态集合，可包含进度、配置和可选缓存。
- 本地存档：保存在设备文件系统、沙盒或平台本地容器中的副本。
- 服务端持久化：由后端数据库、对象存储或平台云存档托管的权威副本。
- 快照：测试时不可变的输入或输出文件，带有哈希和采集时间。
- 逻辑版本：游戏规则或数据语义版本，例如 season=3。
- schema 版本：字段结构和类型版本，例如 schema=7。
- 迁移版本：将一个 schema 转换为另一个 schema 的脚本版本。
- 数据世代：同一玩家在冲突解决后形成的单调递增修订号。
- 校验和：用于发现意外改写或截断的完整性摘要。
- 兼容窗口：仍被当前客户端或服务端支持的版本范围。
- 旧客户端：低于当前发布版本、但可能仍连接服务的客户端。
- 新客户端：已包含新 schema 或迁移逻辑的客户端。
- 有效载荷：经过解析、验证、授权和业务规则检查的数据。
- 不可恢复数据：经多份副本和人工核验仍无法安全还原的数据。

## 数据分层与权威性

- 将不可重建的玩家进度与可重建缓存分开保存。
- 将用户设置与服务器授予的货币、道具分开保存。
- 将统计、排行榜和成就等派生数据标记为可重算。
- 对每一层声明权威来源、更新方向和冲突策略。
- 本地副本只能作为候选恢复源，不能凭文件时间戳直接覆盖服务端。
- 服务端权威数据不能因客户端提交空对象而被清空。
- 客户端提交应包含玩家身份、数据世代和客户端构建号。
- 服务端写入应包含服务器时间和审计事件编号。
- 迁移只处理明确的 schema 区域，不应顺带改写业务数值。
- 缓存字段即使迁移失败，也不应阻塞核心进度恢复。
- 每个字段记录来源：玩家输入、服务器计算、平台同步或派生。
- 对来源不明字段采用保守默认值并生成诊断事件。

## 最小数据合同

以下是面向多版本恢复的项目合同检查清单，不是 JSON Schema 或 UE 自动生成的通用顶层格式。表述中的“必须”以项目采纳这些合同为前提；字段也可由可信且与载荷绑定的 envelope、存储元数据或审计记录承担。上面的纯数据例只实现缩小后的迁移载荷与一个外层 generation，不声称满足本节完整生产合同。

- 顶层必须包含 schemaVersion。
- 顶层必须包含 dataGeneration 或等价的并发控制值。
- 顶层必须包含 createdAt、updatedAt 和时区明确的格式。
- 顶层必须包含产品或游戏标识，防止跨产品误导入。
- 顶层必须包含校验和或可替代的完整性证明。
- 顶层必须包含迁移历史摘要，但不得无限增长。
- 每个可变资源应定义取值范围和单位。
- 时间字段必须声明使用 UTC、单调时钟或服务器时间。
- 枚举字段应对未知值有明确拒绝或降级策略。
- 数组字段应声明最大长度，避免异常存档造成资源耗尽。
- 字符串字段应声明最大字节数，而不仅是字符数。
- 二进制字段应声明编码、压缩和加密状态。
- 引用外部资源时应使用稳定 ID，不保存易变路径。
- 删除字段时先停写，再观察兼容窗口，最后移除读取逻辑。
- 新增字段默认值必须是业务安全值，而不是语言默认值。
- 关键经济字段须由服务端重新计算或签名校验。
- 迁移后的输出不得比输入增加未声明的玩家资产。

## schema 版本策略

- 版本号采用单调整数或明确的语义版本，不混用日期字符串。
- 一个版本只表达一组可审查的结构变化。
- 记录字段新增、删除、重命名、类型变化和语义变化。
- 类型变化必须有正向迁移、失败分支和回滚策略。
- 语义变化即使字段类型不变，也必须提升版本。
- 旧版本读取能力写入支持矩阵，不依赖口头约定。
- 将 schema 定义、样例和迁移脚本放在同一发布工件中。
- 迁移脚本保持幂等：重复执行不会二次增加资产。
- 迁移脚本保持确定性：相同输入和配置得到相同输出。
- 迁移脚本禁止读取网络实时状态来决定核心字段。
- 迁移脚本失败时保留原始快照，不原地覆盖唯一副本。
- 新版本发布前冻结字段命名和默认值，并完成审查。
- 对跨大版本迁移设置最大跳跃值。
- 超过最大跳跃值时使用链式迁移或人工恢复流程。
- 删除旧迁移脚本前确认兼容窗口已结束并有归档副本。

## 本地 SaveGame 流程

“写入原子可见”和“掉电后持久”是不同保证。例如 Python `os.replace` 说明成功时的原子重命名及跨文件系统限制，并不因此承诺完整耐久协议。对 UE，`SaveGameToSlot` 的公开合同是平台槽保存结果，不能把另一个名为 `.tmp` 的槽自动解释为临时文件事务。实现路径与平台边界参见 [SaveGame 主文](../../05-Gameplay与交互系统/背包装备与存档/12-SaveGame存档系统与序列化.md#10-保存时机与自动存档策略)、[Python 3.12 os.replace](https://docs.python.org/3.12/library/os.html#os.replace)、[Epic 槽 API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UGameplayStatics/SaveGameToSlot)。

- 在项目控制且核实合同的文件后端，可采用同一文件系统内的临时写、必要刷新及原子替换；耐久与崩溃恢复另测。UE 平台槽 API 本身不提供通用文件替换事务。
- 写入前生成上一份只读备份，保留数量由产品策略决定。
- 写入期间崩溃不得留下“新文件名但内容不完整”的状态。
- 读取先检查文件存在、大小上限、编码和魔数。
- 读取再校验校验和、版本、字段类型和业务不变量。
- 解析失败时从最近可验证备份恢复，不自动拼接未知片段。
- 恢复成功后保留损坏文件供诊断，并限制其权限。
- 多个存档槽位必须隔离路径和加密上下文。
- 临时存档不能被正式列表误识别为可加载档。
- 退出游戏时的自动保存应可取消或延迟，避免并发覆盖。
- 在主线程外写入时使用单一写入队列，禁止多协程竞态。
- 写入失败必须向上层返回明确错误码和重试建议。
- 设备空间不足时保留旧存档，不用零字节文件替换。
- 迁移生成的新文件需重新计算校验和并记录迁移链。
- 用户手动删除前显示范围和不可恢复性。

## 服务端持久化流程

- 服务端先鉴权和授权，再解析存档载荷。
- 当前记录用产品/玩家/槽位等业务身份定位；历史快照可再以数据世代区分。防止过期覆盖还需在同一次原子条件写或事务中比较当前世代，不能只靠“身份＋世代”唯一键。
- 使用乐观并发控制拒绝过期客户端覆盖新数据。
- 服务器计算的资产写入应覆盖或校验客户端同名字段。
- 数据库事务应同时写入主记录、版本和审计事件。
- 对象存储写入完成后再更新数据库指针。
- 指针更新失败时旧对象仍应可读取。
- 读路径将迁移分为预览、执行和提交阶段。
- 大批量在线迁移采用限速、分批和熔断。
- 离线迁移输出新的对象键，不覆盖原对象。
- 权限最小化：迁移服务不应拥有删库或读无关玩家数据的权限。
- 管理后台显示数据世代、schema 和迁移状态，不显示完整敏感载荷。
- 服务端返回可供客户端理解的恢复码，不返回内部堆栈。
- 数据保留策略必须包括原始快照、迁移后快照和删除时间。

## 迁移状态与证据链

~~~mermaid
stateDiagram-v2
    [*] --> Snapshot
    Snapshot --> Validate: 记录版本/哈希/归属
    Validate --> Migrate: 输入在兼容窗口
    Validate --> Quarantine: 解析或授权失败
    Migrate --> Verify: 写入候选副本
    Verify --> Commit: 业务不变量通过
    Verify --> Rollback: 校验失败
    Commit --> [*]
    Rollback --> Quarantine: 保留原副本
    Quarantine --> ManualReview: 责任人复核
    ManualReview --> Restore: 选择可验证备份
    Restore --> Verify
~~~

状态图强调：迁移先产生可验证候选副本，只有业务校验通过才提交；隔离、回滚和人工恢复都必须留下责任人与证据。

## 冲突与合并

- 冲突检测至少比较数据世代、更新时间和服务器修订号。
- 不能用客户端时钟作为唯一的新旧判断依据。
- 可合并字段应定义字段级策略，不使用全对象深合并默认值。
- 货币、库存、任务奖励等不可重复发放字段优先服务器裁决。
- 进度标志的合并必须声明是并集、最大值还是版本锁定。
- 设置类字段可采用最后写入，但要保留冲突诊断。
- 无法安全合并时提供只读预览和人工恢复入口。
- 冲突提示不得要求玩家猜测哪个副本“看起来更新”。
- 合并结果重新经过完整性校验和业务不变量检查。
- 任何合并都生成新数据世代，旧副本保持可审计。

## 迁移与回档设计

- 先在离线副本执行迁移，再对输出做统计比对。
- 预迁移阶段只读输入，不修改原始文件或对象。
- 执行阶段写入临时目标并记录每一步计数。
- 提交阶段用原子指针切换或事务提交。
- 每一步记录输入哈希、输出哈希、脚本版本和操作者。
- 回档依据是稳定快照 ID，不依据“最近文件”猜测。
- 回档前锁定玩家写入，避免新旧数据交叉覆盖。
- 回档后增加数据世代或回档世代，防止旧客户端再次写回。
- 回档不应撤销已核实的支付或合规记录。
- 迁移只改变结构，不隐式补偿玩家资产。
- 需要补偿时由独立、可审查的运营流程处理。
- 对大表迁移提供暂停、继续和安全中止能力。
- 熔断阈值包括失败率、校验失败率、耗时和资源占用。
- 迁移完成后保留抽样输入输出用于发布验收。
- 发布说明明确哪些版本可以继续写入。

## 损坏分类

- 截断：文件长度小于最小结构或末尾校验失败。
- 编码损坏：字节序列无法按声明编码解码。
- 结构损坏：JSON、二进制容器或数据库页无法解析。
- schema 损坏：版本缺失、未知版本或字段类型不符。
- 业务损坏：解析成功但违反资源、任务或时间不变量。
- 加密损坏：密钥不可用、认证标签不匹配或上下文错误。
- 并发损坏：多个写入者造成世代倒退或半提交。
- 逻辑损坏：迁移成功但资产数量或进度异常。
- 外部损坏：平台同步返回旧副本、冲突副本或空对象。
- 人为损坏：误删、误导入或客服手工改写未留审计。
- 每类损坏绑定唯一诊断码和恢复等级。
- 诊断码不应包含完整路径、令牌、密钥或个人数据。

## 损坏恢复策略

- 一级恢复：从同一设备最近可验证备份恢复。
- 二级恢复：从平台云存档候选副本恢复并保留本地副本。
- 三级恢复：从服务端历史快照恢复到新的数据世代。
- 四级恢复：由授权人工依据审计记录重建最小可玩状态。
- 恢复前验证玩家身份和数据归属。
- 恢复后重新运行迁移、完整性和业务不变量检查。
- 任何恢复都写入恢复原因、来源快照和结果哈希。
- 恢复失败不得清空现有候选副本。
- 玩家取消恢复时保持原始和候选副本可选。
- UI 提示区分“正在尝试恢复”和“无法自动恢复”。
- 不能承诺恢复已不存在、未备份或违反保留期限的数据。
- 客服工具提供脱敏差异摘要，不提供任意 SQL 或文件上传。

## 边界值与故障注入

- 生成零字节、单字节、最大允许大小和超限大小样本。
- 生成缺失顶层字段、重复键、额外键和未知类型样本。
- 生成校验和正确但业务不变量错误的样本。
- 在文件刷新前、替换前、云端提交前注入进程终止。
- 在数据库事务提交前后注入连接断开。
- 在对象上传完成但指针未切换时模拟重试。
- 模拟密钥轮换期间旧密钥只读、新密钥写入。
- 模拟平台返回两个合法但不同世代的副本。
- 模拟客户端时钟倒退、快进和时区错误。
- 模拟磁盘只读、空间耗尽和权限变更。
- 模拟迁移脚本依赖缺失、超时和内存不足。
- 故障注入必须使用隔离测试账号和非生产数据。

## 证据要求

- 保存输入快照哈希和来源说明。
- 保存客户端构建号、服务端版本和 schema 版本。
- 保存迁移脚本提交号或不可变工件摘要。
- 保存关键字段迁移前后差异摘要。
- 保存校验、业务不变量和性能结果。
- 保存失败诊断码、时间线和重试次数。
- 保存回滚前后数据世代及对象指针。
- 保存抽样人工复核记录和复核人。
- 证据中对玩家 ID、设备 ID、令牌和自由文本脱敏。
- 证据可在隔离环境重放，但不应可直接写入生产。

## 失败信号

- 迁移后资源总量非预期变化。
- 输出 schema 版本与工件声明不一致。
- 同一输入重复迁移得到不同哈希。
- 旧客户端意外写入已停止支持的版本。
- 云端冲突被静默覆盖。
- 损坏文件被当作空新档加载。
- 回档后旧写入仍能覆盖回档结果。
- 迁移失败后原始唯一副本消失。
- 失败率、耗时或内存超过门禁阈值。
- 日志暴露完整载荷或敏感凭据。
- 玩家界面显示内部堆栈、路径或对象键。
- 自动恢复循环反复改写同一副本。

## 通过标准

- 所有声明支持的写入端和读取端组合通过矩阵。
- 迁移脚本具备幂等、确定性和可审计输出。
- 任何失败都保留原始或最近可验证副本。
- 业务不变量和关键资产总量保持产品定义的范围。
- 冲突、过期写入和未知版本均有明确可见结果。
- 本地原子写入和服务端事务在故障注入下成立。
- 大批量迁移在容量、延迟和错误率预算内完成。
- 诊断证据经脱敏后可由独立人员复核。
- 发布门禁记录测试工件、批准人和适用兼容窗口。
- 回滚演练在目标时间内恢复可玩状态。

## 回滚与排障

- 先暂停有问题版本的写入，不先删除异常数据。
- 记录受影响的 schema、脚本、构建和数据世代。
- 以快照哈希定位可验证输入和最后成功输出。
- 将异常对象复制到隔离区，避免排障再次触发迁移。
- 回切服务端指针前确认新写入已排队或安全拒绝。
- 回切后要求客户端重新拉取并清理过期本地缓存。
- 若本地档损坏，提示玩家选择备份，不要求反复重启碰运气。
- 若云端冲突，保留双方副本并转人工恢复。
- 若密钥问题，先恢复密钥访问，再判断是否需要迁移。
- 若迁移超时，按批次继续，不扩大并发掩盖瓶颈。
- 排障完成后补充根因、影响范围和预防测试。
- 回滚工单必须关联审计事件和验证证据。

## 常见误区与最佳实践

- 误区：schema 版本不变就代表业务兼容；实践：语义变化也升版本。
- 误区：把空档当作损坏档；实践：区分首次创建、删除和解析失败。
- 误区：只测“最新档能打开”；实践：覆盖所有支持窗口和中断点。
- 误区：用当前时间修复过期事件；实践：使用服务器时间和审计顺序。
- 误区：迁移失败直接清理文件；实践：原始副本只读保留。
- 误区：把客服手改当作临时操作；实践：使用受限工具和双人复核。
- 误区：只统计迁移成功数；实践：同时统计资产差异和恢复成功率。
- 误区：凭文件名选择云副本；实践：使用数据世代和完整性证明。
- 误区：为兼容旧端永久保留所有字段；实践：公布窗口并有删除计划。
- 误区：让客户端决定货币余额；实践：服务端重算或验证签名。
- 最佳实践：每个迁移版本配套正例、负例、幂等和回滚样本。
- 最佳实践：用合成数据覆盖边界，用脱敏真实快照覆盖组合。
- 最佳实践：把迁移演练纳入灾备和发布日历。
- 最佳实践：为客服提供诊断摘要而不是数据库权限。
