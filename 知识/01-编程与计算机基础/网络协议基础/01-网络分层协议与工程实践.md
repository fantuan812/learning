# 网络分层、协议与工程实践

> 知识成熟度：L2。本轮于 2026-10-07 核对下列固定 RFC 与 Linux 6.12/v6.12 选段；主要承诺是解释一次 HTTPS 请求的因果链，并用完整题设作纸面推导。所有地址、连接、缓存、证书结果、事务和耗时样本均为合成输入，以下结果标为 **PAPER_EXPECTED（纸面预期）**，不是目标网络运行记录。
>
> 适用范围：HTTP/1.1 → TLS 1.3 → TCP → IPv4 → Ethernet 的教学模型；HTTP/2、QUIC、IPv6、安全与运营主题保留用途和条件，未逐项深入验证。未执行网络探测、抓包、配置、编译、压力或故障实验。普通文件、链接和算术检查只能证明相应静态性质。来源位置及未覆盖项见“来源与证据边界”；2026-08-20 原前言完整保存在文末历史区。

## 0. 从“请求成功了吗”开始
<!-- 原用途: 1-3,248-250,299-300 -->

学习网络时，先问一笔订单的结果，比背完协议名字更有用：客户端显示超时，服务器究竟没收到、正在做，还是已经提交了？要回答这个问题，需依次理解封装、寻址与可靠流，再判断安全身份、消息完整性和业务终态。性能与故障分析沿同一链条寻找缺失的证据。

本文假定读者能读十进制地址、二进制前缀、字节长度和简单状态表。学习产物是一张能手算的请求记录：名称从哪里来；下一跳为什么是网关；哪些序号被确认；TLS 验证的对象是谁；HTTP 在哪里结束；最后凭什么显示订单成功。三个完成层次要分开：

- **传输接收**：TCP 连续字节到达接收端 TCP；尚不能证明进程读过它们
- **协议接收完成**：TLS 已认证解密，HTTP 已按规则取得完整消息；尚不能代替业务提交合同
- **业务确认**：客户端取得可归属到本请求的完整终态凭据，并依服务合同判断结果

用户体验预算覆盖解析、连接、安全握手、发送、排队、处理、返回及有限恢复，而非只给 TCP 一个超时。最小权限和最小暴露面必须贯穿身份、应用授权与管理面。本篇提供基础机制和专题入口，后续协议或安全基线变化应回到具体版本和失败条件重新核对；目录齐全、工具能连通、机械检查通过，都不是稳定交付的全部证据。

### 0.1 贯穿全文的纸面输入（P0）

业务目标是为已获应用授权的 `tenant-a` 创建订单。URL 为 `https://api.example.test/orders`，方法 POST，请求标识 `r-17`，去重键 `k-17`。**租户已获授权是独立题设**；请求头里的名称以及只认证服务器的 TLS 不证明客户端属于这个租户。

下面显示 HTTP/1.1 请求的字符内容。每个请求行/头字段行以 **CRLF 两字节**结束，头和 body 之间是 CRLFCRLF；最后一个 `}` 后**没有 LF 或 CRLF**。代码围栏的排版换行不属于输入字节：

```text
POST /orders HTTP/1.1
Host: api.example.test
Content-Type: application/json
Content-Length: 19
Idempotency-Key: k-17
X-Request-ID: r-17

{"sku":"A","qty":1}
```

原始 JSON 为 ASCII，长 19 octets；含终止空行的头区长 144，合计 **163 octets**。`Idempotency-Key` 和 `X-Request-ID` 的含义来自本题服务合同，不宣称是任何服务都支持的标准实现。请求没有 Transfer-Encoding、Content-Encoding、Expect、代理重写或管线化，连接上只有这一个尚待响应的请求。增加鉴权等字段后必须重算总长，不能继续套用 163。

其余输入按用途集中如下，后文反例只独立替换明确指出的条件：

| 对象 | 给定状态 |
| --- | --- |
| 客户端 C | `192.0.2.10/24`，MAC `02:00:00:00:00:10`，接口 eth0；直连 `192.0.2.0/24`，默认路由 via `192.0.2.1` eth0 |
| 路由器 R | 入侧 `192.0.2.1` / `02:00:00:00:00:01`；出侧 `198.51.100.1` / `02:00:00:00:01:01`；两侧直连路由、允许转发 |
| 服务器 S | `198.51.100.20/24`，MAC `02:00:00:00:01:20`；TCP 443 监听；反向默认路由 via `198.51.100.1` |
| 路径与策略 | 无 NAT、隧道、策略路由、多路径或额外路由；正反方向相关策略均允许；ARP 正常，初始邻居缓存空；初始 IPv4 TTL=64，每跳减 1 |
| DNS | t0 获得 A=`198.51.100.20`、TTL=60 秒；现在 t30；无 CNAME、额外缓存、主动刷新或 serve-stale |
| 尺寸 | 每跳 IP MTU=1500；IPv4 头 20、TCP 数据段头 20；对端 MSS=1460；数据段无 options，无 VLAN；Ethernet 头 14、FCS 4，不计前导码和 IFG |
| TCP | C 端口 51000 → S 端口 443；初始 cISN=1000、sISN=9000；握手全部交付；另给 TLS 完成后 C 下一发送序号 5001；该快照不由未知的握手字节量推出 |
| 发送策略 | 待发 TCP payload 共 2000 octets；尽量满段再发尾段，窗口足够、无丢失重排。这是题设，不是每次 write 的保证；SYN 可带 MSS/窗口协商 options |
| TLS | 1.3 完整证书认证握手，无恢复、0-RTT、客户端证书认证；原 URL 决定 reference DNS-ID；SAN 含 `api.example.test`；路径、适用的时间/证书检查、CertificateVerify、双方 Finished 及必要握手检查均成功；SNI 同名，ALPN 选中 `http/1.1` |
| 去重和效果 | 作用域为已授权租户 + CreateOrder + 键；参数规范化为 `(sku字符串, qty整数)`，恰有这两个字段且拒绝重复字段。订单与终态去重记录在一个可原子、持久提交的存储事务内，唯一键/并发串行化保证一个有效提交者；不存在支付、邮件等事务外副作用 |
| 保留和并发 | 执行中重复等待或返回明确 pending，不另开效果；提交前崩溃回滚相关写入，提交后保留订单与结果；成功终态从提交起保留 24 小时，pending 不因该时限提前遗忘；同键异参拒绝 |
| 成功回执 | 本次已验证 TLS 连接上对应请求的完整 HTTP/1.1 201；合法头结束，唯一合法 CL=19、无 TE/Content-Encoding，body=`{"order_id":"o-42"}`，恰为 19 octets；服务合同规定该终态代表订单和去重记录已经持久提交 |

2000 是 **TLS 记录编码占用的 TCP payload**，不是 JSON 长度。一个合法长度见证为：163 字节 HTTP 明文 + 1 字节 inner content type + 1815 字节零 padding + 题设 16 字节 AEAD expansion + 5 字节 TLS 记录头 = 2000。TLSInnerPlaintext 长 1979，满足本题未缩小的记录上限。这里只验证长度可成立，未生成密文或运行 TLS；不同 padding/分记录策略会改变这个数。[RFC 8446 §5.2、§5.4](https://www.rfc-editor.org/rfc/rfc8446#section-5.2)

## 1. 名称解析给地址，缓存决定你此刻看到什么
<!-- 原用途: 106-109,119-120 -->

应用向递归解析器询问名称；解析器可命中缓存，也可循根、顶级域到相应权威的委派链取得回答。权威维护本区数据，但客户端当前收到的缓存回答未必与权威当前内容相同。DNS 的产物是可用于选路的地址及其缓存状态，**不是服务身份验证结果**。

P0 中 t0 得到的 60 秒正缓存，到 t30 尚余 30 秒，因此本次使用 `198.51.100.20`，而原 URL 的主机名仍为 `api.example.test`。若缓存到期却没有给出新回答，就不能继续编造地址。成功率与耗时也应注明观察的解析器、地域、时间窗、请求分母和缓存命中情况；一次快速缓存命中不能代表权威可用性。

### 1.1 正缓存切换题（P4）

独立时间线：解析器 A 在 t0 缓存旧地址、TTL=3600；权威 t600 将 TTL 降为 60，t660 才改地址。t700 时 A 仍可返回旧地址，余 **2900 秒**。解析器 B 在 t650 得旧地址/TTL60，其正常有效期到 t710。降低权威 TTL 不会远程改写 A 已经拿到的倒计时。

因此，“先降 TTL 再切换”的用途是为后来取得回答的缓存缩短寿命，还需考虑已经发出的旧 TTL。B 可以提前淘汰缓存，并非必须等到 t710；连接复用和额外应用缓存也各有寿命。不能把切换后 60 秒写成全世界切换完成的期限，更不能从 DNS 更新推导现有 TCP 连接已经迁移。[RFC 1035 §6.1.3](https://www.rfc-editor.org/rfc/rfc1035#section-6.1.3)、[RFC 8767 §4–6](https://www.rfc-editor.org/rfc/rfc8767#section-4)

### 1.2 “不存在”也会被缓存（P4）
<!-- 原用途: 115 -->

独立输入：无 CNAME，SOA RR TTL=600、SOA.MINIMUM=300。权威对 `new.example.test IN A` 回 NXDOMAIN，携带 SOA 的 TTL 为 min(600,300)=300。递归解析器 t0 接收并缓存；本题排除本地额外 TTL 上限、提前淘汰、serve-stale 和 DNSSEC 合成。

t60 权威创建 A 不会更新这个旧负缓存；t120 它仍可回答 NXDOMAIN，余 **180 秒**。NXDOMAIN 表示该名称不存在，缓存按 QNAME/QCLASS 使用；若原来是 NOERROR/NODATA，表示该名称/类别的 A 类型没有记录，负缓存还受 QTYPE 限定，不能推出 AAAA 也没有。t300 之后，没有新回答就只能停止在“旧负缓存正常有效期已过”，不能声称新记录已解析成功。[RFC 2308 §2、§3、§5](https://www.rfc-editor.org/rfc/rfc2308#section-5)

### 1.3 过期旧值为何还能带正 TTL（P4）

再独立给定：解析器支持并启用 serve-stale、保留过期记录，刷新未及时完成且达到其 client-response/failure-recheck 条件，仍在 max-stale 范围内。它可以返回旧记录并附正 TTL，例如 30 秒。这只表示客户端可怎样缓存这次回答，不证明权威刚刷新。RFC 8767 的示例允许后台继续刷新时先答旧值，并不要求所有刷新尝试最终失败后才能回答。

旧值不是无限期可用；权威成功刷新后，也不能继续把前次失败当作一直答旧值的理由。以上只推出题设解析器的可能回答；没有实际解析器策略和多层缓存证据时，停止推算全网恢复时间。本文采用 RFC 8767 修订后的 TTL 语义，不沿用 RFC 1035 旧文的 signed TTL 或“SOA 永远 TTL0”描述。[RFC 8767 §4–6](https://www.rfc-editor.org/rfc/rfc8767#section-5)

## 2. 先选路，再解析下一跳的链路地址（P1）
<!-- 原用途: 16-19,31-33,39-40,46-47 -->

IPv4 的 `/24` 表示前 24 位是此处的网络前缀；掩码划出的范围用于判断目的是否直连，不能只看地址字符串“长得像不像”。C 的直连前缀为 `192.0.2.0/24`，S 的 `198.51.100.20` 不匹配。最长前缀匹配使更具体路由优于默认 `/0`；在 P0 只有两条候选的条件下，C 选择默认下一跳 `192.0.2.1` 和 eth0。静态路由适合这个已知小拓扑，代价是拓扑变化时配置不会凭空正确。

ARP 在选路之后回答“这个链路上的下一跳 IPv4 对应哪个 MAC”。因此 C 广播询问网关 `192.0.2.1`，不是询问远端 S。邻居缓存空所以本次需要解析，后续在缓存有效且映射适用时可减少重复解析。MAC 标识链路接口，交换机在相应二层域内依据转发表转发；它们都不替 HTTP 或 TLS 决定业务身份。

| 此次转发 | Ethernet 源 → 目的 | IPv4 源 → 目的 | 其余变化 |
| --- | --- | --- | --- |
| C → R 入侧 | `02:00:00:00:00:10` → `02:00:00:00:00:01` | `192.0.2.10` → `198.51.100.20` | TCP 51000→443，TTL64 |
| R 出侧 → S | `02:00:00:00:01:01` → `02:00:00:00:01:20` | 仍为 C → S | R 查出侧直连路由并 ARP S；TTL63，IPv4 头校验和相应更新 |

路由器重新封装链路头，最终目的 IP 在本题无 NAT 条件下保持不变。网关 IP 是选路的下一跳信息，并不是该业务 IP 包的目的地址。S 的返回方向也需自己的路由和允许策略，正向成功不能免除反向条件。

反例：移除 C 默认路由且无其他匹配，本次便无路由；仅知道目标端口 443 无法补出可达性。路由存在而网关 ARP 失败，也不能继续推导成功发出第一跳。邻居记录存在只缩小问题范围，不能证明网关之后能转发。这里采用 [RFC 826 Packet Generation](https://www.rfc-editor.org/rfc/rfc826) 和 [RFC 1122 §3.3.1](https://www.rfc-editor.org/rfc/rfc1122#section-3.3.1) 的职责区分，不把旧文的驱动、路由缓存描述当作 Linux 6.12 的调用路径。

## 3. 同一请求有五种边界和五种长度
<!-- 原用途: 4-15 -->

物理介质传递比特；Ethernet 帧负责一次链路传输；IP 分组带跨链路寻址信息；TCP 在端点之间提供有序字节流；TLS 保护记录中的内容；HTTP 解释方法、头和消息体；业务最后解释“创建订单”。会话、表示等职责常分布在应用及库中，不必一层一台设备。层次的价值是明确各自产物，允许替换承载或实现；跨层优化仍要保住原有边界。

发送时逐层添加必要信息，接收时逐层验证、去头并交给上层。一个封装成功不能替下一层得出结论：校验无误的帧不等于可信服务器，完整 TCP 流也不等于完整 HTTP。本文按下表追踪同一份数据：

| 对象 | P0 的输入或推导 | 边界由谁决定 |
| --- | --- | --- |
| 业务 body | 19 字节 JSON | 本题字段和编码合同 |
| HTTP 请求 | 144 字节头区 + 19 字节 body = 163 | HTTP/1.1 语法及消息体定界 |
| TLS 记录编码 | 给定 2000，长度见证见 P0 | TLS 记录头、认证解密和 padding 规则 |
| TCP 数据 | 将同一 2000 字节放进连续序号空间 | TCP 字节序号；不保留应用 write 边界 |
| IP / Ethernet | 各段加 IP/TCP 头后再封成相应链路帧 | 该路径 MTU、实际头长与链路格式 |

### 3.1 MTU、MSS和实际头长（P2）

这里 **IP MTU1500** 限制 IP 分组总长；未加 VLAN 的 Ethernet payload 承载它，再另加 14 字节帧头与 4 字节 FCS。**MSS1460** 指 TCP 数据预算，包含承载的 TLS 编码，不能理解为可再装 1460 字节 HTTP 明文。

P0 的 IPv4/TCP 数据头各 20，发送策略尽量满段，故 2000 分成 1460+540。第一段 SEQ5001，字节 5001..6460；第二段 SEQ6461，字节 6461..7000。连续收全才可能累计 ACK7001。

| 独立条件 | TCP payload | IP 总长 | Ethernet 长度（含 FCS） |
| --- | --- | --- | --- |
| P0，头 20+20 | 1460、540 | 1500、580 | 1518、598 |
| 数据 TCP 头另加 12 字节 options，其余不变 | 1448、552 | 1500、604 | 1518、622 |
| 已知 PMTU1400，无 options，对端 MSS 仍1460 | 1360、640 | 1400、680 | 1418、698 |

MSS 广告按固定 IP/TCP 头计算；发送时仍要扣除实际 options 等开销，不能因对端报了 1460 就塞 1460 数据加 32 字节 TCP 头并声称 IP 仍为 1500。[RFC 6691 §2](https://www.rfc-editor.org/rfc/rfc6691#section-2)、[RFC 9293 §3.7.1](https://www.rfc-editor.org/rfc/rfc9293#section-3.7.1)

### 3.2 PMTU失败时，不能用一次超时猜尺寸
<!-- 原用途: 251-252 -->

给定原 1500 字节 IP 包在下游遇到 MTU1400 且 DF=1，路由器不能按原样转发。若进一步给定发送者收到了与此路径匹配的可信 ICMP “fragmentation needed / Datagram Too Big”，携带 MTU1400，并采用该反馈，才可按 1360 数据预算重新组织发送。重新发送仍不证明 HTTP 或业务完成。

若缺少 DF、反馈或路径信息，停止在缺证据处；ICMP 被过滤可能形成 PMTUD 黑洞，普通重传并不保证自动修好。未来调查应记录受影响的尺寸、路径、时间与反馈，才讨论降级或其他探测机制，不能把“变小应该就好”写成当前已验证策略。本例不实现分片、IPv6 PMTU 或 PLPMTUD，也不修改 MTU。[RFC 1191 §1–2](https://www.rfc-editor.org/rfc/rfc1191#section-2)

## 4. TCP确认字节，不确认订单
<!-- 原用途: 61-67 -->

可靠字节流的意义是 TCP 利用序号、校验、确认与重传，向接收应用提供按序的数据；它不保证无限期可达，更不产生订单回执。先看连接建立：C 发 SYN SEQ1000；S 回 SYN-ACK SEQ9000、ACK1001；C 发最终 ACK SEQ1001、ACK9001。SYN 各占一个序号，且三步均交付时本题双方建连成立。最后 ACK 未送达时不能称双方都已 ESTABLISHED；建连成立也尚未通过 TLS。

TLS 完成后的 C 下一序号 5001 是独立给定快照。不能拿初始序号 1000 加 HTTP163 算它，因为中间还发送过题设未列长度的握手数据。[RFC 9293 §3.4](https://www.rfc-editor.org/rfc/rfc9293#section-3.4)

### 4.1 ACK必须放在连接状态中解释（P3）

以下每行独立从 C 的 ESTABLISHED 快照出发：SND.UNA=5001（最早未确认），SND.NXT=7001（下一待发送），已有 2000 字节在途。无序号回绕、无 SACK/恢复算法、无 FIN 在途、连续发送无缺口；进入 ACK 分支前，连接、报文及接收序号上下文已验证，ACK flag 开启、非 SYN/RST，来自题设诚实对端。这里只分析 ACK 分支，不实现完整 TCP 输入或安全检查器。

| 收到的输入 | PAPER_EXPECTED | 不能推出什么 |
| --- | --- | --- |
| ACK6461 | 满足 5001 < 6461 ≤ 7001，确认 1460 字节，UNA 推进到6461 | 接收进程已经 read |
| ACK7001 | 累计确认连续的 2000 字节，UNA=7001 | TLS、HTTP、数据库已完成 |
| ACK5001 | 没有新字节被确认，可能是合法重复 ACK | 不能一律当无效报文；按相应规则仍可能带来窗口更新；单条重复 ACK 不是快速重传证明 |
| ACK7002，NXT仍7001且无FIN | 确认了未发送序号，不能推进 UNA；该 ACK 分支按规范发 ACK、丢弃并返回 | 四元组相同不使任意 ACK 合法 |
| **独立改为**已发 FIN SEQ7001，NXT=7002，再收 ACK7002 | 现在 FIN 的一个序号被确认，该数值可以成立 | FIN 消耗序号不等于多了一字节应用数据 |

累计 ACK 标的是下一期待序号。例如 S 的 RCV.NXT=5001，却先收到尾段6461..7000，在题设“保留乱序数据并立即累计确认”的策略下先 ACK5001；头段5001..6460到达后才可推进7001。未推进 ACK 不等于尾段未到，接收端也不必固定每段发一个 ACK。真实序号会按 2³² 回绕，本例普通整数比较只适用于已排除回绕的输入。[RFC 9293 §3.4、§3.10.7.4](https://www.rfc-editor.org/rfc/rfc9293#section-3.10.7.4)

### 4.2 流控与拥塞控限制不同资源（P3）

接收窗口 rwnd 保护接收方可用空间；拥塞窗口 cwnd 限制发送方给网络施加的在途负荷。独立快照仍为 UNA5001/NXT7001、FlightSize2000，无重传恢复，窗口缩放已经解释，rwnd=4096、cwnd=3000，计算期间不变。

流控剩余为 4096−2000=2096；拥塞额度为 3000−2000=1000；此刻**最多可增加1000字节**，即 SEQ7001..8000，不是必须立即发送。若 rwnd 改1000，已有2000在途，新数据额度是0；若 cwnd 改1500，同样是0，而不是还能加500。零窗口规定探测是另一行为，“不能加新数据”不代表任何 TCP 报文都不得发送。缺少缩放、在途量或恢复状态，便不能套这个简式。[RFC 9293 §3.8.6.2.1](https://www.rfc-editor.org/rfc/rfc9293#section-3.8.6.2.1)、[RFC 5681 §2–3](https://www.rfc-editor.org/rfc/rfc5681#section-2)

### 4.3 read、记录与消息不是同一边界

底层 socket 把这 2000 字节 **TLS 密文编码**交给 TLS 实现时，可以分为500+900+600，也可以一次2000，或其他合法分批。TLS 重组记录，认证解密并去 padding 后，才向 HTTP 解析器交付本例163字节明文；HTTP 再解释144字节头区和19字节 body。一次 write、一次 read、一个 TCP segment、PSH 或一个 TLS record，都不是通用的 HTTP 消息终止符。[RFC 9293 §3.7、§3.9.1.2](https://www.rfc-editor.org/rfc/rfc9293#section-3.7)

### 4.4 小报文、复用与连接生命期
<!-- 原用途: 72-79,257-259 -->

Nagle 的用途是减少很多小段：当已有未确认数据时，可暂存新的小写入，直到旧数据获确认或积成满段；延迟 ACK 则减少确认报文。如果交互应用等着小片段触发下一步，两者可能增加等待。`TCP_NODELAY` 是常见的关闭 Nagle 接口选项，选项及库行为需按目标系统核对；关闭它不取消拥塞控制，也不保证“write立即在线上出现”。本轮只比较机制，不提供调参配方。[RFC 9293 §3.7.4、§3.8.6.3](https://www.rfc-editor.org/rfc/rfc9293#section-3.7.4)

连接池与复用减少重复 TCP/TLS 握手，但需要池容量、空闲期限和失败恢复合同。连接不能仅凭“同四元组”全局认定：两端 IP+端口还需地址族、协议、namespace、设备/绑定上下文、观察点与连接生命周期。Linux v6.12 的 NET_NS 和 `inet_match` 中 namespace、地址端口与绑定设备检查，只支持这些上下文确实重要，不证明所有协议的完整解复用算法。

独立裸 TCP 半关闭例：A 发 FIN7001，B 收全前序数据并 ACK7002；A 收到该 ACK 而 B 未发 FIN，此时 A=FIN-WAIT-2、B=CLOSE-WAIT。B 仍能在另一方向发送；A 是否继续读还取决于所用 API。主动关闭后的 TIME_WAIT 有助于隔离旧连接残留报文并处理末尾确认，不是业务提交等待器。HTTPS 还需 TLS1.3 的 close_notify 语义，不能直接把此裸 FIN 例当作 TLS 库的 close/shutdown 行为。[RFC 9293 §3.6](https://www.rfc-editor.org/rfc/rfc9293#section-3.6)、[RFC 8446 §6.1](https://www.rfc-editor.org/rfc/rfc8446#section-6.1)

NAT 映射和服务器空闲回收有各自生命期；一端状态过期或重启，另一端仍可能以为连接存在，形成半开情形。关闭通知也可能未送达，不能假定“已通知”必被客户端看到。Keepalive 需启用并满足空闲条件；成功只表示该次 TCP 对端回应，不证明应用/数据库健康，单次漏答也不能直接判死。应用需要依据自己的期限和业务状态恢复，而不是等一个永远可靠的断连通知。[RFC 9293 §3.8.4](https://www.rfc-editor.org/rfc/rfc9293#section-3.8.4)、[Linux 6.12 keepalive 文档](https://docs.kernel.org/6.12/networking/ip-sysctl.html)

## 5. TLS要验证“谁”，也要验证本次握手（P5）
<!-- 原用途: 91-97 -->

主例的原 URL 指定 `api.example.test`。这个 reference identity 在看服务器证书之前确定，不能由服务器提供的名字或 DNS 中途的 CNAME 替换。握手选择双方支持的版本、密码算法并建立密钥材料，随后TLS用相应密钥保护应用流量。TLS 保护机密性和完整性，但要把数据交给 HTTP，还需一组职责不同的检查：

| 检查 | P0 正向条件及用途 | 独立失败出口 |
| --- | --- | --- |
| 证书路径及适用检查 | 信任路径、时间和相关证书条件通过，使证书有可接受信任依据 | 无法建立信任或不满足适用检查则停；本文不重写 PKIX 验证器 |
| 名称匹配 | SAN 含 reference DNS-ID `api.example.test` | 路径可信但只有 `other.example.test` 仍失败；不换 reference、不关闭校验 |

| Finished | 检查握手及所计算密钥的认证值；P0 双方都成功 | 校验失败不能宣称安全会话完成 |
| 记录认证解密 | 使用已建立密钥，成功验证记录并还原上层字节 | TCP 已 ACK 而记录缺字节或认证失败，不宣布 HTTP 接收完成 |

SNI 让服务器据名称选择虚拟主机配置，**它自己不认证服务器**。ALPN 选择双方支持的应用协议；TLS1.3 的服务器选择放在 EncryptedExtensions。P0 选中 `http/1.1`，所以发送上述文本语法成立；如果另一次协商为 h2，就要用 HTTP/2，不能继续发送这163字节 HTTP/1.1。h3 需要 QUIC 承载及相应连接建立，不能在已有 TCP/TLS 会话里改一个 ALPN 名字得到 HTTP/3。

若独立加入 CNAME `edge.example.test`，本题 reference、SNI 和 HTTP Host 仍由原 URL 决定；解析地址变化不授权更换验证目标。TLS 完成也不自动替服务器认证租户，应用授权仍是单独条件。会话恢复可降低后续握手成本，但本例明确不使用；临时密钥交换与前向保密的关系取决于模式，不能从“TLS1.3”三个字推断 PSK-only 也具有同样性质，更不能把0-RTT数据套进本题无重放的前提。

## 6. HTTP先定界，再解释状态与业务
<!-- 原用途: 121-130,276-280 -->

P0 的直接请求使用 origin-form `/orders`，Host 来自 URL 的 authority。方法、目标、头区和 body 共同形成消息，不能只解析 JSON 看起来完整就越过 HTTP framing。GET 的“安全”表示请求意图只读；“幂等”表示相同请求的预期效果重复执行与一次相同，返回内容和附带日志仍可变化。GET 删除订单不会因为方法名字是 GET 就安全。POST 常用于提交或触发动作；PUT 表达所指定资源的创建/替换语义，PATCH 用于部分修改，但不能把“更新”统称为自动可重试。具体恢复仍需方法和服务合同。[RFC 9110 §9.2](https://www.rfc-editor.org/rfc/rfc9110#section-9.2)

状态码的五类是信息性1xx、成功2xx、重定向类3xx、客户端错误4xx、服务端错误5xx；这只是理解响应的入口。202 可能已接受但还未执行；304 引导使用适用缓存而非必须跳到新 URL；101 切换协议。5xx 也不能证明原业务没有产生副作用。

### 6.1 HTTP/1.1定界有优先级（P5）

下面按 [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112#section-6.3) 的次序判断，先匹配的规则先用。各行是独立接收场景，TLS 已交出认证解密字节；未注明的代理、编码或请求上下文不存在。CL 指 Content-Length，TE 指 Transfer-Encoding。

| 优先条件 | 怎样知道消息结束 | 反例与停止点 |
| --- | --- | --- |
| 对 HEAD 的响应；或1xx（含101）、204、304 | 头后第一个空行结束消息，没有 body/trailer | 即使出现表示长度，也不能越过本规则去读所谓 body |
| 对 CONNECT 的2xx | 头区结束即转为隧道；忽略该响应 CL/TE | 后续是隧道数据；不属于本篇主例 POST |
| 普通消息同时有 TE 与 CL | TE 优先；这种歧义应作为错误看待，本题端点报错并关闭 | 不按 CL 截取。选择转发的中间者必须先移除收到的 CL 并按 TE 处理；本题拒绝策略不是唯一规范动作 |
| 有 TE，最终编码 chunked | 正确块语法、终止0块及完整 trailer 结束后才完成 | 缺终止0块或尾部不全即不完整；不依赖 socket EOF |
| 有 TE，最终编码不是 chunked | **响应**按关闭定界；之后还须按编码解释内容 | **请求**无法可靠定界，服务端400并关闭；不猜 CL、不借 EOF结束请求 |
| 无 TE，CL 无效或冲突（如19与20） | 不可恢复 framing 错误 | 用户代理关闭并丢弃响应；服务端收请求则400/close；代理收响应则关闭上游、丢弃并回502，不能混写角色 |
| 无 TE，合法重复 CL 值全为19 | 可按单一合法19处理，仍须收足19 | 不能写成所有重复字段一概拒绝 |
| 无 TE，单一合法 CL19 | body 恰19 octets后定界 | 只收17到 EOF/timeout：不完整并关闭；不能借下一连接字节补完旧消息 |
| 普通请求，无 TE/CL | body长度0 | 请求不使用关闭定界 |
| 其余普通响应，无 TE/CL且头区完整 | 连接关闭定界，且底层无错误；HTTPS 还须有效 TLS 关闭通知 | 仅有 TCP EOF而 TLS incomplete close，不足以完成该响应 |

这里校验 CL 的意义是配合优先规则和实际收到的字节防止截断，不是见到 CL 就相信它。跨代理解析不一致可能导致两端对消息边界分歧，应拒绝歧义或按规范明确处理，本文不执行请求走私或安全试验。统一错误响应格式有助于客户区分协议错误与业务拒绝，却不能让格式统一的500变成“肯定没提交”。

### 6.2 完整响应与成功结果是两条轴

| 已给定输入 | 协议判断 | 本题客户端业务判断 |
| --- | --- | --- |
| P0 完整201、合法 CL19、19字节订单回执 | HTTP完整 | 依明示持久性合同，confirmed(o-42) |
| 完整202、合法头区、CL0且无TE | HTTP完整 | pending；最后仍可能不执行，缺终态合同不能承诺完成时间 |
| 只有202状态行、头区未完 | 尚未完整 | 不能声称协议接收完成，截止或EOF时按不完整处理 |
| 条件 GET、有适用缓存、完整304头区 | 304无body | 按缓存合同复用/更新元数据；无缓存不能编造表示，也不能把304套到创建订单POST |
| 先前有效Upgrade请求、返回匹配且完整101与Upgrade头 | 切换响应到头区结束 | 后续按选定协议处理；普通POST收到未预期101不能自动接受 |
| 普通201、CL19、只收17后EOF/超时 | 不完整 | unknown，服务端仍可能已经提交 |
| P0 的完整 CL19 响应已被TLS认证，之后 incomplete close | 已定界的该HTTP消息不因此自动失效 | 先前confirmed仍成立；其他未完整消息仍可能被截断 |

反过来，即使关闭定界的响应完整，也没有凭空生成业务终态。TLS close_notify、TCP FIN、HTTP消息结束、数据库提交是四个不同事件。[RFC 9112 §8、§9.8](https://www.rfc-editor.org/rfc/rfc9112#section-9.8)、[RFC 9110 §15.2.2、§15.3.3、§15.4.5](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.3)

当有代理时还需核对它是否重写 Host，以及“真实客户端地址”究竟来自受控代理还是客户端可伪造的头。只信任已确认边界内代理注入的数据，并使关联标识贯穿各跳；否则一串转发头不能证明身份或请求来源。P0 排除了代理，不能把本例的端到端 TLS 身份直接套到分段终止 TLS 的架构。

## 7. 业务unknown如何恢复，取决于服务合同（P6）
<!-- 原用途: 191-194 -->

连接、读、写超时限制局部等待，总 deadline 限制整次用户操作。它们使客户端能停止占用资源，但不能单凭“超时”断言服务端已停止或事务已回滚。纸面终态按证据区分：

| 客户端此刻掌握的证据 | 能判断的状态 | 下一步的边界 |
| --- | --- | --- |
| 仅一次尝试、无0-RTT/旧重试，确认在发送HTTP应用数据之前失败 | 本次请求未交付 | 总预算内修复前提后可重新尝试；不推断系统其他请求无副作用 |
| socket发送成功或ACK7001，没有完整终态回执 | unknown | 可能尚未read、执行中或已提交；不能换新键盲重发POST |
| 500/502/504、RST、EOF、read timeout | 错误类别已知，业务效果仍可能unknown | 需服务端终态证据或已有去重合同；没有合同则停止自动恢复 |
| 完整202但未取得终态 | pending | 已接受不是保证最终执行；查询方式和期限须由服务定义 |
| 本请求完整可信终态回执o-42，且符合P0持久性合同 | confirmed(o-42) | 之后断连不撤销订单 |

### 7.1 去重键不是魔法字段

P0 的去重结论依赖五个环节相接：服务端先完成租户授权；把参数按同一规则规范化；以租户+CreateOrder+键确定唯一作用域；让并发请求串行化或受唯一约束；最后把订单效果与终态结果一同原子持久提交。客户端随便多发一个名叫 Idempotency-Key 的字段，不能建立这些保证。

| 服务端给定状态 | 同作用域、同键、同参数的结果 | 破坏结论的反例 |
| --- | --- | --- |
| 键不存在且事务成功 | 订单o-42与结果记录一起出现 | 若结果记录稍后另写，提交后断连可能出现重复窗口 |
| 两个相同键并发到达 | 只有一个有效提交者；另一个等待或明确pending，完成后复用终态 | 第二请求越过pending另执行，或失效执行者未被隔离，就不能推唯一性 |
| 提交前崩溃且全部相关写入回滚 | 下一有效事务可完成一次 | 事务外支付已发生，便不属于该单事务模型 |
| 已提交后响应丢失，24小时保留期内同键恢复 | 返回同一o-42；客户端取得完整回执后才confirmed | 同键异参拒绝；不同租户/操作是另一作用域；过期后无去重推论 |

成功终态的24小时从提交起算；pending不能因为这个规则到期被遗忘而另开执行。客户端需知道合同仍有效才同键恢复。未知旧请求超过保留期后，不能换新键当作无害修复；应先取得服务方可归属的结果证据。该模型没有跨支付、邮件、消息系统的外部副作用，所以只支持有限作用域的去重与确认，不证明任意分布式系统的 exactly-once。

### 7.2 有上限的恢复时间线

给定总 deadline=t10秒、最多2次尝试。首次t0开始，服务器t1.5已提交，客户端t2读超时；允许退避100–200ms，本次抽到150ms。第二次t2.15携相同作用域/键/参数开始，t3收到完整同o-42回执，因此由unknown转为confirmed。**退避只安排时间，恢复授权来自上述业务合同**。

若当前t9.95，而下一次至少退避100ms，则不能在总deadline前开始；若第二次也失败，本题自动重试到此停止，保留unknown及标识。取消或deadline过期只使客户端停止等待，服务端仍可能执行；确认取消成功需要明确的服务端终态合同，不能把RST或取消信号当回滚证明。本文未定义状态查询URL，因此只指出缺少的终态证据，不伪造可调用接口或查询结果。[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2) 限制非幂等请求的自动重试；具体事务、参数、并发及保留期是本题额外假设。

## 8. 观测回答哪一层问题，结论就停在哪一层

### 8.1 TTL与ICMP的观察边界（P8）
<!-- 原用途: 54-57 -->

TTL 限制 IP 分组可继续转发的寿命，路由环路会不断消耗它。P0 每跳减1，所以 R 转发时64→63；独立将入口 TTL 改1，R 就不能继续转发该包。ICMP Time Exceeded 可报告这类失败，但客户端是否看到回复，还受生成、限速、过滤和返回路径影响。

traceroute 的用途是用逐步增大的 TTL 与相应回复观察路径线索；某跳不回，不足以证明它不转发。ping 成功只证明那次 ICMP Echo 往返，既不充分证明 HTTPS 可用，也不是 HTTPS 成功的必要条件。将“只看到一个星号”直接写成“这台路由器丢业务包”，跳过了观察协议与业务流不同的前提。[RFC 792 Echo / Time Exceeded](https://www.rfc-editor.org/rfc/rfc792)、[RFC 1812 §4.3.2.8、§5.3.1](https://www.rfc-editor.org/rfc/rfc1812#section-5.3.1)

### 8.2 工具的用途与不能替代的证据
<!-- 原用途: 156-170 -->

以下保留常用工具的**读证据用途**，不是本轮运行步骤；这里只分析已给定记录，没有执行表中命令。授权环境中将来采样时，仍须记录目标、时间、权限、采样点和完整性。

| 证据来源 | 可以帮助回答的问题 | 不能单独回答的问题 |
| --- | --- | --- |
| ping | 某次ICMP请求是否取得匹配回复 | TCP443、TLS、HTTP和业务是否成功 |
| traceroute、mtr | TTL探测的回复路径、重复采样中的延迟/漏答分布 | 某跳不回是否转发业务包；路径变动是否唯一故障原因 |
| ss；旧系统的netstat | 当前观察上下文中的socket状态及相关资源线索 | 应用是否消费了缓冲、订单是否提交；工具间字段也不能不核对版本就互换 |
| ip route、ip neigh | 当时选路候选和邻居缓存状态 | 未提供的策略规则、别的namespace、反向路径或远端进程状态 |
| dig | 指定解析器、查询名/类型在当时的回答及TTL | 所有缓存都已更新，或返回地址的服务身份可信 |
| curl | 在其请求参数、协议版本、验证选项下获得的HTTP/TLS结果 | 浏览器全部策略、用户流和业务副作用均已验证；必须保留实际选项才可解释 |
| tcpdump、Wireshark | 某抓点捕获的字节、时间戳和协议字段解析 | 抓点外发生了什么；采集完整；密文内一定是何种业务结果 |
| ethtool计数器 | 某接口/驱动报告的错误、丢弃及卸载线索 | 同名计数在不同设备含义完全相同，或增量对应唯一请求 |
| conntrack | 已观察到的有状态转换/NAT表项生命周期 | 表外另一设备状态、应用终态或未记录的过去流量 |
| 防火墙日志 | 哪条已记录规则在何时处理了流量 | 没日志等于没丢弃；日志可能受采样/限速/记录配置影响 |
| 客户端/服务端指标 | 分别从观察者视角统计错误类别和比率 | 客户端超时与服务器错误必为同一分母或同一业务失败 |

例如客户端100次尝试中5次超时、服务器记录100次处理中2次500，不能相加成7笔失败订单：重试、窗口边界和已提交但回执丢失都可能改变对应关系。先统一“操作、请求、尝试”的分母，再用标识关联。[RFC 9293 §3.3.1、§3.9](https://www.rfc-editor.org/rfc/rfc9293#section-3.9) 说明 TCP 状态及抽象接口；上述具体工具选项和版本未在本轮测试。

### 8.3 主机里的大对象不等于线上巨帧（P2）
<!-- 原用途: 28-30 -->

网卡卸载可把部分处理从 CPU 转给设备，但会改变观察位置看到的对象。TSO 是设备侧发送分段；GSO 提供软件分段能力；GRO 是接收聚合。大 skb 可以在栈中传递到后续分段处，这并不使 TSO/GSO 变成“合并大段发送”。LRO也属于接收聚合方向的扩展问题，具体实现与限制不能从本文所读 GRO 文档直接推出。

假设在发送分段前观察到一个2000字节数据对象，同时在线路上见到1460+540两个 TCP payload，两者可以同时为真；接收方在 GRO 后也可能再次看到较大对象。未知 hook、卸载状态、snaplen、时间戳来源及 FCS 是否可见时，停止把捕获对象称为“原始线上帧”。1518字节含FCS的纸面帧，不保证抓包文件会保存全部1518字节。这里不修改卸载设置。[Linux 6.12 segmentation-offloads：TSO、GSO、GRO](https://docs.kernel.org/6.12/networking/segmentation-offloads.html)、[v6.12 if_ether.h 常量](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/uapi/linux/if_ether.h)

### 8.4 重传是恢复动作，不是根因标签
<!-- 原用途: 68-71 -->

在 RFC 5681 描述的经典算法中，慢启动根据新数据确认增加 cwnd，拥塞避免阶段采用更缓的增长；这是发送者逐步探测可用容量的办法。其快速重传使用满足条件的三个重复 ACK 作为丢失迹象，RTO 则通过动态计时提供另一条重传路径。重复 ACK 还可能由乱序或复制引起，重传也可能因 ACK 返回路径问题触发。

因此一条重复 ACK 不能推出快速重传，看到重传不能推出原数据必在去程丢失；第10节给出反例。本文不实现 RTO 估计公式、完整恢复算法，也不声称 Linux6.12 或当前机器默认采用这个经典算法。[RFC 5681 §3.1–3.2](https://www.rfc-editor.org/rfc/rfc5681#section-3.2)、[RFC 9293 §3.8.1](https://www.rfc-editor.org/rfc/rfc9293#section-3.8.1)

### 8.5 BDP与窗口只能给出有条件的上界（P7）
<!-- 原用途: 141-150 -->

RTT 是一次相应往返的时间尺度，瓶颈带宽约束大流量的理想速率。输入为100,000,000bit/s、RTT=0.040s，则 BDP=4,000,000bit=500,000byte≈488.28125KiB。它说明维持理想管道所需的在途量数量级，**不是直接可用的buffer配置值**。

另给稳态理想快照：cwnd=64,000byte，已解释缩放的rwnd=256,000byte；持续满窗口，忽略协议开销、起步、丢失和供应不足。窗口/RTT上界为min(64,000,256,000)/0.040=1,600,000byte/s=12.8Mbit/s。把rwnd改512,000仍受cwnd限制；真实吞吐可更低，增加buffer不保证得到12.8Mbit/s。未协商Window Scale时，16bit窗口字段的精确上限是65535，不是65536。[RFC 7323 §1.1、§2](https://www.rfc-editor.org/rfc/rfc7323#section-2)

如果只写RTT“40”或窗口“64K”，没有秒/毫秒、byte/KiB及缩放含义，就停止数值推导。应用供给、CPU/TLS、队列、丢失、重排与恢复都能使带宽未被用满。丢失会带来重传需求，拥塞控制还可能减少发送额度；下降幅度和恢复过程依具体算法及状态，不能从丢失计数直接算出唯一吞吐。窗口覆盖BDP只是特定管道模型中的条件，不能升级成普遍吞吐保证。

队列还会改变延迟：前项未完成可能阻塞后项，即队头阻塞；持续积压的缓冲可能把拥塞表现为长等待。ECN保留为“怎样用显式拥塞标记辅助端点响应”的问题，需双方和路径支持；DSCP用于表达服务类别意图，跨域是否遵守须另核对。限速也要分清：policing可超额丢弃/标记，shaping用排队延迟发出；“平滑突发”有队列和时延代价，不是所有限速器的同义词。这些队列/策略扩展未在本轮验证设备实现，不能据此给生产调参承诺。

## 9. 沿请求链排查，并保存没有答案的地方

### 9.1 先限定事件，再关联证据
<!-- 原用途: 171-175,236-244 -->

网络工程把协议机制与运营约束接在一起。一次事件先固定时间窗、受影响租户/区域、客户端版本、拓扑和依赖，再用连接标识、连接生命周期、请求标识和去重键区别“同一业务的不同尝试”。分布式追踪可关联跨服务耗时，但只代表被采到的span；采样率在成本与可见性之间取舍，缺span不等于没调用。

指标提出范围，日志关联状态，抓点记录限制路径假设；三者不能用一个观察替另一个观察。将来获授权采集时，要保护载荷隐私和密钥，先用最少数据回答已定义问题。本轮只有合成表。缺少时钟同步/抓点完整性，便不能伪造跨机单向耗时或唯一根因。

分层也给出了工程选择的依据：超时、有限重试和隔离各解决不同失败；身份、授权、加密相互补充；性能变更前需同口径测量，变更后需观测及可恢复路径。设计不仅列成功路线，还要列无路由、身份错、不完整响应、已提交而回执丢失等出口，保存依赖和拓扑使后来的人能够重走判断。第10节的回滚题展示了“恢复网络配置”与“对账未知订单”为何要分开。

### 9.2 一个阶段没有证据，不跨过去猜下一阶段
<!-- 原用途: 176-190 -->

这里的“检查”是对已有题设/记录的审阅顺序；复现操作须另有环境和授权，本轮未执行。每行指出下一份有用证据，避免重复泛称“网络不通”。

| 阶段 | 先问什么 | 停止点或分支 |
| --- | --- | --- |
| 事件范围 | 时间窗、地域/运营商、单请求/单连接/全局是否相同 | 跨地域比较须对齐名称、入口、版本、负载和时间；不能把不同条件当正反控制 |
| DNS | 使用哪个解析器、回答/TTL/缓存状态是什么 | 无新回答就停在名称层；不据此更换TLS reference |
| 路由与邻居 | 观察的是哪个namespace/接口？是否有匹配路由、正确下一跳及邻居状态？ | 无路由与邻居解析失败是不同缺口；补正反方向及防火墙/安全组策略证据 |
| TCP建立 | 三次握手何处可见，服务监听地址/端口是否匹配 | 监听环回/错误地址与中间路径拦截都可能导致失败；握手成功不越过TLS |
| TLS | 时间、路径、reference/SAN、CertificateVerify、Finished、ALPN哪一项有结果 | 名称错停在身份；不通过关闭验证来“证明网络好了” |
| HTTP | 对应方法/请求、状态、完整头区、TE/CL和body够不够 | 完整202只到pending；错误格式或状态行不能代替终态 |
| 性能与资源 | 单连接的重传/窗口，还是全局端口、文件描述符、连接池/线程池耗尽？ | 某队列满说明资源约束，尚需入流/服务速率与依赖证据；不要只提高池上限转移压力 |
| 变更关联 | 故障与配置/路由/证书/部署记录时间一致吗？ | 时间相关不是因果证明；恢复须有已批准旧配置、停止条件和独立验证，见E5 |

### 9.3 熔断、舱壁、限流与降级保护的是预算
<!-- 原用途: 195-198 -->

异常依赖连续占满等待资源时，熔断可在约定条件下暂时阻止继续调用；舱壁按资源池/租户限制并发，避免一个故障吞尽全部线程或连接；限流控制进入速率。三者需各自恢复条件和预算，不能把上游拒绝变成无限重试风暴。它们保护剩余服务能力，并不确定先前未知请求的业务结果。

降级可为允许陈旧数据的读取提供旧值，但创建订单不能凭旧页面造出新订单成功。应明确陈旧期限、适用操作和用户可见状态；否则“可用”可能只是掩盖错误。在 P0，保护动作后仍须保留 confirmed/pending/unknown 的真实分类。

## 10. 纸面练习：输入、预期、反例与停止点（P8）

这一节承接原练习的教学用途。原抓包、VLAN、协议比较、P99事件分析和回滚练习，本轮都改为**给定材料的纸面推理**；未执行历史工具、配置或故障活动。答案来自前述输入，不是运行日志。

### 10.1 封装、握手和预算复算
<!-- 原用途: 206-208 -->

给定 P0：画出19字节JSON→163字节HTTP→2000字节TLS记录编码→1460+540 TCP数据→1500/580 IP包→1518/598 Ethernet帧。每个箭头注明谁加了头/编码以及在哪一层结束；把2000直接标成HTTP明文即判错。

再用100Mbit/s与40ms算出BDP500,000byte；用SYN1000、SYN-ACK9000/ACK1001、最后ACK1001/9001解释双向初始序号的确认。正例得到连接建立，反例删去最后ACK交付就不能称双方都已ESTABLISHED。缺单位、头长或握手交付条件时停止计算，不靠想象填入输入。

### 10.2 E1：两端观测仍不等于唯一归因
<!-- 原用途: 209 -->

历史题“使用 tcpdump 定位重传原因”在这里替换为下表。A/B为同一路径两端、同一连接/epoch，方向和序号已归一化；时间不用于跨机单向时延计算。这是**合成观测**，不是抓包。

| 事件 | A发送侧材料 | B接收侧材料 |
| --- | --- | --- |
| 原数据SEQ5001,len1460 | 有 | 有 |
| B回ACK6461 | A没见到 | B发送侧有 |
| 稍后同序号数据 | 标为A发重传 | B又收到 |

可推出：原数据到达了B抓点，A重传与未见ACK相容。候选范围包括ACK返回路径、A接收处理或A采样缺失，不能称原数据去程丢失。反例：A采集漏了ACK但TCP内部已收到，稍后的“重传”标签还可能来自采集或时间关联错误。没有抓点完整性和TCP状态，停止定位根因；即使两端材料完整，也不能凭它确定哪个中间设备丢包。

### 10.3 E2：最小VLAN纸图
<!-- 原用途: 210 -->

历史配置题在此用完整抽象模型替代：S1连接A/B于VLAN10、C于VLAN20；S2连接D于VLAN10、E于VLAN20；S1—S2 trunk仅允许VLAN10。没有路由器或跨VLAN转发；广播只在所属VLAN允许端口复制，且不从入口原样发回。

```text
VLAN10: A -- S1 -- B       S2 -- D :VLAN10
             |             |
             +-- trunk ----+   只允许10
             |             |
VLAN20:      C             E :VLAN20
```

A发广播，B/D可收，C/E不可收。独立移除trunk允许表中的10后，D也收不到，但不能据此说A/B本地失联。这个题分清广播域和允许表的职责；它不是交换机配置教程，也不证明VLAN能替代全部安全策略。

### 10.4 E3：HTTP/1.1与HTTP/2的消息映射
<!-- 原用途: 211 -->

历史抓包比较题替换为两个独立、无body的只读GET A/B。在同一HTTP/1.1连接管线化A再B，响应必须按A再B发送，并各自依定界规则读取。另开一个已完成ALPN=h2及连接preface/SETTINGS等必要初始化的HTTP/2连接，请求用客户端stream1与3，HEADERS均END_HEADERS+END_STREAM。

给定服务端两条流合法、窗口足够，响应可以是：HEADERS1 → HEADERS3 → DATA3(END_STREAM) → DATA1(END_STREAM)，其中响应头块均已完整，随后DATA合法。B先完成；这是不同流的二进制帧交错，不是把HTTP/1.1文本随意穿插。

反例：底层TCP前部字节丢失尚未补齐，后续多个流的帧仍可能一起等TCP按序交付，因此HTTP/2不消除所有队头阻塞。这里不提供HPACK编码或二进制抓包，不把h2c Upgrade当作TLS h2启动流程。[RFC 9112 §9.3.2](https://www.rfc-editor.org/rfc/rfc9112#section-9.3.2)、[RFC 9113 §1、§3.2、§5、§8.1](https://www.rfc-editor.org/rfc/rfc9113#section-8.1)

### 10.5 缓存切换与有限重试复算
<!-- 原用途: 212-213 -->

沿P4时间线，问“t660改权威后，t700旧缓存是否一定过期”，答案是否：A仍余2900秒；负缓存题t120仍可能NXDOMAIN、余180秒。serve-stale的正TTL又是独立条件，不能混进P0无stale输入。缺新的权威回答就停止推导新地址。

沿P6时间线，问“t2超时后换键是否安全”，答案是没有该依据：服务器t1.5可能已提交。本题用同作用域/键/参数在t2.15恢复，t3取得完整同o-42终态才确认；第二次仍失败或预算不足则停止。去重字段、退避和总deadline必须一同遵守服务合同，不以“能重发”代替“允许重发”。

### 10.6 E4：P99升高意味着什么
<!-- 原用途: 214,255-256 -->

历史事件分析题改为两组**合成样本**，各100条、完整无采样、同口径，单位ms。基线98条20、1条30、1条200；新窗口98条20、1条120、1条200。定义nearest-rank P99为排序后第ceil(0.99×100)=99个值，所以P99从30升至120，最大值仍是200。不同插值法或样本范围须重算；这100条不是生产P99。

新窗口的120ms请求用客户端同一单调钟：t0开始、t5 TCP完成、t15 TLS完成、t20请求写入完成、t110首个响应字节、t120完整响应。因此阶段耗时为5/10/5/90/10ms。这组阶段时点没有单列DNS耗时，不能从中发明DNS指标。

其中90ms包含请求剩余传输、服务端排队/处理及返回路径，不全是服务计算时间。没有服务端关联时钟/span，不能定位数据库；不同请求上的各阶段P99也不能相加得到端到端P99。停止点是补充所缺的关联证据，而不是编造真实故障或启动压测。

### 10.7 E5：变更与回滚纸面清单
<!-- 原用途: 215-220 -->

### 11.1 二层运营：广播域、冗余和帧预算
<!-- 原用途: 20-27 -->

| 主题 | 用途及继续设计前要回答的问题 |
| --- | --- |
| VLAN与trunk | VLAN限制广播域，trunk在链路上承载被允许的VLAN；E2说明仅标签存在并不等于允许表或路径正确。跨VLAN需求需另有转发与策略 |
| STP | 在有冗余连接的二层拓扑中处理环路风险；应核对选用协议、角色及收敛过程，不能假设“插更多线只会更可靠” |
| LACP | 聚合多物理链路以供冗余/总体容量；单流能用多少仍由哈希与成员状态决定，不能把总容量当单流必达带宽 |
| 全双工 | 两端可同时收发，避免半双工共享介质式碰撞处理；仍可能拥塞或丢弃，不能用“无碰撞”推出无排队 |
| CRC/FCS | 用于发现帧传输错误；检测错误不等于认证来源，也不负责恢复业务消息 |
| 广播资源 | 广播复制消耗链路及交换/终端处理资源；应先界定广播域、速率和来源，再判断异常，不把所有广播当故障 |
| Jumbo frame | 减少相同数据量的帧数可能有收益；需相关链路、封装及路径预算支持，不是要求互联网所有端点MTU数值相同，也不能忽略途中较小MTU |

### 11.2 地址、DNS与路由控制面
<!-- 原用途: 34-38,41-45,48-53,58-60,110-114,116-118,221-230 -->

| 主题 | 用途及成立条件/下一问题 |
| --- | --- |
| 私网、NAT和端口分配 | 私有地址供内部寻址，公网通信需要适当出口设计；NAT会改地址或端口，因此不同抓点的四元组可能不同。网关端口分配与映射寿命可能耗尽/过期，应问共享出口和并发规模，不能把NAT当身份验证 |
| IPv6、邻居发现、双栈 | IPv6扩展地址空间，邻居发现承担相应链路邻居职责；双栈意味着两套地址/路由/策略都要考虑，一边成功不能证明另一边。本文ARP数字例不能原样套到IPv6 |
| 环回、链路本地、DHCP、SLAAC与RA | 环回用于本机范围，链路本地受所在链路约束；DHCP提供IPv4配置，SLAAC用于IPv6自动配置，RA会影响IPv6默认路由。应分别核对地址、前缀、网关来源和作用域，拿到地址不等于完整配置可用 |
| 地址冲突 | 同一使用范围里地址冲突可表现为邻居映射变化和间歇故障；仍需地址分配与邻居证据，不能把所有间歇超时都归于冲突 |
| 动态路由、OSPF、BGP | 控制面传播可达性并计算/选择路线；OSPF的链路状态视角与BGP的路径及策略视角不同。度量/属性须在其协议和策略语境内比较，不存在脱离上下文的统一“最短就是最优” |
| ECMP、收敛与出口策略 | 等价路径可分担流量，但映射与路径变化会影响流量；收敛存在暂态窗口，出口还受策略约束。需问正反方向及故障期间变化，不把稳定时路由表当全时刻事实 |
| 黑洞路由与ACL | 黑洞路由有意丢弃匹配前缀；ACL按规则过滤流量。它们可用于边界控制，也可成为故障来源；应核对匹配方向、顺序、范围与负责人，不能从“有路由”推到“被允许” |
| A、AAAA、CNAME | 分别用于IPv4、IPv6地址和名称别名关系；别名解析不授权改变TLS reference。类型与名称用途要分开，不能把A缺失当作所有记录缺失 |
| MX、TXT | MX指向邮件服务，TXT可承载特定系统定义的验证信息；应按消费者合同解释，TXT中一段文本本身不证明任何方已获授权 |
| DNSSEC、分流DNS、缓存污染 | DNSSEC用于验证所获DNS数据，分流DNS可按来源给不同答案；异常缓存会给错误去向。分别问验证链、预期视图及缓存来源，DNS数据验证不替TLS名称检查，也不自动加密所有查询 |
| SDN、VXLAN、EVPN | 控制/转发职责分离有利于管理；VXLAN在三层底层承载二层叠加，EVPN分发相关可达性。需同时核对underlay可达、封装MTU和overlay状态，不能只看一层“绿色” |
| 服务发现、四层/七层负载均衡 | 发现维护实例集合，LB按连接或应用信息分发；实例仍在列表不代表已就绪，七层代理还可能改变身份和HTTP边界 |
| 一致性哈希 | 在成员变化时减少某些映射迁移，用于缓存分布等；热点、权重、状态重建与成员视图不一致仍需设计，不保证自动均衡 |
| BFD与前缀泄露 | BFD用于快速检测所监测的转发路径/会话，不是所有物理故障或业务健康的同义词；路由输入/输出策略应约束可传播前缀，误传播风险需结合邻接和授权范围审查 |

这些是保留用途的地图，未核对完整IPv6、路由协议、EVPN或设备配置规范；当前可手算结论仅用第1–3节明确给定的路径与缓存。

### 11.3 UDP、QUIC与实时媒体的不同目标
<!-- 原用途: 81-90 -->

UDP提供数据报机制，不保证按序、交付或去重；无连接机制和较小基础开销不等于应用一定更快。应用可加序号、确认与重传，但也必须承担预算、拥塞和重复处理问题。DNS常见UDP交换说明数据报适合某些请求/响应，并不意味着DNS只能用UDP。[RFC 768 Introduction](https://www.rfc-editor.org/rfc/rfc768)

QUIC在UDP之上提供可靠有序的流，流间没有自动顺序关系，并受流控/流数限制；它没有让“UDP本身变可靠”，可靠性来自上层协议。[RFC 9000 §2](https://www.rfc-editor.org/rfc/rfc9000#section-2) 支持这个区别，本文不审查完整QUIC恢复或迁移算法。

实时音视频更关注播放期限：RTP序号可帮助识别包顺序/缺失，抖动缓冲平滑到达变化，丢包隐藏降低感知中断，FEC用冗余恢复满足条件的部分丢失。它们各有延迟、带宽或质量代价。反例是一包虽重传成功却已过播放时点，此时“最终收到”不能完成实时目标。设计需给出可接受延迟、丢失模式和恢复能力，不能把加大缓冲或增加重传当通用最优方案；本段未实现媒体栈。

### 11.4 HTTP周边、持久连接与消息协议
<!-- 原用途: 131-140,253-254,260-275 -->

| 主题 | 用途及成立条件/反例 |
| --- | --- |
| Cache-Control、ETag | 缓存策略及条件请求减少重复传输；需有适用表示、缓存键和验证条件，不能只看到304就补出不存在的内容，主例创建订单也不能自动套缓存 |
| Cookie、SameSite、CORS | Cookie可承载会话标识，属性控制相应浏览器行为；SameSite限制部分跨站携带情形，CORS约束浏览器跨源访问。它们都不能替服务端授权，非浏览器客户端也不因CORS就被认证；具体浏览器策略需另核对 |
| HTTP/2、HTTP/3与头部压缩 | 多路复用和字段编码减少串行等待/重复字段开销，但TCP承载的HTTP/2仍受TCP按序交付限制；HTTP/3映射到QUIC。压缩状态和资源成本要考虑，不能把h2/h3只当HTTP/1.1文本的新名字 |
| 流式响应和连接复用 | 分批产生内容可降低部分内容的等待，复用可省握手；实际首字节还取决于服务端生成、代理缓冲和客户端消费。复用也需正确定界及失败恢复，不能通过一次read判断结束 |
| 代理Host与LB健康路径 | Host重写可改变应用路由，健康检查路径应代表所需就绪条件；“/health返回200”若未覆盖依赖，并不证明订单路径能成功。TLS在哪里终止、检查走哪条路应写进拓扑 |
| WebSocket、SSE、gRPC | WebSocket长连接需心跳、背压与断连恢复；SSE用于服务器到客户端的事件推送；gRPC常见HTTP/2承载利用流复用。具体协议模式需单独确认，长连接不能免除应用消息和资源预算 |
| 流式RPC取消 | 传播取消可减少无用工作，但传播可能延迟或丢失；客户端停止等待不是对端停止/回滚证明，仍需明确终态和副作用合同 |
| 消息队列与消费者偏移 | 异步队列削峰，但积压和消费能力仍有上限；消费处理与偏移提交是不同事件。先提交偏移后处理可能漏处理，先处理后提交可能重放，需配合业务幂等/事务，而非一个“ACK”包办所有完成层次 |
| 序列化、Protobuf、JSON | 编码影响大小和解析成本，Protobuf字段演进需保持兼容；JSON易检查但实际大小取决于表示与数据，不能无条件宣称总比二进制大。比较时固定同一语义和编码选项 |
| 版本协商、Feature flag与租户灰度 | 用于渐进启用兼容能力和限制变更范围；旧客户端、代理和服务端组合需一同验证，开关回退不保证撤销已经写下的新格式或业务效果。灰度标识也须可信且不跨租户泄漏 |
| 大请求、分页与压缩输入 | 记录请求大小分布，设置体积/处理预算，分页限制单次返回规模；分页还需考虑一致性。压缩输入需约束解压后大小与资源，不能只限制线上字节就防住膨胀；拒绝策略属于应用合同 |

第10.4节给出实际可追踪的HTTP/2帧级教学例；此表不声称已验证浏览器、gRPC、MQ、编码库或代理实现。

### 11.5 安全责任分层及运营问题

| 主题 | 用途及边界 |
| --- | --- |
| SYN flood与建连资源 | 未完成握手的状态可消耗资源，应问队列、限额与缓解机制所保护的对象；本文不制造攻击流量，也不把单次SYN失败归为攻击 |

| 管理端口与策略治理 | 管理面应限制暴露和访问，重要策略变更采用明确复核责任；双人复核用于降低误改风险。防火墙例外应有负责人、适用期/复核时间，失效安全组规则要清理，但删除前仍需确认依赖 |

### 11.6 优化前先固定比较口径
<!-- 原用途: 151-155 -->

连接预热可把建立连接的成本提前，但会占用资源，需确认之后能复用且未空闲过期。CDN把内容放近用户，边缘缓存减少源站请求；可缓存性、失效、地域和回源路径仍决定实际收益，不能把静态内容改善套到所有动态写入。

压缩以CPU和延迟换线上字节，批量以等待聚合和更大失败单位换协议开销。应固定内容、样本范围、首包/全量耗时和资源指标后比较；小体量低延迟请求可能因压缩或等批更慢。本轮无容量或性能实验，P7与E4只提供算术及口径训练。

## 12. 把整条链收回一笔订单（P1）

P0 的正向路径现在可逐步重放：t30 的缓存提供地址，路由选网关，ARP只解析下一跳；每跳更新链路头而保持题设最终IP；TCP握手建立后发送TLS记录编码，累计ACK只确认密文字节流。TLS独立完成身份/握手检查并认证解密，HTTP按头区与19字节body定界；服务按授权、规范化、唯一并发和原子事务合同提交订单与去重结果。客户端收到同请求完整201/o-42，才得到 **confirmed(o-42)**。

反向阅读也有明确停止点：无路由不推导已送达；TCP成功但名称错就停在TLS；记录不完整不宣布HTTP成功；完整202只到 **pending**；已发送但缺完整终态时保留 **unknown**，按受限合同恢复或停止自动动作。已经确认后再断连，订单仍已确认。网络知识的工程价值，是让每个“成功”都有准确对象，每个“未知”都有边界和下一份需要的证据。
