# 02-异常、类型系统与标准库实现

> 知识基线：C++20/23 语言规则；具体 ABI 与编译器行为以所列一手资料和工具链为界。
> 最后更新：2026-10-10（仅澄清 `noexcept` 违约与终止前栈展开规则；本次未运行程序，下文已有实验叙述及结果仍属 2026-10-04 历史验证）。
> 验证与基准：本轮 Test 覆盖见[基础合同实验](../../../evidence/cpp/foundation-contracts/README.md)，安全程序三种构建各45项；不将功能测试当性能基准或UE运行验收。

> 知识成熟度：L2。C++20 的 span、C++17 的 variant 与 C++23 的 expected 分别适用不同问题；本轮用 g++14/libstdc++14 验证新示例，未作UE或Windows异常ABI性能测量。

服务器收到一条非法指令时，调用者需要知道“不能处理的原因”；系统内存分配失败时，又可能需要沿调用栈释放已构造资源。把这两者都写成一个布尔返回值，或者都包装成 `throw`，都容易丢掉恢复策略。

先确定失败属于哪个边界，再选择表示方法：可预期的输入/业务拒绝用结构化错误值；异常是否允许传播由模块合同决定；程序不变量破坏要诊断，但不能把不可信输入当断言条件让服务器退出。

## 1. C++ 异常处理的底层微观机理

### 1.1 Itanium ABI 表驱动（Table-Driven）零开销机制

“Zero-cost exceptions”是常见实现策略的名称，不是“启用异常与禁用异常性能/指令/体积完全一样”的保证。表驱动实现把栈恢复与处理信息放到二进制元数据中，避免每个正常路径都做动态处理器注册；仍可能影响代码布局、优化自由度及体积。

GNU/LLVM体系常见 `.eh_frame` 和语言相关异常表；Windows x64有自己的unwind信息与运行时，不应称为同一种Itanium布局。[Itanium异常处理ABI](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)解释的是具体ABI，而非所有平台耗时基准。

### 1.2 抛出异常时的两阶段栈展开（Two-Phase Unwinding）

在该ABI模型下，可以用“先搜索合适处理器，再展开并执行清理”理解控制流。构造失败时，只清理已经构造完成的子对象；尚未完成构造的对象本体不会调用其析构函数。异常若试图逃出具有非抛出异常规格的函数（例如 `noexcept` 或 `noexcept(true)`），将调用 `std::terminate`，不会继续传播给调用方的 `catch`，也不会自动转换成错误码。函数内部抛出但在到达这个边界前已捕获，不属于此情况；`noexcept(false)` 是潜在抛出规格。终止前栈是否全部展开、部分展开或不展开由实现定义，不能据此保证 RAII 清理必定完成。依据：[C++23 草案 N4950（2023-05-10）§14.5 [except.spec]/5 与 §14.6.2 [except.terminate]/2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf#page=468)。

没有本机证据就不写单次2–50微秒、正常路径0ns或固定15–30%体积膨胀。异常通常在用户态运行时处理，不应把“必有内核信号交互”列为机制。本篇保留ABI解释，性能问题应以同工作量、同优化和真实错误频率另外测量。

## 2. 游戏模块如何选择异常与显式错误边界

这是一道工程选择题，不能推出“所有游戏都禁用”或“遇到一次throw就掉帧”。选择时检查：引擎/第三方模块编译选项、跨模块ABI、析构与异常安全能力、失败频率、尾延迟和诊断要求。

| 场景 | 可用建模 | 调用者责任 |
|---|---|---|
| 非法网络包、背包满、寻路失败 | expected/错误码 | 分支处理、限流或给出业务反馈 |
| 搜索结果缺省且无需失败原因 | optional | 明确无值含义，不能混成全部错误 |
| 模块允许的异常失败 | throw/RAII/catch边界 | 规定传播范围、资源清理和恢复策略 |
| 内部不变量被破坏 | 断言/故障报告 | 区分开发诊断与线上处置，不信任外部输入 |

禁用异常并不把可能抛出的库操作变成可恢复返回值。审查一个“无抛出”接口，必须看调用链、分配、T/E操作及标准库配置；写 `noexcept` 是异常不能逃出该边界的承诺；一旦异常试图逃出，将调用 `std::terminate`（见 §1.2），不是可由外层 `catch` 恢复的错误返回。

## 3. 现代 C++ 确定性错误处理：`std::expected`

expected 将“值或错误”写进类型；这里的“确定性”指调用者可以显式分支，不代表固定耗时、无分配或永不抛出。下节保留前一批已验证的存储与异常合同。

### 3.1 内嵌存储与错误路径的保证边界

当 `T` 非 `void` 时，可用带标签联合体（Tagged Union）理解 `std::expected<T, E>`；下列代码仅示意存储关系，省略构造、析构与状态切换，不规定实际布局：
```cpp
template <typename T, typename E>
class expected {
    union {
        T m_value; // 成功值
        E m_error; // 错误值
    };
    bool m_hasValue; // 判别标志位 (含对齐填充)
};
```
- **内嵌存储**：当前有效的 `T` 或 `E` 对象使用 `expected` 自身的存储，不能为这个对象另行动态分配存储；但包装对象本身可具有自动、静态、线程或动态存储期，并非必然“在栈上”。
- **大小与资源分配**：对象大小取决于类型、对齐和实现布局，没有统一的 `max(sizeof(T), sizeof(E)) + 8` 保证。`T` / `E` 自身仍可拥有动态资源，例如 `std::string` 的字符缓冲区或 `std::vector` 的元素存储；内嵌载荷对象不等于其全部资源也内嵌。
- **显式错误路径**：返回错误状态并用 `has_value()` / `operator bool` 检查，可避免用异常传递可预期的业务失败；但构造、复制或移动载荷仍可能抛出，`expected` 不会自动把这些异常转换为错误状态。满足类型要求的 `.value()` 在错误状态会进入抛出 `std::bad_expected_access<E>` 的路径，错误值的复制或移动也可能抛出，从而可能触发栈展开。需要无分配、无抛出路径时，必须同时约束所选类型与实际操作；不能仅凭返回类型推断传参 ABI、分支预测表现或固定延迟。

依据：[WG21 P0323R12（存储与设计理由）](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p0323r12.html)、[C++23 草案 N4950 §22.8.6（构造与观察器）](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf#page=749)、[类对象大小与填充规则](https://eel.is/c++draft/expr.sizeof#2)。

可执行验证：[std::expected 内嵌存储与异常边界实验](../../../evidence/cpp/expected-contract/README.md)（含复现命令、原始输出与验证边界）。

### 3.2 Monadic 操作链（链式调用）

`and_then`在成功时调用返回expected的下一阶段，`transform`只映射成功值；回调仍可能抛异常。不要把一条链当异常捕获器。C++23语言模式也不保证老标准库已经实现全部monadic API，应核对所用实现及特性宏。

第5节定义parse、Command和Delta，下面的函数与它们一起组成完整可编译实验。先把它读成直接分支：解析失败返回错误；成功则访问具体命令得到变化量；范围检查失败返回Range，成功再乘2。然后对应到transform和and_then：

~~~cpp
std::expected<int, ParseError> doubled_delta(std::span<const std::uint8_t> bytes) {
    return parse(bytes)
        .transform([](const Command& c) { return std::visit(Delta{}, c); })
        .and_then([](int delta) -> std::expected<int, ParseError> {
            if (delta < -500 || delta > 500) return std::unexpected(ParseError::Range);
            return delta * 2; // Bound checked before arithmetic.
        });
}
~~~

这里输入Heal(1000)能够通过字节解析，却被第二阶段范围策略拒绝；Damage(42)得到-84。未知tag不会调用transform回调，测试以独立called标志确认短路。三种情况已用实际g++14标准库编译运行；不是只展示未定义函数声明。

## 4. 现代类型系统核心组件：Variant 与 Span

### 4.1 `std::variant` 类型安全联合体与访客模式

先定义每个候选类型，再放进 `std::variant<A,B>`；不能在模板实参列表内直接定义 `struct A {...}`。variant维护当前活跃分支，visit要求访客覆盖所有候选，错误 `get<T>` 会有明确失败行为。

非平凡对象并非一律不能放C++ union；难点是活跃成员的构造/析构与特殊成员函数。variant替你管理许多状态转换，但包含string等载荷仍可能分配。某些抛出异常的类型转换可能产生 `valueless_by_exception`；不能宣称所有variant永远有值。

visit实现可用跳表或其他方式，也可能被优化；不承诺一定比虚函数快。封闭类型集合是它的建模优势。[标准variant条款](https://eel.is/c++draft/variant)

### 4.2 `std::span` 连续内存的无所有权视图

span借用连续区间，不延长底层对象生命周期。动态extent实现常见指针+长度，但标准不保证16字节，静态extent又可能有不同布局。C++20/23的operator[]不提供通用运行时越界异常保证，subspan的前提同样要由调用者满足。

函数若保存span，必须说明调用者何时能释放、重分配或修改原容器；一个正确长度也不能拯救悬空的data指针。本篇解析器只同步读取调用期间有效的字节，不保存视图。[span规范](https://eel.is/c++draft/views.span)

## 5. 可运行示例：固定字节协议与类型化错误

下面仅演示一个固定三字节命令的解码及错误表示，不含会话、鉴权、请求关联、限流或重试。把类型包装用对，是协议实现的起点，不是生产RPC框架验收。

先写协议，再写内存类型：第1字节为tag（1=Damage，2=Heal）；第2–3字节是大端unsigned16；amount限定1..1000；报文必须恰好3字节。错误优先级依次是长度、tag、数值。禁止把宿主struct直接memcpy当作跨平台协议：填充、端序和浮点表示都需要另行定义。

~~~cpp
struct Damage { std::uint16_t amount; };
struct Heal { std::uint16_t amount; };
using Command = std::variant<Damage, Heal>;
enum class ParseError { Length, Tag, Range };

// Teaching wire format: [tag:1][amount:2, big endian], exactly three bytes.
std::expected<Command, ParseError> parse(std::span<const std::uint8_t> bytes) {
    if (bytes.size() != 3) return std::unexpected(ParseError::Length);
    if (bytes[0] != 1 && bytes[0] != 2) return std::unexpected(ParseError::Tag);
    const auto amount = static_cast<std::uint16_t>(
        (static_cast<unsigned>(bytes[1]) << 8) | bytes[2]);
    if (amount == 0 || amount > 1000) return std::unexpected(ParseError::Range);
    if (bytes[0] == 1) return Command{Damage{amount}};
    return Command{Heal{amount}};
}
struct Delta {
    int operator()(const Damage& d) const { return -static_cast<int>(d.amount); }
    int operator()(const Heal& h) const { return static_cast<int>(h.amount); }
};
~~~

完整文件含 `<expected> <variant> <span> <cstdint>` 及测试main，见[foundation-contracts](../../../evidence/cpp/foundation-contracts/README.md)。类型定义在variant之前；用位移显式解码，span只在长度检查后索引，Error是小型枚举。访客Delta返回正负变化量，但真实游戏结算仍需鉴权、冷却、资源和状态校验，不能信任客户端amount就直接改生命值。

示例没有宣称全系统 noexcept，也不需捕获异常来处理非法报文。该closed variant的两个载荷都是整数，不会自行申请动态资源；如果日后加入string分支，重新分析该承诺。输入长度、tag、零值、1000/1001、大端解码、尾部冗余字节、两种visit分支都在测试中覆盖。它不覆盖通用浮点协议、NaN、分包粘包或吞吐容量。

### 5.1 练习：把错误类型变成调用方策略

1. 截断包与未知tag是否该触发同一个重试动作？解释重试能否改变确定性坏输入。
2. 如果amount允许0，应修改协议合同、解析器和边界测试，不应只删掉失败断言。
3. 加一种新命令，先看现有visit是否编译，再补对应业务验证，避免用万能兜底静默忽略。
4. 把返回类型改成optional会丢掉哪些错误信息？哪些业务真的只关心存在与否？

新组合实验在Linux g++14下按O0/O2/UBSan编译执行；故意非法的旧variant模板定义只作为编译失败反例隔离检查，不作为正常程序。PR17的[expected独立实验](../../../evidence/cpp/expected-contract/README.md)与原始结果保留。没有运行MSVC/UE、没有测试异常ABI耗时，也没有把结果类型的使用等同于安全网络协议。
