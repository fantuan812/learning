# 01-对象布局、虚函数与内存分配

> 知识基线：C++20/23 语言规则；具体 ABI 与编译器行为以所列一手资料和工具链为界。
> 最后更新：2026-10-04。
> 验证与基准：本轮 Test 覆盖见[基础合同实验](../../../evidence/cpp/foundation-contracts/README.md)，安全程序三种构建各45项；不将功能测试当性能基准或UE运行验收。

> 知识成熟度：L2。主体采用 C++20 的对象与存储模型；新增代码用 C++23 工具链验证。标准保证、ABI示意和本次运行结果分开。未实测 MSVC/UE 布局。

## 1. 核心模型：对象物理表示与生命周期

游戏对象池同时管理三件不同的事：一块足够大的存储、活在存储中的对象、谁可以访问或销毁它。只分配字节不能证明这三件事都正确。

例如每帧复用 Buff 槽位：上一 Buff 析构后，槽位可以还在；下一 Buff 的地址可以与上一对象相同。但旧句柄并不会因为地址相同就合法地指向新的逻辑 Buff。需要把存储、C++ 生命周期和业务代次分别建模。

- `sizeof(T)` 描述完整对象表示的大小，包含填充；不等于成员大小简单相加。
- 同一块存储可以在不同时间承载不同对象。空基类、`[[no_unique_address]]` 成员还可能与其他子对象共享地址，因此“不同对象永远地址不同”是错误概括。
- 一般对象生命周期要求适当存储及初始化完成；构造/析构期间另有专门规则，不能把“生命周期未开始”解释成构造函数不能访问任何成员。
- 自动存储期不等于语言强制放物理栈，动态存储期也不指定某种操作系统堆布局。[对象生命周期规则](https://eel.is/c++draft/basic.life)

本篇从一个实际出错的池实现走向可运行的小合同，并用布局工具区分可移植保证与实现观察。

## 2. 内存对齐（Alignment）与结构体填充（Padding）

### 2.1 对齐基本规则

对齐约束作用于对象地址，不是“所有标量对齐都等于大小”。例如 `struct Bytes { char data[100]; };` 可有100字节大小、1字节对齐。`alignas` 可以增强对齐，基类、虚继承与ABI布局也会影响整体结果；`max(成员对齐)`只是许多普通聚合的常见布局，不是所有类的计算公式。

类型化数组自动按正确元素步距排列；手写字节数组必须自己保证每一槽的起点对齐和足够容量。未对齐构造对象本身可违反 C++ 规则，不必等硬件真的抛异常才能判错。[标准对齐规则](https://eel.is/c++draft/basic.align)

### 2.2 结构体成员重排对比

~~~cpp
struct Original { char a; double b; char c; int d; };
struct Reordered { double b; int d; char a; char c; };
// 输出 sizeof / alignof，再结合目标ABI分析，不用固定数值static_assert冒充标准。
~~~

在常见8字节double对齐的64位实现中，可能得到24与16字节。这是该布局的例子，不是每台平台保证。成员重排也可能破坏二进制兼容、序列化布局或访问局部性；先确认结构没有持久格式契约，再分析填充。更小也不自动更快：热循环只读位置却跨越大量冷字段时，按访问模式拆分数据可能比单纯按大小排序更有用。

## 3. 虚函数表（vtable）与虚派发（Virtual Dispatch）机理

### 3.1 单继承下的物理内存布局

C++ 规定虚调用行为，不规定 vptr 在0偏移或指针固定8字节。Itanium C++ ABI 常用对象中的 vptr 指向虚表的 address point，其附近还可有 RTTI、offset-to-top 等信息；Windows/MSVC 使用自己的 ABI，不能把 Itanium 负索引布局与 Windows 的 `rcx` 传参拼成统一事实。[Itanium ABI](https://itanium-cxx-abi.github.io/cxx-abi/abi.html)

可用“取对象的派发信息→找到槽位→调用目标”理解尚未去虚化的调用，但实际编译器可能去虚化甚至内联。不要靠把对象强转成 `void***` 读取所谓通用虚表来实现可移植功能。

### 3.2 多重继承与 this 指针调整（Thunk）

~~~cpp
struct A { virtual int a() const = 0; virtual ~A() = default; };
struct B { virtual int b() const = 0; virtual ~B() = default; };
struct Both final : A, B {
    int a() const override { return 1; }
    int b() const override { return 2; }
};
~~~

`Both*` 转换到 `B*` 可能需要定位另一个基类子对象。ABI可用调整桩修正 `this`，语言层应使用正常转换；偏移不是通用16字节，调整也没有固定“微秒级”成本。通过基类删除时，需要正确的析构接口；本例两个基类都给出虚析构。

## 4. 虚调用的微架构性能代价剖析

虚派发可能带来间接访存、目标预测及内联机会损失，但并非“高性能游戏一律禁用虚函数”。类型分布稳定、代码与对象在缓存中时成本可能不同；随机对象指针访问也会让数据局部性成为更大问题。

比较前先保持算法与数据规模一致，再分别改变对象排列、派发形式、编译器LTO/去虚化条件。没有本机测量就不写15–20周期、固定体积比例或性能保证。批量同型数据处理可减少派发次数，但并不要求整个工程放弃面向对象。

## 5. 编译器查看对象布局实操

保存小型类定义并实际创建对象，使编译器实例化相应布局。记录工具链、目标ABI、编译参数和报告，不把示意输出当实测。

### 5.1 MSVC 编译器

`/d1reportSingleClassLayout类名` 是常用诊断选项，属于实现工具而非语言合同；本轮未运行。示例：`cl /c /d1reportSingleClassLayoutBoth layout.cpp`，以该版本是否支持为准。

### 5.2 Clang 编译器

~~~sh
clang++ -std=c++20 -Xclang -fdump-record-layouts -c layout.cpp
~~~

以下观察函数与前文相同的结构定义一起进入实际测试；完整测试文件提供 require 函数和头文件。无需读取虚表内部即可验证双基类接口的派发与完整对象转换：

~~~cpp
struct Original { char a; double b; char c; int d; };
struct Reordered { double b; int d; char a; char c; };
struct A { virtual int a() const = 0; virtual ~A() = default; };
struct B { virtual int b() const = 0; virtual ~B() = default; };
struct Both final : A, B {
    int a() const override { return 1; }
    int b() const override { return 2; }
};
void layout_observations() {
    std::cout << "OBS Original size/align/offsets=" << sizeof(Original) << '/'
              << alignof(Original) << '/' << offsetof(Original, a) << ','
              << offsetof(Original, b) << ',' << offsetof(Original, c) << ','
              << offsetof(Original, d) << '\n';
    std::cout << "OBS Reordered size/align=" << sizeof(Reordered) << '/'
              << alignof(Reordered) << '\n';
    Both object;
    A* a = &object; B* b = &object;
    std::cout << "OBS base address offsets A/B="
              << reinterpret_cast<std::uintptr_t>(a) - reinterpret_cast<std::uintptr_t>(&object)
              << '/' << reinterpret_cast<std::uintptr_t>(b) - reinterpret_cast<std::uintptr_t>(&object)
              << '\n';
    // Numeric address offsets are observations on this implementation, not ABI constants.
    require(a->a() == 1 && b->b() == 2, "virtual dispatch through both bases");
    require(dynamic_cast<Both*>(b) == &object, "base pointer resolves complete object");
    require(sizeof(Original) % alignof(Original) == 0, "array element size supports alignment");
}
~~~

本轮 g++14 x86_64 三种构建均观察到 Original 大小/对齐24/8，成员偏移0、8、16、20；Reordered为16/8。两个无数据多态基类在这个Both例中地址偏移为0与8，并非旧文硬写的16。Reordered最后仍有尾填充；B子对象偏移解释了为何沿B接口调用或向回转换必须尊重基类调整。运行输出是这份类型/ABI的证据，不是所有多继承类的模板。没有提交跨MSVC/Clang的完整布局对比结论。

## 6. 空基类优化（EBO）与 C++20 `[[no_unique_address]]`

### 6.1 传统空基类优化（EBCO）

独立完整空类对象必须有非零大小，但不是普适 `sizeof(Empty)==1` 断言。空基类优化能让某些子对象不增加大小；具体限制与布局类别有关。智能指针常利用这类技术，但不能从“无状态删除器”直接推断每种 `unique_ptr` 都等于一根指针。

### 6.2 C++20 `[[no_unique_address]]` 属性

该属性允许潜在重叠子对象，包含利用尾填充的情况；是否实际节省字节还要查询实现。保留它的意图：把空策略与对象组合而不过度支付布局成本；不要承诺任何类型都变成固定8字节。

## 7. 动态内存分配原语与 Placement New

### 7.1 分配操作符的本质分解

`new T(args...)` 将分配与初始化组合；过度对齐、类专属分配函数、构造失败后的释放都属于它的真实语义，不能机械替换成两行就声称完全等价。手工分配时必须把异常退出如何回收写出来。

### 7.2 原位构造（Placement New）与显式析构

~~~cpp
alignas(T) std::byte bytes[sizeof(T)];
T* p = ::new (static_cast<void*>(bytes)) T(args...);
// 使用 p，且保持 bytes 的存储期覆盖使用区间。
std::destroy_at(p); // 清理对象资源；不释放 bytes。
~~~

上面是模板语境示意，不是独立可编译程序。对于这样的栈内/池内存储，不能 `delete p`；对象销毁后，存储由其所有者管理。更一般的原则是构造/销毁及分配/释放必须匹配，而不是“凡是 placement new 都只能一种清理方式”。对象构造函数自身仍可能分配动态资源。

## 8. 游戏工程实践与避坑要点

### 8.1 严禁对含有虚函数的类执行 memcpy / memset

不要把字节复制当非平凡对象的复制构造或跨进程序列化。虚派发数据、指针、资源所有权都可能被破坏；即使没有虚函数，`std::string` 也不能这样复制。普通平凡可复制类型的对象表示复制另有标准保证，但也不意味着其内存布局是跨平台线协议。

### 8.2 数据驱动架构（DOD）与 Mass Entity

按热路径访问模式组织连续数据可提高局部性，是否 SoA、分块AoS或混合要由访问集合决定。ECS/Mass不是“100% L1预取”或“必然SIMD”的保证。这里的对象池解决固定容量与生命周期，和按数据布局批量遍历是两条不同优化轴。

### 8.3 虚继承与菱形继承的物理内存实现

虚继承可让最派生对象共享指定虚基类子对象，代价与布局由ABI决定。不同实现可能使用虚基偏移、表指针等；不应把“虚基类强制在最末尾”当标准。判断是否使用它，应先问需要表达什么共享基类语义，再实测布局与调用，而非只背固定字节图。

### 8.4 固定容量对象池：存储与生命周期合同

旧例在 `std::byte m_pool[sizeof(Node)*N]` 上使用 `&m_pool[index]` 取得槽位，实际步距是1字节，节点互相覆盖且可能未对齐。只补上乘号仍不解决构造抛异常、未归还对象析构及union活跃成员问题。

下面改用类型化 Slot 数组，每槽都有独立对齐存储和元数据。合同是固定容量、单线程、不可复制移动、构造/析构不重入池；create耗尽返回空，构造失败不消耗槽，池析构清理剩余对象。为保持教学简单，destroy用 O(N)扫描定位当前live指针，不冒称工业最优free-list实现。

~~~cpp
// Single-threaded; constructors/destructors must not re-enter this pool.
template<class T, std::size_t N>
class FixedPool {
    static_assert(N > 0);
    static_assert(std::is_nothrow_destructible_v<T>);
    struct Slot {
        alignas(T) std::byte bytes[sizeof(T)];
        T* live = nullptr;
        std::size_t next = N;
    };
    std::array<Slot, N> slots_{};
    std::size_t free_ = 0;
public:
    FixedPool() noexcept {
        for (std::size_t i = 0; i < N; ++i) slots_[i].next = i + 1;
    }
    FixedPool(const FixedPool&) = delete;
    FixedPool& operator=(const FixedPool&) = delete;
    FixedPool(FixedPool&&) = delete;
    FixedPool& operator=(FixedPool&&) = delete;
    ~FixedPool() {
        for (auto& slot : slots_) if (slot.live) std::destroy_at(slot.live);
    }
    template<class... Args>
    T* create(Args&&... args) {
        if (free_ == N) return nullptr;
        Slot& slot = slots_[free_];
        // Commit metadata only after successful construction.
        T* p = ::new (static_cast<void*>(slot.bytes)) T(std::forward<Args>(args)...);
        free_ = slot.next;
        slot.live = p;
        return p;
    }
    bool destroy(T* p) noexcept {
        if (!p) return false;
        for (std::size_t i = 0; i < N; ++i) {
            Slot& slot = slots_[i];
            if (slot.live == p) {
                std::destroy_at(p);
                slot.live = nullptr;
                slot.next = free_;
                free_ = i;
                return true;
            }
        }
        return false;
    }
};
~~~

完整头文件和运行用例见[组合实验](../../../evidence/cpp/foundation-contracts/README.md)。空间固定的是槽位，不是 `T` 拥有的全部资源；`T` 若含 vector 仍可能分配。N=0 编译期拒绝；T 必须无抛出析构。

**重要限制**：调用 destroy 后旧指针失效，调用者必须丢弃它。示例可以拒绝 null 和外来活指针，但不是世代句柄系统；槽位复用后旧地址可能与新对象相等，不能靠裸指针识别业务代次或承诺检测所有double-free。生产接口通常返回带generation的句柄、明确借用范围，再配合线程/回收协议。不要故意拿失效指针做“安全测试”。

测试覆盖3槽互不覆盖、64字节对齐、容量1/3耗尽、构造异常后复用、外来活指针拒绝、析构计数及池析构。UBSan通过只是这些执行路径的观测；线程安全、实时延迟、任意用户T和UE集成尚未验证。
