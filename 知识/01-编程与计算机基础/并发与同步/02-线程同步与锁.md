# 02-线程同步与锁
> 验证与基准：按文中命令执行最小实验，记录结果与边界。

> 知识成熟度：L2
> 知识基线：ISO C++20 内存模型、线程库与原子操作。
> 最后更新：2026-08-20。
> 来源：[cppreference thread support](https://en.cppreference.com/w/cpp/thread)、[C++ draft atomics](https://eel.is/c++draft/atomics)。
> 验证入口：`-fsanitize=thread`（Clang/GCC）与锁竞争基准。

## 1. 核心原则

数据竞争是未定义行为；同步既建立 happens-before，也保护不变量。先定义共享状态，再选择最小同步原语。

## 2. 互斥量

1. `mutex` 提供独占所有权。
2. `lock_guard` 适合单作用域持锁。
3. `unique_lock` 支持延迟、转移和条件变量。
4. `scoped_lock` 可一次锁定多个互斥量。
5. 多锁应使用统一顺序避免死锁。
6. `recursive_mutex` 通常掩盖设计问题。
7. `shared_mutex` 区分读锁和写锁。
8. 读多写少才适合共享锁。
9. 自旋锁只适合极短临界区。
10. 持锁期间避免阻塞 IO。
11. 不在未知回调中持锁。
12. 锁粒度需和不变量边界一致。
13. 锁对象不可复制。
14. 异常路径必须自动解锁。
15. 记录锁等待时间定位竞争。

## 3. 条件变量

1. `wait` 必须配合谓词循环。
2. 虚假唤醒是允许行为。
3. 修改谓词与通知需受同一互斥量保护。
4. `notify_one` 只唤醒一个等待者。
5. `notify_all` 可能造成惊群。
6. 退出标志应纳入等待谓词。
7. 生产者消费者队列需限制容量。
8. 超时等待应处理时钟跳变。
9. `condition_variable_any` 支持自定义锁但开销更高。
10. 关闭队列时唤醒全部消费者。

## 4. 原子与无锁

1. 原子读写不会产生数据竞争。
2. relaxed 只保证原子性和修改顺序。
3. acquire 读取同步发布方 release。
4. release 不保证后续读取可见。
5. seq_cst 提供全局单一顺序但成本可能更高。
6. compare_exchange 失败时更新 expected。
7. ABA 问题需版本标记或安全回收。
8. lock-free 不等于 wait-free。
9. `atomic_wait` 可减少忙等。
10. 无锁结构必须证明内存回收安全。
11. false sharing 会放大缓存一致性流量。
12. 使用 `hardware_destructive_interference_size` 隔离热点。
13. 原子复合不变量仍需锁或事务算法。
14. 原子指针不自动延长对象生命周期。
15. 统计计数器可使用 relaxed。

## 5. 线程生命周期

1. `jthread` 在析构时请求停止并 join。
2. `stop_token` 是协作取消，不会强杀线程。
3. detach 后必须确保共享状态仍存活。
4. 线程函数异常必须在线程内处理。
5. 线程池应限制工作线程数量。
6. 任务队列关闭需要明确拒绝新任务语义。
7. future 等待可能造成线程池自死锁。
8. 优先级继承依赖平台实现。
9. 线程命名便于诊断。
10. 栈大小和 guard page 需按平台验证。

## 6. 死锁与活锁

1. 死锁必要条件包括互斥、占有等待、不可剥夺、环路等待。
2. 全局锁序可破坏环路等待。
3. try_lock 回退可能形成活锁。
4. 随机退避可降低碰撞。
5. 锁超时用于诊断而非掩盖问题。
6. 资源分层减少嵌套锁。
7. 事务式复制修改可缩短持锁时间。
8. RCU 适合读多写少且可延迟回收。
9. hazard pointer 保护正在读取节点。
10. epoch reclamation 需管理线程退出。

## 7. 验证清单

1. ThreadSanitizer 检查数据竞争。
2. 压测覆盖高竞争和低竞争。
3. 注入随机线程暂停。
4. 检查异常和取消路径。
5. 记录锁等待、持有、队列长度。
6. 用 litmus test 验证内存序。
7. 固定 CPU 亲和性比较基准。
8. 测试 shutdown 时所有线程可退出。
9. 验证无悬空引用和 double join。
10. 保存编译器、OS、硬件信息。

## 8. 示例

```cpp
std::mutex m; std::condition_variable cv; std::queue<int> q; bool stop=false;
void worker(){ for(;;){ std::unique_lock lk(m); cv.wait(lk,[&]{return stop||!q.empty();}); if(stop&&q.empty()) return; int x=q.front(); q.pop(); lk.unlock(); consume(x); }}
```

## 9. 结论

同步设计应围绕不变量、生命周期和取消协议展开；锁、原子和无锁算法都必须以可复现测试证明正确性与性能。

## 10. 案例：有界队列

生产者消费者队列由环形缓冲区、互斥锁和两个条件变量组成。

`not_empty` 表示至少有一个元素，`not_full` 表示仍有空槽。

等待条件必须使用 `while`，不能使用 `if`，因为存在虚假唤醒。

生产者在锁内写入元素并更新尾指针。

解锁后再通知消费者，可减少被唤醒线程立即阻塞的概率。

消费者取走元素后通知 `not_full`。

关闭队列时设置 `closed` 标志，并同时唤醒所有等待者。

等待者醒来后检查 `closed && empty`，据此结束消费循环。

## 11. 实验：锁粒度

实现全局 mutex、分片 mutex 和读写锁三个版本。

固定任务数量，改变线程数 1、2、4、8、16、32。

分别测量临界区占比 10%、50% 和 90%。

记录吞吐、平均等待时间和 P99 等待时间。

全局锁在高竞争下通常出现明显长尾。

分片锁减少冲突，但需要处理跨分片操作。

读写锁在读多写少时有优势，写入频繁时可能不如 mutex。

使用 perf lock 或 ETW 等待事件验证瓶颈。

## 12. 案例：线程池

线程池由任务队列、工作线程、停止标志和 join 逻辑组成。

提交任务返回 future，异常通过 future 传播给调用方。

工作线程使用条件变量睡眠，避免空转消耗 CPU。

停止流程分为 drain（执行完队列）和 cancel（放弃未执行任务）。

析构函数必须先设置停止标志，再通知所有工作线程，最后 join。

任务不得持有外部锁等待 future，否则容易形成锁顺序反转。

递归提交任务时应限制队列深度，避免无限膨胀。

## 13. 实验：任务调度策略

比较 FIFO、优先级队列和 work-stealing 三种调度方式。

生成短任务与长任务混合的负载，记录平均完成时间和尾延迟。

FIFO 实现简单，但长任务可能阻塞后续短任务。

优先级队列改善关键任务延迟，却可能造成低优先级饥饿。

work-stealing 降低中心队列竞争，适合大量细粒度任务。

测量任务窃取次数和队列迁移成本，避免只看吞吐。

## 14. 协程调度注意事项

协程不是线程，挂起点不会自动提供并行性。

事件循环负责恢复协程，线程池负责真正的 CPU 并行。

不得在持锁状态跨越可能挂起的 `co_await`。

取消需要传播停止令牌，并确保资源在取消路径释放。

## 15. 进程间通信案例

匿名管道适合父子进程单向传输，读写具有字节流语义。

Unix domain socket 支持双向通信和文件描述符传递。

共享内存吞吐高，但必须额外设计跨进程同步协议。

信号量可表示资源计数，eventfd 适合 Linux 事件通知。

跨进程协议必须定义版本、长度、端序和崩溃恢复行为。

## 16. 死锁排查清单

记录每把锁的全局序号，要求线程按序获取。

使用 `std::scoped_lock` 同时获取多把 mutex，避免手写顺序错误。

检测线程是否在持锁时调用未知回调。

检查析构、日志和内存分配是否隐式获取其他锁。

采集阻塞栈，确认循环等待关系而非误判 CPU 饥饿。

## 17. Benchmark 规范

预热线程池和内存分配器，排除首次初始化成本。

固定 CPU 亲和性，记录 NUMA 节点和系统负载。

分别测量无竞争、低竞争和高竞争场景。

报告吞吐、锁等待、上下文切换和 P99 延迟。

使用 TSAN 验证正确性，再进行 release 优化基准。

优化后必须重复基准，确认收益不是随机噪声。

## 18. 验收题

能解释 mutex、spinlock、semaphore 和 condition_variable 的适用边界。

能实现支持关闭和超时的有界队列。

能定位一次 ABBA 死锁并给出锁序修复。

能设计线程池停止、取消和异常传播语义。

能用 TSAN 复现数据竞争并解释报告中的 happens-before。

## 19. 原子与锁的选择

单个计数器可使用 `fetch_add`，但复合不变量通常需要 mutex。

原子操作不能自动保护关联的多个字段。

release/acquire 适合发布已经初始化的对象。

relaxed 只保证原子性，不提供跨变量顺序。

seq_cst 易于推理，但可能增加栅栏和缓存一致性成本。

## 20. 条件变量超时

`wait_for` 返回后必须重新检查谓词。

超时不代表任务不存在，可能只是竞争导致未及时获取锁。

系统时钟跳变时，定时任务应优先使用 steady_clock。

超时路径应记录原因、剩余队列和线程状态。

## 21. 负载测试矩阵

线程数：1、2、4、8、16、32。

任务大小：空任务、1 微秒、100 微秒、10 毫秒。

队列容量：1、64、1024、65536。

生产消费比：1:1、2:1、1:2。

每个组合至少运行 30 秒并重复五次。

剔除系统抖动后报告中位数和置信区间。

## 22. 工程检查

线程入口必须捕获异常，不能让异常穿过 pthread 边界。

所有 joinable 线程在拥有者析构前完成 join 或 detach 决策。

锁对象不可复制，封装 API 应明确锁的所有权。

日志代码避免在持锁状态执行慢速 IO。

生产环境开启死锁检测或周期性线程栈采样。

## 23. 代码审查问题

是否明确每个共享变量的保护锁？

是否存在锁外读取导致竞态？

是否所有等待都有超时或取消路径？

是否在异常、提前返回和析构路径释放锁？

是否记录线程池队列上限和拒绝策略？

是否用压力测试覆盖线程创建失败？

是否保留可复现的调度随机种子？

是否检查优先级反转和 CPU 饥饿？
