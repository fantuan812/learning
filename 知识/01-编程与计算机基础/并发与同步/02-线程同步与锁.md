## 1. 先定义保护域，再谈“加锁”

两个线程交接整数记录：生产者写入，消费者取走后计算。容量固定为2，满时生产者应等空间，空时消费者应等数据，关闭后不能再接纳新值，但已经接纳的值仍应被取走。需要一起维护的状态是 `slots[2]、head、tail、count、closed`：

- `0 <= count <= 2`，`head` 和 `tail` 始终为0或1；有效记录从 `head` 起按环形顺序排列
- 入队必须把“检查准入、写槽、移动尾指针、增加count”作为一个状态转换；出队同理
- `closed` 只能由false变true；关闭与入队的先后顺序必须明确

本例让一个 `std::mutex m` 保护整个状态组，包括谓词的每次读取。若只把 `count` 改成原子，两个生产者仍可能都判断有空间，再覆盖同一槽；各字段单独没有数据竞争，不等于复合操作正确。锁的粒度应覆盖不变量，不能为了缩短临界区拆散“检查后使用”。

对同一mutex，释放与随后成功获取建立同步；写槽、解锁、另一个线程加锁、读槽因此形成可见性的因果链。潜在并发的冲突访问中，至少一个非原子且缺少所需的 happens-before，才构成这里讨论的数据竞争，其行为未定义。锁外调试打印共享 `count` 也不能免除同步要求。[N4861 intro.races](https://timsong-cpp.github.io/cppwp/n4861/intro.races)、[mutex requirements /5–26](https://timsong-cpp.github.io/cppwp/n4861/thread.mutex.requirements.mutex)

## 2. 线程拥有锁，RAII管理解锁责任

`std::mutex` 提供非递归的独占所有权，自身不可复制或移动。`lock_guard` 适合一次作用域持锁；`unique_lock` 另外记录“关联哪个mutex、现在是否拥有锁”，适合CV需要临时解锁的场景。管理器并不拥有mutex的寿命，mutex必须活得足够久。[lock_guard](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.guard)、[unique_lock](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.unique)

同一个线程内可以这样追踪管理责任：以 `defer_lock` 构造A时尚未加锁，调用 `A.lock()` 后A负责解锁，再把A移动构造为B，A不再负责、B负责；最后B析构解锁。`adopt_lock` 则是假定调用线程已经拥有这把锁，不能拿它补做一次加锁。把B交给另一个线程并不会授权那个线程解锁原线程持有的 `std::mutex`。[unique_lock构造、移动、析构](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.unique.cons)

错误也要按具体类型区分：原始 `std::mutex::unlock()` 要求调用线程拥有mutex，无所有权调用违反前提，属于未定义行为，不能依赖它抛异常；`std::unique_lock::unlock()` 在管理器的 `owns_lock()` 为false时规定 `operation_not_permitted` 的 `system_error`。后者不是所有非法unlock的通用救生网。[mutex要求](https://timsong-cpp.github.io/cppwp/n4861/thread.mutex.requirements.mutex)、[unique_lock locking /23–26](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.unique.locking)

RAII在栈展开时释放所管理的锁，却不会自动撤销已经写坏的业务状态。若“count先加一、随后用户构造抛错”，守卫解锁后别人看到的仍可能是假记录。本例只在锁内复制 `int` 和更新有界下标，业务计算移到锁外；改为任意类型、分配器或回调时，须重新证明异常保证。

## 3. 等的是状态，通知只是让线程重新检查

`std::condition_variable::wait` 的关键阶段是：原子地释放传入锁并进入等待；被通知或虚假唤醒而解除等待；重新取得锁后返回。通知不把mutex直接交给等待者，也不储存“未来可消费的一项”。带谓词的 `wait(lock, pred)` 自己循环检查；用它时不必再在外面机械套一层while。裸 `wait(lock)` 才需要调用者显式循环判断。[condition_variable /7–16](https://timsong-cpp.github.io/cppwp/n4861/thread.condition.condvar)

两个消费者的纸面轨迹能说明重查不只为了虚假唤醒：C1得到通知但尚未重取m，C2先取得m并取走唯一记录，C1随后看到空队列，应继续等待。`notify_one` 有等待者时解除一个等待；没有等待者时不会积攒许可，也不保证FIFO、公平性或立即运行。`notify_all` 解除当前所有等待，可能增加竞争，但关闭时两种等待者都必须得到退出机会。[CV通知与等待阶段总序](https://timsong-cpp.github.io/cppwp/n4861/thread.condition)

**丢通知的纸面反例**：消费者检查“空”后手工解锁，尚未调用裸wait；生产者在这个间隙入队并notify；消费者随后才进入等待。通知已经过去，消费者可能一直等下去。正确协议是在同一锁下检查谓词，再让wait原子地完成“解锁并进入等待”，生产者也在这把锁下改变谓词状态。这里没有“检查空”和“注册等待”之间供生产者插入的漏洞。

本例的状态读写必须持m；notify既可在持锁时调用，也可在解锁之后调用。本例选择先提交状态、解锁、再通知，避免把锁内业务无谓延长；这不是跨平台性能胜出的证明。解锁之后还要访问CV，owner就必须保证最后一次notify结束前对象仍活着。将 `closed` 随手换成锁外atomic也不是同一协议的等价简化。

具体等待前提不能混用：

- `std::condition_variable` 接收 `std::unique_lock<std::mutex>&`，调用线程须拥有对应mutex；同一CV的并发等待调用须使用同一mutex对象。本例的两个CV都使用m
- `std::condition_variable_any` 的Lock类型满足BasicLockable要求；非标准锁还需实际建立与谓词有关的同步。不能把前一类型的具体mutex同一性句子机械套给所有Lock，也不能只因名字有any便认为任意锁都正确。其成本取决于实现和使用方式

依据：[CV前提](https://timsong-cpp.github.io/cppwp/n4861/thread.condition.condvar)、[CV_any /1](https://timsong-cpp.github.io/cppwp/n4861/thread.condition.condvarany)。mutex解决独占保护；自旋是等待实现策略；[counting_semaphore](https://timsong-cpp.github.io/cppwp/n4861/thread.sema.cnt)保存计数许可，acquire消耗许可；CV本身不保存队列状态或许可。不能把信号量直接当作带线程所有权的mutex。

## 4. 关闭、drain与截止时间是一套队列合同

两个CV服务不同谓词：生产者等 `closed || count < 2`，消费者等 `closed || count > 0`。成功入队/出队的锁内状态转换是本例判定先后的依据；这是一种应用协议，并非标准库自带的Close API。

| 最终持锁状态 | Push / PushUntil | Pop / PopUntil |
| --- | --- | --- |
| closed且有存量 | Closed，拒绝新值 | Item，先取存量 |
| closed且为空 | Closed | Closed |
| open且有对应资源 | Accepted | Item |
| open且没有对应资源 | Push继续等；Until最终谓词false才Timeout | Pop继续等；Until最终谓词false才Timeout |

生产者醒来先检查closed，即使此时有空位也拒绝；消费者醒来先检查count，直到存量耗尽才Closed。满是本例的等待状态，并没有一个立即返回的Full结果；它与线程池篇的非阻塞准入API不同。`Accepted` 只说明进入队列，`Item` 只说明被领取，都不等于业务处理成功。

`Close()` 在m下置closed，解锁后对 `not_empty` 和 `not_full` 都notify_all。只通知消费者会漏掉正在满队列上等待的生产者；只notify却不改closed，等待者重查后仍可能等下去。重复Close不抹掉存量，也不会重新开放准入。入队和Close争m时只有两种合法归属：先接纳后drain，或先关闭后拒绝。

Until接受一个 `steady_clock::time_point`，每次等待重用同一个deadline。带谓词的 `wait_until` 返回bool已经包含最终的锁内谓词求值；返回false才Timeout。若deadline已过而谓词为真，仍按表返回Accepted、Item或Closed。无谓词版本返回的 `cv_status` 并不替调用者检查业务条件；不要混用这两种结果。[timed wait /29–41](https://timsong-cpp.github.io/cppwp/n4861/thread.condition.condvar)

该deadline限制等待预算，不是端到端硬时限：初次获取m、唤醒后的调度与重取m都可能延后；锁外计算也不在其内。反复从“现在”重新加完整 `wait_for` 时长会重启预算，达不到一个总deadline的意图。Timeout仅指本次最终检查没有相应资源，既不取消其它工作，也不保证下一瞬间还是空/满。使用steady_clock避免墙钟调整影响预算，仍不能消除OS延迟。[timing specifications](https://timsong-cpp.github.io/cppwp/n4861/thread.req.timing)

## 5. 完整C++20有限程序

队列不拥有线程，唯一外部owner拥有两个线程槽。结果数组只有consumer写，接纳计数只有producer写，owner在成功join后读取。每轮仅尝试1/2/3，最多领取3项；`Process(2)` 抛出指定业务异常，1和3分别得到10和30。计算前检查输入域，所以不会以任意int的乘法溢出充当演示。

程序自身检查正常传递、两个安全的owner异常点及单线程deadline分支。它没有观察CV内部阻塞的测试钩子；“线程已启动”与“真的阻塞在CV上”始终分开。`AfterConsumer` 是启动第二线程前的普通owner异常，不伪称真实的线程资源耗尽。

```cpp
#include <array>
#include <chrono>
#include <condition_variable>
#include <cstddef>
#include <exception>
#include <initializer_list>
#include <iostream>
#include <mutex>
#include <stdexcept>
#include <thread>

class BoundedQueue {
public:
    using Clock = std::chrono::steady_clock;
    enum class PushResult { Accepted, Closed, Timeout };
    enum class PopKind { Item, Closed, Timeout };
    struct PopResult { PopKind kind; int value; }; // value只在Item时有效

    BoundedQueue() = default;
    BoundedQueue(const BoundedQueue&) = delete;
    BoundedQueue& operator=(const BoundedQueue&) = delete;
    BoundedQueue(BoundedQueue&&) = delete;
    BoundedQueue& operator=(BoundedQueue&&) = delete;

    // 本例政策：同步操作不可恢复失败即terminate，不冒充安全返回。
    PushResult Push(int value) noexcept {
        std::unique_lock lock(m_);
        not_full_.wait(lock, [&] { return closed_ || count_ < slots_.size(); });
        return PutLocked(value, lock);
    }
    PushResult PushUntil(int value, Clock::time_point deadline) noexcept {
        std::unique_lock lock(m_);
        if (!not_full_.wait_until(lock, deadline, [&] {
                return closed_ || count_ < slots_.size();
            })) return PushResult::Timeout;
        return PutLocked(value, lock);
    }
    PopResult Pop() noexcept {
        std::unique_lock lock(m_);
        not_empty_.wait(lock, [&] { return closed_ || count_ > 0; });
        return TakeLocked(lock);
    }
    PopResult PopUntil(Clock::time_point deadline) noexcept {
        std::unique_lock lock(m_);
        if (!not_empty_.wait_until(lock, deadline, [&] {
                return closed_ || count_ > 0;
            })) return {PopKind::Timeout, 0};
        return TakeLocked(lock);
    }
    void Close() noexcept {
        {
            std::lock_guard lock(m_);
            closed_ = true;
        }
        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    // 仅由上述成员在持有m_且等待谓词为真时调用。
    PushResult PutLocked(int value, std::unique_lock<std::mutex>& lock) noexcept {
        if (closed_) return PushResult::Closed;
        slots_[tail_] = value;
        tail_ = (tail_ + 1) % slots_.size();
        ++count_;
        lock.unlock();
        not_empty_.notify_one();
        return PushResult::Accepted;
    }
    PopResult TakeLocked(std::unique_lock<std::mutex>& lock) noexcept {
        if (count_ == 0) return {PopKind::Closed, 0};
        const int value = slots_[head_];
        head_ = (head_ + 1) % slots_.size();
        --count_;
        lock.unlock();
        not_full_.notify_one();
        return {PopKind::Item, value};
    }
    std::mutex m_;
    std::condition_variable not_empty_, not_full_;
    std::array<int, 2> slots_{};
    std::size_t head_ = 0, tail_ = 0, count_ = 0;
    bool closed_ = false;
};

class ThreadOwner {
public:
    ThreadOwner(BoundedQueue& queue, std::thread& producer,
                std::thread& consumer) noexcept
        : queue_(queue), producer_(producer), consumer_(consumer) {}
    ThreadOwner(const ThreadOwner&) = delete;
    ThreadOwner& operator=(const ThreadOwner&) = delete;
    ~ThreadOwner() noexcept { CloseAndJoin(); }

    void FinishNormally() noexcept {
        // producer正常末尾先Close。这里不持queue的mutex。
        Join(producer_);
        CloseAndJoin();
    }
private:
    static void Join(std::thread& thread) noexcept {
        try {
            if (thread.joinable()) thread.join();
        } catch (...) {
            std::terminate(); // 无法确认Joined，不能继续销毁共享数据
        }
    }
    void CloseAndJoin() noexcept {
        queue_.Close();
        Join(producer_);
        Join(consumer_);
    }
    BoundedQueue& queue_;
    std::thread& producer_;
    std::thread& consumer_;
};

struct BusinessError {};
struct OwnerError {};
struct Row { int input = 0; bool succeeded = false; int output = 0; };
struct Results {
    std::array<Row, 3> rows{};
    std::size_t used = 0;
    bool closed = false;
};
enum class Mode { Normal, AfterConsumer, AfterBoth };

int Process(int value) {
    if (value < 1 || value > 3) throw std::logic_error("outside demo input domain");
    if (value == 2) throw BusinessError{};
    return value * 10; // 限定1..3后，int计算有界
}
void Check(bool condition, const char* message) {
    if (!condition) throw std::runtime_error(message);
}

void RunFinite(Mode mode, const char* name) {
    BoundedQueue queue;
    Results results;
    std::size_t accepted = 0;
    bool owner_exception = false;
    std::thread consumer; // 默认非joinable；共享数据在线程槽之前构造
    std::thread producer;
    try {
        ThreadOwner cleanup(queue, producer, consumer); // 最先析构
        consumer = std::thread([&]() noexcept {
            try {
                for (;;) {
                    const auto item = queue.Pop();
                    if (item.kind == BoundedQueue::PopKind::Closed) {
                        results.closed = true;
                        return;
                    }
                    if (item.kind != BoundedQueue::PopKind::Item ||
                        results.used == results.rows.size()) std::terminate();
                    Row row{item.value, false, 0};
                    try {
                        row.output = Process(item.value); // Pop已解锁
                        row.succeeded = true;
                    } catch (const BusinessError&) {
                        // 这一项失败由consumer记录，不重入队，继续drain。
                    }
                    results.rows[results.used++] = row;
                }
            } catch (...) {
                std::terminate(); // 未约定的失败不是可恢复业务错误
            }
        });
        if (mode == Mode::AfterConsumer) throw OwnerError{};
        producer = std::thread([&]() noexcept {
            for (int value : {1, 2, 3}) {
                if (queue.Push(value) == BoundedQueue::PushResult::Closed) break;
                ++accepted;
            }
            queue.Close();
        });
        if (mode == Mode::AfterBoth) throw OwnerError{};
        cleanup.FinishNormally();
    } catch (const OwnerError&) {
        // cleanup已先Close并join；到这里才可以读共享结果。
        owner_exception = true;
    }
    // thread构造若真失败：同一guard清理后继续向main传播，不报此轮PASS。
    Check(!consumer.joinable() && !producer.joinable(), "thread still joinable");
    Check(results.closed && results.used == accepted && accepted <= 3, "drain mismatch");
    Check(owner_exception == (mode != Mode::Normal), "owner exception mismatch");
    if (mode == Mode::Normal) Check(accepted == 3, "normal admission mismatch");
    if (mode == Mode::AfterConsumer) Check(accepted == 0, "unexpected admission");
    for (std::size_t i = 0; i < results.used; ++i) {
        const Row& row = results.rows[i];
        const int expected = static_cast<int>(i) + 1;
        Check(row.input == expected, "FIFO mismatch");
        Check(row.succeeded == (expected != 2), "business status mismatch");
        Check(row.output == (expected == 2 ? 0 : expected * 10), "business value mismatch");
    }
    std::cout << name << " accepted=" << accepted << " consumed=" << results.used
              << " closed=" << results.closed << " owner_exception=" << owner_exception << '\n';
    for (std::size_t i = 0; i < results.used; ++i) {
        const Row& row = results.rows[i];
        std::cout << "item=" << row.input << " success=" << row.succeeded
                  << " output=" << row.output << '\n';
    }
}

void CheckDeadlines() {
    using Q = BoundedQueue;
    Q queue; // 此组检查没有其它线程，不靠sleep制造交错
    const auto past = Q::Clock::now() - std::chrono::seconds(1);
    Check(queue.PopUntil(past).kind == Q::PopKind::Timeout, "empty timeout");
    Check(queue.PushUntil(1, past) == Q::PushResult::Accepted, "past ready push1");
    Check(queue.PushUntil(2, past) == Q::PushResult::Accepted, "past ready push2");
    Check(queue.PushUntil(3, past) == Q::PushResult::Timeout, "full timeout");
    queue.Close();
    queue.Close();
    Check(queue.PushUntil(3, past) == Q::PushResult::Closed, "closed beats timeout");
    Check(queue.Push(3) == Q::PushResult::Closed, "closed push");
    for (int expected : {1, 2}) {
        const auto item = queue.PopUntil(past);
        Check(item.kind == Q::PopKind::Item && item.value == expected, "closed drain");
    }
    Check(queue.PopUntil(past).kind == Q::PopKind::Closed, "empty closed until");
    Check(queue.Pop().kind == Q::PopKind::Closed, "empty closed pop");
    std::cout << "deadline_priority_and_repeated_close=PASS\n";
}

int main() {
    try {
        RunFinite(Mode::Normal, "normal");
        RunFinite(Mode::AfterConsumer, "owner_after_consumer");
        RunFinite(Mode::AfterBoth, "owner_after_both");
        CheckDeadlines();
        std::cout << "finite_checks=PASS\n";
    } catch (const std::exception& error) {
        // 例如启动失败已由guard清理；检查失败也必须返回非零。
        std::cerr << "FAIL: " << error.what() << '\n';
        return 1;
    }
}
```

### 为什么这段状态转换成立

初态count为0、head/tail为0。Put只在open且有空位时写一个int并递增；Take只在有存量时读取并递减。下标取模保持范围，槽位与计数在同一临界区提交，因此成功入队次序决定出队次序。关闭分支不改槽或计数，Timeout也没有这类副作用；通知发生在提交以后。这个推导依赖所有访问都走这些入口，不能从“某个计数恰好等于3”倒推出任意改版也正确。

存量被取走后就从队列所有权移交consumer；这时释放m，生产者可以补槽，consumer独占自己的局部Row并执行Process。2失败后仍追加一条失败记录再下一次Pop，因而该项只领取一次、失败一次；不是事务回滚、自动重试或future异常传播。

### 唯一owner如何覆盖所有出口

| 路线 | 清理因果与结果归属 | 证据边界 |
| --- | --- | --- |
| 正常 | producer逐项Push后Close；owner join producer，再Close并join consumer；最后读取结果 | 程序正常轮检查3次接纳与3次领取 |
| 单项业务异常 | consumer在锁外捕获BusinessError，记录2失败，继续领取3与最终Closed | 程序正常轮检查1/3成功、2失败 |
| 第二个线程尚未启动，owner抛错 | guard Close并通知两端，join已经启动的consumer；默认producer槽跳过 | AfterConsumer安全异常点，观察最终退出，不证明consumer曾阻塞 |
| 两线程启动后owner抛错 | guard Close，producer后续Push拒绝，consumer把已经接纳的前缀drain；join两线程后才读 | AfterBoth轮允许接纳0到3项；不强求某个调度 |
| 任一个thread构造真失败 | guard同样先Close再join已成功启动者，然后原异常传到main，返回失败 | 静态路线；未制造资源耗尽或注入标准库创建失败 |
| mutex/CV/重取锁/join等不可恢复失败 | 队列操作的noexcept和Join的catch明确采用terminate，无法证明Joined时不继续安全析构的叙述 | fatal政策，未注入；不是保证从所有系统故障恢复 |

先创建consumer再创建producer，使得第二线程启动失败时没有“已接纳任务却根本没有消费者”的窗口。guard比线程槽晚构造、比它们和结果/queue早析构，所有join都在不持m的外部owner线程进行；已经join的槽通过 `joinable()` 跳过。thread对象自身的join操作不供多个owner并发调用。成功join把线程的完成同步到owner，才允许无额外锁读取结果。[thread构造](https://timsong-cpp.github.io/cppwp/n4861/thread.thread.constr)、[thread members](https://timsong-cpp.github.io/cppwp/n4861/thread.thread.member)

Close只关闭准入并唤醒，**Close返回不等于drain完成，queue空不等于锁外Process完成**。本例等所有调用和最后notify结束、join全部线程后才销毁queue。CV标准析构前提允许已经解除阻塞的线程随后还在重取mutex，不代表整个含谓词状态的queue可以提前销毁；join后整体销毁是本例选择的更强owner策略，不是所有CV都必须用thread join。[CV析构 /4](https://timsong-cpp.github.io/cppwp/n4861/thread.condition.condvar)

进展还依赖线程最终获调度、Process有限返回、没有外部等待环；标准不保证公平性或最大排队时间。增加外部producer时，owner必须额外阻止未来调用并收束在途调用；closed位不会让已销毁对象的地址继续可用。detach也不能解除这个寿命责任。

## 7. 多把锁、锁类型与等待环

ABBA纸面轨迹：线程A持L1等L2，线程B持L2等L1，双方所需释放都依赖对方推进。固定全局锁序可以打破该环；多参 `std::scoped_lock` 通过 `std::lock` 获取它负责的那组锁，其算法避免这组获取操作自身死锁。不要重复传同一非递归mutex，也不能据此忽略已经持有的外部锁、回调和join/future形成的环。[scoped_lock](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.scoped)、[lock algorithms](https://timsong-cpp.github.io/cppwp/n4861/thread.lock.algorithm)

**持锁join的纸面反例**：owner持m并等待consumer结束；consumer退出前必须重取m检查closed；owner等待consumer、consumer等待owner持有的m，构成环。修复是锁内设置closed后释放m、通知，再join。本例不开放m给外部，也不在队列临界区调用未知回调、慢IO、日志或分配器，减少引入隐式锁的机会。没有执行故意死锁程序。

`std::mutex::try_lock()` 允许虚假失败，false不能证明别人持有锁，失败也没有成功获取时的同步边。两线程对称地“失败、退让、同时重试”可能活锁；随机退避是可测的缓解策略，不能推出公平性或终止证明。超时用于暴露等待问题，不能把不断重试当作修好等待环。[mutex try_lock /14–20](https://timsong-cpp.github.io/cppwp/n4861/thread.mutex.requirements.mutex)

选择锁类型时，先写成立条件：

- `recursive_mutex` 支持同线程递归拥有，却不使半完成的不变量适合重入；若递归来自层次混乱，应先拆分持锁/未持锁职责
- `shared_mutex` 区分共享读和独占写；读比例、持锁长度、调度与写入等待共同决定收益，“读多”不是充分证据
- 自旋占用CPU等待，持锁者被抢占、过量线程或长临界区会浪费运行机会；短临界区只是考虑它的线索，不是通用优胜条件
- 分片锁减少冲突的可能性取决于访问分布；跨分片操作须重新定义不变量与锁序。复制后锁外计算再提交可以缩短持锁段，但必须验证版本并处理冲突，不能覆盖期间的新修改

排查时先收集阻塞栈并画出“谁等谁”，区分等待环、CPU饥饿和优先级反转。线程命名、栈大小、guard page、优先级继承和周期栈采样都依赖平台及部署能力，本轮没有启用或测量。RAII解决退锁责任，不保证业务进展。

## 8. 旁支如何接回本篇的责任边界

### 原子、无锁与缓存

独立统计计数可考虑 `fetch_add` 和relaxed；它只给该原子对象的原子性与修改顺序，不给关联普通字段建立发布关系。acquire必须读取相应release或其释放序列的值才有相应同步；release不是“令任意后续读取都可见”的命令。seq_cst的总序针对这些原子操作及fence，不是把整个程序的所有访问自动纳入一个全局安全顺序。[atomics.order /1–7](https://timsong-cpp.github.io/cppwp/n4861/atomics.order)

compare_exchange失败会更新expected，weak版本还涉及虚假失败；atomic_wait提供按值等待的接口，也要设计通知、状态和寿命。ABA、lock-free与wait-free的差别以及节点回收不可由“原子指针”一词解决：指针原子不延长对象寿命。RCU、hazard pointer和epoch都是带各自读侧及回收责任的方案，不能只替换一行指针类型。具体合同与实践见[Atomic与C++内存模型](02-Atomic与C++内存模型.md)和[LockFree与FalseSharing](03-LockFree与FalseSharing.md)。本篇没有复测这些算法。

false sharing可能让独立热点争同一缓存行；`hardware_destructive_interference_size` 是布局参考，隔离可能增加空间、缓存或NUMA代价。是否需要padding应测真实访问模式，不能据它推导所有机器的缓存行行为；同样转前述LockFree篇，不复制一个新基准。

### 线程池、future和协程

`std::thread` 入口有未捕获异常，或析构时仍joinable，都会触发terminate；不是简单套用“不能穿过pthread边界”的平台描述。[thread destructor](https://timsong-cpp.github.io/cppwp/n4861/thread.thread.destr)、[thread constructor](https://timsong-cpp.github.io/cppwp/n4861/thread.thread.constr)

joinable的 `jthread` 析构会先request_stop再join；停止请求是协作的，并不自动令普通CV的closed谓词变真、唤醒它或打断任意IO。若使用stop-aware等待或回调，必须另行设计这些连接，不能去掉本例Close。[jthread /12](https://timsong-cpp.github.io/cppwp/n4861/thread.jthread.cons)、[stop token](https://timsong-cpp.github.io/cppwp/n4861/thread.stoptoken.intro)

线程池仍须限制线程/队列、规定准入拒绝及drain/cancel。future仅在设计了promise/结果通路后才传播异常；持锁等future时，完成该future的任务可能也需要此锁，池内同步等待子任务还可能耗尽worker。FIFO、优先级和work-stealing分别涉及队首长任务、饥饿、公平性、窃取与迁移成本，没有脱离负载的统一排名。

协程挂起不是自动并行。持 `std::mutex` 跨潜在挂起点，可能占住恢复任务所需的锁；若在别的线程继续，还涉及mutex线程所有权。取消后仍须管理frame、恢复权与资源退出。完整调度、停止和结果协议见[线程池、任务调度与协程调度](04-线程池、任务调度与协程调度.md)，本篇只解释它们为何不能绕开锁与owner的合同。

### 进程间通信

管道/Unix domain socket承担数据传输，共享内存共享存储，信号量或Linux eventfd可参与平台通知；字节流或消息语义、文件描述符传递、计数和崩溃恢复须按所选API确认。共享内存不自动等于吞吐更高，仍需跨进程同步、版本/长度/端序与恢复协议。本例的std::mutex/CV没有给出跨进程或持久化保证；[Win32 CV文档](https://learn.microsoft.com/en-us/windows/win32/sync/condition-variables)的进程内边界也不能外推所有OS实现。具体选型转[进程间通信与跨进程同步](05-进程间通信与跨进程同步.md)，本次未全文复核该篇或POSIX robust/process-shared协议。

## 10. 自测与审查：给出答案所在的状态变化

1. 哪些字段归m保护？若只让count原子化为什么不够？答：slots/head/tail/count/closed共同构成一次转换，见第1、5节
2. wait为何既解锁又要重新加锁？通知后为何仍可能无数据？答：等待期间让生产者推进，醒后重新读取被其它消费者改变的谓词，见第3节
3. 满队列关闭时谁必须醒？答：not_full上的producer与not_empty上的consumer；前者拒绝、后者存量优先，见第4、6节
4. deadline已过仍取到Item是否错误？答：本合同以锁内最终谓词与优先级决定，deadline不代表任务级取消或硬返回上界，见第4节
5. RAII解锁能否回滚业务、延长mutex或queue寿命？答：不能；Process失败由consumer记账，寿命由外部owner收束，见第2、5节
6. 所有等待都一定要超时吗？答：普通Push/Pop用Close作为退出协议；若处理永不返回或线程不获调度，单加timeout也不能证明整体退出
7. 在两次thread创建之间抛异常会怎样？答：guard先Close再join已启动槽；真实资源失败没有被本轮安全owner异常点冒充，见第5节
8. ABBA、持锁join和持锁等future分别是哪条等待边闭合了环？答：先画出线程/锁/任务依赖，再选锁序、释放锁或异步组合，见第7、8节
9. 正确性与性能如何各自验收？答：核状态不变量与所有出口，读检测报告及其覆盖边界，再独立做有口径和原始样本的性能测量；本轮不要求故意制造race

## 11. 来源定位与核对边界

本次固定版本的核心依据是[WG21 N4861官方PDF](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2020/n4861.pdf)：§32.5.3.2（mutex所有权、try_lock、unlock）、§32.6（通知/等待阶段）、§32.6.3（CV与timed wait）。本轮准备与独审实际读取了这些位置；本次作者复核固定镜像的对应条文。官方PDF原始文件hash未取得，未声称逐页阅读全文。

上文每个条文链接指向固定N4861的timsong镜像，它是工作草案条文镜像而非WG21官方域名。RAII、unique_lock错误、CV_any、thread/jthread、stop token、原子顺序和信号量的具体定位见各段。输入域检查另依据[N4861 expr.pre /4](https://timsong-cpp.github.io/cppwp/n4861/expr.pre)：先做有符号int乘法再把结果转大类型，不能补救此前已发生的越界。

队列的Closed优先、drain、固定结果存储及owner退场是本文在标准原语上建立的应用合同，不是标准直接规定的容器。未核libstdc++/libc++/MSVC具体同步实现、futex映射、硬实时、公平性或跨平台性能。历史来源和旧失败记录保持原身份；本轮成功读取官方核心段落不能改写以前timeout/403的事实。
