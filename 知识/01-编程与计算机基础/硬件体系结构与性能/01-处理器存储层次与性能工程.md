# 01-处理器存储层次与性能工程

> 知识成熟度：L2。本文用固定一手资料解释执行资源、地址翻译、缓存、相干、布局和观测之间的因果关系；纸面推导不代表程序运行或性能测量。
> 知识基线：Intel 248966-050US Volume 1（April 2024）选读、Linux v6.12 固定文档、C++ N4861 源码提交 `6aea7f6be0895b9dd361c6562bdee2f3809e4fa0`。准确选读范围见第 8 节，不宣称覆盖所有 AMD、Arm 或具体 MESI 实现。
> 适用范围：普通可缓存内存上的合法访问及 CPU 热路径诊断；不把 MMIO、持久化、块设备 I/O 或语言未定义行为套入同一缓存模型。
> 最后更新：2026-10-07。本轮只核对文本与纸面算术，未编译、运行样例、计时、采集 perf/PMU、查询机器拓扑或更改系统设置。五组 `PAPER_EXPECTED` 都是给定假设下的预期推导。

设一帧要更新一批实体的位置。循环变慢，可能因为每次更新依赖前一次结果，也可能因为热字段分散、共享写频繁、页面离执行线程较远，或前端供给不足。先明确“完成相同的一帧”是什么，再解释数据经过哪些状态，最后用能区分原因的观察决定是否改布局；不能从一个 cache-miss 百分比直接跳到 SoA。

## 1. 先固定工作量，再看延迟和吞吐

### 1.1 同一个循环有不同计数口径

“更新 1000 个实体”“执行 1000 条指令”和“发出 1000 次内存请求”不是相同的工作量。优化可能减少指令、合并访问或改变数据流，但必须仍完成原任务及其可观察结果。

| 量 | 应先给出的定义 | 能回答什么 |
|---|---|---|
| 操作延迟 | 起点到结果可被依赖者使用的时间，如某类 load-to-use；单位 cycles 或 ns | 一条依赖链至少要等待什么 |
| 吞吐 | 指定区间完成的业务操作数/时间，或指定执行资源可处理的操作数/cycle | 持续供给时能完成多少工作 |
| 带宽 | 明确层级或接口上搬运的 bytes/时间 | 数据流量是否逼近该处供给能力 |
| 退休架构指令数 | 对应 PMU 事件在给定范围内计到的已退休指令 | 该机器码的指令工作量，不等于实体数 |
| μop 与 pipeline slot | 微架构内部操作及供给/分配机会；定义依目标而定 | 哪类内部资源或机会被使用、浪费或阻塞 |

架构指令、μop 和 slot 不能一比一互换；退休的指令也可能是在做可从算法上删去的工作。CPU cycles 不等于业务请求经历的全部墙钟时间，等待 I/O 或调度的时间需另有口径。

### 1.2 等待何时能与别的工作重叠

以下是乱序核的职责图，不是某型号逐周期流水线：

```text
前端：预测下一段代码、取指和译码，供给内部操作
    → 调度/执行：依赖就绪且资源可用的操作开始执行
         ├─ 算术、分支等使用各自执行资源
         └─ load/store 产生地址、翻译和数据访问需求
    → 退休：把可提交的结果纳入架构状态
```

前端没有及时供给操作时，后端即使空闲也无事可做；操作已经到达调度器，也可能因为输入未就绪或执行端口繁忙而等待；执行过的投机操作还可能被丢弃，不能算作退休工作。内存访问延迟只有在后续可执行的独立工作不足时，才会更充分地暴露在关键路径上。[Intel §2.7.2、§22.1–22.1.5](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

例如更新各自独立的实体，后一个实体的地址与输入若已知，可能在等待前一个 load 时继续发起工作。若下一实体的地址必须由这次 load 返回的指针取得，依赖链就限制了这种重叠。调度窗口、队列、执行端口和在途请求能力都有限；独立性提供机会，并不保证所有延迟被隐藏。这是“内存墙”在具体热路径上的含义：数据供给跟不上该工作所能利用的执行能力，而非任何程序都以 DRAM 为首要瓶颈。

### 1.3 P1：量纲一致的延迟纸面例

**模型假设**：频率固定为 3 GHz，即每 ns 有 3 cycles；两次访问采用相同的 load-to-use 口径，分别假设为 4 cycles 和 200 cycles。它们只是输入常数，不是本机或某一系列 CPU 的规格。

| 项目 | 纸面换算 | `PAPER_EXPECTED` |
|---|---|---|
| 一个周期 | 1 / 3 ns | 约 0.333 ns |
| 假设的 L1 访问 | 4 / 3 ns | 约 1.333 ns |
| 另一访问 | 200 / 3 ns | 约 66.667 ns |
| 后者相对该 L1 | 200 / 4 | 50 倍；L1 相对自己为 1 倍 |

若再假设某资源能持续处理 3 操作/cycle，`200 × 3 = 600` 的单位是“操作”，只表示充分供给时的理想算术容量。**反例**：后续操作都依赖尚未返回的值，或端口/队列已满，就没有这 600 次可执行工作；更不能把它改称必然完成 600 条架构指令。

寄存器操作的依赖延迟取决于所执行的指令，不能给“寄存器”一个通用 0–1 cycle 访问预算。DRAM 请求延迟与 cache load-to-use 要先对齐起止点；NVMe 请求还涉及另一条软件与设备路径，不应混进同分母的缓存倍数表。实际频率变化时也不能用固定 3 GHz 换算全过程。[Intel §2.5.1.3 Table 2-9、§2.7.3 Table 2-16 的软件可见延迟脚注](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

## 2. 一次合法访问：翻译、权限与数据供给各做什么

### 2.1 先分开地址和内容

语言层先要求对象仍存活、访问在范围内且符合类型与并发合同；有一个指针数值不能证明这些条件。对这里讨论的普通用户态访问，程序提供虚拟地址（VA），MMU 利用 TLB、页表等得到访问所需的翻译及权限。TLB 缓存的是翻译信息，data cache 保存的是数据，二者未命中不是同一事件。[Linux v6.12，MMU/TLB/Page Faults](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/mm/page_tables.rst)

```text
合法的程序访问：地址 + 长度 + 读/写类型
    ├─ 翻译与权限职责：TLB / 页表遍历 → 可访问的物理位置，或异常
    └─ 数据供给职责：目标缓存层次 / 相干系统 / 内存提供所需内容
异常分支：由系统判断能否补足条件；成功可重试，错误不保证恢复
```

这不是必须依次走完“TLB→L1→L2→DRAM→磁盘”的串行流程。真实实现可以重叠部分工作，页表遍历自身的读取也可能由缓存满足。一次数据访问可能命中已有缓存，或由其他层级、相干参与者提供；只读 1 byte 不等于必向 DRAM 新取一整行，更不等于一次磁盘 I/O。

理解多级数据供给时，可以把已读 Intel 实现中的常见层次按职责分开；具体共享范围与参数仍须查目标型号：

| 数据位置 | 在热路径中的作用 | 不能混同的边界 |
|---|---|---|
| L1 数据缓存 | 较近的数据复用位置，命中可较快供给依赖者 | L1D 与取指用的 L1I 不是同一职责；命中不消除所有依赖等待 |
| L2 缓存 | 为 L1 未满足的访问提供另一层缓存机会 | 是否私有及与其他层的包含关系分别判断 |
| LLC（末级缓存，所述例子为 L3） | 进入缓存层次外之前的最后一级缓存，可涉及多个核心的共享 | LLC miss 不保证数据只能来自 DRAM，相干参与者也可能持有最新内容 |
| DRAM 主存 | 提供未由较近层次满足的普通内存数据 | 请求排队、带宽和并发会改变等待；它不是磁盘持久化 |

局部性让后续访问有机会在较近层次复用已有数据；并行请求则可能重叠等待。这两种机制相辅相成，但“更少 miss”和“更短业务时间”仍需分别判断。[Intel §2.7.3、§22.1.4](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

### 2.2 P3：4 KiB 页映射纸面追踪

**模型假设**：普通页大小为 4 KiB，即 `0x1000` bytes；访问长度为 1 byte；`VA = 0x1234`；有效映射将虚拟页号 VPN 1 映射到物理页框号 PFN 9，且允许本次操作。

页内偏移为 `0x234`，故 `PA = 9 × 0x1000 + 0x234 = 0x9234`。**`PAPER_EXPECTED`：PA 为 `0x9234`，页内偏移保留。** 这里保留的是这个页模型的低位偏移，不是所有虚实地址位都相同，也不是所有 cache index 位都相同。

| 当前状态 | 下一步及结果 | 不能作出的推断 |
|---|---|---|
| TLB 有合适翻译且权限允许 | 无需为此次访问遍历页表 | 数据一定命中 L1 |
| TLB miss，页表已有可访问映射 | 遍历并取得翻译后继续 | 必然 page fault 或磁盘 I/O |
| 当前映射/权限不能直接满足 | 可能进入 page fault，由系统判断原因 | 所有 fault 都是非法访问或都能恢复 |

**反例**：TLB hit 与 data-cache miss 可以同时成立；TLB miss 也可以发生在页表数据和目标数据已经缓存的情况下。按需分配和 COW 可以借正常可服务的 fault 补齐条件，非法访问、后备错误或资源不足则可能失败。文件映射、页面生命周期和故障恢复的完整合同见[虚拟内存、PageFault 与 mmap](../操作系统与系统I-O/02-虚拟内存、PageFault与mmap.md)，这里不把缺页次数换算成固定 I/O 时间。

## 3. 缓存行与组相联：先写出模型再判断冲突

### 3.1 行粒度、共享关系和容量是不同变量

在本文的简单模型中，cache line 是保存数据并参与缓存管理的块。对象大小、指令访问宽度、缓存行大小、预取范围各有含义；一个字段跨越几行由字段范围和布局决定。后续统一**假设 64 bytes/line**，不是声明所有 x86、Arm 或所有层级都采用同一粒度。Intel §9.6.3 的枚举还明确区分 coherency line 与 prefetch stride。[Intel §9.6.3](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

“每核私有”描述谁共享缓存；inclusive、exclusive、non-inclusive 描述不同层级内容的包含关系。这两个维度不能合成“L2 独占所以 L3 没有副本”。已核的 Skylake Server 例子具有每核私有 L2 和 non-inclusive LLC，含义是 L2 中的块不要求在 LLC 中保留副本，不是说两者绝不重叠。[Intel §2.6.1.1–2.6.1.2](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

压缩热数据、提高空间局部性可让一次取来的行包含更多接下来要用的字段；缩短重复访问间隔可提高时间局部性。代价是压缩/解压、格式转换或索引计算可能增加执行工作。选择分块大小时还要考虑共同活跃的数据流、代码和其他线程所占资源，不能把标称 cache 容量全部当成该循环的独占预算。

### 3.2 P2：32 KiB、64 bytes、8-way 的模映射

**模型假设**：字节寻址、数据容量 `C = 32 KiB = 32768 bytes`、行长 `L = 64 bytes`、每组 `W = 8` 行，组数为 `S`；不含额外分区、hash、slice 或其他索引变换。`A` 是这个模型使用的非负字节地址，不默认等于实际 C++ 指针值或物理 LLC 地址。

```text
S      = C / (L × W) = 32768 / (64 × 8) = 64 sets
block  = floor(A / 64)
offset = A mod 64
set    = block mod 64
tag    = floor(block / 64)
```

| A（bytes） | block | offset（bytes） | set | tag | `PAPER_EXPECTED` 的关系 |
|---:|---:|---:|---:|---:|---|
| 0 | 0 | 0 | 0 | 0 | 第一行 |
| 64 | 1 | 0 | 1 | 0 | 相邻行，落在另一组 |
| 4096 | 64 | 0 | 0 | 1 | 与地址 0 同组、不同 tag |

offset 定位行内字节，set 选择候选组，tag 区分映到该组的不同块，ways 给出该组可同时容纳多少行。三者用途不同；“同行”“同组不同 tag”和“超过 ways”也不是一个判断。按上述假设，地址 bits 5..0 是 offset、bits 11..6 是 set；更高位属于本模型的 tag，不需假定真实物理地址一定有 64 个有效位。

本模型的 4096-byte 步长每次跨 64 个 block，因此回到同一 set。**反例**：若另一个模型使用 bits 17..6 作 index，则有 4096 sets；同样步长让 set 每次增加 64（mod 4096），走过 `0、64、128、…、4032` 后回到 0，共经过 64 个不同组。“所有 2 的幂步长都同组”因此不成立。[Intel §3.6.7，对实现相关 aliasing 的讨论](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

九个不同 tag 都映到一个 8-way 组时，该组无法同时保存全部九行；这说明一种冲突条件，尚未给出精确 miss 次数。首次访问、整个活跃集合过大、局部同组竞争、相干失效等都可能产生未命中。要数某条序列的 miss，仍需初始状态、访问顺序、替换规则、预取、并发和写策略。本例只输出地址映射，不输出 miss、总线流量或耗时。

真实缓存的索引/标签选择可能涉及虚拟地址、物理地址及额外映射；仅凭任意用户态地址的余数不能推导物理 LLC set 或 slice。Intel cache 枚举公式还含 physical partitions 因子 P；这里 `C=L×W×S` 只属于已排除额外分区的模型。若怀疑冲突，可在相同算法工作量下考虑改变步距或分块，但增加 padding 也会扩大工作集和 TLB 压力，模型上的分散不保证实机更快。

## 4. 相干维护写权限，语言模型维护程序正确性

### 4.1 一个明示简化的写回模型

以下是**教学抽象**：普通可缓存内存、按行协调，允许多个可读副本，但写入前须取得该行适当的写权限；持有最新脏数据的一方承担保存或转交最新数据的责任。它省略瞬态、请求竞合、目录细节和实际互联，不是对某 CPU 完整 MESI 状态机的认证。

| 抽象状态 | 在这个模型中的含义 | 为什么下一步不同 |
|---|---|---|
| 本地无有效副本 | 不能用该项直接完成有效命中 | 要取得数据及所需权限；原因可为从未持有、替换或失效 |
| 有可读副本但无写权限 | 可按模型读取，不能直接修改 | 写前需协调其他副本，取得写权限 |
| 已有写权限 | 当前可继续修改该行 | 无其他干预且权限仍有效时，不为每次写重复获取所有权 |
| 已修改且持写权限 | 最新内容可能只在较近的相干层次中 | 替换或其他请求到来时，需按协议保存/转交最新值 |

在这类 write-back 抽象中，常见的 Modified 一词涉及脏数据与写权限，**“回写”不是刷磁盘，也不等于持久化完成**。Invalid 表示本地该项不能作为有效副本使用，不必是“被他核篡改”。真实实现可采用侦听、目录等机制；Intel §12.3.1 所述 Optane 多处理器平台就是目录方式的一个具体例子，不能据此推导所有 CPU 的目录格式或状态转换。[Intel §11.6.2、§12.3.1](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

沿一个允许的抽象次序追踪：A、B 都持可读副本；A 要写，先获得写权限，使 B 不能继续用旧副本读；A 在权限未丢失期间连续写，无须每写一次都发新的 RFO；B 随后再读，需要取得当前有效内容，可能由相干层次满足。此追踪说明了权限交接的成本来源，不指定广播范围、消息条数或固定 DRAM 访问次数。[Linux v6.12，CPU cache 与相干观察](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/memory-barriers.txt)

### 4.2 伪共享为何能发生在合法程序里

假设两个线程分别独占两个不同的普通计数槽，槽在启动线程前已构造，工作期间容器结构不变，所有线程结束并完成适当交接后才汇总。语言层访问可以合法；若两个热槽共行、且工作线程在不同核心反复写，行级权限仍可能在核心间交接。这就是不同数据之间不必要的相干交互。即使另一核心只读同一行内另一个不变字段，也可能受写失效影响；全只读则没有这种写权限争用。

因此先区分“两个语言内存位置”与“两个缓存行”。同一位置的并发冲突若至少一个非原子，且缺乏所需 happens-before，可以构成 C++ data race，行为未定义；换成有相干缓存的机器不会使其合法。相干也不自动建立跨对象的发布关系。[N4861 intro.races，冲突与同步](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/basic.tex#L5796-L5825)、[data race 条件](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/basic.tex#L6094-L6149)

改善候选是减少交接频率，例如每线程局部累加后在合法交接点合并；代价是合并工作、额外内存和结果可见性延迟。布局隔离则需同时核行粒度、字段跨度、对象起点和元素步距：只给数组起点加 `alignas(64)`，不会使其内部每个标量相距 64 bytes。过度填充会增加缓存/TLB 占用，对没有共享写瓶颈的路径可能更差。

布局、无锁与历史实验的详细边界见[LockFree 与 FalseSharing](../并发与同步/03-LockFree与FalseSharing.md)；语言同步见[Atomic 与 C++ 内存模型](../并发与同步/02-Atomic与C++内存模型.md)及[ISA 篇的发布合同](../编译链接与ABI/03-ISA汇编与调用约定.md#8-并发abi-正确不等于发布协议正确)。这里不把邻篇的运行结果转成本篇的性能证据。

## 5. 从地址依赖到预取，再到 AoS/SoA

### 5.1 连续性提供什么机会

在连续数组中，下一个元素地址通常能由基址和下标算出，不必先等前一个元素的数据返回。可提前知道多个地址，才有机会保持多笔独立内存请求在途，形成内存级并行（MLP）；规律的流也给硬件预取器提供线索。若及时取入的行被后续使用且未被替换，需求访问的等待可能减少。

机会受可识别模式、预取距离、页边界相关限制、请求资源、带宽和具体实现约束。Intel §3.7 的部分例子讨论旧微架构，不能把其中固定 4 KiB 边界或特定触发距离当成所有新 CPU 的规律。预取过早可能提前占用缓存，过晚无法隐藏等待，取来未用的数据还消耗带宽；“顺序遍历”不能承诺近 100% 命中。[Intel §3.7–3.7.3](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

指针追踪的主要约束是依赖：若下一地址存放在当前节点中，必须先取得那个指针值，才能形成下一次访问。普通程序指针在这里代表程序地址，不是可直接拿来映射 LLC 的物理地址。**反例**：节点已缓存，或分配/遍历具有局部性，就不必每节点都等 DRAM；有多个独立链时也可能产生更多并行机会。不能把所有预取机制说成绝对不能处理任何指针相关模式。

`std::list` 的标准接口支持双向迭代，不能把它标成单向链表；N4861 的概览也没有替所有库规定节点布局。选择数组、池化节点或紧凑索引可改善局部性，但需要承担插入/删除、地址稳定性或索引维护方面的代价，须保留应用需要的语义。[N4861 list.overview](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/containers.tex#L4835-L4861)

### 5.2 P4：先证明两种布局完成相同更新

**语义模型假设**：四个实体，初始 `x=[1,2,3,4]`、`vx=[4,3,2,1]`，`dt=2`；每实体只做 `x←x+vx×dt`，其余字段和实体对应关系全部保留。数值在本数学模型中精确，不涉及实际浮点重关联、溢出或别名问题。AoS 将每实体字段放在一起，SoA 将同名字段放在各自数组中；改变位置不授权删字段或改算法。

| 实体 | 同一更新 | AoS 的 `PAPER_EXPECTED` | SoA 的 `PAPER_EXPECTED` |
|---:|---|---:|---:|
| 0 | 1 + 4 × 2 | 9 | 9 |
| 1 | 2 + 3 × 2 | 8 | 8 |
| 2 | 3 + 2 × 2 | 7 | 7 |
| 3 | 4 + 1 × 2 | 6 | 6 |

两边预期结果都是 `[9,8,7,6]`。这只是有限输入的同语义纸面追踪，不是编译程序的输出，也不证明任意实现都正确。比较真实实现时还要检查合法访问、字段对应、精度、生命周期和输出是否确实被使用。

### 5.3 P4：再数热字段覆盖的抽象行

**布局模型另作假设**：字段宽度为 4 bytes，行长为 64 bytes；AoS 起点为字节地址 0，实体步距 48 bytes，x 的偏移为 0，vx 的偏移为 12，其余字段仍存在但本操作不用；SoA 的 x 起点为 `0x1000`、vx 起点为 `0x2000`，每数组含 4 个连续字段。这里的地址是用于数行的抽象字节坐标，不是测得的 `sizeof`、分配器结果或真实物理地址。

| 实体 | AoS 的 x 字节区间（含端点） | AoS 的 vx 字节区间（含端点） | 覆盖的抽象行号 |
|---:|---|---|---|
| 0 | 0..3 | 12..15 | 0 |
| 1 | 48..51 | 60..63 | 0 |
| 2 | 96..99 | 108..111 | 1 |
| 3 | 144..147 | 156..159 | 2 |

以 `floor(字节地址/64)` 数成员字节，AoS 热字段的不同抽象行集合为 `{0,1,2}`，共 3 行。SoA 的 x 覆盖 4096..4111，全在线 64；vx 覆盖 8192..8207，全在线 128，集合为 `{64,128}`，共 2 行。**`PAPER_EXPECTED`：3 行与 2 行，单位是“成员字节覆盖的不同抽象行”，不是 miss 或事务。** 写回 x 不增加这个成员地址集合，但写分配、相干和预取等可能引入其他事务。

读取 x、vx 的成员访问不等于按结构体边界搬运整个 48-byte 对象；硬件的数据路径和块粒度另有规则。上述 3/2 既不是流量比也不是加速比：初始是否在 cache、真实布局是否相同、所经层级、写策略和并发都未给出，不能从集合大小造出时间结论。

SoA 在“遍历许多实体、只用少数字段”时让热字段更紧密，可能减少无用字段随行进入缓存，也更便于组成 SIMD 字段流。但自动向量化还受别名、循环依赖、精度要求、对齐、目标扩展和编译器影响，不能保证发射 AVX2 或一次处理固定数量。AoS 与 SoA 间动态转换也需要额外操作。[Intel §5.5.1](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

**反例与选择代价**：若一次处理实体的大多数成员，AoS 的实体内局部性可能更合适；SoA 的多个数组会形成多条访问流，增加存储管理和数据交换成本。起点变化或字段跨行时要重算集合，不能沿用 3/2。布局选择应根据热阶段实际使用哪些字段、实体访问次序及转换频率作出，再用同工作量的测量检验。

### 5.4 从纸面例走向公平比较需要补什么

一份可用于比较的证据应先固定输入、更新语义、结果校验与完成的实体数，再记录生成代码、计时区间、构建选项、热身/冷启动目标、运行次序与重复波动。计时区间是否包括初始化、分配和转换，要与真实问题一致。不同实体大小、不同字段或不同运算的两个程序，不能只按 AoS/SoA 名字当作单变量对照。

旧大规模示例没有核验/使用更新结果，也缺少完整构建与采集对应关系；as-if 规则允许在不改变可观察行为时省掉不需要的计算，因此“源码里有循环”不是测到了全部工作的证据。本轮没有编译或反汇编旧代码，不能声称已观察到循环被删除；本节的纸面追踪也不外推为旧 500 万实体的性能结果。[N4861 intro.execution](https://github.com/cplusplus/draft/blob/6aea7f6be0895b9dd361c6562bdee2f3809e4fa0/source/intro.tex#L499-L524)

## 6. 拓扑与政策：线程在哪里，数据又在哪里

### 6.1 CPU 数量不能代替拓扑

| 名称 | 本文区分的职责 | 对性能判断的影响 |
|---|---|---|
| Logical CPU / 硬件线程 | Linux 可调度的逻辑 CPU 单位 | 多个编号不一定拥有独立的全部执行资源 |
| Core | 包含一个或多个硬件线程的核心 | 同核 SMT 线程可能共享或分割资源 |
| Package / socket | 前者是拓扑中的封装单位，后者是物理插槽概念 | 名称常被混用，不能据此推导 NUMA 或 LLC 边界 |
| NUMA node | 系统描述内存局部性和分配关系的节点 | 本地/远端是相对执行位置与内存位置而言 |
| LLC sharing domain | 共享同一末级缓存的处理器集合 | 不自动等于一个 NUMA node 或所有逻辑 CPU |

Linux v6.12 的 x86 topology 文档给出 package/core/thread 和 LLC 标识的用途，但其中历史厂商用语不能被当作所有现代平台的统一别名。[Linux v6.12 x86 Topology](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/arch/x86/topology.rst)

Intel HT 通过多个架构状态让同一物理核心可执行多个软件线程，利用一个线程暂时用不上的资源可能提高总吞吐；若两个线程竞争同一端口、缓存或队列，也可能互相干扰。它不是完整核心数量翻倍，不承诺单线程延迟改善。手册 §2.8.2 后续队列对半分割等描述明确以早期实现为主，不能推广成所有 SMT 的固定资源表。[Intel §2.8.2–2.8.2.2](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

以下是**假设双节点职责图**，不表示本机，也不规定延迟和容量：

```text
Node A：一组 CPU 与其局部内存资源 ←互联→ Node B：另一组 CPU 与内存资源
线程在 A、页在 A：本地性候选       线程在 A、页在 B：远端访问候选
```

这个图没有规定“一节点一插槽”。Intel SNC 的已核示例按地址范围将 LLC 分为不同 cluster，并联系各自内存控制器子集；开启该模式可以得到更多 NUMA 节点。这足以说明 socket 与 node 不能一一等同，却没有给所有系统一个固定远端惩罚。[Intel §10.1–10.3](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

### 6.2 CPU 绑定和内存政策改变的是不同状态

CPU 落点约束决定线程在哪里执行；NUMA memory policy 决定适用范围内新分配页的节点选择。Linux v6.12 文档区分 task、VMA 和 shared policy，并说明 cpuset 的允许范围优先。task policy 对安装它的线程及随后创建的线程适用，不能假定已经存在的所有兄弟线程同时改变。[Linux v6.12 NUMA Memory Policy，Scope of Memory Policies](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/admin-guide/mm/numa_memory_policy.rst)

用一个**政策反例**检查“绑定后全本地”：初始化时，页已在 Node B 分配；之后把工作线程限制在 Node A 并安装倾向 A 的新政策。仅安装政策不会自动搬走原先的页，线程对这些页仍可能远端访问。新分配与已有页迁移是两项不同工作；共享后备的放置也不只取决于当前读取者。

普通共享文件映射的 page-cache 页不会简单服从给该虚拟地址范围安装的 VMA policy；文档另述 task/default policy 及共享对象政策的适用范围。因此只看启动参数，不能证明每个匿名页、共享页、库映射或内核访问都已本地化。原文中的节点绑定命令表达的意图可保留为“同时约束线程落点与适用分配”，但不承担“完全消除远端”的承诺。

实践上，先按热数据的所有权划分工作，再把相应执行位置、分配时点与政策放在同一份说明中。若工作频繁交换大块数据，硬绑单节点可能增加跨节点共享，或放弃其他节点的容量、带宽和空闲核心；单节点容量不足或政策受约束时也不能承诺成功。采用绑定或分片前，需能解释已有页、共享页、SMT 同胞与其他负载的影响；这里没有执行查询、迁移或绑核操作。

## 7. PMU 观测：从有效数据到可检验的假设

### 7.1 先确认分子分母是否在说同一件事

性能计数器不是零开销、无条件可用的传感器。Linux v6.12 的 perf-stat 文档明确包含工具开销、计数聚合、复用、缩放与 CPU 支持范围；完整采集和权限流程见[性能工具：插桩与 perf 采样](../../08-工程实践与质量/调试与性能分析/03-性能工具：插桩与perf采样.md)。先判断问题发生在 CPU 执行阶段还是 I/O、调度等阶段，再决定微架构指标能解释多少。[Linux v6.12 perf-stat](https://raw.githubusercontent.com/torvalds/linux/v6.12/tools/perf/Documentation/perf-stat.txt)

| 记录项 | 为什么缺它会改变结论 |
|---|---|
| CPU/PMU、内核、perf 版本及事件定义 | 通用名字不保证各 PMU 计的是同一种访问，混合核不能随意合并解释 |
| PID/TID/CPU、用户态/内核态与聚合范围 | 线程的指令数不能直接除以另一核心或整个系统的 cycles |
| 相同时间区间与业务完成量 | 初始化、空闲与热循环混在一起，可能掩盖阶段性瓶颈 |
| 分子、分母、单位和原始计数 | 次数不是比例，架构指令不是 μop，slot 比例不是请求墙钟占比 |
| 计数实际运行时间/比例、缩放及复用告警 | 只在部分窗口采到的计数不能当作全程直接观察 |
| 失败信息与测量开销 | 不支持、权限不足或未计数不等于该事件发生零次 |

`IPC = instructions / cycles` 只有在对应退休指令事件和 cycles 的范围、区间及口径兼容时才可解释。某层 miss 比率也必须有与 miss 匹配的访问分母，不能把 `L1-dcache-load-misses` 除以任意总指令数后称为 L1 miss rate，或把通用 `cache-misses/cache-references` 当全部层级总命中率。

有限计数器可能轮流测不同事件。perf 可缩放计数，但缩放没有把没测到的阶段变成实际观察；负载相位变化、分子分母不同期运行都会影响比率。Linux 文档说明 metric 分组试图让相关事件一起调度，改变分组也可能改变复用与准确性。先保留运行比例、分组和告警，再决定是否能回答当前问题；此处不另给脱离 API/工具版本的精确缩放公式。

### 7.2 P5：纸面判读的正反例

本组只有逻辑输入和判断，不制造终端输出或虚构 perf 记录。**模型前提**是检查一次候选推断是否具备所需事件和范围。

| 纸面输入 | `PAPER_EXPECTED`：可接受的判断 | 被排除的错误推断 |
|---|---|---|
| 分子来自线程热阶段，分母来自全机另一窗口 | 拒绝该比率，补足匹配区间与范围 | 两个计数都有值，所以百分比有效 |
| 出现 `unsupported`、`not counted`、权限失败或分母为 0 | 标记不可用，停止这个指标的归因 | 记成 0% miss，说明缓存很好 |
| 事件只在部分窗口运行，工作负载分阶段变化 | 缩放结果需带覆盖限制，不能直接跨阶段比 | 缩放后等同全程连续实测 |
| IPC 低，但没有区分依赖、前端、分支和访存的证据 | 保留多个候选原因，寻找能区分它们的观察 | IPC 小于 1 就一定 Memory Bound |
| LLC miss 较多，仅知道这一计数 | 调查首次访问、冲突、容量、相干和数据供给来源 | 工作集一定超过 LLC，每次都到 DRAM |

正向推理应像这样：热循环只用少数字段，布局分析发现它们分散在许多行，因此提出“热字段利用率低”假设；第 5 节同语义重排是候选改变，后续需要匹配的访存观测和业务时间来判断收益。若实际是下一地址依赖链限制并行，或大量共享写在交接权限，仅把字段换成连续数组可能未解决主因。

### 7.3 Top-Down 将 slot 分类，用来选择下一层问题

Intel 的 TMA 以目标微架构定义的 pipeline slots 为口径。已分配操作最终退休，可归入 Retiring；未退休的投机操作及错误推测恢复时阻塞 issue 的 slots 属于 Bad Speculation。后端不能接收更多工作对应 Backend Bound；在后端可接收时前端未供给操作对应 Frontend Bound。这个解释不能简化为“Bad Speculation 只包含执行了但没退休的分支指令”，恢复损失也是一部分。[Intel §22.1–22.1.6](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

| 顶层方向 | 下一步要区分的机制 | 有条件的候选改变与代价 |
|---|---|---|
| Retiring | 退休工作是否必要，能否完成同一任务而少做计算 | 简化算法或数据处理；高占比仍可能在做冗余工作，不等于无需优化 |
| Bad Speculation | 分支误判、机器清除及恢复分别贡献什么 | 改数据/控制流或比较无分支方案；branchless 可能增加无用计算、访存或依赖链 |
| Frontend Bound | 取指/ITLB 延迟还是供给带宽不足 | 缩小热点代码或重排；过度内联可能增大代码体积，减少调用也可能有益，需看实际供给原因 |
| Backend → Core Bound | 端口/执行单元压力还是缺少指令级并行 | 调度独立工作或使用合适向量化；额外操作、寄存器压力和语义约束可能抵消收益 |
| Backend → Memory Bound | 哪一层供给、翻译、store 资源或依赖导致等待 | 减少热数据、改善访问次序/布局、降低共享；SoA 不会自动消除所有 cache miss |

Memory Bound 不等于“从 DRAM 读得多”。手册例子中，即使最终由 L1 满足，先前 store 相关阻塞也能使 load 的有效等待变长；翻译和 store 资源同样可进入相应下级分类。向量化减少指令工作可能让瓶颈转到数据供给，指标占比变化也不直接表示业务变差或变好。最终仍需比较同一任务的绝对时间、吞吐及所关心的延迟。

使用前还要核采集范围。Linux v6.12 的 `--topdown` 文档把 per-core 限制明确放在较旧 Intel CPU 和 Atom 的条件下，并说明较新 CPU（Ice Lake 及以后）可按线程收集；这不是所有 CPU、所有 perf 版本都通用的一条命令合同。该文档还要求所分析负载确实 CPU-bound，且更深层指标可能因需要更多计数器降低准确性。本篇未执行其中的权限、watchdog、taskset 建议，也没有固定 60%/15%/20%/35% 的通用优化阈值。

从这里回到业务选择：先验证正确性和完成量，再定位实际耗时阶段，再用可用指标选择一条区分性假设。改动若只降低 miss 数却增加转换、指令或等待总成本，就不能称完成性能优化；证据无效或无法区分原因时，应停在“尚不能归因”。
