# 虚拟化与硬件辅助隔离

> 知识成熟度：L2。依据 Intel SDM 326019-078US（2022-12）、Linux v6.12 与 QEMU v9.2.0 的指定选段解释机制；不是平台安全认证或性能结论。
> 最后更新：2026-10-07。本文的 P1–P11 均为 `PAPER_EXPECTED`：输入是假设，结果是静态推导。本次能力查询、虚拟机运行、配置、设备/DMA、网络、采样、编译、压力与故障实验全部 `NOT_RUN`。

## 一台客户机，几种不同的责任

设 Linux 宿主上的 QEMU 使用 KVM 运行一个普通、非嵌套、非机密的 x86 guest。guest 应用先读一段内存，再读一次设备数据。本文追踪这两次访问，回答三个问题：guest 内核为什么能在自己的 CPL0 运行却不能任意控制宿主；访问受阻后由谁继续处理；选择设备、页粒度、资源放置和迁移方案时需要哪些证据。

guest 管理应用与自己的页表；KVM 在宿主内核中维护 VM/vCPU 对象、处理硬件进入与退出，并协调二阶段地址映射；QEMU 提供机型、用户态设备模型及相关内存/I/O 接入。宿主调度器决定线程何时真正获得 CPU，宿主内存管理维护 backing，设备及 VFIO/IOMMU 又有各自的访问与所有权合同。一次设备操作可以穿过多种责任，不能用一个“hypervisor”标签省掉中间状态。〔S2、S3、S7〕

Type-1 通常描述直接在硬件上承担监控职责的部署，Type-2 通常描述借助宿主操作系统的部署。这些历史分类不决定一次访问会走哪条路径：QEMU 可以使用 KVM，也可以使用软件 TCG；设备处理可以在 QEMU、卸载后端或直通设备上。先记录 accelerator、机型、设备后端和资源拥有者，才有可比较的对象。

QEMU v9.2.0 的安全文档将 TCG 仿真归入 non-virtualization use case，并明确该版本的这类用例不提供用户可依赖的 guest 隔离与安全保证。这是版本化的安全支持政策，不能改写为“TCG 技术上完全没有隔离”。开发或跨 ISA 仿真可以有不同目标；若目标是隔离恶意 guest，就必须采用符合该目标的受支持部署。使用 KVM 也不自动证明设备模型、管理接口、固件及宿主权限都安全。〔S7〕

容器共享宿主内核，VM 则有独立 guest 内核并增加 VMM/设备边界；“更轻”不是安全强弱排序。沙箱与微型 VM 产品应按威胁模型、所运行内核和设备面比较，不在这里按名称排名。Linux 凭据、namespace、cgroup、seccomp 的完整责任见[权限、安全与隔离](../操作系统与系统I-O/04-权限安全与隔离.md)。

## CPU：guest 的 CPL0 为什么仍受控制

Intel VMX root/non-root 与 CPL 是两个维度。CPL 表达当前执行环境中的特权级；VMX 决定 guest 执行受到哪些控制。VMCS 关联受控的 guest/host 状态、执行控制与退出信息。VM entry 进入 non-root，VM exit 将控制交回 VMM 指定的宿主入口；guest 在自己的用户态与内核态之间切换，不必因此退出 VM。用“ring -1”统称所有 VMM 活动，会丢掉宿主用户态 QEMU 这一层。〔S1〕

### P1：把执行身份放到两个维度

输入：Intel 逻辑 CPU 已合法进入 VMX operation，采用普通保护执行，无 SMM、嵌套或机密 VM。A 是宿主 VMM 内核，B 是 guest kernel，C 是 guest application，D 是在该 VMX 活跃 CPU 上运行的宿主 application。这些是给定身份。

| 身份 | PAPER_EXPECTED P1：VMX / CPL | 能解释什么 |
|---|---|---|
| A | 通常 root / CPL0 | 宿主内核执行 VMM 的受控处理 |
| B | non-root / CPL0 | guest 内核仍可使用其原有特权级，但受 VMX 控制 |
| C | non-root / CPL3 | guest 应用由 guest 内核管理 |
| D | 可以是 root / CPL3 | root 不等于宿主内核态 |

C→B 的 guest syscall 可以只改变 guest CPL；B→A 的 VM exit 改变 VMX 模式，并不是一次普通 syscall。反例是把 CPL0 等同 root，从而误判 B 已能控制宿主；反过来把 root 等同 CPL0，又无法解释 D。正确选择是分别描述两维，再研究哪些事件由执行控制截获。

观察边界与停止点：P1 没有证明本机支持或启用了 VMX，也没有证明设备隔离。VMFUNC、APIC virtualization、posted interrupt、各类 bitmap 都另有能力和控制前提，本文不把它们列为已可用的调优开关。依据为 S1 §24.3–24.5。

AMD SVM/NPT、Arm EL2/Stage-2 是不同架构的后续比较入口。原 AMD APM 与 Arm ARM 链接保留在历史区；本次没有核对 VMCB/intercept、ASID/AVIC、HCR_EL2/VTTBR_EL2 或异常路由细节，因此不把 Intel 的模式名称、保留位、fault 分类直接套过去。CPU 手册也不能代替对应 IOMMU/SMMU 规范。

## 内存：CPU 翻译链与 VMM 管理关系

对开启 guest paging 和 EPT 的所选案例，CPU 的逻辑翻译关系是 GVA → guest 页表 → GPA → EPT → HPA。guest 页表本身也在 guest 内存里：硬件遍历 guest 页表时，对这些页表页的 GPA 访问同样需要 EPT。不能把整次访问想成“先完整走完 guest 页表，最后才只翻一次 EPT”。缓存可能避免一些遍历；未给页表层数和缓存状态时，不计算硬件访存次数。〔S1 §29.3、S3〕

另一条是普通 userspace-backed memslot 的管理关系：用户态登记 GPA 区间与 `userspace_addr` 对应的 HVA 区间，宿主再维护这些 HVA 的 backing。HVA 不是 CPU 最终访问 HPA 前必经的第三套 guest 页表。匿名内存、文件等可作为 backing，但 VMA、驻留和宿主物理页可能变化；不能把登记过 slot 当成页永远固定。这里不覆盖 guest_memfd、私有/机密内存或嵌套虚拟化。〔S2 §4.35、S3〕

| 地址 | 谁使用、表示什么 | 容易混淆的地方 |
|---|---|---|
| GVA | guest 指令使用的虚拟地址 | 同一个数值不等于宿主地址 |
| GPA | guest 认为的物理地址；guest 页表指向的空间 | 仍需所选二阶段翻译 |
| HPA | CPU 最终访问的宿主物理地址 | 与 VMM 指针不是同一个空间 |
| HVA | 宿主用户态管理普通 guest backing 的虚拟地址 | 是 memslot 管理关系，不插入硬件 guest 翻译链 |
| IOVA | 设备可见 DMA 地址，在所选 IOMMU domain 中解释 | 不通过 guest/host CPU 的普通虚拟地址翻译来授权 DMA |

### P2：沿页内偏移手算一次读

输入：采用上述普通 userspace-backed guest，页大小 4 KiB。读取 GVA `0x1234`；guest 映射 `[0x1000,0x2000)` → GPA `[0x4000,0x5000)`，EPT 映射 `[0x4000,0x5000)` → HPA `[0x904000,0x905000)`；两层合法且允许读。memslot 为 GPA `[0x4000,0x6000)` → HVA `[0x70000000,0x70002000)`。guest 页表页的 EPT 访问也全部允许，backing 有效且驻留，无并发映射变化，实际翻译状态与给定表一致。

**PAPER_EXPECTED P2**：页内偏移为 `0x1234−0x1000=0x234`，所以 GPA=`0x4234`，HPA=`0x904234`。管理关系中的 HVA=`0x70000000+(0x4234−0x4000)=0x70000234`。guest PTE 给的 `0x4000` 是 GPA 基址，不是宿主物理地址。

反例：在另一个重新给定且一致的映射模型里，仅将 EPT 目标基址换为 `0xA04000`，HPA 就是 `0xA04234`，GVA/GPA/HVA 可以保持原值。这说明改的是哪一层关系，并不是教读者在运行中改表而省略失效与同步协议。

观察边界与停止点：以上只证明给定区间和偏移的关系，不证明真实 backing、TLB 命中或性能。页表可访问性、旧翻译处理或并发状态不明时，不能把这条成功链照搬到现场。依据为 S1 §29.3.3.2、S2 §4.35、S3 Translation/Memory。

## 受阻时先分清哪一层故障

guest #PF 由 guest 地址翻译和权限语义产生；EPT violation 表示二阶段访问被合法的缺项或权限条件阻挡；EPT misconfiguration 表示遇到该架构版本不支持的条目编码。host backing 缺页或改变则是宿主 VM/KVM 要协调的事件。它们可能在一次请求的不同阶段关联出现，却不是同一种计数，更不能直接等同磁盘 I/O 或 QEMU 设备模拟。〔S1、S3〕

### P3：每次只改变一个障碍

共同输入：沿用 P2 的普通 x86/EPT 范围；关闭 EPT-violation #VE。下列各行相互独立，相关表可访问，无并发变化或未处理旧翻译；除本行的单一障碍外，其余条件足以走到该障碍。正常异常交付所需 guest 状态有效，不构造嵌套异常。

| 情境输入 | PAPER_EXPECTED P3 | 可得结论与反例 |
|---|---|---|
| A：guest PTE 不 present；相关 EPT 有效；已给 VMX 异常控制不截获这次 #PF | #PF 交给 guest 处理 | guest #PF 不等于一次用户态 KVM_RUN 返回；不能只看 exception bitmap bit14，#PF 截获还涉及 page-fault mask/match |
| B：guest 页表有效且可访问，最终目标 EPT 不 present | EPT violation；在本例 #VE 关闭的前提下发生硬件 VM exit | 不证明应用非法、发生磁盘 I/O 或得到 KVM_EXIT_MMIO |
| C：guest 允许写，目标 EPT 是合法的 R=1/W=0 条目，实际发起写 | EPT write violation | R=0/W=1 属于非法编码问题，不能当普通只读条目 |
| D：可到达的 present EPT leaf，其余编码合法，memory-type bits=2 | 选定 SDM 版本下为 EPT misconfiguration | 与缺项/写拒绝不同；合法 PAT/EPT 内存类型不同本身不等于 violation |
| E：memslot 仍登记，宿主 backing 未驻留或发生变化 | 宿主 VM/KVM 需依具体状态协调；完成结果未给 | 不能据此断定 guest PTE 缺失、某个 errno、MMIO 返回或已经恢复 |
| F：只有 translation-cache miss，所需表和权限均有效 | 可通过走查完成翻译 | TLB miss 不必产生 fault，也不必产生 VM exit |

因此，A 的已有证据应对准 guest 页表和 guest 异常处理；B/C 对准 EPT 访问与控制；E 对准 host backing。先找到责任层，才能判断下一份记录会排除哪种解释。

观察边界与停止点：若多个条件同时失效，或缓存一致性、异常交付、#VE 控制没有给定，本例不能决定全局 fault 优先级。开启 #VE 且满足转换条件时，部分 EPT violation 可以交付 virtualization exception；本文没有给出完整 #VE 条件表。依据为 S1 §25.6.3、§29.3.3.1–.2、§29.3.7 与 S3 Events，以上不是故障注入结果。

## 退出到谁：硬件事件不等于用户态返回

在 QEMU/KVM 案例中，硬件 VM exit 先将控制交给内核 KVM。内核可以处理后再次进入 guest，也可以需要 QEMU 服务而返回用户态。四种信息必须分别记录：

| 信息 | 属于哪层 | 解释范围 |
|---|---|---|
| 硬件 exit reason/qualification | CPU/VMCS | 为什么发生这次硬件转换 |
| KVM handler/运行路径返回值 | 内核内部 | 当前分支继续、返回或失败；不是标准用户态 ioctl 返回值 |
| ioctl 返回值与 errno | 用户态 ABI | 本次 KVM_RUN 调用成功返回还是报错 |
| `kvm_run.exit_reason` 及对应数据 | KVM userspace ABI | 仅在该 ABI 规定的有效条件下解释本次返回 |

普通成功返回 0 时，`exit_reason` 说明用户态返回原因；错误返回必须检查具体约定，不能复用旧 union 数据。Linux v6.12 有一个明确的 MEMORY_FAULT 错误返回例外，见 P4 旁支。内核运行循环与用户态调用是不同粒度，一次调用可以跨越多次硬件 exit。〔S2 §4.10/§5、S4〕

退出成本也沿这条路径分解：硬件转换、内核处理、可能的用户态设备服务与调度、再次进入，各自可能付费。CPUID、I/O、EPT 等事件需结合控制和处理路径解释，不能只按名称给固定纳秒数。VMX transition 不要求无条件清空所有翻译缓存；“每次退出都重填全部 TLB”不是通用成本模型。virtio、批处理或后端卸载改变的是具体路径，收益仍需同工作量证据。〔S1 §29.1、S7〕

### P4：读数据返回了，guest 操作何时才算完成

输入：仅统计一个给定 vCPU 的合法抽象轨迹。第一次 KVM_RUN 中，硬件退出 H1/H2 都由内核完成并再次进入 guest；H3 是需用户态服务的单字节、非重复 port-I/O read，`size=1`、`count=1`，`data_offset` 和完整数据范围已核为有效。第一次标准 ioctl 返回 0，`exit_reason=KVM_EXIT_IO`，用户态在对应数据位置填入 `0x2A`。

填数据之后操作仍是 pending。v6.12 ABI 明确，这类 I/O 操作须再入 KVM_RUN 才完成，pending 状态不完整呈现在用户态可保存状态中；迁移前必须完成它。这里的第二次调用限定为 completion-only：完成旧指令留下的工作，不开始新的 guest 指令。〔S2 §5 IO/MMIO〕

第二次调用必须同时满足以下纸面输入，不能由返回的 errno 倒推它们成立：

1. 假设 `KVM_CAP_IMMEDIATE_EXIT` 可用，调用开始前 `immediate_exit=1`。本文没有查询此能力；该字段只在 KVM_RUN 开始时采样一次，运行途中仅改字段不保证立刻踢出。
2. 调用来自创建 VM 的正确地址空间，vCPU 有效，参数合法，没有并发运行同一 vCPU；已通过全部前置检查与锁，没有 VM 已死、抢锁中断、非法同步寄存器或其他提前返回。
3. 实际到达 `complete_userspace_io`，本次 pending callback 成功完成，不需要更多用户态设备服务，没有其他失败，并继续到 `wants_to_run` 检查。这是轨迹前提，不是一个用户态可查询的 completion ack。

| 步骤 | 状态变化 | PAPER_EXPECTED P4：累计计数 |
|---|---|---|
| H1/H2 | 内核处理后继续 guest | 硬件 exits=2，用户态 ioctl 返回=0 |
| H3 | 第一次 ioctl 返回 0/IO，等待用户态读数据 | 硬件 exits=3，ioctl 返回=1，有效 exit_reason=1 |
| 用户态填 `0x2A` | 数据已提供，操作尚未完成 | 计数不变，不能据此开始迁移 |
| 第二次调用走到给定 completion 路径 | 先完成 pending；随后因入口采样得到 `wants_to_run=false` 返回 | 内核返回 `-EINTR`；标准用户态 ioctl 返回 `-1`、`errno=EINTR` |
| 轨迹终点 | 没有再进入 guest 硬件执行，没有开始后续 guest 指令 | 3 次硬件 exits、2 次 ioctl 返回、1 次有效 exit_reason |

pending 指令的寄存器/RIP 等状态可在 completion 中完成，所以“没有更多 guest 指令”不等于 guest 状态完全不改变。第二次 EINTR 后若把残留 `exit_reason=IO` 再计一次，就虚增了设备返回。

更关键的反例是：只观察到 `-1/EINTR` 并不能证明 pending 完成。v6.12 的 vCPU ioctl 入口在取得锁时就可能提前返回内核 `-EINTR`，尚未到达 completion。MMIO 还可能分片，需要下一轮用户态服务；PIO completion 也可能回到 emulator。因而“一次再入必完成，EINTR 就是确认”的通用循环不成立。若考虑信号替代，须是 KVM_RUN 有效信号掩码下仍 pending 且未屏蔽的信号，并满足到达成功 completion 的全部前提；仅发送过信号不够，SIGKILL/SIGSTOP 仍保留原语义。

观察边界与停止点：更多设备服务、提前失败或实际完成协议未知时，停止套用 3/2/1 终点，不宣布可迁移或可回收。本文只解释 ABI 与指定路径，不实现 VMM loop。依据为 S2 §4.10/§4.21/§5、S4 的运行循环与 pending completion，以及 S5 vCPU ioctl 入口。

#### P4 旁支：错误返回中的 MEMORY_FAULT 有独立有效性合同

独立输入：假设有 `KVM_CAP_MEMORY_FAULT_INFO`；标准 KVM_RUN 返回 `-1`，`errno=EFAULT`，且 `exit_reason=KVM_EXIT_MEMORY_FAULT`；有效字段为 `gpa=0x4000`、`size=0x1000` bytes、PRIVATE 位清零。该能力是 informational，不是必须经 KVM_ENABLE_CAP 开启的开关，本文没有查询或启用它。

**PAPER_EXPECTED（P4 旁支）**：能力、错误返回/errno、reason 的联合条件满足，故可判读 `memory_fault` 给出的 GPA 范围 `[0x4000,0x5000)`，PRIVATE 清零表示 shared 访问。只将 errno 改为 EHWPOISON，其他条件不变，仍满足该 ABI 的有效性条件。这个记录说明 KVM 不能解决的相关内存 fault，不证明具体 VMA 根因、错误已经恢复或 pending I/O 已完成。〔S2 §5 MEMORY_FAULT、§7.34〕

反例：errno=EFAULT 而 reason 不是 MEMORY_FAULT，不能判读该 union；errno=EINTR 时，即使旧 reason 仍是 MEMORY_FAULT，也须按陈旧/未定义处理。其他 reason 在错误返回时不可默认有效。能力或返回约定不明、范围无法合法解释时，不套此分支。反复遇到相同 error/annotated fault，或没有已核的具体恢复协议时，停止继续执行、迁移、回收的推断，保留范围与错误；不无限重试相同 KVM_RUN。旁支没有扩大为 guest_memfd/机密 VM 实现，也不改变上面 IO/EINTR 轨迹的计数。

## 设备：CPU 访问 BAR 与设备 DMA 是不同方向

回到那次设备读：CPU 读设备寄存器，走的是 CPU 对 BAR/MMIO 的访问路径；设备为传送数据访问 RAM，走的是设备发出的 DMA；设备随后通知 CPU，又涉及中断路径。三者的地址、权限、路由与完成条件不能互相替代。给 CPU 映射了 BAR，不等于已经为设备 DMA 授权内存；出现中断也不自动证明全部在途 DMA 已停止。〔S6〕

在所选简单 IOMMU 模型中，设备发出 IOVA/设备可见 DMA 地址，选定 domain 将它转换为准许的 HPA。方向是 IOVA→HPA；CPU 使用的 HVA/GVA 不会直接成为设备 DMA 权限。IOMMU 映射解决特定地址范围和访问方向的问题，不能自动修复设备固件、共享队列或错误生命周期。

### P5：跨页不一定跨授权范围

输入：简单 flat IOMMU domain，无 ATS、PASID、嵌套或 passthrough。唯一映射为 IOVA `[0x4000,0x6000)` → HPA `[0x900000,0x902000)`，设备读允许、写不允许。

**PAPER_EXPECTED P5**：设备读 `[0x4FF0,0x5010)` 共 `0x20` 字节，偏移 `0xFF0`，对应 HPA `[0x900FF0,0x901010)`。请求虽然跨过 `0x5000` 页边界，仍完整位于 `0x2000` 字节的授权范围内。

反例：读 `[0x5FF0,0x6010)` 的最后 `0x10` 字节越出给定映射；在正例地址发起写又缺写权限。两者都不能由给定映射授权完整请求。选择映射时须同时对齐对象、完整区间和设备读写方向，而不只比较起始地址。

观察边界与停止点：这不是实际总线事务，不能推出跨界请求原子失败、零部分效果、固定 fault 日志，或设备已经能 reset/重分配。不用真实越界 DMA 证明纸算。依据为 S6 DMA guide:15–96、VFIO:35–75；未取得的 VT-d 规范不承担硬件 fault 细节。

### P6：一个 VF 不等于一个独立隔离域

输入是给定拓扑：group G={A,B}，另一 group H={C}。拟将 A 交给 VFIO owner X，而 B 仍由 native host driver 拥有 DMA。采用 Linux v6.12 cdev/IOMMUFD，所需 CONFIG 条件作为已具备的假设，不读取 sysfs，也不绑定设备。

**PAPER_EXPECTED P6**：G 不满足这种拆分的单一 DMA owner 要求。即使 A 是 SR-IOV VF，也不能改变结论。cdev 通过 BIND_IOMMUFD 取得 DMA ownership，虽不依赖旧 group/container 驱动接口，仍受 group 语义约束；替换接口不是取消隔离粒度。〔S6 VFIO:269–299〕

反例：C 独占 H 只能支持“Linux group 不同”，不能证明它不与 A 共享 PF 固件、reset、总线或带宽。A/B 同属一个 owner，也不等于它们已能安全交付租户。SR-IOV 的最大 VF 能力、已创建 VF 数、驱动绑定、实际分配状态分别回答不同问题；队列数、RSS、带宽、中断与 reset 需具体设备资料，不能由另一块 NIC 的记录推断。

正向选择：若目标是两个互不信任租户，给定 G 无法承担 A/B 拆用目标，应评估满足所需 group 与设备合同的硬件，或合适的虚拟设备方案。group 所有权之后仍需分别核对 reset 影响范围、中断隔离、驱动/固件、共享资源和回收完成条件。

观察边界与停止点：缺少这些条件，结论停在“不能证明分配/移交成立”。不创建 VF、不改分组、不重绑驱动，也不将独立 group 宣称为无侧信道或安全认证。依据为 S6 VFIO Groups 与 Device cdev。

### 用业务目标选择设备路径

需要通用 guest 接口、可管理机型和有支持的迁移路线时，先评估 guest 有适合驱动的 virtio 设备；若镜像只能识别某种传统模拟设备，则先解决兼容性，再讨论性能。virtio 不是零 exit，vhost 等卸载也只是改变处理责任的位置。原 virtio/IDE、CPUID/I/O 比较要回答的，正是 P4 的路径与 P9 的业务代价，而非哪种名称天然更快。〔S7〕

需要特定硬件功能或队列时，可以评估 VFIO/SR-IOV 直通，但要把 group ownership、设备恢复、固件、监控和迁移支持一并纳入成本。直通减少某些设备模拟工作，不证明生产总成本最低；也不能不看具体支持就说所有直通都可迁移或都不可迁移。条件无法满足时，虚拟设备路径往往更容易满足可管理性目标；实际性能方向仍待同工作量证据。

## 资源：页粒度、CPU 归属与容量各算各的

guest 页大小、host backing 粒度、实际 EPT leaf 大小是三个变量。guest 使用 hugepage，不能直接推出 EPT 已安装同样大小的 leaf；host THP 也不是 EPT 状态记录。所选 KVM MMU 文档描述 large SPTE 的 host page、写保护和 slot 覆盖条件，且对 TDP 明确排除了“guest PTE 必须至少同大”的限制；不能把 shadow paging 条件无差别套到 EPT。〔S2 §4.35、S3 Large pages〕

### P7：算覆盖叶项，不把数量比当速度比

输入 A/B：一个 16 MiB 区间，对齐、物理连续性、权限和 memory-slot 条件均给足；A 的实际 EPT leaf 明确为 4 KiB，B 明确为 2 MiB。

**PAPER_EXPECTED P7**：A 需 `16×1024×1024/4096=4096` 个覆盖叶项，B 需 `16/2=8` 个。它们只数表示该区间的叶映射，不含非叶表页，也不是 page-walk 实测次数。

独立输入 C：一个 1 GiB 完全对齐区间，分别假设支持且已合法安装的实际 EPT leaf 为 4 KiB、2 MiB、1 GiB。对应覆盖叶项分别为 262144、512、1；1 GiB 支持是给定条件，不是所有 CPU 的事实。

反例：只给“guest hugepage=2 MiB”或“host THP=2 MiB”，没有实际 EPT leaf，就不能选上述计数。对齐、slot 边界、backing、写保护及 dirty tracking 可能影响实际映射；文档选段不是所有版本实现条件的穷举。

正向选择与边界：目标是减少翻译表示开销时，先确认合法覆盖与实际 leaf，再权衡碎片、共享、回收和 dirty-tracking 代价。`4096/8=512` 不表示 512 倍速度，不保证 fault 更少或回收更好。需要弹性内存时，不能仅因叶项更少就选择更大粒度。此例不切 THP、不预留页或运行 PMU。依据为 S1 §29.3.2、S2 §4.35、S3 Large pages。

THP、KSM、balloon/free-page reporting 和预分配仍是有用的选题，但回答的问题不同：THP 涉及 host backing 粒度；KSM 涉及共享；balloon 与相关 guest 驱动涉及归还/回收和容量；预分配涉及启动时付费、内存占用与运行时按需准备的取舍。本次未核这些实现的完整条件，不教具体设置或保证收益。内存加密/机密 VM 则另有信任、调试、迁移和设备合同，不能由内存保护推出全部 I/O、快照、管理面和侧信道都受保护。

### P8：pinning 固定的是哪一个对象

输入：CPU0/1 是同一物理 core 的 SMT siblings，都属于 node0；vCPU0 允许运行集合={CPU0}；其 backing 页位于 node1；emulator、I/O thread、IRQ 归属未给。

**PAPER_EXPECTED P8**：这里只收窄了 vCPU0 的允许 CPU 集合，既没有保证它持续获得 CPU，也没有排除 CPU1 对同核资源的竞争。backing 在 node1，不能从 pinning 推出内存本地；emulator/I/O/IRQ 的位置仍未知。

正向对照：另给 vCPU0 一个独立可用 core、backing 位于对应 node0，相关线程归属也明确，便可判断设计中的资源归属已对齐；要称更快，仍需同业务工作量与计时证据。只绑定一个逻辑 CPU 就声称独占物理核，漏掉了 SMT；将 emulator/I/O thread 等同 vCPU，又漏掉了执行对象。

观察边界与停止点：亲和性、housekeeping、SMT、频率、host 噪声及内存政策是不同条件；扩大绑定可能减少调度弹性或转移竞争，不能自动作为异常修复。拓扑未知不等于拓扑不存在，本文不改这些设置。CPU/cache/NUMA/PMU 的主责见[处理器存储层次与性能工程](01-处理器存储层次与性能工程.md)，普通 VMA/mmap/backing 见[虚拟内存、PageFault与mmap](../操作系统与系统I-O/02-虚拟内存、PageFault与mmap.md)。

## 观察：同一个计数，换分母就换了问题

vCPU 是可调度执行实体，不等于独占物理核。过量分配可能引入等待，但容量判断仍须把成功工作、请求延迟、线程调度、backing 和设备等待分开。宿主总体 CPU 利用率、guest 的 iowait、emulator CPU 成本或某个 steal 数，都不能单独替代客户机可用算力和 P99/P999。

计时也先定域。测间隔需明确定义单调时钟域和起止事件；host 与 guest 时间戳、wall clock 校正、暂停时段不能未经对应直接相减。TSC offset/scaling、kvmclock、HPET/PIT/APIC timer 的具体实现和迁移连续性未在本次选读中核全，这里不提供配置。否则一次时钟校正就可能被误记为服务停顿。

### P9：exit/s 更高，也可能每个请求退出更少

输入：窗口 A 在 10 秒内完成 1000 个等价成功请求，hardware exits=3000；窗口 B 在 5 秒内完成 2000 个相同定义的成功请求，hardware exits=4000。对象均为同口径目标 VM/vCPU，成功终点一致，时间窗已定义；没有真实日志。

| 窗口 | PAPER_EXPECTED P9：exit/s | exit/成功 request | 成功 request/s |
|---|---:|---:|---:|
| A | 3000/10=300 | 3000/1000=3 | 1000/10=100 |
| B | 4000/5=800 | 4000/2000=2 | 2000/5=400 |

B 同时具有更高 exit/s、更低 exit/request 与更高吞吐。没有各次处理耗时和请求延迟分布，不能按退出频率说 B 性能退化；也不能反过来用吞吐证明尾延迟改善。userspace returns 要独立计数，不能用 hardware exits 替代，原因见 P4。

另给同一 vCPU 的两份 steal 快照：每份都按读取前后相同且为偶数的 `version` 取得有效值，累计 steal 从 100000000 ns 到 160000000 ns；与之对应的宿主测量窗口为 1 s，归属关系已给定。静态推导得到增量 60000000 ns=60 ms，“报告的 steal 增量/该窗口”为 6%。Linux v6.12 x86 ABI 的 steal 不包含 idle 时间，更新间隔由实现决定；因此 6% 只是给定记录口径的比例，不是精准业务不可用率、请求尾延迟或该窗口全部未运行时间。〔S8〕

反例：steal=0 只说明该计数没有报告损失，不能推出独占物理核、全窗口执行、没有排队或设备等待。其他产品的 ready time 不能不看定义就替换 steal。version 为奇数或前后改变、计数重置、窗口不同或 guest/host 时间域未对应时，不能照算差值。

正向选择与停止点：先按同等成功工作归一化，再对齐 exit、host 调度、guest/host fault、设备 fault 与业务延迟，判断哪层变化能解释目标。计数定义、错误样本或终点未知时，保留未知，不用全机采样、加重复或删除慢样本填空。依据为 S8:259–304 和 P4 的返回层级；本例没有实现采集器。

### 六类性能问题仍须各自定义终点

以下是解释已有记录的合同，不是要在共享宿主跑完的 benchmark 矩阵。比较 bare-metal/宿主基线时，也须先确认业务工作和完成语义相同；否则只能展示不同路径，不能归因全部虚拟化开销。

| 场景与决策目标 | 记录中必须对齐的条件 | 可以解释什么；什么还不能判断 |
|---|---|---|
| CPU：业务吞吐与尾延迟 | 相同成功工作、vCPU/线程对象、CPU 型号、微码、频率、SMT、调度窗口 | P8/P9 可拆归属与分母；exit 数或 steal 不代替延迟分布 |
| 内存：翻译与容量代价 | guest/host/EPT 三种页口径、工作集相对 cache/NUMA 的位置、vCPU 数、驻留/故障类别 | P2/P3/P7 可分翻译与缺页；叶项数不等于带宽或 cache miss |
| 块存储：请求何时完成 | 相同读写比例/块大小/工作量，队列深度，缓存/direct 策略，完成端点是 guest 应答、后端完成还是持久化 | 可比较同端点 IOPS/延迟；guest 应答不自动证明已持久化。fio 的 ioengine/iodepth/direct 字段细节须另核 |
| 网络：数据如何送达 | bytes 与 packets、包大小、发送/接收端点、丢包/重传、CPU/软中断成本、时间窗 | Gbps 与 pps 是不同分母；吞吐提高不证明丢包/尾延迟改善 |
| 启动：多久提供服务 | 同镜像/机型、预分配或按需策略，起点与“guest 启动完成/服务就绪”终点 | 启动缺页代价不能混成运行请求尾延迟；未就绪不报成功启动 |
| 迁移：完成期限与暂停预算 | 总时长、guest 暂停、服务恢复、发送字节/带宽、dirty rate、设备与 pending 状态 | P10 可按目标选择；短暂停不证明收敛或恢复正确 |

工作集、vCPU 数、4 KiB/2 MiB/1 GiB、样本数与预热都用于识别变量和偏差，不是必跑组合；任意“至少 10 次”不能保证统计有效。真实不稳定结果需解释分布、失败样本和环境变化，增加预热或 CPU 隔离不应自动替代调查。本文没有核对 perf/libvirt/fio/流量发生器的具体字段与平台事件支持，缺字段不能被补成 0 或成功。

## 迁移：暂停结束与工作完成是不同终点

迁移要保存、传输并恢复 guest/设备状态。大状态可以迭代传输，部分剩余设备状态在 CPU 暂停时完成，因此 guest 暂停只是总过程的一部分。CPU/机型/设备兼容、backing、在途 I/O、源目标信任和恢复业务正确性，都必须进入“成功”的定义；P4 的 pending 状态没有完成时，用户态已拿到读数据仍不足以形成一致快照。〔S7 Migration、S2〕

### P10：同一组时间，两个业务目标

输入：相同工作量与服务口径；方案 A 总迁移 20 s、guest 暂停 0.2 s；B 总迁移 8 s、guest 暂停 0.3 s。CPU/device/机型兼容、backing、pending I/O 完成、迁移状态完整性与恢复业务正确性均为已给前提，两边时钟口径对应。没有真实迁移输出。

**PAPER_EXPECTED P10**：A 的暂停更短，B 的总时长更短。若唯一硬约束为 pause≤0.25 s，其他条件满足，则 A 符合、B 不符；若唯一硬约束为 total≤10 s，则 B 符合、A 不符。两项硬约束同时要求时，两者都不符合，不能强选一个。

这也是一份有值的纸面记录：A/B 对象、成功终点和窗口口径来自输入，暂停与总时长分别为 0.2/20 s 和 0.3/8 s；迁移字节、带宽、dirty rate、请求延迟分布在本例未给，不能补造。P9 则记录的是成功请求数与硬件退出数，两类记录不能互换。

反例：把 0.2 s 当总迁移时间，会漏掉预复制等工作；只凭较短暂停判 A 成本更低，也忽略总占用。短暂停不保证脏页收敛，guest 恢复执行不自动等于服务就绪。选择时须按暂停预算、完成期限、资源占用和请求影响权衡，而非固定偏爱某个指标。

观察边界与停止点：实际记录若缺 pending completion、设备状态/兼容、backing 或恢复正确性，便不属于上述成功样本，不能宣布迁移成功或回收源端。本文不提供迁移命令、脏页负载或自动重试。依据为 S7 Migration:1–30、69–105、474–518 与 S2 pending 说明。

## 生命周期：还活着、可访问、已完成是三件事

VM/vCPU/device 文件、`kvm_run` 映射、普通 memslot backing、设备与 DMA 各有拥有者和寿命。fd 是资源访问入口，但 fd 还在不保证 backing 永远有效，fd 关闭也不证明所有访问和设备动作结束。API 的“VM 寿命不只由创建进程决定”要结合对象引用与地址空间实现来理解，不能读成一条万能回收规则。〔S2、S5〕

### P11：两份 VM fd 不是全部资源账

输入：同一 VM 文件有 A/B 两份引用，A 关闭自己的那份，B 仅持有引用；不假定 B 可跨 mm 操作 VM。vCPU 将不再执行新的 guest 指令，但独立的 device/DMA 状态未知；还可能存在 vCPU/device/stats 文件和 mmap 访问者，数量没有穷举。

**PAPER_EXPECTED P11**：B 仍持 VM 文件引用，不能宣称 VM 对象已销毁。这只是 VM 文件引用的局部事实，不是整个 VM 的 `users_count` 账。即使改输入为两份 VM fd 都关闭，只要 vCPU/device 等关联文件仍持 VM 对象引用，也不能推出对象已销毁；VM file release 只放掉自己那一份引用，`users_count` 归零才触发 destroy。stats fd 是还存在其他持有者的反例，不能把列出的三类 fd 当穷举。〔S5〕

引用与调用资格也不同：API 不保证 fork/SCM_RIGHTS 迁移 fd 后的那些跨进程用法，当前源码检查创建者 mm。B 仅持有引用，不能据此推出它在另一个地址空间可以继续发 VM/vCPU/device ioctl。〔S2 General description/File descriptors、S5〕

KVM 的 `mmgrab` 保持创建者 `mm_struct` 结构，不保证关联用户地址空间继续存在；即使 `mmget` 保住地址空间，其中的部分也仍可能被修改或释放。普通 memslot 指向的 VMA、backing、驻留与物理页有效性须另行维护，不能由“VM 对象活着”推出内存已钉住或访问完成。`kvm_run` 等 mmap 又是独立访问路径，所有相关访问者须停止并协调；本次只核 KVM 侧 mmap/fault 路径，没有审完整通用 VMA/file/fput 生命周期。〔S5，S2 §4.35〕

正向完成条件是各负责人分别交付证据：

- 不再开始新的 guest 指令；仍允许 ABI 所需的 completion-only KVM_RUN
- pending 确已完成，排除仍需用户态服务或提前失败；P4 的 EINTR 本身不是确认
- 设备不再发起相关 DMA，已发起访问的完成或停止状态满足该设备合同
- 映射可依各自合同撤销，访问者已退出，实际拥有的引用已按相应接口释放

这是条件集合，不是所有设备通用的 close/unmap/reset 顺序。反例是禁止一切 KVM_RUN，从而阻止必要的 pending completion；另一个反例是把 VM 对象消失当 DMA 已结束，进而复用内存或移交设备。CPU/KVM 回收与设备安全移交有不同后置条件。

观察边界与停止点：DMA 状态未知、还有设备服务、引用/访问者未盘清、backing 有效性未确定时，不宣布安全回收、迁移或可交新租户，不自动 reset/重绑/重试。依据为 S2:21–72、1373–1395、6616–6629，S5 的 get/put、mmap/fault、mmgrab 与 mm 检查。

## 从症状找到证据，缺一层就停在那一层

下表给已有材料的判读路线。未知、拒绝、错误、缺记录、版本或对象不匹配都保留原状态；“需要某类证据”不等于授权新实验、提权、改配置或故障恢复。

| 症状 | 待区分的层与已有证据 | 能得出的判断与停止点 |
|---|---|---|
| `/dev/kvm` 缺失或不可访问 | 节点、内核支持、固件与当前主体访问记录分别核对 | 单个路径不足以定位原因；没有证据就不推断应加载模块、改固件或权限 |
| EPT/NPT 未可用 | 架构/能力/配置与具体 VM 的资料 | shadow paging 与硬件 TDP 不同；未知不等于缺失，不自动切参数 |
| exit 计数偏高 | 硬件 exit 还是 userspace return，哪台 VM/vCPU、哪个窗口、每单位工作多少 | 按 P4/P9 分层；不能据总数直接改 virtio、APICv 或调试设置 |
| P99/P999 抖动 | 同请求定义，CPU 等待、SMT、backing、host 噪声及设备记录 | P8 的归属只给候选解释；缺时间关联不能声称因果或自动绑核 |
| IOMMU fault | 设备、domain、IOVA 范围、方向与时间；reset 状态另列 | 可定位映射合同问题；不由 fault 日志推断零部分效果，不回放 DMA |
| VF 没出现 | 最大支持、已创建、绑定与分配四种状态及设备资料 | 少一项就保持未知，不写创建数量或重绑驱动 |
| 时钟跳变 | guest/host 时钟域、校正与迁移记录、计时终点 | 先排除口径混用；不自动调整 NTP/TSC/timer |
| 迁移失败 | P4 pending、CPU/device/机型兼容、backing、dirty rate、源目标状态 | 缺恢复正确性就不算成功，不按短暂停自动重试/回收 |
| 容器性能异常 | [Linux 权限与隔离](../操作系统与系统I-O/04-权限安全与隔离.md)及[进程、线程与调度](../操作系统与系统I-O/01-进程线程虚拟内存与系统调用.md)所负责的限流、归组与调度证据 | 不混成 guest 的 EPT/VM exit 问题；不在本篇复制或更改宿主资源政策 |
| 安全告警 | hypervisor/QEMU、设备/IOMMU、管理面和审计记录的对象、时点、可信来源 | 只定位责任与待补证据；实际隔离 VM/设备、销毁或恢复须具体事件方案，告警不是本文自动动作 |

### 安全目标落实到具体责任者

威胁模型要先说清是否防恶意 guest、guest 内核、外部输入、设备固件或侧信道。固件/微码与 hypervisor/QEMU 版本支持复核 CPU 与软件边界；精简设备面减少可达接口；进程最小权限与 Linux 安全机制约束 QEMU 逃逸后的宿主权限；管理网络、认证与 socket 访问保护控制面。这些是不同责任，不能因 VMX 已开启就一并打勾。〔S7；Linux 权限主责见前文链接〕

迁移流的认证/保密与目标主机信任、快照/core dump/调试日志中的敏感信息，又属于传输和持久材料责任。设备面则需 P5/P6 的 DMA、group、中断与固件证据，并在 P11 分别确认停止与回收。一次清单完成不等于安全认证，本篇也未核具体加密、reset 或中断重映射配置。

| 阶段 | 要回答的问题 | 相应证据与未满足时的边界 |
|---|---|---|
| 设计 | 威胁主体、隔离目标与业务完成终点是什么 | 评审中的对象与合同；没有目标就不能比较“更安全/更快” |
| 采购 | 所需 CPU/IOMMU/设备能力是否属于该型号与版本 | 对应厂商规格；不能用别机 feature 字样替代 |
| 部署 | 哪个软件/固件/机型/设备合同实际生效 | 已有配置快照与版本；磁盘配置不证明运行态 |
| 运行 | 哪个 vCPU、backing、设备属于谁 | 对象映射与有效状态；名称相同不保证同一实例 |
| 观测 | 计数、窗口、成功终点与失败样本能否对应 | P9/P10 的分母和终点；缺数据不补造 |
| 升级 | 源目标兼容与恢复路线是否有具体证据 | 对应版本记录；旧演练不承诺新版本成功 |
| 退役 | pending、DMA、映射/访问者、引用和持久资料分别结束了吗 | P11 完成条件及实际销毁记录；关闭 fd 不代替设备或数据回收 |

## 学习顺序与可复核记录

正常学习顺序是：用 P1 定执行身份，用 P2/P3 画地址与故障责任，用 P4 分清硬件与用户态返回，再用 P5/P6 判断设备权限和所有权；P7/P8 处理资源归属，P9/P10 按工作与终点选择，最后用 P11 解释完成和回收。每例都应先由输入写出推导，再改变一个前提，指出结论在哪一步失效。

静态验收看能否解释以下问题：guest CPL0 为什么不等于宿主控制；guest 页表遍历为何也涉及 EPT；哪个返回字段现在有效；读数据何时完成；给定 DMA 区间与 group 是否满足合同；哪一种页、哪一个线程和哪一种完成终点正在计量。单个 exit reason 只提供路径线索，不能独立解释性能回退；给定 group 只供判读，不要求证明真实硬件分组。无需创建最小 VM、跑完整 benchmark、做越界 DMA 或故障注入才能完成这轮学习。

复核记录应标来源/版本、输入、对象、单位、时间域、起止与成功终点、推导、反例、缺失/错误和未验证边界。P9/P10 中已填的数值全部是假想输入；操作者、实际宿主/guest、原始输出、运行提交、命令与分析程序在本次均为未运行或不适用，不填虚构值。以后若另有明确授权的真实观察，应保留原始 CSV/输出、环境与失败样本，不能只保存结论图；本篇不提供或启动该执行流程。
