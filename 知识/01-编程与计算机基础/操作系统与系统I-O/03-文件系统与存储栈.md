# 文件系统与存储栈

> 知识成熟度：L2。主要承诺是存储责任链、接口语义和选择方法的原始资料核对；一个有限例的正常运行不代表整篇实现、性能或掉电恢复已验证。
> 资料基线：Linux 6.12 文档、Linux man-pages 6.19、fio 3.42、sysstat 12.8.0 及 Little 2011 原作者论文。资料版本与本机运行版本分别记录；核对范围见文末。
> 本次修订：2026-10-06。适用讨论以 Linux 普通文件、本地文件系统、唯一写者为主；网络/叠加文件系统、设备文件、多文件事务和物理故障保证不能直接套用示例。

## 1. 先问配置更新要承诺什么

设服务读 `live` 中的一份配置。写者准备新配置时，至少有四件不同的事：应用交出的字节被接受；后来打开这个名字的读者见到新对象；请求的文件和目录同步成功返回；发生指定故障后，恢复程序能取回并接受那一代数据。把这四件事合成一个“写完”会让接口选择和性能测量同时出错。

直接把旧 `live` 截短后分段写新内容，读者可能看见更新中间状态。一个更合适的单文件换代设计是：在同一目录准备完整新对象，检查写入与同步，再用 `rename` 替换 `live`。名字的切换解决新打开者的视图；此前已打开的 FD 继续引用旧对象。如果还要向调用方确认持久化，就须处理文件内容、目录名字及已经持久的祖先路径这些独立责任。运行中能重新读到数据，不能代替这些同步合同。[rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)、[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)

本文用这个问题贯穿全栈：先确定对象和完成点，再选择写法，最后确定哪些指标能回答问题。后文的阶段表是应用协议推导；有限 C 例只观察当次接口返回和旧 FD/新路径的视图，不模拟掉电。

## 2. 从路径找到对象，从对象访问数据

### 名称链与打开引用

路径解析要结合进程看到的挂载关系逐级查找目录。VFS 用 dentry 缓存名字查找结果，用 inode 表达具体文件对象的类型、权限、大小等状态，用 superblock 表达一个文件系统实例。RAM 中的 dentry 缓存与文件系统保存的目录项不是同一份持久数据；同步目录不是要求把整个 dentry 缓存原样写盘。[Linux 6.12 VFS：dcache、inode、superblock](https://docs.kernel.org/6.12/filesystems/vfs.html)

`open` 成功后，进程取得 FD，它是进程描述符表中的整数索引，0 也合法。FD 引用 open file description（OFD，Linux 中与 `struct file` 对应），OFD 保存文件偏移和打开状态标志，并持有文件对象引用。`dup` 或 `fork` 后的描述符可共享一个 OFD；对同一个名字再 `open`，通常得到新的 OFD，各自有偏移，却可以引用同一个 inode。这就是“FD、OFD、inode”不能互换着说的原因。[open(2)：Open file descriptions](https://man7.org/linux/man-pages/man2/open.2.html)

正常 `read`/`write` 使用已经打开的引用，并非每次重新解析当初的路径字符串。因而名字替换后，旧 FD 仍能读旧代；删除最后一个名字也不等于仍打开的文件对象立即消失。最后名称和打开引用都释放，才满足该类对象回收的条件，实际空间统计仍受文件系统机制影响。[unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)

### 数据链及其分支

|责任层|处理的对象与工作|向下一层不能偷换的保证|
|---|---|---|
|应用与系统调用|确定目标 FD、字节、偏移、错误处理和业务完成点|一次正返回只覆盖实际返回字节数；业务确认需要自己的协议|
|VFS 与文件对象|把打开引用分派给具体文件系统操作；关联 inode 和缓存|统一接口不意味着各文件系统所有内部算法相同|
|page cache / address_space|普通 buffered I/O 访问文件关联的缓存页；写入可使页变脏|缓存命中可不产生设备请求；脏页不等于已持久|
|具体文件系统|处理目录、分配、文件块映射、元数据及回写/恢复规则|extent 或 journal 是具体机制，不是所有 VFS 对象都必有的结构|
|块层|把 bio 组织成 request，经软件/硬件队列，可能合并或拆分|应用一次 I/O 与设备一次请求不是一一对应；完成也没有通用全序|
|驱动与设备|转换并提交命令，处理完成与设备缓存合同|设备普通写完成、易失缓存刷新和持久化完成须按合同区分|

文件系统的 extent 用连续区间描述映射，避免对连续大文件逐块保存同样规模的映射条目；例如 ext4 的 extent tree 就承担这项工作。设备内部又是另一层：传统固件管理的 SSD 通过 FTL 做地址重映射、垃圾回收与磨损均衡，文件系统看到的连续逻辑块不等于掌握 NAND 内部布局。二者的元数据/回收成本应分层分析，不能用一个 journal 名词包办。[Linux v6.12 Extent Tree](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/filesystems/ext4/ifork.rst)、[Geriatrix，USENIX ATC 2018，§3 Device aging](https://www.usenix.org/system/files/conference/atc18/atc18-kadekodi.pdf)

这是一张责任图，不是所有 Linux 版本都逐项经过的内核函数调用图。buffered 读命中页缓存时可以跳过块层；`O_DIRECT` 改变数据缓存路径，但仍依赖文件系统，且不自动提供同步持久性；tmpfs 使用内存并可利用 swap，其文件数据不走普通磁盘文件的同一条链。路径位于 `/tmp` 本身不能判定它是哪种文件系统。[VFS：address_space](https://docs.kernel.org/6.12/filesystems/vfs.html)、[blk-mq](https://docs.kernel.org/6.12/block/blk-mq.html)、[tmpfs](https://docs.kernel.org/6.12/filesystems/tmpfs.html)

普通 buffered 写先在缓存中更新，文件系统随后回写。聚合小写入可能省请求，也可能因内存/脏页限额让写者等待。后台回写阈值与促使写者参与回写的阈值不同；`dirty_background_bytes/ratio`、`dirty_bytes/ratio` 分别有对应关系，设置一方会使相应另一方失效。ratio 基于可用于这类计算的可用内存，不是把机器总 RAM 简单乘一个百分比。不能从一次 `write` 很慢就直接断言介质很慢。[Linux 6.12 vm：dirty 参数](https://docs.kernel.org/6.12/admin-guide/sysctl/vm.html)

设备还可能把数据保存在易失写缓存中。Linux 块栈用 flush/FUA 等机制表达此前写入刷新或本次请求完成的持久要求，并依赖映射层与驱动正确传播。这里只说明合同；没有核验某个 NVMe/SATA 固件或设备断电行为。[Linux v6.12：writeback cache control](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/block/writeback_cache_control.rst)

## 3. 把接受、同步和发布拆成接口合同

|操作|成功时可以说什么|仍须处理什么|
|---|---|---|
|普通 `write(fd, p, n)` 返回正数 k|本次接受 k 字节，应推进 k 后继续剩余部分|短写不是全部成功；不能据此确认掉电安全；错误可延后到后续写、同步或关闭|
|`fsync(file_fd)` 返回 0|文件数据及关联元数据的同步请求完成，等待设备报告完成|不自动同步父目录中的名字；依赖文件系统/块栈/设备兑现合同|
|`fdatasync(file_fd)` 返回 0|同步数据及后续取回数据所需的元数据|不是“完全不写元数据”；文件大小通常不能省略，也不代替目录同步|
|Linux `close(fd)`|释放描述符引用；错误仍应记录|不是提交点；不能因为错误就盲目再次关闭同一整数 FD|
|同目录 `renameat(dir, next, dir, live)` 返回 0|在运行中的命名空间发布新 `live`|旧打开引用不切代；持久化需另处理文件与目录；不能跨挂载点套用|
|`fsync(dir_fd)` 返回 0|对该目录请求的同步完成|新建该目录的父目录项、祖先路径和设备合同仍是完整路径承诺的前提|

依据：[write(2)](https://man7.org/linux/man-pages/man2/write.2.html)、[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)、[close(2)](https://man7.org/linux/man-pages/man2/close.2.html)、[rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)。表述限定这些 Linux 接口；不能据 Linux 手册的标准标签声称已经直接核完 POSIX 原文。

对本文固定普通文件写入，正短写按实际数量前进；调用返回 `-1/EINTR` 时按未接受字节处理。示例每次 helper 累计只允许 8 次 EINTR 重试，不因中途有进展而重置；写 0 被应用转成 `EIO`，避免无进展循环。这里的预算和停止策略是教学设计，不是所有 I/O 的通用重试规则。文件同步遇任何错误即停止，不无限重试。

Linux 的 `close` 错误通常发生在描述符已释放之后；重试可能关闭被复用的另一资源。示例先把拥有者槽置为 -1 再关闭一次，保留错误诊断。Linux 的 EINTR 关闭行为与手册描述的 POSIX.1-2024 要求有差异，跨平台代码应重新审合同，不能机械搬用本例。

### Direct I/O 是缓存选择，不是提交协议

`O_DIRECT` 不等于 `O_SYNC`，更不等于目录项持久化。对齐要求随内核、文件系统与文件而变；不支持可能在打开时失败，错位可能报 `EINVAL` 或回到 buffered 路径。因此“设置 direct 成功”还不是实际路径和持久性证据。[open(2)：O_DIRECT](https://man7.org/linux/man-pages/man2/open.2.html)

Linux 6.1 起可向 `statx` 请求 `STATX_DIOALIGN`，但必须检查返回的 `stx_mask`。没有返回该位表示没有取得信息，不能解释为无约束；该位存在且相应对齐字段为 0，按所读接口表示该文件不支持 direct I/O。缓冲地址、偏移和长度要按实际返回合同处理，不能固定套 512 或 4096 字节。Linux 6.14 后的单独读对齐字段也不能写成 6.1 已有。[statx(2)：DIOALIGN](https://man7.org/linux/man-pages/man2/statx.2.html)

## 4. 同目录替换：先给每个阶段命名

假设唯一写者在稳定且独占的目录中操作普通文件，后来读者通过重新打开 `live` 取得当前代。替换已有目标时，`rename` 的运行期原子性使新打开者不会遇到“先删除旧目标、还没放入新目标”的缺名窗口；旧 FD 不受影响。源名与目标名短暂同时指向新对象的窗口也不破坏这个目标名保证。它不是给所有文件系统内部步骤建立全序，更不是通用崩溃结果全集。[rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)

|阶段|程序已知状态|出错后的责任|
|---|---|---|
|准备 `live=old`，文件同步、关闭、目录同步|仅当这些调用都成功才完成本例旧代初始化|任一步失败不开始替换；不能把部分旧内容称作可用基线|
|打开并持有旧 reader|旧 FD 引用旧对象|后面名字变了也不主动把它换成新对象|
|创建 `next`，写完整、文件同步、一次关闭|新对象已完成这些请求，但尚未发布|失败保留当前名字供检查，不调用 rename|
|调用 rename|调用前记录“已尝试”；成功立即记录“已发布，持久性未确认”|失败记录需检查，不无限重试；成功后的错误不能再声称“未发布”|
|同步替换目录|成功才记录“文件和目录同步调用已接受”|若失败，live 已在运行中发布；保留名字，停止承诺，不盲目 rollback|
|重新打开 live，对照旧 FD|新路径读新代；旧 FD 读旧代|读取或检查错误不撤销已经发生的发布|
|关闭读 FD、移除自己的 live、关闭目录、移除空目录|每步成功后才前进|清理是另一组有状态操作，不能把已删名称说成仍保留|

rename 返回错误时，本例用保守标签要求检查，并不主张受控本地文件系统可以任意破坏旧目标；例如 NFS 有服务端已生效但客户端收到失败的特殊情形，不能把本地正常路径结论外推过去。本例本身不验证网络文件系统。

### 一个完整、有限的 Linux C 例

只接受零参数；任何附加参数在文件操作前拒绝并返回 64。调用方须提供可信、独占、可写且执行期间不被移动或替换的 CWD。程序用 `mkdtemp` 创建一个 0700 随机子目录，两个文件请求模式 0600（仍受 umask 限制），只有 `live`、`next` 两个自建普通文件对象，各写 `old\n`、`new\n` 的 4 字节，不含字符串结尾 NUL。没有路径、尺寸、循环次数输入，也没有多写者、线程、映射、设备或通用 WAL。[mkdtemp(3)](https://man7.org/linux/man-pages/man3/mkdtemp.3.html)

`dir/file/old/current` 是四个拥有者槽；`file` 顺序复用作两个写 FD，正常累计五次打开，同时最多三个本例 FD。`pread` 用显式偏移读最多五字节，要求恰好四字节且遇到 EOF，因此不仅检查前四字节相等，也拒绝截断或额外尾部。[pread(2)](https://man7.org/linux/man-pages/man2/pread.2.html)

```c
/* Linux-only API demo: single owner, trusted exclusive working directory.
 * Creates one private directory and only two fixed four-byte file objects.
 * This is an API/ownership demo, not a power-loss or durability test.
 */
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

/* Invalidate ownership before close; Linux close errors must not be retried. */
static int close_owned(int *fd)
{
    int n = *fd;
    *fd = -1;
    return n < 0 ? 0 : close(n);
}

static int write_four(int fd, const char data[4])
{
    size_t done = 0;
    unsigned interrupts = 0;
    while (done < 4) {
        ssize_t n = write(fd, data + done, 4 - done);
        if (n > 0) { done += (size_t)n; continue; }
        if (n < 0 && errno == EINTR && interrupts++ < 8) continue;
        if (n == 0) errno = EIO; /* No progress is an error, not an endless loop. */
        return -1;
    }
    return 0;
}

/* A four-byte object must match exactly, including EOF at byte four. */
static int matches_four(int fd, const char expected[4])
{
    char bytes[5];
    size_t done = 0;
    unsigned interrupts = 0;
    while (done < sizeof bytes) {
        ssize_t n = pread(fd, bytes + done, sizeof bytes - done, (off_t)done);
        if (n > 0) { done += (size_t)n; continue; }
        if (n == 0) break;
        if (errno == EINTR && interrupts++ < 8) continue;
        return -1;
    }
    if (done != 4 || memcmp(bytes, expected, 4) != 0) {
        errno = EIO;
        return -1;
    }
    return 0;
}

int main(int argc, char **argv)
{
    char directory[] = "./storage-demo-XXXXXX";
    int dir = -1, file = -1, old = -1, current = -1;
    int made_directory = 0, removed_directory = 0;
    const char *stage = "argument check";
    const char *publication = "replacement not attempted";
    int saved_error;
    (void)argv;
    if (argc != 1) {
        fputs("usage: replace-owned-demo (no arguments)\n", stderr);
        return 64;
    }

    stage = "create private directory";
    if (mkdtemp(directory) == NULL) goto fail;
    made_directory = 1;
    stage = "open private directory";
    dir = open(directory, O_RDONLY | O_DIRECTORY | O_CLOEXEC | O_NOFOLLOW);
    if (dir < 0) goto fail;

    stage = "create old live file";
    file = openat(dir, "live", O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC,
                  0600);
    if (file < 0) goto fail;
    stage = "write old file";
    if (write_four(file, "old\n") < 0) goto fail;
    stage = "sync old file";
    if (fsync(file) < 0) goto fail;
    stage = "close old writer";
    if (close_owned(&file) < 0) goto fail;
    stage = "sync old directory entry";
    if (fsync(dir) < 0) goto fail;
    stage = "hold old reader";
    old = openat(dir, "live", O_RDONLY | O_CLOEXEC | O_NOFOLLOW);
    if (old < 0) goto fail;

    stage = "create next file";
    file = openat(dir, "next", O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC,
                  0600);
    if (file < 0) goto fail;
    stage = "write next file";
    if (write_four(file, "new\n") < 0) goto fail;
    stage = "sync next file";
    if (fsync(file) < 0) goto fail;
    stage = "close next writer";
    if (close_owned(&file) < 0) goto fail;

    stage = "rename next to live";
    publication = "rename attempted; failure requires inspection";
    if (renameat(dir, "next", dir, "live") < 0) goto fail;
    publication = "published; durability unconfirmed";
    stage = "sync replacement directory entry";
    if (fsync(dir) < 0) goto fail;
    publication = "published; file and directory sync calls accepted";

    stage = "open new live reader";
    current = openat(dir, "live", O_RDONLY | O_CLOEXEC | O_NOFOLLOW);
    if (current < 0) goto fail;
    stage = "check retained old view";
    if (matches_four(old, "old\n") < 0) goto fail;
    stage = "check new pathname view";
    if (matches_four(current, "new\n") < 0) goto fail;
    stage = "close new reader";
    if (close_owned(&current) < 0) goto fail;
    stage = "close old reader";
    if (close_owned(&old) < 0) goto fail;

    /* Cleanup only after the normal checks; no rollback after publication. */
    stage = "remove own live name after checks";
    if (unlinkat(dir, "live", 0) < 0) goto fail;
    publication = "replacement checked; own live name removed for cleanup";
    stage = "close directory";
    if (close_owned(&dir) < 0) goto fail;
    stage = "remove own empty directory";
    if (rmdir(directory) < 0) goto fail;
    removed_directory = 1;
    stage = "report success";
    if (puts("old_fd=old live=new sync_calls=accepted cleanup=complete") == EOF)
        goto fail;
    if (fflush(stdout) == EOF) goto fail;
    return 0;

fail:
    saved_error = errno;
    /* Close each still-owned descriptor once. Do not delete further names; report state. */
    if (close_owned(&file) < 0) perror("secondary: close file");
    if (close_owned(&current) < 0) perror("secondary: close current");
    if (close_owned(&old) < 0) perror("secondary: close old");
    if (close_owned(&dir) < 0) perror("secondary: close directory");
    fprintf(stderr, "%s: %s; %s; directory=%s (%s)\n",
            stage, strerror(saved_error), publication,
            made_directory ? directory : "not created",
            removed_directory ? "already removed" : "retain and inspect if present");
    return 1;
}
```

这个例子的可见性正例是旧 FD 检查 `old`、新路径检查 `new`；反例是“rename 会让所有已有读者自动升级”这一推断。末尾 stdout 回顾刚才的检查结果，输出时临时文件已被清理，不表示输出后还可打开 `live`。

### 失败、清理和输出的边界

下表中未实际触发的分支均为 **PAPER_EXPECTED**，依据源码与接口推导，不能当故障注入通过记录。

|分支|如何保留首状态与资源责任|
|---|---|
|参数拒绝 / mkdtemp 失败|前者不创建资源；后者没有确认拥有新目录，不删除任何名称。usage 为尽力诊断|
|创建目录后 open 失败|保留已创建目录；没有 dirfd 就不假称已清理|
|old/next 的 create、write、fsync 或 close 失败|可能留下部分内容；保存首个 errno 和 stage 后，所有仍拥有 FD 各关闭一次；不继续发布，不认领失败 open 的目标|
|rename 失败 / 成功后 dirsync 失败|分别报告“尝试后需检查”/“已发布、持久性未确认”；不删 live、不用旧对象盲目反向替换|
|新 open、任一次精确读取或 reader close 失败|发布阶段保持真实状态；尚未开始正常名称清理，剩余 FD 继续关闭|
|unlink 成功后 close(dir) 或 rmdir 失败|live 已删除，目录是否仍存在按当前结果检查；不能再声称全部名字保留，不递归删除|
|rmdir 成功后 puts/fflush 失败|目录已删除，输出通道失败不会逆转数据或清理状态；返回失败、报告 already removed，不重做替换|
|fail 中又发生 close 错误|次级诊断单列，不覆盖此前保存的 errno；常规控制流仍处理其余拥有者槽|

FD 0 按非负值合法处理；关闭前把槽置 -1，故失败清理不会二次 close。短 I/O 按正进度前进，每次 `write_four` 在调用均返回的前提下至多 4 次正进度加 8 次重试；`matches_four` 最多读入 5 字节再拒绝或读到 EOF。有限字节和重试预算不保证内核调用的硬超时。四次 fsync 的对象依次为旧文件、旧目录项、新文件、替换目录项；应用 payload 共 8 字节并不等于设备物理写入只有 8 字节。

`fail` 不再删除名字，只报告已经到达的状态。这不包括非协作终止：程序没有信号处理器；早期致命信号、强制结束或机器故障可能跳过显式清理。stdout 仅在 rmdir 成功后使用，所以此时 SIGPIPE 不能令已删目录重新存在；stderr 在更早诊断中也可能触发 SIGPIPE，使后续诊断/显式 close 未完成。进程终止后内核释放 FD 与程序成功删除目录是两件事。`fflush` 处理 stdio 用户缓冲，不是文件持久同步。[puts(3)](https://man7.org/linux/man-pages/man3/puts.3.html)、[fflush(3)](https://man7.org/linux/man-pages/man3/fflush.3.html)、[rmdir(2)](https://man7.org/linux/man-pages/man2/rmdir.2.html)

程序没有同步新建随机目录的父目录，末尾又主动删除自己的内容，删除后也没有再次同步目录/祖先。因此它不承诺完整路径或清理动作跨故障持久。即使在 ext4/XFS 正常运行、所有同步调用成功，也只能报告那次接口和视图；在 tmpfs 上成功更不能变成物理介质耐久证据。

## 5. 恢复要先声明故障模型

进程被结束只停止应用，内核和设备还可能继续回写。正常卸载/重新挂载也可能主动同步。两者都不能代替系统崩溃或失去电源，所以不能用一次 kill 后读对了文件来认证掉电安全。

下面另设一个**已经建立持久基线的目录 D、祖先路径及旧 live**，唯一写者、支持目录同步的本地文件系统，且整个存储栈兑现同步合同。这些前提不是上述临时例已经完成的工作。全表为 **PAPER_EXPECTED**：

|停止点|仅更新进程结束，内核仍运行|系统/电源故障后的接口推导|
|---|---|---|
|next 未写完，rename 未调用|live 仍引用旧对象，next 可部分存在|旧 live 有另行建立的持久基线；next 内容/名字没有新保证|
|next 文件同步成功，未 rename|live 仍旧，next 在当次运行已完整|数据同步与 next 名字同步不同，不能只凭 stat 的大小证明恢复内容或名字|
|rename 成功，目录同步未成功|新 open 见新对象，旧 FD 仍旧|不能预设恢复结果只能旧/新二选一；分类旧、新、缺失、不可解析/损坏、其它代次或未知，再结合具体实现判断|
|文件和替换目录同步均成功|新名字/内容正常可见|在所述前提下完成申请的持久协议；不覆盖介质损坏、固件违约、后续写者破坏|

目录 fsync 报错只表示该调用未确认完成；不是系统已经掉电，也不证明新文件已丢失。应用应记录阶段和错误，停止对外承诺，依据自己的恢复协议处理；错误时自动把名字还原也会产生一次新的发布与同步问题。

### 三种文件系统不能合成统一的 redo/undo 流程

|文件系统与已核范围|机制如何帮助恢复|不能推出的结论|
|---|---|---|
|ext4 / JBD2，Linux v6.12 Journal 开头、data 模式和提交说明|日志维护相关事务；`data=ordered` 以元数据日志及数据顺序约束工作，`data=writeback` 不提供同样的数据先行约束，`data=journal` 还让文件数据经过日志|元数据可恢复不保证任意业务文件更新原子；模式名字不替代应用同步与检查|
|XFS，Linux 6.12 Logging Design|元数据采用 WAL；异步事务提交返回与日志已经到稳定存储不同，需要区分 log force/检查点等责任|不能把文件系统事务返回当业务提交，也不应套统一“撤销未提交数据”的步骤|
|Btrfs，Linux 6.12 概览|采用 COW，extent 等机制与日志文件系统路径不同|概览不足以核定所有树根提交/Tree-log 细节；不能称所有 FS 都按一条 replay/undo 全序恢复|

依据：[ext4 Journal](https://raw.githubusercontent.com/torvalds/linux/v6.12/Documentation/filesystems/ext4/journal.rst)、[XFS Logging Design](https://docs.kernel.org/6.12/filesystems/xfs/xfs-delayed-logging-design.html)、[Btrfs 6.12](https://docs.kernel.org/6.12/filesystems/btrfs.html)。此处刻意只用固定版本已读范围，不从未固定 revision 的 Btrfs latest 设计页推导 6.12 实现细节。

文件系统不了解“订单与余额必须同时更新”这类业务约束。若应用采用 WAL，必须自行定义记录格式、提交点、重做/幂等和数据文件顺序；未设计 WAL 的程序没有可供“重放 WAL”的恢复动作。校验和帮助检测其覆盖范围内的变化，并不自动修复；RAID 的冗余与故障容忍取决于级别和实现，也不能替代事务或备份。更完整的事务恢复见原关联中的数据库主篇。

## 7. 先定义工作量和完成点，再谈快慢

### 比较的是哪一种成本

机械盘上寻道/旋转可能使随机小请求付出较高代价；SSD 上并行度、写放大、垃圾回收和温控可能影响结果。这些是待验证的机制假设，不是按介质或文件系统名字给固定排名。业务选型可以比较不同设备的绝对吞吐/延迟，但要使工作量、完成口径可比并披露配置差异；未经控制的变化不能归因于单一因素。

比较文件复制时，要固定读取的有效字节、内容验证、输出字节、缓冲大小和是否计入最终同步。先创建文件可能已经加热缓存；首次启动进程也不等于冷缓存。热缓存回答重复读取的成本，冷缓存回答另一种条件，未知就记录未知。不同条件都可能符合真实业务，不能把冷数据叫唯一“真实成本”。mmap 创建与完整扫描、仅写接受与含 fsync 的总耗时，都不是等量比较。

旧教程中未提供实现的 `file_copy` 不是可复现输入。未来比较须先交付确切实现、fixture、内容 oracle、计时边界与错误计数，再解释系统调用数、CPU 周期/字节和 I/O 延迟。trace/perf 可帮助定位，但会扰动测量；单条跟踪命令不能自动把总时间准确分拆到 VFS、锁、块层和设备。

### fio 的五个独立维度

以 fio 3.42 HOWTO 为资料基准，以下是未来测量合同，本批不运行 fio：

|维度|应明确记录|反例|
|---|---|---|
|工作量|顺序/随机、读写比例、块大小与单位、总有效数据、预置与内容验证、文件布局|4 KiB 随机与 1 MiB 顺序同时改变多个因素；70/30 只是一种指定负载，不是业务默认值|
|缓存路径|buffered/direct、实际支持、文件系统/挂载、数据准备及缓存状态|direct 不能与 fsync 列成二选一，也不是“没有任何缓存”|
|提交引擎|明确 ioengine、同步/异步能力、操作系统限制及提交/完成批量|引擎名 `sync`/`psync` 表示调用方式，不表示每次写都持久同步|
|并发|numjobs、每 job requested iodepth、实际深度分布与作用层|Linux 默认 psync 是同步引擎，`iodepth=32` 不创造 32 个同时未完成的 I/O；jobs×requested depth 也不是观测值|
|同步/完成|每次或批次同步、阶段末同步、是否等待完成以及单列的同步耗时|异步 engine 也可能达不到请求深度；write 完成 p99 不能改名为持久化 p99|

依据：[fio 3.42 engine](https://github.com/axboe/fio/blob/ab77643023f5d7e3c1b71a7576a564f368bf577a/HOWTO.rst#L2124-L2173)、[iodepth 与批量](https://github.com/axboe/fio/blob/ab77643023f5d7e3c1b71a7576a564f368bf577a/HOWTO.rst#L3425-L3485)、[同步选项](https://github.com/axboe/fio/blob/ab77643023f5d7e3c1b71a7576a564f368bf577a/HOWTO.rst#L1472-L1536)。同步选项能否按预期产生调用还需结合 engine/direct 的文档条件；不能仅从参数名断言。fio 对 fdatasync 的简写不覆盖前文 Linux 接口中必要元数据的要求。

`slat` 是 fio 提交侧计量，`clat` 是提交至 fio 获得完成的计量，异步情况下还可包含收割完成的时机；`lat` 对单个请求涵盖两者。它们不是“纯设备服务时间”。单请求可相加，不代表两个 p99 相加等于总 p99。应明确统计了哪一列、单位、同步请求是否单列及 group reporting 是否混合了不同 job。[fio 输出语义](https://github.com/axboe/fio/blob/ab77643023f5d7e3c1b71a7576a564f368bf577a/HOWTO.rst#L4924-L4967)

深度分布和 submit/complete 批量分布的桶含义不同。例如文档中 depth 的 16 桶覆盖 16–31，而 submit 的 16 桶表示高于前桶至 16 的一次提交量，不能拿提交批量当持续在途深度。[fio IO depths / submit / complete](https://github.com/axboe/fio/blob/ab77643023f5d7e3c1b71a7576a564f368bf577a/HOWTO.rst#L5020-L5038)

### IOPS、吞吐、平均延迟与平均在途量

IOPS 是指定层、指定计量窗内操作完成数除以时间；固定操作大小且统计对象一致时，吞吐可由 IOPS 乘每操作字节数得到。混合大小应使用实际总字节/时间。应用请求可能被块层合并或拆分，所以应用 IOPS、设备请求率和业务事务率不能混用。

Little’s Law 的有用连接是：**同层、同窗、同一请求总体的时间平均在途量，约等于完成率乘平均逗留时间**，单位是“次/秒 × 秒 = 个请求”。计入排队还是连服务中的请求一起计入，必须与逗留时间起止一致。有限批次若起止都排空，系统内数量曲线的面积等于这批请求逗留时间之和，可得到精确等式；窗口两端有残留时，须处理截断/边界项，不能随便拿窗内完成者的全寿命平均来乘。长期平均另有存在与收敛条件；实用稳定窗口只是控制边界影响的方法，不能说所有数学形式都要求 stationary 或 FIFO。[Little 2011，论文页 536–539，§2 / LL.1 / LL.2](https://people.cs.umass.edu/~emery/classes/cmpsci691st/readings/OS/Littles-Law-50-Years-Later.pdf)

**PAPER_EXPECTED 算例**：另设同层同窗平均完成率 2,000 次/秒，平均逗留时间 0.002 秒，且边界影响可忽略，则平均在途量约为 4。它不是本机测量。requested depth 32、瞬时峰值 32 或 p99 20 ms 都不能替换这三个平均量；改大深度之后速率和等待时间也会改变，公式本身不会预测吞吐线性提高或最佳队列深度。

### iostat 与页缓存观测的口径

|指标/现象|可以帮助回答|不能单独断言|
|---|---|---|
|iostat r/s、w/s|所选设备合并后的请求完成率|等于应用调用数或业务事务吞吐|
|await，单位 ms|所选设备请求的平均等待，包含排队与服务|业务请求 p99，或纯介质服务时间|
|aqu-sz|对应设备的平均请求队列长度|fio requested depth、某一时刻峰值或应用队列长度|
|%util|设备有 I/O 活动的时间比例口径|对并行 SSD/RAID 而言等于性能容量已用百分比；100% 必然吞吐到顶|
|首报/间隔报|默认首报通常覆盖开机至今，之后是相邻报表间隔；多次间隔模式可用 -y 省首报|把首报与某一次应用采样窗直接并排归因|
|`/proc/meminfo` Dirty、Writeback|全局等待回写与正在回写的内存量快照|本应用独占的脏页、业务尾延迟，或数据已经持久|

依据：[sysstat 12.8.0 iostat 定义与字段](https://github.com/sysstat/sysstat/blob/ffabe8175aa9a7aa056380c66ed3648e50c1967d/man/iostat.in#L21-L219)、[-y 与时间选项](https://github.com/sysstat/sysstat/blob/ffabe8175aa9a7aa056380c66ed3648e50c1967d/man/iostat.in#L355-L373)、[Linux 6.12 proc：meminfo](https://www.kernel.org/doc/html/v6.12/filesystems/proc.html)。该 sysstat release 自称 technical/debug，本文采用其资料定义而非建议安装。默认 vmstat 输出不能假定包含 dirty、pgscan 字段，工具版本和具体字段需另核。

从这些量推断瓶颈，应对齐窗口、设备/分区/映射层、读写类别与单位。不能把 fio 延迟、合并后的设备队列、另一时段的 Dirty 拼成一个 Little’s Law 算式，也不能把设备层 await 直接从业务 p99 中相减得到“应用开销”。

## 8. 排障从可区分的假设开始

|现象|下一步需要的证据|结论与处置边界|
|---|---|---|
|吞吐低或长尾突增|同窗应用工作量/完成点、CPU/等待、实际深度、设备请求、错误；温控/GC/回写只列为候选原因|高 await 或高 %util 只能支持相关假设；容器 cgroup 限额、文件系统锁和网络存储 RTT 也可能改变结果|
|fsync 慢或失败|具体 FD、阶段、返回值/errno、同步批次、挂载/设备缓存合同及同窗负载|失败不等于已丢数据；成功也不构成硬件断电实测；批次调整要保业务确认语义|
|目录遍历慢|实际路径/对象数量、缓存状态、调用与 CPU/等待证据|一次 perf 采样不自动区分 dentry miss 与介质延迟，关联跟踪要考虑开销|
|容量看似异常|逻辑大小与已分配块、稀疏/预留块、inode 与 quota、实际 errno|`ls -l` 与 `du` 差异不自动表示丢失；块容量、inode 耗尽与 EDQUOT 配额不是同一故障，不能一律写成 ENOSPC|
|删名字后空间未释放|链接及打开引用的拥有者、对象身份、文件系统实际回收统计|先确认谁仍需要引用及释放方式；不默认滚动重启持有者，也不递归删目录“试试”|
|文件系统转只读或出现 I/O 错误|真实错误、挂载状态、失败阶段与可保存的原始材料|先停止不安全的继续写入，按专用恢复计划检查；没有 WAL 就不能指定重放 WAL|
|恢复后缺少预期代次|故障模型、此前持久基线、同步结果、恢复出的名字/内容和业务校验|不要先把结果筛成只有旧/新两种；未满足前提时记录未知/缺失，不倒填保证|

这些是取证顺序而非本批工具运行结果。stat/容量/打开引用检查、系统调用跟踪、块层跟踪、eBPF 和设备遥测都只是证据入口；相应完整工具手册、本机版本及权限未逐一核验，本文不给默认执行命令，也不声称单工具能判定根因。
