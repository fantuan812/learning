# 权限、安全与隔离

> 知识成熟度：L2。本篇解释固定资料支持的机制与纸面推导，不是安全认证或运行记录。
> 知识基线：Linux v6.12（`adc218676eef25575469234709c2d87185ca223a`）、util-linux v2.40.2（`1cebcc34373ed34266f726fff71030a83b4df7da`）、man-pages 6.15 的保存成员选读；补充手册快照与来源限制见文末。
> 最后更新：2026-10-06。全文的 `PAPER_EXPECTED` 都是给定前提下的预期；本次安全设置、权限、隔离、网络、压力、性能实验全部 `NOT_RUN`，没有本机成功输出或真实拒绝日志。

## 从一个服务的请求开始

设服务 W 需要读取自己的 `config/service.conf`，处理有界请求，并创建少量工作任务。启动者负责交付配置、规定权限和资源预算；外部监督者 M 负责观察、停止和回收自己创建的实例。这里的 W、M、UID、路径和额度都是案例输入，不指当前机器上的对象，也不要求读者先在共享宿主部署它们。

正常业务的合同是：W 能读指定配置，不能借输入路径读取根目录之外的配置，不能写只读配置，不能无限增加任务；发生拒绝时，M 仍能记录原因并恢复一个符合原合同的新实例。要解释这个合同，必须分别回答：

| 问题 | 需要对上的状态 | 单看什么不够 |
|---|---|---|
| 谁在操作？ | 该线程的实际凭据、附加组、有效 capability 及其作用域 | 登录名或容器里显示的 uid 0 |
| 找到哪个对象？ | 起始目录、每一层目录、挂载视图、链接解析约束、最终对象或已有 fd | 一段已规范化的字符串 |
| 该操作获准吗？ | 请求的读写位、DAC/ACL、适用 capability 与 LSM 等检查 | 最终文件有一个读 ACL |
| 看见哪些对象？ | user/PID/mount/net 等 namespace 的具体实例和拥有者 | 创建过某一种 namespace |
| 消耗算到哪里？ | 目标任务归组、实际内存计费、控制器和祖先约束 | 某个 cgroup 目录中有一个限额值 |
| 调用与恢复会怎样？ | 实际加载的过滤器、动作、线程范围、未受同一限制的启动者 | 磁盘 profile 的内容或 hash |

这是解释问题的关系图谱，**不是所有 syscall 都按表中顺序经过同一条检查流水线**。例如 seccomp 可能直接阻止调用，路径操作才涉及目录遍历，已有 fd 的 I/O 又不是重新从原路径查找。一个机制放行只说明该机制没有拒绝；`EACCES`、`EPERM`、`EAGAIN` 也不是某一机制的唯一指纹。

## 文件从创建到访问：主体、祖先目录和 ACL

Linux 的文件权限判断使用 fsuid、fsgid 和 supplementary groups。fsuid/fsgid 通常与 euid/egid 相同，但它们不是同一个概念；真实 UID、有效 UID、保存 UID 又各有用途。因此排查 W 时应把实际操作线程的凭据与文件 owner/group 对上，不能只记录账号名字。下面文件案例统一假设：普通、支持 POSIX ACL 的非 idmapped 挂载，对象固定且无并发改权，无相关 capability 绕过，没有预先取得的文件 fd，也没有可跳过受阻祖先的目录 fd；另无 seccomp、LSM 等先行拒绝。来源是 man-pages 6.15 `credentials(7)`、`path_resolution(7)` 与固定内核 [`posix_acl_permission()`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/posix_acl.c#L375-L442)。

### P1：创建位是按位屏蔽，不是减法

输入：配置创建者 A 的 fsuid=euid，普通文件创建请求的 mode 是八进制 `0666`，umask 是 `0022`，父目录没有 default ACL，创建所需目录权限已满足。创建时去掉 umask 所标的位，得到 `0666 & ~0022 = 0644`。这一步决定初始权限位，不为未来每次读操作作统一授权。

**PAPER_EXPECTED P1**：初始位为 owner `rw-`、group `r--`、other `r--`。把请求 mode 改成 `0644`，仍得 `0644 & ~0022 = 0644`，而不是八进制减法的 `0622`；umask 不能补回请求里本来没有的位。

反例：若父目录已有 default ACL，改走“继承为新对象的 access ACL，再由请求 mode 限制对应权限”的分支，不能再叠加一次 umask。假定 default ACL 的三项为 owner `rwx`、group `r-x`、other `r-x`，请求 `0666`，则执行位被 mode 去掉，仍可得到 `0644`；即便此时 umask 是 `0077`，也不能据它把该结果改算成 `0600`。复杂 ACL 还须检查 mask 与对应 mode 位。`umask(2)` 的创建分支支持此推导；它不证明 B 能穿过配置文件的父目录。

### P5：文件可读，路径仍可能走不到

输入：A 拥有祖先目录 `private`，其 mode 为 `0700`，没有另行授予 B search 的目录 ACL。B 的 fsuid 不等于 A。最终文件 `private/data` 虽然有 named-user B 的 `r--`，B 从必须经过 `private` 的路径发起普通读取。

目录的 `x` 在这里是 search，决定能否沿已知名字继续查找下一分量；它与列出目录内容的读权限不同。查找经过 `private` 时，B 没有 search，因此到不了对最终文件读权限的有效判定。

**PAPER_EXPECTED P5**：在这些前提下，打开因祖先 search 不足而返回 `EACCES`。只给最终文件增加 B 的读 ACL 不改变这个结果。正向对照是让每一层祖先均满足 B 的 search，再进入 P6 的最终对象判断；若 B 已有文件 fd、有越过该祖先的目录 fd 或适用绕过能力，就不再是本反例，不能沿用这个结论。

### P6：匹配哪一项，比“所有权限加起来”更重要

现在令所有祖先的 search 均通过。文件 owner 明确为 A，B 明确不是 owner；下面是完整有效 access ACL 的纸面状态，B 的组不匹配 owning group：

| ACL 项 | 初始权限 | 用途 |
|---|---|---|
| owner A：`user::` | `rw-` | owner 分支 |
| named user B：`user:B:` | `r--` | 精确匹配 B |
| owning group：`group::` | `---` | 文件所属组 |
| mask：`mask::` | `r--` | named user 和各 group 类的上界 |
| other：`other::` | `r--` | 没有匹配 owner、named user 或组时才使用 |

内核先比较 owner，再比较 named user；B 在 named-user 项命中后，对所请求的整项权限 `want` 检查 `entry & mask & want == want`。读请求是 `r`，交集含 `r`；写请求需要 `w`，交集没有它。

**PAPER_EXPECTED P6**：初始 ACL 在本机制上允许 B 读，拒绝 B 写。只把 mask 改成 `---`，B 的读也被拒；即使 other 仍有 `r--`，也不会在 named-user 匹配失败后退回 other。owner 与 other 不被 mask 截断；mask 约束 named user、owning group、named group。

再作撤销对照：移除 named B 项后重新从主体匹配开始。如果 B 不属于任何匹配组，other 的 `r--` 可能让它继续读；如果匹配了组但该组权限不足，则不能逃到 other。因而“删 named B 就恢复 EACCES”并不成立。

多个匹配组也不是把零散位任意拼起来。另一个有效 ACL 状态中，B 非 owner、没有 named-user 项，同时属于 G1 和 G2；owning group 为 `---`，named G1 为 `r--`、named G2 为 `-w-`、mask 为 `rw-`、other 为 `rw-`。对一次 `rw` 请求，没有任一匹配 group entry 满足整个 `want=rw`，故拒绝；对一次 `r` 请求，G1 满足整项请求且通过 mask，故该机制允许。固定内核 L400–435 的判断是“某个匹配 entry 满足整个 want，再受 mask 限制”，不是先合并 G1/G2。

这也说明恢复不能只反向删除一条 ACL。应比较完整 access/default ACL、mask、mode、owner/group 与原基线；有 mask 时，mode 的 group 位对应 mask，不等于 owning-group entry。上游 [`acl(5)`](https://man7.org/linux/man-pages/man5/acl.5.html) 和 [`setfacl(1)`](https://man7.org/linux/man-pages/man1/setfacl.1.html) 的 2026-10-06 快照还说明，工具可能重算 mask。其泛化的 effective-ID 文案不取代 Linux fsuid 的内核判定；本例没有实际改 ACL。

## 让配置路径的边界在查找时成立

W 若接受相对配置名，先 `stat` 检查、再 `open` 使用，中间路径可能被替换。预先规范化字符串也没有把“检查到的对象”与“实际打开的对象”绑定为一次原子授权。应先明确可信根目录及取得它的权限，再使用稳定 dirfd，把所需约束交给这一次内核路径解析。dirfd 自身的可信来源是前提，不是 `openat2` 自动替应用决定的。

下列是额外的路径纸面正反例，不执行调用。输入为一个有权限取得、指向可信配置根 R 的稳定 dirfd；普通 `O_RDONLY` 打开，`mode=0`，参数结构有效，所有目录/对象权限通过，其他机制不拒绝。

| 安全目标与输入 | 解析约束 | PAPER_EXPECTED 与边界 |
|---|---|---|
| 只接受 R 下的相对名字；`config/service.conf` 各层都是正常目录/文件 | `RESOLVE_BENEATH`，按链接政策另选下列标志 | 正常相对路径可到达指定文件；这不是绕过 DAC/ACL 的许可 |
| 输入从 R 真正向外逃逸：`../outside`，R 的父目录确在边界外 | `RESOLVE_BENEATH` | 检测越根可返回 `EXDEV`；绝对输入也被 BENEATH 拒绝 |
| 业务允许 `/config/service.conf`，但其中的 `/` 必须指 R | `RESOLVE_IN_ROOT` | 绝对输入从 R 解释，R 处的 `..` 留在 R；它与拒绝绝对输入的 BENEATH 不是同一语义 |
| 禁止路径任一分量解析 symlink；其中一项实际为链接 | `RESOLVE_NO_SYMLINKS` | 普通读取需解析链接时可返回 `ELOOP`；此标志隐含 `RESOLVE_NO_MAGICLINKS` |
| 允许普通 symlink，但禁止 `/proc` 等 magic link 的解析 | 显式 `RESOLVE_NO_MAGICLINKS` | 遇到需解析的 magic link 可返回 `ELOOP`；不依赖 BENEATH/IN_ROOT 当前顺带阻止 magic link 的行为永远不变 |
| `..` 的并发变化使内核无法确认是否越根 | `RESOLVE_BENEATH` 或 `RESOLVE_IN_ROOT` | 可返回 `EAGAIN`；无法确认安全不等于已经安全 |

仅 `O_NOFOLLOW` 通常只管末段，前面的 symlink 仍可被解析，不能替代全路径 NO_SYMLINKS。还有明确例外：使用 `O_PATH | O_NOFOLLOW`，配合相应 NO_SYMLINKS 或 NO_MAGICLINKS 约束时，可以返回指向末段链接本身的 O_PATH fd，而非解析它。因此不能概括成“任何含链接的输入都 ELOOP”；这个 fd 也不是本例 `O_RDONLY` 得到的内容读取句柄。其他权限、对象或参数错误仍可能先发生。依据 man-pages 6.15 `openat2(2)` 的 resolve 与 ERRORS 段、`open(2)` 的 O_NOFOLLOW 段。

失败策略同样属于安全合同。若业务要求上述边界，`ENOSYS`、`EINVAL`、`EXDEV`、`ELOOP` 都不能触发“去掉安全 flag，再退回普通 open”。对可能的解析竞态，可由应用设置有限重试预算，例如本案例最多再尝试两次，始终保留安全约束，仍无法确定就报告失败；两次是案例选择，不是内核保证。`RESOLVE_CACHED` 仅是要求纯缓存完成的性能提示，其导致的 `EAGAIN` 可在保留全部安全 flag 的前提下去掉该提示重试，两者不能混为安全降级。

成功打开后的 fd 指向 open file description，原路径后来改名或移除不会把该引用自动改向另一个文件。若 W 随后 exec 不应继承配置 fd，应在获取时原子使用 `O_CLOEXEC`：多线程的“先 open、后 fcntl 设置 CLOEXEC”之间，另一线程可能 fork/exec 并泄漏句柄。CLOEXEC 解决的是这一 exec 继承窗口，不负责所有 fd 传递或所有生命周期清理。setuid 或其他特权辅助程序还需有清楚的环境、路径和继承 fd 合同；不可信输入不能凭辅助程序的特权自动获得授权。

## exec 会重新计算能力，bounding 不是当前 effective

capability 把传统特权拆成不同检查项，但“有哪个能力”还要连同资源所属 user namespace 来说。文件上的 capability 属性是 exec 的输入；线程的集合才描述运行中的状态：

| 集合 | 在本例中回答什么 |
|---|---|
| permitted（P） | 该线程可使之成为 effective 的能力上界 |
| effective（E） | 内核实际进行 capability 权限检查时使用的能力 |
| inheritable（I） | 与可执行文件 inheritable 集合配合，参与 exec 后 permitted 的计算 |
| bounding（B） | 对 exec 从文件 permitted 获得能力施加上界，也约束向 inheritable 添加能力；不是 E 的实时总开关 |
| ambient（A） | 非特权程序 exec 时可保留的一组能力；必须同时属于 P 和 I；执行带文件能力或相应 set-ID 属性的特权文件时会清空 |

在排除 root/set-ID 特殊处理、`no_new_privs` 等改变获权语义的条件，并且文件能力按通常规则生效时，man-pages 6.15 `capabilities(7)` 给出的核心关系是：exec 后 P 由 `I ∩ 文件I`、`文件P ∩ B` 与新 ambient 合成；若文件 effective 位设置，新 E 取新 P，否则新 E 取新 ambient。这里文件 effective 是标志位，不是与线程 E 同形的独立集合。普通非特权可执行文件、带文件能力的文件与 setuid 程序不能混用一份无前提结论。

所以从 B 丢弃某能力，不等于当场清空 P/E/I 中的该能力；原有 I 与文件 I 还可能参与后续 exec。限制启动业务时，必须在 exec 边界对所需集合和资源作用域作完整判断，而非从一个工具选项推断状态。来源：`capabilities(7)` 的 Thread capability sets、Transformation、Bounding 与 capability-dumb 安全检查。

### P3：为什么 ping 成败不能单独证明 cap-drop

比较同一个服务诊断需求的三条纸面路径，网络资源所属 user namespace U 已明确，执行后的集合已明确，不使用预先传入的 socket fd，其他限制不抢先拒绝：

1. W 请求新建 RAW/PACKET socket。若在管理目标网络资源的 U 中没有有效 `CAP_NET_RAW`，相关 capability 检查不能通过；有适用有效能力只表示该项检查通过，不保证整个网络请求成功。
2. W 使用 ICMP datagram ping socket。假设目标 netns 的 `ping_group_range` 为 `[1000,1000]`，W 的 egid 是 1000，即便 E 中没有 `CAP_NET_RAW`，`ping_init_sock()` 的组检查仍可通过。反向输入为 egid=1001 且全部 supplementary groups 都不在范围内，此分支返回 `EACCES`。这里检查 egid/附加组，不能照搬文件访问的 fsuid/fsgid。
3. 尚未运行 W 的网络逻辑：目标可执行文件的 permitted 声明含 `CAP_NET_RAW` 且设置文件 effective 位；假定通常文件能力路径适用，但 exec 后 P 没有取得完整文件 permitted 集。capability-dumb 安全检查可使 exec 自身先以 `EPERM` 失败，根本没有发生目标 socket 操作。

**PAPER_EXPECTED P3**：以上前提决定的是三个不同检查的结果。`ping` 可能选择哪一种 socket、`capsh` 的具体版本及 drop 是否成功，本例都没有运行资料；不能写成“drop 后 ping 必失败”，也不能把 ping 成功当作获得宿主特权。LSM、路由、网络配置、程序实现或已有 fd 还会改变端到端结果。固定内核依据为 [`ping_init_sock()` L252–280](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/ipv4/ping.c#L252-L280) 与 [`ping_group_range`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/Documentation/networking/ip-sysctl.rst#L1425-L1430)，不是当前宿主设置。

`no_new_privs` 提供另一种边界：设置后不能撤销，并经 fork/clone/exec 继承，主要承诺 exec 不授予原本没有的权限，例如 set-ID 不改变身份、文件能力不增加 permitted。它不自动阻止非 exec 的一切权限变化，也不撤销现有能力或收到的 fd；LSM 的 exec 转换也需单独核对。固定 [`no_new_privs.rst`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/Documentation/userspace-api/no_new_privs.rst) 支持这个有限承诺，本篇不设置该位。

## Namespace 改变对象与视图，不自动完成授权

W 显示的 ID、能用的 PID 编号、看到的挂载树可能属于不同维度。辨清对象后，才知道某项 capability 需要在哪个 user namespace 有效。

| namespace | 隔开的对象或视图 | 不能随之推得 |
|---|---|---|
| user | UID/GID 映射及相关 capability 作用域 | 内部 uid 0 等于初始 userns 的 uid 0 |
| PID | PID 编号与按 PID 操作的可见范围 | 旧 procfs 挂载自动变成新 PIDns 的视角 |
| mount | 挂载列表/目录树视图 | 共享的底层文件内容变成独立副本 |
| network | 网络栈、接口、路由、端口等网络对象 | 业务必断网，或已有连接、传入 fd 与策略都已处理 |
| UTS | hostname、domainname | 文件、任务和资源额度也已隔离 |
| IPC | SysV IPC 与 POSIX 消息队列命名空间 | 应用层认证授权已经完成 |
| cgroup | cgroup 路径的可见根与视图 | 对该子树有控制器配置或迁移权限 |

### P2：先判断能否建立环境，再讨论输出

假设本例的父 user namespace 就是 initial user namespace，调用者为该域 UID 1000 的无特权用户，计划映射一行“内 0 → 外 1000，长度 1”。先分支：创建 userns、建立合法 ID 映射、创建相关 namespace 或挂载 procfs 的任一步若被内核、运行时或 LSM 拒绝，就记录“前提未成立”并停止；目标程序可能根本没有启动，**不能替它写出 id/ps 的预期成功输出**。Linux 版本号、rootless 或有某个工具都不是上述步骤必然成功的保证。

只有这些操作已成功的假设分支，才有 **PAPER_EXPECTED P2**：内部身份可表示为 0，映射回 initial user namespace 仍是 UID 1000，而非 UID 0，也没有因这条映射获得 initial user namespace 的 capability。映射长度 1 也不授权任意父域身份。任意嵌套父域需逐层核对映射，不能只凭父域数值 1000 判断宿主身份。

进一步比较两种视图。util-linux v2.40.2 的 `--mount-proc` 在运行目标程序前挂 procfs，并隐含新 mount namespace，**不隐含新 PID namespace**。只请求 user 与 mount-proc 时，旧 PIDns 仍存在；新 userns 内的 capability 不自动成为旧 PIDns 所属 userns 的 capability，procfs 挂载可能就在输出 id/ps 之前失败。即便该分支假定另有合法权限使挂载成功，也不能因此声称 PID 已隔离。

正向对照是另行显式创建 PIDns，让其后出生的子进程 W 位于其中，并在相应 PIDns 视角挂载新 procfs。调用者自身不会因创建新的 PIDns 就改变自己的 PIDns；第一个子进程成为其中的 PID 1，承担该域 init/reaper 的职责。此时配套的 procfs 才能让 `ps` 看到与新 PIDns 对应的进程集合。祖先 PIDns 仍可见后代；“子看不见祖先”限于 PID 编号与相应操作范围，不表示继承的祖先 procfs 文件视图凭空消失。PIDns 的 init 退出会导致内核终止该域其余进程，也不能替代对其他登记资源的清理。

mount 视图还须区分传播：private 不向内/外传播挂载事件；shared 与同伴传播；slave 可从 master 接收而不向其反向传播。底层文件若仍共享，对内容的改变不因 mount namespace 不同就分家。util-linux `unshare` 的默认 private 处理是工具行为，不能概括为直接调用 `unshare(2)` 的所有环境都已设置相同传播状态；较低权限 mount namespace 还有额外限制。依据固定 [`unshare.1.adoc`](https://github.com/util-linux/util-linux/blob/1cebcc34373ed34266f726fff71030a83b4df7da/sys-utils/unshare.1.adoc#L17-L119) 及 man-pages 6.15 `user_namespaces(7)`、`pid_namespaces(7)`、`mount_namespaces(7)`。

若把 W 的某个挂载设为只读，作用是约束对应写入并减少相应持久化面。per-mount 与底层 filesystem superblock 的只读位不同，经该挂载可写需要两者都不只读；只读不提供保密性，也不自动覆盖独立可写挂载、传入 fd 或其他资源。既不能说“所有旧可写 fd 都绕过只读”，也不能说“只读根撤销全部已开句柄”。句柄指向何种 mount/对象及动态重挂载细节须另核；本篇仅据 2026-10-06 保存的 [`mount(2)` 补充选段](https://man7.org/linux/man-pages/man2/mount.2.html) 作以上限制，不将它冒充 6.15 固定成员。

为将来核对 P2，记录应绑定“哪个实例、哪个时刻、哪个观察者”：外/内凭据与映射、目标 PID/TID、namespace 标识、procfs 的挂载视角及 mount 传播。单条 `id`、一个 namespace inode 或一段 `ps` 输出都不能同时证明这些关系；本次没有生成这样的运行档案。

## cgroup：先有委托和成员，资源才有归因

服务的工作任务需要有限预算，cgroup v2 将资源控制组织成层级。父层 `cgroup.controllers` 中可用的控制器，须由相应 `cgroup.subtree_control` 启用后，子组才有对应控制接口；还要核实际委托范围与迁移权限。写目标 `cgroup.procs` 所需的权限，包含源与目标共同祖先的相关写权限，不能把“能创建目录”当成“能把任何服务移进去”。合法委托允许管理自己的子树，父层资源限制仍约束它。

对非 root 的 domain cgroup，启用 domain controller 向子组分配时有 no-internal-process 约束：不能一边保有自身进程，一边这样分配 domain 资源。该规则有 root 特例，也不能不加区分地套到所有 threaded 情形。本文案例采用正常 domain 叶组，不扩写 threaded 配置教程。

监督者 M 必须在受测限制及祖先共同故障域之外，保有已授权观察/停止能力；仅仅位于叶组 C 之外不够，若 M 与 C 仍受同一紧缩祖先限制，M 也可能失去恢复能力。不能把当前工作 shell 移入试验额度，然后假定它仍可靠地清理自己。本段是未来实验前提，本次不创建、迁移、冻结、终止任何 cgroup 对象。

### P4：写了限额，服务却仍在另一个组

输入：C 为已合法委托的有效 v2 叶组，memory controller 在相应父层启用，C 的 `memory.max` 有限；W 实际仍在与 C 无祖先关系的 S 中。只改变 C 的配置，不改变 W 的成员关系。

**PAPER_EXPECTED P4**：不能据 C 的限额声称 W 已受 C 限制。必须把目标 W 的 cgroup 归属、C 的成员及工作开始时点对起来；cgroup namespace 显示一个路径，也不自动授予此迁移权限。

正向对照：假设经授权把 W 正确归到 C，随后在 C 中实例化并计费的新内存才按相应 C/祖先限制判断。反例是 W 在 S 时产生的旧内存：迁移进程不自动迁移其旧计费；W 的新请求也可能使用已经记在其他组上的共享页。`memory.current` 是该组与后代的内存使用计量，不是 W 的 RSS 别名。把进程 RSS 全部减出来、再与 C 的 max 相比，无法还原真正的计费和回收路径。依据固定 [cgroup-v2 的 Processes、Delegation 与 Memory Ownership](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/Documentation/admin-guide/cgroup-v2.rst)。

### P7：只推导一次新增任务

输入：C 的 pids controller 有效，`pids.current=3`、`pids.max=3`；祖先没有更紧的剩余额度，没有并发迁移、退出或其他任务变化。W 请求增加恰好一个受此控制的任务。这里 pids 计数按内核任务/TID，不能把一个多线程服务误算成只有一个额度。

**PAPER_EXPECTED P7**：这一次 fork/clone 若使计数超过该限制，pids 策略拒绝并返回 `EAGAIN`。对照 current=2、max=3 且其他前提相同，此组的 pids 检查允许增到 3；这仍不保证调用通过其他资源或安全检查，无须循环 fork 来观察边界。

祖先要逐层比较各自的 current 与 max：即使 C 尚有一个额度，共同祖先也可能已被兄弟工作负载用满；仅取各层 max 的最小数字会遗漏这个事实。组织迁移或降低限额可以产生 `current > max`，所以它也不是“内核绝不允许出现”的状态。反过来，单独看到 `EAGAIN` 不能排除其他限额或失败来源。依据 cgroup-v2 的层级约束与 PIDs L2232–2285。

### P8：high、max、oom 与 oom_kill 描述不同阶段

输入：W 已正确归组，所讨论的新内存计费落在 C，比较同一组在请求前后的事件值与时间。下面按回收和分配分支推导，不假定 RSS 达到某常量就立刻杀进程：

| 分支 | PAPER_EXPECTED P8 | 不足以推出的结论 |
|---|---|---|
| 使用量越过 `memory.high` | 进程遭节流并承受直接回收压力；high 自身不调用 OOM killer，极端情况可越过 high | high 事件增加不等于有进程被杀 |
| 计费将超过 `memory.max`，直接回收能够降低使用量 | 可发生 max 事件，回收后继续处理 | max 增加不等于 oom 增加 |
| 到 max 且无法回收，进入适用的 OOM 路径 | 可能进入组内 OOM 并调用 OOM killer | 不能把每种分配失败都写成 OOM 杀进程 |
| 某类分配不把 OOM killer 当选项 | 可有重试、`ENOMEM` 或其他分配语义 | 此类失败未必增加 oom；oom 与 oom_kill 也不是同一计数 |

`memory.events` 的 high 记录因 high 超限节流/回收，max 记录将超过上限，oom 记录到限且分配将失败的相应情形；`oom_kill` 统计该组进程被各种 OOM killer 杀死的数量，可包含其他类型 OOM，不能仅据它断言 C 的 max 是唯一原因。`memory.events` 默认是层级累计，后代事件也可反映在其中；`memory.events.local` 才限于本层。应保存同一目标组、同一口径的前后差值并关联时间，不能拿一个历史非零值当成本请求的事件。清理后 `memory.current` 精确为零也不是通用验收条件。

其他预算同样有口径：`cpu.max` 的 MAX/PERIOD 约束带宽，不保证请求在某墙钟时延内完成；`io.max` 按设备和读/写方向限制 BPS/IOPS，并允许临时 burst；PSI 描述资源等待压力，单独一个压力值不能证明本次失败由某条限额造成。应用的超时、连接/队列上限和 backpressure 用于让进入系统的工作有界，不能只靠 cgroup 在资源耗尽后兜底。本文没有性能预算、压力采样或 OOM 实验结果。

## seccomp：动作、日志和实际加载是三件事

seccomp BPF 看 syscall 编号、ABI/架构及参数值，用于缩小进程可触达的内核调用面；它不能解引用 pathname 指针去做文件路径授权，也不是完整 sandbox。W 的配置路径仍由前述解析与对象授权保护。LSM 可在内核安全检查点实施其他策略，seccomp 的 ALLOW 不替 LSM、DAC 或 capability 授权；LSM 概览只支持这一角色划分，不承诺某发行版的策略或日志格式。

过滤器按线程生效。普通安装路径需要满足 `no_new_privs` 或相应 userns 的 `CAP_SYS_ADMIN` 等要求，安装也可能失败。TSYNC 用于把同一进程其他线程同步到同一 filter tree，但必须检查实际成功；若别的线程处于 strict mode 或过滤树已分叉，同步可能失败，不能从磁盘 profile 推断所有线程已一致加载。

### P9：deny 不只有 EPERM

输入：固定一个受支持 ABI 下的 syscall，例如 W 的一次 `mount` 调用，仅讨论**一个已成功安装的过滤器**，其对这次输入返回下表 action/data；不实际执行 mount。这个设定使最终动作没有多过滤器歧义。

| 最终 action/data | PAPER_EXPECTED P9 | 业务解释 |
|---|---|---|
| `SECCOMP_RET_ERRNO`，data=`EPERM` | 不执行 syscall，向用户态返回指定错误 | 是本例明确指定的 EPERM，不是所有 deny 的统一结果 |
| `SECCOMP_RET_TRAP` | 不执行，向触发线程发送 `SIGSYS` | 信号处理及后续状态不能按普通 errno 路径处理 |
| `SECCOMP_RET_KILL_THREAD` | 不执行，终止触发线程 | 多线程进程的其他线程范围与下一行不同 |
| `SECCOMP_RET_KILL_PROCESS` | 不执行，终止整个进程的线程组 | 不能只验证一个线程停止就称对应恢复完成 |
| `SECCOMP_RET_LOG` | 进入 syscall 执行路径，动作日志受日志条件约束 | LOG 不是拒绝；调用仍可能因其他机制失败 |
| `SECCOMP_RET_ALLOW` | 进入 syscall 执行路径 | 不证明 mount 有权限或业务成功 |

若存在多个过滤器，取最高优先级动作；相同优先级时使用其中最新安装过滤器的对应 data。ERRNO 的较小错误码不是优先级；只说“没有更高动作”仍不足以知道最终 errno，因为同级的新 data 可不同。反向对照是在原 ERRNO 过滤器之后追加一个 ALLOW 过滤器：较高优先级的 ERRNO 仍获选，调用不会因此放开。固定文档还定义 TRACE/USER_NOTIF，但它们及 ptrace/CRIU 特殊机制不属于本篇恢复方案；不据旧 TRACE 说明推断所有 v6.12 行为。

日志是另一条条件链：动作、`SECCOMP_FILTER_FLAG_LOG`、`actions_logged` 及 audit 配置共同影响是否记录。seccomp 的 ALLOW 动作本身不被这种 action 审计记录，不表示同一次调用绝不产生其他审计。没有日志不能推出调用获准，也没有“所有拒绝日志必带 PID/profile-version”的统一格式保证。本次没有读取宿主 audit 设置或生成拒绝日志。依据 man-pages 6.15 `seccomp(2)` 与固定 [`seccomp_filter.rst`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/Documentation/userspace-api/seccomp_filter.rst#L84-L182)。

### P10：修改文件不能撤掉已继承的坏过滤器

输入：W 已安装 F坏，磁盘启动 profile 从 F坏 改回 F旧，W 仍存活。若 W 的过滤器允许 fork/clone 与 exec，后代会继承已有过滤器，exec 也保留它。磁盘文本变了，没有改变 W 持有的过滤树；再加一个更宽松过滤器也不撤销 F坏。

**PAPER_EXPECTED P10**：W 及普通继承路径产生的后代仍受 F坏 约束。即使新 shell、容器名称或 profile hash 不同，也不能据此宣称恢复；关键是启动链是否仍继承 F坏。

正向恢复合同是：由**从未安装或继承 F坏的启动者 M**，在受测限制及祖先共同故障域之外，按已有授权停止受影响的自有实例，再使用 F旧 创建新实例。随后核对真实安装结果、受影响线程范围、应允许的配置读取和应拒绝的操作，以及业务与数据完整性；任一步没有证据就保持未恢复状态。M 还必须本来就有相应已授权权限，不能靠换父进程的说法凭空获得权限。本篇未启动或停止实例；该推导限于普通安装与继承路径，不宣称已经排查所有特权调试/恢复接口。

来源定位为 `seccomp(2)` 的 filter 继承、TSYNC 与动作段，以及固定 [`kernel/seccomp.c`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/seccomp.c) L424–462、1919–2030、2060–2128，共选读 220 行。它们核对模式和安装入口及普通分发边界，不等于全内核、ptrace 或 CRIU 审计。

## 怎样组织观察和排障证据

原有身份、capability、namespace、cgroup、syscall 观察的用途仍然需要，但观察必须围绕同一个 W 的实例与时间线。将来的已授权试验应先确定实际 service、ABI、profile、工具版本和成功合同；本篇并未提供 service 实现或可加载 profile，不能从一次 trace 凭空生成“完整 allowlist”。单次 trace 只是该次训练输入覆盖的下界，冷启动、错误处理、不同依赖与 ABI 的调用都可能缺席。

| 排查问题 | 需要关联的证据 | 避免的误判 |
|---|---|---|
| 配置读失败 | 凭据、每级 search、最终 owner/group/ACL/mask、请求位、挂载和已有 fd 情况 | 只看最终文件 mode；把所有错误都归为 ACL |
| 内外视图不同 | PID/TID 与实例、ID map、namespace 标识、对应 procfs/mount 视角 | `CapEff` 或 `NSpid` 一项证明整个隔离合同 |
| 网络调用失败 | 具体 socket 路径、资源所属 userns、实际有效能力/组、netns 路由与适用策略 | 一次 ping 失败证明 cap-drop，或新 netns 必断网 |
| 资源请求失败 | 实际成员、controller/父层约束、新旧计费、current 与事件差值 | 配置存在就是归组；max、oom、oom_kill 等价 |
| syscall 返回错误或进程退出 | 实际 ABI、已加载过滤树、动作/data、线程范围、返回值/信号与日志可用性 | 将 profile 文件 hash 当运行中加载证明 |
| LSM 拒绝或没有日志 | 所用策略、目标对象与上下文、可用审计证据及其缺失 | 因出现拒绝就自动新增允许规则；无日志就是放行 |

`/proc/PID/status`、`/proc/PID/cgroup`、映射与 mountinfo 是可用的观察入口，但访问权限和视角都需成立；PID 还要与实例生命周期绑定，避免把复用后的 PID 当旧服务。`nsenter` 只是需相应授权的诊断入口，不是“看一眼就无副作用”的默认步骤。auditd、systemd 的沙箱检查工具可帮助整理事实，其可用性与输出需按真实发行版核对，评分不等于安全证明。本篇没有执行这些工具。

允许与拒绝应配对：正常配置读取、有限工作任务是正向业务合同；越根路径、无写权文件、明确过滤动作与超额的一次任务请求是反向合同。发现不符时先保留实例、配置身份、请求、时间、原错误及缺失证据，定位哪一个前提没有成立；不自动改内核开关、增加权限、放宽 ACL/LSM/seccomp 或换账号重试。

## P11：先定义测量对象，再谈分位数

假设手头只有 30 次 `service --self-test` 的完整启动耗时，没有逐请求或逐 syscall 样本，也没有业务 SLO。这是一个假设数据集，本次连这 30 个样本也没有实际采集。

**PAPER_EXPECTED P11**：这些样本至多描述这批 self-test 启动耗时，不能被改名为 syscall p99 或请求 p99。完整启动计时可能包含加载、初始化与测试本体；perf 的 cycles、instructions、context-switches 等计数衡量的又是指定测量区间内的硬件/调度事件，不自动产生请求时延分布。RSS、cgroup 内存使用和峰值也要分别说明口径。

正向对照是先选一个问题，再收集对应分母：若研究请求尾延迟，就定义请求开始/结束、成功与失败样本、并发/负载与时钟区间，保存逐请求数据；若研究启动，就比较相同 self-test 合同的启动过程。30 次不是可靠性保证，少量样本的极端分位数很不稳定；“退化 10%”也不是安全机制的普遍性能预算。本次不填写任何延迟、吞吐、峰值或退化判定。

未来比较宿主、namespace、rootless 或 seccomp 配置时，先确保相同功能与安全合同通过，再固定输入、内核/运行时/工具与构建版本、硬件、资源设置、预热方式和同步终点，记录全部原始样本及失败，而非只保留成功最快值。首次加载、编译优化、CPU 频率、SMT/NUMA 和后台负载都可能改变测量；异步工作未完成就停表会漏算实际耗时。吞吐、IOPS、CPU/请求、错误/重试率与尾延迟要各自对应操作单位，预算来自真实业务需求。

这保留了原 Benchmark 的对照、控制变量、原始日志与失败分析用途，但没有引入新的 runner、性能阈值或 CI。仓库 lint/CI 只能证明其实际检查的对象，不能将本文 L2 静态解释提升为安全实验或性能验证。

## 由限制外的监督者恢复，并只清理自有资源

先做桌面推演：资产包括配置、用户数据、凭据及内核接口；主体包括 W、启动者、维护者和输入提供者；边界还涉及 setuid 辅助程序、设备节点、容器 socket、环境变量和日志。每个事件分别列已观察事实、仍缺证据、谁有权响应、可逆与不可逆动作、替代启动和数据完整性检查。

例如，W 的某次 syscall 被 seccomp 拒绝，只能先说明该动作命中，不是容器逃逸证据；配置读取失败也不能单独证明恶意。授权响应者应先核对象、主体、时间和策略，再决定处置。凭据吊销可能无法原样恢复，冻结任务、改变 ACL/LSM、修改审计规则或放宽策略都有独立影响，不能因一条日志就自动执行。内核与运行时更新属于持续维护，不能把它们当成本次未知拒绝的即时替代解释。

### P12：干净退出是有边界的资源账，不是全宿主静止

输入：M 持有本实例的资源登记，逐项包含有权处理的 PID/任务实例、自有子组、挂载或持久引用、独占目录及所有者；试验已停止接收新任务。假定 C 仍有活进程或空子组，或一个 namespace 仍有登记的持久 bind 引用。

**PAPER_EXPECTED P12**：有活进程或子组时，不满足 cgroup 文档所述删除条件；持久 bind 引用可使 namespace 在无成员后继续存在。不能把“某次 cgroup.procs 为空”当无竞态证明：它可能漏掉后代，也可能随后有新成员；`populated=0` 表示当时该子树没有活进程，不表示不存在空子组，更不是未来永远为空。

正向清理合同是由 M 根据登记和授权结束自己的实例，确认不再新增/迁入，处理登记的子组及引用，并逐项确认所拥有的资源完成相应生命周期。任何停止或删除失败，都保留具体对象、时间、原错误及未完成责任，交回有权处理者；不吞 `rmdir` 错误、不扩大删除范围，也不以删除未知共享临时目录补救。没有登记的对象不因名称看起来像“实验目录”就可回收。

即便 cgroup 目录删除成功，它也可能暂时处于 dying 状态并保留资源；`memory.current` 精确回零不是通用清理条件。本篇只核对已登记的持久 bind 引用用途，没有审遍所有 namespace/fd 引用寿命。来源是 cgroup-v2 的 Processes、populated、`nr_dying_descendants` 与 util-linux unshare 的持久化说明。

恢复验收仍要回到业务：新 W 按正确配置可读、越界与写入继续被拒、有限工作能完成、数据完整性检查符合预先约定。检查的是自有资源和对应结果，不要求共享宿主全局进程表、挂载表、路由表与开始时逐字完全相同；其他合法工作本来就可能改变它们。

将任一 PAPER_EXPECTED 转为真实实验，需另有明确授权的可销毁环境、无真实业务数据或凭据、有界资源与网络影响、已确认委托、独占记录目录和上述外部监督/停止方案。普通用户、rootless 或容器名都不能替代这些条件；前提不成立就停止。本文保留观察合同与正反例，不提供共享宿主默认执行流程。
