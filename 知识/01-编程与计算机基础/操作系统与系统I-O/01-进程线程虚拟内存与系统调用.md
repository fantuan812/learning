# 01-进程线程虚拟内存与系统调用

> 知识成熟度：L2。主要承诺是经一手资料与固定版本源码核对的系统执行机制、策略取舍和诊断口径；两个有限程序的本次运行证据单列，不证明调度性能、生产实时性或整篇达到 L3/L4。
> 知识基线：Linux man-pages 6.19；实现分析固定 upstream Linux v6.12。系统调用入口只讨论传统非 FRED 的 x86-64 路径；厂商手册已读范围见 6.3。宿主运行版本与资料版本分别记录。
> 最后更新：2026-10-06，整篇重审任务、调度、入口、内存风险、策略决策与观测链；保留旧日期及原导航。

一帧或一个服务器 Tick 变慢，可能是线程仍在执行但工作集变差，也可能是已能运行却排不上 CPU，或正在等 I/O、锁与缺页处理。三者需要的证据不同。本篇先把“谁在执行、持有什么资源、处于什么状态”连起来，再解释哪些配置能改变什么，最后给出可复核的小练习和有限诊断步骤。

前提是理解地址、函数调用和线程共享内存。本文负责系统执行与调度决策；映射、COW、文件对象/FD/映射寿命和文件故障的完整机制由 [虚拟内存与文件映射主篇](02-虚拟内存、PageFault与mmap.md) 承担。

## 1. 任务身份：共享资源不等于同一条执行流

Linux 用 `task_struct` 描述可调度的任务，但“使用同一种任务结构”不意味着进程级资源或线程组概念不存在。通常的 Linux/glibc NPTL 线程模型中，一个进程的多个线程属于同一线程组，能共享地址空间、文件描述符表和文件系统上下文；每条执行流仍有自己的寄存器执行上下文、用户栈、TLS 和内核栈。

```text
同一线程组（TGID=1001，用户 getpid() 所见的 PID；同一 PID namespace 示例）

Task A：TID=1001（组长）                  Task B：TID=1002
  mm    ──────────> [同一地址空间] <────────── mm
  files ──────────> [同一 FD 表]    <────────── files
  fs    ──────────> [cwd/root/umask] <────────── fs
  执行上下文 A                              执行上下文 B
  用户栈 A / TLS A                          用户栈 B / TLS B
  内核栈 A                                  内核栈 B

PGID：另一个“进程组”标识，用于 shell 作业控制等，可包含多个进程
```

这里的“各有用户栈”是分工，不是地址空间隔离：同组线程通常可以通过有效指针访问对方栈上的存活对象，因此共享数据的寿命和同步仍由程序保证。A 通过共享 FD 表关闭一个描述符，会影响 B 对同一描述符编号的使用；两个独立 FD 表中指向同一 open file description 的描述符又是另一层共享，不能混为一谈。

`gettid()` 给出内核 TID；同组线程的 `getpid()` 给出共同 TGID。`pthread_self()` 返回的 `pthread_t` 是线程库标识，不应强转成 TID 使用，也不应在其寿命结束后继续使用。PGID 与 TGID 不是同义词。依据：[gettid(2) 的 DESCRIPTION/NOTES](https://man7.org/linux/man-pages/man2/gettid.2.html)、[pthreads(7) 的属性与 Thread IDs](https://man7.org/linux/man-pages/man7/pthreads.7.html)、[setpgid(2)](https://man7.org/linux/man-pages/man2/setpgid.2.html)。

### 1.1 从创建 API 追到共享关系

先问需要的是“另一个进程的独立地址空间”，还是“在同一地址空间中并发执行”。这决定程序要依赖的 API 合同，不能只按一个 `clone` flag 列表猜实现。

- `fork()` 的子进程具有独立虚拟地址空间。Linux 借助 COW 延迟复制数据页，创建时仍要建立子任务、处理页表等状态；相同虚拟地址不代表之后写入相互可见。glibc/NPTL 的 `fork` 包装器使用 `clone` 提供等效语义，并处理已注册的 fork handlers；这不是可跨架构直接抄写的 `clone(SIGCHLD, 0)` 原始调用签名
- glibc 的 `clone()` 包装函数接受入口函数、栈等参数；raw `clone` 的参数布局有架构差异。Linux `clone3` 用 `clone_args` 结构传递参数，手册所述 glibc 不提供对应包装器。它们是 Linux 接口，不是所有线程平台的统一创建接口
- `CLONE_VM`、`CLONE_FILES`、`CLONE_FS`、`CLONE_THREAD` 分别控制地址空间、FD 表、文件系统上下文和线程组等关系，且有 flag 依赖。完整 `pthread_create` 实现还要安排线程库状态、用户栈、TLS、退出及 join/detach 等生命周期。几个共享 flags 不是可替代线程库的完整配方

“轻量级进程/LWP”可帮助理解共享资源的任务，但不应掩盖这些合同差别。本篇不手写 raw clone 线程库，也没有核对 glibc 全部创建调用链。依据：[clone(2) 的接口区别及 CLONE_FILES/FS/THREAD/VM](https://man7.org/linux/man-pages/man2/clone.2.html)、[fork(2) 的 VERSIONS/NOTES](https://man7.org/linux/man-pages/man2/fork.2.html)。

## 2. 从任务状态解释等待、切换和运行成本

### 2.1 进入内核不等于换线程

用三个教学状态追踪一条执行流：running 表示此刻正在某个逻辑 CPU 上执行；runnable 表示具备运行条件，可以参与调度，但可能仍在排队；blocked 表示在等事件或资源。这不是 Linux 全部任务状态枚举，尤其内核 `TASK_RUNNING` 还覆盖“正在执行/可运行”的区别。

以阻塞读取为例：线程正在用户态运行 → 发起系统调用并由同一任务在内核态执行 → 数据未就绪而阻塞 → 调度器让其他任务运行 → 数据就绪后唤醒原任务，使其可运行 → 获选后继续执行并返回用户态。唤醒不会自动把 CPU 交到它手中。反例是无需等待的调用：同一任务完成入口、内核工作和返回，全程可以没有任务上下文切换。

因此，业务 wall time 里可能同时有实际 CPU 执行、blocked 等待与 runnable 排队。一次切换的计数不提供这三项时长；系统调用次数也不能直接换算成切换次数。

### 2.2 直接工作与间接工作集成本

任务切换的直接工作可能包括选择下一任务、保存/恢复所需架构状态、切换内核栈，以及在需要时切换内存上下文。具体保存步骤取决于入口时已保存的状态、架构与配置，不是每次机械重存所有寄存器。传统 x86-64 的软件 RSP 切换、TSS 字段、每 CPU 入口栈和每任务内核栈要分别理解：TSS 不是一个统一的“当前线程栈指针”。v6.12 的 [entry_64.S `__switch_to_asm`](https://github.com/torvalds/linux/blob/v6.12/arch/x86/entry/entry_64.S#L168)、[switch_to.h `update_task_stack`](https://github.com/torvalds/linux/blob/v6.12/arch/x86/include/asm/switch_to.h#L60) 给出了具体路径，不能扩展成所有中断/异常的完整栈规则。

切换后执行同样的业务代码，可能因缓存和翻译命中率变化而多做工作。这是间接成本的动机，但没有通用的固定微秒预算：

- **地址翻译：** 同一 `mm` 的线程间不必换地址空间。v6.12 `switch_mm_irqs_off` 在同 `mm`、非 lazy 情况可以直接返回；不同 `mm` 时，PCID/ASID 槽和 TLB 代际等决定是否刷新，有效翻译可以沿 no-flush 路径复用。PCID 不是 PID，也不意味着翻译永久有效。[tlb.c 的 `choose_new_asid`、`load_new_mm_cr3` 与同 mm 分支](https://github.com/torvalds/linux/blob/v6.12/arch/x86/mm/tlb.c#L201)
- **数据与指令工作集：** 其他任务可能挤走热点，迁移后的 CPU 也可能缺少所需缓存；是否发生、损失多少取决于工作集、缓存层次、共享关系和竞争。不能从“切换/迁移发生”推出 L1/L2 全冷，更不能给每次访问固定 DRAM 次数
- **NUMA：** CPU 位置改变而内存仍位于原节点时，局部性可能变差；是否远程取决于真实内存放置。改变 CPU affinity 不会自动把已有内存迁到目标节点。[NUMA policy 的范围和已分配页规则](https://docs.kernel.org/6.12/admin-guide/mm/numa_memory_policy.html)

需要优化时，应先辨认 runnable 等待还是执行中的工作集成本，再选择证据；`perf sched` 的排队时间不能拿来填“寄存器切换耗时”。

### 2.3 自愿与非自愿计数是线索

`voluntary_ctxt_switches` 描述任务主动让出 CPU 的计数，常见原因是等待资源；`nonvoluntary_ctxt_switches` 描述被抢占等非自愿切换。针对具体线程可读 `/proc/PID/task/TID/status`，同一线程的两个时点作差，再除以采样窗口。不能将 `/proc/PID/status` 中的每个字段都当作进程所有线程总和；线程已退出、PID/TID 被复用或窗口不同也不能直接比较。[proc_pid_task(5)](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html)、[proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)、[getrusage(2) 的 ru_nvcsw/ru_nivcsw](https://man7.org/linux/man-pages/man2/getrusage.2.html)

正常事件驱动服务频繁等待网络就绪，也可能有大量自愿切换；这不是锁竞争的充分证据。非自愿计数高时，再看同窗口 CPU 负载、可运行等待和业务尾延迟，才能判断资源竞争是否与症状相关；不能单凭它宣布宿主严重超售。

### 2.4 CFS 历史直觉与 EEVDF 的选择条件

`SCHED_OTHER` 是普通分时调度策略名称；它不是 `SCHED_RR` 的另一个名字。API 策略和内核公平类的具体实现应分层理解。

[CFS 设计文档](https://docs.kernel.org/6.12/scheduler/sched-design-CFS.html) 的历史模型用虚拟运行时间衡量服务量，将可运行实体组织为有序树，倾向选择较小 `vruntime` 的实体。忽略分层和整数实现细节时，增量可写为 `Δvruntime = Δt × W_NICE_0 / W_task`。nice 较低，相对权重较大，同样 CPU 时间增长的虚拟运行时间较少；这为相对份额提供解释，不保证固定 CPU 百分比或业务 deadline，也不能由“缓存最左节点”概括整次调度复杂度。

[EEVDF 文档](https://docs.kernel.org/6.12/scheduler/sched-eevdf.html) 则先判断是否欠该实体服务（eligible），再比较合格实体的虚拟截止时间。正 lag 表示尚欠服务，负 lag 表示已超出公平份额；virtual deadline 不是业务的墙钟截止时间。小请求可以有更早的虚拟截止时间，所以“最小 vruntime”不能代替第二步。

下面是 **PAPER_EXPECTED 纸上快照**，不是实际调度记录或调度器模拟：假设同一层三个始终可运行实体，权重均归一化为 1，没有入出队、迁移或整数舍入。取 `V=(9+10+11.6)/3=10.2`，`lag_i=1×(V-v_i)`。仅为静态算例，将 deadline 视为刚设定的 `v_i + r_i/w_i`，正请求长度分别为 4、1、0.2；等权不要求请求等长。

| 实体 | vruntime v | 归一化 lag | 请求长度 r | 已给虚拟 deadline | eligible |
| --- | ---: | ---: | ---: | ---: | --- |
| A | 9 | 1.2 | 4 | 13 | 是 |
| B | 10 | 0.2 | 1 | 11 | 是 |
| C | 11.6 | -1.4 | 0.2 | 11.8 | 否 |

lag 之和为 0。先排除 C，再在 A/B 中选 deadline 更早的 B；只取最小 vruntime 会错选 A，只比较所有 deadline 也忽略了资格条件。这个推导只解释抽象规则。v6.12 [fair.c 的平均虚拟时间与 eligibility](https://github.com/torvalds/linux/blob/v6.12/kernel/sched/fair.c#L526)、[`pick_eevdf`](https://github.com/torvalds/linux/blob/v6.12/kernel/sched/fair.c#L833) 还涉及当前任务、单实体捷径、`RUN_TO_PARITY` 等条件，不能宣称内核每次进入该函数都必选 B。组调度与 cgroup 限额还会改变实际资源分配；本文不据概览文档重建精确版本迁移史。

## 3. 系统调用：特权入口、软件保存与返回条件

系统调用是请求内核服务的重要受控接口，但库函数不必每次都陷入内核；映射内存和 vDSO 是理解这个区别的两个入口。以下图只表达 Linux v6.12 传统非 FRED x86-64 路径的责任分工，省略追踪、安全检查和其他入口分支，不是所有配置的完整调用全序。

```text
用户态同一任务
  Linux syscall ABI：RAX=调用号
  参数1..6：RDI, RSI, RDX, R10, R8, R9（不是普通C ABI的第四参数RCX）
       |
       | SYSCALL
       v
硬件：返回地址 -> RCX，标志 -> R11；按MSR更新入口/段状态与标志屏蔽
      不自动保存或切换RSP，不把全部通用寄存器压到内核栈
       |
       v
entry_SYSCALL_64 软件：保存用户RSP；按配置处理CR3；加载任务内核栈
                      构造pt_regs -> do_syscall_64 -> 分派/执行内核服务
                      （服务可能阻塞，任务可能被调度走，再继续）
       |
       v
处理返回工作并检查用户状态，结果写回RAX
  符合SYSRET条件 -> 恢复相应状态，以SYSRET返回
  不符合/特定路径 -> 走IRET返回路径
       |
       v
用户态继续；调用者按所用libc API的返回值/errno合同检查结果
```

图中硬件责任来自 [Intel SDM 325462-090 Vol.2B，SYSCALL p.4-698 官方节选](https://cdrdv2-public.intel.com/874240/325462-090-sdm-vol-1-2abcd-3abcd-4.pdf)，软件责任来自 [entry_64.S L47–161](https://github.com/torvalds/linux/blob/v6.12/arch/x86/entry/entry_64.S#L47)。其中 `TSS.sp2` 是入口软件显式使用的临时保存空间，不能读成 SYSCALL 硬件通过 TSS 自动换栈。寄存器 ABI 另见 [syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html)。raw 返回寄存器约定不等于每个 libc 包装函数都有同样的返回类型与错误处理。

v6.12 [`do_syscall_64`](https://github.com/torvalds/linux/blob/v6.12/arch/x86/entry/common.c#L69) 检查 RCX/RIP、R11/flags 是否一致、CS/SS 是否符合约定、IP 是否位于允许的用户范围，以及 RF/TF 等状态；Xen PV 也走 IRET。因而“正常系统调用必 SYSRET”过强。这些是固定源码的返回条件，不是所有未来内核的不变 ABI。

### 3.1 成本为什么需要按条件测量

入口/出口状态处理、内核服务本身、安全缓解以及可能的阻塞都可能付出成本，工作不同便不能用某个固定纳秒数或普通函数调用的固定倍数替代测量。

Intel 已读指令节规定了 SYSCALL 的特定执行排序限制，但后续指令可在早先 store 对其他处理器全局可见之前执行。因此不能把它说成“完整 serializing 指令、通用内存屏障、排空全部写缓冲”，也不能把 Intel 的该条细序直接推广给未核对的 AMD 指令正文。

[PTI 文档](https://docs.kernel.org/6.12/arch/x86/pti.html) 描述启用隔离时的两套页表视图：用户态视图保留进出内核必需的少量映射，故并非“完全不相交”。是否启用受 CPU、内核配置与启动策略影响。v6.12 [`SWITCH_TO_KERNEL_CR3`](https://github.com/torvalds/linux/blob/v6.12/arch/x86/entry/calling.h#L147) 会按特性跳过，配置关闭时宏可为空；PCID 又可影响 no-flush 路径。宏名不证明每次入口都写 CR3，更不证明必清全部 TLB 或固定多出某个百分比。本篇不建议为测量修改缓解或权限设置。

### 3.2 vDSO：把可安全完成的查询留在用户态

[vDSO(7)](https://man7.org/linux/man-pages/man7/vdso.7.html) 描述的是内核映射到进程的 ELF 共享对象，具有符号与版本 ABI；通常由 libc 检测并选择合适入口。对支持的时间查询，它可读取内核提供的时间数据和可用时钟源，在用户态完成换算，省去那次陷入。这解释了减少高频查询开销的动机，但不是“一页数据、固定 RDTSC、所有时钟都只需 5ns”的合同。

支持情况还取决于架构、符号、clock id 与 clocksource。v6.12 [`__cvdso_clock_gettime_common/data`](https://github.com/torvalds/linux/blob/v6.12/lib/vdso/gettimeofday.c#L227) 先检查 clock 范围和支持位，再尝试相应路径；不能处理时调用 fallback。因此调用者仍检查 `clock_gettime` 的结果。直接用户态路径不经过 syscall trace，`strace` 中没有相应条目不能证明应用没有查询时间。

## 4. 内存执行风险与有限预触摸

### 4.1 只在明确模式下解释地址拆分

下图限定 **x86-64 四级分页、4 KiB 普通页**，拆的是地址低 48 位。Linux 的软件层次为 PGD→P4D→PUD→PMD→PTE；在此四级模式中 P4D 折叠，不能挤掉 PTE。

```text
低48位：
| 47..39 (9位) | 38..30 (9位) | 29..21 (9位) | 20..12 (9位) | 11..0 (12位) |
| PGD / PML4   | PUD / PDPT   | PMD / PD     | PTE / PT     | 4 KiB页内偏移 |
      |                |              |              |
      +-- 下一层表 ----+-- 下一层表 ---+-- 下一层表 ---+-- 页帧 + 偏移
软件层次中的P4D在这里折叠；本图不是五级分页或大页叶项的地址格式
```

该模式的高位仍须满足 canonical 约束：位 63..48 是位 47 的符号扩展。Linux 的用户与内核范围有划分，低 48 位可组合不表示全部 256 TiB 都是连续可用的用户地址，更不是任意 64 位值都有效。五级分页改变有效地址范围和层数，大页可能在更高层结束翻译。依据：[Page Tables 的层次/折叠](https://docs.kernel.org/6.12/mm/page_tables.html)、[5-level paging](https://docs.kernel.org/6.12/arch/x86/x86_64/5level-paging.html)、[x86-64 Memory Management 的范围与 canonical 说明](https://docs.kernel.org/6.12/arch/x86/x86_64/mm.html)。

### 4.2 TLB miss、可服务缺页与非法访问

TLB 未命中只表示快表未给出可用翻译。硬件可继续走页表，且页表数据/中间翻译也可能命中缓存，所以“TLB miss＝缺页＝五次 DRAM”是错误等式。

Page fault 是异常：原因可以是需求分配、COW、缺失页，也可以是权限或无效地址。有效映射中可被内核服务的 fault，按服务是否需要 I/O 区分 minor/major；minor 不仅是“分一个空闲页”，major 也不对应固定 4 KiB、固定磁盘操作或固定毫秒数。无权写入、越界等错误不能用“正常 major/minor”掩盖，可能以信号结束访问。[getrusage(2) 的 minflt/majflt](https://man7.org/linux/man-pages/man2/getrusage.2.html)

主循环对延迟敏感时，首次分配、COW 或 I/O 服务都可能超过当前预算；风险取决于负载和存储/内存状态，不能从一次 major fault 推出必卡一到两帧。应把映射、首次访问与 steady-state 业务分开规划和观测。详细正确例、文件映射边界及 COW 机制见 [02](02-虚拟内存、PageFault与mmap.md)。

### 4.3 三个合同：分配、触碰、锁页

1. **预分配**把取得资源的工作提前。匿名 `mmap` 得到连续虚拟区间，不承诺物理连续或所有后备页已按最终用途就绪
2. **预触摸**在准备阶段实际访问选定范围，把这次首次写的相关工作提前；它不保证之后没有 COW、其他区域的 fault 或回收后的工作
3. **锁页**是另外的驻留策略，涉及范围、限额与生命周期；触摸成功不等于锁定成功，锁定也不等于整个系统关闭 swap

下面只演示前两项及回收。它是用 C++17 编写的 **Linux/glibc `mmap` 字节存储练习**，依赖该平台映射与字节访问约定；`mmap` 和指针转换本身不是纯 ISO C++17 的任意对象/数组寿命创建证明。不要把这段代码改称通用对象 arena。

程序先取得实际基础页大小，再检查上限和乘法边界，只映射两页、总量不超过 2 MiB。映射成功后立即进入唯一 owner 管理；owner 不可复制或移动，借用指针仅在 owner 存活的块中访问，不逃逸。`cleanup` 先构造且活得更久，析构不抛异常，把一次 `munmap` 尝试结果传回主函数。

完整文件 `owned_pretouch.cpp`：

```cpp
// Linux/glibc mmap byte-storage exercise, written in C++17.
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <cerrno>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <cstring>
#include <limits>
#include <sys/mman.h>
#include <unistd.h>

struct CleanupResult {
    bool attempted = false;
    bool succeeded = false;
    int error = 0;
};

class OwnedMapping {
public:
    OwnedMapping(void* address, std::size_t length, CleanupResult& result) noexcept
        : address_(address), length_(length), result_(result) {}
    OwnedMapping(const OwnedMapping&) = delete;
    OwnedMapping& operator=(const OwnedMapping&) = delete;
    OwnedMapping(OwnedMapping&&) = delete;
    OwnedMapping& operator=(OwnedMapping&&) = delete;
    ~OwnedMapping() noexcept {
        result_.attempted = true;
        result_.succeeded = (::munmap(address_, length_) == 0);
        result_.error = result_.succeeded ? 0 : errno;
    }
    volatile unsigned char* bytes() noexcept {
        return static_cast<volatile unsigned char*>(address_);
    }
private:
    void* address_;
    std::size_t length_;
    CleanupResult& result_;
};

int main() {
    errno = 0;
    const long raw_page = ::sysconf(_SC_PAGESIZE);
    if (raw_page <= 0) {
        std::fprintf(stderr, "sysconf(_SC_PAGESIZE) failed: value=%ld errno=%d\n",
                     raw_page, errno);
        return 1;
    }
    const auto page_value = static_cast<std::uintmax_t>(raw_page);
    constexpr std::uintmax_t max_page = 1024U * 1024U;
    if (page_value > max_page ||
        page_value > std::numeric_limits<std::size_t>::max() / 2U) {
        std::fputs("page size outside this small exercise's bound\n", stderr);
        return 1;
    }
    const auto page = static_cast<std::size_t>(page_value);
    const std::size_t length = page * 2U;
    void* const address = ::mmap(nullptr, length, PROT_READ | PROT_WRITE,
                                 MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (address == MAP_FAILED) {
        std::fprintf(stderr, "mmap: %s\n", std::strerror(errno));
        return 1;
    }

    CleanupResult cleanup;
    bool values_ok = false;
    {
        OwnedMapping owned(address, length, cleanup);
        volatile unsigned char* const bytes = owned.bytes();
        bytes[0] = 17;
        bytes[page] = 29;
        values_ok = bytes[0] == 17 && bytes[page] == 29;
    }  // The sole owner attempts munmap once; cleanup result outlives the owner.
    if (!cleanup.attempted || !cleanup.succeeded) {
        std::fprintf(stderr, "munmap failed: %s\n", std::strerror(cleanup.error));
        return 1;
    }
    if (!values_ok) {
        std::fputs("byte readback failed\n", stderr);
        return 1;
    }
    if (std::printf("page_size=%zu mapped_bytes=%zu touched_pages=2 readback=PASS unmapped=1 lock_requested=0\n",
                    page, length) < 0 || std::fflush(stdout) == EOF) {
        return 1;
    }
    return 0;
}
```

这条成功链必须完整成立：有效 page/length → 映射成功 → 写两个基础页起点 17/29 → 读回匹配 → 正常离开 owner 作用域 → `munmap` 返回成功 → 结果输出刷新成功 → 退出 0。任一已检查环节失败都不报成功。映射成功到 owner 接管之间仅有不抛出的本地标量初始化；当前调用只建立一个 owner，public 接管构造器并不能防住所有未来误用。

`volatile` 让教学字节读写实际发生，不提供线程同步；`touched_pages=2` 只指两个虚拟页偏移被写过，不证明恰好分配两个物理页、恰好发生两次 fault 或长期常驻。`&&` 在首个读回失败时可能短路，成功路径则要求两个值都匹配。

RAII 覆盖正常离开及实际发生的栈展开。本例没有运行异常用例；信号、`abort`、`_Exit`、OOM kill 或未捕获异常等不提供统一“必析构”保证。进程终止时系统回收地址空间也不能当作本例析构成功证据。输出可能在刷新失败前已部分显示，所以必须同时看文字和退出状态；`fflush` 不是存储持久化保证。API 依据：[mmap/munmap 的 RETURN VALUE](https://man7.org/linux/man-pages/man2/mmap.2.html)、[sysconf 的 PAGESIZE](https://man7.org/linux/man-pages/man3/sysconf.3.html)。

### 4.4 需要锁页时怎样作决定

这次练习不调用锁页 API。实际系统只有在“哪段内存、哪个阶段的 fault 风险”已明确后，才值得设计锁页：确定自有范围和字节预算 → 核对 `RLIMIT_MEMLOCK`、权限及其他组件的锁定责任 → 选择局部范围或进程级策略 → 检查 API 返回和实际锁定指标 → 评估尾延迟及资源代价 → 按同一 owner 范围释放。失败时记录错误并选择降级或停止进入依赖锁页的关键阶段，不能继续打印 locked。

[mlock(2)](https://man7.org/linux/man-pages/man2/mlock.2.html) 区分普通锁定、on-fault 形式和 `mlockall` 标志。权限不足不是唯一失败原因；非特权调用也可能在限额内成功。`MCL_FUTURE` 是进程范围的未来映射策略，后续分配乃至栈增长可能因限额失败；`fork`/COW 又会引入另外的访问工作。一个局部工具不能随意 `munlockall` 撤销其他组件的锁定。保留这些条件，才有依据判断是否值得调优，而不是把所有服务器都套进锁页配方。

### 4.5 按映射和时间解读内存指标

[smaps(5)](https://man7.org/linux/man-pages/man5/proc_pid_smaps.5.html) 给出每个 mapping 的细分：Rss 是当前驻留量，汇总多个进程时共享页会重复计入；Pss 按共享者分摊，例如同一批 10 MiB 页全部被 10 个进程共享时，各分摊 1 MiB。`Private_Clean` 与 `Private_Dirty` 分别计私有干净/脏页，后者不包含全部私有占用，更不是独自成立的泄漏证据。

排查增长应比较同一 mapping、相近负载和多个时点，并关联对象/资源寿命；虚拟区间变大也不等于相同大小已驻留。锁定状态可结合 `smaps` 的 `Locked` 和 `status` 的 `VmLck`，单个快照不证明未来无 fault。详细映射指标与回收边界继续由 [02](02-虚拟内存、PageFault与mmap.md) 展开。

## 5. 亲和性和策略选择：先知道限制了什么

### 5.1 亲和性为什么可能有用，也可能使等待更久

减少不必要迁移可能改善局部性，尤其是稳定工作集的服务器主逻辑线程；但缩小可运行集合也减少了调度器的选择，若目标 CPU 忙，runnable 排队可能更久。CPU affinity 是每线程的允许运行集合，CPU 编号指逻辑 CPU。编号 2 不能直接读成“第二颗物理核”；物理核、package、SMT sibling 关系要查 [CPU topology](https://docs.kernel.org/6.12/admin-guide/cputopology.html)。

实际集合受在线/可用 CPU 和 cpuset 等约束。限制集合不提供独占、关闭 SMT、IRQ 隔离、NUMA 本地内存或硬实时保证，读回一个 mask 也不说明此刻正在其中哪颗 CPU 上运行。[sched_setaffinity(2) 的 NOTES 与大 mask 边界](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html)

若有真实绑定需求，应完整走：确认目标 TID 与延迟预算 → 读当前 mask 和拓扑/资源约束 → 选有依据的逻辑 CPU 集合并确认权限 → 检查 setter 返回 → 重读实际 mask → 在同负载下检查业务尾延迟与其他线程影响 → 无收益或更差时按已准备方案回退。失败意味着“目标未实现”，不能继续按绑定成功假设运行。以下只完成安全的查询与编号判定，不改变集合。

### 5.2 完整只读 mask 练习

`affinity_query.c` 使用 C11、Linux/glibc 与 `-pthread`。它先验证 `strtol` 的范围错误、空转换、尾字符和编号边界，再允许编号进入 `CPU_*`。语法沿用 `strtol`，允许前导空白及正负号；`+0`、`-0` 可表示 0，不是“只接受无符号数字串”的解析器。

固定 `cpu_set_t` 使练习有限；若内核 mask 大于该缓冲区，查询可能返回 `EINVAL`，此时明确失败，不静默截断。真实大系统需另设计动态 mask 支持。无参选择此次快照中的首个成员，不假设 CPU 0 可用；查询目标是 `pthread_self()`，不是整个进程所有线程。依据：[CPU_SET(3)](https://man7.org/linux/man-pages/man3/CPU_SET.3.html)、[pthread affinity 的错误码与限制](https://man7.org/linux/man-pages/man3/pthread_setaffinity_np.3.html)。

```c
/* Linux/glibc C11: read-only affinity snapshot exercise. */
#define _GNU_SOURCE
#include <errno.h>
#include <limits.h>
#include <pthread.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

enum membership { INVALID_ID, NOT_IN_SNAPSHOT, IN_SNAPSHOT };

static enum membership classify(const cpu_set_t *set, long cpu) {
    if (cpu < 0 || cpu >= CPU_SETSIZE) return INVALID_ID;
    return CPU_ISSET((int)cpu, set) ? IN_SNAPSHOT : NOT_IN_SNAPSHOT;
}

int main(int argc, char **argv) {
    if (argc > 2) {
        fprintf(stderr, "usage: %s [logical_cpu_id]\n", argv[0]);
        return 2;
    }
    long requested = 0;
    if (argc == 2) {
        char *end = NULL;
        errno = 0;
        requested = strtol(argv[1], &end, 10);
        if (errno == ERANGE || end == argv[1] || *end != '\0' ||
            requested < 0 || requested >= CPU_SETSIZE) {
            fprintf(stderr, "invalid ID: require 0 <= id < CPU_SETSIZE=%d\n", CPU_SETSIZE);
            return 2;
        }
    }

    /* Pure local mask checks: no affinity changes. */
    cpu_set_t synthetic;
    CPU_ZERO(&synthetic);
    CPU_SET(0, &synthetic);
    if (classify(&synthetic, -1) != INVALID_ID ||
        classify(&synthetic, CPU_SETSIZE) != INVALID_ID ||
        classify(&synthetic, 0) != IN_SNAPSHOT ||
        (CPU_SETSIZE > 1 && classify(&synthetic, 1) != NOT_IN_SNAPSHOT)) {
        fputs("mask checks failed\n", stderr);
        return 1;
    }

    cpu_set_t snapshot;
    CPU_ZERO(&snapshot);
    int rc = pthread_getaffinity_np(pthread_self(), sizeof snapshot, &snapshot);
    if (rc != 0) {
        fprintf(stderr, "pthread_getaffinity_np: %s (%d)\n", strerror(rc), rc);
        if (rc == EINVAL)
            fputs("fixed cpu_set_t may be too small; no mask result claimed\n", stderr);
        return 1;
    }
    int first = -1;
    int count = 0;
    for (int cpu = 0; cpu < CPU_SETSIZE; ++cpu) {
        if (classify(&snapshot, cpu) == IN_SNAPSHOT) {
            if (first < 0) first = cpu;
            ++count;
        }
    }
    if (first < 0) {
        fputs("empty snapshot; no usable logical CPU observed\n", stderr);
        return 1;
    }
    if (argc == 1) requested = first;
    enum membership result = classify(&snapshot, requested);
    if (printf("mask_checks=PASS count=%d logical_cpu=%ld in_snapshot=%d changed_affinity=0\n",
               count, requested, result == IN_SNAPSHOT) < 0 || fflush(stdout) == EOF) {
        return 1;
    }
    /* Membership is one observation, not a promise that a later set will work. */
    return result == IN_SNAPSHOT ? 0 : 3;
}

```

局部 synthetic mask 的负数/上界分类先返回，未把非法编号传给宏；宏参数也无副作用。pthread API 失败时用它直接返回的错误号 `rc` 解释，不误读 `errno`。

退出 0 表示读到非空快照且所选编号在其中；退出 3 表示合法编号在此次快照中不是成员；退出 2 表示参数被拒绝；查询、内部检查或输出失败为 1。`changed_affinity=0` 对应程序未调用 setter，不是测量了整个宿主状态恒定。CPU 热插拔或外部策略随时可改变之后的集合，这个快照既不是未来可用性承诺，也不能证明线程运行位置。

### 5.3 普通权重、FIFO 和 RR 的适用差别

| 机制 | 改变什么 | 仍须处理的边界 |
| --- | --- | --- |
| `SCHED_OTHER` / nice | 普通分时策略中的相对权重；Linux nice 较低权重较高 | 组调度/cgroup、可运行竞争与阻塞影响实际份额；不是固定 CPU 配额或业务 deadline |
| `SCHED_FIFO` | 实时优先级及同优先级队列次序；没有 RR 式时间量子轮转 | 更高优先级抢占、阻塞、yield、运行预算/节流等；忙等会挤压其他工作 |
| `SCHED_RR` | 在 FIFO 规则基础上，同优先级线程按时间量子轮转 | 量子耗尽不等于业务完成；仍有更高优先级与资源依赖 |

Linux 的实时优先级范围为 1–99，但跨平台代码应查询 `sched_get_priority_min/max`。nice 在 Linux 上是每线程属性；降低 nice 的权限、`RLIMIT_NICE`，以及 RT 的 `CAP_SYS_NICE`/`RLIMIT_RTPRIO` 都要分别核对。获得权限不意味着具备运行预算，RT throttling、`RLIMIT_RTTIME` 与其他资源竞争仍可能改变行为。[sched(7) 的策略、nice、Privileges/resource limits、Limiting CPU usage](https://man7.org/linux/man-pages/man7/sched.7.html)

为主逻辑线程提升优先级前，先用 2.1 的状态分解确认它确实在等 CPU；如果它正在等磁盘、缺页或持锁者，调权重不会消除这项依赖。再明确需要的响应预算、可持续 CPU 占用、同核其他任务和故障恢复方式；有权限且预算成立后才进入受控变更、读回与对照评估。API 失败应保留失败记录并维持原策略假设，不能用一个默认 50 的布尔函数掩盖原因。

非阻塞的 RT 忙等可能造成严重饥饿，但不能据此断言所有内核维护必永久冻结；要按系统实际调度和预算限制分析。普通 nice 和 RT 策略都不授予 CPU 独占、NUMA 本地性或端到端硬实时保证。本次未执行 setter、nice/renice、FIFO/RR、cpuset/isolcpus 或权限/预算设置变更。

## 6. 诊断步骤、实践证据和来源边界

### 6.1 先定义目标和窗口，再挑工具

以下均为 **NOT_RUN 诊断计划**，不是这次两个小程序的运行结果。先记录目标 PID/TID、进程身份、起止时间与业务负载；两次快照必须属于同一任务实例。权限不足、目标退出、采样缺失或扰动过大时停止并记录，不能把空结果当正常。再将计数/等待与同窗口的业务延迟关联，只有基础证据不足时才考虑更有扰动的 trace。

| 要回答的问题 | 有限观察方式与范围 | 输出含义及下一步 |
| --- | --- | --- |
| 某线程是否频繁让出/失去 CPU | 同一 `/proc/PID/task/TID/status` 的两次快照；或 `pidstat -w -t -p PID 1 5` | 得到计数增量/频率；与 CPU 负载和业务延迟对齐，再区分正常事件等待或争用，不能直接定因 |
| fault 是否与卡顿同时出现 | 授权进程的 `pidstat -r -t -p PID 1 5` | minflt/majflt 频率提示进一步查映射、首次访问和 I/O；不是 fault 时长，更不是单次物理分配数 |
| 内存增长属于哪个映射 | 对授权进程取有限的 maps/smaps 快照并保持相同口径 | 比较 Rss/Pss、private clean/dirty 与资源寿命；增长趋势仍需解释负载和共享变化 |
| 内核接口调用分布是否异常 | 另行确定目标、采集起止和可接受扰动后考虑 `strace` | `-c` 默认统计 system CPU time；`-w` 才改用起止间 wall time。追踪本身有开销估计与扰动，不是纯 syscall 指令成本 |
| runnable 后为何迟迟没运行 | 分析自己已获授权、目标和窗口明确的调度 trace | `perf sched latency` 的 delay 是 ready/runnable→实际运行的等待；进一步找同 CPU 的竞争和约束，不能当寄存器切换成本 |

[pidstat 手册](https://www.man7.org/linux/man-pages/man1/pidstat.1.html) 的 `-t` 展开线程，`1 5` 限定间隔/次数；表中 PID 必须替换为实际授权目标，不能原样粘贴占位符。没有有限 count 的旧命令容易把不同阶段混在一起。

[strace 手册](https://man7.org/linux/man-pages/man1/strace.1.html) 还规定 `-f -p PID` 会附加该多线程进程的现有线程并跟踪后代，观察范围因此扩大；应先确认是否需要这些对象，不能默认为一个线程。汇总模式可能聚合这些被追踪对象。直接 vDSO 路径可以不出现，调用条目缺席不是应用没有做该项操作的证据。

[perf-sched 手册](https://man7.org/linux/man-pages/man1/perf-sched.1.html) 区分 `timehist` 的 wait（sched-out 到下一次 sched-in 的间隔）与 scheduling delay（runnable 到 running），前者可能包含阻塞等离 CPU 时间。这里仅说明已有 trace 的分析口径；本次没有采集 trace，也没有执行 `perf sched record`、`strace` 或 `pidstat`。真正诊断时需记录内核/工具版本、CPU 与负载条件，不能将不同窗口的统计拼成性能证明。

### 6.2 有限程序怎样复现、怎样判定
