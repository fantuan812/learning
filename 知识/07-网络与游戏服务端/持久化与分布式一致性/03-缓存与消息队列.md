# 缓存与消息队列
> 知识成熟度：L2

> 知识基线：以当前标准、协议或 Linux/工具链版本为准，平台差异需实测。
> 最后更新：2026-08-20。
> 官方参考：https://en.cppreference.com/、https://man7.org/。
> 验证与基准：按文中命令执行最小实验，记录结果与边界。

## 目标
缓存降低热路径延迟，消息队列隔离生产与消费；两者都引入一致性、容量和故障边界。

## 缓存模型
- Cache-aside：读未命中回源，写库后删除缓存。
- Read-through：缓存层封装回源逻辑。
- Write-through：写缓存同步写持久层。
- Write-back：先写缓存，异步刷盘，需处理丢失风险。
- TTL 防止永久陈旧；随机抖动避免同时过期。
- LRU 适合时间局部性；LFU 适合频率热点。
- 分片哈希保持键分布；一致性哈希减少扩缩容迁移。
- 热点键需要本地缓存、请求合并和限流。
- 雪崩：批量过期；穿透：查询不存在键；击穿：单热点失效。
- 布隆过滤器可拦截明显不存在键，但存在误判。

## 一致性
- 删除缓存优先于更新缓存可减少并发覆盖。
- 延迟双删用于降低旧值回填窗口。
- 版本号或 compare-and-set 防止旧写覆盖新写。
- 事件驱动失效时必须保证消息至少一次和幂等。
- 最终一致性需要明确可接受陈旧时间。

## 消息语义
- at-most-once 可能丢消息但不重复。
- at-least-once 可能重复，消费者必须幂等。
- exactly-once 通常只在受控边界内成立，不等于端到端一次。
- 顺序通常只保证分区内顺序。
- 重试应指数退避并设置最大次数。
- 死信队列保存无法处理的消息并触发人工或自动修复。
- 消费位点提交应在业务成功后进行。
- Outbox 将数据库写入与待发送事件放入同一事务。
- Inbox/去重表记录已处理事件 ID。

## 容量与运维
- 估算峰值 QPS、消息大小、保留时间和副本数。
- 监控命中率、回源率、驱逐数、队列深度和消费延迟。
- 队列积压增长率为正时需要扩容或降级生产。
- 分区过少限制吞吐，过多增加元数据和重平衡成本。
- 备份、恢复演练和跨区复制应纳入发布流程。
- 安全上使用 ACL、TLS、租户隔离和密钥轮换。

## 验证实验
1. 注入缓存节点宕机，观察回源洪峰。
2. 重复投递同一事件，验证幂等结果。
3. 暂停消费者，测量积压恢复时间。
4. 模拟乱序事件，验证版本检查。

## 案例：房间状态缓存
以房间快照为例，键为 `room:{id}:v{version}`，值包含版本、更新时间和校验和。
读路径先查本地 L1，再查 Redis L2，最后查数据库；每层都记录命中与耗时。
写路径在数据库事务提交后写 Outbox，再由失效消费者删除 L2。
消费者以事件版本比较，只有新版本才覆盖本地缓存。
进程重启时从数据库恢复热房间，避免冷启动洪峰。
缓存值限制 64 KiB，超过则拆分成员列表与元数据。
热点房间使用单飞锁，锁等待超过 20 ms 直接回源并限流。
删除失败进入重试队列，重试间隔 100 ms、1 s、10 s、1 min。
超过五次进入死信，运维面板提供按键重放。
缓存不可用时启用只读降级，禁止写入旧快照。
所有事件带 trace_id、event_id、entity_version。

## 实验：缓存击穿
准备 1 个 Redis、1 个数据库模拟服务和 100 个并发客户端。
先写入一个 TTL=2 s 的热点键。
使用 `wrk -t4 -c100 -d30s http://localhost:8080/room/1` 产生请求。
记录 p50、p95、p99、数据库 QPS 与 Redis 命中率。
关闭单飞锁，观察过期瞬间数据库 QPS 峰值。
重新开启单飞锁，比较峰值和尾延迟。
加入 TTL 抖动 `ttl + rand(0,300)`，重复测试十轮。
验收条件：数据库峰值不超过稳态的 3 倍，p99 增幅小于 30%。
测试节点故障时，客户端必须收到明确的降级标记。

## 实验：消息幂等与乱序
生产 10 万条带递增版本的更新事件。
随机复制 1% 事件并打乱 5% 的顺序。
消费者先查 Inbox，再执行带版本条件的更新。
统计重复事件、过期版本、成功更新三类数量。
期望最终版本等于最大输入版本，且业务计数不重复增加。
将提交位点提前到业务处理前，验证故障重启时的丢失风险。
将提交位点延后到业务处理后，验证重复投递可由 Inbox 消除。
测量 Inbox 表增长，设计按天分区与保留策略。

## Benchmark：队列吞吐
固定消息大小 256 B、1 KiB、8 KiB 三档。
分别测试 1、4、16、64 个生产者与消费者。
记录 publish latency、consume latency、吞吐和 CPU。
逐步增加分区数，绘制吞吐曲线并标注重平衡时间。
启用 TLS 与压缩各测试一次，报告额外 CPU 和尾延迟。
开启批量发送（batch=1、32、128）比较网络包数量。
在消费者处理时间 1 ms、10 ms、100 ms 下测试积压恢复。
恢复时间定义为队列深度回到基线所需时间。
报告必须包含硬件、内核、客户端版本和完整参数。

## 可运行实验：Redis 缓存击穿
环境：Redis 7.x、Python 3.11、redis-py。使用 asyncio.Lock 实现 single-flight，100 个并发只允许一次回源。
```python
import asyncio,time,redis.asyncio as redis
r=redis.Redis(decode_responses=True); locks={}
async def origin(k): await asyncio.sleep(.02); return 'v-'+k
async def get(k):
 v=await r.get(k)
 if v:return v
 lock=locks.setdefault(k,asyncio.Lock())
 async with lock:
  v=await r.get(k)
  if v:return v
  v=await origin(k); await r.set(k,v,ex=30); return v
async def main():
 await r.delete('hot'); t=time.perf_counter(); await asyncio.gather(*[get('hot') for _ in range(100)]); print((time.perf_counter()-t)*1000)
asyncio.run(main())
```
预期耗时 20--40 ms；删除锁后回源次数接近并发数。验收回源峰值降低 90%。

## Redis 配置基线

开发环境可用 Docker 启动单节点：

```yaml
services:
  redis:
    image: redis:7.2
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "256mb", "--maxmemory-policy", "allkeys-lru"]
    ports: ["6379:6379"]
```

生产环境至少记录 `appendonly`、`appendfsync`、最大内存、驱逐策略、连接上限和慢日志阈值。AOF everysec 允许约一秒数据窗口；always 降低窗口但增加 fsync 延迟。不要把缓存当作唯一事实来源，RDB/AOF 只用于缩短重建时间。

Python 最小客户端：

```python
import redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True,
                socket_timeout=0.2, retry_on_timeout=True)
r.set("room:1", '{"version":7}', ex=30, nx=False)
print(r.get("room:1"), r.ttl("room:1"))
```

C++ 客户端应设置连接池、超时和断线重连；伪代码如下：

```cpp
auto c = pool.acquire();
auto reply = c->command("GET", "room:1");
if (!reply || reply->is_error()) metrics.cache_error++;
```

验收：正常请求超时不超过 200 ms；Redis 不可达时 100% 请求进入可观测的降级分支；连接池耗尽必须有单独指标，不能静默排队。

## Redis 原子性与分布式锁

复合读改写使用 Lua 或事务，不能依赖多条命令之间没有并发。库存扣减示例：

```lua
local n = tonumber(redis.call('GET', KEYS[1]) or '0')
if n <= 0 then return 0 end
redis.call('DECR', KEYS[1]); return 1
```

锁必须带随机 token，释放时用 Lua 比较 token 后删除，避免过期后误删他人锁。租约时间应大于 P99 业务耗时并留有续租余量；长事务优先使用数据库约束或队列串行化，而不是无限续租。

## Kafka 配置与生产者示例

关键配置：生产者使用 `acks=all`、`enable.idempotence=true`、合理的 `linger.ms` 与 `batch.size`；主题设置副本数、`min.insync.replicas`、保留时间和最大消息大小。消费者使用显式提交、静态成员或 cooperative rebalance 降低抖动。

```python
from confluent_kafka import Producer
p = Producer({"bootstrap.servers":"localhost:9092",
              "acks":"all", "enable.idempotence":True,
              "linger.ms":5, "compression.type":"lz4"})
p.produce("room-events", key="room-1", value=b'{"v":8}',
          headers={"event_id":"e-8"})
p.flush(10)
```

`flush` 返回前检查错误回调；生产成功只代表 broker 接收，不代表下游业务已完成。跨数据库和 Kafka 的写入使用 Outbox，而不是试图把两个系统伪装成一个事务。

## Kafka 消费者与重试拓扑

业务处理成功后再提交 offset。失败消息进入带退避级别的重试主题，例如 `events.retry.1m`、`events.retry.10m`，超过次数进入 DLQ。重试消息必须保留原始 event_id、首次时间、失败原因和 schema 版本。

```python
from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers":"localhost:9092",
              "group.id":"room-writer", "enable.auto.commit":False,
              "auto.offset.reset":"earliest"})
c.subscribe(["room-events"])
while True:
    m = c.poll(1.0)
    if m is None: continue
    if m.error(): raise RuntimeError(m.error())
    apply_once(m.key(), m.value())
    c.commit(message=m, asynchronous=False)
```

若 `apply_once` 成功后进程在 commit 前崩溃，消息会重复投递；唯一索引 `(event_id)` 或 Inbox 表必须使第二次处理成为 no-op。不要以 offset 作为业务幂等键，因为重新分区、重放或跨主题复制都会改变 offset。

## RabbitMQ 适用边界

RabbitMQ 更适合工作队列、路由和短消息确认；Kafka 更适合高吞吐日志、长时间回放和分区顺序。RabbitMQ 使用 durable exchange/queue、persistent message、publisher confirms 和 manual ack；仅设置 durable queue 不等于消息已经持久化。

```python
import pika
conn = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
ch = conn.channel(); ch.queue_declare('jobs', durable=True)
ch.basic_qos(prefetch_count=32)
ch.basic_publish('', 'jobs', b'job-1',
  pika.BasicProperties(delivery_mode=2, message_id='job-1'))
```

消费者完成业务后 `basic_ack`，失败用 `basic_nack(requeue=False)` 路由到 DLX；无限 requeue 会造成热循环。使用 quorum queue 时记录节点数、镜像策略和磁盘水位，确认切主期间的可接受暂停时间。

## 一致性故障注入剧本

|注入|操作|观察|通过标准|
|---|---|---|---|
|Redis 主节点断电|停止容器 30 秒|错误率、回源 QPS、恢复时延|无静默写丢失，降级可识别|
|缓存网络丢包|tc 注入 5% 丢包|超时与连接池|p99 小于预算，线程不耗尽|
|Kafka broker 重启|滚动停止一个 broker|ISR、生产错误、consumer lag|无确认成功后的消息丢失|
|消费者崩溃|业务写入后 kill -9|重复处理数|最终状态正确且重复可计数|
|RabbitMQ 磁盘满|限制卷空间|publisher confirm、告警|生产暂停并能恢复，不无限重试|

每项注入保存时间线：注入前基线、注入命令、首个告警、错误峰值、恢复动作、数据校验和复盘结论。恢复后用数据库计数、事件 ID 集合和校验和比对，不能只看服务返回 200。

## Benchmark 可复现协议

固定 CPU 型号、核心数、内存、磁盘、内核、容器镜像 digest、客户端版本和配置文件。压测前预热 60 秒，正式采样 10 分钟，至少重复 5 次并报告中位数与 p95/p99；同时采集 CPU、RSS、网络、GC、磁盘 fsync 和 broker lag。

Redis 基准变量：键大小 64 B/1 KiB/16 KiB，并发 1/32/256/1024，命中率 99%/90%/50%，pipeline 1/32。Kafka 变量：消息 256 B/4 KiB、分区 3/12/48、batch 1/64/256、压缩 none/lz4/zstd。RabbitMQ 变量：prefetch 1/32/256、持久化开关和 quorum/classic queue。

示例命令：

```text
redis-benchmark -h 127.0.0.1 -p 6379 -n 1000000 -c 256 -d 1024 -t get,set
kafka-producer-perf-test --topic room-events --num-records 1000000 --record-size 1024 --throughput -1 --producer.config producer.properties
```

输出至少包括 ops/s、平均延迟、p50、p95、p99、错误数、回源次数、重复率和恢复时间。验收阈值由业务 SLO 给出；没有阈值时不得用“吞吐更高”宣称优化完成。任何参数变更都重新预热和采样，并把原始 CSV、命令行和火焰图放入 evidence 目录。

## 生产前验收清单

- 所有键有 owner、schema、TTL、最大大小和删除策略。
- 所有消息有 event_id、schema_version、trace_id、重试上限和 DLQ 负责人。
- 明确 at-least-once 下的幂等约束及重放流程。
- 明确缓存、队列、数据库之间的 RPO/RTO 和降级行为。
- 监控命中率、回源率、热键、驱逐、连接池、lag、重平衡、DLQ、确认延迟。
- 压测、节点故障、乱序、重复、磁盘满和网络分区均有原始证据。
- 变更可回滚，配置密钥不进入仓库，客户端超时和重试有上限。
- 生产演练结束后清理临时主题、测试键和访问凭据。
- 保留至少一次完整压测的原始日志，确保结果可审计。
- 对关键事件建立端到端 trace，关联生产、消费和数据库提交。
- 对时钟偏移设置告警，事件排序优先使用逻辑版本。
- 记录扩缩容前后分区、连接和缓存槽位的变化。
- 将容量模型中的峰值、增长率和安全余量写入变更单。
- 对客户端库升级执行兼容性、性能和故障回归。
- 检查 TLS、ACL、租户隔离与审计日志是否覆盖管理面。
- 明确人工重放权限、审批人和重复执行保护。
- 复盘结论必须转化为可追踪的工程任务。
