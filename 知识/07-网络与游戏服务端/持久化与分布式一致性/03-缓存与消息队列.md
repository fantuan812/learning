## 1. 目标与责任边界

房间服务希望高频读取快照，更新后又要让其他服务收到变更。数据库承担事实提交，L1/L2 缓存承担可重建的读加速，消息系统承担异步传递；三个“成功”发生在不同边界。缓存命中不能证明它是最新快照，生产确认不能证明消费者完成，消费者提交位点也不能代替业务事务。

本文让读者能把这条链逐项接起来：选择缓存模型 → 定义实体与版本 → 合并回源并限制积压 → 同事务登记事件 → 确认发布 → 原子消费 → 完成或追踪失效任务 → 处理迟到、重复与关停。一般共识、分区与租约原理留给[分布式系统基础](02-分布式系统基础.md)，本篇负责 Redis/Kafka/RabbitMQ 的产品边界和客户端责任。更具体的业务幂等设计见[幂等重试与消息语义](03-幂等重试与消息语义.md)。

先区分三类结果：SUCCESS 是所讨论边界已有肯定证据；DEFINITE_FAILURE 是已知该步未接受或事务已回滚；UNKNOWN 是调用方不知道结果，必须保留同一业务身份并查询、重试或交给持久恢复任务。超时、取消、断连和关停期限用尽通常只能建立 UNKNOWN，不能证明远端没有副作用。

## 2. 缓存模型、命中与陈旧分别是什么

Cache-aside 由应用在未命中时回源，写入数据库后另行失效缓存；优点是数据库可独立运行，代价是两个系统没有共同提交点。Read-through 把回源封装进缓存层，仍要回答失败和并发回填。Write-through 等待持久层完成后再确认写成功，也要定义“缓存成功、数据库失败”如何处理。Write-back 先确认缓存再异步刷盘，缓存此时承担未落盘写的可靠性责任，不能沿用“丢缓存只影响速度”的假设。

LRU/LFU 依据访问局部性或频率选择淘汰对象，Redis 7.2.5 的相应策略是近似算法；它们都不判断业务新旧。`allkeys-*` 可能驱逐失效水位或去重记录，因此不能把正确性必需的状态随普通缓存一起随意驱逐。普通哈希分片与一致性哈希决定键的放置和迁移量；Redis Cluster 的槽位方案不能直接叫作客户端一致性哈希。扩缩容也不自动消除热点键。[Redis 7.2.5 配置注释](https://github.com/redis/redis/blob/7.2.5/redis.conf#L1052-L1075)

雪崩是大量条目集中失效引起的回源压力，击穿关注某个热键失效，穿透关注持续请求不存在对象。TTL 抖动可以分散一批写入的过期时刻；负缓存可以限制不存在对象的重复查询；布隆过滤器仅能在过滤器覆盖完整且及时维护等前提下排除确定不存在的项，阳性仍需查询。新建对象尚未进入过滤器时，不能据此永久拒绝读取。每种措施都必须与回源限流配合。

TTL 只限制一次存储的生存时间，并不检查数据库最新版本。读到旧副本后重新写入、把 L2 剩余寿命重置成完整 L1 TTL、后台反复续旧值，都可能延长陈旧。Redis 7.2.5 `expireGenericCommand` 把相对期限转换为 Unix 毫秒时间；墙钟跳变也会影响期限，不应把 TTL 当作单调时钟证明。[expire.c](https://github.com/redis/redis/blob/7.2.5/src/expire.c#L497-L625)

## 3. 房间身份、L1/L2/DB 与旧回填

本篇 PAPER_EXPECTED 模型只处理完整房间快照，不处理必须逐项执行的增量指令。实体身份为 `(tenant_id, room_id, incarnation)`；房间删除后重建使用新的 incarnation，防止旧房间事件污染新房间。`entity_version` 由数据库事务为同一实体单调分配，`event_id` 标识一次逻辑事件，重试不改它；`schema_version` 描述消息结构，`trace_id` 用于追踪。这几个字段不可互换，墙钟只用于诊断，不用于取代版本顺序。

采用稳定键 `room:{tenant/room/incarnation}:snapshot`，值带实体、版本、完整快照与序列化版本。`{...}` 表示示意的 Redis Cluster hash tag，实际编码必须无歧义并处理输入转义。历史的 `room:{id}:v{version}` 可以保留不可变历史快照，却不能独自回答“当前版本是多少”；若用它，就还需要最新版本发现和旧键回收协议。本例不用猜版本遍历键。

读路径检查 L1 → L2 → DB 权威读。每层都区分 MISS、合法空值、解码/版本错误、超时与服务错误，不能用 `if value` 把空字符串等合法值当未命中。缓存错误可进入有预算的数据库回退，数据库也不可用时返回明确的不可用/允许的陈旧结果，不能从旧缓存反写事实库。只读降级是业务选择，不是 Redis 不可达后所有写请求都必须失败；依赖数据库不变量的写可以继续，前提是事件及失效责任仍有持久记录。

对每一缓存代次和实体维护“已知至少到 v”的失效水位 F。收到 v8 时，原子执行 `F=max(F,8)` 并删除小于 F 的缓存项；回填 v7 必须同时检查当前代次、F 和现有缓存版本，不得用先 GET 再 SET 的两个独立步骤冒充 CAS。L2 上相关键必须在可原子处理的同一范围，L1 用进程内同步。若新版本 v9 已在缓存中，迟到的 v8 失效不应把它降成 v8。

水位解决的是“已知更新之后的旧回填”，不是“尚未收到的更新”。PAPER_EXPECTED 反例：A 读取 DB v7 后暂停；B 提交 DB v8、删除缓存；A 随后把 v7 放回。单删和固定延迟的第二次删除都可被更晚的 A 越过。若失效已建立 F=8，A 的条件写被拒绝；若 F 被驱逐、过期或恢复成旧值，同样的证明就失效。

因此，本例把F和代次视作正确性状态：正常代次内不驱逐，至少保留至该代次全部回填与回调终止，回收还须满足第11节的重放/恢复窗口和旧写者停止条件。水位条目数有硬上限，达到上限时拒绝新缓存入场并限流直读，不能用清掉活跃水位来腾空间。重启、恢复、主从切换或不能确认水位完整时，停止该代次缓存服务和新回填提交，进入BYPASS；已发请求仍受真实在途责任约束。只有业务控制方确认旧代次请求不能再被当前服务接受、建立新代次并以数据库重建所需水位后，才重开缓存；做不到就继续限流直读/不可用。不能把普通Redis复制或一把租约锁当作这个代次隔离已经实现。本篇给的是应用合同，没有实现该控制协议。

删除房间也不能抹掉顺序信息后接受旧快照复活它：在同一 incarnation 中，删除是较高版本的墓碑；重建房间用新 incarnation。事实库的墓碑/身份退役记录须覆盖所有允许的旧事件、回填、备份恢复与人工重放窗口，且回填必须核对实体仍存在。不能证明旧工作已退出或保留窗口已封闭时，停止回收该正确性状态；超出合法重放窗口的输入进入隔离/权威查询，不让缓存的短 TTL 决定墓碑寿命。单独读到版本号再执行普通 SET 仍会竞态，实际接受点缺少原子比较/安装就不能声称已 fence。

未收到失效时，L1 使用短的有限 TTL，L2 有有限 TTL；复制到上层不得无限续旧值。回源快照读取、等待与新回填提交共用总期限。到期后不再向调用者交付该结果，也不再发起新回填；但deadline之前已发给L2的写仍可能在到期后执行，必须保留UNKNOWN责任和真实owner，不能声称取消已阻止安装。该代次不能安全继续服务时进入BYPASS，直至满足实际接受点隔离条件。若要额外声称“到期后绝不安装”，还须让实际接受点原子检查期限、代次及版本，并提供时钟/控制前提；本例没有实现或认证这种强期限保证。

不接受无界旧数据库快照作为新请求结果，也不无限使用 stale-while-revalidate。只有回源工作与已发写影响寿命、各层TTL、恢复路径及时钟误差都有成立的上界，才可推导陈旧上界；本篇没有这组实测证据，因此不声称固定秒数内最新。要求读到自己刚提交的 v8 时，可携带最低版本 8，低于它的缓存回源权威 DB；要求线性化最新读则使用相应数据库/一致性服务接口。恢复缓存必须同时证明旧代次无法被当前服务接受、新代次接受点确实原子比较、水位/墓碑和权威快照已重建、旧在途写不能越过接受点且正确性状态有容量；一个本地数字、普通GET/SET或Redis旧快照均不足，不满足就保持BYPASS。

L1 失效还涉及扇出：同一个 Kafka consumer group 会分配工作，不会把每个事件广播给每个进程。[Kafka 3.8 Consumer Position](https://kafka.apache.org/38/design/design/#consumer-position) 说明分区在组内分配给消费者；本例的跨进程即时失效则是另外需要实现的项目合同。没有该合同的实例依赖已声明的 L1 到期或最低版本检查。下面单进程纸面轨迹会明确 A 收到通知，不能外推所有 L1 同时已失效。

## 4. single-flight：合并一次工作，还要限制全部等待

single-flight 是每个进程、每个实体共享一次在途回源。它降低同一波请求的重复工作，不保证全机群只回源一次，也不保证后续失败重试不会再次回源。历史 `locks={}` 示例把每个见过的键永久留在字典，没有容量、等待上限和完整清理；`asyncio.Lock` 等待者在回源失败后还可能逐个再次回源，故“100 个并发只一次”只在特定成功时间线上成立。

以下是状态伪代码，不是 Python 实现。`B` 限制 live/draining 实体条目总数，`F` 限制每条目等待者，`C` 限制实际在途数据库工作；所有直接回退也共用 C。host拥有registry、supervisor、pool及回调接收对象，入场与关闭使用同一入口门。入场不允许无限等待连接池或信号量。

```text
PAPER_EXPECTED / 进程内协调器
admit(key, deadline):
  在同一入口门内检查 host=OPEN、B、该 key 的 F
  已有 flight: 增加 waiter 引用，取得同一 future
  无 flight: 非阻塞取得实际回源槽 C；登记唯一 flight、operation 与真实owner引用
  登记成功后才允许发布至队列/驱动；supervisor执行，请求只等共享future
waiter 完成/超时/取消:
  只释放自己的引用；不自动取消或移除仍在途的共享工作
supervisor:
  再查缓存；必要时做一次有总期限的权威读
  新回填提交再次通过入口门、deadline检查；实际接受点原子比较代次/水位/版本
  成功或失败都将共享 future 置终态，统一观察异常
  底层工作确实终止后释放 C；底层终止、回调退场且引用为零才按flight身份删除条目
```

关键是把请求生命期与底层工作生命期分开。一个等待者取消不能取消其他等待者的 future；超时不等于数据库操作或 Redis 写已经停止，不能提前释放 C、删掉条目再开第二波。若驱动不能确认底层终止，条目进入draining/UNKNOWN，仍占实际容量并持有对象，拒绝新增工作并告警，直到取得实际退场证据；没有这种证据就维持未关闭。清理必须比较条目身份与代次，避免旧任务的finally删除新flight，future只能置终态一次。失败可设置短的受限退避，但不能将错误冒充不存在的业务数据。

PAPER_EXPECTED：B=2、F=3、C=1仅为手算参数。热键k有一个leader与两个跟随等待者，共享同一次读；第4个同键请求被拒绝或返回已允许的陈旧值。另一个键不能绕过C直接回源。若leader请求取消，supervisor继续；若底层读取明确失败，所有等待者得到同一失败，仍须底层终止、回调退场且引用归零后才回收条目，下一次获准请求才开启下一波。这个轨迹证明模型的容量记账，不证明20–40ms或回源下降90%。

有限宿主的关闭合同是PAPER_EXPECTED，不能由一个超时预算推导它必然完成：

|状态|允许的转移与对象责任|
|---|---|
|OPEN|入口门内检查状态并登记flight/operation、真实槽和owner引用，成功后才发布。登记/发布明确失败由同一所有者回滚本地资源；外部接受未知则保留UNKNOWN|
|CLOSING|在同一入口门内将OPEN改成CLOSING，拒绝新请求、新回填提交和新重试派发。此前已登记并发布的工作仍归原owner，不能漏掉“关闭枚举之后才可见”的工作|
|DRAINING|等待所有已发布DB读、L2写、producer回调、consumer完成与registry清理退场。每个operation/回调持有实际owner引用；请求取消只减自身waiter引用，不销毁pool/registry/host|
|预算到期仍未静默|close返回INCOMPLETE/UNKNOWN，host保持DRAINING，保留依赖对象、真实容量和回调接收端。持久待办只交接业务恢复，不授权内存对象销毁；父宿主也不能销毁它|
|CLOSED|入口封闭且再无新增发布可能，实际底层访问及回调均已确认退场，leases归还、queue/registry清空，才允许销毁host和pool|

登记后但发布尚未决的operation也必须留在registry中、持有owner引用；关闭时只有明确证实它未发布且以后不会发布，才可撤销其本地资源，不能因为它未出现在“已发布”枚举里而漏账。退场证据必须来自实际宿主与固定driver提供的完成/回调静默保证；抽象inflight计数、future终态、取消成功或flush预算结束都不足。driver若还可能通过隐藏线程、连接回收或延迟回调访问对象，即使账本计数为零也不能CLOSED。没有可证明静默点，合法停止线是持续DRAINING和对象持有，不能编造最后一次完成事件。强制退出若另需进程隔离和外部接受边界，应另行定义与授权，本篇不执行或认证。

PAPER_EXPECTED关闭轨迹：B=2、F=3、C=1，k已登记发布后入口关闭，三个waiter都离开但底层仍运行，则C仍为1、host仍存活，第一次close预算到期返回INCOMPLETE。只有真实底层完成、回调完成身份核对并退场后，才归还C、移除条目，再判断CLOSED；若底层永不终止，结论就是持续DRAINING。Python redis-py关闭/取消与C++ pool实现仍未版本化核对，下面只给接口合同，不能作为已编译客户端：

```cpp
// PAPER_EXPECTED / 伪代码：pool 的具体库与 ABI 未核对

if (!lease) return Overloaded;

// 必须区分 Miss、Value（含空值）、DecodeError、TimeoutUnknown、ServiceError
```

## 5. 同事务 Outbox 与原子 Inbox

原文消息语义节“Outbox 将数据库写入与待发送事件放入同一事务”是正确的；房间案例“数据库提交后再写 Outbox”与它冲突。如果提交 v8 后进程停止、事件行尚未写入，就出现永久缺失的通知。正确顺序是在一个本地事务内更新 Room、登记请求结果并插入 Outbox，然后一起提交。数据库事务不能包住外部 Kafka 或 Redis。[PostgreSQL 16 事务](https://www.postgresql.org/docs/16/tutorial-transactions.html)

为防止“同事务”指代不清，本例将 Room、RequestResult、Outbox 放在 FactDB 的一个事务域，FactDB 是房间事实权威；将 Inbox、Projection、InvalidationTask 放在 ViewDB 的一个事务域，ViewDB 是消费结果与待办责任的持久记录，Projection 只是派生视图。T1 属于 FactDB，T2 属于 ViewDB；二者没有共同原子提交点。InvalidationTask 只表示 ViewDB 已接手后续工作，实际 Redis/L1 删除、水位安装及其确认都发生在 T2 之外。

T1的请求身份不能只有一个可跨租户误用的裸ID。本例唯一键为 `(tenant_id, authenticated_actor_id, request_id)`，记录并比较实体（含incarnation）、操作种类、请求schema、expected_version与规范化业务负载摘要。规范化规则固定字段/类型/编码和版本；不能使用会随序列化顺序变化的随意JSON字符串，也不把trace或重试时间当业务参数。同ID同绑定返回原终态；同ID不同实体、操作或规范参数为CONFLICT，不能返回旧成功冒充新操作完成。摘要只是比较机制，实际保留足以验证绑定的规范参数/摘要版本并处理碰撞风险。

```text
PAPER_EXPECTED / 一个事实库事务 T1
前提：实体 E=(t,r,incarnation) 存在；请求作用域键 R 和规范绑定 D 有固定定义
BEGIN
  读取/唯一认领 R；若已有已提交终态，比较 D：一致返回原结果，否则 CONFLICT
  原子预留/登记本次RequestResult、Outbox所需持久容量；失败则不提交业务成功
  条件更新 Room：expected_version=7 -> version=8，写完整快照
  若唯一竞争或版本条件不满足：ROLLBACK本次事务，进入原终态判定
  插入唯一 Outbox(event_id=e8, entity=E, version=8, snapshot, schema_version)
  登记 RequestResult(R,D) -> 已提交结果(version=8,event_id=e8)
COMMIT
原终态判定（本次事务退出后，在能见已提交结果的FactDB权威边界）：
  若R存在终态且D一致 -> 返回原结果；D不一致 -> CONFLICT
  若竞争/旧事务可能仍未决、读取不可用或结果不可判定 -> UNKNOWN，保留R
  仅证实无同R已提交/在途成功且本次确实回滚时，才返回逻辑请求的确定失败
```

数据库明确回滚只证明本次事务DEFINITE_FAILURE，不证明同一逻辑请求从未成功。两个相同R/D并发都曾读不到结果时，一个可能提交8/e8，另一个因唯一竞争或版本条件失败回滚；后者应在旧事务外查询已提交原终态，返回同一个8/e8。读不到结果也不足以证明不存在，若另一事务未决或权威读取不可用，保持UNKNOWN。COMMIT回复丢失同样按R/D查询/安全重试，不能换ID或重生成事件。发件器只读已提交Outbox；经确认后更新发送状态，更新未知允许重发同一e8。限制扫描批次、在途数、重试次数和总时长；停止热重试后仍保留持久待办及负责人。

消费者不能“先查 Inbox 不存在，再脱离事务写业务”。两个消费者可以同时查到不存在；业务成功而去重记录失败也会重复执行。下面的 T2 使去重认领、完整快照投影和后续失效责任同一提交。Inbox 的唯一键为 `(consumer_role, event_id)`，并记录实体、schema 和负载摘要；相同 ID 不同内容是冲突，需隔离，不作为普通重复吞掉。[PostgreSQL 16 INSERT：ON CONFLICT 与 RETURNING](https://www.postgresql.org/docs/16/sql-insert.html)

```text
PAPER_EXPECTED / 一个消费者数据库事务 T2
BEGIN
  尝试唯一插入 Inbox(role, event_id, payload_digest)
  已存在：核对 digest；一致则返回已保存的处理结论，不重复应用
  新认领：按同一实体串行化/原子条件更新 Projection
    incoming_version > current_version -> 用完整快照替换
    incoming_version < current_version -> 记为 STALE，无副作用
    incoming_version == current_version -> 摘要一致才 NOOP，否则 CONFLICT
  原子登记/合并每个目标的InvalidationTask并预留所需容量；不能登记则ROLLBACK
  将Inbox处理结果与Projection、各目标失效责任一起提交
COMMIT
```

实际实现须保证投影不存在时的创建与更新也受唯一约束/并发控制，检查每个条件更新的结果；不能只贴伪代码就声称数据库并发正确。T2明确回滚时本次Inbox/Projection/Task均不留下半边，原位点不越过；提交回复丢失则查询 `(role,event_id,digest)` 的已提交终态，或在相同唯一约束下重试，不能盲目推进位点。T2成功只证明业务与责任持久，Redis/L1实际失效仍在事务之外。

本例采用合并任务，但按 `(entity, cache_generation, target_id)` 分开记录，每行有不复用的task_id、required_version、completed_version；L2与显式加入证明的L1_A是不同target，单个L2回执不能替代所有L1。T2在同事务内以原子操作提升required=max(required,目标版本)，不得降低或清掉completed。STALE/重复事件复用已有责任时也不能删除它；新代次/新目标必须建立独立任务身份，不把旧代次DONE搬过去。

worker领取 `(task_id,g,target,v_taken)` 后，在实际缓存接受点原子核对g并安装至少v_taken的水位及完成相应失效。只有获得该目标/代次的明确成功回执，才在ViewDB中按同一个task_id/g/target原子推进completed=max(completed,v_taken)。DONE必须由更新后的completed≥required导出，不能无条件标记，更不能直接删行。若required从8提升到9，旧W8回执只能推进completed到8，任务仍PENDING；W9明确完成后才可到9。任何目标不匹配、缓存操作未知、完成标记未知或失败，都保留待办并查询/按原身份重试。

持久容量也是事务成立条件：T1无法原子容纳RequestResult/Outbox，或T2无法容纳Inbox/必要目标任务时，必须回滚/拒绝本次业务提交，不能先确认成功再寄望异步后补。并发容量预留也需在事务域内原子成立，单独“先查剩余容量”不够。事务结果未知按上述原终态规则处理，原消息保持未越过连续前沿；不能删除未确认责任为新任务腾位置。

“最大版本最后赢”只适用于这里的可替代完整快照。库存增减、结算、奖励等增量事件若跳过中间版本，会遗漏必须发生的效果，需连续序列/补齐协议或单独幂等副作用设计。Inbox 保留期必须覆盖允许的消息保留、跨主题重放、人工补发及备份恢复窗口；删除去重记录后再次回放，就不再有“应用一次”的证明。

## 6. Kafka：事件身份、分区、发布确认

消息语义总要带范围：at-most-once 允许丢失而不重投；at-least-once 在指定持久性、重试与恢复前提下允许重复，并非无限故障或保留期耗尽后仍必达；exactly-once 要说明“一次”的对象是日志记录、事务输出还是业务效果。本文的目标是允许至少一次传递，以业务身份和原子消费避免重复业务应用，而不声称网络只传一次。

以实体 E 的稳定编码作为 key，把 event_id 放在消息头或负载用于去重。每个事件都以 event_id 作 key 可能将同一房间分散到不同分区；按实体作 key 也只在相同分区器、键字节与分区布局等前提下维持映射。跨客户端分区器差异、增加分区、转发至其他主题和多个发布者乱序，都需要业务版本检查。broker 保持分区日志顺序，不负责恢复应用原本想要的顺序。[Kafka 3.8 协议：Partitioning](https://kafka.apache.org/38/design/protocol/)、[Debezium 3.0.0.Final 的 id/aggregateid 分工](https://github.com/debezium/debezium/blob/v3.0.0.Final/documentation/modules/ROOT/pages/transformations/outbox-event-router.adoc#L119-L143)

`acks=all` 等待当前 ISR 确认；与副本数和 `min.insync.replicas` 一起定义可用性/数据安全取舍，不等于所有配置副本始终可用，更不覆盖所有副本数据丢失、误删和任意灾难。生产幂等处理协议范围内的重试重复，不能按业务 event_id 识别发件器重启后重新调用 produce 的同一逻辑事件。[Kafka 3.8 Design 与复制条件](https://kafka.apache.org/38/design/design/#replication)

Kafka 3.8 的 Java producer 配置页与 librdkafka v2.5.0 不是同一套默认值。例如 librdkafka 的 `enable.idempotence` 默认 false，本例显式开启；`linger.ms`、批量、压缩、队列大小和投递期限必须按实际客户端配置，不能照抄另一客户端默认。静态成员/cooperative rebalance 可能降低某些场景的抖动，不替代消费所有权与提交合同。[librdkafka v2.5.0 配置](https://github.com/confluentinc/librdkafka/blob/v2.5.0/CONFIGURATION.md)

以下是既有 Python producer 用途的有限 API 节选；p 已由有界配置创建，payload 已序列化，存储方法仅表示发件器状态机，不是已实现持久代码。不要执行本段。

```python
# PAPER_EXPECTED / confluent-kafka 2.5.0 API 节选
results = {}                    # 本批容量必须有上限
def delivery(err, msg, eid=e8):
    results[eid] = (err, msg.topic(), msg.partition(), msg.offset())

try:
    p.produce("room-events", key=entity_key, value=payload,
              headers={"event_id": e8}, on_delivery=delivery)
except BufferError:
    record_not_enqueued(e8)      # 本次调用未入本地队列；保留 Outbox
else:
    remaining = p.flush(timeout=shutdown_budget_seconds)
    if e8 not in results:
        retain_unknown(e8, remaining)
    elif results[e8][0] is None:
        persist_confirmed_delivery(e8, results[e8][1:])
    else:
        retain_for_error_classification(e8, results[e8][0])
```

这里 `produce` 返回只表示本地异步入队；`poll`/`flush` 驱动回调，`flush` 返回剩余队列数量。剩余为零仍可能有投递失败，所以必须逐事件检查回调；剩余非零或没有对应回调保留 UNKNOWN。错误回调也应按错误类别判断是否可证未发送，不能把所有失败解释为 broker 从未接受。关停不能仅调用一次flush就标全批成功或销毁回调依赖，重启仍可能重发。`persist_confirmed_delivery` 的DB更新若未知，继续保留可重放责任；内存对象按第4节静默合同存活。生产确认没有包含T2的业务结果。[本轮自标2.5.0的Producer API快照](https://docs.confluent.io/platform/7.6/clients/confluent-kafka-python/html/index.html#producer)

## 7. Kafka：offset、并行间隙与重试转交

串行单分区处理可在T2确认提交后显式提交 `message=m`；本API提交的是该消息所在分区的 `offset+1`。不带message/offsets的commit会使用分配分区的存储位点，不能随手用于并行工作。配置同时关闭 `enable.auto.commit` 与 `enable.auto.offset.store`，把进度记录完全交给本例的应用合同，避免将已交付给应用但未处理的记录误当完成。[本轮Consumer API快照](https://docs.confluent.io/platform/7.6/clients/confluent-kafka-python/html/index.html#consumer)

来源存在一个具体不一致：本轮自标2.5.0的API快照，commit说明写 `.err`，TopicPartition类说明写 `.error`；固定confluent-kafka-python v2.5.0的 `TopicPartition_members` 实际暴露 `error`，没有 `err`。本例以固定tag成员表为准用 `part.error`；这是该成员的窄源码核对，不是整个客户端认证。`platform/7.6` URL本身不能证明Python版本。[固定v2.5.0成员表](https://github.com/confluentinc/confluent-kafka-python/blob/v2.5.0/src/confluent_kafka/src/confluent_kafka.c#L1075-L1109)

```python
# PAPER_EXPECTED / 串行单消息 API 节选；状态记录函数为示意合同
outcome = apply_in_one_db_transaction(event)  # T2 的明确提交结果
if outcome in ("APPLIED", "DUPLICATE", "STALE"):
    wanted = (m.topic(), m.partition(), m.offset() + 1)
    try:
        committed = c.commit(message=m, asynchronous=False)
    except Exception as exc:
        record_call_exception(wanted, exc, status="UNKNOWN")
    else:
        if not committed or len(committed) != 1:
            record_incomplete_response(wanted, committed, status="UNKNOWN")
        else:
            part = committed[0]
            observed = (part.topic, part.partition, part.offset)
            if part.error is None and observed == wanted:
                record_known_committed(wanted)
            elif part.error is not None:
                record_partition_error(wanted, observed, part.error)
            else:
                record_mismatched_response(wanted, observed, status="UNKNOWN")
# DB 结果 UNKNOWN/失败/内容冲突时，不能按成功跳过该记录
```

同步异常、缺失/不匹配的返回、逐分区error与明确成功必须分别记录；`record_partition_error`保留错误码和分区/目标位点，只有实际错误合同足以证明该提交未接受时才归为DEFINITE_FAILURE，其余为UNKNOWN并查询/安全重试，不能简单把非空error当零副作用。异步提交则观察on_commit；一分区成功不代表其他分区成功。源API若使用错误属性造成客户端异常，broker位点也可能已提交，不能据异常倒推未接受。

处理错误先分类正常EOF/状态事件与真正消息错误，不能把每个m.error都解释成业务损坏。长任务须持续满足实际poll/组所有权合同，设置有限prefetch、work queue与分区并行度；每项交付和完成绑定本次分配代次。revocation/lost后旧worker不得进入新owner的完成前沿或继续发布新位点，晚到DB工作仍由原子Inbox防重复。关停只提交本代次已明确完成/持久转交的连续前沿；消费者close不能替代未完成的业务。

PAPER_EXPECTED 间隙：分区 P 已提交 next=10；并行处理中 10 未完成，11 已完成。提交 message=11 会写 next=12，从而跨过 10，重启会跳过它。正确的连续完成前沿仍是 10；等 10 也有持久完成/转交责任后才可推进到 12。位点约束按每个分区单独维护；不能用“最大已完成 offset”替代它。业务提交后、offset 提交前停止会重复投递，这正是 Inbox 要处理的窗口。

重试主题名 `.1m` 并不会让 Kafka 自动等待一分钟，需要明确的调度消费者/到期协议。转交顺序是：持久创建带原 event_id、实体、版本、schema、首次时间、attempt、原因和目标的重试责任 → 确认重试消息发布（或确认持久任务将负责发布）→ 原分区才可标为已转交并推进连续前沿。若先提交原位点再发重试消息，中间失败会丢失；若重试发布结果未知，保留原责任，重发可能重复，目标仍须幂等。DLQ 也是一个可能失败的目的地，不是把错误“丢过去”就已完成。

Kafka 内部消费→生产→offset 可以使用 Kafka 事务把输出和位点合并，读者还要满足适当隔离级别；它不把外部 DB/Redis 纳入原子事务。本文采用 T2 的数据库失效/重试任务承接外部副作用，未实现 Kafka 事务客户端，也不认证任一连接器。原文“exactly-once 通常只在受控边界内成立，不等于端到端一次”的界限保留。[Kafka 3.8 Message Delivery Semantics](https://kafka.apache.org/38/design/design/#message-delivery-semantics)

## 8. 一条从提交到关停的有限纸面轨迹

初始事实库与投影均为 E/v7；L1_A、L2 是 v7；Outbox/Inbox 无 e8；分区 P 下一处理位点是 40；F=7。数据库原子性、唯一约束、版本比较、正常缓存代次和以下消息到达次序是模型前提，不是运行观察。

|步|输入与状态转移|PAPER_EXPECTED 与责任|
|---|---|---|
|1|A开始旧快照读取，暂持v7；B的T1以作用域R/绑定D将Room更新为v8，并写e8与RequestResult|T1提交则三者一起存在；本次回滚不代表同R从未成功。回复丢失或并发失败后查FactDB原终态，同绑定返回8/e8，异绑定CONFLICT，不能判定则UNKNOWN|
|2|发件器发送 e8，key=E|本地入队不算发送完成；回调成功才登记 broker 边界成功；回调/flush 超时不删 e8|
|3|P/40的e8进入T2，原子认领Inbox、写投影v8并登记各目标/g1任务required=8|T2提交：APPLIED一次；缓存可能仍旧。持久任务容量不足则本次T2回滚，不能确认成功或越过P/40；响应未知按Inbox原终态恢复|
|4|W8给L2/g1建F=8并删v7；A也明确收到通知，各有任务回执|完成只按task_id/g/target推进completed=8。若required并发升9仍PENDING，W8不清新责任；L2回执不代表L1_A。实际接受点拒绝A的v7，其他L1只按各自合同|
|5|T2成功后offset提交响应丢失；重启再读P/40|Inbox一致判DUPLICATE，投影仍v8，任务不因重复而删除。同步返回核对TopicPartition.error、分区及next=41；异常/缺响应/未决错误保留UNKNOWN|
|6|晚到 e6/v6、重放 e8；再收到完整快照 e9/v9|e6=STALE、e8=DUPLICATE、e9=APPLIED；最大已知水位为9。若 e8 同 ID 内容不同则 CONFLICT，隔离且不静默提交为成功|
|7|原分区有一条需重试的记录，转发回调未知|既不声明重试队列已收到，也不抛弃原责任；查询/重发同一逻辑身份，可出现重复但应可审计|
|8|同一入口门转CLOSING，拒绝新入场/提交/派发，已发布工作保留owner|只提交本代次连续完成前沿。pending=1、底层未退场或延迟L2写使close返回INCOMPLETE，host/registry/pool仍在DRAINING；持久UNKNOWN不授权销毁，实际driver静默后才能CLOSED|

如果把步1改成“先提交 Room，后独立写 Outbox”，T1 后停止会使 e8 不存在；如果把步3改成“独立先查 Inbox”，两个处理者可能重复应用；如果把步4水位驱逐，A 可重新填入 v7；如果把步5提前提交位点，业务可能未发生却被跳过。这些反例各自破坏不同不变量，不能用一句“至少一次”修复所有窗口。

## 9. Redis 的原子性、锁与持久性边界

Redis 7.2.5 范围内的 Lua 脚本可以把本实例的读改写隔离成一个操作，但不是跨 Redis/数据库事务，也不是运行时错误的通用回滚机制。`MULTI/EXEC` 中一条命令执行报错不自动撤销其他已执行命令；Lua 首次写入后再出错也不能据此推定零副作用。应在首个写入前验证参数、键类型及数值域，并保持脚本短小。Cluster 的跨键可执行范围另需检查。[固定 Redis Lua 文档](https://github.com/redis/docs/blob/4125129b8efb00be8969a724b95dd210e5540ef0/content/develop/programmability/eval-intro.md)、[固定事务文档](https://github.com/redis/docs/blob/4125129b8efb00be8969a724b95dd210e5540ef0/content/develop/using-commands/transactions.md)、[7.2.5 script.c 的写入状态与停止限制](https://github.com/redis/redis/blob/7.2.5/src/script.c#L262-L279)

历史库存 Lua 示例仍在历史区，适合解释“检查和递减不被别的命令插入”，不能作为业务库存可靠性或重试幂等性的完成实现。即使输入是规范正整数，一次递减成功而回复丢失，再次执行仍会再次递减。需要的是业务操作 ID 与事实库原子约束，或明确的同一持久边界内去重，不能用 Redis 超时重试代替。

以下保留 token 条件释放的短例用途，仅是 PAPER_EXPECTED 的 Redis Lua API 节选，尚未执行：

```lua
-- KEYS[1] 是锁键，ARGV[1] 是本次唯一 token；仅用于条件释放
if redis.call('GET', KEYS[1]) ~= ARGV[1] then return 0 end
return redis.call('DEL', KEYS[1])
```

它只防止旧持有者删除新持有者的锁；随机 token 不是单调 fencing token，也不能阻止已暂停的旧持有者恢复后写数据库。把租约设为大于 P99 耗时仍会有超过 P99 的尾部、停顿与时钟问题。对必须拒绝旧写的资源，实际写入点要原子校验单调 fence/版本并拒绝旧代次；不能仅在发请求前检查锁。失去租约后应停止发起新操作，但已经在途的副作用仍可能 UNKNOWN。[固定锁文档：单实例释放与一致性警示](https://github.com/redis/docs/blob/4125129b8efb00be8969a724b95dd210e5540ef0/content/develop/clients/patterns/distributed-locks.md)

RDB/AOF 的用途取决于 Redis 是否承担事实。本文把它作为可重建缓存，因此持久化主要帮助恢复热数据，恢复的数据仍需版本/代次验证。7.2.5 的 `appendfsync everysec` 是周期 fsync 策略，不是任意故障下严格 RPO≤1s；`always` 也不能超越文件系统、存储硬件和副本故障模型。记录 appendonly、appendfsync、rewrite 相关设置、内存/驱逐、池容量和超时，不能由“已开启 AOF”推出零丢失。[Redis 7.2.5 redis.conf 的 AOF 说明](https://github.com/redis/redis/blob/7.2.5/redis.conf#L1321-L1364)

本篇不提供默认容器启动或线上客户端命令。历史 redis:7.2 标签也不是镜像 digest；历史 redis-py 未固定包版本，其 `retry_on_timeout=True` 不能解释所有版本的重试行为。后续实际验证必须先固定库版本、重试策略和所有命令的幂等性。C++ GET 短例的读超时可安全放弃返回值，但若将模式用于 SET/DECR，超时就可能有写副作用，二者不能混用。

## 10. RabbitMQ：三种确认与队列类型

选择产品时，RabbitMQ 常用于路由和工作队列，Kafka 常用于保留日志和回放；这是本文场景的适配讨论，不是吞吐排名。RabbitMQ streams 等其他模式有不同合同，本节仅核对 RabbitMQ 4.1 的 AMQP 0-9-1 队列/确认及 Pika 1.3.2 BlockingChannel 的相关节选。

|观察|能证明的边界|不能推出|
|---|---|---|
|publisher confirm|broker 对这次发布承担相应队列接受责任；持久消息到 durable queue 与 quorum queue 有各自确认条件|消费者已完成业务；消息必然路由到预期队列|
|mandatory 发布收到 basic.return|本次消息未路由到任何队列，发布者应保留修复/重发责任|未收到 return 就可忽略尚未知的 confirm，或预期的全部队列均收到|
|consumer manual ack|消费者告诉 broker 这次投递可移除|broker 了解业务事务是否真的成功；数据库已回滚或已提交的自动证明|

无路由消息也可能被 confirm；启用 mandatory 才有相应 return，且发布者仍须处理它。durable queue 与 persistent message 本身也不是已经持久化的收据。ack 通道与 publisher confirm 相互独立。[RabbitMQ 4.1 confirms：两类确认、无路由与接受条件](https://www.rabbitmq.com/docs/4.1/confirms)

下面补齐历史 Pika 发布短例缺少的确认和路由检测。`ch` 已由批准的连接建立，`jobs` 的预期队列类型/持久性/绑定已在外部核验；本节不执行声明、不改变现存队列。示例没有覆盖连接恢复、TLS、blocked connection timeout 等完整客户端实现。

```python
# PAPER_EXPECTED / Pika 1.3.2 BlockingChannel API 节选
ch.confirm_delivery()
try:
    ch.basic_publish(exchange="", routing_key="jobs", body=payload,
        mandatory=True,
        properties=pika.BasicProperties(delivery_mode=2, message_id=event_id))
except pika.exceptions.UnroutableError:
    keep_for_routing_repair(event_id)
except pika.exceptions.NackError:
    keep_for_publish_retry(event_id)
# 连接中断/超时等另列 UNKNOWN，不能当作未发布
```

Pika 1.3.2 的该模式会等待确认并把 return/nack 作为相应异常暴露；这一源码节选不认证其他语言库或异步适配器。消费者在原子业务与 Inbox 提交后才 manual ack，断连前 ack 结果不明可能重投，仍靠业务幂等。delivery tag 属于通道；并行消费用 multiple ack 时也要避免跨过尚未处理的投递。[Pika 1.3.2 basic_publish/confirm_delivery](https://github.com/pika/pika/blob/1.3.2/pika/adapters/blocking_connection.py#L1980-L2134)

`basic_nack(requeue=False)` 只有正确配置 DLX/路由才可能进入死信；没有 DLX 或目标不满足条件可能丢弃，无限 requeue 则会热循环。RabbitMQ 4.1 默认死信转发不使用内部 confirms，不能当可靠交接。quorum queue 的 at-least-once dead-lettering 需要显式策略及规定的 overflow 等前提，并可能重复、积压；目的地不可用时资源责任仍在源队列。[4.1 DLX Safety](https://www.rabbitmq.com/docs/4.1/dlx#safety)、[4.1 quorum queue Dead Lettering](https://www.rabbitmq.com/docs/4.1/quorum-queues#dead-lettering)

quorum queue 的成员/多数派与 classic mirrored queue 不是同一种机制。RabbitMQ 4.0 已移除 classic queue mirroring；4.1 classic queue 为非复制类型，不能照抄历史“quorum 记录镜像策略”。本例只要求记录实际类型、成员数、确认条件、资源水位及允许的不可用窗口；没有阅读 RabbitMQ broker Erlang 实现，也没有验证切主行为。[4.1 classic queues](https://www.rabbitmq.com/docs/4.1/classic-queues)、[4.1 quorum queues](https://www.rabbitmq.com/docs/4.1/quorum-queues)

## 11. 容量、观测与排查顺序

容量必须同时算正常路径和恢复路径。缓存容量包含键/值/索引、连接池、待回源条目、等待者及错误缓冲；消息容量包含原主题、Outbox、Inbox、RequestResult、失效/重试任务、DLQ与复制开销。积压不仅是一个计数，还意味着最老事件年龄与业务完成延迟。分区数约束同一group的分区并行度，但不能把热实体的串行工作无限分散。达到持久容量停止线时，T1/T2必须按第5节回滚/拒绝或保留UNKNOWN，不能先提交成功、后补事件/任务；达到重试次数或总时长只停止热重试，不删除原责任。

正确性状态的回收须有证据，而不是普通TTL到期就删：

|状态|可回收的必要条件；不满足则保留/停止新入场|
|---|---|
|RequestResult与请求绑定|同作用域ID的重试、并发未决事务及允许的备份/人工恢复窗口已关闭，旧ID不会被误当新请求再次接受；否则同ID去重/原终态查询证明会消失|
|Outbox与发送状态|发布/交接结果已在约定边界确认且恢复/审计保留期满足；未知发送与未决状态更新不能删除|
|Inbox与消费结果|全部允许的原主题/重试/DLQ/人工重放与备份恢复窗口已封闭，旧处理者不会再提交同一副作用；未满足就不能因按天分区到期丢去重|
|失效任务与完成状态|每个task_id/代次/target的completed覆盖required，迟到worker不再改变责任，所有可能提升required的允许重放/恢复路径已封闭；新代次独立承担必要任务，旧回执不能跨代次复用|
|墓碑/水位/缓存代次|删除实体的旧输入和旧写者均不能越过实际接受点；允许重放/备份恢复窗口已封闭或有明确隔离处理，所有旧回填/回调退场；不能证明就不回收并保持BYPASS/不可用|

这些是联合前提，单独记录保留天数、一个版本数字、重试耗尽或对象计数归零都不够。容量紧张也不放松回收条件；要拒绝新工作、降低生产或由有界负责人解决积压，而不是丢掉未完成责任。本文没有实现回收服务或验证备份恢复流程。

PAPER_EXPECTED 的流量账：若输入 λ=100 条/s、可持续完成 μ=80 条/s，连续 30s 增加 600 条积压；之后输入仍为100而完成升到160，净消化60条/s，理想清空需10s。若 μ≤λ 则不能靠等待恢复。每条假设1KiB且暂不含协议、索引和副本，600条仅负载约600KiB；三副本还要另算其磁盘和网络成本。这是算术模型，没有测得任何服务容量。

排查按边界定位：

- 命中差：先查实体编码、schema、TTL 单位、合法空值与负缓存，再看驱逐/过期；不要立即放大 TTL 隐藏陈旧问题。
- 回源风暴：查 single-flight 作用域、容量拒绝、超时仍在途、失败后连环重试和绕过 C 的回退；指标区分 leader/follower、入场拒绝、真实在途与 draining。
- 重复/丢失：沿 event_id 对照 T1、Outbox、publish 回调、T2/Inbox、失效任务及 offset/ack。先查原子边界和 UNKNOWN 记录，再查 broker 副本配置，不能用 acks=all 一项解释业务丢失。
- 积压/抖动：看每分区 lag、最老任务年龄、处理时间、rebalance、下游限流、GC、fsync 与网络重传。重试不能与新流量争抢所有容量，DLQ 必须有负责人及退出条件。

指标标签使用有限枚举/分桶，event_id、用户/房间 ID 放受控追踪日志，不作无限基数标签。规定日志脱敏、保留期、ACL/TLS、租户隔离、密钥托管和审计范围；这里是设计审查项，没有更改任何权限或配置。跨地域 RPO/RTO 包含事件保留、事实库恢复、去重状态和缓存代次，不能仅填 broker 的复制延迟。

~~~~text
> 知识成熟度：L2

> 知识基线：以当前标准、协议或 Linux/工具链版本为准，平台差异需实测。
> 最后更新：2026-08-20。

## 目标
缓存降低热路径延迟，消息队列隔离生产与消费；两者都引入一致性、容量和故障边界。

## 缓存模型
- Cache-aside：读未命中回源，写库后删除缓存。
- Read-through：缓存层封装回源逻辑。
- Write-through：写缓存同步写持久层。
- Write-back：先写缓存，异步刷盘，需处理丢失风险。
- TTL 防止永久陈旧；随机抖动避免同时过期。
- LRU 适合时间局部性；LFU 适合频率热点。
- 分片哈希保持键分布；一致性哈希减少扩缩容迁移。
- 热点键需要本地缓存、请求合并和限流。
- 雪崩：批量过期；穿透：查询不存在键；击穿：单热点失效。
- 布隆过滤器可拦截明显不存在键，但存在误判。

## 一致性
- 删除缓存优先于更新缓存可减少并发覆盖。
- 延迟双删用于降低旧值回填窗口。
- 版本号或 compare-and-set 防止旧写覆盖新写。
- 事件驱动失效时必须保证消息至少一次和幂等。
- 最终一致性需要明确可接受陈旧时间。

## 消息语义
- at-most-once 可能丢消息但不重复。
- at-least-once 可能重复，消费者必须幂等。
- exactly-once 通常只在受控边界内成立，不等于端到端一次。
- 顺序通常只保证分区内顺序。
- 重试应指数退避并设置最大次数。
- 死信队列保存无法处理的消息并触发人工或自动修复。
- 消费位点提交应在业务成功后进行。
- Outbox 将数据库写入与待发送事件放入同一事务。
- Inbox/去重表记录已处理事件 ID。

## 容量与运维
- 估算峰值 QPS、消息大小、保留时间和副本数。
- 监控命中率、回源率、驱逐数、队列深度和消费延迟。
- 队列积压增长率为正时需要扩容或降级生产。
- 分区过少限制吞吐，过多增加元数据和重平衡成本。
- 备份、恢复演练和跨区复制应纳入发布流程。
- 安全上使用 ACL、TLS、租户隔离和密钥轮换。

## 案例：房间状态缓存
以房间快照为例，键为 `room:{id}:v{version}`，值包含版本、更新时间和校验和。
读路径先查本地 L1，再查 Redis L2，最后查数据库；每层都记录命中与耗时。
写路径在数据库事务提交后写 Outbox，再由失效消费者删除 L2。
消费者以事件版本比较，只有新版本才覆盖本地缓存。
进程重启时从数据库恢复热房间，避免冷启动洪峰。
缓存值限制 64 KiB，超过则拆分成员列表与元数据。
热点房间使用单飞锁，锁等待超过 20 ms 直接回源并限流。
删除失败进入重试队列，重试间隔 100 ms、1 s、10 s、1 min。
超过五次进入死信，运维面板提供按键重放。
缓存不可用时启用只读降级，禁止写入旧快照。
所有事件带 trace_id、event_id、entity_version。

## 可运行实验：Redis 缓存击穿
环境：Redis 7.x、Python 3.11、redis-py。使用 asyncio.Lock 实现 single-flight，100 个并发只允许一次回源。
```python
import asyncio,time,redis.asyncio as redis
r=redis.Redis(decode_responses=True); locks={}
async def origin(k): await asyncio.sleep(.02); return 'v-'+k
async def get(k):
 v=await r.get(k)
 if v:return v
 lock=locks.setdefault(k,asyncio.Lock())
 async with lock:
  v=await r.get(k)
  if v:return v
  v=await origin(k); await r.set(k,v,ex=30); return v
async def main():
 await r.delete('hot'); t=time.perf_counter(); await asyncio.gather(*[get('hot') for _ in range(100)]); print((time.perf_counter()-t)*1000)
asyncio.run(main())
```
预期耗时 20--40 ms；删除锁后回源次数接近并发数。验收回源峰值降低 90%。

## Redis 配置基线

开发环境可用 Docker 启动单节点：

```yaml
services:
  redis:
    image: redis:7.2
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "256mb", "--maxmemory-policy", "allkeys-lru"]
    ports: ["6379:6379"]
```

生产环境至少记录 `appendonly`、`appendfsync`、最大内存、驱逐策略、连接上限和慢日志阈值。AOF everysec 允许约一秒数据窗口；always 降低窗口但增加 fsync 延迟。不要把缓存当作唯一事实来源，RDB/AOF 只用于缩短重建时间。

Python 最小客户端：

```python
import redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True,
                socket_timeout=0.2, retry_on_timeout=True)
r.set("room:1", '{"version":7}', ex=30, nx=False)
print(r.get("room:1"), r.ttl("room:1"))
```

C++ 客户端应设置连接池、超时和断线重连；伪代码如下：

```cpp
auto c = pool.acquire();
auto reply = c->command("GET", "room:1");
if (!reply || reply->is_error()) metrics.cache_error++;
```

验收：正常请求超时不超过 200 ms；Redis 不可达时 100% 请求进入可观测的降级分支；连接池耗尽必须有单独指标，不能静默排队。

## Redis 原子性与分布式锁

复合读改写使用 Lua 或事务，不能依赖多条命令之间没有并发。库存扣减示例：

```lua
local n = tonumber(redis.call('GET', KEYS[1]) or '0')
if n <= 0 then return 0 end
redis.call('DECR', KEYS[1]); return 1
```

锁必须带随机 token，释放时用 Lua 比较 token 后删除，避免过期后误删他人锁。租约时间应大于 P99 业务耗时并留有续租余量；长事务优先使用数据库约束或队列串行化，而不是无限续租。

## Kafka 配置与生产者示例

关键配置：生产者使用 `acks=all`、`enable.idempotence=true`、合理的 `linger.ms` 与 `batch.size`；主题设置副本数、`min.insync.replicas`、保留时间和最大消息大小。消费者使用显式提交、静态成员或 cooperative rebalance 降低抖动。

```python
from confluent_kafka import Producer
p = Producer({"bootstrap.servers":"localhost:9092",
              "acks":"all", "enable.idempotence":True,
              "linger.ms":5, "compression.type":"lz4"})
p.produce("room-events", key="room-1", value=b'{"v":8}',
          headers={"event_id":"e-8"})
p.flush(10)
```

`flush` 返回前检查错误回调；生产成功只代表 broker 接收，不代表下游业务已完成。跨数据库和 Kafka 的写入使用 Outbox，而不是试图把两个系统伪装成一个事务。

## Kafka 消费者与重试拓扑

业务处理成功后再提交 offset。失败消息进入带退避级别的重试主题，例如 `events.retry.1m`、`events.retry.10m`，超过次数进入 DLQ。重试消息必须保留原始 event_id、首次时间、失败原因和 schema 版本。

```python
from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers":"localhost:9092",
              "group.id":"room-writer", "enable.auto.commit":False,
              "auto.offset.reset":"earliest"})
c.subscribe(["room-events"])
while True:
    m = c.poll(1.0)
    if m is None: continue
    if m.error(): raise RuntimeError(m.error())
    apply_once(m.key(), m.value())
    c.commit(message=m, asynchronous=False)
```

若 `apply_once` 成功后进程在 commit 前崩溃，消息会重复投递；唯一索引 `(event_id)` 或 Inbox 表必须使第二次处理成为 no-op。不要以 offset 作为业务幂等键，因为重新分区、重放或跨主题复制都会改变 offset。

## RabbitMQ 适用边界

RabbitMQ 更适合工作队列、路由和短消息确认；Kafka 更适合高吞吐日志、长时间回放和分区顺序。RabbitMQ 使用 durable exchange/queue、persistent message、publisher confirms 和 manual ack；仅设置 durable queue 不等于消息已经持久化。

```python
import pika
conn = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
ch = conn.channel(); ch.queue_declare('jobs', durable=True)
ch.basic_qos(prefetch_count=32)
ch.basic_publish('', 'jobs', b'job-1',
  pika.BasicProperties(delivery_mode=2, message_id='job-1'))
```

消费者完成业务后 `basic_ack`，失败用 `basic_nack(requeue=False)` 路由到 DLX；无限 requeue 会造成热循环。使用 quorum queue 时记录节点数、镜像策略和磁盘水位，确认切主期间的可接受暂停时间。

## 一致性故障注入剧本

|注入|操作|观察|通过标准|
|---|---|---|---|
|Redis 主节点断电|停止容器 30 秒|错误率、回源 QPS、恢复时延|无静默写丢失，降级可识别|
|缓存网络丢包|tc 注入 5% 丢包|超时与连接池|p99 小于预算，线程不耗尽|
|Kafka broker 重启|滚动停止一个 broker|ISR、生产错误、consumer lag|无确认成功后的消息丢失|
|消费者崩溃|业务写入后 kill -9|重复处理数|最终状态正确且重复可计数|
|RabbitMQ 磁盘满|限制卷空间|publisher confirm、告警|生产暂停并能恢复，不无限重试|

每项注入保存时间线：注入前基线、注入命令、首个告警、错误峰值、恢复动作、数据校验和复盘结论。恢复后用数据库计数、事件 ID 集合和校验和比对，不能只看服务返回 200。

## Benchmark 可复现协议

固定 CPU 型号、核心数、内存、磁盘、内核、容器镜像 digest、客户端版本和配置文件。压测前预热 60 秒，正式采样 10 分钟，至少重复 5 次并报告中位数与 p95/p99；同时采集 CPU、RSS、网络、GC、磁盘 fsync 和 broker lag。

Redis 基准变量：键大小 64 B/1 KiB/16 KiB，并发 1/32/256/1024，命中率 99%/90%/50%，pipeline 1/32。Kafka 变量：消息 256 B/4 KiB、分区 3/12/48、batch 1/64/256、压缩 none/lz4/zstd。RabbitMQ 变量：prefetch 1/32/256、持久化开关和 quorum/classic queue。

示例命令：

```text
redis-benchmark -h 127.0.0.1 -p 6379 -n 1000000 -c 256 -d 1024 -t get,set
kafka-producer-perf-test --topic room-events --num-records 1000000 --record-size 1024 --throughput -1 --producer.config producer.properties
```

输出至少包括 ops/s、平均延迟、p50、p95、p99、错误数、回源次数、重复率和恢复时间。验收阈值由业务 SLO 给出；没有阈值时不得用“吞吐更高”宣称优化完成。任何参数变更都重新预热和采样，并把原始 CSV、命令行和火焰图放入 evidence 目录。
~~~~
