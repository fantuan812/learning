## 问题边界

本文要回答一个贯穿业务、复制与恢复的问题：客户端提交一次库存扣减，响应丢失后重试，系统凭什么既不重复扣减，又能在换主后返回有根据的结果？先约定接口与故障模型，再追踪请求、日志、提交、应用、读取和外部通知，才能知道每层究竟承担了什么。

中心模型是一组固定的三个副本 A/B/C，使用 Raft 复制确定性状态机，允许消息延迟、丢失、重复、乱序与节点崩溃后恢复；已确认的稳定存储不丢失，节点遵守协议，消息不会被未检测地篡改。磁盘永久丢失、所有副本同时损坏、恶意节点或错误执行不在该容错承诺内。真实节点会共享机架、电源与上游网络，因此“多个节点”也不意味着统计独立的故障域。

安全性要求任何前缀都不能出现库存为负、同一请求被再次扣减或已提交日志被另一结果替换。活性要求在多数可通信、执行与持久化持续取得进展、选主最终稳定等前提下，非故障客户端的有效请求最终得到结果。失去多数时可以暂停相关写与强读来保安全；这不是“协议失效”。把安全性理解成愿望、再用重试掩盖无法证明的提交，只会把未知结果变成重复副作用。[S1](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)[S2](https://ongardie.net/var/blurbs/pubs/dissertation.pdf)

这里的库存只是有限纸面对象，所有后文轨迹均标作 `PAPER_EXPECTED`。没有运行集群、数据库、客户端、故障注入或新协议模拟器；这些轨迹只核对给定规则的因果与反例，不代表某个产品通过一致性测试。

## 网络模型

异步模型没有已知消息时延和进程执行速度上界；同步模型给出这类已知界。部分同步有不同形式：界存在但事先未知，或已知界只在未知的稳定时刻之后成立。本文只使用“最终稳定后，多数间消息和处理能及时推进”的进展前提，不把一个配置好的超时时间当成已经证明的网络界。[S3](https://dspace.mit.edu/entities/publication/108bf327-aff6-414b-a48f-b357a821c48e)

FLP 的结论针对纯异步、确定性共识和允许至少一个进程崩溃的模型：不能保证所有允许执行都终止。它不说每次执行都会失败，也不禁止保安全的协议在常见网络条件下进展；它与允许长期丢失跨分区消息的 CAP 命题不是同一问题。[S4](https://dspace.mit.edu/entities/publication/287e7d14-a6f3-4ab4-b21a-a98ea86c1212)[S5](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf)[S17](https://www.microsoft.com/en-us/research/wp-content/uploads/2004/01/consensus-on-transaction-commit.pdf)（§2）

连接断开或截止时间到期时，客户端只能说“我没得到可判定结果”。请求可能未到达，也可能在处理，或已完成但回包丢失。不能由网络超时推导业务回滚，更不能立即换一个请求 ID 重做不可逆动作。客户端持有原 ID 查询或重试，同时受截止时间、次数与退避预算约束；服务端必须为同一意图提供可恢复的判定记录，唯一 ID 本身没有这种能力。这里进入复制与业务判定的边界，消息定界及传输确认细节沿用网络基础篇，不在本篇再造一套网络例子。

## 一致性模型

一致性首先是接口允许返回哪些历史。线性一致性要求每个完成的操作都可看成在其调用到响应之间某一点原子生效，并且保持不重叠操作的真实时间先后；并发操作可按某个满足对象顺序规范的次序排列。并不是“所有操作在同一时刻发生”，也不是“读必须包含响应时刻以前所有并发写”。未返回的请求可能已经生效，不能直接当成失败删除。[S6](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf)（§2.1–2.2）

`PAPER_EXPECTED C1`：寄存器初值 0，P 的 write(1) 调用于 t1、成功响应于 t2；Q 的 read 调用于 t3、返回 0 于 t4，且 t1<t2<t3<t4，无其他写。这不满足线性一致性，因为写必须排在读之前，合法读只能是 1。若读调用提前到 t1 与 t2 之间并与写重叠，返回 0 或 1 都可能合法。判定所需是完整调用/响应和对象规范，不是仅看服务器完成日志。

顺序一致性要求存在一个符合每个进程自身操作顺序的合法全局序，不额外保持不同进程间真实时间先后。因此 C1 的两个独立进程可以排列为 Q.read→P.write，满足顺序一致性。若同一进程先成功 write(1) 再 read，则不能这样换序。[S6](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf)（§3.3）

因果一致性保留模型内进程顺序、读到某写所建立的依赖及传递依赖；并发写不因此得到统一顺序，也不自动收敛。最终一致性的收敛承诺需要更新停止、相关更新最终传播、各副本执行可收敛的冲突处理等条件；永久分区或不同副本永久采用不同胜出规则，不满足这些条件。COPS 的 causal+ 特意把因果与收敛冲突处理列为两个要求，本篇不把它们混成一个词。[S7](https://pdl.cmu.edu/PDL-FTP/Storage/cops-sosp2011.pdf)（§3）

`PAPER_EXPECTED C2`：P 写会话元数据 x=ready；Q 读到它后写 y=joinable。观察者若已看见 y，就不能再返回一个缺失其因果前驱的状态；实现需要传递和检查依赖，给消息附普通时间戳并不够。另有两个并发设置 z=red 与 z=blue，因果顺序无法替业务选胜者；要另定统一的冲突策略，或让接口显式返回冲突。

会话保证要逐项写：读己之写让后续读包含本会话成功写的效果；单调读避免相对于本会话已观察历史后退；单调写保持该会话写的次序。这些不等于全局线性一致。版本令牌必须有可比较的语义与资源域：同一日志的 applied index 可表示前缀进度，任期号只标逻辑时代，业务数量变小也可能是更新。粘到一个已追平的副本可以帮助会话保证，单纯“会话粘性”无法修复副本回退或故障后改路由。

## CAP 与 PACELC

Gilbert–Lynch 的模型中，C 是原子/线性一致的读写对象；A 是每个非故障节点收到的请求最终有符合对象语义的响应，不是某个百分位延迟或“返回错误也算完成”；P 允许任意多跨节点消息丢失。分区是需要承受的环境条件，不能把 CAP 读成平时在速度、成本和正确性中任选两个。[S5](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf)（§2–3）

`PAPER_EXPECTED C3`：初值 x=0，A 与 B 完全隔离。若 A 为满足可用性完成 write(1)，随后 B 的 read 在仍未收到 A 消息时也必须完成，B 无法分辨“发生过该写”和“没有写”的执行。它若仍返回 0 就破坏已完成写→后续读的线性顺序；若等待就放弃这一执行中的全面可用性。多副本系统可以让有合法多数的一侧继续部分操作，但不能因此声称每个分区都满足 CAP 的 A。

PACELC 提醒读者即使没有分区，远距离复制、读路径和等待策略仍有一致性/延迟取舍。它是设计分析框架；这里仅采用 Abadi 2012 文中的取舍问题，不把其当年产品分类当成当前产品认证，也不据此推断“更多副本必然更慢”。具体时延还取决于等待哪个确认集合。[S8](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)（PACELC 段）

## 复制

复制先规定什么算收到：字节到达、进入内存、写入稳定日志、协议已提交、状态机已应用，分别是不同进度。主从/leader–follower 描述路由与角色，不自动给出故障时的数据保留或读取保证。同步复制必须注明等待哪些副本及何种确认；异步复制可在副本尚未接收前响应，因此在主节点永久丢失或切到落后副本时存在已响应写丢失的窗口。

日志按稳定身份排序，Raft 使用 index/term；校验信息只能发现某些损坏，不能替代共识规则。断点追赶需要核对前缀而非仅按最大序号接续。快照应对应一个确定的已应用前缀，保存 lastIncludedIndex/Term、必要配置和应用状态；去重记录若属于状态机，也要随快照/重放恢复，否则切主后可能重复执行。日志截断必须保留快照或恢复所需的充分状态。[S1](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)（§5）[S2 extended §7](https://raft.github.io/raft.pdf)

两个节点都认为自己是 leader，不等于它们都能合法提交。任期、选举和日志约束限制内部协议；外部存储若不检查写权代次，旧主仍能产生外部副作用。后文把复制内的安全和资源端 fencing 分开说明。

## Quorum

N 表示副本总数，W 表示写确认数，R 表示读确认数。
若 R+W>N，读写集合在固定副本配置下至少相交一个副本；这只是集合交集条件，不自动提供线性一致性。
还必须定义版本比较、冲突解决、读写路径和副本成员变更规则；读取时需比较版本并按协议修复旧副本。

前面两条原有正确限定保留。补齐的关键问题是：相交节点持有什么状态，读取如何选择结果，不完整写如何影响后续读，以及新旧配置如何安全衔接。[S8](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)（关于 quorum 附加协议的脚注）

`PAPER_EXPECTED Q1`：固定 A/B/C，初值 x=0，R=W=2。写 x=1 已在 A、B 持久化并响应。读集合 B、C 的回复分别为 1、0；如果实现“先收到谁就返回谁”，仍可能返回 C 的 0。集合确实相交，却没有利用相交副本的新状态，故 C1 型历史仍不合法。

`PAPER_EXPECTED Q2`：即使读取最高版本，仍需完整协议。初始三副本都是 (v0,0)。未完成写只把 (v1,1) 发给 A；第一次读 A、B 取 v1 并返回 1，却没有按协议传播该观察。之后第二次读 B、C 只看见 v0 而返回 0，期间没有其他写。要解释第一次读为 1，就必须把未完成写纳入其前面；第二次读随后退到 0，无法得到合法线性序。本反例证明“取最高版本”仍不足，**不是 ABD 实现或其正确性证明**；本文不展开原子寄存器协议，正向路线使用下面固定版本的 Raft 状态机。

动态成员变更不是“永远不能存在两个多数集合”，固定配置本来也有多个相交多数；危险是不同配置允许互不制约的决定。配置规则见 Raft 节。跨地域 quorum 的成本由确认路径与拓扑决定，不把单一环境的显著尾延迟概括成定律。

## Raft 与共识

### 从持久复制到原结果重用

single-decree 共识先解决一个实例选择一个值；复制状态机要让一串命令在相同槽位拥有相同决定并按序应用。Raft 的角色、任期和心跳是这条链的组件，单靠选出 leader 不够。[S1](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)（Figure 2、§5）

Raft 的 currentTerm、votedFor 和 log 是持久状态。投票每任期至多一次，投票还比较候选日志的最新 term/index；AppendEntries 检查前一条的 index/term，冲突时才修正相应未提交后缀。这使相同 index/term 的条目拥有相同前缀，并使新 leader 带有已提交条目。相关回复前完成必要稳定存储；“收到包”不是可计入的持久确认。

leader 按副本数推进 commitIndex 时，要存在 N>commitIndex，使多数 matchIndex≥N，且 log[N].term 等于当前任期。旧任期条目不能只因当前看见多数副本就直接判定提交；当前任期条目提交后，其前缀才随之提交。提交后，各节点按序应用；面向业务的成功响应在状态机应用并取得结果之后发出。无需等所有副本应用，也不能用“leader 本机已有日志”替代提交。[S1](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)（§5.3–5.4.2）

`PAPER_EXPECTED R1` 的完整输入与轨迹如下。初始 A/B/C 均持有到 index20/term3 的已提交、已应用前缀，库存 qty=10，去重表 D 为空；A 是 term4 leader。命令 q 的键为 (角色7, 客户端实例X, request42)，语义参数为扣减3，固定目标是该库存；数量按非负整数计算，整个轨迹都保留D记录、不发生ID重用。三者 state machine 相同，不执行网络外部动作。应用规则：原子地检查 D；若已有同参终态，复用原结果；若同键异参，拒绝；否则 qty≥3 时执行 qty←qty−3，并在D[q]中保存参数、成功终态和扣减后的数量（本例10→7，原结果为7）；不足则记确定的业务拒绝。该业务状态、结果和恢复进度必须一起恢复，不能只保存其中一半。

| 步骤 | 消息与稳定状态 | commit / applied / 客户端所知 |
| --- | --- | --- |
| 1 | 客户端调用 q；A 在本机稳定存储写入 (index21,term4,q)，B/C 尚无21 | A 仍 commit20/applied20；客户端未知 |
| 2 | A→B AppendEntries；B 校验前缀、持久化21后回复，A 收到确认；C 暂不可达 | A+B 是固定配置多数，21 属本任期；A 可把 commit 推到21 |
| 3 | A 按序应用21，qty=7、D[q]=原成功结果；发出业务响应但回包丢失；发往 B 的 commit 通知也未到 | A commit21/applied21；B 日志到21但只知道 commit20、applied20；客户端仍未知 |
| 4 | A 暂停；B 以 term5 与 C 形成合法选举，多数持久化投票。C 的日志较旧，不妨碍其给更新的 B 投票 | B 不因自己的旧 term4 条目已有若干副本就跳过当前任期规则 |
| 5 | B 在本机稳定存储追加 index22/term5 no-op，把缺失21及22复制到 C；C 持久化后回复 | B+C 对22满足本任期多数；B commit22，再依次应用21、22，恢复 qty=7 和 D[q] |
| 6 | 客户端用同一键同一参数重试；为避免未经证明的本地快读，B 将重试命令作为23/term5在本机持久保存，复制给 C，收到其持久确认后提交、应用 | 应用23查到 D[q]，不再扣减；响应仍为原成功结果7；后续库存变化不会篡改这个原结果 |

该轨迹中，B应用21是在该副本重放已决定命令，不是又一次全局库存扣减。A的响应丢失只让客户端不知道结果；B一度只知道commit20，也不撤销21已经提交的事实。到步骤6，重试身份、参数和原终态已通过状态机重新关联起来。下面继续区分两种恢复起点，不能一边保留旧业务状态，一边又假装从空白快照开始。

负向分支：若 A 在步骤1就返回成功，随后在复制前永久丢失，B/C 可能合法继续旧前缀，客户端已收到的成功就没有依据。若 A/B 在步骤2只落内存并都崩溃丢内存，所谓多数也不保留该写。另开一个错误实现的独立负向分支：初始qty=10、D为空，两个首次并发调用使用同一q和相同扣减3参数；错误实现把检查、业务效果与终态记录拆成独立步骤。两个调用先各自查到D[q]不存在，随后不重新核对D，各自按当前qty扣减并独立提交，先10→7、再7→4；最后才另行写入D的终态，终态写入失败也不会回滚已经提交的扣减。这里ID没有阻止重复；它不是R1步骤6中已有D[q]的状态，也不是合法串行状态机的执行。以上都在第一个不满足前提的步骤停止，不继续声称安全。

### 重启时从哪一份状态恢复

`PAPER_EXPECTED R1-restart` 是从R1步骤6结束另开的独立分支，与后面R2使用index24的读分支互不拼接。本分支选择**全量重建内存状态**：B的应用恢复事实源只有固定快照S20和Raft稳定日志，S20之后的qty、D仅在内存；不存在另一个已保存qty=7的业务数据库。固定S20=(lastIncludedIndex=20,lastIncludedTerm=3,配置ABC,qty=10,D空)；B的稳定后缀为21/term4/q、22/term5/no-op、23/term5/同q。currentTerm、votedFor随协议持久保存。沿用R1的q=(角色7,客户端实例X,request42)、固定库存扣减3、同参数才复用原终态、D不回收、ID不重用、无外部动作与稳定存储不丢失；此分支没有新的业务写。

| 步骤 | 明确状态与消息 | 可安全推进到哪里 |
| --- | --- | --- |
| a | R1之后，B发给C的commit23通知实际到达；C按序应用到23 | B/C均为qty7、D[q]=(扣减3,成功,7)，但B仍只有旧快照S20和稳定后缀21–23作为应用恢复事实源 |
| b | B进程崩溃，内存qty、D、易失commitIndex和lastApplied全部丢失；S20、稳定log21–23及term/votedFor保留 | 日志中存在23不能自动充当B重启后已知的提交进度，更不能直接许可强读 |
| c | A从暂停恢复，仍保有21/term4。C以更完整的23/term5日志发起term6选举；C/A在term6持久投票使C成为leader | A日志较旧仍可合法投给C；新主C不能跳过本任期提交规则 |
| d | C在本机持久追加24/term6/no-op；向A补齐22、23并复制24，A核对前缀、稳定保存后确认 | C/A构成多数，24属于当前term6，C据此commit24，前缀21–23也已确定 |
| e | B重启，载入S20得到qty10、D空、应用恢复位置20，保守从快照前缀建立本地进度；读入稳定后缀及持久term/vote，作为follower等待推进。C发送term6的有效AppendEntries，prevLogIndex=23、prevLogTerm=5，携带24/no-op和leaderCommit=24 | B核对前缀，先按协议持久更新必要term/vote及日志，再接受不超过已匹配日志末端的提交上界；此处可把本地commit推进到24。未获有效通知前不能盲目应用稳定后缀 |

这个分支的允许结论是B从明确的S20重建出7，且保住q的原成功结果7。之后同q若再经合法leader复制提交，仍复用这个终态；即使别的合法命令随后改变当前库存，也不能改写q的旧响应。若快照与日志前缀不匹配、恢复所需后缀缺失、稳定状态损坏或无法确认合法提交上界，应停止恢复服务并核对证据，不猜测缺失状态。[S1](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)（Figure2、§5.4.2）[S2 extended](https://raft.github.io/raft.pdf)（§7）；上述固定输入和重放结果是本文纸面推导。

`PAPER_EXPECTED R1-incremental` 则另从apply21的切点说明**持久数据库增量应用**，不是接着前表再扣一遍。输入是已确认可应用的21/term4/q，数据库初始(库存10,D空,applied20)，q、保留期与确定性规则同R1；没有其他写。一次apply必须把qty、D中的参数身份和原终态、applied marker放在同一个可恢复原子提交内（或提供同等的恢复协议），对no-op和重复命令也正确推进应用位置：

- 崩溃在apply21事务提交前：持久数据库仍为(10,D空,applied20)，恢复确认提交前缀后，从21重放一次，得到(7,D[q]=(扣减3,成功,7),applied21)
- 崩溃在该事务提交后：持久数据库已是(7,D[q]=(扣减3,成功,7),applied21)，恢复从22继续；不能把保留下来的qty7当作S20的qty10，再无条件执行扣减3
- 负向撕裂分支：若只落qty7、D和marker缺失，恢复会把q当新请求，可能再扣成4；若marker先落为21而qty/D还停在旧状态，恢复可能跳过未完成效果。这些状态必须由原子合同排除，发现后停下并核对，不能靠重试ID掩盖
- 若完整D已和效果原子持久而marker落后，这个特定q在重放时可能命中去重而避免第二次扣减，不能断言所有marker落后都必双扣。合同仍应覆盖整个状态机的效果、结果身份与恢复进度；不能把一条碰巧能去重的命令当作任意恢复算法的证明

两种模型都必须从一个一致的恢复基线开始：前者丢弃易失业务状态并从S20重建，后者保留持久数据库并从其原子applied位置继续。本轮只检查这些崩溃切点的纸面后果，没有验证某个数据库事务、日志格式或快照安装实现。

### 强读的屏障、应用进度与时间区间

不入日志的线性读还需要独立的读协议。学位论文 §6.4 的路线是：新 leader 先提交一条本任期日志以知道可安全使用的提交前缀；读请求到来后记下 readIndex，向多数发起与本次读关联的新一轮心跳，并等待该轮/任期的有效确认；再等本地 lastApplied≥readIndex，执行查询并响应。任意历史心跳回复不能替代该确认，follower 取得 readIndex 后也要等自己应用。[2014 extended §8](https://raft.github.io/raft.pdf)讨论同一读问题；正式会议版省略客户端交互，不能将其 §8 错当成读协议章节。[S2 学位论文§6.4](https://ongardie.net/var/blurbs/pubs/dissertation.pdf)

`PAPER_EXPECTED R2`：独立接R1步骤6，不接R1-restart。B在term5已应用23，qty=7，当前任期条目22、23都已提交；另一个不同ID的扣减1命令在B/C持久化为index24/term5，B已推进commit24、但应用暂时只到23，该写尚未响应。除此之外没有业务写。给本次读完整的调用/响应区间：

| 时点 | 本次读及状态机的动作 |
| --- | --- |
| r0 | 客户端调用read |
| r1 | B记录readIndex=24，作为查询至少需要的已提交前缀 |
| r2 | B发出关联本次读的新一轮term5心跳 |
| r3 | B收到C对该轮/任期的有效确认，连同B形成多数 |
| r4 | B应用24，使qty7→6并完成该命令的结果记录 |
| r5 | B在已应用前缀上执行查询，得到6 |
| r6 | B向本次读返回6 |

规定r0<r1≤r2<r3≤r4≤r5<r6。在这个没有其他业务写的有限历史中，可把该read线性化在r2：24在读调用前已经提交，返回6对应其后状态，r2又确实位于调用与响应之间。r4的apply使本地查询取得该状态，不必把本地apply时刻当成抽象读的唯一线性化点。

收到本轮多数确认的论证是：**在r2发出心跳时，尚不存在已经取代B的更高任期leader**；它不是从r3收齐ACK直到r6响应都仍然当选的持续授权。ACK在途期间或之后可以发生合法换主，不能仅凭“后来不是leader”判这个已有合法屏障的读一定不线性；仍要按读区间、屏障和已应用状态证明返回值。一般查询可以观察readIndex之后的合法前缀，本例不推出所有读的唯一线性化点都是r2，也不要求精确只读readIndex对应的状态。[S2 学位论文§6.4，pp72–73](https://ongardie.net/var/blurbs/pubs/dissertation.pdf)

若在上述输入下省去等待、直接读applied23而返回7，则不满足所采用协议的lastApplied≥readIndex前提，应在这里停止强读；但24尚未响应且与read重叠，仅凭这一有限历史不能武断判它一定无法线性化。另若读与后续写25重叠，它可以返回24之后、25之前的状态，不要求包含所有并发写。真正的已完成写→新读反例见下面独立分支。

`PAPER_EXPECTED R2-negative`：另一个独立负向分支从R1步骤6的qty=7出发，尚无上述24扣减：B随后隔离，C/A形成term6多数，C按协议先追齐A并提交本任期no-op24，再提交/应用扣减1的25，向另一客户端响应qty=6。之后B才收到新的read调用，却仅凭term5历史心跳缓存返回7。在没有其他写时，这次读违反已完成扣减→后续读的实时顺序；应在缺少本次多数确认处停止强读。选择lease减少心跳开销则另需相对时钟速率等界、暂停/迁移和leader转移失效规则；本机单调钟、NTP同步或“租约还没到期”的自信都不自动建立这些前提。[S2](https://ongardie.net/var/blurbs/pubs/dissertation.pdf)（§6.4.1）

### 配置变更使用哪一个版本

配置变更固定采用 2014 论文 §6 的联合共识：Cold→Cold,new→Cnew；联合阶段的选举和提交分别满足旧多数与新多数，联合配置提交后才进入下一阶段，不是把两组节点合起来只算一次多数。`PAPER_EXPECTED R-config`：固定Cold={A,B,C}，Cnew={C,D,E}，各确认均满足相应持久化要求：联合确认 {A,B,C} 虽满足旧多数，却只含一个新成员，不能决定联合条目；{A,C,D} 才同时满足两边多数。2014方案中节点看到日志中的新配置就按它行动，不等待本节点得知该配置提交；因此阶段衔接必须遵守论文规则，不能自行改成全局同时切换。最终Cnew按新配置多数提交后，旧配置才可退出。新节点先作为非投票成员追赶，配置与日志必须持久恢复。

学位论文 §4.1 的单成员增删是另一机制，不能与 §4.3 联合共识混写。[2015 作者勘误](https://groups.google.com/g/raft-dev/c/t4xj6dJTP6E)指出前者跨任期变更存在缺陷，并提出新 leader 先提交本任期条目再追加新配置等补充条件；公告明确区分单成员变更与联合共识，且当时只给安全论证、未给完整形式证明。本篇主线不实现这一变体，不能把“每次只改一个成员”当成充分条件。[S2 学位论文](https://ongardie.net/var/blurbs/pubs/dissertation.pdf)（§4.1、§4.3）

## Paxos 视角

Paxos 用单调提案编号和多数派交集维护“至多一个值被选定”的安全性；编号本身不是完整证明。
prepare 阶段，proposer 向 acceptor 请求承诺不再接受更低编号，并收集其已接受的最高编号值。
若 prepare 返回了已接受值，proposer 必须继承其中编号最高者；只有没有已接受值时才能选择新值。
accept 阶段，acceptor 仅接受不违反既有承诺的提案；某值获得多数 accept 即被选定。

这些原有关键句保留。最后一句的“多数accept”严格指同一提案编号与值(n,v)获得多数acceptor接受，不能跨编号累计同value的接受；前面的继承规则则针对同一个实例、同一prepare编号得到的多数有效回复。继承的是回复中最高**提案编号所对应的 value**，不是最大 value、最多票 value，也不能等已经知道 chosen 才继承。promise 和 accepted 记录需跨崩溃保存，提案编号须唯一。[S9](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)（§2）

`PAPER_EXPECTED P1`：A/B/C 是 acceptor，起始 promise=0、accepted=空。编号5先获得 A/B 的 promise，向 A/B 提交 value=red；A/B 稳定接受，red 因而 chosen，即使通知 proposer 的回包丢失。编号8向 B/C prepare；B 回复 accepted=(5,red)，C 为空。8 必须继承 red；B/C 接受 (8,red) 不会改变决定。反例是8自行选 blue：它若获得 B/C 接受，5的多数与8的多数虽在B相交，却选出两个值；错误发生在忽略 highest-accepted 约束，而不是多数不相交。

只有 A 接受5、B/C尚未接受时，red 还没 chosen；但8的 prepare 若问到 A，也仍可能必须继承 red。协议保护“可能已经选定”的历史，不能用观察者不知道多数就否认其存在。prepare 成功也不保证随后的 accept 一定成功，更高编号可以抢占，进展仍需稳定 proposer 与有效通信。

Multi-Paxos 用一系列实例形成命令日志，稳定 leader 可摊销 prepare 成本；换主仍要恢复逐槽位 accepted 状态、补洞并按序执行。它不是一次选主后永久免除 prepare，也不能把单实例证明直接当成完整的日志、读或客户端去重协议。[S9](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)（§3）

## 时钟

单调时钟适合本机测间隔，物理墙钟可能校正；“单调”只保证不倒退，不自动给出跨机速率漂移上界。租约读若依赖时间界，必须另外证明计时、暂停、迁移、续期及交接规则的适用性。任期是逻辑时代，不是秒；业务版本、日志位置与时间戳也不能互换。

Lamport 的 happened-before 包括进程内顺序、发送→对应接收以及传递闭包，正确时钟满足 a→b 蕴含 L(a)<L(b)。L(a)<L(b) 不能反推有因果。对同一完整模型中不同事件，L(a)=L(b) 则可排除两个方向的 happened-before，证明模型内并发；现实日志若重置计数器、漏传播或遗漏因果渠道，两个相同数字不能证明现实无因果。同一事件重复记录不是两个不同事件；相等的墙钟或HLC字段也不能未经各自定义核对就套用此推论。并发表示无因果先后，不是物理同时。[S10](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)

`PAPER_EXPECTED T1`：P、Q 初值0，互不通信，P 的事件 a 得 L=1，Q 的两个本地事件 b,c 得 L=1,2。a 与 c 的数字有大小但无消息/进程路径，因此并发。a 与 b 同为1且是不同事件，也无因果。之后 P 发送携带2的消息，Q 接收按 max(2,2)+1 得3，此次发送确实因果先于接收。把进程 ID 加到标量以打破平局能构造扩展偏序的全序，但新增次序不是因果证明。

完整向量时钟按分量比较，所有分量≤且至少一个<定义严格前序；在完整进程维度、每事件本地递增、所有消息携带向量、接收按分量 max 合并的模型中，这与因果先后对应，不可比较的不同事件并发。例如 (2,0) 与 (1,1) 不可比较；(2,1) 支配二者。截断向量、重用进程身份或丢掉传播渠道后不能照搬该保证。Dynamo 原论文也明确说明截断会损伤祖先关系判定；其对象版本方案不是完整事件向量时钟的无条件替代。[S11](https://vs.inf.ethz.ch/publ/papers/VirtTimeGlobStates.pdf)[S12](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)（§4.4）

混合逻辑时钟是进一步的版本设计选项，本篇不依赖它完成提交或 fencing；采用时仍须核对自己的排序与误差合同，不能因名称含“物理”就代替因果证明。

## 消息语义

至多一次/至少一次首先限定某一投递边界；网络投递次数与业务副作用次数不是同一个量。至少一次还依赖可重试存储、恢复和最终可达等前提；有限重试后进死信队列，不能同时无条件承诺每个消息最终完成。“恰好一次”必须写出覆盖的生产、日志、消费者状态和输出边界。

同一个请求的判定记录至少包含作用域、请求ID、参数身份和原终态。并发同键必须通过唯一约束/串行状态机等机制原子竞争；业务效果与终态同一个事务或同一可恢复状态机变迁提交。恢复后返回原结果，并不重新读取当前 qty 冒充原结果。保留期是协议的一部分：删除去重记录之后，晚到重试可能再做一次；因此要拒绝已过期的请求域/会话或依约保留状态，不能随便设一个TTL就保证永久幂等。[S13](https://d1.awsstatic.com/builderslibrary/pdfs/making-retries-safe-with-idempotent-apis-malcolm-featonby.pdf)

outbox 将业务状态和待发送事件放入同一本地事务，关闭“状态已写但没有发送意图记录”的窗口；relay 真正发出后、尚未来得及记录已发送就崩溃，恢复时仍会重复发布。inbox 表也只有在去重标记与目标业务效果原子提交时才覆盖该效果。事务外HTTP调用、邮件、外部存储或游戏实例指令，不会因表里有 event_id 就自动去重。[S14](https://microservices.io/patterns/data/transactional-outbox.html)[S15](https://microservices.io/patterns/communication-style/idempotent-consumer.html)

`PAPER_EXPECTED M1`：初始权威库存与消费者投影均为10，outbox、inbox及relay已发送记录均空。扣减3的q使库存变7，并将 outbox e=(event42,q,delta=-3,version21) 随同一可恢复状态变迁提交（数据库实现则须同库事务）；整个轨迹无其他写和消息，event42与inbox记录不回收。relay只发送已提交outbox中的e；broker持久接收并确认，relay在保存发送进度前崩溃。恢复再发e，消费者收到两份。消费者在自己的事务中插入唯一(subscriber,e)，把自己的库存投影10减为7并提交，随后发消费ACK；若ACK丢失，重投在唯一键/事务检查处识别原终态，不重复更新。最终库存扣减一次、投影应用一次、网络可以有多次投递。若消费者先ACK再提交就崩溃，broker可能不再重发而业务效果丢失；若先单独插入inbox再崩溃，重试会把未做的业务当完成；若先做效果再单独记inbox，重复会再次做效果。

ACK 的准确范围取决于发送者是谁：broker 的发布确认只证明它约定的接收/持久性；消费者 ACK 是自己负责的消费处理已到约定可恢复终点。它们都不是所有下游已完成。相同业务键上的顺序须定义分区、版本和乱序策略；广播各订阅者分别推进进度，工作队列是在消费者之间分配任务，两者的“都处理了”也不同。死信队列保留原消息、失败原因和进度用于修复，不能当作成功终态。

## 流处理

事件时间描述业务事件发生时刻，处理时间描述流水线何时观察到它。水位线是某种事件时间进度或完成度估计，能否断言后续不会再有更早事件，取决于来源给出的严格界或启发式假设；不能一概写成概率保证。Dataflow 2015 明确讨论实际水位线常为启发式，迟到输入需要触发、更新/撤回或丢弃规则。[S16](https://research.google.com/pubs/archive/43864.pdf)（§1.3、§2.3）

`PAPER_EXPECTED W1`：窗口[0,10)，先收到 event-time=2、值1和event-time=8、值1，水位线推进到10后输出count=2；此后迟到event-time=7、值1。若合同允许截至处理时间30修正且该事件在20到达，输出应改成3并带可识别修订；若合同已关闭窗口，则应记录丢弃/旁路，不能无声把旧结果称为全部事件总数。检查点需把算子状态与输入位置对齐；恢复重放及输出端幂等/事务仍决定是否重复对外输出。水位线不替代这套恢复责任。

重放日志还承担审计用途，应保留能追溯输入、修订与恢复进度的记录。状态后端和快照体量要受控，并连同重放量评估恢复成本；一张大快照或无限增长的状态不能仅凭“已有检查点”满足恢复目标。这些都是后续实现验收义务，本轮没有运行流水线或测量快照大小。

## 故障检测

心跳缺失只能产生怀疑。选举会用超时推动进展，但过小阈值在队列拥塞或暂停时会频繁误判，增加选举、重试和恢复负担。阈值应参考实际消息/执行分布及目标误判率，还要认识到历史分位数不是未来的上界。Phi accrual detector 可作为把到达间隔统计转成怀疑程度的后续选读对象，本篇不声称验证它的分布模型或部署参数。

故障后先问该节点仍能承担什么：进程存活、能否接流量、是否达到所需复制/应用进度是不同检查。熔断暂时拒绝调用、半开限制探测、限流和重试预算帮助防止积压扩散；它们不决定旧请求是否已提交。诊断必须保留原请求ID与提交查询通道，不能因熔断而把所有未知请求批量标为失败。

## 分区与路由

网络分区是通信故障，数据分片是键空间分配，二者不能只凭“分区”一词混用。一致性哈希让成员变化时只迁移部分范围，虚拟节点可改善范围分配与异构资源分担，但不能消除单个热点键；Dynamo 的 preference list 还特意排除把同一物理节点的多个虚拟位置算成多个独立副本。[S12](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)（§4.2–4.3）

范围分片方便相邻键扫描却可能集中写热点；哈希分片分散键不等于分散请求，跨分片查询仍有汇聚成本。热点拆分/加盐改变查询与合并方式，局部缓存则需要前述一致性合同。路由更新携带配置版本能识别过期请求，但版本号本身不交接写权；旧节点须拒绝/重定向，迁移必须包含追赶、权威交接与恢复，不能让新旧位置同时无约束受理同一库存写。

## 事务与 Saga

复制组共识决定日志顺序；跨多个独立资源的原子提交是另一个问题。2PC 中参与者进入 prepared 后要持久保留准备状态和承诺，协调者收齐所有同意后持久记录 commit 再通知各方。协调者在决定传播前故障，prepared 参与者可能无法判定 commit还是abort而阻塞；它不能只因超时自行回滚，因为另一参与者可能已经接到commit。[S17](https://www.microsoft.com/en-us/research/wp-content/uploads/2004/01/consensus-on-transaction-commit.pdf)（§2–3）

`PAPER_EXPECTED X1`：初始T的协调者K尚无决定，资源I和S均working，客户端未收到终态。I和S同意后都稳定记录prepared(T)，协调者K持久记录commit(T)，通知I后崩溃，给S的通知未到。I=committed、S=prepared；S若自行abort就破坏统一结果。安全停止点是S保留prepared并查询可恢复的决定证据；K恢复读到commit后重发，S完成commit。把K日志复制可以帮助恢复决定，但不自动解决所有参与者可达性和业务锁等待。

3PC 是另有通信、故障与超时假设的协议族，不能把“多一阶段”写成任意分区下不阻塞的魔法。本篇没有核定一个完整3PC变体，不给可部署参数或通用保证，保留它作为与2PC比较时必须先审模型的术语入口。

Saga 将长过程拆为可交错的本地事务，并显式设计补偿或向前恢复。补偿修正业务含义，不一定把数据库恢复到旧字节状态；后续用户动作可能已经观察或使用先前效果，有些步骤根本没有可接受的逆动作。补偿自身也可能失败，必须记录进度、幂等重试、截止与人工收敛责任。原始Sagas资料本轮只成功取得摘要及关于设计补偿/向前恢复的索引正文，未完整选读其实现算法；以下只是本文有限业务轨迹。[S18](https://www.cs.princeton.edu/techreports/1987/070.pdf)

`PAPER_EXPECTED X2`：初始可用库存5、冻结0、会话名额未分配、流程s无完成步骤记录；各步与流程进度分别随其本地事务持久化，跨库不假设原子。T1以步骤键(s,1)冻结1件，使可用4、冻结1；T2分配会话名额，T3通知客户端。T2若响应丢失、结果未知，应保留原步骤身份(s,2)，查询或按该身份重试核对，不得直接当作“未分配”而补偿T1；在结果仍未知时停止这种自动回滚。只有T2明确失败且确认未分配名额时，记录补偿意图C1=(s,undo1)，C1原子检查步骤键并释放那笔冻结，使可用5、冻结0。另开T2成功、T3通知已被客户端观察的分支，则不能“收回事实”，只能发布取消并使服务端拒绝后续使用。C1响应丢失时仍用原补偿ID查询/重试。若资源损坏或人工条件阻止补偿，状态保持“待修复”，不能仅靠名为Saga的流程把它改成成功。设计要先决定哪些步骤可补偿、哪些不可逆、哪一步之后只能向前恢复。

## 缓存

Cache-aside 在未命中时读权威存储并回填。数据库先写再删缓存是常见安排，但不是线性一致算法。`PAPER_EXPECTED K1`：初始DB v1、cache空；读R查DB得到v1后暂停；写W把DB改成v2并提交，再成功删除cache；R恢复把旧v1写回cache。W完成后的读仍可能命中v1，删除成功也没解决陈旧回填。[S19](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)（§3.2.1）

若采用带代次的填充许可，cache miss给R一个token，失效操作同时使旧token失效，回填时cache验证token并原子决定是否接受；K1中的旧R因此被拒绝：例如R拿到填充token7，W删除时使7失效；R的SET(v1,7)被拒绝，重新获取有效token8并读取DB v2后才能回填(v2,8)。这是需由cache端实现的机制，不能拿普通GET/SET加一个应用内变量冒充。版本拒绝策略也须在空缓存上保留足够的失效代次，单纯比较当前缓存值可能在删除后丢掉防护。强一致读取若无法证明缓存路径，就直接走满足合同的存储读路径。

TTL限制某次写入后缓存保留时长，不证明此前没有陈旧回填或给业务提供统一的新鲜度界。随机抖动可分散同批过期时间，不能保证没有雪崩；singleflight只合并其协调范围内同键并发回源，不提供分布式一致性，多个实例可能各回源一次。布隆过滤器的误判和更新传播要被接受；负缓存要有过期/失效策略，否则新创建对象可能暂时被隐藏。逻辑过期加后台刷新适用于允许陈旧读的接口；刷新失败时仍需陈旧上限和降级决策。缓存始终不能作为“已持久完成”的证据。

## 可观测性

沿R1建立日志字段而不是只写“增加监控”：请求作用域与ID、命令index/term、持久确认集合、commitIndex、lastApplied、响应结果身份、配置ID、outbox/inbox进度和资源端fence代次。trace ID与父子span帮助定位跨层调用，但它不是幂等键或提交证明，采样链路可能缺失。

复制滞后要区分接收、持久化、提交和应用差距；新主term升高却lastApplied落后，可解释为何强读仍需等待。监控选举频率、日志堆积、未知请求年龄、重投次数、待补偿数量和水位线停滞；按区域、操作与结果拆尾延迟。SLO从用户可感知的正确结果和时延定义，错误预算用于明确发布与可靠性取舍；告警必须指向可执行的诊断与停止动作，平均延迟正常不代表恢复正确。

## 安全

本篇的崩溃容错不覆盖拜占庭节点。认证、加密和权限隔离用于限制未授权读写/成员变更；nonce、序列号或有效期只有结合验证状态和身份绑定才能构成防重放措施，不能仅发一个随机数。密钥轮换需要可核对的交接和兼容窗口，审计记录要限制访问并防止未授权篡改；这些是部署审查义务，本篇未执行安全配置或攻击测试。

`PAPER_EXPECTED F1`：外部资源E持久保存maxFence=10、value=100。旧主O持有token10并暂停，其待发命令是value=150；新主N取得11，命令value=200。E原子校验11、更新maxFence为11并执行N的写，稳定保存(11,200)后响应。之后O携带10的晚到写被E拒绝，状态仍为(11,200)。如果E不校验，或只在客户端检查、检查与写之间可穿插换代，旧写仍能覆盖新效果。E尚未见到11且没有向权威锁服务验证时，单凭“10是旧数字”也不会自动知道它已过期；要阻止这一窗口，必须让资源先安装新fence或使用有证明的权威校验/交接协议。[S20](https://www.usenix.org/legacy/events/osdi06/tech/full_papers/burrows/burrows.pdf)（§2.4）

fencing阻止失效角色继续改变资源，不自动去重同一合法代次的重复命令。内部Raft拒绝旧term、客户端用单调钟判断lease和外部E验证写权，是不同责任。调用外部效果后失去回包仍要面对未知结果，按M1选择接收端幂等或恢复核对。

## 测试与演练

先写对象顺序规范与故障模型，再记录调用、返回、参数、结果及故障窗口。线性化检查是在这套规范下寻找合法序；只记录成功请求或删除超时请求会漏掉可能已执行的操作。模型检查可以穷举指定有限状态范围；有限纸面轨迹只能解释选定路径，两者都不能替某个未运行集群出具认证。

原有网络分区、延迟/丢包、进程终止、磁盘满、成员变化、重平衡、时钟异常及压测清单保留为后续部署验收用途，必须在隔离、获准环境中按明确恢复目标执行并归档原始流。本轮没有执行这些操作，也没有把“有实验计划”算成运行证据。Jepsen analyses原入口作为历史阅读导航保留，未引用任何具体产品分析来证明本篇协议或实现。

## 运行手册要点

发布前记录成员/配置、协议与格式版本、稳定日志和快照恢复入口。是否先扩容后缩容须服从具体变更协议：加入尚未追平的投票节点可能提高多数门槛反而损伤进展，不能把操作顺序当成普适安全步骤。缩容前确认所需副本和恢复路径仍满足协议，日志追平只是其中一个条件。

切主或迁移时先核对旧写权如何在资源端失效，再允许新角色承担对应效果；控制面和元数据优先恢复但不得凭旧配置强写。重平衡限并发和带宽，任务可暂停、重试并校验交接结果；跨区流量有预算与告警。异常时保持故障半径受控，保留稳定配置和恢复证据；回滚不能盲目把旧配置文件覆盖到正在运行的新多数上。

RPO描述可接受的数据丢失目标，RTO描述恢复服务目标；是否达到必须依据具体持久化/恢复运行事实，本篇不填写虚构数值。失去多数、决定证据缺失、去重过期、未知外部效果或补偿失败时，手册应写清停止自动动作并由谁核对。

## 典型故障推演

用R1替代没有状态的“超时→重试→幂等”口号：先定位日志是否复制到合法多数，再看提交是否确定、当前读者是否应用，以及原结果记录是否恢复。客户端超时只改变客户端知识，不撤销已经提交的库存命令。

遇到旧主恢复，先区分内部AppendEntries会被较高term拒绝，还是事务外请求仍能到达E；后者由F1决定。遇到消费者已处理但未ACK，由M1检查去重与效果是否同一提交。遇到网络分区，不写成“两边各写、事后随便合并”：本篇Raft路线只有合法多数可决定新条目，失去多数的一侧不能成功接受这些写；恢复时修正未提交后缀，不抹去已提交命令。若业务有意采用多主最终一致，则必须另有明确冲突语义，不能借用R1的保证。

## 性能推导

端到端路径包含排队、通信、执行、持久化与响应，但并行阶段不能全部机械相加。先画依赖关系与等待策略，再找关键路径。`PAPER_EXPECTED L1`：假设同一时刻发出、五个副本确认时间固定为[2,3,8,20,50]ms，无其他排队/故障，任意W=3的确认集合足够，且各确认表示相同持久级别，则复制阶段在第3个确认8ms完成；全等五个则50ms。真实Raft还要满足leader自身持久化、任期、配置和客户端响应条件，不能直接用本算术替代完整时延。

一般等待W个是第W顺序统计量，等全部才是最大值。若n条独立同分布支路都必须完成，单支路CDF为F(t)，则全部完成的概率是F(t)^n；在这个明确模型下增加支路会使尾部变差。若只等第一个，分布变为1−(1−F(t))^n；若支路完全相关，二式的独立假设失效。增加副本同时改变多数门槛、路由、资源争用或故障相关性时，不能普遍断言尾延迟随副本数上升或下降。

批量减少每条消息的固定开销，却可能增加排队等待和失败时重做范围；压缩节省网络流量但增加CPU工作；局部缓存和读写分离可改变路径但引入新鲜度责任。以上是选型的因果问题，本轮没有吞吐、P99、跨区成本或容量实测。

## 术语对照

| 术语 | 本文的可操作含义 |
| --- | --- |
| 副本 | 同一逻辑数据的一份拷贝；只有明确持久化的副本才承担相应恢复承诺 |

| 补偿 | 用新业务动作修正已发生的效果，不保证回到旧状态或必然成功 |
| 水位线 | 按输入合同建立的事件时间进度/估计，不是所有输出已持久完成 |
| 脑裂 / 重平衡 | 角色认知或写权出现分叉 / 数据与负载重新分配；二者需要不同恢复动作 |

## 反模式

- 把超时等同未执行，换新ID重做；或只存ID不存可恢复终态
- 无截止/无预算重试，把短暂过载放大成不可恢复积压
- 用R+W>N推出线性一致，或用多数内存ACK代替稳定提交
- 以旧term日志的多数副本直接推进Raft提交，或在应用前返回业务结果
- 本地leader自信、任意历史心跳或未证明的lease直接支持强读
- 只在应用侧检查fencing token，随后无保护地写外部资源
- outbox/inbox记录与效果分开提交，却宣称全链路exactly-once
- 先写DB再删cache后，忽略暂停读者的陈旧回填
- 由Lamport大小逆推出因果，或对不完整日志声称完整并发证明
- 只看平均复制滞后、混用副本数与等待数、无回滚地并发变更成员和迁移数据

## 最小实验清单

本轮最小验证是上面的完整纸面轨迹及其反例，不包含运行。后续若要为一个具体实现升级证据，应固定实现revision、存储假设、客户端历史格式、初始快照与恢复方法，再在隔离环境逐项执行原有练习：三节点Raft任期/日志、AppendEntries丢失、重启恢复、成员加入退出、快照安装、至少一次消费者与去重保留期、重复库存命令、单调计时与lease前提、同区/跨区复制及线性化历史检查。

每项预先声明断言、负向控制和安全停止/恢复方式，保存所有失败、超时、原始操作历史与实际环境。未来对比同步与异步复制的P99时，还需固定负载分布、并发、持久级别、等待策略与故障相关性，说明两组成功响应分别承诺什么，再按同一端到端口径测量；本轮没有执行该比较。未来计划不填补当前语义论证，也不把未执行的清单标成已完成。

## 交付前审查

- 是否从调用、持久状态、提交、应用一直追到响应与下游效果，而不是在中间一层停止
- 是否区分对象一致性、CAP可用性、条件活性与业务SLO
- 是否明确失败/重试的身份、并发判定、保留期与原终态复用
- 是否核对读的权威与应用前缀，并识别缓存和落后副本的反例
- 是否在资源接收端验证写权，说明尚未安装新代次的窗口
- 是否有配置/快照/补偿的恢复与停止责任，并保留格式兼容窗口
- 是否将纸面推导、原始资料选读和实际运行证据分开，未把他人论文实验当成本库实测

## 复盘问题

最早观察到的是丢失响应、复制滞后还是提交停滞？哪个假设首先不再成立？重试是否创建了新身份或扩大负载？恢复时谁能证明原决定，谁只是在猜测？是否丢掉去重、fence或配置状态？某个补偿是否被误写成必然可逆？应自动化的步骤能否在未知结果时安全停止？这些答案决定修复协议、部署还是运行手册，不能全部归因于“网络不好”。
